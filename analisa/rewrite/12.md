Lanjut. Sekarang kita turun ke **Platform Android + FBE + Multi-user + SELinux**. Ini layer yang membuat core engine yang tadi kita desain benar-benar cocok dengan Android, bukan sekadar Linux daemon generik.

Saya juga cek ulang dokumentasi AOSP terbaru: Android modern menggunakan FBE, dengan pemisahan **CE (Credential Encrypted)** dan **DE (Device Encrypted)** per user; perangkat yang diluncurkan dengan Android 10+ wajib menggunakan FBE, sementara Android 9 masih merupakan masa transisi dan FDE masih relevan pada perangkat lama. ([Android Open Source Project][1])

# 1. Jangan masukkan path Android ke core engine

Kesalahan arsitektur yang ingin kita hindari:

```rust
if path.starts_with("/data/user/0/") {
    ...
}
```

di dalam:

```text
Safety
Policy
Planner
Executor
```

Android path adalah **platform knowledge**.

Jadi:

```text
                 Generic Core
                      │
                      │ Platform abstraction
                      ▼
               AndroidPlatform
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
        Users        FBE       SELinux
```

Core tidak perlu tahu detail Android.

# 2. Platform abstraction

```rust
pub trait Platform {

    fn runtime_state(&self) -> Result<RuntimeState>;
    fn filesystem_info(&self, path: &Path) -> Result<FilesystemInfo>;

```

Implementasi Android:

```rust
pub struct AndroidPlatform {
    ...
}
```

Core hanya memanggil:

```rust

```

bukan:

```rust
Command::new("pm")
```

di seluruh codebase.

# 5. Android multi-user bukan sekadar `/data/user/0`

AOSP mendokumentasikan path per-user seperti:

```text
/data/user/{userId}
/data/media/{userId}
/storage/emulated/{userId}
```

dan juga `/data/user_de/{userId}` untuk DE storage. ([Android Open Source Project][1])

Maka Target Catalog harus dibangun berdasarkan:

```text
UserId
+
StorageDomain
+
TargetKind
```

bukan hard-code:

```text
/data/user/0
```

sedangkan:

Dan:


# 7. CE dan DE harus diperlakukan berbeda

Pada FBE:

```text
DE
    tersedia setelah boot/Direct Boot

CE
    baru tersedia setelah user unlock
```

AOSP secara eksplisit menyatakan bahwa CE storage hanya tersedia setelah user unlock, sementara DE tersedia selama Direct Boot. ([Android Open Source Project][1])

Maka:

```text
CE locked
    ↓
do not touch
```

bukan:

```text
CE locked
    ↓
try anyway
```

# 8. Jangan mengandalkan "permission denied" sebagai FBE detection

Ini penting.

Jangan:

```rust
match access(path) {
    Err(_) => assume_locked(),
}
```

Karena:

```text
permission denied
```

bisa berarti:

```text
SELinux
Unix permissions
wrong owner
path missing
CE locked
mount issue
```

Jadi encryption state harus berasal dari:

```text
platform encryption state
```

sedangkan filesystem error hanya menjadi evidence tambahan.

# 9. `StorageState`

Model yang lebih lengkap:

```rust
pub struct StorageSnapshot {
    pub domain: StorageDomain,
    pub availability: StorageAvailability,
}
```

Dengan:

```rust
pub enum StorageAvailability {
    Available,
    Locked,
    Unmounted,
    Unknown,
}
```

Contoh:

```text
User 0
CE → Available

User 10
CE → Locked

User 0
DE → Available
```

Maka scanner bisa memilih target:

```text
UserCe(0) → scan
UserCe(10) → skip
UserDe(10) → scan jika policy mengizinkan
```

# 10. Multi-user policy

Jangan otomatis membersihkan semua user hanya karena daemon Root.

Ada tiga pilihan:

```rust
pub enum UserScope {
    Current,
    Active,
    AllUnlocked,
    Explicit(Vec<UserId>),
}
```

Untuk automatic cleanup saya lebih menyukai:

```text
Active / eligible users
```

daripada:

```text
All users
```

karena background cleanup lintas user dapat menjadi sangat mahal.

Untuk manual deep:

```text
--all-users
```

bisa menjadi explicit capability jika memang diperlukan.

# 11. Work profile

Work profile bukan sekadar directory lain.

AOSP menjelaskan bahwa work profile mempunyai DE dan CE key sendiri; satu user yang unlocked tidak berarti semua user/profile unlocked. ([Android Open Source Project][1])

Jadi jangan:

```text
user 0 unlocked
    ↓
all CE unlocked
```

Ini salah.

Harus:

```text
User 0
    CE = unlocked

Work profile 10
    CE = locked
```

maka:

```text
UserCe(0) → eligible
UserCe(10) → blocked
```

# 14. Package identity

Jangan percaya nama directory sepenuhnya.

Misalnya:

```text
/data/user/0/com.example.foo
```

tidak otomatis berarti:

```text
package = com.example.foo
```

Pada target yang memerlukan assurance lebih tinggi, kita bisa memakai:

```rust
pub trait PackageResolver {
    fn resolve(
        &self,
        user: UserId,
        package: &PackageName,
    ) -> Result<PackageIdentity>;
}
```

Dengan:

```rust
pub struct PackageIdentity {
    pub package: PackageName,
    pub uid: Option<u32>,
    pub user: UserId,
}
```

Kemudian target dapat dikaitkan dengan identity.

---

# 15. Mengapa package identity berguna?

Misalnya directory:

```text
/data/user/0/com.example.foo/cache
```

sudah ada.

Tetapi package:

```text
com.example.foo
```

telah dihapus/reinstalled.

Directory stale mungkin tetap ada.

Kita tidak boleh langsung menyimpulkan:

```text
directory name valid
    ↓
safe to delete
```

Policy dapat membuat:

```text
package missing
    ↓
UnknownPackage
    ↓
reject/defer
```

Untuk conservative profile, saya akan default reject.

---

# 16. Jangan membuat PackageResolver wajib untuk semua target

Ada tradeoff.

Jika setiap candidate harus melakukan package lookup:

```text
10.000 files
    ↓
10.000 package lookups
```

akan buruk.

Lebih baik resolve sekali di TargetRoot:

```text
TargetRoot
    ↓
PackageIdentity
    ↓
many candidates
```

Jadi:

```text
package resolution
```

adalah target-level operation.

---

# 17. SELinux

SELinux di Android bukan sekadar permission tambahan.

Android menggunakan SELinux MAC untuk membatasi domain process terhadap file/object berdasarkan security context. AOSP menjelaskan bahwa file dan process mempunyai label/context dan policy menentukan aksesnya. ([Android Open Source Project][2])

Jadi:

```text
Unix permission
+
SELinux
```

adalah dua layer berbeda.

---

# 18. Jangan mencoba "memperbaiki" SELinux dari cleaner

Ini sangat penting.

Kalau:

```text
unlink()
    ↓
EACCES
```

jangan:

```text
changecon
chmod
chown
restorecon
```

secara otomatis untuk memaksa delete.

Cleaner bukan policy repair daemon.

Failure harus menjadi:

```text
PermissionDenied
```

atau:

```text
SelinuxDenied
```

dan dilaporkan.

---

# 19. SELinux context sebagai diagnostic

Kita bisa memiliki:

```rust
pub struct SecurityContext {
    pub label: Option<String>,
}
```

Untuk diagnostics:

```text

    /data/user/0/foo/cache

```

Tetapi jangan membuat deletion bergantung pada string label jika tidak diperlukan.

# 20. Security context bukan pengganti path safety

# 24. Android 9 legacy FDE

Karena target rewrite ingin mendukung Android 9, kita tidak boleh menganggap:

```text

```

AOSP menyatakan FDE masih dapat ada pada perangkat lama yang diluncurkan dengan Android 9 atau lebih rendah; perangkat baru Android 10+ menggunakan FBE. ([Android Open Source Project][3])

Tetapi jangan sampai compatibility layer membuat core menjadi rumit.

# 26. `/data/media` dan `/storage/emulated`

Ini area yang saya sarankan **tidak menjadi default cache target**.

AOSP membedakan `/data/media/{userId}` sebagai user media storage dan `/storage/emulated/{userId}` sebagai shared internal storage view. ([Android Open Source Project][1])

Cleaner tidak boleh berpikir:

```text
storage penuh
    ↓
hapus /storage/emulated/0/*
```

Itu bukan cache cleaning.

Jadi Target Catalog:

```text
SharedUserStorage
    → disabled by default
```

dan jika suatu hari ingin membersihkan `.thumbnails` atau cache spesifik:

```text
explicit TargetKind
explicit root
explicit policy
```

bukan generic shared storage cleanup.

---

# 27. Adoptable storage

Android 9+ mendukung FBE bersama adoptable storage. AOSP menyebut adoptable storage memiliki struktur yang mirip internal storage dan mendukung isolasi multi-user. ([Android Open Source Project][4])

Jadi jangan hard-code:

```text
/data/...
```

sebagai satu-satunya storage.

Tetapi juga jangan otomatis scan:

```text
/mnt/expand/*
```

hanya karena ditemukan.

Harus:

```text
detect mounted volume
    ↓
classify storage
    ↓
validate filesystem
    ↓
TargetCatalog
    ↓
policy
```

---

# 28. External storage default deny

Untuk rewrite pertama:

```text
External
    → not automatic cleanup
```

Alasannya sederhana:

```text
removable media
mount/unmount
different filesystem
user content
permissions
multi-user mapping
```

membuat risk jauh lebih tinggi.

Kita bisa menambah dukungan nanti setelah internal storage stabil.

Ini penting.

Jangan:

```text

    ↓
```

# 37. Tetapi FD jangan hidup selamanya

Jangan membuat daemon menyimpan ribuan directory FD selama berjam-jam.

TargetRoot dapat menyimpan:

```text
identity
display path
target metadata
```

dan FD dibuka:

```text
at execution/scanning boundary
```

atau menggunakan scoped handle.

Jadi ada tradeoff:

```text
FD lifetime short
+
identity revalidation
```

lebih scalable.

# 38. Platform invariant

Saya akan menetapkan:

```text
1. Core never parses Android paths for semantic meaning.

2. User IDs come from platform discovery.

3. CE/DE state is explicit.

4. Locked CE is never touched.

5. One unlocked user does not imply all users are unlocked.

6. Package identity is resolved at target level when required.

7. Shared user storage is not automatically treated as cache.

8. External/adoptable storage is opt-in.

9. SELinux denial is failure/diagnostic, not something cleaner repairs.

10. Android version checks are centralized.

11. Capability detection is separate from version detection.

12. Platform adapters never expose arbitrary shell execution.
```

## Berikutnya: `Config + Target Policy + Profiles`

Setelah platform, bagian yang paling tepat berikutnya adalah **mendesain configuration system secara konkret**.

Kita akan menentukan:

```text
config.toml
    ↓
parse
    ↓
schema
    ↓
validation
    ↓
immutable Config
    ↓
Profile::Conservative / Normal / Deep
    ↓
TargetPolicy
    ↓
PolicyEngine
```

Termasuk membahas **mana setting yang boleh dikonfigurasi user dan mana yang HARUS hard-coded sebagai security invariant**, bagaimana format `config.toml`, default yang aman, migration antar versi config, atomic reload, per-target age/size budget, exclusion rules, dan bagaimana mencegah config menjadi jalan untuk mematikan safety.
