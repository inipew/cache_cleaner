Lanjut. Sekarang kita masuk ke **Safety Engine**. Ini sebenarnya jantung keamanan `cache_cleaner`: scanner boleh salah klasifikasi, policy boleh konservatif, tetapi **tidak boleh ada jalur yang memungkinkan target berbahaya sampai ke executor**.

Repo saat ini sudah memiliki beberapa fondasi yang bagus—`fstatat` tanpa mengikuti symlink, `st_dev` boundary, multi-user/FBE awareness, serta RBAC IPC. Pada rewrite, semuanya sebaiknya dipusatkan menjadi satu model safety yang eksplisit.

# 50. Safety Engine Bukan Policy Engine

Kita harus benar-benar memisahkan dua konsep:

```text
SAFETY
= "Apakah secara teknis aman untuk menyentuh ini?"

POLICY
= "Apakah user/system menginginkan kita menyentuh ini?"
```

Contoh:

```text
/data/user/0/com.foo/cache/a.tmp
```

Safety:

```text
trusted root       ✓
regular file       ✓
same filesystem    ✓
not symlink        ✓
valid user         ✓
```

Maka:

```text
Safety = SAFE
```

Tetapi policy bisa mengatakan:

```text
age < 3 days
```

sehingga:

```text
Policy = REJECT
```

Jadi:

```text
Safety PASS
+
Policy REJECT
=
JANGAN HAPUS
```

Sebaliknya:

```text
Safety FAIL
+
Policy ALLOW
=
TETAP JANGAN HAPUS
```

Ini invariant yang sangat penting.

# 51. Urutan Safety Pipeline

Saya akan membuat pipeline:

```text
Candidate
   │
   ▼
Boundary Validation
   │
   ▼
Target Validation
   │
   ▼
Identity Validation
   │
   ▼
Filesystem Validation
   │
   ▼

   │
   ▼
```

```rust
pub fn validate_candidate(

```

Tetapi di dalamnya jangan menjadi satu fungsi 500 baris.

# 52. `SafetyDecision`

Saya sarankan:

```rust
pub enum SafetyDecision {
    Safe(SafetyProof),
    Reject(SafetyViolation),

```

Bukan:

```rust
bool
```

Karena:

```rust
false
```

tidak menjelaskan kenapa.

Sedangkan:

```rust
SafetyDecision::Reject(
```

* `explain`

* metrics
* testing

# 53. Safety Proof

Bagian ini menarik.

Kalau target sudah lolos seluruh hard safety check, kita dapat object:

```rust
pub struct SafetyProof {
    pub root: RootIdentity,
    pub entry: EntryIdentity,
    pub device: DeviceId,
    pub file_type: SafeEntryType,
}
```

Kemudian:

```rust
Candidate
```

tidak langsung berubah menjadi operation.

Harus:

```text
Candidate
    ↓
SafetyProof
    ↓
PolicyDecision
    ↓
Plan
```

# 54. Type-State Security

Kalau ingin rewrite ini benar-benar kuat secara Rust, kita bisa menggunakan type-state.

Contohnya:

```rust
pub struct Candidate {
    // untrusted
}

pub struct SafetyValidated {
    // hard safety passed
}

pub struct PolicyApproved {
    // policy passed
}

pub struct PlannedOperation {
    // plan generated
}

pub struct AuthorizedOperation {
    // authorized to execute
}
```

Sehingga API:

```rust
pub fn validate(
    candidate: Candidate,
) -> Result<SafetyValidated>;
```

kemudian:

```rust
pub fn evaluate(
    candidate: SafetyValidated,
    policy: &Policy,
) -> Decision;
```

kemudian:

```rust
pub fn plan(
    candidate: PolicyApproved,
) -> PlannedOperation;
```

dan:

```rust
pub fn authorize(
    operation: PlannedOperation,
) -> AuthorizedOperation;
```

Executor:

```rust
pub fn execute(
    operation: AuthorizedOperation,
);
```

Tidak ada:

```rust
execute(Candidate)
```

secara tipe.

Ini jauh lebih bagus daripada hanya mengandalkan programmer untuk mengingat urutannya.

# 55. Trusted Root

Safety pertama:

```text
Apakah entry masih berada di dalam root yang dipercaya?
```

Misalnya:

```text
TrustedRoot:
    /data/user/0/com.foo/cache
```

Candidate:

```text
foo/bar.tmp
```

maka:

```text
root
 └── foo
      └── bar.tmp
```

boleh dipertimbangkan.

Tetapi:

```text
../../system/important
```

langsung:

```text
REJECT
```

# 56. Root Itu Bukan String

Jangan:

```rust
pub struct TrustedRoot {
    pub path: String,
}
```

Lebih baik:

```rust
pub struct TrustedRoot {
    directory: DirectoryFd,
    identity: RootIdentity,
    kind: TargetKind,
}
```

Path boleh disimpan untuk:

```text
logging
diagnostics
display
```

tetapi bukan sebagai security primitive utama.

# 57. Root Identity

Ketika root dibuka:

```text
open root
    ↓
fstat
    ↓
device
inode
mode
```

Simpan:

```rust
pub struct RootIdentity {
    pub dev: u64,
    pub ino: u64,
}
```

Kemudian sebelum operasi:

```text
fstat(root_fd)
        ↓
compare identity
```

Jika root sudah berubah:

```text
Reject(RootChanged)
```

# 58. Device Boundary

Salah satu property yang wajib dipertahankan dari desain repo sekarang adalah `st_dev` enforcement.

Misalnya:

```text
/data
  dev=100

/data/user/0/com.foo/cache
  dev=100
```

Aman.

Tetapi:

```text
cache/mounted_volume
  dev=200
```

jangan otomatis traversal.

Safety:

```rust
if entry.dev != root.dev {
    return Reject(CrossDevice);
}
```

Ini mencegah cleaner mengikuti filesystem lain yang kebetulan dipasang di bawah target.

---

# 59. Mount Boundary

Ini lebih dalam daripada sekadar symlink.

Contoh:

```text
cache/
└── strange/
      ↓
   mounted filesystem
```

Path masih terlihat:

```text
cache/strange
```

tetapi sebenarnya boundary filesystem sudah berubah.

Jadi:

```text
same path
≠
same filesystem object
```

Makanya `st_dev` harus diperiksa pada traversal.

Untuk versi awal, saya bahkan lebih memilih:

```text
different st_dev → skip/reject subtree
```

daripada mencoba memahami semua jenis mount Android.

# 60. File Type

Safety layer harus punya daftar explicit:

```rust
pub enum SafeEntryType {
    RegularFile,
    Directory,
}
```

Perhatikan: saya sengaja **tidak** memasukkan `Symlink`.

Jadi untuk menjadi `SafeEntryType`, entry harus melewati:

```text
regular file
atau
directory
```

Sedangkan:

```text
symlink
socket
fifo
block device
char device
unknown
```

tidak punya representasi `SafeEntryType`.

Ini contoh bagus penggunaan type system untuk safety.

# 61. Symlink = Hard Deny

Jangan punya config:

```toml
follow_symlinks = true
```

untuk cleanup privileged.

Saya akan menganggap:

```text
Symlink
    ↓
hard deny
```

selamanya.

Kalau suatu saat memang ada kebutuhan khusus untuk symlink, buat operasi baru dengan security model berbeda. Jangan mengubah behavior cleaner utama.

# 62. Broken Symlink

Broken symlink:

```text
foo -> /does/not/exist
```

juga tetap:

```text
REJECT
```

Jangan berpikir:

> target-nya tidak ada, jadi aman dihapus.

Karena object yang ada tetap symlink.

# 63. Identity Validation

Misalnya scanner menemukan:

```text
inode=123
dev=100
```

Ketika executor ingin menghapus:

```text
current inode=456
dev=100
```

berarti object telah berubah.

Maka:

```text
REJECT
```

dengan:

```rust
pub enum SafetyViolation {
    ChangedSinceScan,
}
```

Jangan menghapus object baru hanya karena path-nya sama.

# 64. Tapi Ada Nuansa: Inode Bisa Reuse

Identity:

```text
dev + inode
```

berguna, tetapi bukan magic.

Filesystem dapat menggunakan kembali inode setelah object dihapus.

Karena itu kita tetap memerlukan:

```text
FD-relative lookup
+
NOFOLLOW
+
identity check
+
immediate validation
```

Bukan hanya:

```text
inode == old_inode
```

Security berasal dari kombinasi beberapa layer.

# 65. User Validation

Karena Android memiliki multi-user/storage domain, `user_id` harus menjadi bagian dari target identity.

Misalnya:

```rust
pub struct UserScope {
    pub user_id: u32,
}
```

Jangan hanya:

```rust
package = "com.foo"
```

Karena:

```text
user 0 / com.foo
user 10 / com.foo
```

adalah target berbeda.

Maka:

```rust
pub struct AppTarget {
    pub user_id: UserId,
    pub package: PackageName,
}
```

# 66. Package Name Jangan Dipercaya dari Path Saja

Misalnya:

```text
/data/user/0/com.foo/cache
```

terlihat seperti package.

Tetapi filesystem name:

```text
com.foo
```

tidak otomatis membuktikan bahwa itu package Android yang valid.

Untuk conservative mode:

```text
unknown package identity
→ reject
```

atau gunakan `PlatformPackageResolver` untuk validasi.

Contoh:

```rust
pub trait PackageResolver {
    fn resolve(
        &self,
        user: UserId,
        package: &PackageName,
    ) -> Result<PackageIdentity>;
}
```

# 67. FBE / Storage State

Ini juga harus berada di safety layer, bukan hanya scheduler.

Contoh:

```text
Credential Encrypted storage
```

ketika user belum unlock.

Scheduler mungkin mengatakan:

```text
screen off
thermal normal
battery good
```

tetapi safety mengatakan:

```text
CE storage locked
→ tidak boleh disentuh
```

Jadi:

```text
Scheduler = boleh mulai?
Safety = boleh menyentuh target?
```

dua pertanyaan berbeda.

# 68. Runtime Safety Context

```rust
pub struct SafetyContext {

    pub filesystem: FilesystemSnapshot,
```


dan:


# 69. Safety Tidak Sama dengan Scheduler

Misalnya:

```text
screen ON
```

Untuk policy background cleanup:

```text
DEFER
```

Tetapi bukan:

```text
SAFETY VIOLATION
```

Karena target tetap aman; hanya kondisi runtime tidak sesuai.

Maka saya sarankan safety memiliki dua kategori:

```rust
pub enum SafetyResult {
    Safe,
    Unsafe(SafetyViolation),
    TemporarilyUnavailable(AvailabilityReason),
}
```

Dengan:

```text
Unsafe
    = hard deny

TemporarilyUnavailable
    = boleh dicoba lagi nanti
```

Ini sangat berguna untuk scheduler.

# 70. Risk Level

Setelah hard validation, kita bisa memberi risk:

```rust
pub enum RiskLevel {
    Low,
    Medium,
    High,
}
```

Contoh:

```text
AppCache
→ Low

AppCodeCache
→ Medium

FrameworkCache
→ High
```

Risk **tidak boleh override safety**.

Misalnya:

```text
Risk = Low
```

tidak berarti:

```text
Safety = Allow
```

Risk hanya input tambahan untuk policy/planner.

# 71. Safety Rules Harus Immutable

Saya ingin struktur seperti:

```rust
pub struct SafetyPolicy {

```

tetapi idealnya sebagian besar tidak berasal dari config.

Misalnya:

```rust

    }
```

```rust

```

Secara dependency:

```text

   ↓

   ↓
SafetyPolicy
```

bukan:

```text
Config
   ↓
SafetyPolicy
```

# 80. Setelah Ini, Baru Policy Engine

Jadi sekarang tiga komponen fundamental sudah kita punya:

```text
1. Target Catalog
   "Apa yang kita kenal?"

2. Filesystem Engine
   "Bagaimana menyentuh filesystem dengan aman?"

3. Safety Engine
   "Apakah object ini secara hard security boleh disentuh?"
```

Komponen berikutnya:

```text
4. Policy Engine
   "Apakah object yang aman ini memang layak dibersihkan sekarang?"
```

Di bagian itu kita bisa membangun **rule evaluation system** yang tidak menjadi spaghetti `if/else`, termasuk:

```text
age rule
size rule
target rule
user rule
storage rule
filesystem rule
runtime rule
budget rule
profile rule
```

dan terutama bagaimana membuat hasil akhirnya **explainable**, misalnya:

```text
ALLOW
because:
  target = AppCache
  age = 14d >= 7d
  size = 183MB
  runtime = idle
  storage = available

REJECT
because:
  age = 2h < 7d

DEFER
because:
  screen = ON
```

Itu yang akan kita desain berikutnya sebelum masuk ke Planner.
