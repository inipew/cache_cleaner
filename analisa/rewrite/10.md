Lanjut. Sekarang kita masuk ke **Scheduler + Daemon State Machine**. Ini yang mengubah kumpulan scanner/executor menjadi daemon Android yang benar-benar hidup, tidur, bangun karena event, membatalkan pekerjaan saat kondisi berubah, dan tetap predictable.

Saya sarankan **Scheduler menjadi otak waktu/keadaan**, tetapi **bukan otak cleanup**.

---

# 1. Tanggung jawab Scheduler

Scheduler hanya menjawab:

> **“Kapan job boleh berjalan, kapan harus berhenti, kapan boleh dilanjutkan, dan kapan harus dicoba lagi?”**

Bukan:

> “File apa yang harus dihapus?”

Itu sudah menjadi tanggung jawab:

```text
Scanner  → menemukan
Safety   → memvalidasi
Policy   → memutuskan
Planner  → membuat plan
Executor → mengeksekusi
```

Scheduler berada di atas semuanya:

```text
                    Scheduler
                       │
         ┌─────────────┼─────────────┐
         ↓             ↓             ↓
      Scanner       Planner       Executor
```

# 2. Daemon State Machine

Saya akan menggunakan explicit state machine.

Minimal:

```rust
pub enum DaemonState {
    Starting,
    Idle,
    Preparing,
    Scanning,
    Planning,
    Cleaning,
    Paused,
    Stopping,
    Failed,
}
```

Tetapi state `Paused` perlu alasan:

```rust
pub enum PauseReason {
    ScreenOn,
    UserActive,
    Thermal,
    Battery,
    StorageUnavailable,
    CredentialStorageLocked,
    SystemBusy,
}
```

Jadi bukan sekadar:

```text
Paused
```

melainkan:

```text
Paused(ScreenOn)
Paused(Thermal)
Paused(StorageUnavailable)
```

Ini sangat membantu `status` dan diagnostics.

# 3. State transition harus eksplisit

Jangan menyebarkan:

```rust
self.state = ...
```

ke seluruh codebase.

Buat satu tempat:

```rust
pub struct DaemonStateMachine {
    state: DaemonState,
}
```

dan:

```rust
impl DaemonStateMachine {
    pub fn transition(
        &mut self,
        event: DaemonEvent,
    ) -> Result<StateTransition, StateError> {
        ...
    }
}
```

Contoh:

```text
Idle + StartCleanup
    → Preparing

Preparing + PreparationComplete
    → Scanning

Scanning + ScanComplete
    → Planning

Planning + PlanReady
    → Cleaning

Cleaning + JobComplete
    → Idle
```

# 4. Event-driven, bukan polling loop

Ini salah satu hal yang perlu dipertahankan dari desain lama.

Jangan:

```rust
loop {
    check_screen();
    check_thermal();
    check_storage();
    check_timer();
    sleep(Duration::from_secs(5));
}
```

Masalahnya:

* latency
* wakeup tidak perlu
* CPU waste
* response terhadap screen-on tidak deterministik
* banyak race kecil
* sulit scaling event source

Lebih baik:

```text
             epoll
               │
       ┌───────┼────────┐
       ↓       ↓        ↓
    timerfd  signalfd  uevent
       │       │        │
       └───────┼────────┘
               ↓
          SystemEvent
               ↓
        State Machine
```

# 7. Event loop

Core event loop kira-kira:

```rust
loop {
    let events = event_loop.wait()?;

    for event in events {
        scheduler.handle(event)?;
    }

    scheduler.run_ready_work()?;
}
```

Tetapi ada satu prinsip penting:

> **Event handler jangan melakukan cleanup berat.**

Jangan:

```rust
handle_screen_off() {
    run_full_cleanup();
}
```

Event handler hanya mengubah state / membuat command menjadi ready.

# 12. Scheduler tick

Timer tidak berarti:

```text
timer fires → cleanup immediately
```

Timer hanya berarti:

```text
timer fires
    ↓
evaluate readiness
    ↓
if ready → schedule job
if blocked → remain idle/paused
```

Contoh:

```text
02:00
 ↓
timer event
 ↓
screen ON
 ↓
don't start
 ↓
wait for next relevant event
```

Kalau user kemudian mematikan layar:

```text
screen OFF
 ↓
event
 ↓
scheduler reevaluates
 ↓
ready
 ↓
start job
```

Ini jauh lebih efisien daripada menunggu timer berikutnya.

# 13. Cancellation semantics

Ini perlu dibedakan:

```text
Pause
Cancel
Stop
```

### Pause

Pekerjaan mungkin dilanjutkan.

```text
Cleaning
   ↓
Paused(ScreenOn)
   ↓
Resume
   ↓
Cleaning
```

### Cancel

Job dibatalkan dan harus membuat plan baru jika ingin berjalan lagi.

```text
Cleaning
   ↓
Cancelled
   ↓
Idle
```

### Stop

Daemon sendiri dimatikan.

```text
Any state
   ↓
Stopping
   ↓
exit
```

# 14. Untuk cleanup saya lebih suka cancel daripada pause

Secara teknis kita bisa membuat resume dari tengah plan.

Tetapi filesystem berubah selama pause.

Contoh:

```text
Plan:
1000 files
```

Setelah 300 file:

```text
screen ON
```

Pause.

Lalu 30 menit kemudian:

```text
screen OFF
```

Selama itu aplikasi mungkin sudah:

```text
create new files
delete old files
rename directories
```

Plan lama sudah stale.

Jadi default saya:

```text
runtime interruption
    ↓
cancel current job
    ↓
return Idle
    ↓
rescan
    ↓
build fresh plan
```

Ini lebih aman daripada resume stale plan.

# 18. Hanya satu cleanup job

Untuk versi pertama saya sangat merekomendasikan:

```text

```

Jangan langsung membuat:


* budget lebih sulit
* reporting lebih sulit

# 21. `clean` manual vs automatic

Manual cleanup dan scheduled cleanup sebaiknya menggunakan engine yang sama.

Jangan:

```text
automatic cleanup
    → new implementation

manual clean
    → another implementation
```

Harus:

```text
manual command
      ↓
JobRequest
      ↓
same Scanner
same Safety
same Policy
same Planner
same Executor
```

Perbedaannya hanya:

```rust
JobTrigger::Automatic
JobTrigger::Manual
```

# 23. Thermal handling

Thermal state harus mempengaruhi Scheduler.

Misalnya:

```rust
pub enum ThermalState {
    Normal,
    Warm,
    Hot,
    Critical,
    Unknown,
}
```

Policy Scheduler:

```text
Normal
    → full eligible

Warm
    → mungkin allowed dengan reduced budget

Hot
    → pause/cancel

Critical
    → immediate cancellation
```

Detail threshold sebaiknya configurable dalam batas yang masuk akal, tetapi `Critical` harus selalu fail-safe.

# 40. Satu perubahan desain yang saya rekomendasikan

Setelah melihat keseluruhan pipeline, saya justru akan menyederhanakan:

```text
Paused
```

menjadi **scheduler condition**, bukan job state utama.

Jadi:

```text
DaemonState = Idle
RuntimeConditions = {
    screen: On,
    thermal: Normal,
}
Readiness = Blocked(ScreenOn)
```

lebih baik daripada:

```text
DaemonState = Paused(ScreenOn)
```

Kenapa?

Karena daemon sebenarnya tidak sedang melakukan sesuatu yang perlu “dipause”. Ia hanya:

```text
Idle + not eligible
```

Sedangkan kalau **job aktif** lalu screen-on:

```text
JobState = Cancelling
```

kemudian:

```text
JobState = Cancelled
DaemonState = Idle
```

Ini menghasilkan model yang lebih sederhana.

# 41. Prinsip akhir Scheduler

Saya akan tulis sebagai invariant:

```text
1. Scheduler never deletes files.

2. Scheduler never creates cleanup operations.

3. Scheduler owns daemon lifecycle.

4. Scheduler owns job admission.

5. Runtime events become typed SystemEvents.

6. Global unsafe conditions trigger cancellation.

7. Cancelled jobs are rebuilt from a fresh scan.

8. Only one cleanup job runs at a time.

9. Invalid configuration never replaces valid configuration.

10. Shutdown is graceful and bounded.

11. Unknown runtime conditions fail closed for destructive work.

12. Manual and automatic cleanup use the same pipeline.
```

Dengan ini kita sudah mempunyai empat lapisan besar yang sangat jelas:

```text
DECISION PIPELINE
    Scanner
    Safety
    Policy
    Planner

EXECUTION PIPELINE
    Authorization
    Executor
    Verifier

CONTROL PLANE
    Scheduler
    State Machine
    Job Controller

RUNTIME
    epoll
    timerfd
    signalfd
    uevent
    UDS
    locks
```

**Tahap berikutnya yang paling penting adalah `IPC + Authorization + Protocol`**, karena sekarang kita perlu mendesain bagaimana `cleaner status`, `cleaner clean`, `reload`, `stop`, `explain`, dan request dari Root/System/Shell masuk ke daemon tanpa membuat IPC menjadi jalur bypass terhadap Safety/Policy/Planner. Kita juga perlu menentukan format protocol, request/response ID, timeout, `SO_PEERCRED`, RBAC, capability per command, dan bagaimana `cleaner clean --deep --trim --zram` diterjemahkan menjadi `JobRequest` tanpa memberikan client akses langsung ke Executor.
