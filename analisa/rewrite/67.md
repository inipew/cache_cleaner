67.md — Job Lifecycle, Attempt State Machine, Transition Rules, Recovery, Cancellation, Timeout, Reconciliation, and Terminal-State Contract

Tujuan

Dokumen ini mendefinisikan lifecycle Job secara formal agar Scheduler, Worker, Planner, Authorization, Executor, Verifier, Recovery, Persistence, dan IPC tidak mempunyai interpretasi state yang berbeda.

Job bukan sekadar fungsi asynchronous yang berjalan dari awal sampai selesai. Job adalah durable unit of work yang mempunyai identity, configuration generation, policy context, plan, authorization, attempts, operations, resource reservations, outcome, dan audit trail.

Prinsip utama:

- state transition harus explicit
- transition harus deterministic
- illegal transition harus ditolak
- durable state harus dipersist sebelum dipublikasikan sebagai fakta
- terminal state tidak boleh diam-diam berubah
- UNKNOWN outcome tidak boleh diperlakukan sebagai FAILED
- cancellation tidak otomatis berarti mutation berhasil dihentikan
- timeout tidak membuktikan operation gagal
- restart tidak boleh mengulang mutation secara buta
- setiap execution terikat pada AttemptId
- Job, Attempt, Operation, dan Worker adalah identity yang berbeda

Flow utama:

Submit

  ▼
Received
  │
  ▼
Validated
  │
  ▼
Admitted

1. Job Identity

Setiap Job memiliki JobId typed.

JobId tidak boleh direpresentasikan sebagai raw String di domain layer.

JobId harus immutable sepanjang lifecycle.

2. Attempt Identity

Satu Job dapat memiliki lebih dari satu AttemptId.

Attempt merepresentasikan satu execution attempt terhadap Job.

Retry harus menghasilkan AttemptId baru.

3. Operation Identity

Satu Job dapat mempunyai banyak OperationId.

OperationId merepresentasikan intended mutation, bukan invocation function.

Retry execution terhadap operation yang sama tidak boleh menghasilkan OperationId baru jika semantics operation tetap sama.

4. Worker Identity

WorkerId mengidentifikasi execution worker.

WorkerId berbeda dari AttemptId.

Satu worker dapat menjalankan banyak attempt sepanjang lifecycle process.

5. Job != Attempt

Job adalah logical request.

Attempt adalah execution instance.

Contoh:

Job J1
  ├── Attempt A1
  └── Attempt A2

A1 gagal sebelum mutation.
A2 dapat dijalankan kembali secara aman.

6. Attempt != Operation

Attempt menjalankan satu atau beberapa Operation.

Operation mempunyai identity dan postcondition sendiri.

7. Durable State

State yang diperlukan untuk recovery harus persisted.

In-memory enum saja tidak cukup untuk state yang menentukan recovery behavior.

8. State Machine Is Authoritative

Tidak boleh ada module yang mengubah field state secara langsung.

Gunakan domain transition function:

current_state + event + validated_context -> next_state

9. Legal Transition

Transition harus explicit.

Contoh:

Received -> Validated

Validasi gagal tidak boleh menghasilkan:

Received -> Executing

10. Illegal Transition

Illegal transition harus menghasilkan typed error.

Jangan diam-diam melakukan fallback ke state lain.

11. Initial State

Job baru dimulai pada:

Received

setelah identity dan minimal envelope berhasil dibentuk.

12. Received

State Received berarti request sudah diterima tetapi belum dianggap valid secara semantic.

Tidak ada mutation boleh terjadi pada state ini.

13. Validated

State Validated berarti:

- request schema valid
- identity valid
- configuration reference valid
- requested mode valid
- basic constraints terpenuhi

14. Admitted

Admitted berarti Job lolos admission control.

Admission dapat mempertimbangkan:

- global capacity
- resource pressure
- queue limits
- maintenance mode
- system health
- privilege/capability availability

15. Queued

Queued berarti Job menunggu scheduling/execution opportunity.

Job tidak boleh memegang exclusive execution resource ketika hanya queued.

16. Preparing

Preparing adalah tahap membangun execution context tanpa mutation destructive.

Dapat meliputi:

- load EffectiveConfig
- load platform snapshot
- resolve TargetCatalog view
- prepare cancellation context
- allocate bounded planning resources

17. Scanning

Scanning menghasilkan Candidate set/stream.

Scanning tidak boleh langsung melakukan destructive mutation.

18. Planning

Planning mengubah Candidate menjadi Plan.

Plan harus deterministic terhadap input snapshot, configuration generation, policy, dan catalog generation.

19. AwaitingAuthorization

Jika authorization diperlukan secara eksplisit, Job dapat masuk state:

AwaitingAuthorization

20. Authorized

Authorized berarti Plan telah memperoleh authorization yang valid.

Authorization harus mempunyai identity sendiri dan generation binding.

21. WaitingResources

WaitingResources berarti execution context valid tetapi resource belum tersedia.

Job boleh menunggu tanpa dianggap gagal.

22. Executing

Executing adalah state ketika mutation operation dapat dilakukan.

Hanya executor yang boleh memasuki mutation boundary.

23. Verifying

Verifying berarti mutation sudah attempted dan postcondition sedang diverifikasi.

24. Reconciling

Reconciling digunakan ketika outcome mutation tidak diketahui atau state runtime tidak konsisten dengan durable state.

25. Completed

Completed hanya boleh digunakan jika seluruh required postconditions terpenuhi atau domain policy secara eksplisit mendefinisikan partial completion sebagai successful terminal result.

26. Failed

Failed berarti Job berhenti dengan known failure dan tidak ada unresolved mutation outcome yang masih membutuhkan recovery.

27. Cancelled

Cancelled berarti cancellation diterima dan Job berhenti sesuai cancellation semantics.

Jika mutation sudah berjalan, cancellation tidak boleh mengubah unknown outcome menjadi Cancelled sebelum reconciliation.

28. TimedOut

TimedOut hanya boleh dipakai jika timeout semantics membuktikan tidak ada unresolved mutation atau setelah reconciliation menentukan terminal timeout.

29. RecoveryRequired

RecoveryRequired adalah terminal-ish safety state untuk Job yang tidak dapat dinyatakan aman sebagai Completed, Failed, atau Cancelled.

State ini harus durable.

30. Stale

Job dapat dinyatakan stale ketika execution context tidak lagi valid karena:

- config generation berubah secara incompatible
- catalog generation berubah
- target identity berubah
- authorization expired
- required safety invariant berubah

Stale bukan synonym untuk Failed.

31. Requeue vs Stale

Jika Job dapat direncanakan ulang dengan aman, Job dapat di-requeue.

Jika existing plan/authorization tidak lagi valid, stale state harus dicatat terlebih dahulu.

32. Terminal States

Minimal terminal semantics:

Completed
Failed
Cancelled
TimedOut
RecoveryRequired

Stale dapat menjadi non-terminal jika sistem mendukung re-planning, atau terminal jika policy memilih invalidation permanen. Pilihan harus explicit.

33. Terminal State Immutability

Setelah terminal state persisted, tidak boleh ada transition normal ke non-terminal state.

Recovery administrative action harus berupa new transition/event dengan audit, bukan silent overwrite.

34. State Transition Event

Setiap transition sebaiknya memiliki:

- JobId
- AttemptId jika relevan
- previous state
- next state
- event type
- actor/source
- timestamp
- correlation id
- reason code

35. Transition Reason

Reason harus typed enum atau stable code.

Jangan menggunakan free-form string sebagai satu-satunya source of truth.

36. Event vs State

Event menjelaskan apa yang terjadi.

State menjelaskan kondisi durable terkini.

Keduanya tidak boleh dicampur.

37. Persistence Before Publication

Jika state transition mengubah durable truth:

persist
→ commit
→ publish event

bukan:

publish
→ persist

38. Crash Between Persist and Publish

Jika crash setelah persist tetapi sebelum event publish, state tetap valid.

Event delivery dapat direcover melalui outbox/replay mechanism.

39. Crash Before Persist

Jika crash sebelum transition persisted, transition dianggap belum terjadi secara durable.

Recovery tidak boleh menganggap in-memory state sebagai truth.

40. Idempotent Transition

Processing duplicate transition event tidak boleh mengubah state dua kali.

Gunakan event identity/idempotency key.

41. Optimistic Concurrency

Transition harus memverifikasi expected current state/version.

Contoh:

UPDATE job
SET state = Executing, version = version + 1
WHERE job_id = J1 AND version = 8 AND state = WaitingResources

42. State Version

Job record sebaiknya memiliki monotonic state version.

Version berbeda dari JobId dan ConfigGeneration.

43. ConfigGeneration Binding

Job menyimpan ConfigGeneration yang digunakan untuk membentuk execution context.

44. Plan Generation Binding

Plan menyimpan ConfigGeneration dan CatalogGeneration yang menjadi dasar planning.

45. Authorization Binding

Authorization harus terikat minimal pada:

- JobId
- PlanId
- ConfigGeneration
- CatalogGeneration jika target identity bergantung padanya
- authorization scope
- expiration jika berlaku

46. Execution Binding

Executor tidak boleh mengambil configuration terbaru secara implicit lalu menganggapnya sebagai context Job.

Execution memakai immutable JobExecutionContext.

47. Current Config vs Job Config

Current config dapat berubah selama Job berjalan.

Job config snapshot tidak berubah.

Runtime safety limits yang global dapat mempersempit execution tetapi tidak memperluas authority.

48. Scheduler Ownership

Scheduler bertanggung jawab terhadap admission, queue, wake-up, dan assignment.

Scheduler bukan authority untuk menentukan mutation safety.

49. Worker Ownership

Worker bertanggung jawab menjalankan lifecycle execution yang telah ditentukan.

Worker tidak boleh membuat operation baru di luar execution set.

50. Planner Ownership

Planner bertanggung jawab menghasilkan Plan.

Planner tidak boleh melakukan mutation.

51. Authorization Ownership

Authorization menentukan apakah Plan tertentu boleh dieksekusi.

Authorization bukan safety substitute.

52. Safety Ownership

Safety Gate dapat menolak operation meskipun authorization valid.

53. Executor Ownership

Executor adalah satu-satunya layer yang masuk ke mutation boundary.

54. Verifier Ownership

Verifier menentukan apakah postcondition terpenuhi.

55. Recovery Ownership

Recovery Manager menentukan langkah setelah crash, timeout, unknown outcome, atau state inconsistency.

56. Cancellation Request

Cancellation adalah event/request, bukan langsung state.

Contoh:

CancelRequested

kemudian state machine menentukan apakah:

- cancel before execution
- cancel while waiting
- cooperative cancellation
- reconciliation required

57. Cancellation Before Mutation

Jika Job belum memasuki mutation boundary, cancellation dapat menghasilkan Cancelled secara langsung setelah cleanup context.

58. Cancellation During Planning

Planning dapat dihentikan jika operation belum authorized/executed.

Partial plan tidak boleh dipublikasikan sebagai executable authorization.

59. Cancellation During Execution

Executor harus cooperative terhadap cancellation.

Tetapi cancellation tidak boleh memotong critical mutation sequence pada titik yang menghasilkan ambiguous outcome tanpa reconciliation.

60. Cancellation After Mutation

Jika mutation telah committed tetapi verification belum selesai, hasil cancellation adalah:

Reconciling

bukan langsung Cancelled.

61. Hard Timeout

Hard timeout tidak berarti operation gagal.

Jika worker tidak dapat memastikan mutation state, Job masuk:

RecoveryRequired
atau
Reconciling

sesuai recovery capability.

62. Soft Timeout

Soft timeout dapat meminta cooperative stop sebelum hard timeout.

63. Timeout Budget

Timeout harus dibatasi dan dibagi secara eksplisit antara:

- queue wait
- preparation
- scanning
- planning
- resource wait
- execution
- verification
- reconciliation

64. Timeout Does Not Grant Retry

Timeout tidak otomatis berarti retry.

Retry hanya boleh jika operation idempotency dan recovery contract mengizinkan.

65. Retry Classification

Failure sebelum mutation dapat lebih mudah di-retry.

Failure setelah mutation attempt memerlukan verification/reconciliation terlebih dahulu.

66. Retry Attempt

Setiap retry execution harus membuat AttemptId baru.

JobId tetap sama.

67. Retry Limit

Retry count harus bounded.

Tidak boleh ada infinite retry loop.

68. Backoff

Retry menggunakan bounded backoff dengan jitter jika diperlukan untuk mencegah thundering herd.

69. Poison Job

Job yang berulang kali gagal dengan error deterministic harus dapat ditandai sebagai poison/dead-letter candidate.

70. Resource Wait Cancellation

Job yang menunggu resource harus dapat dibatalkan tanpa meninggalkan reservation leak.

71. Reservation Ownership

Setiap reservation harus memiliki identity dan owner Job/Attempt yang jelas.

72. Resource Release

Resource harus dilepas pada:

- Completed
- Failed
- Cancelled
- terminal timeout
- recovery transition yang tidak lagi membutuhkan resource

73. Crash Resource Recovery

Reservation yang dimiliki Attempt yang crashed harus dapat diidentifikasi sebagai stale.

74. Worker Crash

Worker crash saat non-mutating phase dapat membuat Attempt failed/retryable.

Worker crash setelah mutation boundary harus memicu reconciliation.

75. Worker Restart

Worker baru mendapat WorkerId baru.

Jangan menganggap worker identity lama masih hidup.

76. Stale Worker Messages

Message dari WorkerId/AttemptId lama harus ditolak atau diabaikan secara idempotent.

77. Heartbeat

Long-running Attempt dapat mengirim heartbeat.

Heartbeat hanya evidence of liveness, bukan bukti mutation success.

78. Hung Worker

Jika heartbeat hilang:

- mark worker suspect
- stop assignment baru
- tunggu bounded grace period
- lakukan recovery

79. State Reconciliation After Restart

Saat daemon restart:

load durable jobs
→ detect non-terminal attempts
→ inspect worker state
→ inspect operation state
→ reconcile
→ resume/retry/fail/recovery

80. No Blind Resume

Daemon tidak boleh melanjutkan mutation dari state Executing hanya karena durable state mengatakan Executing.

Harus ada recovery decision.

81. Recovery Decision Inputs

Recovery mempertimbangkan:

- last durable transition
- AttemptId
- OperationId
- operation idempotency
- executor journal
- verifier evidence
- filesystem/platform snapshot
- worker liveness
- resource ownership

82. Unknown Outcome

Unknown outcome adalah first-class state.

Contoh:

Executor mengirim delete request
→ process crash
→ tidak diketahui apakah delete berhasil.

Jangan mengubahnya menjadi Failed secara otomatis.

83. Reconciliation

Reconciliation mencoba menentukan actual state berdasarkan observable postcondition.

84. Reconciliation Must Be Bounded

Reconciliation tidak boleh retry tanpa batas.

85. Reconciliation Success

Jika postcondition terbukti terpenuhi:

Unknown → Verified/Completed

86. Reconciliation Failure

Jika postcondition terbukti tidak terpenuhi dan operation aman untuk retry:

Unknown → retryable state

87. Reconciliation Unresolved

Jika evidence tidak cukup:

Unknown → RecoveryRequired

88. RecoveryRequired Is Safe Failure

RecoveryRequired lebih aman daripada mengarang hasil.

89. Partial Completion

Job dengan banyak operations dapat mempunyai sebagian operation berhasil.

JobResult harus membedakan:

- succeeded operations
- failed operations
- skipped operations
- cancelled operations
- unknown operations

90. Partial Completion Policy

Apakah partial success menghasilkan Completed atau Failed harus ditentukan domain policy.

Tidak boleh tergantung pada implementation accident.

91. Operation Ordering

State Job tidak menggantikan dependency state Operation.

Operation graph tetap menjadi source of truth untuk ordering.

92. Empty Plan

Jika Plan valid tetapi tidak memiliki mutation operation:

Job dapat langsung menuju Completed dengan reason NoEligibleOperations setelah seluruh validation/safety prerequisites terpenuhi.

93. Empty Candidate Set

Tidak menemukan candidate bukan failure.

94. No Target Available

Jika requested target tidak tersedia:

Job dapat Failed/Stale/Skipped sesuai typed reason.

95. Safety Rejection

Safety rejection harus menghasilkan explicit result.

Jangan menyamarkannya sebagai generic execution failure.

96. Authorization Rejection

Authorization rejection harus terjadi sebelum mutation.

97. Resource Rejection

Resource admission failure berbeda dari operation failure.

98. Configuration Stale

Jika configuration generation yang menjadi dasar authorization tidak lagi valid untuk execution, Job harus stale/re-authorized sesuai policy.

99. Catalog Stale

Jika target catalog generation berubah sehingga target identity tidak lagi valid, plan harus direvalidasi.

100. Safety Policy Tightening

Jika runtime safety policy menjadi lebih restrictive, Job boleh dihentikan atau narrowed.

Tidak boleh otomatis diperluas.

101. State Machine API

Recommended API:

```rust
pub trait JobStateMachine {
    fn transition(
        &self,
        job: &Job,
        event: JobEvent,
        context: &TransitionContext,
    ) -> Result<StateTransition>;
}
```

Transition result minimal memiliki:

- previous state
- next state
- state version
- event id
- reason
- timestamp

102. Typed JobState

Recommended enum:

```rust
pub enum JobState {
    Received,
    Validated,
    Admitted,
    Queued,
    Preparing,
    Scanning,
    Planning,
    AwaitingAuthorization,
    Authorized,
    WaitingResources,
    Executing,
    Verifying,
    Reconciling,
    Completed,
    Failed,
    Cancelled,
    TimedOut,
    RecoveryRequired,
    Stale,
}
```

Enum final dapat disesuaikan dengan domain implementation, tetapi semantics harus dipertahankan.

103. Typed JobEvent

Contoh event:

```rust
pub enum JobEvent {
    ValidationPassed,
    ValidationFailed,
    AdmissionGranted,
    AdmissionRejected,
    Queued,
    PreparationComplete,
    ScanComplete,
    PlanCreated,
    AuthorizationGranted,
    AuthorizationRejected,
    ResourcesGranted,
    ResourcesReleased,
    ExecutionStarted,
    ExecutionFinished,
    VerificationPassed,
    VerificationFailed,
    ReconciliationRequired,
    ReconciliationResolved,
    CancelRequested,
    Timeout,
    WorkerLost,
    ConfigBecameStale,
    CatalogBecameStale,
    RecoveryRequired,
}
```

104. Transition Matrix

Transition matrix harus menjadi testable artifact, bukan hanya dokumentasi.

Contoh:

| Current | Event | Next |
|---|---|---|
| Received | ValidationPassed | Validated |
| Validated | AdmissionGranted | Admitted |
| Admitted | Queued | Queued |
| Queued | PreparationStarted | Preparing |
| Preparing | ScanStarted | Scanning |
| Scanning | ScanComplete | Planning |
| Planning | PlanCreated | AwaitingAuthorization/Authorized |
| Authorized | ResourcesGranted | WaitingResources/Executing |
| Executing | ExecutionFinished | Verifying |
| Verifying | VerificationPassed | Completed |
| Verifying | ReconciliationRequired | Reconciling |
| Reconciling | ReconciliationResolved | Completed/Failed |

105. Impossible Transitions Must Be Tested

Test wajib mencakup:

- Received -> Executing
- Completed -> Executing
- Failed -> Planning
- Cancelled -> Executing
- RecoveryRequired -> Executing tanpa recovery authorization

Semua harus ditolak.

106. State Persistence Schema

Minimal Job persistence membutuhkan:

- job_id
- state
- state_version
- created_at
- updated_at
- current_attempt_id
- config_generation
- plan_id jika ada
- authorization_id jika ada
- recovery status

107. Attempt Persistence

Attempt minimal membutuhkan:

- attempt_id
- job_id
- worker_id
- attempt number
- state
- started_at
- finished_at
- last heartbeat
- outcome
- error/recovery code

108. Operation Persistence

Operation minimal membutuhkan:

- operation_id
- job_id
- attempt association
- operation type
- target id
- intended effect
- execution state
- verification state
- idempotency key

109. Monotonic Attempt Number

Attempt number harus monotonically increasing untuk satu Job.

110. Duplicate Submit

Duplicate request dengan idempotency key yang sama tidak boleh membuat Job baru secara tidak sengaja.

111. Job Submission Idempotency

Jika caller mengulang submit karena timeout IPC, daemon harus dapat mengembalikan Job yang sama jika idempotency semantics cocok.

112. Event Ordering

Event dengan sequence lebih rendah tidak boleh overwrite state yang lebih baru.

113. Clock Independence

Correctness state machine tidak boleh bergantung pada wall-clock ordering.

Gunakan sequence/version untuk ordering.

114. Timestamp Usage

Timestamp hanya untuk:

- audit
- timeout calculation
- observability

bukan identity atau concurrency authority.

115. Monotonic Runtime Clock

Timeout/elapsed duration harus menggunakan monotonic clock jika tersedia.

116. Wall Clock Jump

Perubahan wall clock tidak boleh menyebabkan job tiba-tiba dianggap selesai atau stale secara incorrect.

117. State Snapshot

IPC/UI dapat menerima immutable JobSnapshot.

Snapshot bukan mutable command object.

118. Command vs Event

Command meminta daemon melakukan sesuatu.

Event menyatakan sesuatu telah terjadi.

Contoh:

CancelJob = command
JobCancelled = event

119. UI Cannot Set State

Frontend/CLI tidak boleh mengirim:

state = Completed

Sebagai command.

UI hanya dapat meminta action seperti:

CancelJob
RetryJob
RecoverJob

120. Administrative Recovery

RecoveryRequired dapat memerlukan explicit administrative command.

Command tersebut harus:

- authenticated/authorized
- audited
- bounded
- typed

121. RetryJob

RetryJob tidak boleh bypass safety/authorization.

Ia hanya meminta pembuatan Attempt baru setelah eligibility diperiksa.

122. RecoverJob

RecoverJob harus menjalankan reconciliation sebelum mutation baru.

123. Force Semantics

Tidak boleh ada generic:

force = true

yang melewati state machine.

Jika ada force operation, semantics dan authority harus typed serta explicit.

124. Shutdown

Graceful shutdown harus menghentikan assignment baru terlebih dahulu.

125. Shutdown Ordering

Recommended:

stop intake
→ stop scheduling
→ request cooperative cancellation
→ wait bounded
→ persist active states
→ release safe resources
→ reconcile unresolved attempts on next startup

126. Shutdown During Mutation

Shutdown tidak boleh menganggap in-flight mutation gagal hanya karena process berhenti.

127. Crash Safety

Crash adalah event eksternal.

State machine recovery harus mampu menentukan next safe state setelah restart.

128. Durable Outbox

State transition penting sebaiknya menghasilkan durable outbox event untuk observer.

129. Observer Failure

Kegagalan mengirim telemetry/UI event tidak boleh membatalkan durable Job transition.

130. Audit Completeness

Setiap transition security-relevant harus dapat ditelusuri ke:

JobId
AttemptId
actor
reason
config generation
plan/authorization identity

131. Error Taxonomy

Error state harus dibedakan minimal menjadi:

ValidationError
AdmissionError
ConfigurationError
AuthorizationError
SafetyError
ResourceError
ExecutionError
VerificationError
RecoveryError
InternalInvariantError

132. InternalInvariantError

Jika state machine menemukan impossible state internal, jangan fallback ke normal Failed tanpa audit.

Lebih aman masuk RecoveryRequired dan log invariant violation.

133. Panic Boundary

Panic di worker tidak boleh mematikan state authority.

Supervisor harus mengubah worker state dan memulai recovery workflow.

134. Persistence Failure

Jika durable state gagal disimpan, state transition tidak boleh dianggap committed.

Mutation yang membutuhkan durable intent harus dihentikan sebelum boundary jika persistence tidak reliable.

135. Database Unavailable

Jika Job persistence unavailable, scheduler harus melakukan fail-safe admission.

Jangan menerima destructive job yang tidak dapat direcover.

136. Queue Durability

Jika queued job harus survive restart, queue membership harus durable atau dapat direconstruct secara deterministic dari Job state.

137. Assignment Durability

Worker assignment yang menentukan recovery harus durable.

138. Execution Journal

Operation yang mutation-sensitive sebaiknya memiliki execution journal minimal:

prepared
started
commit-attempted
returned
verification-started
verified

139. Journal Is Not Proof

Journal `commit-attempted` bukan bukti mutation berhasil.

Verification tetap diperlukan.

140. State and Result Separation

JobState menunjukkan lifecycle.

JobResult menunjukkan outcome.

Jangan menggunakan state enum untuk menyimpan seluruh detail result.

141. Result Publication

JobResult final dipublikasikan hanya setelah terminal state persisted.

142. Terminal Result Immutability

JobResult terminal tidak boleh diubah tanpa explicit correction event.

143. Correction Event

Jika observability menemukan kesalahan result setelah terminal publication, gunakan correction/audit event dan jangan menghapus sejarah asli.

144. Recovery History

Semua recovery attempt harus dapat ditelusuri.

145. Maximum Recovery Attempts

Recovery juga harus mempunyai bounded attempts.

146. Dead Letter / Manual Intervention

Jika recovery tidak dapat diselesaikan secara otomatis, Job harus dapat masuk manual intervention queue.

147. Manual Intervention Safety

Manual operator tidak boleh mendapatkan primitive unrestricted mutation melalui recovery interface.

148. State Machine Determinism

Dengan current state, event, dan context yang sama, transition result harus deterministic kecuali field audit yang memang ephemeral.

149. No Hidden Transition

Tidak boleh ada background task yang mengubah JobState tanpa melalui state authority.

150. No Direct Mutable State

Field state pada Job domain sebaiknya private.

151. Transition Invariants

Setiap transition harus memeriksa invariant sebelum dan sesudah transition.

152. Pre-transition Invariant

Contoh:

Executing hanya valid jika:

- authorization valid
- plan valid
- required resources held
- safety prerequisites valid
- Attempt active

153. Post-transition Invariant

Contoh:

Completed harus memiliki:

- terminal JobResult
- no unresolved mutation
- resources released
- attempt terminal

154. Resource Invariant

WaitingResources tidak boleh mengklaim resource yang belum granted.

155. Authorization Invariant

Executing tidak boleh terjadi tanpa valid authorization atau explicit non-destructive execution class.

156. Safety Invariant

Executing destructive operation harus mempunyai successful final safety check.

157. Verification Invariant

Completed destructive operation harus memiliki required verification evidence.

158. Recovery Invariant

RecoveryRequired tidak boleh langsung menuju Executing tanpa successful recovery decision.

159. Stale Invariant

Stale authorization tidak boleh dipakai untuk mutation.

160. Restart Invariant

Restart daemon tidak boleh menghasilkan duplicate mutation hanya karena state sebelumnya non-terminal.

161. Concurrency Invariant

Satu Job tidak boleh memiliki dua active destructive Attempts kecuali domain secara eksplisit mengizinkannya.

162. Default Concurrency

Default harus satu active mutation Attempt per Job.

163. Cross-Job Concurrency

Cross-job concurrency dikontrol Resource Manager, bukan JobState machine.

164. State Machine Testing

Minimum test suite:

- legal transition tests
- illegal transition tests
- terminal immutability
- duplicate event idempotency
- stale version rejection
- cancellation races
- timeout races
- worker crash
- restart recovery
- config generation change
- catalog generation change
- resource release
- authorization expiry
- unknown mutation outcome

165. Property Testing

Property:

Tidak ada sequence event yang valid dapat menghasilkan Executing tanpa seluruh execution prerequisites.

166. Model Checking

Transition matrix dapat diuji dengan generated event sequences untuk mencari state yang unreachable atau illegal.

167. Race Testing

Wajib menguji race:

- cancel vs execute
- timeout vs verify
- shutdown vs execute
- config reload vs authorization
- resource release vs worker completion
- worker crash vs result publication

168. Persistence Crash Testing

Simulasikan crash pada setiap boundary:

before persist
after persist
before publish
after publish
before mutation
mutation attempted
before verification
verification complete

169. Recovery Test

Untuk setiap crash point harus ada expected recovery state yang eksplisit.

170. Definition of Done

Implementasi Job lifecycle dianggap memenuhi dokumen ini jika:

- semua state typed
- semua transition melalui satu authority
- illegal transition ditolak
- state version durable
- Job/Attempt/Operation identity terpisah
- ConfigGeneration binding tersedia
- cancellation semantics explicit
- timeout semantics explicit
- unknown outcome first-class
- recovery durable
- worker crash dapat direcover
- resource ownership dapat dipulihkan
- terminal state immutable
- result publication mengikuti persistence barrier
- destructive execution tidak dapat terjadi tanpa prerequisites
- restart tidak menghasilkan blind retry
- race tests lulus
- crash/recovery tests lulus
- state machine dapat direkonstruksi dari durable history

171. Final Invariants

Sistem rewrite harus mempertahankan invariant berikut:

1. JobId immutable.
2. AttemptId unik untuk setiap execution attempt.
3. OperationId merepresentasikan intended mutation.
4. State transition hanya melalui state authority.
5. Illegal transition selalu ditolak.
6. Durable transition dipersist sebelum dipublikasikan.
7. Terminal state tidak berubah secara normal.
8. Cancel request bukan bukti cancellation selesai.
9. Timeout bukan bukti mutation gagal.
10. Unknown outcome bukan Failed.
11. RecoveryRequired lebih aman daripada asumsi hasil.
12. Retry tidak boleh bypass authorization.
13. Retry tidak boleh bypass safety.
14. Worker crash tidak boleh menghasilkan silent duplicate mutation.
15. Current configuration tidak boleh mengganti Job configuration snapshot.
16. Stale ConfigGeneration tidak boleh menghasilkan authority baru.
17. Stale CatalogGeneration tidak boleh digunakan tanpa revalidation.
18. Executing selalu mempunyai execution prerequisites.
19. Completed membutuhkan required verification evidence.
20. Resources tidak boleh bocor setelah terminal state.
21. Queue/assignment recovery harus deterministic.
22. State ordering menggunakan version/sequence, bukan wall-clock.
23. UI/CLI tidak boleh menentukan JobState secara langsung.
24. Recovery administrative action harus audited.
25. Tidak boleh ada hidden background transition.
26. Tidak boleh ada direct mutable state bypass.
27. State machine harus deterministic.
28. Semua mutation-sensitive crash points harus mempunyai recovery semantics.
29. Persistence failure harus menghasilkan fail-safe behavior.
30. Job lifecycle harus dapat direkonstruksi setelah daemon restart.
