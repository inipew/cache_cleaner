Lanjut. Sekarang kita bangun **Policy Engine**. Kalau Safety Engine menjawab *“boleh disentuh secara aman?”*, Policy Engine menjawab *“apakah sekarang memang layak dibersihkan?”*

Saya ingin Policy Engine dibuat **deterministik, explainable, dan tidak punya akses untuk menghapus apa pun**.

# 81. Policy Engine

Alurnya:

```text
SafetyValidated
      │
      ▼
Policy Engine
      │
      ├── target rule
      ├── age rule
      ├── size rule
      ├── runtime rule
      ├── storage rule
      ├── profile rule
      └── budget rule
      │
      ▼
PolicyDecision
```

API utamanya:

```rust
pub fn evaluate_candidate(
    candidate: &SafetyValidated,
    ctx: &PolicyContext,
) -> PolicyDecision;
```

Hasil jangan `bool`.

```rust
pub enum PolicyDecision {
    Allow(PolicyApproval),
    Reject(PolicyRejection),
    Defer(PolicyDeferral),
}
```

---

# 82. Bedakan Reject dan Defer

Ini harus konsisten dari awal.

### Reject

```text
candidate tidak cocok dengan policy
```

Contoh:

```text
age = 2 jam
minimum = 7 hari
```

Maka:

```text
REJECT
```

Tidak perlu dicoba lagi pada job yang sama.

### Defer

```text
candidate sebenarnya valid,
tetapi kondisi runtime sekarang tidak ideal.
```

Contoh:

```text
screen = ON
```

Maka:

```text
DEFER
```

Scheduler bisa mencoba lagi nanti.

## 111. Satu Prinsip yang Akan Menyelamatkan Banyak Bug

Saya ingin kita pegang satu aturan:

> **Scanner menemukan. Safety membatasi. Policy memilih. Planner merencanakan. Executor melakukan. Verifier memastikan.**

Jangan pernah biarkan tanggung jawab tersebut bercampur.

```text
Scanner
  ❌ delete
  ❌ policy decision

Safety
  ❌ delete
  ❌ relax itself from config

Policy
  ❌ syscall
  ❌ delete

Planner
  ❌ syscall
  ❌ bypass safety

Executor
  ❌ decide arbitrary path
  ❌ discover targets

Verifier
  ❌ repair silently
```

Dengan boundary ini, rewrite akan jauh lebih mudah diaudit.

---

### Tahap berikutnya: Planner + Operation Model

Setelah Policy Engine, bagian berikutnya sebaiknya kita bedah **Planner secara penuh**, termasuk desain:

```text
Candidate
   ↓
Operation
   ↓
dependency graph
   ↓
ordering
   ↓
deduplication
   ↓
resource budget
   ↓
estimated freed bytes
   ↓
CleanupPlan
```

dan terutama bagaimana menangani kasus seperti **parent-child deletion, duplicate candidate, directory kosong, operation ordering, cancellation di tengah plan, partial failure, retry, serta membedakan filesystem cleanup dengan F2FS/trim/zram maintenance**. Ini akan menjadi tahap terakhir sebelum kita masuk ke executor nyata.
