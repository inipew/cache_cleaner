44.md — Result Aggregation, Reporting, Audit Trail, Explainability, dan User-facing Job Result Contract

1. Tujuan

Result Aggregation adalah lapisan yang mengubah hasil per-operation menjadi hasil Job yang konsisten, immutable, deterministic, auditable, dan aman untuk dikonsumsi oleh CLI, IPC, telemetry, serta komponen aplikasi.

Alur:

```
OperationResult
      │
      ▼
VerificationResult
      │
      ▼
ResultAggregator
      │
      ├──────────────┐
      ▼              ▼
  JobResult      AuditRecord
      │
      ├──────────────┐
      ▼              ▼
  Reporter       Explain
      │              │
      └──────┬───────┘
             ▼
         CLI / IPC
```

Result Aggregator tidak boleh:

→ melakukan filesystem mutation
→ melakukan retry
→ mengubah policy
→ mengubah authorization
→ melakukan scan ulang
→ memperbaiki operation
→ mengubah hasil Executor atau Verifier

2. Masalah Yang Harus Diselesaikan

Satu Job dapat memiliki ribuan operation.

Contoh:

```
O1  → Applied → Verified
O2  → Applied → Verified
O3  → AlreadyGone → AlreadySatisfied
O4  → Applied → Changed
O5  → Unknown
O6  → Cancelled
```

User tidak membutuhkan enam object internal yang terpisah.

User membutuhkan:

```
JobResult
   │
   ├── status
   ├── summary
   ├── operations
   ├── failures
   ├── verification
   └── explanation
```

Maka diperlukan aggregation layer.

3. Separation of Concerns

Pembagian final:

```
Executor
    │
    └── "Apa yang terjadi saat mutation?"

Verifier
    │
    └── "Apakah postcondition terpenuhi?"

ResultAggregator
    │
    └── "Apa arti keseluruhan hasil Job?"

Reporter
    │
    └── "Bagaimana hasil ditampilkan?"

Audit
    │
    └── "Apa yang perlu dicatat sebagai evidence?"
```

Tidak boleh satu komponen melakukan semuanya.

4. Result Hierarchy

Struktur hasil:

```
Job
 │
 ├── OperationResult
 │
 ├── VerificationResult
 │
 ├── OperationSummary
 │
 ├── JobSummary
 │
 └── JobResult
```

Contoh:

```
JobResult
   │
   ├── JobId
   ├── PlanId
   ├── FinalState
   │
   ├── Summary
   │     ├── total
   │     ├── succeeded
   │     ├── partial
   │     ├── failed
   │     └── unknown
   │
   ├── OperationResults
   │
   ├── VerificationSummary
   │
   └── AuditSummary
```

5. JobResult Harus Immutable

Setelah Job mencapai terminal state:

```
Completed
CompletedPartial
Failed
Cancelled
Stale
Stopped
```

JobResult tidak boleh berubah.

Contoh yang dilarang:

```
Completed
   │
   ▼
JobResult published
   │
   ▼
background verifier modifies result
        ✕
```

Yang benar:

```
Execute
   │
   ▼
Verify
   │
   ▼
Aggregate
   │
   ▼
Validate
   │
   ▼
Publish immutable JobResult
   │
   ▼
terminal state
```

6. Internal Result vs Public Result

Result internal dapat memiliki detail teknis.

Contoh:

```
InternalOperationResult {
    operation_id
    syscall_class
    errno
    fd_context
    identity
    timing
    verification
}
```

Tetapi CLI/IPC tidak boleh otomatis menerima semuanya.

Buat boundary:

```
InternalResult
      │
      ▼
ResultSanitizer
      │
      ▼
PublicJobResult
```

Tujuannya:

→ mengurangi information leakage
→ menjaga compatibility
→ menghindari exposure detail internal
→ memastikan output tetap bounded

7. Public Result Contract

Public JobResult minimal:

```
{
    job_id
    state
    started_at
    finished_at

    operations_total
    operations_succeeded
    operations_partial
    operations_failed
    operations_unknown

    bytes_requested
    bytes_removed

    verification_status

    summary
}
```

Field tambahan dapat tersedia melalui Explain atau verbose mode.

8. Status Taxonomy

Gunakan status typed.

Contoh:

```
JobResultStatus

    ├── Completed
    ├── CompletedPartial
    ├── Failed
    ├── Cancelled
    ├── Stale
    └── Stopped
```

Jangan menggunakan:

```
success = true/false
```

karena Job dapat memiliki:

```
successful execution
tetapi partial verification.
```

9. Status Aggregation

Contoh baseline:

```
semua required operation satisfied
        │
        ▼
   Completed


sebagian satisfied
        │
        ▼
  CompletedPartial


fatal failure sebelum useful execution
        │
        ▼
     Failed


explicit cancellation
        │
        ▼
    Cancelled


context invalid
        │
        ▼
     Stale


process/runtime stopped
        │
        ▼
     Stopped
```

Mapping final harus didefinisikan oleh Job policy.

10. Precedence Rules

Jika beberapa kondisi terjadi bersamaan, precedence harus deterministic.

Contoh:

```
Stale
  >
Cancelled
  >
Failed
  >
CompletedPartial
  >
Completed
```

Tetapi precedence tidak boleh diterapkan secara sembarang.

Lebih aman mendefinisikan terminal decision berdasarkan Job state machine dan cause classification.

Contoh:

```
explicit cancellation accepted
    +
20 operations already executed

→ Cancelled
```

Bukan:

```
CompletedPartial
```

11. Cancellation Semantics

Cancellation bukan failure biasa.

Contoh:

```
Job
  │
  ├── 500 operations planned
  ├── 200 executed
  ├── cancellation
  └── 300 skipped
          │
          ▼
      Cancelled
```

Result harus menyimpan:

```
executed = 200
skipped = 300
cancelled = true
```

Tidak boleh menyembunyikan 200 mutation yang sudah terjadi.

12. Partial Execution

Job dapat berhenti di tengah.

Contoh:

```
Planned:
    1000 operations

Executed:
    437

Verified:
    432

Unknown:
      5
```

Maka result harus menyatakan keadaan aktual.

```
planned   = 1000
attempted = 437
verified  = 432
unknown   = 5
remaining = 563
```

Tidak boleh:

```
completed = 1000
```

13. Bytes Accounting

Bytes adalah metrik penting tetapi harus dibedakan.

Gunakan:

```
planned_bytes
attempted_bytes
removed_bytes
verified_bytes
unknown_bytes
```

Contoh:

```
planned = 10 GiB
attempted = 4 GiB
verified = 3.5 GiB
unknown = 0.5 GiB
```

Jangan menyatakan:

```
4 GiB cleaned
```

jika 0.5 GiB masih unknown.

14. Bytes Tidak Selalu Akurat

Filesystem dapat berubah antara:

```
scan
execution
verification
```

Ukuran object juga dapat berubah.

Karena itu:

```
planned_bytes
```

adalah estimate/snapshot.

Sedangkan:

```
verified_bytes
```

adalah jumlah yang berhasil dikaitkan dengan postcondition yang terverifikasi.

Result harus mempertahankan perbedaan tersebut.

15. OperationSummary

Setiap operation dapat diringkas menjadi:

```
OperationSummary {
    operation_id
    operation_type

    execution_status
    verification_status

    result_class

    bytes
    duration

    reason_code
}
```

Tidak perlu membawa seluruh internal metadata ke public API.

16. Result Classes

Gunakan classification yang stabil.

Contoh:

```
Success
AlreadySatisfied
Partial
Failed
Unknown
Cancelled
Stale
```

Contoh mapping:

```
Applied + Verified
    → Success

AlreadyGone + AlreadySatisfied
    → AlreadySatisfied

Applied + Changed
    → Partial

Applied + NotSatisfied
    → Failed/Partial

Unknown
    → Unknown

Cancelled
    → Cancelled

Stale
    → Stale
```

17. Reason Codes

String error tidak cukup untuk API.

Gunakan typed/stable reason code.

Contoh:

```
TARGET_ALREADY_ABSENT
TARGET_CHANGED
TYPE_CHANGED
PERMISSION_DENIED
MOUNT_CHANGED
ROOT_CHANGED
VERIFICATION_UNKNOWN
BUDGET_EXCEEDED
CANCELLED
STALE_GENERATION
RUNTIME_STOPPED
```

Human-readable message dapat dibuat dari reason code.

18. Reason Code Harus Stable

CLI dan IPC tidak boleh bergantung pada:

```
"Permission denied while checking target"
```

Karena wording dapat berubah.

Gunakan:

```
PERMISSION_DENIED
```

Kemudian presentation layer dapat menghasilkan:

```
"Target could not be verified because permission was denied."
```

19. Error Message Bukan Authority

Message:

```
"cleanup failed"
```

tidak boleh digunakan scheduler sebagai logic.

Scheduler menggunakan:

```
reason_code
typed result
retryability
```

Message hanya presentation.

20. Retryability

Result harus dapat menyatakan apakah error secara konseptual dapat di-retry.

Contoh:

```
TARGET_BUSY
    → potentially retryable

ROOT_CHANGED
    → stale, requires new scan

TYPE_CHANGED
    → do not retry blindly

PERMISSION_DENIED
    → usually non-retryable

UNKNOWN
    → inspect/reconcile before mutation retry
```

Namun ResultAggregator tidak menjalankan retry.

21. Audit Trail

Audit berbeda dari logging.

Logging:

```
membantu debugging
```

Audit:

```
menjelaskan tindakan keamanan dan lifecycle Job
```

Audit record minimal:

```
timestamp
job_id
operation_id
actor
action
result
reason_code
```

Contoh:

```
Job J42
   │
   ├── authorized
   ├── execution_started
   ├── operation_applied
   ├── verification_completed
   └── job_completed
```

22. Audit Tidak Menyimpan Secret

Audit tidak boleh menyimpan:

→ credentials
→ tokens
→ raw IPC payload
→ environment secrets
→ file content
→ arbitrary sensitive path

Audit harus bounded dan privacy-aware.

23. Audit vs Telemetry

Telemetry:

```
"berapa lama execution berlangsung?"
```

Audit:

```
"Job mana melakukan operation apa dan hasilnya apa?"
```

Telemetry dapat diagregasi.

Audit harus mempertahankan correlation.

24. Correlation IDs

Gunakan:

```
JobId
PlanId
OperationId
AttemptId
```

Contoh:

```
Job J1
  │
  └── Plan P1
        │
        ├── Operation O1
        ├── Operation O2
        └── Operation O3
```

Setiap event harus dapat dikaitkan kembali.

25. Audit Ordering

Event harus memiliki ordering yang deterministic.

Minimal gunakan:

```
sequence_number
```

Contoh:

```
seq 100 → execution_started
seq 101 → operation O1 applied
seq 102 → operation O1 verified
seq 103 → job completed
```

Wall clock saja tidak cukup karena timestamp dapat sama atau berubah.

26. Monotonic Sequence

Audit sequence harus monotonic dalam satu Job.

```
1
2
3
4
...
```

Jika process restart dan persistence digunakan, sequence harus dapat dilanjutkan atau diberi epoch/attempt yang jelas.

27. Explainability

Explain adalah kemampuan menjawab:

```
"Mengapa operation ini dijalankan?"

"Mengapa operation ini tidak dijalankan?"

"Mengapa Job partial?"

"Mengapa target dianggap tidak aman?"

"Mengapa cleanup ditunda?"
```

Explain tidak boleh menjalankan operation.

28. Explain Request

Contoh:

```
ExplainRequest {
    job_id
    operation_id?
    verbosity
}
```

Output:

```
ExplainResult {
    subject
    decision
    reasons[]
    evidence[]
}
```

29. Explain Decision Chain

Untuk operation:

```
candidate
   │
   ▼
safety
   │
   ▼
policy
   │
   ▼
planning
   │
   ▼
authorization
   │
   ▼
execution
   │
   ▼
verification
```

Explain harus mampu merepresentasikan chain tersebut tanpa membocorkan internal security detail.

30. Contoh Explain

    Operation O17

    target:
    app_cache

    decision:
    executed

    reasons:
    target matched cleanup policy
    target was inside trusted root
    target identity matched
    operation was authorized

    execution:
    applied

    verification:
    verified

    final:
    success

31. Explain Untuk Operation Yang Ditolak

    Operation O18

    target:
    unknown path

    decision:
    rejected

    reasons:
    target is outside authorized scope
    target catalog entry not found

    execution:
    not attempted

    final:
    rejected

Penting:

```
rejected ≠ failed execution
```

32. Explain Untuk Safety Failure

```
Operation O19

decision:
    rejected

safety:
    target identity changed

execution:
    not attempted

result:
    stale_candidate
```

Tidak boleh:

```
"delete failed"
```

karena deletion tidak pernah dijalankan.

33. Explainability Tidak Boleh Menjadi Security Leak

Explain harus menyembunyikan detail yang dapat membantu bypass security.

Contoh:

```
jangan expose:
    raw internal FD
    SELinux internal details yang sensitif
    arbitrary absolute paths
    secret configuration
    capability token
```

Expose:

```
reason code
high-level scope
safe target identifier
policy outcome
```

34. Reporting Layer

Reporter menerima immutable JobResult.

```
JobResult
   │
   ├── CLI Reporter
   ├── IPC Reporter
   ├── JSON Reporter
   ├── Human Reporter
   └── Audit Reporter
```

Reporter tidak boleh mengubah result.

35. CLI Output

Default CLI harus ringkas.

Contoh:

```
Cleanup completed.

Operations:
  planned:   120
  successful: 118
  partial:      1
  unknown:      1

Space:
  verified: 842 MiB

Verification:
  partial
```

Untuk detail:

```
cache-cleaner status --job <id> --verbose
```

36. Machine-readable Output

IPC/JSON membutuhkan schema stabil.

Contoh:

```
{
    "job_id": "...",
    "state": "completed_partial",
    "operations": {
        "planned": 120,
        "successful": 118,
        "partial": 1,
        "unknown": 1
    },
    "verification": {
        "status": "partial"
    }
}
```

Public schema tidak boleh mengekspos internal Rust/domain object secara langsung.

37. Versioning

Public result harus memiliki:

```
schema_version
```

Contoh:

```
schema_version = 1
```

Perubahan internal tidak boleh otomatis memecahkan CLI/IPC.

Compatibility boundary:

```
internal result
      │
      ▼
public DTO v1
      │
      ▼
CLI / IPC
```

38. Serialization Boundary

Domain type:

```
JobResult
```

tidak boleh langsung digunakan sebagai wire format jika hal tersebut mengikat domain dengan IPC.

Gunakan:

```
JobResult
   │
   ▼
PublicJobResultDto
   │
   ▼
Serializer
```

Dengan demikian domain tetap bersih.

39. Bounded Output

Job dapat memiliki:

```
50.000 operations
```

Tidak boleh IPC mengirim:

```
50.000 full operation details
```

secara default.

Gunakan:

```
summary
pagination
bounded detail
```

Contoh:

```
GET job summary

GET job operations page=1 limit=100
```

40. Pagination

Untuk operation result:

```
offset/cursor
limit
```

Harus:

→ bounded
→ deterministic
→ stable selama JobResult immutable

Karena JobResult immutable, pagination menjadi aman dan reproducible.

41. Sorting

Operation listing harus memiliki ordering stabil.

Default:

```
OperationId ascending
```

atau:

```
Plan order
```

Jangan:

```
filesystem traversal order
```

atau:

```
completion order
```

karena tidak deterministic.

42. Filtering

Public result dapat mendukung:

```
status
reason_code
operation_type
```

Contoh:

```
show only:
    unknown
    failed
```

Filtering hanya membaca JobResult.

43. Result Retention

JobResult tidak harus disimpan selamanya.

Policy retention harus configurable.

Contoh:

```
active jobs:
    full result

recent jobs:
    full summary + bounded details

old jobs:
    summary only
```

Audit retention dapat memiliki policy berbeda.

44. Crash-safe Result Publication

Jangan publish:

```
Job completed
```

sebelum result tersedia secara konsisten.

Flow:

```
collect results
    │
    ▼
aggregate
    │
    ▼
validate invariants
    │
    ▼
persist/publish result
    │
    ▼
mark terminal
    │
    ▼
emit completion event
```

45. Completion Event

Setelah terminal state dipublish:

```
JobCompletedEvent
```

harus membawa reference:

```
JobId
```

bukan seluruh result besar.

Consumer kemudian dapat mengambil:

```
JobResult
```

Dengan demikian event tetap kecil.

46. Event Delivery

Completion event harus aman jika duplicate.

Contoh:

```
event emitted
   │
   ▼
consumer restart
   │
   ▼
event delivered again
```

Consumer harus dapat menangani:

```
duplicate JobCompletedEvent
```

Maka event harus memiliki:

```
event_id
job_id
sequence
```

47. Idempotent Reporting

Reporter boleh dipanggil lebih dari sekali.

```
report(JobResult)
   │
   ├── first → output
   ├── second → same semantic output
   └── third → same semantic output
```

Reporter tidak boleh menyebabkan mutation.

48. No Side Effect Dari Reporting

Dilarang:

```
report()
   │
   ├── refresh filesystem
   ├── retry job
   ├── modify scheduler
   └── mutate state
```

Reporting harus:

```
pure/read-only
```

49. Result Validation

Sebelum publish, aggregator harus memvalidasi invariant.

Contoh:

```
verified + partial + failed + unknown
    ≤
attempted
```

dan:

```
attempted ≤ planned
```

serta:

```
removed_bytes ≤ attempted_bytes
```

Jika invariant dilanggar:

```
internal consistency error
```

Job tidak boleh dipublikasikan sebagai Completed dengan result korup.

50. Internal Consistency Error

Jika bug internal menyebabkan:

```
impossible result
```

maka:

```
JobResultStatus::Failed
```

dengan reason:

```
INTERNAL_RESULT_INCONSISTENCY
```

Detail internal masuk log/diagnostics, bukan public API secara mentah.

51. No Fabricated Metrics

Jika bytes tidak diketahui:

```
bytes_removed = unknown
```

Bukan:

```
bytes_removed = 0
```

karena:

```
0
```

berarti tidak ada bytes yang dihapus, sedangkan:

```
unknown
```

berarti tidak dapat ditentukan.

52. Unknown Semantics

Unknown harus tetap eksplisit pada semua level.

```
Operation
   │
   ▼
Unknown
   │
   ▼
JobSummary
   │
   ▼
JobResult
   │
   ▼
Reporter
```

Jangan menghilangkan unknown saat aggregation.

53. Partial Semantics

Partial juga harus dipertahankan.

Contoh:

```
100 operations
   │
   ├── 90 success
   ├── 8 partial
   └── 2 unknown
```

Job:

```
CompletedPartial
```

bukan:

```
Completed
```

54. Empty Job

Jika tidak ada candidate:

```
planned = 0
```

Result harus tetap valid.

Contoh:

```
state = Completed
operations = 0
bytes_removed = 0
summary = "No eligible targets found"
```

Ini bukan failure.

55. All Targets Rejected

Jika scan menemukan candidate tetapi semua ditolak Safety/Policy:

```
candidates = 100
authorized = 0
executed = 0
```

Job result harus membedakan:

```
"nothing eligible"
```

dari:

```
"everything rejected"
```

Contoh:

```
Completed
rejected = 100
```

atau state lain sesuai policy.

56. Explain Rejected vs Skipped

Classification:

```
Rejected:
    decision layer menolak operation.


Skipped:
    operation tidak dijalankan karena lifecycle,
    cancellation, budget, dependency, atau shutdown.
```

Contoh:

```
Safety rejection
    → Rejected


cancellation before execution
    → Skipped / Cancelled
```

Jangan mencampurkan keduanya.

57. Dependency Failure

Jika:

```
O1 = Failed
```

dan:

```
O2 bergantung pada O1
```

maka O2 mungkin:

```
SkippedDependency
```

Bukan:

```
Failed
```

karena O2 tidak pernah dieksekusi.

58. Result Graph

Untuk dependency-aware result:

```
O1
 │
 ├── Failed
 │
 ▼
O2
 │
 └── SkippedDependency
```

Aggregator harus mempertahankan causal relationship.

59. Failure Summary

Failure summary harus bounded.

Contoh:

```
failures:
    count = 17

    top reasons:
        TARGET_CHANGED: 8
        PERMISSION_DENIED: 5
        TYPE_CHANGED: 4
```

Jangan mengirim ribuan full error strings ke CLI.

60. Error Grouping

Group berdasarkan:

```
reason_code
operation_type
target_type
```

Contoh:

```
TARGET_CHANGED
   ├── regular_file: 10
   └── directory: 2
```

Ini membantu diagnosis tanpa membocorkan detail individual.

61. Audit Summary

JobResult dapat memiliki:

```
audit_summary {
    events = 124
    warnings = 3
    security_rejections = 2
}
```

Audit detail tetap berada pada audit subsystem.

62. Telemetry Summary

Metrics:

```
planned_operations
attempted_operations
verified_operations
unknown_operations
removed_bytes
verification_duration
total_duration
```

Semua metrics harus memiliki semantics jelas.

63. Privacy Boundary

Reporting harus menghormati:

```
package scope
user scope
path sensitivity
```

Public result sebaiknya menggunakan:

```
TargetId
PackageId
relative safe path
```

jika diperlukan.

64. Multi-user

Job dapat memiliki:

```
UserId
```

Result tidak boleh mencampurkan data antar-user tanpa authorization.

Contoh:

```
Job J1
  ├── user 0
  └── user 10
```

Reporter harus memastikan caller berhak melihat kedua scope tersebut.

65. IPC Authorization

IPC client tidak boleh meminta:

```
JobResult(job_id=arbitrary)
```

kemudian mendapatkan detail Job yang bukan miliknya.

Flow:

```
IPC Request
   │
   ▼
authorization
   │
   ▼
Result access
   │
   ▼
sanitized DTO
```

Read-only result tetap membutuhkan authorization.

66. CLI Authorization

Hal yang sama berlaku untuk CLI.

CLI tidak boleh otomatis dapat membaca semua:

```
job
audit
package
user
```

Access control harus mengikuti security model daemon.

67. Result Storage

Jika result dipersist:

```
ResultStore
```

Interface:

```
save(JobResult)
get(JobId)
list(Query)
delete(JobId)
```

ResultStore bukan bagian dari Executor.

68. ResultStore Tidak Menjadi Source of Truth Filesystem

ResultStore hanya menyimpan:

```
what system observed
```

Filesystem tetap:

```
source of truth untuk state aktual
```

Jangan menggunakan stale JobResult sebagai dasar destructive action.

69. New Job Dari Old Result

Jika user meminta:

```
retry failed operations
```

system tidak boleh langsung mengeksekusi operation dari JobResult.

Flow:

```
old JobResult
     │
     ▼
new request
     │
     ▼
new Scan
     │
     ▼
new Safety
     │
     ▼
new Policy
     │
     ▼
new Plan
     │
     ▼
new Authorization
     │
     ▼
new Execution
```

70. Audit Immutability

Audit event yang sudah committed tidak boleh diedit.

Jika terjadi koreksi:

```
append new event
```

bukan:

```
modify old event
```

Contoh:

```
event 10:
    verification = unknown

event 11:
    reconciliation = verified
```

History tetap terlihat.

71. Reconciliation

Untuk Unknown outcome:

```
JobResult
   │
   └── Unknown
          │
          ▼
      reconciliation
          │
          ▼
     new observation
          │
          ▼
      new event
```

Reconciliation tidak mengubah historical event.

72. Historical Truth vs Current Truth

Audit:

```
historical observation
```

Filesystem:

```
current state
```

Contoh:

```

    target existed at scan time
```

Filesystem sekarang:

```
target absent
```

Keduanya bisa benar.

73. Explain Historical Context

Explain harus menjelaskan context:

```

    generation G10

    generation G11
```

Dengan demikian user memahami mengapa hasil lama tidak dapat dijadikan authorization baru.

    → breaking

Versioning harus eksplisit.

85. Failure Containment

Jika Reporter gagal:

```
JobResult tetap valid.
```

Jika AuditSink gagal:

```
execution result tidak boleh berubah menjadi success palsu.
```

Jika IPC disconnected:

```
Job tetap selesai sesuai lifecycle.
```

Contoh:

```
Job Completed
   │
   ├── IPC disconnected
   │
   ▼
JobResult tetap Completed
```

Transport failure bukan execution failure.

86. Audit Failure Policy

Audit sink failure harus memiliki policy eksplisit.

Pilihan:

```
strict:
    audit failure prevents completion
```

atau:

```
best-effort:
    completion tetap terjadi
    audit failure dicatat
```

Untuk security-sensitive events, sebagian event dapat menggunakan strict mode.

Jangan biarkan policy ini implicit.

87. Reporter Failure

Reporter adalah consumer.

Jika:

```
CLI output write failed
```

maka:

```
Job tidak menjadi Failed
```

Contoh:

```
filesystem cleanup
    → Completed

stdout pipe closed
    → report failed
```

Dua hal tersebut berbeda.

88. IPC Disconnect

Jika client disconnect setelah Job accepted:

```
Job lifecycle tetap berjalan sesuai contract.
```

Jika client disconnect sebelum request diterima:

```
tidak ada Job
```

Jika request sudah diterima dan JobId sudah diterbitkan:

```
disconnect ≠ cancellation
```

Cancellation harus eksplisit.
