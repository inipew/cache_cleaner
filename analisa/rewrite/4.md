Lanjut. Sekarang kita masuk ke bagian yang menurut saya paling menentukan kualitas rewrite: **Target Catalog → Candidate → Operation**. Kalau tiga lapisan ini benar, bagian scanner, safety, planner, dan executor akan jauh lebih mudah dipisahkan.

Sebagai acuan, struktur repo sekarang memang masih mengelompokkan logika berdasarkan `engine`, `hardware`, `platform`, dan `system`; rewrite sebaiknya mengubahnya menjadi alur berdasarkan **tanggung jawab dan tingkat risiko**, bukan sekadar memindahkan file.

# 1. Target Catalog

Jangan mulai dengan:

```rust
if path.ends_with("/cache") {
    delete(path);
}
```

Itu terlalu berbahaya untuk daemon privileged.

Lebih baik sistem mengenal **jenis target** secara eksplisit.

```rust
pub enum TargetKind {
    AppCache,
    AppCodeCache,
    AppExternalCache,

    PackageManagerCache,
    FrameworkCache,
    Temporary,

    Unknown,
}
```

Kemudian setiap target mempunyai descriptor:

```rust
pub struct TargetRoot {
    pub id: TargetId,
    pub kind: TargetKind,
    pub root: TrustedRoot,
    pub scope: TargetScope,
    pub storage: StorageDomain,
    pub policy: TargetPolicy,
}
```

Dengan:

```rust
pub enum TargetScope {
    User {
        user_id: u32,
        package: String,
    },
    System,
    Global,
}
```

dan:

```rust
pub enum StorageDomain {
    DeviceEncrypted,
    CredentialEncrypted,
    Shared,
    External,
}
```

Tujuannya supaya path **tidak menjadi sumber kebenaran utama**.

Path hanya representasi fisik.

Yang menentukan apakah sesuatu boleh dibersihkan adalah:

```text
TargetKind
   ↓
TargetPolicy
   ↓
Safety rules
   ↓
Candidate
   ↓
Plan
```

# 2. Bedakan Target Root dan Entry

Ini penting.

Misalnya:

```text
/data/user/0/com.example.app/cache/
├── image/
│   ├── a.webp
│   └── b.webp
├── okhttp/
├── thumbnails/
└── temporary.bin
```

`cache/` adalah **TargetRoot**.

Sedangkan:

```text
image/
okhttp/
thumbnails/
temporary.bin
```

adalah **Candidate**.

Jadi:

```text
TargetRoot
    └── Scanner
          ├── Candidate
          ├── Candidate
          ├── Candidate
          └── Candidate
```

Jangan membuat scanner menganggap setiap direktori sebagai target independen.

# 3. Cache Root Jangan Dihapus

Saya sangat menyarankan operasi utama untuk app cache adalah:

```rust
PurgeDirectoryContents
```

bukan:

```rust
RemoveDirectory
```

Contoh:

```text
cache/
├── a
├── b
└── subdir/
```

Yang dilakukan:

```text
cache/
    ↓
hapus a
hapus b
hapus subdir/*
    ↓
cache/ tetap ada
```

Bukan:

```text
remove_dir_all(cache)
mkdir(cache)
```

Alasannya sederhana: directory root tersebut bisa mempunyai metadata, permission, ownership, dan filesystem/security context yang sebaiknya dipertahankan.

Jadi operasi:

```rust
pub enum Operation {
    PurgeDirectoryContents {
        target: TargetId,
    },

    RemoveEntry {
        candidate: CandidateId,
    },

    RemoveEmptyDirectory {
        candidate: CandidateId,
    },

    TrimFilesystem {
        filesystem: FilesystemId,
    },

    F2fsMaintenance {
        filesystem: FilesystemId,
    },

    ZramMaintenance,

    FrameworkMaintenance,
}
```

# 4. Candidate Harus Berisi Informasi yang Cukup

Jangan membuat candidate hanya:

```rust
pub struct Candidate {
    pub path: PathBuf,
}
```

Itu terlalu miskin informasi.

Lebih baik:

```rust
pub struct Candidate {
    pub id: CandidateId,
    pub target: TargetId,

    pub name: OsString,
    pub file_type: EntryType,

    pub size: u64,
    pub age: Duration,

    pub filesystem: FilesystemInfo,
    pub user: Option<UserId>,

    pub safety: SafetySnapshot,
}
```

Contoh hasil scanner:

```text
Candidate #184
target      = AppCache
user        = 0
package     = com.example.app
name        = thumbnails
type        = Directory
size        = 184 MB
age         = 14 days
filesystem  = /data
```

Kemudian policy engine yang menentukan:

```text
14 days old
+
AppCache
+
trusted root
+
not symlink
+
same device
+
user unlocked
+
screen idle
=
ALLOW
```

# 5. Jangan Campur "Discovery" dengan "Permission"

Misalnya scanner menemukan:

```text
/data/user/0/com.example.app/cache/foo
```

Scanner hanya boleh mengatakan:

> "Saya menemukan entry."

Bukan:

> "Entry ini aman untuk dihapus."

Jadi:

```rust
scanner::discover()
```

menghasilkan:

```rust
Vec<Candidate>
```

lalu:

```rust
policy::evaluate()
```

menghasilkan:

```rust
Decision
```

# 6. Decision Model

Saya akan menggunakan tiga hasil utama:

```rust
pub enum Decision {
    Allow,
    Reject(RejectReason),
    Defer(DeferReason),
}
```

Contoh:

```rust
pub enum RejectReason {
    UnknownTarget,
    OutsideTrustedRoot,
    Symlink,
    WrongFilesystem,
    ProtectedPath,
    WrongFileType,
    TooYoung,
    InvalidUser,
    InvalidPackage,
    LockedStorage,
}
```

Sedangkan `Defer` berarti:

> sebenarnya target mungkin valid, tetapi sekarang belum waktunya.

Misalnya:

```rust
pub enum DeferReason {
    ScreenOn,
    UserActive,
    ThermalTooHigh,
    BatteryTooLow,
    StorageBusy,
    FilesystemMaintenanceActive,
}
```

Ini perbedaan penting:

```text
REJECT
= jangan pernah lakukan

DEFER
= mungkin lakukan nanti
```

# 7. Safety vs Policy

Jangan satukan semuanya dalam satu rule engine.

Saya ingin dua lapisan:

```text
                 Candidate
                     │
          ┌──────────▼──────────┐
          │     HARD SAFETY     │
          └──────────┬──────────┘
                     │
                 SAFE/REJECT
                     │
          ┌──────────▼──────────┐
          │    CLEAN POLICY     │
          └──────────┬──────────┘
                     │
               ALLOW/DEFER
```

## Hard safety

Tidak boleh dikonfigurasi menjadi lebih permisif.

Contoh:

```rust
if candidate.is_symlink() {
    return Reject(Symlink);
}
```

User tidak boleh menulis config:

```toml
allow_symlinks = true
```

dan membuat daemon kemudian menghapusnya.

Begitu juga:

```text
outside trusted root
wrong st_dev
unknown target
protected directory
device node
socket
```

harus menjadi **hard deny**.

# 8. Policy Boleh Dikonfigurasi

Sebaliknya, ini boleh configurable:

```toml
[policy.app_cache]
enabled = true
min_age = "3d"

[policy.app_code_cache]
enabled = false
min_age = "7d"

[policy.external_cache]
enabled = false

[policy.limits]
max_entries = 50000
max_bytes = 2147483648
max_duration = "30s"
```

Tetapi:

```text
config
  ↓
policy
```

tidak boleh mem-bypass:

```text
safety
```

# 9. Target Catalog yang Saya Sarankan untuk v2

Mulai konservatif.

| Target                |         Default |   Risiko | Catatan                     |
| --------------------- | --------------: | -------: | --------------------------- |
| App cache             |              ON |   rendah | kandidat utama              |
| App code cache        | OFF/konservatif |   sedang | perlu policy khusus         |
| External app cache    |             OFF |   sedang | filesystem/storage berbeda  |
| Package-manager cache |             OFF |   sedang | adapter khusus              |
| Framework cache       |             OFF |   tinggi | jangan dicampur app cache   |
| Temporary files       |             OFF |   sedang | perlu definisi sangat ketat |
| Unknown               |           NEVER | critical | hard deny                   |

Dan kategori:

```text
NEVER TOUCH
```

harus eksplisit.

Misalnya secara konseptual:

```rust
pub enum ProtectedKind {
    Database,
    SharedPreferences,
    AppFiles,
    NoBackup,
    NativeLibraries,
    PackageMetadata,
    UserDocuments,
    Unknown,
}
```

Prinsipnya:

> **unknown bukan cache.**

# 10. Jangan Jadikan `--deep` Sebagai "Delete More"

Ini juga perlu kita ubah dari desain lama.

`--deep` jangan berarti:

```text
scan lebih banyak
→ delete lebih banyak
```

Lebih baik:

```text
normal
    AppCache

deep
    AppCache
    + optional CodeCache
    + optional maintenance
    + optional framework maintenance
```

Jadi:

```rust
pub enum CleanProfile {
    Conservative,
    Normal,
    Deep,
}
```

Profile kemudian diterjemahkan menjadi policy.

```rust
pub struct PolicyContext {
    pub profile: CleanProfile,
    pub runtime: RuntimeContext,
    pub config: PolicyConfig,
}
```

Dengan begitu `--deep` tidak mempunyai kekuasaan langsung terhadap filesystem.

# 11. Planner

Setelah policy selesai, **baru** planner bekerja.

Input:

```text
Candidate[]
+
Decision[]
```

Output:

```rust
pub struct CleanupPlan {
    pub id: PlanId,
    pub operations: Vec<Operation>,
    pub summary: PlanSummary,
}
```

Misalnya:

```text
Candidate A → ALLOW
Candidate B → REJECT
Candidate C → ALLOW
Candidate D → DEFER
```

Planner menghasilkan:

```text
Plan
├── Remove A
└── Remove C
```

Bukan:

```text
scanner → delete
```

---

# 12. Planner Harus Memikirkan Parent/Child

Misalnya:

```text
cache/
└── foo/
    ├── a
    └── b
```

Kalau:

```text
a = delete
b = delete
foo = empty
```

planner bisa menghasilkan:

```text
Remove a
Remove b
Remove empty foo
```

Tetapi jangan menghasilkan:

```text
Remove foo
Remove a
Remove b
```

Urutan harus jelas.

Untuk tree deletion:

```text
children first
parent last
```

Secara umum:

```rust
pub fn order_operations(
    operations: Vec<Operation>,
) -> Vec<Operation>;
```

# 13. Executor Harus "Bodoh"

Ini prinsip yang sangat saya rekomendasikan.

Jangan membuat executor seperti:

```rust
fn execute(path: PathBuf) {
    if path.ends_with("cache") {
        ...
    }
}
```

Executor seharusnya menerima:

```rust
AuthorizedOperation
```

Contoh:

```rust
pub struct AuthorizedOperation {
    pub operation: Operation,
    pub authorization: AuthorizationToken,
}
```

Kemudian:

```rust
pub trait Executor {
    fn execute(
        &self,
        operation: AuthorizedOperation,
    ) -> Result<OperationResult>;
}
```

Executor tidak memutuskan:

> "boleh hapus atau tidak?"

Itu sudah diputuskan sebelumnya.

# 14. Tetapi Executor Tetap Harus Revalidate

Ini tidak kontradiktif.

Alurnya:

```text
scan
 ↓
policy
 ↓
plan
 ↓
authorization
 ↓
REVALIDATE
 ↓
execute
```

Kenapa?

Karena filesystem bisa berubah.

Contoh:

```text
T0:
foo = regular directory

T1:
scanner selesai

T2:
attacker/process mengganti foo
menjadi symlink

T3:
executor mencoba delete
```

Kalau executor percaya hasil scan 100%, kita punya TOCTOU.

Jadi sebelum destructive syscall:

```rust
fn revalidate_target(
    target: &PlannedTarget,
) -> Result<ValidatedTarget>;
```

# 15. File Descriptor adalah Boundary Security

Untuk operasi privileged, saya ingin jalur seperti:

```text
TrustedRoot
    ↓
openat()
    ↓
DirectoryHandle
    ↓
openat(parent_fd, child)
    ↓
EntryHandle
    ↓
fstatat(..., NOFOLLOW)
    ↓
validate
    ↓
unlinkat()
```

Bukan:

```text
PathBuf
 ↓
canonicalize()
 ↓
remove_file()
```

Dan terutama bukan:

```rust
Command::new("rm")
    .arg("-rf")
    .arg(path)
```

Dengan desain ini, filesystem layer menjadi tempat satu-satunya yang menangani primitive berbahaya.

# 19. Dan Ini Menghasilkan Security Boundary yang Jelas

Pada akhirnya saya ingin hanya satu jalur yang boleh melakukan destructive action:

```text
CLI / IPC
    ↓
Request
    ↓
Controller
    ↓
Scanner
    ↓
Policy
    ↓
Safety
    ↓
Planner
    ↓
Revalidation
    ↓
Authorization
    ↓
Executor
    ↓
Filesystem syscall
```

Tidak boleh ada shortcut seperti:

```text
CLI ───────────────→ filesystem
IPC ───────────────→ filesystem
scheduler ─────────→ filesystem
scanner ───────────→ delete
policy ────────────→ delete
```

**Hanya Executor yang destructive.**

Dan Executor hanya menerima operation yang sudah melewati seluruh boundary.

## Tahap berikutnya

Setelah Target Catalog dan Function Catalog ini, bagian yang paling menarik untuk kita bedah adalah **filesystem engine** karena ini jantung keamanan `cache_cleaner`.

Kita bisa desain sampai level konkret:

```text
TrustedRoot
   ↓
DirFd
   ↓
openat()
   ↓
fstatat(NO_FOLLOW)
   ↓
EntryHandle
   ↓
same st_dev
   ↓
symlink protection
   ↓
race handling
   ↓
unlinkat()
```

termasuk desain `struct DirFd`, `Entry`, `TrustedRoot`, error model, recursive walker, **TOCTOU/rename attack**, mount boundary, dan bagaimana membuatnya aman untuk Android `/data` tanpa `remove_dir_all()`. Ini menurut saya bagian yang harus benar-benar kita selesaikan **sebelum** menulis scanner dan cleaner lainnya.
