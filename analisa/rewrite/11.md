Lanjut. Sekarang kita masuk ke **IPC + Authorization + Protocol**. Ini adalah **control plane** dari daemon.

Tujuan desainnya bukan sekadar “bisa menerima command dari CLI”, tetapi memastikan:

> **Client hanya boleh meminta intent. Client tidak pernah menentukan operasi filesystem secara langsung.**

Jadi bahkan Root sekalipun tetap masuk melalui pipeline yang sama.

---

# 1. Posisi IPC

Arsitektur lengkapnya:

```text
CLI
 │
 │ Unix Domain Socket
 ▼
┌─────────────────────┐
│     IPC Server      │
├─────────────────────┤
│ decode              │
│ validate protocol   │
│ peer credentials    │
│ authorize command   │
└──────────┬──────────┘
           │
           ▼
      JobRequest
           │
           ▼
       Scheduler
           │
           ▼
       JobController
           │
           ▼
 Scanner → Safety → Policy → Planner
           │
           ▼
        Executor
```

Yang **tidak boleh** terjadi:

```text
CLI
 ↓
IPC
 ↓
unlink()
```

---

# 2. IPC harus command-oriented

Client mengirim **intent**, bukan filesystem instruction.

Contoh request:

```rust
pub enum Request {
    Status,
    StartCleanup(CleanRequest),
    Explain(ExplainRequest),
    ReloadConfig,
    Restart,
    Stop,
}
```

Bukan:

```rust
DeleteFile {
    path: String,
}
```

atau:

```rust
RunCommand {
    command: String,
}
```

Ini salah secara arsitektur.

---

# 3. `CleanRequest`

Misalnya:

```rust
pub struct CleanRequest {
    pub profile: CleanProfile,
    pub dry_run: bool,
    pub enable_trim: bool,
    pub enable_f2fs: bool,
    pub enable_zram: bool,
}
```

Kemudian:

```rust
pub enum CleanProfile {
    Conservative,
    Normal,
    Deep,
}
```

Client:

```text
cleaner clean
```

menghasilkan:

```text
CleanRequest {
    profile: Normal,
    ...
}
```

Sedangkan:

```text
cleaner clean --deep --trim
```

menjadi:

```text
CleanRequest {
    profile: Deep,
    enable_trim: true,
    ...
}
```

Tetapi request ini **belum berarti operasi tersebut pasti akan dijalankan**.

# 4. CLI tidak boleh menentukan target

Misalnya user mencoba:

```text
cleaner clean --path /data/user/0/foo
```

Saya justru tidak akan menyediakan option seperti itu untuk daemon privileged.

Kenapa?

Karena itu mengubah model:

```text
intent
```

menjadi:

```text
arbitrary privileged filesystem access
```

Lebih baik:

```text
cleaner clean --package com.example.foo
```

pun tetap diperlakukan sebagai **filter intent**, lalu target sebenarnya harus ditemukan dan divalidasi oleh engine.

# 5. Protocol versioning

Protocol harus punya version.

Misalnya:

```rust
pub struct RequestEnvelope {
    pub version: u16,
    pub request_id: RequestId,
    pub request: Request,
}
```

Response:

```rust
pub struct ResponseEnvelope {
    pub version: u16,
    pub request_id: RequestId,
    pub response: Response,
}
```

Sehingga:

```text
request ID = 1042
```

response selalu bisa dicocokkan:

```text
response ID = 1042
```

# 6. Request ID

Jangan mengandalkan urutan request.

Client bisa:

```text
request 100
request 101
request 102
```

dan response mungkin:

```text
102
100
101
```

kalau nanti asynchronous.

Maka:

```rust
pub struct RequestId(pub u64);
```

menjadi mandatory.

Untuk versi pertama kita boleh memproses satu request per connection secara sequential, tetapi tetap sebaiknya protocol sudah punya ID.

# 13. Authorization dimulai dari `SO_PEERCRED`

Unix Domain Socket memberi kemampuan mendapatkan peer credentials.

Server membaca:

```text
pid
uid
gid
```

secara kernel-provided.

Kemudian:

```rust
pub struct PeerIdentity {
    pub pid: Pid,
    pub uid: Uid,
    pub gid: Gid,
}
```

Jangan menerima:

```text
uid
```

dari payload client.

Payload:

```json
{
    "uid": 0
}
```

tidak mempunyai authority.

Yang dipercaya:

```text
SO_PEERCRED
```

# 23. Protocol format

Untuk internal daemon, saya menyarankan **length-prefixed binary protocol** daripada parsing text bebas.

Misalnya:

```text
┌────────────┬──────────┬────────────┬──────────────┐
│ length u32 │ version  │ request_id │ payload      │
└────────────┴──────────┴────────────┴──────────────┘
```

Payload dapat menggunakan serialization library yang deterministic dan versionable.

Tidak perlu JSON untuk internal privileged IPC.

---

# 24. Kenapa bukan JSON?

JSON memang mudah debug:

```json
{
  "command": "clean",
  "deep": true
}
```

tetapi binary protocol memberi:

* schema lebih eksplisit
* type safety
* payload lebih kecil
* parsing lebih predictable
* lebih mudah reject unknown/invalid fields secara ketat

Namun untuk versi awal, **JSON-line juga masih acceptable** jika implementasi jauh lebih sederhana. Security boundary tetap berasal dari typed validation dan authorization, bukan karena format binary.

Kalau memilih binary, saya lebih menyukai protocol sederhana daripada framework RPC besar.

# 32. Security boundary IPC

Saya akan membagi IPC menjadi:

```text
ipc/
├── protocol.rs
├── framing.rs
├── server.rs
├── client.rs
├── auth.rs
├── permissions.rs
└── errors.rs
```

### `protocol.rs`

Domain request/response.

### `framing.rs`

Length-prefix/read/write.

### `server.rs`

Socket accept loop.

### `auth.rs`

`SO_PEERCRED`.

### `permissions.rs`

Role/capability matrix.

### `client.rs`

CLI client.

# 33. IPC Server tidak boleh punya cleanup logic

Server:

```rust

    authorize(req)?;
    scheduler.submit(req)
```

```rust
fn handle_request(req: Request) {
    match req {

            scan();
```

# 44. Invariant IPC

Saya akan menetapkan:

```text
1. Client cannot specify arbitrary filesystem paths for deletion.

2. Client cannot directly invoke Executor.

3. Client cannot bypass Safety.

4. Client cannot bypass Policy.

5. Root authorization does not disable safety invariants.

6. Peer identity comes from SO_PEERCRED, never request payload.

7. Every request has a bounded size.

8. Every request has a protocol version.

9. Every request has a request ID.

10. Long-running cleanup is asynchronous.

11. Client disconnect does not implicitly cancel an accepted job.

12. Only one cleanup job executes at a time.

13. Invalid config never replaces valid config.

14. Restart/stop use graceful daemon lifecycle.

15. Explain and status are read-only.
```

---

```text
             ┌──────────────────────┐
             │       CLI / IPC      │
             └──────────┬───────────┘
                        ↓
                Authentication
                        ↓
                 Authorization
                        ↓
                  JobRequest
                        ↓
                   Scheduler
                        ↓
                  JobController
                        ↓
                    Scanner
                        ↓
                     Safety
                        ↓
                     Policy
                        ↓
                    Planner
                        ↓
                  AuthorizedPlan
                        ↓
                    Executor
                        ↓
                   Verifier
                        ↓
                     Report
```

**Tahap berikutnya sebaiknya kita turun ke `Platform + Android + FBE + Multi-user + SELinux`**, karena di situlah arsitektur generic Linux tadi harus diterjemahkan ke Android nyata: bagaimana menemukan user/profile, membedakan DE/CE storage, mendeteksi CE locked/unlocked, menentukan target per-user, menangani Android 9–16, SELinux context/permission, package identity, `/data/user/*`, `/data/user_de/*`, `/storage/emulated/*`, serta bagaimana Target Catalog dibangun tanpa hard-code path yang rapuh.
