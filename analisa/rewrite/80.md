# 80.md — CLI Contract, Command Semantics, Output, Exit Codes, Idempotency, Configuration, Safety, and Operational UX

## Tujuan

CLI adalah operational interface, bukan implementation shortcut. CLI harus menjadi thin client terhadap domain/IPC contract dan tidak boleh memiliki cleaning semantics sendiri.

## 1. CLI Boundary

```text
argv → parse → validate → request DTO → domain/IPC
```

## 2. Parser

Gunakan typed command enum. Jangan menyebarkan string command ke business logic.

## 3. Command Groups

Recommended:

```text
cache-cleaner
  status
  targets
  scan
  plan
  clean
  cancel
  job
  config
  maintenance
  recover
  diagnostics
```

Exact names may evolve, semantics must remain stable.

## 4. Read vs Mutating Commands

Read-only commands harus jelas dibedakan dari destructive commands.

## 5. `status`

Menampilkan daemon health, lifecycle state, active jobs, resource pressure, config/catalog generation, dan last result yang diizinkan.

## 6. `targets`

Menampilkan TargetCatalog snapshot. Output tidak boleh menyiratkan bahwa target otomatis boleh dihapus.

## 7. `scan`

Scan hanya discovery/candidate generation. Tidak boleh mutation.

## 8. `plan`

Plan menghasilkan immutable plan preview tanpa execute.

## 9. `clean`

Clean membuat durable Job lalu mengikuti lifecycle normal.

## 10. `job`

Query status/result/recovery state dari JobId.

## 11. `cancel`

Meminta cancellation, bukan memaksa syscall berhenti.

## 12. `config`

Subcommands:

- show
- validate
- reload
- get
- set

Persistent mutation harus melalui validated atomic config update.

## 13. `maintenance`

TRIM/F2FS/ZRAM/sysfs operation harus explicit dan capability-gated.

## 14. `recover`

Recovery/admin operations harus privileged dan audited.

## 15. `diagnostics`

Tidak boleh menjadi hidden mutation interface.

## 16. Dangerous Command Confirmation

Interactive CLI dapat meminta confirmation untuk high-risk operation, tetapi confirmation bukan pengganti server-side authorization/safety.

## 17. Non-Interactive Mode

`--yes`/non-interactive hanya menghilangkan prompt; tidak boleh bypass safety.

## 18. Dry Run

Dry-run harus menghasilkan plan yang tidak mempunyai mutation authority.

## 19. Output Modes

Recommended:

- human
- JSON
- JSON Lines untuk streaming

## 20. Stable JSON

Machine-readable output harus mempunyai stable field names dan explicit schema version.

## 21. Human Output

Human output boleh berubah selama semantic contract dan exit codes dipertahankan.

## 22. Secret Redaction

Config/status output harus selalu meredact secrets.

## 23. Path Privacy

Verbose path output harus explicit; default sebaiknya minimal untuk sensitive locations.

## 24. Progress

Long-running jobs dapat menggunakan progress events.

## 25. Progress Is Not Result

100% progress tidak otomatis berarti successful verification.

## 26. Completion

CLI harus menunggu terminal Job state bila command mode meminta synchronous behavior.

## 27. Async Mode

Async submission mengembalikan JobId setelah durable acceptance.

## 28. Lost Response

Jika response submit hilang, client dapat retry dengan idempotency key.

## 29. Exit Codes

Recommended semantic classes:

```text
0  success
1  generic/operational failure
2  invalid CLI usage
3  invalid configuration/request
4  unauthorized/forbidden
5  not found
6  conflict/stale
7  resource unavailable
8  cancelled
9  timeout
10 recovery required/unknown outcome
```

Actual numeric mapping should remain stable once public.

## 30. Partial Success

If Job completed with partial failures, exit code must not falsely report full success.

## 31. Unknown Outcome

RecoveryRequired must have distinct non-success exit code.

## 32. Cancellation

User-requested cancellation may use dedicated exit code even if some operations already completed.

## 33. Timeout

CLI wait timeout should distinguish local wait timeout from server Job TimedOut.

## 34. `--timeout`

Default meaning must be documented: request wait timeout or Job deadline.

Never overload one flag with both semantics.

## 35. `--config`

Config path is input to config loader and remains untrusted until validated.

## 36. `--target`

Target selector must resolve through TargetCatalog; it is not raw filesystem authority.

## 37. `--path`

If supported, path is candidate/location input and must pass Safety resolution.

## 38. `--package`

Package selector must use typed package validation.

## 39. `--user`

User selector must be validated against platform scope.

## 40. `--force`

Avoid generic `--force`. If needed, define exact semantic such as `--ignore-interactive-confirmation`; never let it bypass Safety/Authorization.

## 41. `--dry-run`

Must not create executable authorization.

## 42. `--json`

Must not suppress critical security/recovery errors merely to preserve formatting.

## 43. Error Streams

Human errors should go stderr; machine protocol should remain parseable.

## 44. stdout Contract

Successful structured data goes stdout.

## 45. stderr Contract

Diagnostics/warnings/progress can go stderr unless JSON streaming contract says otherwise.

## 46. TTY Detection

Interactive confirmation only when appropriate TTY is present.

## 47. Piped Input

Never assume stdin is interactive.

## 48. Signal Handling

SIGINT/SIGTERM should request cancellation/shutdown according to command context.

## 49. Double Ctrl-C

Second interrupt may request forced client exit, but must not fabricate server cancellation/completion.

## 50. Daemon Commands

CLI should use IPC to daemon when daemon mode is active.

## 51. Embedded Mode

If embedded execution remains supported, use the same domain services and state semantics.

## 52. No Duplicate Engine

Do not maintain separate CLI cleaning algorithm.

## 53. `targets` Output

Show:

- TargetId
- kind
- scope
- availability
- safety class
- capabilities
- generation

Avoid claiming capability equals permission.

## 54. `scan` Output

Show candidate count, bytes, skipped/unknown counts, generation, and bounded diagnostics.

## 55. `plan` Output

Show operation summary, policy decisions, safety prerequisites, estimated bytes/count, and bound generations.

## 56. `clean` Output

Show JobId and state. Do not print "deleted" until verifier confirms.

## 57. Job Watch

`job watch <id>` should reconnect/replay from event cursor after disconnect.

## 58. Job Result

Result should expose:

- terminal state
- operations completed
- verified bytes
- failed/skipped/unknown counts
- reason
- generations

## 59. Config Validation

`config validate` must not mutate active config.

## 60. Config Reload

`config reload` only replaces active config after full validation and atomic commit.

## 61. Config Show

Show effective normalized config, not raw potentially invalid input.

## 62. Maintenance Confirmation

High-risk system-wide maintenance should require explicit command and privilege checks.

## 63. Recovery UX

If Job is RecoveryRequired, CLI should explain that retrying the mutation is unsafe until reconciliation.

## 64. Diagnostics

Diagnostic commands should expose safe evidence, not internal secret state.

## 65. Shell Completion

Completion must not perform filesystem mutation or privileged discovery with side effects.

## 66. Exit Status From Daemon

Daemon result maps to CLI exit code through stable adapter.

## 67. Protocol Error

Malformed/unsupported response should return internal/protocol failure, never success.

## 68. Compatibility

CLI can negotiate protocol version and gracefully reject unsupported server versions.

## 69. Deprecation

Old flags should emit warnings before removal.

## 70. Alias

Aliases must map to one canonical command semantics.

## 71. Environment Variables

Environment overrides must have explicit precedence and validation. Secrets from environment must be redacted.

## 72. Configuration Precedence

Recommended:

```text
built-in defaults
→ config file
→ environment
→ explicit CLI override
```

Only permitted fields may be overridden.

## 73. Authorization Boundary

CLI arguments never expand server-side authority.

## 74. Audit

Mutating CLI commands should send caller identity/context to the server audit layer.

## 75. Definition of Done

CLI production-ready if:

- typed commands
- stable exit codes
- machine-readable output
- durable async Job IDs
- idempotent submit
- explicit timeout semantics
- cancellation semantics
- no `force` safety bypass
- config atomicity
- recovery-aware UX
- secret/path redaction
- protocol compatibility
- no duplicate business logic

## 76. Final Invariants

1. CLI is not an authority.
2. CLI cannot bypass Safety.
3. CLI cannot grant Authorization.
4. `--yes` only suppresses confirmation.
5. `--force` never bypasses safety.
6. Dry-run never grants mutation capability.
7. Progress never equals verification success.
8. Lost submit response is recoverable through idempotency.
9. Disconnect does not cancel Job.
10. RecoveryRequired is never reported as success.
11. CLI and daemon share one domain contract.
12. Machine-readable output has stable schema.
13. Config changes are validated and atomic.
14. Privileged commands are audited.
15. Exit codes remain semantically stable.
