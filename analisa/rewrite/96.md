# 96.md — Android Lifecycle, Process Survival, Suspend/Resume, dan Process Death

## Tujuan

Daemon Android tidak boleh mendefinisikan lifecycle seperti server Linux biasa. Process dapat dihentikan, device dapat suspend, screen dapat off, thermal/power policy dapat berubah, dan system dapat reclaim process.

Kontrak utama:

```text
process alive ≠ daemon work guaranteed
screen off ≠ deep sleep
resume ≠ clean startup
process death ≠ data loss
```

## 1. Lifecycle Model

State minimal:

```text
Starting
Ready
Idle
Working
Suspending
Recovering
ShuttingDown
Degraded
```

State lifecycle harus berbeda dari Job state.

## 2. Process Survival

Daemon tidak boleh mengandalkan process selalu hidup.

Semua state yang diperlukan recovery harus durable sesuai `86.md`.

## 3. In-Memory State

RAM hanya boleh menyimpan reconstructable state seperti:

- cached catalog
- queue snapshot
- worker runtime
- scheduler wait state

State yang menentukan recovery outcome harus durable.

## 4. Screen Off

Screen off hanya sebuah signal.

Daemon tidak boleh otomatis menjalankan maintenance besar hanya karena screen off.

## 5. Device Idle

Device idle adalah power-management condition yang berbeda dari screen off.

Scheduler harus menghormati platform power policy.

## 6. Suspend

Sebelum suspend, daemon idealnya berada pada blocked state jika tidak ada urgent bounded work.

Jangan mempertahankan periodic runnable loop untuk menjaga process "aktif".

## 7. Resume

Resume menjadi revalidation boundary.

Setelah resume:

```text
wake
→ lightweight snapshot
→ inspect relevant generations/events
→ invalidate stale context
→ continue or block
```

Tidak perlu full rescan secara otomatis.

## 8. Missed Deadlines

Timer yang terlewat selama suspend tidak boleh menghasilkan execution storm.

Multiple missed schedules harus coalesce menjadi bounded work.

## 9. Clock Choice

Gunakan clock berdasarkan semantics:

- monotonic untuk durations
- boot-relative clock jika perlu elapsed time across suspend
- wall clock untuk human/calendar schedule

## 10. Wakeup Semantics

Ordinary process timer tidak boleh diasumsikan dapat membangunkan suspended device.

Jika true wake-from-suspend diperlukan, gunakan Android/platform mechanism yang memang mempunyai semantics tersebut.

## 11. Wakelock

Wakelock bukan mekanisme default untuk membuat daemon reliable.

Jika diperlukan:

```text
acquire
→ bounded work
→ durable state
→ release
```

## 12. Process Death During Idle

Tidak ada special recovery jika tidak ada active durable operation.

Startup cukup rebuild runtime state.

## 13. Process Death During Mutation

Recovery mengikuti durable journal:

```text
Prepared
MutationMayStart
MutationStarted
ReceiptRecorded
...
```

Jika outcome tidak dapat dibuktikan, classify Unknown dan reconcile.

## 14. Process Death During Scan

Scan state dapat dibuang jika candidate list reconstructable.

Jangan memperlakukan partial scan sebagai complete scan.

## 15. Process Death During Planning

Plan yang belum durable dapat dibuang.

Jika plan sudah durable tetapi tidak compatible dengan current context, revalidate/replan.

## 16. Process Death During Verification

Mutation mungkin sudah terjadi.

Recovery harus verify actual state daripada mengulang mutation secara blind.

## 17. Startup Recovery Order

Urutan startup yang direkomendasikan:

```text
load minimal runtime
→ open durable store
→ validate/migrate
→ recover leases
→ recover unresolved operations
→ rebuild queues
→ initialize platform snapshot
→ activate scheduler
→ block when idle
```

## 18. Recovery Before New Work

Unresolved operations pada target harus ditangani sebelum scheduler menerima new mutation pada target yang sama.

## 19. Platform Events

Relevant Android events dapat meliputi:

- power/battery
- thermal
- screen
- storage/mount
- package/user lifecycle
- daemon control

Events adalah signals, bukan durable truth.

## 20. Event Loss

Android/process lifecycle dapat menyebabkan event loss.

Periodic/sparse reconciliation dan authoritative snapshots menjadi safety net.

## 21. Event Burst

Resume atau storage event burst harus coalesced.

Jangan membuat satu Job per event.

## 22. Thermal Changes

Thermal pressure dapat menurunkan work admission/concurrency.

Thermal event tidak boleh memicu busy polling.

## 23. Battery Changes

Battery state dapat mempengaruhi policy/schedule.

Policy re-evaluation harus bounded.

## 24. Storage Mount Changes

Mount/unmount adalah context invalidation boundary.

Target catalog generation dapat berubah.

Existing plan terhadap mount yang berubah harus stale/revalidated.

## 25. Package Changes

Package install/uninstall/update dapat membuat target identity berubah.

Path existence saja tidak membuktikan object yang sama.

## 26. User/Profile Changes

Jika daemon mendukung multiple Android users/profiles, scope identity harus memasukkan user/profile context.

Jangan mencampur cache namespace antar user.

## 27. Boot

Boot startup harus ringan.

Jangan melakukan full cleanup otomatis sebelum runtime/platform state siap dan policy mengizinkan.

## 28. Boot Storm

Multiple lifecycle events saat boot harus coalesced.

Scheduler menunggu stable state sebelum expensive evaluation.

## 29. Shutdown

Shutdown sequence:

```text
stop admission
→ wake scheduler/workers
→ cancel new work
→ finish/abort according to operation contract
→ persist state
→ release resources
→ exit
```

## 30. Bounded Shutdown

Daemon tidak boleh menunggu indefinitely hanya karena satu worker macet.

Timeout harus menghasilkan explicit recovery state.

## 31. Restart

Restart harus setara dengan process death dari sisi durable correctness.

Tidak boleh ada hidden assumption bahwa shutdown selalu graceful.

## 32. Service Supervision

Jika deployment menggunakan Android service/root manager/supervisor, supervisor restart policy harus konsisten dengan daemon recovery semantics.

Supervisor bukan replacement untuk durable state.

## 33. Crash Loop

Repeated crash saat startup harus dicegah menjadi infinite restart storm.

Supervisor dapat backoff, daemon dapat enter degraded/recovery-required state.

## 34. Health During Recovery

Process hidup tetapi recovery belum selesai bukan `Healthy`.

Health = `Recovering`/`Degraded` sesuai kondisi.

## 35. Readiness

Readiness harus hanya true jika:

- durable store usable
- migration complete
- critical platform capabilities ready
- no blocking recovery condition

## 36. Liveness

Liveness menjawab apakah process/control loop masih responsif.

Liveness tidak membuktikan destructive execution safe.

## 37. Fast Resume

Fast resume dicapai dengan:

- minimal startup path
- persistent state
- bounded recovery
- lazy rebuild
- event-driven scheduler

Bukan dengan periodic CPU activity.

## 38. Memory Pressure

Android dapat reclaim memory.

Caches harus bounded dan reconstructable.

Durable queues/state tidak boleh bergantung pada in-memory object lifetime.

## 39. FD Reclamation

Process death otomatis menutup FDs, tetapi durable resource ownership tetap perlu recovery.

## 40. JNI/Native Boundary

Jika menggunakan JNI/native helper, process lifecycle crash dapat terjadi di luar Rust safety guarantees.

Boundary harus diperlakukan sebagai fault domain.

## 41. Long-Running Operation

Long cleanup harus chunked agar:

- cancellation feasible
- progress durable
- recovery bounded
- thermal adaptation possible

## 42. Background Work

Background execution harus mengikuti Android constraints dan deployment model.

Root privilege bukan alasan untuk mengabaikan platform power/lifecycle semantics.

## 43. Idle Target

Idle target:

```text
no Job
→ no worker activity
→ no polling
→ no unnecessary wakelock
→ scheduler blocked
→ device free to suspend
```

## 44. Resume Target

Resume target:

```text
platform event
→ bounded evaluation
→ enqueue/coalesce if eligible
→ return to blocked state
```

## 45. Definition of Done

Android lifecycle production-ready jika:

- process death recoverable
- suspend/resume semantics explicit
- screen-off tidak disalahartikan sebagai idle
- missed schedules coalesced
- wake semantics correct
- wakelock bounded
- lifecycle events coalesced
- mount/package/user changes invalidate context
- startup recovery precedes new work
- crash loop controlled
- readiness ≠ liveness
- idle state power-neutral

## Final Invariants

1. Process hidup bukan bukti work aman.
2. Process death harus recoverable.
3. Screen off bukan deep sleep.
4. Suspend bukan crash.
5. Resume adalah revalidation boundary.
6. Missed timers tidak boleh menghasilkan wake storm.
7. Ordinary timer tidak dijamin membangunkan device.
8. Wakelock hanya bounded exception.
9. Event adalah signal, snapshot/durable state adalah evidence.
10. Event burst harus coalesced.
11. Mount/package/user changes dapat invalidate target context.
12. Recovery harus mendahului new mutation pada target yang sama.
13. Readiness berbeda dari liveness.
14. Startup recovery harus bounded.
15. Crash loop harus dikendalikan.
16. In-memory state harus reconstructable.
17. Long operation harus chunkable.
18. Android power policy tetap berlaku.
19. Idle daemon tidak boleh mempertahankan runnable polling loop.
20. Fast resume berasal dari lightweight recovery, bukan busy activity.
