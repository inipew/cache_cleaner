# 86.md — Crash Consistency & Transaction Boundaries

## Tujuan

Failure model hanya berguna jika sistem mempunyai aturan yang jelas tentang apa yang harus tetap benar setelah process crash atau device kehilangan power.

Dokumen ini mendefinisikan batas durability antara durable state, filesystem mutation, journal, verification, dan publication.

Prinsip dasarnya:

```text
Durable intent
    ↓
mutation
    ↓
verification
    ↓
durable result
    ↓
publication
```

Crash di antara dua tahap tidak boleh membuat daemon mengarang state.

## 1. Durable State Adalah Sumber Recovery

State yang menentukan recovery harus persisted sebelum process mengandalkannya setelah restart.

In-memory state boleh menjadi cache, tetapi bukan satu-satunya sumber kebenaran.

Minimal yang perlu durable:

- Job state
- Attempt state
- Operation identity
- operation status
- plan identity/version
- relevant generations
- authorization identity/expiry
- journal state
- recovery state
- resource ownership yang perlu dipulihkan
- final result

## 2. Transaction Tidak Berarti Semua Mutation Bisa Di-rollback

Database transaction dapat meng-rollback perubahan database, tetapi tidak otomatis dapat meng-rollback:

- unlink
- rename
- mkdir
- chmod
- filesystem maintenance

Karena itu jangan mendesain seolah filesystem mutation dan database transaction adalah satu atomic transaction.

Model yang benar adalah **durable protocol dengan reconciliation**.

## 3. Mutation Boundary

Executor harus mempunyai titik yang jelas:

```text
prepare
  ↓
validate
  ↓
journal intent
  ↓
mutation boundary
  ↓
syscall
  ↓
journal receipt
  ↓
verification
```

Sebelum mutation boundary, cancellation dan failure umumnya masih dapat menghasilkan clean abort.

Setelah mutation boundary, hasil dapat menjadi Unknown.

## 4. Intent Harus Durable Sebelum Mutation

Sebelum mutation yang berpotensi destructive dilakukan, durable store/journal harus mengetahui bahwa operation akan dijalankan.

Contoh:

```text
persist OperationPrepared
commit
↓
execute unlink
```

Jangan:

```text
unlink
↓
baru persist "operation started"
```

Jika crash pada urutan kedua, recovery kehilangan evidence bahwa mutation mungkin sudah terjadi.

## 5. Journal Is Evidence

Journal mencatat fakta tentang lifecycle mutation.

Contoh state:

```text
Prepared
MutationMayStart
MutationStarted
ReceiptRecorded
VerificationStarted
Verified
Unknown
```

Journal bukan pengganti verifier.

`MutationStarted` tidak berarti mutation berhasil.

`ReceiptRecorded` juga tidak selalu berarti postcondition terpenuhi.

## 6. Commit Ordering

Untuk destructive operation, baseline ordering:

```text
1. validate fresh context
2. persist intent
3. commit intent
4. enter mutation boundary
5. perform syscall
6. persist receipt/result evidence
7. commit
8. verify fresh state
9. persist final classification
10. commit
11. publish
```

Jika implementation membutuhkan journal record tambahan sebelum syscall, record tersebut tetap harus durable sebelum syscall dapat dimulai.

## 7. Crash Matrix

Setiap boundary harus mempunyai recovery behavior eksplisit.

| Crash point | Recovery interpretation |
|---|---|
| sebelum intent commit | mutation belum boleh dianggap terjadi |
| setelah intent commit, sebelum syscall | safe to reconcile/abort according to operation state |
| syscall sedang/baru dimulai | Unknown |
| setelah syscall return, sebelum receipt commit | Unknown unless stronger evidence exists |
| receipt committed, verification belum selesai | needs verification |
| verification selesai, result belum commit | recompute/verify before terminalization |
| result commit, publication belum terjadi | durable state wins; publish can replay |
| publication sudah terjadi | duplicate publication must be idempotent |

Crash matrix ini harus menjadi test matrix, bukan hanya dokumentasi.

## 8. Database Transaction Scope

Database transaction harus pendek dan fokus pada durable metadata.

Jangan menahan database transaction selama:

- full scan
- long filesystem traversal
- delete banyak file
- verification yang lambat
- resource wait

Gunakan:

```text
read snapshot
→ compute
→ short transaction
→ commit
→ external work
→ short transaction
```

## 9. Filesystem dan DB Tidak Atomic Bersama

Contoh:

```text
DB says mutation started
filesystem says object exists
```

atau:

```text
filesystem object gone
DB still says executing
```

Keduanya dapat terjadi akibat crash.

Recovery harus mempertemukan kedua dunia melalui observation, bukan menganggap salah satunya selalu benar.

## 10. SQLite/WAL Semantics

Jika durable store menggunakan SQLite/WAL, transaction commit memberikan durability sesuai konfigurasi database dan filesystem.

Tetapi aplikasi tetap harus menentukan durability level yang dibutuhkan.

Untuk state kritis recovery, konfigurasi journal/synchronous harus dipilih secara sadar dan diuji pada device target.

Jangan menganggap `COMMIT` otomatis berarti data sudah aman dari semua bentuk power loss tanpa memperhatikan storage stack.

## 11. Atomic File State

Untuk state file yang harus diganti secara atomik:

```text
write temporary file
→ fsync file jika diperlukan
→ rename
→ fsync parent directory jika durability semantics memerlukannya
```

Detail durability filesystem/platform harus diverifikasi pada Android/Linux target.

## 12. Publication Barrier

Publication bukan sumber truth.

Urutan wajib:

```text
persist
→ durable commit
→ publish
```

Jika crash sebelum publish, state tetap dapat ditemukan dan publication dapat diulang.

Jika crash setelah publish, duplicate event harus aman.

## 13. Outbox

Untuk event yang wajib dikirim, gunakan durable outbox:

```text
transaction:
    update state
    insert outbox event
commit

publisher:
    read outbox
    publish
    mark delivered
```

Dengan begitu state dan intent publication berada dalam durable boundary yang sama.

## 14. Exactly-Once Publication Tidak Diasumsikan

Delivery internal sebaiknya diperlakukan sebagai at-least-once.

Consumer harus mempunyai event identity/idempotency key.

Jangan membangun correctness berdasarkan asumsi bahwa event hanya akan diterima sekali.

## 15. Result Finalization

Result hanya menjadi terminal setelah:

```text
postcondition known
+ required evidence durable
+ state transition committed
```

Progress UI bukan result finalization.

## 16. Accounting Boundary

Accounting harus mengikuti durable operation identity.

Jika crash terjadi setelah object terhapus tetapi sebelum accounting commit, recovery harus menghitung ulang berdasarkan operation evidence tanpa double count.

Jangan menjadikan in-memory byte counter sebagai sumber accounting final.

## 17. Idempotent Recovery

Recovery dapat dijalankan berkali-kali.

Contoh:

```text
restart
→ reconcile
→ crash lagi
→ reconcile lagi
```

Hasil tidak boleh menjadi semakin salah.

Recovery operation harus read-first dan mutation hanya jika contract benar-benar mengizinkan.

## 18. Reconciliation Setelah Crash

Recovery sequence:

```text
load durable state
↓
identify non-terminal operations
↓
load journal
↓
check target/catalog identity
↓
observe actual state
↓
classify
↓
verify/replan/retry/recovery-required
```

Tidak boleh langsung melanjutkan syscall hanya karena state terakhir adalah `Executing`.

## 19. Recovery Epoch

Setiap daemon startup dapat mempunyai `RecoveryEpoch`.

Tujuannya untuk membedakan evidence dari execution sebelum dan sesudah restart.

Contoh:

```text
Attempt A1
RecoveryEpoch R7

restart

Attempt A1 reconciliation
RecoveryEpoch R8
```

Ini membantu audit dan mencegah stale worker evidence diterima sebagai current execution.

## 20. Resource Ownership Recovery

Reservation yang tertinggal setelah crash harus mempunyai lease/owner identity yang dapat dinilai stale.

Recovery tidak boleh menganggap reservation lama masih aktif hanya karena record belum dibersihkan.

## 21. Lock Files dan Process Ownership

Lock harus dapat membedakan:

- active owner
- stale owner
- unknown owner

PID saja tidak cukup sebagai identity karena PID dapat reused.

Gunakan owner/session identity tambahan bila diperlukan.

## 22. Cancellation dan Crash

Cancellation request juga harus durable jika dibutuhkan recovery.

Namun:

```text
CancelRequested
```

bukan bukti mutation berhenti.

Jika crash setelah mutation boundary, cancellation tetap membutuhkan reconciliation.

## 23. Timeout dan Crash

Timeout yang tercatat sebelum crash harus diperlakukan sebagai event/context, bukan bukti mutation failure.

Recovery tetap melihat operation state dan evidence.

## 24. Power Loss

Power loss adalah failure paling keras.

Test harus menganggap:

- process memory hilang
- buffered I/O mungkin belum durable
- kernel state dapat berubah
- mount/storage dapat kembali dengan kondisi berbeda
- wall clock dapat berubah

Recovery harus selalu dapat kembali ke durable state minimal.

## 25. No False Durable State

Jangan menulis state terminal sebelum evidence tersedia.

Contoh salah:

```text
unlink requested
→ persist Completed
→ verifier belum jalan
```

Yang benar:

```text
unlink requested
→ persist execution evidence
→ verify
→ persist Completed
```

## 26. No Lost Durable Transition

Transition penting tidak boleh hanya dipublish ke memory/event bus.

Jika transition mempengaruhi recovery, transition harus durable.

## 27. Schema Version

Journal dan durable records harus mempunyai schema/version jika format dapat berubah antar release.

Recovery terhadap record versi lama harus:

- migrate
- interpret safely
- atau mark unsupported/recovery-required

Jangan silently ignore unknown record.

## 28. Corruption Handling

Jika durable store rusak atau record tidak dapat dibaca:

```text
do not guess
→ fail safe
→ preserve evidence
→ enter degraded/recovery state
```

Daemon tidak boleh menjalankan destructive cleanup dengan state store yang integrity-nya tidak dapat dipercaya.

## 29. Backup dan Repair

Repair database/state harus menjadi administrative operation terpisah dari normal cleanup.

Repair tidak boleh otomatis menghapus evidence hanya supaya daemon terlihat healthy.

## 30. Crash Injection

Test harness harus dapat menghentikan process pada setiap boundary:

```text
before intent
after intent
before syscall
syscall window
before receipt
after receipt
before verify
after verify
before final commit
after final commit
before publish
```

Targetnya bukan sekadar crash test, tetapi membuktikan recovery classification.

## 31. Power-Loss Testing

Untuk device/filesystem yang kritis, lakukan test dengan forced reboot/power interruption pada workload kecil yang dapat diverifikasi.

Jangan hanya mengandalkan unit test database.

## 32. Transaction Boundary dan Lock Boundary

Database transaction, resource lock, filesystem lock, dan mutation boundary tidak boleh diasumsikan sama.

Masing-masing mempunyai lifecycle sendiri.

Contoh:

```text
DB tx
  ↓ commit
resource reservation
  ↓
filesystem operation
  ↓
verification
```

## 33. Recovery Tidak Boleh Mengubah History

Recovery boleh membuat transition baru:

```text
Executing
→ Reconciling
→ Completed
```

tetapi tidak boleh mengedit history seolah-olah `Executing` tidak pernah terjadi.

Audit trail harus append-only.

## 34. Deterministic Recovery

Input recovery yang sama harus menghasilkan classification yang sama.

Perbedaan hanya boleh berasal dari actual observed state atau explicitly changing external conditions.

## 35. Definition of Done

Crash consistency production-ready jika:

- mutation intent durable sebelum destructive mutation
- crash matrix didefinisikan
- filesystem dan DB diperlakukan sebagai dua consistency domains
- Unknown dipertahankan
- journal/recovery evidence tersedia
- publication memakai durable barrier/outbox
- accounting idempotent
- recovery read-first
- resource ownership dapat direcover
- corruption fail-closed
- schema/version handling tersedia
- crash injection mencakup semua boundary
- power-loss behavior diuji pada target filesystem/device

## Final Invariants

1. Durable state adalah sumber recovery.
2. Database transaction tidak membuat filesystem mutation atomic.
3. Destructive intent harus durable sebelum mutation.
4. Mutation boundary harus explicit.
5. Crash setelah mutation mungkin terjadi menghasilkan Unknown.
6. Missing receipt bukan bukti Failed.
7. Terminal success membutuhkan postcondition evidence.
8. Publication dilakukan setelah durable commit.
9. Event publication harus idempotent.
10. Accounting final tidak boleh bergantung pada memory.
11. Recovery harus idempotent.
12. Restart tidak boleh blind resume.
13. Power loss diperlakukan sebagai kehilangan seluruh volatile state.
14. Durable history tidak boleh di-rewrite untuk menyembunyikan crash.
15. Corrupt durable state harus fail-closed.
16. Schema migration harus explicit.
17. Lock ownership tidak cukup berdasarkan PID.
18. Resource reservation harus dapat direcover.
19. Crash testing harus mencakup setiap critical boundary.
20. Correctness tidak boleh bergantung pada exactly-once event delivery.
