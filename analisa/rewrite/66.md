66.md — Domain Model, Typed Identity, Value Objects, Generation Binding, Serialization, and Invariant Contract

Tujuan

Dokumen ini mendefinisikan domain model inti untuk rewrite cache_cleaner. Fokus utamanya adalah menghilangkan penggunaan identifier, path, string, integer, dan state yang ambigu sebagai dasar authority.

Rewrite harus mempunyai domain model typed yang membuat invalid state sulit dibentuk dan membuat batas antara discovery, planning, authorization, execution, verification, persistence, dan presentation menjadi eksplisit.

Prinsip utama:

Raw Input
    │
    ▼
Validated DTO
    │
    ▼
Domain Value Object
    │
    ▼
Typed Entity / Identifier
    │
    ▼
Immutable Plan

Authorization

1. Domain Model Is the Contract

Domain model bukan sekadar struct untuk memindahkan data.

Ia harus merepresentasikan invariant yang wajib benar pada runtime.

2. Raw Primitive Must Not Become Authority

String seperti:

"job-123"
"/data/user/0/foo/cache/x"
"app-cache"

tidak boleh langsung menjadi authority.

Primitive harus dikonversi menjadi typed domain value setelah validation.

3. Typed Identity

Identifier utama harus mempunyai tipe berbeda walaupun representasi internalnya sama.

Contoh:

JobId
AttemptId
OperationId
PlanId
AuthorizationId
TargetId
ResourceId
WorkerId
ReservationId
RuleId
ConfigGeneration
CatalogGeneration

4. JobId

JobId mengidentifikasi logical cleanup job.

JobId tidak mengidentifikasi attempt tertentu.

Satu Job dapat mempunyai beberapa Attempt hanya jika recovery/retry semantics secara eksplisit mengizinkannya.

5. AttemptId

AttemptId mengidentifikasi satu execution attempt.

AttemptId harus unik dalam domain persistence.

Retry terhadap Job menghasilkan AttemptId baru jika mutation attempt sebelumnya sudah tidak dapat dipastikan hasilnya.

6. OperationId

OperationId mengidentifikasi satu operation mutation atau maintenance action dalam sebuah Plan.

OperationId tidak boleh digunakan ulang untuk operation berbeda.

7. PlanId

PlanId mengidentifikasi immutable execution plan.

Plan baru berarti PlanId baru walaupun operation set kebetulan sama.

8. AuthorizationId

AuthorizationId mengidentifikasi keputusan authorization terhadap Plan tertentu.

Authorization tidak boleh dipindahkan ke Plan lain.

9. TargetId

TargetId mengidentifikasi logical target yang diketahui TargetCatalog.

TargetId bukan path.

10. ResourceId

ResourceId mengidentifikasi resource yang digunakan untuk admission dan execution.

Contoh:

- storage
- mount
- block device
- package scope
- target
- worker slot
- memory budget

11. WorkerId

WorkerId mengidentifikasi worker instance.

Worker restart harus menghasilkan WorkerId baru jika identity worker lama tidak dapat dipertahankan secara aman.

12. ReservationId

ReservationId mengidentifikasi resource reservation tertentu.

ReservationId harus mempunyai owner dan lifecycle yang jelas.

13. RuleId

RuleId mengidentifikasi policy rule secara stabil.

RuleId tidak boleh bergantung pada array index.

14. ConfigGeneration

ConfigGeneration mengidentifikasi revision EffectiveConfig.

Ia harus typed dan tidak boleh diperlakukan sebagai timestamp biasa.

15. CatalogGeneration

CatalogGeneration mengidentifikasi snapshot/revision TargetCatalog.

Perubahan mount/storage/target discovery dapat menghasilkan generation baru.

16. Generation Types Must Be Distinct

ConfigGeneration dan CatalogGeneration tidak boleh menggunakan satu primitive type yang mudah tertukar.

Contoh yang lebih aman:

struct ConfigGeneration(u64);
struct CatalogGeneration(u64);

17. Opaque Identifiers

Identity sebaiknya opaque dari sisi domain.

Consumer tidak boleh bergantung pada struktur internal ID.

18. ID Representation

Implementation dapat menggunakan:

- UUID
- ULID
- cryptographically random identifier
- monotonic numeric identifier

Pemilihan harus mempertimbangkan persistence, ordering, debugging, dan storage.

19. Monotonicity

Jika ID membutuhkan ordering, ordering harus menjadi contract eksplisit.

Jangan mengasumsikan UUID secara otomatis chronological.

20. ID Uniqueness

ID harus mempunyai collision risk yang sesuai dengan lifetime sistem.

Untuk persistent domain, collision harus dianggap fatal, bukan silently overwritten.

21. No ID Reuse

JobId, PlanId, AuthorizationId, OperationId, dan AttemptId tidak boleh digunakan ulang setelah entity terminal/persisted.

22. Display vs Identity

Display string bukan identity.

Nama seperti:

"manual-clean"
"daily-maintenance"

boleh berubah tanpa mengubah JobId.

23. Value Object

Data yang mempunyai semantic invariant sendiri harus menggunakan value object.

Contoh:

ByteCount
DurationMs
Percentage
Temperature
PackageName
RelativePath
AbsolutePathCandidate
Priority
RetryCount

24. ByteCount

Ukuran byte harus mempunyai tipe domain daripada integer mentah jika digunakan pada budget/accounting.

25. ByteCount Arithmetic

Arithmetic harus checked.

Overflow harus menghasilkan error atau saturating behavior yang secara eksplisit didefinisikan.

26. Duration

Timeout, interval, cooldown, dan backoff harus menggunakan duration type yang mempunyai bound.

27. Percentage

Nilai percentage harus divalidasi pada domain yang benar, misalnya 0..=100.

28. Temperature

Temperature yang berasal dari Android kernel harus mempunyai unit eksplisit.

Jangan mencampur Celsius, milli-Celsius, atau raw sensor unit.

29. PackageName

PackageName harus divalidasi sebagai Android package identifier.

String arbitrary tidak boleh dianggap package.

30. RelativePath

Path relatif domain harus:

- tidak absolute
- tidak mempunyai parent escape
- tidak mengandung NUL
- menggunakan canonical component semantics

31. AbsolutePath Is Not TrustedRoot

Absolute path hanya locator/candidate information sampai diverifikasi oleh TargetCatalog/Safety.

32. Path Authority

Authority berasal dari TargetDescriptor + TrustedRoot + resolved identity, bukan dari string path.

33. ResourceIdentity

ResourceId harus dapat dikaitkan dengan identity fisik ketika dibutuhkan.

Contoh:

mount ID
st_dev
block device
filesystem UUID

34. Entity vs Value Object

Entity memiliki stable identity.

Value object ditentukan oleh value dan invariant-nya.

Contoh:

Target = Entity
RelativePath = Value Object

35. Immutable Domain Objects

Plan, Authorization, EffectiveConfig, TargetDescriptor, dan Candidate snapshot harus immutable setelah publication.

36. Builder Boundary

Mutable builder hanya boleh digunakan sebelum object menjadi domain state.

37. Constructor Validation

Public constructor domain type harus mencegah invalid state sejauh mungkin.

38. Smart Constructors

Gunakan constructor seperti:

PackageName::parse()
RelativePath::parse()
ByteCount::try_from()

daripada menerima string mentah di seluruh codebase.

39. Parse Error

Error parsing value object harus typed dan dapat menjelaskan field/context tanpa membocorkan secret.

40. Domain Error != IO Error

Error domain harus dibedakan dari error filesystem, permission, IPC, atau kernel.

41. Error Context

Error harus dapat dikaitkan dengan:

JobId
AttemptId
OperationId
TargetId

jika context tersebut tersedia.

42. No Stringly-Typed State

State seperti:

"running"
"failed"
"waiting"

tidak boleh menjadi source of truth.

Gunakan enum.

43. State Enums

Contoh:

JobState
AttemptState
OperationState
WorkerState
ReservationState
ConfigHealth

44. Exhaustive Matching

State machine harus menggunakan exhaustive match sehingga penambahan state memaksa audit transition.

45. Illegal State Transition

Transition yang tidak legal harus menghasilkan domain error dan tidak mengubah persisted state.

46. Entity Ownership

Setiap entity harus mempunyai owner module yang jelas.

Contoh:

Scheduler memiliki queue state.

WorkerSupervisor memiliki worker lifecycle.

PolicyEngine memiliki policy decision.

47. No Cross-Module Mutable Ownership

Module lain tidak boleh memperoleh mutable reference ke internal state module authority.

Gunakan command/query interface.

48. Snapshot Over Shared Mutation

Jika module membutuhkan data dari module lain, lebih baik gunakan immutable snapshot daripada shared mutable object.

49. Domain Snapshot

Snapshot harus membawa generation/identity yang diperlukan untuk mengetahui freshness.

50. Freshness Is Explicit

Object yang stale harus dapat diidentifikasi melalui generation atau revision binding.

51. Config Binding

JobExecutionContext harus menyimpan ConfigGeneration.

52. Catalog Binding

Plan/Candidate harus menyimpan CatalogGeneration jika decision bergantung pada catalog snapshot.

53. Plan Binding

Plan harus mengikat:

- JobId
- ConfigGeneration
- CatalogGeneration
- target set
- operation set
- limits

54. Authorization Binding

Authorization harus mengikat:

- AuthorizationId
- PlanId
- JobId
- ConfigGeneration
- decision
- scope
- expiry jika ada

55. Operation Binding

Operation harus mengikat PlanId dan OperationId.

Operation tidak boleh dieksekusi tanpa parent Plan yang valid.

56. Attempt Binding

Attempt harus mengikat:

- AttemptId
- JobId
- PlanId
- worker identity
- execution start
- terminal status

57. Worker Binding

Worker message yang merujuk Attempt harus memuat WorkerId untuk menolak stale worker messages.

58. Reservation Binding

Reservation harus mengikat:

- ReservationId
- ResourceId
- JobId/AttemptId
- owner
- lease/expiry
- state

59. Generation Mismatch

Jika execution context menggunakan ConfigGeneration G10 tetapi current global config G11, executor tidak boleh otomatis mengganti G10 menjadi G11.

60. Narrowing Rule

Runtime dapat menerapkan global safety/resource limit yang lebih ketat daripada plan.

Tetapi tidak boleh memperluas authority plan.

61. Domain Identity Is Not Authorization

Memiliki valid JobId atau TargetId tidak berarti caller berhak melakukan mutation.

Identity dan authorization harus terpisah.

62. Domain Object Is Not Capability

TargetId bukan capability.

AuthorizationToken/CapabilitySet, jika digunakan, harus menjadi tipe berbeda.

63. Capability Must Be Scoped

Capability harus mempunyai scope yang eksplisit:

- operation
- target
- resource
- action
- expiry/generation

64. No Capability From String

Caller tidak boleh membuat capability hanya dengan mengirim string target/action.

Capability harus dikeluarkan oleh Authorization layer.

65. Candidate Identity

Candidate harus mempunyai identity snapshot yang memungkinkan revalidation.

Minimal dapat mencakup:

- TargetId
- RelativePath
- device identity
- inode/file identity
- metadata snapshot
- CatalogGeneration

66. Candidate Is Not Operation

Scanner menghasilkan Candidate.

Planner memutuskan apakah Candidate menjadi Operation.

Scanner tidak boleh menentukan mutation authority.

67. Operation Is Not Execution

Operation adalah desired mutation yang sudah direncanakan.

Executor baru melakukan mutation setelah authorization dan safety gate.

68. Result Is Immutable

OperationResult/JobResult setelah published tidak boleh diubah secara in-place.

Correction dibuat sebagai reconciliation/update event yang mempunyai identity sendiri.

69. Unknown Outcome

Jika mutation terjadi tetapi hasil tidak dapat dipastikan, domain state harus mendukung Unknown/RecoveryRequired.

Jangan mengubah Unknown menjadi Failed hanya karena error komunikasi.

70. Idempotency Key

OperationId dapat digunakan sebagai idempotency identity jika semantics mutation mendukungnya.

Jika tidak, diperlukan mutation-specific idempotency key.

71. Equality

Entity equality harus berdasarkan identity.

Value object equality berdasarkan value canonical.

72. Ordering

Jangan menggunakan lexical ordering ID sebagai semantic priority kecuali contract secara eksplisit menyatakannya.

73. Hashing

Typed IDs harus dapat digunakan sebagai map/set key jika diperlukan, tetapi hashing tidak boleh menghapus type distinction di API.

74. Serialization

Domain object yang dipersist harus mempunyai serialization format versioned.

75. Serialization of IDs

ID sebaiknya diserialisasi sebagai scalar canonical representation tetapi deserialisasi kembali ke typed ID.

76. Serialization Validation

Deserialisasi tidak boleh membuat typed object bypass constructor invariant.

77. Backward Compatibility

Schema lama boleh dibaca melalui migration layer.

Domain model tidak perlu mempertahankan legacy ambiguity setelah migration.

78. Unknown Fields

Unknown persisted fields harus mengikuti contract compatibility dari storage layer.

79. Missing Required Identity

Jika persisted entity kehilangan required ID atau generation:

RecoveryRequired atau migration failure.

Jangan generate identity pengganti secara diam-diam untuk entity existing.

80. Entity Version

Entity persisted dapat memiliki revision/version terpisah dari domain ID.

Revision digunakan untuk optimistic concurrency.

81. Optimistic Concurrency

Update terhadap entity mutable harus dapat memastikan caller bekerja pada revision yang benar.

82. Compare-and-Swap

Publish state dapat menggunakan:

expected_revision → new_revision

Jika expected revision stale, update ditolak.

83. Transaction Boundary

Perubahan beberapa entity yang harus atomic harus berada dalam transaction boundary storage yang sama.

84. Publication Boundary

State tidak boleh diumumkan ke Scheduler/IPC sebelum persistence berhasil jika persistence adalah source of truth.

85. Event Payload

Event harus membawa typed identity dan revision/generation yang relevan.

86. Event Ordering

Consumer tidak boleh mengandalkan arrival order network/IPC sebagai satu-satunya ordering guarantee.

Gunakan sequence/revision bila ordering penting.

87. Correlation Identity

CorrelationId dapat digunakan untuk menghubungkan request, command, log, event, dan result.

CorrelationId berbeda dari JobId.

88. RequestId

RequestId mengidentifikasi satu request transport/API.

Jangan menggunakan RequestId sebagai JobId secara implicit.

89. Audit Identity

Audit record harus menyimpan identity domain yang relevan, bukan hanya free-form message.

90. Logging

Structured logging harus menggunakan typed ID dalam field terpisah:

job_id
attempt_id
operation_id
plan_id

dan seterusnya.

91. Redaction

Domain Display/Debug implementation tidak boleh mencetak secret atau sensitive payload secara otomatis.

92. Debug Representation

`Debug` untuk object yang memuat sensitive material harus mempertimbangkan redaction.

93. Clone Semantics

Clone pada domain object harus aman dan tidak boleh memberikan mutable alias terhadap authority state.

94. Send/Sync

Domain object yang dipakai antar worker harus memenuhi concurrency contract yang benar.

Jangan memaksa Send/Sync dengan unsafe implementation.

95. Arc Is Not Domain Ownership

`Arc<T>` hanya mekanisme sharing memory.

Ia tidak menggantikan ownership semantics domain.

96. Mutex Is Not State Machine

`Mutex<DaemonState>` tidak otomatis membuat transition legal.

State transition harus mempunyai domain API.

97. Current Code Migration

Current `DaemonConfig` masih menggunakan primitive fields seperti `String`, `u64`, `f32`, `bool`, dan `Vec<String>` secara langsung.

Rewrite harus secara bertahap memindahkan semantics penting ke typed value objects tanpa memutus compatibility secara mendadak. fileciteturn40file0

98. Current Path Constants

Path seperti `CONFIG_PATH`, `SOCKET_PATH`, `LOG_PATH`, dan `PID_PATH` saat ini berupa static string constants.

Untuk rewrite, fixed deployment paths dapat tetap berupa platform constants, tetapi path yang masuk ke security-sensitive domain tidak boleh dianggap trusted hanya karena berasal dari constant/config string.

99. Current SafetyMode

`SafetyMode` sudah merupakan contoh typed enum yang benar.

Pattern tersebut harus diperluas ke configuration dan domain lain yang mempunyai finite semantics.

100. Domain Model Layering

Direkomendasikan struktur konseptual:

`domain::id`
`domain::value`
`domain::job`
`domain::plan`
`domain::operation`
`domain::target`
`domain::candidate`
`domain::authorization`
`domain::resource`
`domain::worker`
`domain::result`

101. API Boundary

Module boundary harus menerima domain types, bukan primitive combinations.

Contoh buruk:

`execute(job_id: String, path: String, max_bytes: u64)`

Contoh yang lebih benar:

`execute(context: AuthorizedExecutionContext)`

102. AuthorizedExecutionContext

Context execution minimal membawa:

- JobId
- AttemptId
- PlanId
- AuthorizationId
- ConfigGeneration
- operation set/reference
- effective runtime limits
- cancellation handle

103. No Hidden Global Context

Executor tidak boleh mengambil configuration, authorization, atau target scope dari global mutable singleton untuk melengkapi context secara diam-diam.

104. Explicit Dependencies

Dependency domain harus diberikan melalui typed interface sehingga source of authority terlihat dari signature.

105. Serialization Boundary

Transport DTO tidak sama dengan domain entity.

IPC request harus di-parse menjadi validated command lalu diterjemahkan ke domain command.

106. DTO Must Not Leak Into Domain

Serde/transport-specific struct sebaiknya tidak menjadi core domain state jika field semantics berbeda.

107. Persistence DTO

Storage schema juga boleh mempunyai DTO sendiri.

Conversion:

StorageRecord → ValidatedDomainEntity

harus melalui validation.

108. No Direct Deserialization Into Authority

Jangan deserialize IPC/database payload langsung menjadi object yang mempunyai mutation authority.

109. Testability

Typed domain model harus dapat diuji tanpa Android kernel.

Job, Plan, Authorization, Candidate, Operation, dan state transition harus memiliki unit tests murni.

110. Property Testing

Value objects dan state machines sebaiknya diuji dengan property-based testing untuk menemukan kombinasi invalid.

111. Fuzzing Boundary

Fuzz target utama:

- ID parsing
- path parsing
- package parsing
- config conversion
- persisted record decoding
- IPC command decoding

112. Final Domain Invariants

Rewrite dianggap memenuhi contract ini apabila:

- identity penting tidak lagi stringly typed
- JobId berbeda dari AttemptId
- PlanId berbeda dari AuthorizationId
- TargetId berbeda dari path
- ResourceId berbeda dari target identity
- generation types tidak tertukar
- value object memvalidasi invariant
- state menggunakan enum
- illegal transition ditolak
- stale generation dapat dideteksi
- authority tidak berasal dari primitive/string
- persisted data divalidasi sebelum menjadi domain state
- IPC DTO tidak menjadi authority secara langsung
- Unknown outcome dapat direpresentasikan
- result immutable setelah publication
- audit memiliki typed identity
- domain model dapat diuji tanpa platform dependency

113. Definition of Done

Implementasi domain model dinyatakan selesai apabila setiap boundary utama dapat menjawab secara eksplisit:

1. Siapa identity object ini?
2. Siapa owner lifecycle-nya?
3. Generation/revision apa yang mengikatnya?
4. Apakah object ini immutable?
5. Apakah object ini authority atau hanya data?
6. Siapa yang boleh membuatnya?
7. Siapa yang boleh mengubahnya?
8. Bagaimana stale state ditolak?
9. Bagaimana persistence dan publication disinkronkan?
10. Bagaimana crash/recovery menangani object tersebut?

Jika pertanyaan tersebut tidak mempunyai jawaban pada type/API boundary, domain model belum cukup kuat untuk production-grade rewrite.
