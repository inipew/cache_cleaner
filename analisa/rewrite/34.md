# 1000. Runtime Layer dan Event Loop

Lanjut. Sekarang kita masuk ke **`runtime/`**, yaitu lapisan yang membuat daemon benar-benar hidup.

Sampai titik ini kita sudah memiliki:

```text
CLI / IPC
    ↓
Application
    ↓
Scheduler
    ↓
Job
    ↓
Target Catalog
    ↓
Scanner
    ↓
Safety
    ↓
Policy
    ↓
Planner
    ↓
Authorization
    ↓
AuthorizedPlan
    ↓
Executor
    ↓
Verifier
```

Tetapi seluruh pipeline tersebut membutuhkan satu komponen yang menghubungkan dunia luar dengan scheduler:

```text
                  Android / Linux
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
       timerfd      signalfd       UDS
          │            │            │
          └────────────┼────────────┘
                       ▼
                    epoll
                       │
                       ▼
                 Event Decoder
                       │
                       ▼
                  SystemEvent
                       │
                       ▼
                   Scheduler
```

Prinsip utama:

> **Event loop hanya menerima, mendecode, dan meneruskan event. Event loop tidak pernah melakukan cleanup secara langsung.**

---

# 1001. Struktur `runtime/`

Saya akan menggunakan:

```text
src/runtime/
├── mod.rs
├── event_loop.rs
├── events.rs
├── source.rs
├── timer.rs
├── signals.rs
├── uevent.rs
├── ipc.rs
├── lock.rs
├── paths.rs
├── readiness.rs
└── error.rs
```

Pembagian tanggung jawab:

```text
event_loop.rs
    epoll ownership dan dispatch

events.rs
    domain-level SystemEvent

source.rs
    event source abstraction

timer.rs
    timerfd

signals.rs
    signalfd

uevent.rs
    kernel netlink / uevent

ipc.rs
    Unix socket event source

readiness.rs
    runtime readiness state

lock.rs
    single-instance flock

paths.rs
    fixed runtime paths

error.rs
    runtime errors
```

Yang penting:

```text
runtime
    ≠
scheduler
```

Runtime menghasilkan event.

Scheduler memutuskan apa yang harus dilakukan terhadap event tersebut.

---

# 1002. Runtime bukan business logic

Jangan membuat:

```rust
if screen_on {
    cleaner.clean();
}
```

di dalam event loop.

Juga jangan:

```rust
match event {
    ScreenOn => executor.cancel(),
    ThermalHot => executor.pause(),
}
```

Karena event loop kemudian menjadi scheduler kedua.

Yang benar:

```text
kernel event
    ↓
decode
    ↓
SystemEvent::ScreenChanged(On)
    ↓
Scheduler
    ↓
SchedulerDecision::CancelActiveJob
```

Dengan demikian:

```text
Runtime = what happened?
Scheduler = what should happen?
Worker = perform the action
```

Ini boundary yang harus dipertahankan.

---

# 1003. `SystemEvent`

Kita membutuhkan satu representasi event internal.

Contoh:

```rust
pub enum SystemEvent {
    Timer(TimerEvent),

    Screen(ScreenState),

    Thermal(ThermalState),

    Battery(BatteryState),

    Storage(StorageEvent),

    User(UserEvent),

    Uevent(Uevent),

    Ipc(IpcEvent),

    Signal(SignalEvent),

    Worker(JobEvent),

    Shutdown(ShutdownReason),
}
```

Jangan membiarkan scheduler menerima:

```text
epoll event
RawFd
netlink packet
signalfd struct
```

Scheduler hanya menerima:

```rust
SystemEvent
```

Dengan begitu scheduler tidak tahu bagaimana event tersebut diperoleh.

# 1004. Event source

Saya ingin setiap sumber event memiliki abstraction yang sederhana:

```rust
pub trait EventSource {
    fn fd(&self) -> BorrowedFd<'_>;

    fn interests(&self) -> EventInterest;

    fn handle_readable(
        &mut self,
    ) -> Result<Vec<SystemEvent>, RuntimeError>;
}
```

Tetapi ada satu catatan penting.

`EventSource` tidak boleh menjadi tempat untuk menjalankan business logic.

Contoh:

```rust
fn handle_readable(&mut self) -> Result<Vec<SystemEvent>, RuntimeError> {
    let event = decode_event()?;

    Ok(vec![
        SystemEvent::Screen(ScreenState::On)
    ])
}
```

bagus.

Sedangkan:

```rust
fn handle_readable(&mut self) {
    scheduler.cancel_current_job();
}
```

tidak bagus.

# 1005. Epoll Reactor

Event loop utama:

```rust
pub struct EventLoop {
    epoll: Epoll,
    sources: SourceRegistry,
}
```

Secara konseptual:

```text
register sources
      ↓
epoll_wait()
      ↓
events
      ↓
lookup source
      ↓
read/decode
      ↓
SystemEvent
      ↓
dispatch
```

Loop:

```text
while !shutdown {
    wait_for_events();

    for event in events {
        source = registry.lookup(event);

        decoded = source.handle_readable()?;

        for system_event in decoded {
            dispatcher.dispatch(system_event);
        }
    }
}
```

Tidak ada:

```text
scan filesystem
delete file
trim
zram
F2FS maintenance
```

di loop ini.

---

# 1006. Mengapa `epoll`?

Daemon ini harus idle hampir sepanjang waktu.

Kita tidak ingin:

```text
loop {
    check_screen();
    check_temperature();
    check_battery();
    check_storage();
    sleep(1);
}
```

Itu polling loop.

Lebih baik:

```text
kernel event
    ↓
wake daemon
    ↓
handle event
    ↓
sleep again
```

Dengan:

```text
epoll
timerfd
signalfd
netlink
Unix socket
```

daemon dapat tetap dormant ketika tidak ada pekerjaan.

---

# 1007. Tidak semua state memiliki event sempurna

Ini penting.

Kita tidak boleh berasumsi bahwa setiap perubahan Android selalu menghasilkan event yang dapat kita tangkap.

Karena itu arsitektur harus memiliki dua mekanisme:

```text
event-driven invalidation
+
bounded state refresh
```

Contoh:

```text
UserUnlocked event
    ↓
invalidate catalog
```

Kemudian job berikutnya:

```text
build fresh catalog
```

Bukan:

```text
event mengatakan user unlock
→ langsung mengubah seluruh state internal
```

Event terutama digunakan sebagai **trigger invalidation**.

---

# 1008. Event sebagai invalidation

Contoh:

```text
UserUnlocked
    ↓
CatalogInvalidated
```

bukan:

```text
UserUnlocked
    ↓
catalog.users[uid].state = unlocked
```

Kenapa?

Karena event dapat:

```text
hilang
duplikat
datang terlambat
berurutan berbeda
```

Maka event harus dianggap sebagai:

> "state kemungkinan berubah; lakukan refresh pada boundary berikutnya."

# 1009. Runtime snapshot

Scheduler membutuhkan state yang sudah dinormalisasi:

```rust
pub struct RuntimeSnapshot {
    pub screen: ScreenState,
    pub thermal: ThermalState,
    pub battery: BatteryState,
    pub storage: StorageStateSummary,
    pub users: UserStateSummary,
    pub timestamp: MonotonicTimestamp,
}
```

Snapshot ini bukan source of truth permanen.

Ia adalah:

```text
latest observed state
```

Untuk keputusan penting, subsystem terkait tetap dapat melakukan refresh/revalidation.

# 1010. Monotonic timestamp

Runtime tidak boleh menggunakan wall clock untuk menghitung interval internal.

Jangan:

```rust
SystemTime::now()
```

untuk:

```text
timer timeout
retry delay
job duration
event ordering
cancellation timeout
```

Gunakan monotonic clock.

Secara konseptual:

```rust
pub struct MonotonicTimestamp(Duration);
```

Wall clock hanya untuk:

```text
logging
report
mtime policy
human-readable output
```

---

# 1011. `timerfd`

Scheduler membutuhkan timer untuk:

```text
scheduled cleanup
retry
backoff
status refresh
periodic capability refresh
```

Gunakan:

```text
timerfd
```

daripada:

```text
thread sleep
```

Karena timer dapat menjadi event source epoll.

Flow:

```text
Scheduler
    ↓
next deadline
    ↓
timerfd_settime()
    ↓
sleep
    ↓
timerfd readable
    ↓
TimerEvent
    ↓
Scheduler
```

---

# 1012. Timer bukan scheduler

Timer hanya mengatakan:

```text
"deadline reached"
```

Ia tidak mengatakan:

```text
"start cleanup"
```

Contoh:

```rust
SystemEvent::Timer(TimerEvent::CleanupDue)
```

kemudian:

```text
Scheduler
    ↓
check readiness
    ↓
check cooldown
    ↓
check active job
    ↓
decide
```

Jadi timer tidak pernah bypass scheduler.

---

# 1013. Timer coalescing

Jangan membuat timer untuk setiap job kecil.

Misalnya:

```text
retry A → timer A
retry B → timer B
retry C → timer C
```

lebih kompleks.

Scheduler dapat mempertahankan:

```text
next_deadline
```

dan hanya menggunakan satu timer utama.

Contoh:

```text
now = 100

job A deadline = 120
job B deadline = 150
job C deadline = 130

next deadline = 120
```

Set timer ke:

```text
120
```

Setelah event:

```text
now = 120

process due jobs

next deadline = 130
```

Set timer lagi.

---

# 1014. Timer generation

Race dapat terjadi ketika scheduler mengubah deadline sementara event timer lama masih berada di queue.

Gunakan generation:

```rust
pub struct TimerGeneration(pub u64);
```

Contoh:

```text
timer generation 10
```

Scheduler mengubah deadline:

```text
generation 11
```

Event lama:

```text
generation 10
```

dapat diabaikan jika sudah stale.

---

# 1015. Timer expiration count

`timerfd` dapat mengakumulasi expiration.

Jangan hanya membaca satu byte atau mengabaikan count.

Secara konsep:

```text
expiration count = N
```

berarti timer telah expired N kali.

Tetapi scheduler tidak harus menjalankan cleanup N kali.

Untuk periodic maintenance:

```text
N expirations
    ↓
coalesce
    ↓
one scheduler evaluation
```

Kita tidak ingin device baru bangun lalu menjalankan:

```text
100 cleanup jobs
```

karena daemon tidur selama beberapa jam.

# 1016. Signalfd

Signal handling juga dimasukkan ke event loop.

Gunakan:

```text
signalfd
```

untuk:

```text
SIGTERM
SIGINT
SIGHUP
```

Flow:

```text
signal
  ↓
signalfd
  ↓
epoll
  ↓
SignalEvent
  ↓
Scheduler/Application
```

Jangan memiliki:

```text
signal handler
    ↓
mutex
    ↓
cleanup
```

Signal handler asynchronous adalah boundary yang sulit diaudit.

# 1017. `SIGTERM`

`SIGTERM` berarti:

```text
graceful shutdown
```

Flow:

```text
SIGTERM
   ↓
SignalEvent::Terminate
   ↓
Application
   ↓
SchedulerCommand::Shutdown
   ↓
reject new jobs
   ↓
cancel active job
   ↓
wait bounded
   ↓
close resources
   ↓
release lock
   ↓
exit
```

# 1018. `SIGINT`

`SIGINT` dapat memiliki semantics sama:

```text
SIGINT
    ↓
Shutdown
```

Tidak perlu membuat dua shutdown implementation.

Cukup:

```rust
ShutdownReason::Signal(SignalKind::Int)
```

dan:

```rust
ShutdownReason::Signal(SignalKind::Term)
```

---

# 1019. `SIGHUP`

`SIGHUP` berarti:

```text
reload configuration
```

Flow:

```text
SIGHUP
   ↓
SignalEvent::Reload
   ↓
ConfigLoader
   ↓
parse
   ↓
validate
   ↓
ValidatedConfig
   ↓
new generation
```

Jika gagal:

```text
old valid config remains active
```

Tidak boleh:

```text
invalid reload
    ↓
config = empty/default
```

---

# 1020. Reload tidak membatalkan active job

Active job memiliki:

```text
ConfigSnapshot generation N
```

Reload menghasilkan:

```text
generation N+1
```

Active job tetap menggunakan:

```text
generation N
```

Job baru menggunakan:

```text
generation N+1
```

Dengan demikian tidak ada perubahan policy di tengah execution.

# 1021. Uevent / Netlink

Android/Linux memberikan banyak event melalui kernel netlink.

Untuk cleaner kita terutama tertarik pada event yang relevan dengan:

```text
power
screen
storage
device
```

Tetapi parser harus tetap dipisahkan:

```text
raw netlink
    ↓
uevent parser
    ↓
typed Uevent
    ↓
SystemEvent
```

Jangan memasukkan string kernel langsung ke scheduler.

# 1022. Uevent parser

```text
ACTION=change
SUBSYSTEM=power_supply

```

menjadi:

```rust
Uevent::PowerSupplyChanged
```

atau:

```rust
SystemEvent::Battery(BatteryEvent::Changed)
```

Scheduler tidak perlu tahu:

```text
"POWER_SUPPLY_STATUS"
```

atau:

```text
"SUBSYSTEM=power_supply"
```

# 1023. Uevent tidak selalu lengkap

Event kernel dapat memberikan:

```text
device changed
```

tetapi tidak selalu membawa seluruh state.

Karena itu:

```text
event
    ↓
invalidate
    ↓
read authoritative state
```

Contoh:

```text
PowerSupplyChanged
    ↓
BatteryStateReader
    ↓
BatteryState
```

Bukan:

```text
PowerSupplyChanged
    ↓
anggap battery = 100%
```

# 1024. Screen state

Screen state merupakan kondisi penting karena cleaning harus berhenti ketika user mulai menggunakan device.

Model:

```rust
pub enum ScreenState {
    On,
    Off,
    Unknown,
}
```

Jika:

```text
ScreenOn
```

dan cleanup sedang berlangsung:

```text
Scheduler
    ↓
CancellationReason::ScreenOn
    ↓
cancel worker
```

---

# 1025. Screen event harus high priority

Tidak semua event memiliki urgency yang sama.

Misalnya:

```text
screen_on
```

lebih urgent daripada:

```text
periodic_timer
```

Maka event priority perlu diperkenalkan.

```rust
pub enum EventPriority {
    Critical,
    High,
    Normal,
    Low,
}
```

Contoh:

```text
SIGTERM       → Critical
ScreenOn      → Critical
ThermalHot    → Critical
StorageChange → High
IPC command   → High
Timer         → Normal
Telemetry     → Low
```

---

# 1026. Event priority tidak berarti event loop menjalankan policy

Event loop tetap hanya:

```text
receive
decode
queue
```

Priority menentukan urutan dispatch.

Misalnya:

```text
timer
screen_on
```

masuk hampir bersamaan.

Scheduler harus melihat:

```text
screen_on
```

lebih dulu sehingga tidak memulai cleanup baru hanya karena timer datang lebih dahulu.

---

# 1027. Event queue

Kita membutuhkan queue bounded.

Jangan:

```rust
VecDeque<SystemEvent>
```

tanpa batas.

Gunakan:

```rust
pub struct EventQueue {
    capacity: usize,
    ...
}
```

Karena event storm mungkin terjadi.

Misalnya:

```text
100000 uevents
```

tidak boleh membuat daemon menghabiskan memory.

---

# 1028. Event coalescing

Event tertentu boleh digabung.

Misalnya:

```text
ThermalChanged(Normal)
ThermalChanged(Warm)
ThermalChanged(Hot)
ThermalChanged(Warm)
```

Jika scheduler belum memproses semuanya, cukup simpan:

```text
latest thermal state = Warm
```

Untuk event state-like:

```text
ScreenChanged
ThermalChanged
BatteryChanged
```

coalescing sangat berguna.

Tetapi jangan melakukan coalescing untuk event yang merupakan command:

```text
Shutdown
Reload
CancelJob
```

karena semantics-nya berbeda.

```rust
pub enum EventClass {
```

Unix Domain Socket juga harus masuk event loop.

Flow:

```text

  ↓
UDS
  ↓
epoll readable
  ↓
accept/read
  ↓
frame decoder
  ↓
ProtocolRequest
  ↓
IPC layer
  ↓

```

Tetapi IPC layer tidak menjalankan executor.

# 1031. Partial socket reads

Jangan mengasumsikan:

```text
read()
```

menghasilkan satu frame penuh.

Bisa:

```text
read #1:
header + sebagian payload
```

kemudian:

```text
read #2:
sisa payload
```

Maka setiap connection membutuhkan:

```rust
FrameDecoder
```

dengan state:

```text
ReadingHeader
ReadingPayload
Ready
Error
Closed
```

---

# 1032. Partial writes

Response juga dapat mengalami partial write.

Jangan:

```rust
write(fd, response)
```

dan menganggap semuanya terkirim.

Gunakan:

```text
write buffer
    ↓
writable event
    ↓
continue write
    ↓
buffer empty
    ↓
remove EPOLLOUT
```

`EPOLLOUT` hanya diaktifkan ketika memang ada data yang menunggu dikirim.

---

# 1033. Frame size limit

Protocol memiliki hard limit:

```rust
const MAX_FRAME_SIZE: usize = ...;
```

Sebelum allocation:

```text
read header
    ↓
decode length
    ↓
if length > MAX_FRAME_SIZE
    reject
```

Jangan:

```rust
Vec::with_capacity(attacker_controlled_length)
```

sebelum validasi.

---

# 1034. Connection limit

Jangan hanya membatasi frame.

Batasi juga:

```text
MAX_CONNECTIONS
MAX_IN_FLIGHT_REQUESTS
MAX_OUTPUT_BUFFER
MAX_REQUEST_RATE
```

Karena caller lokal yang memiliki akses socket tetap dapat melakukan resource exhaustion.

---

# 1035. IPC disconnect

Disconnect:

```text
client closes socket
```

tidak berarti:

```text
cancel job
```

Job tetap menjadi milik scheduler.

Jika user ingin membatalkan:

```text
CancelJob(job_id)
```

secara eksplisit.

Ini konsisten dengan desain sebelumnya:

```text
connection lifecycle
    ≠
job lifecycle
```

---

# 1036. Event loop tidak memiliki Job

Event loop tidak boleh memiliki:

```rust
active_job: Option<Job>
```

Scheduler yang memiliki.

Event loop hanya:

```text
produce SystemEvent
```

dan:

```text
consume outbound runtime commands
```

# 1037. Runtime command

Arah sebaliknya membutuhkan:

```rust
pub enum RuntimeCommand {
    SetTimer(Deadline),
    CancelTimer,
    RegisterSource(SourceId),
    ModifyInterest(SourceId, EventInterest),

```

Scheduler mengirim command.

Runtime menjalankan command tersebut.

Contoh:

```text
Scheduler
   │
   │ SetTimer
   ▼
Runtime
```

Tetapi:

```text
Runtime
   │
   │ SystemEvent
   ▼
Scheduler
```

Ini membuat boundary dua arah menjadi jelas.

# 1038. Jangan memberikan `&mut Scheduler` kepada Runtime

Anti-pattern:

```rust
runtime.run(&mut scheduler)
```

lalu runtime mulai memanggil:

```rust
scheduler.start_cleanup()
scheduler.cancel()
scheduler.reload()
```

Lebih baik:

```text
Runtime
   ↓
SystemEvent
   ↓
Application/Scheduler
```

dan:

```text
Scheduler
   ↓
RuntimeCommand
   ↓
Runtime
```

# 1039. Runtime command queue

Command dari scheduler juga harus bounded.

```rust
pub struct RuntimeCommandQueue {
    ...
}
```

Namun command tertentu harus selalu diterima:

```text
Shutdown
```

Jangan sampai:

```text
queue full
    ↓
Shutdown dropped
```

Karena itu command priority diperlukan.

---

# 1040. Shutdown harus bypass queue pressure

Untuk shutdown:

```text
SIGTERM
    ↓
Runtime receives directly
    ↓
Critical event
```

Scheduler juga harus memiliki jalur shutdown yang tidak tergantung pada queue yang mungkin penuh.

---

# 1041. Event loop failure

Jika `epoll_wait()` gagal:

```text
fatal runtime error
```

Jangan mencoba:

```text
recreate epoll
```

tanpa desain yang jelas.

Runtime adalah fondasi daemon.

Jika event delivery tidak dapat dipercaya:

```text
fail closed
```

lebih baik daripada menjalankan cleanup dengan observability/control plane yang rusak.

---

# 1042. Source failure

Tidak semua source failure harus fatal.

Contoh:

```text
F2FS uevent unavailable
```

mungkin berarti:

```text
feature unavailable
```

sedangkan:

```text
epoll broken
```

berarti:

```text
runtime unavailable
```

Kita membutuhkan classification:

```rust
pub enum RuntimeFailure {
    Fatal(RuntimeError),
    Degraded(SourceId, SourceError),
}
```

---

# 1043. Capability degradation

Contoh:

```text
signalfd        ✓
timerfd         ✓
UDS             ✓
uevent          ✗
```

Daemon masih dapat berjalan jika:

```text
uevent
```

hanya optional.

Tetapi scheduler harus tahu:

```text
event source unavailable
```

agar tidak membuat asumsi yang salah.

---

# 1044. Screen event unavailable

Ini lebih sensitif.

Jika design mengharuskan:

```text
cleanup only when screen off
```

tetapi screen state tidak dapat diketahui:

```text
ScreenState::Unknown
```

maka readiness policy harus:

```text
Unknown → not ready
```

bukan:

```text
Unknown → assume off
```

Fail closed.

---

# 1045. Thermal state unavailable

Untuk thermal:

```text
Unknown
```

dapat memiliki policy berbeda.

Jika cleanup sangat konservatif:

```text
Unknown → defer
```

Ini lebih aman daripada:

```text
Unknown → normal
```

# 1046. Runtime Readiness

Kita sekarang dapat membangun:

```rust
pub struct Readiness {
    pub screen: ScreenReadiness,
    pub thermal: ThermalReadiness,
    pub storage: StorageReadiness,
    pub user: UserReadiness,
    pub daemon: DaemonReadiness,
}
```

Kemudian:

```rust
pub enum ReadinessDecision {
    Ready,
    Deferred(DeferReason),
}
```

---

# 1047. Readiness bukan Policy

Bedakan:

```text
Readiness
```

dengan:

```text
CleanupPolicy
```

Readiness menjawab:

> "Apakah sekarang aman secara runtime untuk memulai?"

Policy menjawab:

> "Target mana yang boleh dibersihkan?"

Contoh:

```text
screen on
```

→ readiness defer.

Sedangkan:

```text
cache age < 7d
```

→ policy reject.

---

# 1048. Readiness sebelum scan

Jangan:

```text
scan 50000 entries
    ↓
screen ternyata on
    ↓
discard semuanya
```

Lebih baik:

```text
check readiness
    ↓
if blocked → defer
    ↓
```

# 1083. Invariant Runtime

Saya ingin menulis invariant berikut ke test suite:

```text
1. Runtime never performs cleanup.
2. Runtime never deletes filesystem objects.
3. Runtime never executes kernel maintenance.
4. Runtime never owns Job state.
5. Runtime never owns Policy state.
6. Runtime never trusts IPC payload as authority.
7. Runtime event queues are bounded.
8. Critical shutdown events cannot be dropped.
9. State-change events may be coalesced.
10. Command events are not silently coalesced.
11. Partial IPC frames are supported.
12. Oversized frames are rejected before allocation.
13. Signal handling is event-driven.
14. Timer handling is event-driven.
15. Uevent parsing is isolated from scheduler logic.
16. Runtime uses monotonic time for deadlines.
17. Runtime failures are classified as fatal/degraded.
18. Unknown readiness state fails closed where required.
19. Runtime resources have deterministic ownership.
20. Shutdown is cooperative and bounded.
21. Active jobs use immutable snapshots.
22. Runtime events never directly mutate domain state.
23. Runtime commands never directly execute cleanup.
24. Event ordering is observable through sequence numbers.
25. Event storms cannot cause unbounded memory growth.
```

```text
├── mod.rs
├── capabilities.rs
├── trim.rs
├── f2fs.rs
├── zram.rs
├── scheduler.rs
├── cgroup.rs
└── governor.rs
```

Bagian ini harus diperlakukan berbeda dari filesystem cleanup.

Filesystem deletion memiliki semantics:

```text
destructive object operation
```

sedangkan:

```text
F2FS GC
FITRIM
ZRAM
SCHED_IDLE
IO priority
cgroup
```

adalah:

```text
system maintenance operations
```

Maka kita perlu menentukan secara eksplisit:

```text
Capability detection
        ↓
Maintenance policy
        ↓
Maintenance plan
        ↓
Authorization
        ↓
Precondition validation
        ↓
State snapshot
        ↓
Apply
        ↓
Verify
        ↓
Restore
        ↓
Report
```

terutama untuk operasi yang mengubah state kernel sementara.

Dokumen berikutnya seharusnya membedah **`kernel/maintenance` sampai level API, capability detection, precondition, RAII state restoration, F2FS `gc_urgent`, FITRIM, ZRAM, scheduler/IO governor, cgroup placement, failure/degradation semantics, dan batas aman antara cleanup filesystem dengan system maintenance**.
