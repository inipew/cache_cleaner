1000. Sekarang kita masuk ke runtime

Sampai tahap ini architecture kita sudah memiliki hampir semua komponen utama:

Tetapi semua itu masih membutuhkan satu komponen yang membuat daemon benar-benar hidup.

Komponen tersebut adalah runtime.

Runtime bukan tempat business logic cleanup.

Runtime bertanggung jawab terhadap:

event loop
timer
signal
IPC readiness
system event
lifecycle

Prinsip paling penting:

Runtime tidak mengambil keputusan cleanup.

Runtime tidak melakukan filesystem mutation.

Runtime tidak memanggil executor secara langsung.

1002. Runtime bukan scheduler

Ini harus dibedakan dengan sangat jelas.

Scheduler menjawab:

Contoh:

timer expired

adalah runtime event.

Sedangkan:

saat timer expired, apakah cleanup boleh dimulai?

adalah keputusan scheduler.

Jadi:

↓

↓
Scheduler
↓

Bukan:

↓

1023. Timer coalescing

Kita tidak perlu memiliki timer terpisah untuk setiap event kecil.

Misalnya terdapat:

cleanup timer
status timer
metrics timer
health timer

Jika semuanya memiliki deadline berdekatan, runtime dapat melakukan coalescing.

Tujuannya:

mengurangi wakeup
mengurangi battery impact
mengurangi scheduler overhead

Tetapi coalescing tidak boleh mengubah semantics.

1024. Monotonic clock

Untuk interval dan timeout gunakan monotonic clock.

Jangan menggunakan wall clock untuk:

timeout
elapsed duration

Wall clock dapat berubah karena:

NTP

timezone
manual clock adjustment

Monotonic clock tidak terpengaruh oleh perubahan tersebut.

1025. Wall clock

Wall clock tetap berguna untuk:

Tetapi bukan untuk menentukan:

Untuk itu gunakan monotonic time.

Tidak boleh ada:

Gunakan lock file atau mekanisme kernel yang sesuai.

1037. Partial frame

UDS adalah stream.

Bisa:

↓

↓

└── yes → process frame

1038. Event loop tidak boleh blocking

Ini sangat penting.

Harus:

↓

↓

Dengan demikian client yang lambat tidak memblokir client lain.

1039. Output backpressure

Hal yang sama berlaku untuk response.

Jika client tidak membaca response:

daemon tidak boleh terus mengalokasikan buffer tanpa batas.

Connection harus memiliki:

Jika terlampaui:

connection dapat diputus atau response dipangkas sesuai protocol semantics.

Tidak boleh:

unbounded Vec<u8>

1040. IPC fairness

Satu client tidak boleh memonopoli event loop.

Misalnya:

10 MB readable

client B
1 small request

Event loop tidak boleh menghabiskan waktu tanpa batas pada A.

Gunakan processing budget:

max bytes per iteration

atau:

max frames per dispatch

Kemudian kembali ke epoll.

1041. Scheduler fairness

Prinsip serupa berlaku pada scheduler.

Satu job besar:

Karena itu pekerjaan berat harus berada di worker context.

Event loop hanya mengatur control plane.

scheduler tidak boleh melakukan busy loop:

try
defer
try
defer
try
defer

Gunakan backoff.

1168. Backoff state

Misalnya:

attempt 1
attempt 2
attempt 3

dengan bounded delay.

Backoff harus menggunakan monotonic time.

1169. Backoff reset

Jika kondisi kembali normal:

backoff dapat di-reset.

Contoh:

ThermalHigh
↓
backoff

ThermalNormal
↓
re-evaluate

Tidak harus menunggu backoff maksimum jika sistem sudah sehat, tergantung policy.

1170. Runtime versus backoff

Runtime hanya memasang timer sesuai permintaan scheduler.

Backoff policy bukan milik runtime.

1171. Wakeup merging

Jika scheduler meminta:

wake at T1

kemudian:

wake at T2

dengan:

T2 > T1

runtime cukup mempertahankan deadline paling awal.

Jika:

T2 < T1

timer di-update.

1172. Wakeup cancellation

Scheduler harus dapat membatalkan scheduled wakeup jika:

shutdown
job no longer relevant
state invalidated

1173. State invalidation

Event:

UserUnlocked
StorageChanged
ThermalChanged

dapat menyebabkan scheduler invalidation.

Scheduler kemudian meminta:

re-evaluate

Runtime tidak perlu tahu apa yang akan dievaluasi.

1174. Runtime command queue

Selain event source, internal command queue dapat digunakan jika diperlukan.

Contoh:

worker
↓
queue JobEvent
↓
eventfd wakeup

Tetapi jangan membuat:

100 jenis queue

tanpa alasan.

Satu bounded internal event channel biasanya cukup.

1175. Thread model

Saya menyarankan:

main/control thread
worker pool terbatas

Main thread:

event loop
IPC lifecycle
scheduler dispatch
runtime state

Worker:

planning jika berat
execution
verification

Namun pure policy/planner yang ringan tetap dapat dilakukan pada control context jika profiling membuktikan aman.

1176. Jangan membuat thread untuk setiap job

Tidak:

spawn thread per cleanup.

Gunakan bounded worker pool atau controlled worker execution.

Tujuannya:

bounded CPU
bounded memory
predictable lifecycle

1177. Worker count

Jumlah worker harus dibatasi.

Cleanup daemon tidak membutuhkan:

32 worker

hanya karena device memiliki 32 CPU.

Filesystem cleanup sering I/O-bound dan terlalu banyak concurrency justru dapat:

meningkatkan latency
meningkatkan thermal
mengganggu foreground app
meningkatkan contention

1178. Runtime worker policy

Worker count dapat dipengaruhi:

CPU count
thermal state
screen state
device class

Tetapi keputusan tersebut sebaiknya berada pada scheduler/resource policy.

Runtime hanya menjalankan worker infrastructure.

1179. Foreground impact

Runtime harus mengutamakan:

low latency
low wakeup
bounded CPU

Karena daemon cleanup seharusnya tidak terasa sebagai foreground workload.

1180. Event loop latency budget

Target praktis:

event handling harus cepat.

Jika event loop harus melakukan pekerjaan berat:

pindahkan ke worker.

Jangan:

read IPC
scan 500k files
return to epoll

dalam satu callback.

1181. Runtime security model

Runtime berjalan dengan privilege tinggi.

Maka:

setiap FD
setiap socket
setiap path
setiap signal
setiap event

harus diperlakukan sebagai boundary.

Privilege tidak boleh menghapus kebutuhan validation.

Tetapi socket permission bukan satu-satunya authorization.

1183. Runtime socket path

untuk daemon.

1184. Lock path

Jangan mengambil lock berdasarkan path dari IPC/config user.

1185. Environment

Daemon privileged tidak boleh mempercayai environment variable secara membabi buta.

Runtime startup sebaiknya:

dan menggunakan path yang eksplisit.

1186. Working directory

Daemon tidak boleh bergantung pada current working directory untuk:

1187. Umask

Runtime startup harus menentukan umask yang aman sebelum membuat:

socket

logs

1188. File permissions

Runtime-created files harus menggunakan permission minimum.

Contoh:

lock
socket
state

tidak boleh world-writable.

1189. Socket credential retrieval

Peer identity berasal dari kernel credentials.

Jangan percaya field:

uid

yang dikirim client dalam protocol sebagai sumber authority.

1. Event loop tidak melakukan destructive operation.

2. Event loop tidak membuat filesystem authority.

4. Event loop tidak bypass Scheduler.

7. Semua queue bounded.

8. Semua buffer bounded.

9. Semua connection bounded.

10. Semua timer menggunakan monotonic semantics.

11. Shutdown memiliki priority lebih tinggi daripada normal work.

12. Shutdown menghentikan penerimaan pekerjaan baru.

13. Disconnect client tidak otomatis membatalkan accepted job.

14. Cancellation bersifat cooperative.

15. Cancellation bukan rollback.

16. Stale plan tidak boleh dilanjutkan setelah critical platform change.

17. Unknown state tidak diasumsikan safe.

18. Optional event source failure menghasilkan degraded behavior, bukan silent bypass.

1220. Prinsip penutup runtime

Runtime harus tetap sederhana.

Semakin banyak business logic yang masuk ke event loop, semakin sulit daemon diaudit.

Idealnya ketika seseorang membaca runtime, jawabannya jelas:

"Runtime hanya menunggu event, mengubah event mentah menjadi event terstruktur, mengatur lifecycle, dan mengirimkannya ke application layer."

Dan ketika seseorang bertanya:

"Di mana keputusan bahwa cache boleh dihapus dibuat?"

Jawabannya tetap:

Safety
→ Policy
→ Planner
→ Authorization

Bukan Runtime.

1221. Invariant terbesar seluruh architecture

Pada akhirnya semua pembahasan dari rewrite 1 sampai tahap runtime dapat diringkas menjadi satu invariant:

Tidak ada input eksternal, event kernel, timer, konfigurasi, client request, atau runtime event yang dengan sendirinya memiliki authority untuk melakukan destructive operation.

Semua harus melewati pipeline:

→ Candidate

→ Policy
→ Plan
→ Authorization
→ AuthorizedPlan
→ Execution
→ Verification

Dan runtime hanya memastikan event dapat mencapai layer yang tepat tanpa pernah menjadi jalan pintas menuju execution.
