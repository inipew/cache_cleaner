# 100.md — Implementation Dependency Graph, Execution Order, dan Cutover Plan

## Tujuan

Dokumen 65–99 sekarang harus diterjemahkan menjadi dependency graph implementasi nyata. Tujuannya mencegah rewrite dikerjakan secara acak atau executor destructive dibuat sebelum safety/durability foundation siap.

Prinsip:

```text
foundation
→ domain
→ durable state
→ safety/policy
→ planning
→ authorization
→ execution
→ verification
→ orchestration
→ interfaces
→ migration/cutover
```

## 1. Hard Dependency Graph

```text
Configuration
    ↓
Typed Domain IDs
    ↓
Target Catalog ─────┐
    ↓               │
Candidate Model     │
    ↓               │
Safety ← Platform ──┘
    ↓
Policy
    ↓
Planner
    ↓
Authorization
    ↓
Durable Operation Store
    ↓
Executor
    ↓
Verifier
    ↓
Recovery
    ↓
Scheduler / Worker
    ↓
IPC / CLI
```

Cross-cutting:

```text
Resource Manager
Concurrency
Backpressure
Security
Observability
Lifecycle
Migration
```

harus menjadi constraint seluruh layer, bukan feature setelah executor.

## 2. Phase 0 — Freeze Current Behavior

Sebelum rewrite:

- inventory existing behavior
- capture existing config semantics
- capture CLI semantics
- identify current targets
- record current cleanup results
- identify compatibility requirements

Output: behavioral baseline.

## 3. Phase 1 — Domain Foundation

Implement terlebih dahulu:

```text
TargetId
CandidateId
JobId
AttemptId
OperationId
EventId
Generation
```

Tambahkan typed enums/error taxonomy.

Tidak ada filesystem mutation baru pada phase ini.

## 4. Phase 2 — Configuration

Implement:

- typed config
- validation
- ConfigGeneration
- policy version
- atomic activation
- migration hooks

Config menjadi immutable snapshot untuk downstream decision.

## 5. Phase 3 — Platform Abstraction

Implement platform adapter untuk:

- filesystem metadata
- mount context
- object identity
- power/lifecycle signals
- privilege/capability discovery

Platform-specific code tidak boleh bocor ke domain model.

## 6. Phase 4 — Target Catalog

Implement:

```text
TargetDescriptor
TargetIdentity
TrustedRoot
MountBinding
CatalogGeneration
Availability
SafetyClassification
```

Catalog adalah source untuk target discovery, bukan hard-coded rule engine.

## 7. Phase 5 — Candidate Scanner

Scanner menghasilkan Candidate dari Target Catalog.

Scanner tidak melakukan destructive mutation.

Requirements:

- bounded traversal
- cancellation
- event/reconciliation compatibility
- candidate identity
- deterministic classification input

## 8. Phase 6 — Safety Engine

Implement safety gate:

```text
Candidate
→ trusted target
→ mount/context check
→ identity check
→ object type check
→ revalidation
→ SafetyDecision
```

Safety harus dapat dipanggil kembali dekat mutation boundary.

## 9. Phase 7 — Policy Engine

Implement policy evaluation terpisah dari safety.

Input:

```text
Candidate
Target
ConfigSnapshot
PlatformSnapshot
```

Output typed decision + reason.

## 10. Phase 8 — Planner

Planner mengubah eligible candidates menjadi immutable Plan.

Plan berisi:

- OperationId
- target identity
- expected state
- policy/config generation
- safety context reference
- dependencies
- resource requirements
- budget

## 11. Phase 9 — Authorization

Authorization harus menghasilkan scoped capability.

Capability terikat pada:

- operation
- target
- generation/context
- expiration/lease jika diperlukan

## 12. Phase 10 — Durable Store

Sebelum executor destructive aktif, implement:

- Job store
- Attempt store
- Operation store
- journal
- lease
- idempotency records
- outbox
- schema version

Ini hard blocker untuk production mutation.

## 13. Phase 11 — Resource Manager

Implement admission untuk:

- worker permits
- FD budget
- memory budget
- I/O budget
- per-target serialization

Resource acquisition tidak memberikan authorization.

## 14. Phase 12 — Executor

Executor menjadi satu-satunya mutation boundary.

Pipeline:

```text
claim
→ revalidate
→ authorization check
→ safety check
→ durable intent
→ mutate
→ receipt
→ handoff verifier
```

No shell command.

## 15. Phase 13 — Verifier

Implement:

- postcondition checks
- identity checks
- Unknown classification
- reconciliation
- final result persistence

## 16. Phase 14 — Recovery

Startup recovery harus mampu menangani semua journal states.

Recovery diuji sebelum scheduler mengaktifkan normal mutation.

## 17. Phase 15 — Scheduler

Scheduler menggabungkan:

- manual request
- scheduled maintenance
- platform events
- pressure events
- recovery

Dengan bounded queues/coalescing.

## 18. Phase 16 — Worker Runtime

Worker runtime hanya mengambil authorized work.

Bounded concurrency.

Worker tidak membuat policy sendiri.

## 19. Phase 17 — Backpressure

Implement queue limits sebelum membuka high-rate IPC/event sources.

Queue-full/deferred semantics harus typed.

## 20. Phase 18 — IPC

IPC server menerima untrusted request.

Pipeline:

```text
parse
→ validate
→ identify caller
→ authorize request
→ enqueue
→ return JobId/status
```

Jangan menahan IPC connection untuk full filesystem cleanup.

## 21. Phase 19 — CLI

CLI menjadi thin domain client.

Semua destructive command menggunakan same daemon path.

Tidak ada duplicate filesystem implementation di CLI.

## 22. Phase 20 — Observability

Tambahkan sejak awal execution integration:

- correlation IDs
- structured logs
- metrics
- audit
- health
- wake reason

Jangan menunggu production untuk menambahkan diagnosis.

## 23. Phase 21 — Security Hardening

Sebelum destructive rollout:

- IPC access control
- caller identity
- privilege separation
- no shell
- path race tests
- secret redaction
- resource exhaustion limits

## 24. Phase 22 — Lifecycle / Power

Integrasikan:

- Android lifecycle events
- suspend/resume
- screen/power state
- mount changes
- package/user changes
- bounded wakeup

Idle daemon harus blocking.

## 25. Phase 23 — Migration

Migrasi existing behavior/state:

```text
old config
old targets
old state
old CLI semantics
```

ke new model secara explicit.

## 26. Phase 24 — Test Gate

Test layers:

```text
unit
property
fuzz
integration
filesystem matrix
crash injection
race/stress
Android device
power/lifecycle
upgrade/rollback
performance
```

## 27. Phase 25 — Shadow Mode

Sebelum destructive cutover, new planner dapat berjalan dalam shadow mode:

```text
scan
→ classify
→ plan
→ report
→ NO MUTATION
```

Bandingkan dengan current implementation.

## 28. Phase 26 — Read-Only Production

Deploy new architecture dengan mutation disabled.

Tujuan:

- observe real device behavior
- validate target catalog
- validate policy decisions
- validate resource usage
- validate lifecycle/power behavior

## 29. Phase 27 — Limited Mutation

Enable low-risk target classes terlebih dahulu.

Destructive target categories tetap disabled sampai evidence cukup.

## 30. Phase 28 — Full Cutover

Full mutation hanya setelah:

- recovery proven
- safety proven
- migration proven
- device matrix proven
- power behavior proven
- performance acceptable

## 31. Hard Blockers

Jangan enable destructive executor jika salah satu ini belum selesai:

```text
no durable intent
no verifier
no recovery
no target identity
no safety revalidation
no scoped authorization
unbounded queue
unbounded concurrency
unknown result treated as failed
no crash tests
```

## 32. Parallelizable Work

Dapat dikerjakan paralel setelah domain contracts stabil:

```text
Platform Adapter
Config
IPC protocol
Observability
Test infrastructure
Resource Manager
```

Tetapi interface harus mengikuti domain contracts yang sudah ditetapkan.

## 33. Non-Parallel Work

Urutan yang sebaiknya tetap:

```text
Domain
→ Catalog/Candidate
→ Safety/Policy
→ Planner
→ Authorization
→ Durable Store
→ Executor
→ Verifier/Recovery
```

## 34. Code Ownership Boundaries

Module boundaries yang direkomendasikan:

```text
src/domain/
src/config/
src/platform/
src/catalog/
src/scanner/
src/safety/
src/policy/
src/planner/
src/authorization/
src/store/
src/executor/
src/verifier/
src/recovery/
src/resource/
src/scheduler/
src/worker/
src/ipc/
src/cli/
src/observability/
```

Nama dapat disesuaikan repository, tetapi responsibility harus tetap terpisah.

## 35. Dependency Direction

Idealnya:

```text
domain
  ↑
policy/safety/planner
  ↑
executor/verifier
  ↑
scheduler/worker
  ↑
ipc/cli/platform adapters
```

Infrastructure boleh mengimplementasikan domain interfaces; domain tidak mengimpor concrete infrastructure bila dapat dihindari.

## 36. Forbidden Dependencies

Hindari:

```text
CLI → direct filesystem mutation
Policy → direct syscall
Scanner → executor
Scheduler → filesystem mutation
IPC → privileged syscall
Verifier → mutation
Platform adapter → business policy
```

## 37. Definition of Done

Implementation roadmap selesai jika:

- setiap rewrite document punya implementation owner/module
- dependency direction jelas
- hard blockers enforced
- destructive path melalui satu executor
- durable state tersedia
- recovery tersedia
- lifecycle/power integrated
- security integrated
- tests map ke invariants
- migration/cutover plan executable

## Ultimate Rule

Jika implementasi harus memilih antara:

```text
lebih cepat selesai
```

dan:

```text
lebih mudah dibuktikan aman/recoverable
```

untuk destructive filesystem mutation, pilih yang kedua.

Production readiness adalah property sistem yang dapat dibuktikan, bukan sekadar kumpulan fitur.
