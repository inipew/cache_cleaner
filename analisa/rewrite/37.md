Domain Types dan Immutable Safety Model

Dokumen ini menetapkan tipe domain inti yang digunakan oleh application layer, scheduler, scanner, safety layer, policy engine, planner, authorization layer, executor, verifier, dan telemetry.

Tujuan utamanya adalah membuat representasi data yang aman secara struktural.

Domain type tidak boleh sekadar menjadi wrapper string apabila wrapper tersebut dapat mencegah kesalahan penggunaan.

Sebaliknya, domain juga tidak boleh mengetahui detail Android atau Linux secara langsung.

Domain harus mendeskripsikan konsep.

Platform layer menerjemahkan konsep tersebut menjadi resource sistem yang nyata.

Prinsip utama

Arbitrary filesystem path tidak boleh menjadi input utama ke cleanup pipeline.

Domain menggunakan identifier dan relative path yang tervalidasi.

Platform membuat TrustedRoot.

Scanner menghasilkan Candidate.

Safety mengubah Candidate menjadi SafetyValidatedCandidate.

Policy mengubah candidate yang valid menjadi PolicyApprovedCandidate.

Planner menghasilkan PlannedOperation.

Authorization menghasilkan AuthorizedPlan.

Executor hanya menerima AuthorizedPlan.

Setiap tahap harus memiliki tipe yang berbeda jika perbedaan tersebut membantu mencegah penggunaan object pada tahap yang salah.

Jangan menggunakan satu struct Candidate yang memiliki banyak boolean seperti:

is_safe

is_authorized

is_planned

is_executed

Model seperti itu mudah menghasilkan state yang tidak konsisten.

Lebih aman menggunakan tipe yang mewakili tahap lifecycle.

Primitive domain types

Identifier yang penting harus memiliki type sendiri.

TargetId

PackageId

UserId

JobId

PlanId

OperationId

ConfigGeneration

CatalogGeneration

PlatformGeneration

AttemptId

TimerId

ConnectionId

WorkerId

Jangan menggunakan integer atau string mentah di seluruh subsystem jika nilai tersebut memiliki semantics berbeda.

Contohnya:

UserId(10)

tidak boleh interchangeable secara otomatis dengan:

TargetId(10)

Walaupun representasi internal keduanya mungkin sama-sama integer.

String boundary

String hanya boleh digunakan untuk data yang memang bersifat textual.

Identifier yang memiliki format atau validasi tertentu harus memiliki constructor.

Contoh:

PackageId::parse()

RelativePath::parse()

ProfileId::parse()

Raw string tidak boleh langsung masuk ke executor.

Identifier constructor harus melakukan validation minimum.

Invalid identifier harus gagal pada boundary terdekat.

PackageId

PackageId merepresentasikan identity package Android.

Domain tidak boleh menganggap PackageId selalu dapat diterjemahkan menjadi filesystem path tertentu.

PackageId hanya identity.

Mapping:

PackageId → Android package metadata → target roots

dilakukan oleh platform/catalog layer.

Dengan demikian perubahan Android filesystem layout tidak memaksa perubahan pada domain model.

UserId

UserId merepresentasikan Android user.

User state harus dipisahkan dari identity.

UserId(10) tidak berarti user sedang unlocked.

State seperti:

Unlocked

Locked

Unknown

berada pada platform snapshot atau readiness state.

TargetId

TargetId merepresentasikan logical cleanup target.

Contoh conceptual target:

AppCache

AppCodeCache

TemporaryFiles

DownloadCache

SystemCache

Namun target ID tidak boleh otomatis dianggap sebagai filesystem path.

TargetId hanya menunjuk kategori resource.

Target Catalog menerjemahkan TargetId menjadi target descriptor yang memiliki:

target identity

user scope

package scope

storage class

trusted root

capability requirement

policy metadata

TargetId dari client tidak boleh digunakan untuk membuat arbitrary target.

RelativePath

RelativePath adalah salah satu tipe terpenting dalam filesystem safety.

RelativePath tidak boleh menerima:

absolute path

empty root

parent traversal

embedded null

invalid component

symlink escape semantics

Contoh yang harus ditolak:

/data/foo

../foo

foo/../../bar

foo/../bar

../

.

jika implementation menganggap "." sebagai invalid root component

RelativePath harus memiliki invariant:

path selalu relatif terhadap TrustedRoot.

Namun RelativePath sendiri tidak menjamin filesystem safety.

RelativePath hanya menjamin representasi path tidak keluar dari logical root melalui lexical traversal.

Filesystem identity tetap harus diverifikasi kemudian.

PathComponent

RelativePath sebaiknya dibangun dari validated PathComponent.

PathComponent memiliki aturan lebih ketat.

Component tidak boleh:

empty

"."

".."

mengandung NUL

mengandung separator

memiliki encoding yang tidak dapat direpresentasikan oleh platform abstraction

Dengan demikian RelativePath tidak dibuat dari string concatenation biasa.

Contoh unsafe design:

root + "/" + user_input

Contoh safe conceptual design:

PathComponent → RelativePath → filesystem resolver

TrustedRoot

TrustedRoot bukan string path biasa.

TrustedRoot merepresentasikan filesystem boundary yang sudah diketahui dan diverifikasi.

TrustedRoot minimal memiliki:

root identity

filesystem/device identity

mount identity jika tersedia

root descriptor atau controlled handle

generation

target metadata

Root descriptor sebaiknya dimiliki oleh filesystem abstraction dan tidak diekspos ke domain secara mentah.

Domain cukup mengetahui bahwa sebuah operation memiliki TrustedRootRef.

Filesystem layer yang memegang FD atau handle sebenarnya.

TrustedRoot lifetime

TrustedRoot memiliki lifetime terbatas.

Tidak boleh diasumsikan valid selamanya.

Jika mount berubah:

TrustedRoot dapat menjadi invalid.

Jika device berubah:

TrustedRoot dapat menjadi invalid.

Jika FBE state berubah:

TrustedRoot dapat menjadi unavailable.

Jika catalog generation berubah:

TrustedRoot yang lama tidak boleh dipakai untuk job baru.

TargetDescriptor

TargetDescriptor adalah hasil dari Target Catalog.

Minimal memuat:

TargetId

scope

storage class

capabilities

trusted root reference

generation

availability

TargetDescriptor tidak boleh menyediakan arbitrary path constructor.

TargetDescriptor dibuat oleh platform/catalog layer.

Target scope

Scope dapat berupa:

Global

PerUser

PerPackage

PerPackageUser

Scope menentukan bagaimana target dapat digunakan.

Misalnya AppCache kemungkinan membutuhkan:

PackageId

UserId

TargetId

sedangkan global temporary target mungkin tidak membutuhkan PackageId.

Type system harus mencegah kombinasi parameter yang tidak valid bila memungkinkan.

Target selection

Client tidak boleh mengirim:

TargetId + arbitrary filesystem root

Client hanya boleh meminta target yang sudah didefinisikan catalog.

Jika client meminta target unknown:

request ditolak.

Jika target dikenal tetapi unavailable:

job menjadi Deferred atau request ditolak sesuai semantics.

Candidate

Candidate merepresentasikan resource yang ditemukan scanner.

Candidate belum aman.

Candidate belum diizinkan oleh policy.

Candidate minimal memiliki:

CandidateId

TargetId

RelativePath

object type

metadata snapshot

filesystem identity

object identity

size

timestamps yang relevan

discovery generation

package/user scope bila relevan

Candidate tidak boleh memiliki capability untuk menghapus dirinya sendiri.

Candidate hanya data.

Candidate identity

Candidate harus memiliki identity yang dapat digunakan untuk race detection.

Untuk filesystem object, identity dapat berupa kombinasi metadata yang sesuai platform.

Contoh conceptual identity:

device id

inode

file type

generation/change indicator jika tersedia

Namun implementation tidak boleh menganggap inode saja cukup.

Identity digunakan untuk revalidation.

CandidateSnapshot

Metadata candidate yang dibaca scanner harus dianggap snapshot.

Snapshot dapat menjadi stale segera setelah dibaca.

Karena itu:

CandidateSnapshot != current filesystem state.

Safety layer harus melakukan revalidation sebelum destructive operation.

ObjectType

ObjectType harus typed.

Minimal:

RegularFile

Directory

Symlink

Socket

Fifo

BlockDevice

CharDevice

Unknown

Target policy menentukan object type mana yang dapat dihapus.

Jangan menggunakan string:

"file"

"directory"

"symlink"

sebagai control flow.

Symlink

Symlink harus diperlakukan secara eksplisit.

Secara default cleanup pipeline tidak boleh mengikuti symlink.

Candidate yang merupakan symlink harus ditangani berdasarkan policy.

Jika target hanya mengizinkan regular file:

Symlink → reject.

Jangan dereference lalu menganggap target tersebut sebagai file biasa.

Hard link

Hard link juga harus dipertimbangkan.

Jika policy melarang menghapus object yang memiliki link count tertentu, Candidate harus menyimpan metadata yang diperlukan.

Namun link count bukan satu-satunya safety boundary.

Final filesystem identity check tetap diperlukan.

SafetyValidatedCandidate

SafetyValidatedCandidate hanya dapat dibuat oleh Safety layer.

Constructor publik untuk type ini sebaiknya tidak tersedia secara bebas.

Idealnya hanya safety module yang dapat membuatnya.

Object ini membuktikan bahwa candidate telah melewati validation tertentu.

Validation minimal:

root boundary

path representation

object identity

object type

filesystem identity

symlink rule

target identity

mount/device rule

current availability

race-sensitive revalidation

SafetyValidatedCandidate tetap dapat menjadi stale.

Tipe ini bukan jaminan bahwa filesystem tidak berubah setelah validation.

Ia hanya membuktikan bahwa validation telah dilakukan pada titik tertentu.

PolicyApprovedCandidate

PolicyApprovedCandidate hanya dapat dibuat setelah:

SafetyValidatedCandidate

diberikan kepada Policy Engine.

Policy memeriksa:

target enabled

age requirement

package exclusion

user scope

size constraints

file type policy

maintenance mode

budget

profile

configuration snapshot

Policy rejection bukan safety failure.

Candidate dapat aman secara filesystem tetapi tidak diizinkan policy.

Contoh:

file aman dihapus.

Namun umur file baru dua hari.

Policy minimum age tujuh hari.

Hasil:

SafetyValidatedCandidate berhasil.

PolicyApprovedCandidate tidak dibuat.

PlannedOperation

Planner mengubah PolicyApprovedCandidate menjadi PlannedOperation.

PlannedOperation menjelaskan operation yang ingin dilakukan.

Contoh operation:

DeleteFile

DeleteEmptyDirectory

NoOp

Operation type harus typed.

Jangan membuat operation sebagai arbitrary shell command.

Tidak boleh ada:

RunCommand("rm ...")

Tidak boleh ada:

DeletePath(String)

Planner hanya boleh menggunakan object yang telah melewati safety dan policy.

OperationId

Setiap planned operation memiliki OperationId.

OperationId digunakan untuk:

execution result

verification

telemetry

audit

partial completion

OperationId harus unik setidaknya dalam lifecycle job.

Operation metadata

PlannedOperation dapat memiliki:

OperationId

JobId

TargetId

RelativePath

expected object type

expected object identity

expected filesystem identity

operation kind

estimated bytes

policy reason

safety generation

Namun operation tidak boleh membawa raw privileged capability yang dapat langsung digunakan oleh client.

Authorization

Authorization adalah boundary terakhir sebelum executor.

AuthorizedPlan hanya boleh dibuat setelah semua planned operations lolos final authorization.

AuthorizedPlan memiliki:

PlanId

JobId

ConfigGeneration

CatalogGeneration

PlatformGeneration

operations

execution budget

authorization timestamp

authorization context

plan expiry/deadline

AuthorizedPlan harus immutable.

Setelah dibuat:

operation tidak boleh ditambahkan.

operation tidak boleh diubah.

target tidak boleh diganti.

relative path tidak boleh diganti.

budget tidak boleh dinaikkan.

Jika sesuatu berubah:

buat plan baru.

Plan expiration

AuthorizedPlan sebaiknya memiliki validity boundary.

Plan tidak boleh dianggap valid selamanya.

Plan dapat invalid karena:

timeout

storage change

catalog generation change

config invalidation

platform state change

user lock

cancellation

Jika plan invalid:

executor tidak boleh memaksa execution.

Executor

Executor hanya menerima AuthorizedPlan.

Executor tidak boleh menerima:

raw path

unvalidated candidate

PolicyApprovedCandidate sebagai destructive authorization

TargetId dari client

arbitrary command

Executor harus menggunakan filesystem abstraction.

Filesystem abstraction kemudian melakukan final revalidation.

Ini adalah defense in depth.

ExecutionOperation

Setiap operation dieksekusi secara individual.

Sebelum operation:

check cancellation

check plan validity

check target availability

revalidate identity

revalidate object type

revalidate filesystem identity

perform operation

record result

Jangan menganggap seluruh plan atomic.

Partial execution

Cleanup plan dapat mengalami:

operation 1 success

operation 2 already gone

operation 3 changed type

operation 4 safety rejection

operation 5 filesystem error

Ini harus menjadi hasil yang sah.

Job result harus mampu merepresentasikan partial execution.

OperationResult

OperationResult minimal:

OperationId

status

affected bytes

affected object state

error category bila gagal

verification status

timestamp

Status dapat berupa:

Executed

AlreadyGone

ChangedSinceScan

TypeChanged

SafetyRejected

PolicyRejected

CancelledBeforeExecution

ExecutionFailed

VerificationFailed

Skipped

Tidak semua status harus berarti job failure.

AlreadyGone misalnya dapat dianggap successful cleanup outcome atau benign no-op tergantung policy.

Error model

Error tidak boleh hanya berupa String.

Error harus memiliki category dan context.

Contoh:

FilesystemError

dengan subtype:

PermissionDenied

NotFound

ReadOnlyFilesystem

IoError

InvalidHandle

NoSpace

Busy

Unknown

ProtocolError

dengan subtype:

InvalidMagic

UnsupportedVersion

FrameTooLarge

MalformedPayload

InvalidEnum

TruncatedFrame

Error category harus stabil.

Error message dapat berubah.

Program logic tidak boleh bergantung kepada text message.

SafetyError

Safety error berbeda dari operational error.

Contoh:

PathEscape

RootMismatch

FilesystemMismatch

IdentityMismatch

TypeMismatch

SymlinkRejected

MountChanged

TrustedRootInvalid

CandidateStale

Safety rejection sebaiknya memiliki severity.

Tidak semua safety rejection berarti daemon harus mati.

Candidate-level rejection:

candidate ditolak.

System-level invariant violation:

job dapat dibatalkan.

Runtime invariant violation:

daemon dapat masuk Failed.

PolicyError

Policy rejection bukan exception infrastructure.

Lebih baik direpresentasikan sebagai decision:

PolicyDecision::Allow

PolicyDecision::Reject(reason)

PolicyDecision::Defer(reason)

Dengan demikian policy engine tidak menggunakan exception sebagai normal control flow.

Authorization result

Authorization juga dapat menggunakan typed decision:

Authorized

Rejected

Stale

Cancelled

BudgetExceeded

NotReady

Tidak ada AuthorizedPlan jika decision bukan Authorized.

Snapshot model

Snapshot harus immutable.

Jenis snapshot utama:

ConfigSnapshot

PlatformSnapshot

CatalogSnapshot

ReadinessSnapshot

CandidateSnapshot

AuthorizationSnapshot

ConfigSnapshot

ConfigSnapshot berisi configuration yang telah divalidasi.

Tidak boleh berisi raw unvalidated config.

Configuration loading:

raw config

→ parser

→ schema validation

→ semantic validation

→ ValidatedConfig

→ ConfigSnapshot

→ EffectivePolicy

ConfigSnapshot memiliki generation.

PlatformSnapshot

PlatformSnapshot menggambarkan keadaan platform saat snapshot dibuat.

Contoh:

API level

kernel capabilities

storage state

thermal state

screen state

user state

mount summary

filesystem capabilities

PlatformSnapshot tidak boleh menyediakan destructive methods.

CatalogSnapshot

CatalogSnapshot berisi immutable target descriptors.

CatalogSnapshot memiliki generation.

Setelah generation berubah, snapshot lama tetap dapat dibaca untuk reporting, tetapi tidak boleh digunakan untuk membuat job baru.

ReadinessSnapshot

ReadinessSnapshot adalah hasil evaluasi readiness pada suatu waktu.

Contoh:

ready = false

reason = ScreenOn

snapshot generation = platform generation

ReadinessSnapshot tidak boleh dianggap sebagai permanent authorization.

Readiness dapat berubah setiap saat.

Generation model

Generation digunakan untuk mendeteksi perubahan environment.

Minimum:

ConfigGeneration

CatalogGeneration

PlatformGeneration

Generation harus monotonic dalam lifecycle daemon.

Jika overflow secara praktis memungkinkan, implementation harus memiliki defined behavior.

Jangan menggunakan wall-clock timestamp sebagai generation.

Timestamp dan generation memiliki semantics berbeda.

Generation menunjukkan identity versi.

Timestamp menunjukkan waktu.

Capability model

Capability harus bersifat typed.

Contoh:

CanDeleteCache

CanTrimFilesystem

CanConfigureZram

CanAccessCredentialStorage

CanInspectPackageCache

Capability tidak boleh berasal langsung dari client request.

Capability berasal dari platform detection dan authorization.

Capability juga tidak berarti policy mengizinkan operation.

Platform capability:

filesystem mendukung operation.

Policy permission:

profile mengizinkan operation.

Safety:

operation aman pada object tertentu.

Ketiganya berbeda.

Authorization object

Authorization object sebaiknya tidak dapat dibuat dari constructor publik sederhana.

Contoh konseptual:

AuthorizedPlan::new(...)

tidak boleh callable oleh semua module.

Lebih aman jika authorization module menghasilkan object melalui controlled API.

Tujuannya mencegah developer membuat:

AuthorizedPlan::new(client_path)

tanpa melalui validation.

Type-state

Jika bahasa implementasi mendukung type-state atau private constructors, gunakan untuk membedakan:

Candidate

SafetyValidatedCandidate

PolicyApprovedCandidate

PlannedOperation

AuthorizedPlan

Jangan memaksakan type-state jika menghasilkan kompleksitas yang lebih besar daripada manfaatnya.

Namun prinsipnya tetap:

object yang sudah melewati security gate harus lebih sulit dibuat daripada object biasa.

Serialization

Domain object yang memiliki security semantics tidak boleh langsung diserialisasi ke IPC.

Jangan expose:

TrustedRoot internal

raw FD

authorization capability

internal filesystem identity yang sensitif

private policy metadata

IPC memiliki DTO sendiri.

Contoh:

CleanupRequestDto

JobStatusDto

PlanExplanationDto

Domain type tetap internal.

DTO → domain request

domain result → DTO

bukan:

serialize seluruh domain object.

Explanation model

Explain API harus dapat menjelaskan keputusan tanpa memberikan security-sensitive detail berlebihan.

Contoh:

Candidate rejected because:

TooYoung

ExcludedPackage

UnsafeType

OutsidePolicyScope

TargetUnavailable

Tidak perlu mengembalikan detail internal yang memungkinkan client memahami privileged filesystem structure secara berlebihan.

generation

result

AuditEvent tidak boleh menjadi mutable global log object.

Audit record harus immutable setelah dibuat.

Mutation rules

Immutable by default.

Mutable state hanya pada:

Job state

Scheduler queue

runtime state

worker internal execution state

connection state

buffer

Snapshot tidak mutable.

Candidate tidak mutable setelah dibuat.

PlannedOperation tidak mutable setelah dibuat.

AuthorizedPlan immutable.

ExecutionResult immutable setelah selesai.

Dengan demikian race condition lebih mudah dikendalikan.

Serialization boundary

Jika domain object perlu dikirim antar-thread:

gunakan owned immutable value atau explicit message.

Jangan berbagi mutable object global.

Worker menerima JobExecutionContext yang immutable ditambah cancellation handle.

Worker mengirim result baru.

Application layer menggabungkan result ke state job.

No global mutable context

Jangan membuat:

GLOBAL_CONFIG

GLOBAL_CATALOG

GLOBAL_POLICY

GLOBAL_EXECUTOR

GLOBAL_CURRENT_JOB

yang dapat diakses semua module.

Global mutable state membuat generation semantics sulit diverifikasi.

Job harus membawa context yang diperlukan.

ApplicationController memegang active state secara terstruktur.

Security invariant

Invariant 1:

Raw arbitrary filesystem path bukan authorization object.

Invariant 2:

RelativePath selalu relatif secara lexical terhadap root.

Invariant 3:

RelativePath tidak menjamin filesystem safety.

Invariant 4:

TrustedRoot harus berasal dari trusted platform/catalog path.

Invariant 5:

Candidate bukan AuthorizedPlan.

Invariant 6:

SafetyValidatedCandidate hanya dibuat oleh safety layer.

Invariant 7:

PolicyApprovedCandidate hanya dibuat setelah policy decision Allow.

Invariant 8:

PlannedOperation hanya berasal dari approved candidate.

Invariant 9:

AuthorizedPlan hanya dibuat oleh authorization boundary.

Invariant 10:

AuthorizedPlan immutable.

Invariant 11:

Executor tidak menerima arbitrary path dari IPC.

Invariant 12:

Executor tetap melakukan final revalidation.

Invariant 13:

Snapshot memiliki generation.

Invariant 14:

Generation tidak boleh dimanipulasi client.

Invariant 15:

Domain tidak mengetahui filesystem implementation.

Invariant 16:

Error classification tidak bergantung kepada string matching.

Invariant 17:

Terminal job result tidak boleh diubah oleh late worker event.

Invariant 18:

Security-sensitive domain objects tidak langsung diekspos melalui IPC.

API design principle

API harus membuat penggunaan aman menjadi jalur termudah.

Unsafe code harus membutuhkan explicit lower-level operation.

Safe code harus mengikuti pipeline normal.

Contoh konseptual:

request.target_id

→ catalog.resolve()

→ scanner.discover()

→ safety.validate()

→ policy.evaluate()

→ planner.plan()

→ authorization.authorize()

→ executor.execute()

Jangan menyediakan shortcut:

executor.delete(target_id, path)

Jika shortcut ada, developer berikutnya sangat mungkin menggunakannya.

Definition of done

Domain model dianggap siap jika:

semua identifier penting typed.

relative path tervalidasi.

target tidak direpresentasikan sebagai arbitrary path.

snapshot immutable.

generation explicit.

candidate memiliki identity.

safety validation memiliki output type berbeda.

policy decision typed.

planned operation typed.

authorized plan immutable.

execution result typed.

error taxonomy typed.

domain tidak bergantung kepada platform implementation.

IPC tidak langsung serialize security-sensitive domain object.

executor hanya menerima authorized plan.

race condition dapat direpresentasikan oleh result type.

partial execution dapat direpresentasikan.

stale state dapat direpresentasikan.

Kesimpulan

Domain model harus menjadi mekanisme pertahanan pertama terhadap kesalahan desain.

Tujuan type system di sini bukan sekadar membuat kode lebih rapi.

Tujuannya adalah membuat state yang tidak aman sulit direpresentasikan.

Alur yang diinginkan adalah:

Raw Request

Validated Request

Job

Catalog Snapshot

Candidate

SafetyValidatedCandidate

PolicyApprovedCandidate

PlannedOperation

AuthorizedPlan

ExecutionResult

VerificationResult

JobResult

Setiap tahap mempersempit kemungkinan operation.

Semakin dekat ke executor, semakin sedikit data yang dapat berubah dan semakin banyak invariant yang harus sudah terpenuhi.

Dengan model ini, executor tidak perlu mempercayai seluruh application stack.

Executor tetap melakukan final verification.

Sebaliknya, application layer juga tidak perlu mengetahui detail syscall.

Setiap layer memiliki boundary yang jelas.

Setelah domain types ditetapkan, implementasi berikutnya dapat mulai membangun Scanner Contract.

Scanner akan menjadi subsystem pertama yang menghasilkan Candidate secara nyata.
