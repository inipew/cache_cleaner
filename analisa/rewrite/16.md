Lanjut. Sekarang kita masuk ke **Executor Filesystem**, yaitu boundary paling dekat dengan operasi destruktif.

Kalau Scanner menjawab:

> “Objek apa yang ada?”

Policy menjawab:

> “Objek mana yang layak dibersihkan?”

Planner menjawab:

> “Operasi apa yang akan dilakukan?”

maka Executor hanya menjawab:

> **“Bagaimana menjalankan operasi yang sudah diotorisasi, tanpa memperluas scope?”**

---

# 1. Executor harus dibuat "bodoh"

Ini prinsip terpenting.

Executor **tidak boleh** memiliki logic seperti:

```rust
if file.ends_with(".tmp") {
    delete(file);
}
```

atau:

```rust
if age > 7.days() {
    delete(file);
}
```

Itu milik Policy.

Executor menerima:

```rust
AuthorizedPlan
```

lalu:

```text
AuthorizedPlan
      ↓
revalidate
      ↓
execute exact operation
      ↓
verify
      ↓
result
```

---

# 2. API Executor

Saya akan membuat:

```rust
pub trait Executor {
    fn execute(
        &self,
        plan: &AuthorizedPlan,
        ctx: &ExecutionContext,
    ) -> ExecutionReport;
}
```

Dan **tidak** menyediakan:

```rust
fn delete_path(&self, path: PathBuf)
```

sebagai public API.

Kalau ada function seperti itu, cepat atau lambat akan dipakai dari tempat yang salah.

---

# 3. ExecutionContext

```rust
pub struct ExecutionContext {
    pub cancellation: CancellationToken,
    pub limits: ExecutionLimits,
    pub dry_run: bool,
    pub runtime: RuntimeSnapshot,
}
```

Tambahkan:

```rust
pub struct ExecutionLimits {
    pub max_operations: usize,
    pub max_bytes: u64,
}
```

Budget Planner tetap harus divalidasi lagi.

---

# 4. Dispatcher

Executor utama:

```rust
fn execute_operation(
    op: &AuthorizedOperation,
    ctx: &ExecutionContext,
) -> OperationResult {
    match &op.operation {
        Operation::RemoveFile(op) =>
            filesystem.remove_file(op, ctx),

        Operation::RemoveEmptyDirectory(op) =>
            filesystem.remove_empty_directory(op, ctx),

        Operation::TrimFilesystem(op) =>
            trim.execute(op, ctx),

        Operation::F2fsMaintenance(op) =>
            f2fs.execute(op, ctx),

        Operation::ZramMaintenance(op) =>
            zram.execute(op, ctx),
    }
}
```

Tidak ada:

```text
guess target
discover target
recursive arbitrary deletion
```

di dispatcher.

# 5. AuthorizedOperation

Sebelumnya kita punya:

```rust
pub struct AuthorizedPlan {
```

Saya akan membuat tiap operation juga typed:

```rust
pub struct AuthorizedOperation {
```

Tetapi authorization sebaiknya tetap melekat pada plan, sehingga tidak ada cara membuat operation authorization secara terpisah tanpa melalui validation.

# 11. Kenapa `unlinkat()`?

Karena operasi deletion dilakukan relatif terhadap directory FD.

Secara konsep:

```text
root_fd
   │
   └── parent_fd
          │
          └── target
```

Kemudian:

```text
unlinkat(parent_fd, target)
```

bukan:

```text
unlink("/absolute/path/to/target")
```

Ini mempertahankan filesystem namespace yang sudah kita validasi.

---

# 12. Parent directory juga harus trusted

Misalnya:

```text
root/
  a/
    b/
      file
```

Jangan hanya validate:

```text
file
```

Tetapi seluruh traversal:

```text
root
 ↓
a
 ↓
b
 ↓
file
```

harus menggunakan directory handles dan `NOFOLLOW`.

Kalau `a` berubah menjadi symlink:

```text
a → /system
```

traversal berhenti.

---

# 13. RelativePath traversal

Buat:

```rust
pub fn open_relative_parent(
    root: &DirectoryHandle,
    path: &RelativePath,
) -> Result<ParentTarget>;
```

Misalnya:

```text
foo/bar/baz.tmp
```

akan menjadi:

```text
root
 ↓ openat("foo")
foo_fd
 ↓ openat("bar")
bar_fd
 ↓ final = "baz.tmp"
```

Tidak pernah menjadi:

```text
"/root/foo/bar/baz.tmp"
```

---

# 14. Reject `..`

`RelativePath` tidak boleh mengandung:

```text
..
```

Jadi:

```text
foo/../bar
```

ditolak sebelum traversal.

Tidak perlu:

```text
normalize()
```

dan berharap aman.

Lebih baik path representation memang tidak bisa membuatnya.

---

# 15. Absolute path

Juga reject:

```text
/data/user/0/foo/cache/x
```

di `RelativePath`.

Hanya:

```text
x
a/b/x
```

yang valid.

```rust
PurgeDirectoryContents
```


```rust

    target: AppCacheRoot,
```


# 19. Implementasi purge

Secara konsep:

```text
trusted root
 ↓
enumerate
 ↓
validate each entry
 ↓
remove files
 ↓
recurse safe directories
 ↓
remove empty child dirs
 ↓
root remains
```

Jadi:

```text
purge(root)
```

secara semantic berarti:

> remove eligible contents under this already-trusted root.

Bukan:

> delete root recursively.

# 21. Kenapa tidak `std::fs::remove_dir_all()`?

Karena abstraction tersebut terlalu tinggi untuk security boundary ini.

Kita membutuhkan kontrol eksplisit atas:

```text

identity
cancellation
errors
races
```

Dengan recursive custom traversal, setiap step dapat divalidasi.

# 22. Recursive deletion algorithm

Saya akan memakai konsep **post-order traversal**:

```text
directory
    ↓
children
    ↓
files deleted
    ↓
child directories empty
    ↓
remove child directory
```

Contoh:

```text
A/
├── x
└── B/
    ├── y
    └── C/
        └── z
```

Urutan:

```text
x
z
C
y
B
A
```

Tetapi untuk root:

```text
A
```

tidak dihapus jika A adalah trusted target root.

---

# 23. Iterative traversal lebih baik daripada recursive Rust stack

Jangan:

```rust
fn walk(dir) {
    for child in dir {
        if child.is_dir() {
            walk(child);
        }
    }
}
```

untuk unbounded depth.

Lebih baik explicit stack:

```rust
struct WalkFrame {
    dir: DirectoryHandle,
    iterator: DirectoryIterator,
    relative: RelativePath,
}
```

Kemudian:

```text
stack.push(root)
```

dan loop.

Ini membuat:

```text
max_depth
```

lebih mudah ditegakkan.

---

# 24. Executor stack

Contoh:

```text
root
 ↓
frame A
 ↓
frame B
 ↓
frame C
```

Jika:

```text
depth == max_depth
```

jangan push child.

Result:

```text
DepthExceeded
```

---

# 25. Cancellation di recursive executor

Check:

```text
before each frame
before each child
before delete
after expensive operation
```

Contoh:

```rust
if ctx.cancellation.is_cancelled() {
    return Err(ExecutionError::Cancelled);
}
```

Kalau cancellation terjadi setelah 300 dari 1000 file:

```text
300 deleted
700 remain
```

Itu **normal partial execution**.

# 26. Partial execution bukan corruption

Report:

```text
planned = 1000
completed = 300
cancelled = 700
```

Scheduler kemudian:

```text
cancelled
   ↓
fresh scan later
```

Jangan resume plan lama.

# 27. ENOENT

Jika target sudah hilang:

```text
unlinkat()
→ ENOENT
```

Ini:

```rust
OperationResult::AlreadyGone
```

bukan error fatal.

Ini penting karena aplikasi bisa menghapus cache sendiri.

---

# 28. EACCES / EPERM

```text
unlinkat()
→ EACCES
```

hasil:

```rust
OperationResult::Failed {
    error: PermissionDenied
}
```

Jangan retry cepat.

Scheduler bisa menentukan:

```text
RetryPolicy::Never
```

atau:

```text
Later(...)
```

tergantung target.

---

# 29. ELOOP

Kalau:

```text
ELOOP
```

terjadi pada path component:

```text
Symlink
```

atau symlink-related traversal.

Jangan retry.

```text
SafetyViolation::Symlink
```

---

# 30. EXDEV

Kalau:

```text
EXDEV
```

terjadi dalam konteks operation yang seharusnya same-device:

```text
CrossDevice
```

dan:

```text
reject
```

Jangan mencoba:

```text
copy
delete source
```

untuk "menyelesaikan".

Cleaner bukan file mover.

# 31. EBUSY

Directory atau filesystem sedang busy:

```text

```

→:

```text

```

Scheduler bisa:

```text

```

daripada aggressive retry loop.

# 58. Executor invariants final

Ini saya anggap kontrak paling penting:

```text
1. Executor only executes AuthorizedPlan.

2. Executor never discovers new targets.

3. Executor never expands operation scope.

4. Executor never follows symlinks.

5. Executor never crosses filesystem boundaries.

6. Executor revalidates root and target.

7. Executor validates object identity.

8. Executor validates expected type.

9. Executor uses FD-relative operations.

10. Executor never uses canonicalize + delete.

11. Executor never uses rm -rf.

12. Executor never turns RemoveFile into RemoveTree.

13. RemoveEmptyDirectory never becomes recursive delete.

14. ENOENT is idempotent.

15. Identity/type changes fail closed.

16. Cancellation stops further destructive work.

17. Partial execution is explicitly reported.

18. Missing target is not fatal.

19. Verification never performs additional destructive operations.

20. Executor cannot bypass Safety or Policy.
```

```text
                 AuthorizedPlan
                        │
                        ▼
                    Executor
                        │
                        ▼
                 Revalidation
                        │
                        ▼
                 FD-relative op
                        │
                        ▼
                  Linux syscall
                        │
                        ▼
                     Result
```

Perhatikan bahwa semakin ke bawah, informasi tentang **“apa yang sebaiknya dibersihkan”** justru semakin sedikit.

Executor tidak perlu tahu:

```text
"ini cache karena mtime-nya tua"
```

Ia hanya tahu:

```text
"operation #123 meminta RemoveFile terhadap object identity X di trusted root Y."
```

Itulah desain yang kita inginkan.

## Tahap berikutnya: `Domain + Target Catalog` sampai benar-benar siap dikodekan

Kita sudah membahas komponennya secara terpisah. Sekarang langkah yang paling bernilai adalah **mengunci kontrak Rust antar-module** sebelum menulis implementation:

```text
domain/
    Candidate
    TargetRoot
    Operation
    CleanupPlan
    Decision
    Job

fs/
    TrustedRoot
    DirectoryHandle
    ObjectIdentity
    RelativePath

scanner/
    RawEntry
    Scanner
    ScanResult

safety/
    SafetyValidated
    SafetyProof

policy/
    PolicyApproval
    PolicyDecision

planner/
    PlannedOperation
    PlanValidator

executor/
    AuthorizedPlan
    OperationResult
```

Di tahap berikutnya kita bisa menyusun **trait, struct, enum, ownership, lifetime, `Send + Sync`, error hierarchy, dependency antar-crate/module, dan urutan compile dari project kosong sampai binary daemon pertama**. Itu akan menjadi blueprint Rust konkret sebelum kita mulai menulis ulang `cache_cleaner` dari nol.
