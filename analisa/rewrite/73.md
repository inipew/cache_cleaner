73.md — Authorization, Capability Grants, Scope, Expiry, Generation Binding, Confirmation, Revocation, and Execution Admission Contract

Tujuan

Authorization adalah boundary yang menerjemahkan user/job intent + PolicyDecision + platform capabilities menjadi explicit capability grant untuk operation tertentu.

Authorization tidak melakukan filesystem mutation dan tidak menggantikan SafetyGate.

Pipeline:

Intent → Policy → Plan → Authorization → Resource Admission → Safety → Executor

1. Authorization Is Explicit

Tidak boleh ada implicit authorization hanya karena caller mencapai API tertentu.

2. Authorization Identity

Gunakan typed AuthorizationId.

3. Capability

Capability harus typed dan minimal.

Contoh:

```rust
pub enum Capability {
    ReadTarget,
    EnumerateTarget,
    DeleteFile,
    DeleteDirectory,
    ReclaimStorage,
    RunMaintenance,
}
```

4. Least Authority

Grant hanya capability yang benar-benar dibutuhkan operation.

5. No Wildcard Capability

Hindari `FullFilesystemAccess` atau equivalent broad grant untuk normal cleanup.

6. Target Scope

Grant harus mengikat TargetId.

7. Operation Scope

Grant harus mengikat OperationId atau logical operation key.

8. Path Scope

Jika operation path-specific, grant harus mengikat relative path/identity yang relevan.

9. Config Generation

Authorization harus mengikat ConfigGeneration.

10. Catalog Generation

Authorization harus mengikat CatalogGeneration.

11. Policy Fingerprint

Sebaiknya bind ke policy/ruleset fingerprint untuk audit dan stale detection.

12. Intent Binding

Grant harus traceable ke original JobIntent.

13. User/Caller Identity

Authorization record harus menyimpan principal/caller identity sesuai IPC/security model.

14. Local Daemon

Walaupun IPC hanya local socket, client identity dan request authentication harus explicit.

15. CLI

CLI adalah untrusted input boundary.

16. IPC

IPC request tidak boleh langsung menjadi Authorization object.

17. DTO Validation

Parse + validate DTO sebelum authorization.

18. Capability Availability

Platform capability harus dicek sebelum grant.

19. Capability != Permission

Kernel/file permission adalah platform fact; Authorization adalah application decision.

20. Policy Allow

Policy allow diperlukan tetapi tidak cukup untuk authorization.

21. Safety

Authorization allow tidak bypass SafetyGate.

22. Force

Force intent harus menjadi explicit authorization request dan tidak boleh bypass hard safety.

23. Manual Cleanup

Manual invocation tetap melewati policy/protection/safety.

24. Admin Mode

Jika ada admin mode, scope harus explicit dan auditable.

25. Confirmation

Destructive operations tertentu dapat membutuhkan user confirmation.

26. Confirmation Token

Confirmation harus typed dan one-time/scoped bila memungkinkan.

27. Confirmation Binding

Confirmation harus bind ke Job/Plan fingerprint, bukan sekadar `confirmed=true`.

28. Confirmation Expiry

Confirmation harus expire.

29. Replay Protection

Old confirmation tidak boleh dipakai untuk Plan berbeda.

30. Authorization Expiry

Every grant harus mempunyai expiry/deadline bila operation tidak immediate.

31. Long-running Job

Untuk long-running job, grant harus dapat revalidate/renew secara explicit.

32. Renewal

Renewal bukan automatic expansion of scope.

33. Revocation

Authorization dapat direvoke ketika:

- config changes
- catalog changes
- user/session revoked
- safety incident
- daemon shutdown
- job cancelled

34. Revocation Visibility

Executor harus dapat mengetahui grant sudah revoked sebelum mutation.

35. In-flight Syscall

Revocation tidak dapat selalu membatalkan syscall yang sedang berjalan; result harus direconcile.

36. Generation Mismatch

Mismatch ConfigGeneration/CatalogGeneration membuat authorization stale.

37. Stale Authorization

Stale authorization tidak boleh dieksekusi.

38. Reauthorization

Stale authorization harus membuat new authorization decision, bukan patch old grant.

39. No In-place Grant Expansion

Authorization object immutable setelah issue.

40. Immutable Grant

Gunakan immutable capability token/object.

41. Grant Scope

Minimal:

- AuthorizationId
- JobId
- OperationId/logical key
- principal
- capabilities
- target identity
- path scope
- config generation
- catalog generation
- policy fingerprint
- issued_at monotonic/wall timestamp
- expiry
- confirmation state

42. Machine-readable Reason

Authorization denial memiliki stable reason code.

43. Human Explanation

CLI/UI dapat meminta explain authorization.

44. Explain Is Read-only

Explain tidak mengubah grant.

45. Denial Reasons

Contoh:

- CapabilityUnavailable
- PolicyDenied
- ProtectedTarget
- ScopeViolation
- ConfirmationRequired
- ConfirmationInvalid
- GenerationStale
- Expired
- PrincipalNotAllowed
- ResourceUnavailable
- MaintenanceMode
- InternalError

46. Internal Error

Authorization internal error fail-closed.

47. Unknown

Unknown authorization context tidak menghasilkan grant.

48. Protected Target

Authorization tidak dapat grant destructive capability untuk target yang hard-protected oleh architecture.

49. Safety Protected

Even admin cannot bypass kernel/filesystem safety invariants.

50. Capability Mapping

Map target operation → minimum capabilities.

51. No Capability Inflation

Jika operation hanya DeleteFile, jangan grant DeleteDirectory.

52. Recursive Delete

Recursive delete membutuhkan explicit DeleteDirectory/Recursive capability, bukan inferensi dari DeleteFile.

53. Reclaim

Storage reclaim harus capability terpisah dari file deletion.

54. Maintenance

TRIM/ZRAM/F2FS/system maintenance harus capability class terpisah.

55. Platform Capability

Android adapter expose actual supported capability.

56. Root

Root availability bukan automatic application authorization; it is platform capability input.

57. SELinux

SELinux denial harus fail-closed dan observable.

58. Privilege Boundary

Privilege escalation tidak boleh dilakukan sebagai hidden authorization fallback.

59. Subprocess

Authorization tidak boleh menghasilkan arbitrary shell execution.

60. Command Surface

Operation API harus typed; no arbitrary command string grant.

61. Scope Algebra

Authorization scope harus dapat dibandingkan secara formal:

`requested_scope ⊆ granted_scope`.

62. Scope Narrowing

Child component hanya boleh narrow scope, never widen.

63. Scope Expansion

Expansion membutuhkan new authorization.

64. Target Scope

Target scope dapat berupa TargetId + relative prefix.

65. Prefix Safety

String prefix matching bukan sufficient path containment proof.

66. Path Scope

Gunakan normalized RelativePath + identity-bound target root.

67. Package Scope

Package-scoped grant harus bind PackageName + UserId jika relevant.

68. Storage Scope

Storage operation bind StorageIdentity.

69. Mount Scope

Mount-sensitive operation bind MountIdentity.

70. Multi-target Job

Grant per operation/target lebih aman daripada satu wildcard grant.

71. Aggregate Grant

Jika aggregate grant diperlukan, scope list harus bounded dan immutable.

72. Grant Count Limit

Prevent capability token explosion.

73. Time Bounds

Every grant must respect job deadline and authorization expiry.

74. Clock

Use monotonic deadlines for runtime expiry; wall clock only for human/audit timestamps.

75. Clock Rollback

Wall-clock rollback tidak boleh memperpanjang runtime grant.

76. Persistence

Authorization records yang dibutuhkan recovery harus durable.

77. Durable Before Publish

Grant publication harus mengikuti persistence-before-publication contract.

78. Crash Before Commit

No durable grant means no executable authorization after restart.

79. Crash After Commit

Recovery must inspect grant expiry/generation before resuming.

80. Recovery

Recovery tidak boleh blind-resume old grant.

81. Job Cancellation

Cancellation revokes future execution admission.

82. Job Timeout

Timeout invalidates grant for new mutation.

83. Shutdown

Graceful shutdown prevents new grant issuance after shutdown barrier.

84. Daemon State

Authorization issuance harus memperhatikan daemon lifecycle state.

85. Starting

Startup state tidak menerima arbitrary destructive requests sebelum all safety dependencies ready.

86. ShuttingDown

No new destructive authorization.

87. Resource Admission

Authorization tidak reserve resources; ResourceManager melakukan reservation.

88. Resource Failure

Resource unavailable menghasilkan wait/defer, bukan expanded capability.

89. Priority

Priority tidak meningkatkan destructive scope.

90. Fairness

High-priority caller tidak boleh memperoleh unrestricted capability.

91. Policy Exceptions

Exception dapat mempengaruhi authorization only if policy contract permits and exception itself is valid.

92. Exception Expiry

Temporary exception harus expire.

93. Exception Audit

Record exception identity/reason without leaking secrets.

94. Secret Handling

Authorization must never log secret credentials/tokens.

95. Caller Authentication

IPC transport authentication dan authorization application policy harus distinct layers.

96. Caller Identity

Use OS peer credentials/capability mechanism where platform supports it.

97. Spoofed Caller

Caller-provided username/UID string is not trusted identity.

98. Root Caller

Root caller can access IPC only if transport permits, but application safety invariants still apply.

99. Authorization Delegation

A worker must not be able to mint broader authorization than coordinator.

100. Capability Delegation

Delegated capability must be subset of parent grant.

101. Worker Token

Worker execution context should receive narrow operation-bound grant.

102. Token Confusion

AuthorizationId must not be accepted as OperationId/JobId.

103. Type Safety

Distinct IDs prevent confused-deputy bugs.

104. Serialization

Authorization DTO versioned.

105. Deserialization

Deserialized grant must be revalidated before use.

106. Signature/MAC

If persisted/IPC token can cross trust boundary, integrity protection may be required.

107. Local IPC

Do not assume local socket means trusted client.

108. Replay

RequestId/idempotency key must prevent duplicate grant creation where needed.

109. Duplicate Request

Same request may return existing authorization decision if idempotency contract permits.

110. Different Plan

Same idempotency key must never accidentally authorize a different plan.

111. Audit

Issue/revoke/expire/use events should be auditable.

112. Use Event

Execution should record AuthorizationId used.

113. Revocation Event

Revocation should record reason and affected scope.

114. Metrics

Expose grants issued, denied, expired, revoked, stale, and scope violations.

115. Rate Limits

Authorization requests should be bounded to prevent IPC abuse.

116. Denial Flood

Repeated denied requests should not cause unbounded audit growth.

117. Backpressure

Authorization subsystem should cooperate with scheduler/resource limits.

118. Race: Config Reload

If config changes between authorization and execution, generation check must block stale grant.

119. Race: Catalog Refresh

Catalog identity change invalidates affected grant.

120. Race: Policy Update

Ruleset fingerprint change invalidates affected grant.

121. Race: Target Replacement

SafetyGate must detect object replacement even if authorization remains otherwise valid.

122. Race: Cancellation

Cancellation between authorization and executor must prevent new mutation.

123. Race: Timeout

Expired grant must not admit new mutation.

124. Race: Resource Release

Released reservation does not imply authorization remains valid.

125. SafetyProof

Authorization does not substitute SafetyProof.

126. Executor API

Recommended:

```rust
pub struct AuthorizedExecutionContext {
    pub authorization: AuthorizationGrant,
    pub operation: PlannedOperation,
    pub deadline: Instant,
}
```

Executor then obtains SafetyProof separately.

127. No Mutable Authorization Context

Execution context immutable after admission.

128. Context Narrowing

Worker context may remove privileges but never add them.

129. Child Operation

A worker cannot derive authorization for arbitrary sibling/parent paths.

130. Definition of Done

Authorization production-ready jika:

- typed capabilities
- explicit scope
- operation/target binding
- generation binding
- policy fingerprint binding
- expiry
- revocation
- confirmation binding
- caller identity validation
- least authority
- no wildcard destructive grants
- worker delegation narrowing
- durable state where needed
- audit/metrics
- stale checks
- no safety bypass
- property/fuzz/race tests

131. Final Invariants

1. Authorization is explicit.
2. Authorization is immutable after issue.
3. Capability is least-privilege.
4. Capability availability is not authorization.
5. Policy allow is not authorization.
6. Authorization never bypasses SafetyGate.
7. Force never bypasses hard safety.
8. Scope cannot widen through child components.
9. Target identity is bound.
10. Operation identity is bound.
11. ConfigGeneration is bound.
12. CatalogGeneration is bound.
13. Policy fingerprint should be bound where relevant.
14. Expired grant cannot execute.
15. Revoked grant cannot execute.
16. Stale grant cannot execute.
17. Confirmation is operation/plan-bound.
18. Root caller does not bypass application safety invariants.
19. Worker cannot mint broader capability.
20. IPC caller identity is not caller-provided text.
21. Authorization errors fail-closed.
22. Unknown authorization never becomes allow.
23. Arbitrary shell command is never an authorization capability.
24. Recursive deletion requires explicit capability.
25. Reclaim/maintenance are separate capabilities.
26. Crash recovery never blindly resumes stale grants.
27. Cancellation/timeout stop future admission.
28. Every destructive execution records AuthorizationId.
29. Authorization audit is immutable and redacted.
30. SafetyProof remains mandatory before mutation.
