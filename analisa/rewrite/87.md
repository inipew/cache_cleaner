# 87.md — Idempotency, Duplicate Execution, Replay, dan Retry Safety

## Tujuan

Setelah crash consistency ditetapkan, sistem harus mempunyai aturan agar execution yang sama tidak menghasilkan mutation atau accounting yang salah ketika request, worker, event, atau recovery diproses lebih dari sekali.

Prinsip utama:

```text
same logical operation
        ↓
may be observed/executed more than once
        ↓
result must remain safe and deterministic
```

Exactly-once execution tidak boleh diasumsikan hanya karena scheduler memiliki satu worker.

## 1. Identity Adalah Dasar Idempotency

Bedakan identity berikut:

```text
JobId       = logical request
AttemptId   = execution attempt
OperationId = intended mutation
EventId     = event delivery identity
WorkerId    = execution actor
RecoveryEpoch = recovery session
```

Retry terhadap operation yang sama mempertahankan `OperationId` tetapi menggunakan `AttemptId` baru.

## 2. Idempotency Key

Setiap external request yang dapat menghasilkan Job harus mempunyai request identity/idempotency key.

Duplicate request tidak boleh menghasilkan dua cleanup Job jika semantics request sama.

Contoh:

```text
client request X
      ↓
Job J1

client retries X
      ↓
same idempotency key
      ↓
return/reference J1
```

## 3. Idempotency Scope

Idempotency key harus mempunyai scope yang jelas.

Jangan membuat key global tanpa expiration/namespace jika request identity berasal dari client.

Scope dapat mencakup:

- client identity
- operation type
- request key
- API version

## 4. Operation Identity Tidak Sama dengan Attempt

Contoh:

```text
Operation O1
 ├─ Attempt A1
 ├─ Attempt A2
 └─ Attempt A3
```

Semua attempt mengejar postcondition yang sama.

Membuat OperationId baru setiap retry akan menyulitkan reconciliation dan dapat menyebabkan duplicate mutation/accounting.

## 5. Delete Idempotency

Untuk delete, idempotency harus berbasis expected identity.

Jika object yang diharapkan sudah hilang:

```text
AlreadySatisfied
```

dapat valid jika identity semantics membuktikan object tersebut adalah target yang sama.

Jika path berisi replacement object:

```text
NOT satisfied
```

dan operation tidak boleh menghapus replacement hanya karena path sama.

## 6. Idempotency Bukan Blind Retry

Operation idempotent bukan berarti boleh langsung diulang setelah timeout/crash.

Urutan tetap:

```text
Unknown
 ↓
reconcile
 ↓
known actual state
 ↓
retry only if safe
```

## 7. Duplicate Worker Execution

Scheduler harus mencegah dua active worker menjalankan mutation yang sama secara normal.

Jika race tetap terjadi akibat crash/restart atau stale message, operation identity dan execution lease harus membuat duplicate execution dapat dideteksi.

## 8. Execution Lease

Long-running execution dapat menggunakan lease:

```text
Operation O1
owner = Worker W1
lease = L1
```

Worker baru tidak boleh mengambil operation yang masih memiliki valid lease.

Lease expiry bukan bukti worker mati; lakukan liveness/recovery check terlebih dahulu.

## 9. Stale Worker

Message dari worker lama harus membawa identity yang dapat diverifikasi:

```text
JobId
AttemptId
WorkerId
ExecutionEpoch/lease
```

Message stale harus ditolak atau diproses idempotently tanpa mengubah current state.

## 10. Retry Classification

Retry aman bila:

- mutation belum dimulai, atau
- reconciliation membuktikan desired postcondition belum tercapai, dan
- operation contract mengizinkan retry, dan
- fresh safety/authorization tersedia.

Retry tidak aman bila actual state tidak dapat dibedakan.

## 11. Retry Before Mutation

Failure sebelum mutation boundary biasanya dapat membuat Attempt baru:

```text
A1 failed
 ↓
A2
```

OperationId tetap sama.

## 12. Retry After Mutation

Setelah mutation mungkin dimulai:

```text
A1 → Unknown
```

Tidak boleh langsung:

```text
A2 → execute
```

Harus:

```text
A1 Unknown
 ↓
reconcile
 ↓
retry classification
```

## 13. Retry Budget

Retry harus bounded.

Minimal simpan:

- attempt count
- retry reason
- first attempt timestamp
- last attempt timestamp
- next eligible time
- terminal retry classification

## 14. Backoff

Transient failure menggunakan bounded backoff.

Backoff tidak boleh membuat retry tetap aktif ketika device sedang:

- suspended
- thermally constrained
- battery constrained
- storage unavailable

Scheduler dapat menunda retry sampai platform state sesuai.

## 15. Duplicate Event Delivery

Event delivery harus dianggap at-least-once.

Consumer menggunakan EventId/idempotency key untuk menghindari duplicate transition.

Contoh:

```text
Event E17
 ↓
transition committed

E17 delivered again
 ↓
no second transition
```

## 16. Event Ordering

Event yang terlambat tidak boleh mengembalikan state ke masa lalu.

Gunakan sequence/version/generation sesuai domain.

Contoh:

```text
state version 10
late event based on version 8
→ reject/stale
```

## 17. Duplicate Publication

Publisher dapat crash setelah mengirim event tetapi sebelum menandai outbox delivered.

Event dapat dikirim lagi.

Consumer harus aman terhadap replay.

## 18. Job Submission Replay

Jika client tidak menerima response karena IPC disconnect, client boleh mengirim ulang request.

Server harus mengembalikan existing Job untuk idempotency key yang sama daripada membuat Job baru.

## 19. Cancellation Replay

Duplicate cancellation request tidak boleh menghasilkan error yang mengubah outcome.

Cancellation dapat bersifat idempotent:

```text
Cancel J1
Cancel J1 again
```

keduanya tidak boleh menyebabkan additional mutation.

## 20. Recovery Replay

Recovery manager sendiri dapat dijalankan lebih dari sekali.

Contoh:

```text
startup
→ reconcile O1
→ crash
→ startup
→ reconcile O1
```

Reconciliation harus convergent terhadap actual state.

## 21. Verification Replay

Verifier harus dapat dijalankan berkali-kali tanpa mutation.

Jika evidence sama, classification harus sama.

## 22. Accounting Replay

Accounting final harus keyed oleh OperationId/Result identity.

Contoh salah:

```text
Attempt A1 deleted 100 MB
crash
Attempt A2 sees already gone
→ +100 MB lagi
```

Accounting harus mencegah double count.

## 23. Logical vs Physical Accounting

Idempotency harus diterapkan pada setiap accounting metric:

- logical bytes removed
- estimated physical reclaim
- filesystem free-space delta

Jangan menjumlahkan free-space delta sebagai operation bytes tanpa korelasi yang jelas.

## 24. Side Effects Selain Filesystem

Idempotency harus mencakup side effect lain:

- audit event
- metrics
- notifications
- IPC response state
- durable outbox
- cleanup statistics

Telemetry duplicate tidak boleh merusak correctness.

## 25. Idempotent State Transition

Transition harus mempunyai expected version/state.

Contoh:

```text
UPDATE job
SET state = Verifying, version = version + 1
WHERE job_id = ?
  AND version = ?
  AND state = Executing
```

Jika affected rows = 0, transition tidak boleh dipaksakan.

## 26. Compare-and-Swap Semantics

Concurrent actor harus menggunakan CAS/version semantics pada state yang shared.

Ini mencegah:

```text
Worker A sees Executing
Worker B sees Executing
A → Completed
B → Failed
```

tanpa conflict detection.

## 27. Operation Lock

Operation identity dapat dilindungi oleh durable execution claim.

Lock/lease hanya mencegah concurrent execution; lock bukan proof bahwa mutation berhasil.

## 28. Process Restart

Setelah restart:

```text
load operations
 ↓
identify active/unknown attempts
 ↓
reconcile
 ↓
resume only safe work
```

Tidak boleh membuat Attempt baru hanya karena process restart jika existing attempt masih membutuhkan reconciliation.

## 29. Target Reuse

Path reuse merupakan salah satu sumber duplicate-danger terbesar.

```text
/delete/cache.tmp
```

Target lama hilang lalu object baru muncul dengan path yang sama.

Operation identity harus menyimpan expected object identity agar retry tidak menyentuh object baru.

## 30. Rename

Rename dapat mengubah path tanpa mengubah object identity.

Jika operation semantics identity-based, verifier/reconciler harus dapat membedakan rename dari replacement bila filesystem metadata mendukungnya.

## 31. Recursive Operation

Recursive cleanup tidak boleh dianggap satu atomic mutation.

Setiap child operation perlu identity/progress semantics yang dapat direcover.

Jika crash setelah 500 dari 1000 object:

```text
500 verified
500 unresolved/not attempted
```

Recovery melanjutkan berdasarkan actual state, bukan mengulang seluruh tree secara buta.

## 32. Best-Effort Operations

Jika operation contract memang best-effort, retry hanya pada subset yang aman.

Successful child tidak boleh dieksekusi ulang tanpa alasan.

## 33. Deterministic Planner Replay

Replanning setelah failure harus menggunakan explicit snapshot/generation.

Planner tidak boleh menghasilkan mutation berbeda secara diam-diam hanya karena current config berubah, kecuali policy memang mengizinkan replan.

## 34. Authorization Replay

Authorization lama tidak otomatis berlaku untuk retry.

Retry dapat membutuhkan authorization baru jika:

- expired
- generation berubah
- scope berubah
- target identity berubah

## 35. Safety Replay

Safety selalu dievaluasi kembali sebelum mutation baru.

Operation yang sebelumnya aman tidak otomatis aman setelah:

- mount change
- target replacement
- permission change
- config change
- system state change

## 36. Idempotency Window

Beberapa idempotency keys memerlukan retention period.

Retention harus cukup panjang untuk menangani client retry tetapi tidak boleh membuat durable store tumbuh tanpa batas.

Cleanup idempotency records sendiri harus durable dan aman.

## 37. Tombstones

Jika diperlukan, completed request identities dapat disimpan sebagai tombstone agar duplicate request lama tidak membuat Job baru.

Tombstone retention harus mempunyai policy eksplisit.

## 38. Poison Replay

Request yang terus di-replay dengan malformed/deterministically failing semantics tidak boleh membuat unbounded work.

Rate limit/admission control tetap berlaku.

## 39. Convergence

Tujuan idempotency bukan sekadar "tidak duplicate" tetapi convergence:

```text
replay same input
      ↓
actual state approaches desired state
      ↓
repeated processing eventually becomes no-op
```

## 40. Definition of Done

Idempotency production-ready jika:

- Job submission memiliki request identity
- OperationId stabil across retry
- AttemptId baru setiap execution retry
- duplicate events aman
- stale worker message ditolak
- execution claim/lease tersedia
- retry hanya setelah safe classification
- Unknown tidak blind retry
- accounting deduplicated
- target identity dipertahankan
- recursive operations recoverable
- authorization/safety direfresh untuk retry
- replay convergent
- tombstone/retention policy jelas
- duplicate publication aman
- CAS/version transition digunakan

## Final Invariants

1. Retry tidak membuat OperationId baru untuk logical mutation yang sama.
2. AttemptId baru untuk setiap execution attempt baru.
3. Unknown tidak boleh langsung di-retry.
4. Reconciliation mendahului retry setelah mutation boundary.
5. Duplicate request tidak membuat duplicate Job jika idempotency semantics sama.
6. Duplicate event tidak boleh menggandakan transition.
7. Duplicate publication harus aman.
8. Stale worker message tidak boleh mengambil alih current execution.
9. PID bukan execution identity.
10. Accounting tidak boleh double count.
11. Replacement object tidak boleh dianggap target lama.
12. Retry memerlukan fresh safety/authorization bila context berubah.
13. Recursive operation harus recoverable per operation/child semantics.
14. Verification replay harus read-only dan deterministic.
15. Cancellation replay harus idempotent.
16. Recovery replay harus convergent.
17. Retry count harus bounded.
18. Backoff harus bounded.
19. Idempotency records tidak boleh tumbuh tanpa batas.
20. Correctness tidak bergantung pada exactly-once execution.
