# 95.md — Performance Model, Benchmarking, dan Capacity Planning

## Tujuan

Performance production-grade bukan berarti daemon selalu menggunakan CPU sebanyak mungkin. Untuk cache cleaner, tujuan performance adalah menyelesaikan cleanup dengan biaya CPU, I/O, memory, battery, thermal impact, dan wakeup yang masuk akal.

Prinsipnya:

```text
performance = useful work / total system cost
```

## 1. Optimize the Right Work

Pisahkan:

- scheduler overhead
- scan cost
- candidate classification
- planning
- mutation
- verification
- persistence
- IPC
- logging

Jangan mengoptimalkan komponen yang bukan bottleneck.

## 2. Idle Performance

Idle adalah performance mode yang sangat penting pada Android.

Target:

```text
no eligible work
→ no active polling
→ blocked wait
→ negligible CPU
```

Fast wakeup tidak berarti busy loop.

## 3. Wakeup Cost

Ukur:

```text
wake
→ snapshot
→ evaluate
→ decision
```

dan jumlah wakeup per hour/day.

## 4. Throughput vs Latency

Cleanup batch besar lebih cocok diukur throughput:

```text
files/sec
bytes/sec
operations/sec
```

Manual request lebih cocok latency:

```text
request → Job accepted
request → result
```

## 5. End-to-End Latency

Job latency sebaiknya dipecah:

```text
queue wait
+ resource wait
+ scan
+ plan
+ execute
+ verify
+ persist
+ publish
```

## 6. Filesystem Cost

Filesystem cleanup sering dominated oleh metadata operations, bukan raw bandwidth.

Benchmark harus membedakan:

- many small files
- few large files
- deep directories
- large candidate set
- cache-heavy trees

## 7. Directory Traversal

Traversal performance dipengaruhi:

- syscall count
- directory depth
- number of entries
- FD strategy
- metadata reads
- cache state

## 8. Metadata Optimization

Hindari repeated `stat`/metadata calls jika evidence yang sama masih valid dan operation contract mengizinkan.

Tetapi jangan cache safety-critical identity melewati invalidation boundary.

## 9. Scan Streaming

Large scan sebaiknya dapat diproses secara streaming/chunked.

Jangan memaksa seluruh filesystem candidate set berada di RAM.

## 10. Candidate Representation

Candidate object harus compact.

Simpan data yang diperlukan untuk planning/safety, bukan seluruh filesystem metadata jika tidak diperlukan.

## 11. String Allocation

Path-heavy workloads dapat menghasilkan allocation tinggi.

Benchmark allocation rate dan pertimbangkan borrowed/owned representation sesuai lifetime.

Jangan mengorbankan safety demi menghilangkan allocation kecil.

## 12. Parallel Scan

Parallel scan dapat meningkatkan throughput pada workload tertentu, tetapi juga meningkatkan:

- I/O contention
- FD usage
- CPU
- thermal load
- power consumption

Gunakan bounded concurrency.

## 13. Parallel Mutation

Mutation parallelism harus conservative.

Bottleneck filesystem sering bukan CPU.

Benchmark berbagai concurrency level daripada mengasumsikan semakin banyak worker semakin cepat.

## 14. Verification Cost

Verifier dapat menjadi bottleneck setelah mutation throughput dinaikkan.

Capacity model harus memasukkan verification.

## 15. Persistence Cost

Jangan commit database transaction per filesystem entry jika tidak diperlukan.

Gunakan batching dengan batas durability semantics yang jelas.

Critical intent sebelum mutation tetap harus durable sesuai contract.

## 16. Batch Size

Batch terlalu kecil:

- transaction overhead tinggi
- syscall overhead tinggi

Batch terlalu besar:

- crash recovery lebih sulit
- memory tinggi
- latency tinggi

Gunakan bounded adaptive batching.

## 17. Database Indexing

Index hanya untuk query recovery/operational path yang memang sering digunakan.

Over-indexing meningkatkan write cost.

Minimal evaluate index untuk:

- Job state
- Attempt state
- OperationId
- idempotency key
- lease owner/status
- outbox status
- timestamps/next retry

## 18. SQLite Tuning

Benchmark actual device storage.

Parameter seperti WAL/checkpoint/synchronous/cache harus dipilih berdasarkan durability requirement dan measured workload.

Jangan copy tuning dari server database tanpa menguji Android storage behavior.

## 19. Memory Capacity

Tentukan budget eksplisit untuk:

- scanner
- candidate queue
- planner
- worker state
- durable store cache
- IPC

## 20. FD Capacity

Ukur peak FD usage.

Production daemon harus memiliki margin terhadap process/system FD limits.

## 21. Queue Capacity

Queue depth harus bounded dan capacity dipilih berdasarkan memory budget serta expected burst.

## 22. Resource Saturation

Measure:

```text
CPU saturation
I/O saturation
memory pressure
FD pressure
queue saturation
thermal pressure
```

Satu metric tidak cukup.

## 23. Thermal Performance

Sustained benchmark pada Android harus memperhatikan thermal throttling.

Benchmark lima detik dapat menipu untuk workload yang berjalan beberapa menit.

## 24. Battery Cost

Cleanup yang lebih cepat belum tentu lebih baik jika concurrency tinggi meningkatkan battery drain.

Ukur energy proxy seperti:

- active CPU time
- wakeups
- runtime
- screen-off behavior
- suspend disruption

## 25. Suspend Preservation

Benchmark harus memastikan background daemon tidak menghambat suspend.

Test:

```text
idle
→ screen off
→ long sleep
→ wake
```

Bandingkan dengan daemon tidak berjalan jika memungkinkan.

## 26. Fast Resume

Ukur:

```text
resume event
→ daemon ready
→ first useful decision
```

Tidak perlu rebuild seluruh catalog sebelum daemon dapat kembali blocking.

## 27. Cold Start

Benchmark cold start:

```text
process start
→ durable store ready
→ platform snapshot
→ scheduler ready
```

## 28. Warm Start

Warm resume harus lebih murah jika cached metadata masih valid.

Namun stale data harus invalidated berdasarkan generation/event semantics.

## 29. Benchmark Dataset

Gunakan dataset representatif:

```text
tiny
small
medium
large
very-large
```

dan variasi file size/count/depth.

## 30. Real Device Benchmark

Synthetic benchmark berguna untuk regression, tetapi final Android performance harus diuji pada real storage/device.

Storage implementation dan thermal behavior dapat sangat berbeda antar device.

## 31. Benchmark Reproducibility

Catat:

- device model
- Android version
- filesystem
- storage state
- battery state
- thermal state
- config generation/policy version
- dataset characteristics
- build profile

## 32. Warm vs Cold Filesystem Cache

Benchmark perlu membedakan cold-cache dan warm-cache behavior.

Jika tidak, hasil dapat terlihat jauh lebih baik daripada first-run behavior.

## 33. Statistical Reporting

Jangan hanya memakai satu fastest run.

Gunakan:

- median
- p95
- p99 bila relevan
- throughput distribution
- variance

## 34. Regression Budget

Tetapkan threshold untuk perubahan penting:

```text
idle wakeups
memory peak
FD peak
scan latency
cleanup throughput
verification latency
startup time
```

Regression yang signifikan harus terlihat di CI/device benchmark.

## 35. Microbenchmark

Microbenchmark berguna untuk:

- path parsing
- candidate classification
- policy evaluation
- serialization
- hashing

Tetapi jangan menjadikannya proxy utama untuk end-to-end filesystem performance.

## 36. Macrobenchmark

Macrobenchmark mengukur:

```text
scan → plan → execute → verify → persist
```

Ini lebih relevan untuk release acceptance.

## 37. Fault + Performance

Performance testing juga perlu failure conditions.

Contoh:

- permission errors
- mount unavailable
- partial scan failure
- DB contention
- queue saturation
- retry/backoff

Sistem yang cepat hanya pada happy path belum production-grade.

## 38. Power + Performance

Benchmark background cleanup saat screen-off.

Pastikan workload tidak menghasilkan wake storm atau wakelock berlebihan.

## 39. Scheduler Efficiency

Ukur:

```text
wakeup → useful decision ratio
```

Jika daemon bangun 100 kali tetapi hanya satu wakeup menghasilkan work, scheduler/dependency perlu diperbaiki.

## 40. Logging Impact

Benchmark dengan:

- normal logging
- debug logging

untuk mengetahui apakah logging menjadi bottleneck.

Production idle mode harus minim I/O.

## 41. Allocation Profiling

Jika candidate-heavy workload lambat, ukur allocation/clone/copy overhead sebelum melakukan optimization.

## 42. Flamegraphs

Gunakan profiling untuk menemukan hot path.

Jangan mengoptimalkan berdasarkan tebakan.

## 43. Performance Contract

Performance requirement dapat berupa budget:

```text
idle CPU ≈ no runnable polling loop
max memory ≤ budget
max workers ≤ configured bound
wakeups/hour ≤ target under idle
startup ≤ target on reference device
```

Nilai exact harus berasal dari measured target hardware, bukan arbitrary universal numbers.

## 44. Capacity Planning

Tentukan maximum supported workload:

- candidate count
- path length
- tree depth
- concurrent jobs
- database records
- queue depth

Jika workload melewati limit, daemon harus degrade gracefully atau reject/defer.

## 45. Large Operation Strategy

Operation sangat besar dapat dipecah menjadi bounded chunks.

Setiap chunk memiliki durable progress/recovery semantics.

## 46. No Unbounded Optimization Cache

Cache metadata harus mempunyai:

- size limit
- lifetime
- invalidation

Cache tidak boleh menjadi memory leak terselubung.

## 47. Optimization Safety

Setiap optimization harus mempertahankan:

- identity semantics
- safety checks
- authorization
- verification
- recovery

Fast unsafe deletion bukan performance success.

## 48. Benchmark CI

CI dapat menjalankan micro/macro benchmarks pada deterministic fixtures.

Real-device benchmark dapat dilakukan pada dedicated hardware when available.

## 49. Performance Observability

Production metrics harus dapat menjawab:

```text
why slow?
```

misalnya apakah karena scan, resource wait, I/O, thermal backoff, atau persistence.

## 50. Definition of Done

Performance model production-ready jika:

- idle behavior measurable
- wakeup cost measurable
- scan/plan/execute/verify separated
- memory/FD/queue budgets explicit
- concurrency bounded
- Android real-device benchmark tersedia
- thermal/power effects measured
- cold/warm behavior measured
- statistical reporting digunakan
- regression budget tersedia
- fault + performance tested
- capacity limits explicit
- optimization tidak bypass safety/recovery

## Final Invariants

1. Performance bukan CPU usage maksimum.
2. Idle daemon harus power-neutral secara praktis.
3. Wakeup count sama pentingnya dengan CPU time.
4. Scan/plan/execute/verify harus dapat diatribusikan.
5. Parallelism harus bounded.
6. Memory/FD/queue capacity harus explicit.
7. Database batching tidak boleh merusak durability semantics.
8. Android performance harus diuji pada real device.
9. Thermal throttling harus diperhitungkan.
10. Suspend preservation harus diuji.
11. Fast resume tidak memerlukan busy activity.
12. Benchmark harus reproducible.
13. Median/p95 lebih berguna daripada fastest run tunggal.
14. Fault conditions harus masuk performance testing.
15. Logging impact harus diketahui.
16. Optimization tidak boleh menghapus safety/authorization.
17. Large workload harus bounded/chunked.
18. Cache harus bounded dan invalidatable.
19. Capacity overflow harus degrade/reject/defer secara explicit.
20. Performance regression harus observable sebelum release.
