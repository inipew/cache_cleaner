45.md — Policy Engine Contract, Rule Evaluation, Eligibility Decision, Policy Precedence, Safe Defaults, dan Explainable Cleanup Policy

1. Tujuan

Policy Engine adalah decision layer yang menentukan apakah Candidate secara konseptual eligible untuk dibersihkan berdasarkan EffectivePolicy.

Policy Engine tidak melakukan:

→ filesystem mutation
→ filesystem traversal
→ authorization
→ capability escalation
→ raw syscall
→ arbitrary path resolution
→ retry
→ execution

Policy Engine menjawab satu pertanyaan:

```
"Berdasarkan policy yang berlaku,
 apakah Candidate ini eligible untuk menjadi operation?"
```

Alur:

```
Candidate
    │
    ▼
Policy Engine
    │
    ├── Eligible
    ├── Excluded
    ├── Deferred
    └── Rejected
    │
    ▼
PolicyDecision
    │
    ▼
PolicyApprovedCandidate
    │
    ▼
  Planner
```

2. Posisi Policy Engine

Arsitektur:

```
Scanner
   │
   ▼
Candidate
   │
   ▼
Safety
   │
   ▼
Policy Engine
   │
   ▼
PolicyDecision
   │
   ▼
Planner
```

Safety dan Policy memiliki tanggung jawab berbeda.

```
Safety:
    "Apakah object ini aman untuk dipertimbangkan?"

Policy:
    "Apakah object ini sesuai aturan cleanup?"
```

Policy tidak boleh menganggap:

```
policy match = safe
```

Safety tetap mandatory.

3. Policy Engine Tidak Menjadi Safety Layer

Contoh policy:

```
minimum_age = 7 days
```

Candidate:

```
age = 30 days
```

Policy:

```
eligible
```

Tetapi jika Safety menemukan:

```
identity changed
```

hasil akhir tetap:

```
reject
```

Flow:

```
Candidate
   │
   ▼
Safety
   │
   ├── reject ───────────────► stop
   │
   ▼
Policy
   │
   ├── eligible
   └── excluded
   │
   ▼
Planner
```

4. EffectivePolicy

Policy Engine hanya menerima policy yang sudah tervalidasi.

```
RawConfig
    │
    ▼
ConfigValidator
    │
    ▼
ValidatedConfig
    │
    ▼
EffectivePolicy
    │
    ▼
Policy Engine
```

Policy Engine tidak boleh menerima raw configuration.

5. EffectivePolicy Harus Immutable

Untuk satu Job:

```
Job J1
   │
   └── ConfigGeneration G10
                │
                ▼
          EffectivePolicy
```

Policy tidak boleh berubah di tengah Job.

Jika configuration reload:

```
G10 → G11
```

Job J1 tetap:

```
G10
```

Job berikutnya menggunakan:

```
G11
```

6. Policy Snapshot

Policy input minimal:

```
PolicyContext {
    policy
    candidate
    catalog_snapshot
    platform_snapshot
    runtime_snapshot
    config_generation
}
```

Semua snapshot harus konsisten dengan Job.

7. PolicyDecision

Gunakan typed result.

```
PolicyDecision

    ├── Eligible
    ├── Excluded
    ├── Deferred
    └── Rejected
```

Makna:

```
Eligible
    → boleh dilanjutkan ke Planner

Excluded
    → secara policy tidak menjadi target

Deferred
    → belum boleh diproses sekarang,
      tetapi bukan permanent rejection

Rejected
    → input atau kondisi melanggar policy
```

8. Excluded vs Rejected

Keduanya berbeda.

Contoh:

```
target:
    app cache

policy:
    cleanup app cache = false
```

Result:

```
Excluded
```

Sedangkan:

```
target:
    unsupported object type
```

Result:

```
Rejected
```

Excluded berarti:

```
"policy tidak memilih target ini."
```

Rejected berarti:

```
"candidate tidak memenuhi contract."
```

9. Deferred

Contoh:

```
target eligible
   │
   ▼
runtime condition:
    user active
   │
   ▼
policy requires idle
   │
   ▼
Deferred
```

Deferred bukan failure.

10. PolicyDecision Harus Explainable

Decision minimal memiliki:

```
decision
reason_code
rule_id
evidence
```

Contoh:

```
Eligible

rule:
    APP_CACHE_MIN_AGE

evidence:
    age = 30d
    minimum_age = 7d
```

11. Reason Code

Reason code harus typed dan stabil.

Contoh:

```
TARGET_TYPE_NOT_ALLOWED
TARGET_EXCLUDED
AGE_BELOW_MINIMUM
PACKAGE_EXCLUDED
USER_SCOPE_EXCLUDED
TARGET_CLASS_DISABLED
RUNTIME_NOT_ELIGIBLE
MAINTENANCE_DISABLED
UNKNOWN_TARGET_CLASS
POLICY_CONFLICT
INVALID_POLICY_CONTEXT
```

String message hanya presentation.

12. Policy Rule

Policy terdiri dari rule.

Contoh:

```
Rule {
    id
    priority
    matcher
    action
}
```

Matcher:

```
target type
package
user
age
size
scope
runtime state
```

Action:

```
Allow
Exclude
Defer
Reject
```

13. Rule Tidak Boleh Memiliki Mutation

Rule hanya membaca:

```
Candidate
PolicyContext
```

Tidak boleh:

```
delete()
unlink()
rename()
chmod()
```

Policy evaluation harus pure.

14. Rule ID

Setiap rule harus memiliki stable identifier.

Contoh:

```
APP_CACHE_ENABLED
MINIMUM_AGE
EXCLUDED_PACKAGE
USER_SCOPE
TARGET_CLASS
RUNTIME_IDLE_REQUIRED
```

Rule ID berguna untuk:

→ explain
→ audit
→ debugging
→ testing

15. Rule Ordering

Rule harus deterministic.

Jangan bergantung pada:

```
HashMap iteration order
```

Gunakan:

```
explicit priority
```

Contoh:

```
priority 100
    safety-derived exclusion

priority 80
    explicit package exclusion

priority 50
    target class eligibility

priority 20
    minimum age
```

Namun ordering harus didefinisikan oleh policy semantics, bukan kebetulan implementasi.

16. Default Deny

Untuk target class yang tidak dikenal:

```
Unknown
   │
   ▼
Excluded / Rejected
```

Default tidak boleh:

```
Unknown → Allow
```

Prinsip:

```
unknown ≠ eligible
```

17. Unknown Metadata

Jika Candidate tidak memiliki age yang valid:

```
age = Unknown
```

dan policy membutuhkan:

```
minimum_age
```

maka:

```
tidak memenuhi evidence
```

Default:

```
Excluded atau Rejected
```

tergantung policy contract.

Tidak boleh menganggap:

```
Unknown age = old
```

18. Unknown User State

Jika User state tidak diketahui:

```
Locked
Unlocked
Unknown
```

Policy tidak boleh menganggap:

```
Unknown = Unlocked
```

Default conservative.

Jika policy membutuhkan unlocked:

```
Unknown → Deferred
```

atau:

```
Unknown → Excluded
```

sesuai semantics.

19. Package Identity

Policy dapat menggunakan:

```
PackageId
```

tetapi tidak boleh membuat PackageId dari arbitrary path.

Package identity berasal dari:

```
TargetCatalog
```

Bukan:

```
parse("/data/user/0/...") → package
```

20. Package Exclusion

Contoh:

```
excluded_packages:
    com.example.system
    com.example.critical
```

Jika candidate terkait package tersebut:

```
Excluded
```

Policy tidak boleh menghapus exclusion hanya karena target sudah tua.

21. System Package

System package harus conservative.

Jika status package:

```
system
privileged
unknown
```

policy dapat:

```
exclude
```

Default aman lebih penting daripada maximum cleanup.

22. Shared Storage

Shared storage bukan otomatis app cache.

Contoh:

```
/storage/emulated/0/...
```

Policy harus memiliki target class eksplisit.

Jika tidak ada target class:

```
Excluded
```

Jangan melakukan:

```
"path looks temporary → delete"
```

23. Target Class

Gunakan typed classification.

Contoh:

```
TargetClass

    ├── AppCache
    ├── AppCodeCache
    ├── Temporary
    ├── PackageSpecific
    ├── SharedStorage
    ├── SystemData
    └── Unknown
```

Policy rule harus match berdasarkan class.

24. Arbitrary Path Tidak Bisa Menjadi Policy Target

Dilarang:

```
policy:
    delete_path = "/some/path"
```

Policy hanya bekerja terhadap:

```
TargetId
```

Flow:

```
TargetCatalog
    │
    ▼
TargetId
    │
    ▼
Candidate
    │
    ▼
Policy
```

25. Minimum Age

Age policy harus menggunakan timestamp semantics yang jelas.

Contoh:

```
now = 2026-09-02
minimum_age = 7d

last_modified =
    2026-08-20

age = 13d

→ eligible
```

Clock untuk age evaluation harus berasal dari:

```
WallClock snapshot
```

dan harus konsisten dalam satu evaluation batch.

26. Clock Skew

Jika timestamp filesystem:

```
future timestamp
```

misalnya:

```
mtime > now
```

policy tidak boleh menganggap object sangat tua.

Conservative result:

```
AgeUnknown
```

atau:

```
Excluded
```

27. Timestamp Tidak Boleh Menjadi Satu-satunya Safety

Object:

```
age = 365 days
```

tidak berarti:

```
safe to delete
```

Safety tetap memeriksa:

→ root
→ identity
→ type
→ mount
→ scope
→ authorization

28. Size Policy

Jika policy memiliki:

```
maximum_cleanup_bytes
```

maka size digunakan untuk eligibility/planning.

Contoh:

```
candidate size = 2 GiB
policy limit = 1 GiB
```

Candidate dapat:

```
Eligible
```

tetapi Planner kemudian hanya dapat mengalokasikan budget secara terbatas.

Policy dan budget tetap berbeda.

29. Global Cleanup Budget

Policy tidak boleh menggunakan mutable global counter.

Jangan:

```
rule evaluation
   │
   └── global bytes_remaining -= size
```

Karena:

→ non-deterministic
→ concurrency-sensitive
→ sulit diuji

Budget allocation adalah tanggung jawab Planner/Scheduler.

30. Policy Evaluation Pure

Idealnya:

```
decision = evaluate(policy, context)
```

tanpa side effect.

Dengan input sama:

```
evaluate(P, C)
    ==
evaluate(P, C)
```

31. Determinism

Policy Engine harus deterministic.

```
same Candidate
same EffectivePolicy
same Snapshot
    │
    ▼
same PolicyDecision
```

Tidak boleh bergantung pada:

→ thread scheduling
→ filesystem traversal timing
→ random state
→ global mutable state

32. Rule Composition

Policy dapat terdiri dari:

```
AND
OR
NOT
```

Contoh:

```
AppCache
  AND
age >= 7d
  AND
package not excluded
```

Hasil:

```
Eligible
```

Namun expression tree harus bounded.

33. Expression Depth

Policy tidak boleh menerima expression tree yang tidak terbatas.

Contoh:

```
max_rule_depth = 32
```

Jika lebih:

```
INVALID_POLICY
```

Ini mencegah stack exhaustion dan evaluation abuse.

34. Rule Count

Policy juga memiliki:

```
max_rules
```

Contoh:

```
max_rules = 1000
```

Policy dengan:

```
1.000.000 rules
```

harus ditolak saat config validation.

35. Evaluation Cost

Policy evaluation harus bounded.

Budget dapat berupa:

```
max_rules_evaluated
max_expression_depth
max_lookup_count
```

Jika budget habis:

```
PolicyEvaluationError
```

Tidak boleh infinite evaluation.

36. Short-circuit Evaluation

Jika:

```
A AND B AND C
```

dan:

```
A = false
```

maka:

```
B dan C tidak perlu dievaluasi.
```

Tetapi explain harus tetap dapat menunjukkan:

```
A caused exclusion
```

bukan membuat user mengira seluruh rule dievaluasi.

37. Explain Trace

Internal trace:

```
Rule A → match
Rule B → match
Rule C → fail
```

Public explanation:

```
excluded because:
    minimum age requirement not met
```

Jangan mengirim seluruh internal evaluation tree secara default.

38. Precedence

Policy conflict harus deterministic.

Contoh:

```
Rule A:
    Allow

Rule B:
    Exclude
```

Jika keduanya match, harus ada contract.

Baseline:

```
Reject
    >
Exclude
    >
Defer
    >
Allow
```

Tetapi precedence final harus ditetapkan eksplisit dalam EffectivePolicy.

39. Explicit Exclusion Wins

Sebagai default konservatif:

```
explicit exclusion
    >
generic allow
```

Contoh:

```
rule:
    allow AppCache

rule:
    exclude package X
```

package X:

```
Excluded
```

40. Safety Failure Wins

Policy tidak boleh mengalahkan Safety.

```
Safety = reject
Policy = allow
```

Final:

```
reject
```

Safety berada di luar Policy precedence.

41. Authorization Wins Later

Policy:

```
Eligible
```

tidak berarti:

```
Authorized
```

Flow:

```
Policy Eligible
    │
    ▼
Planner
    │
    ▼
Authorization
    │
    ├── authorized
    └── denied
```

Policy tidak dapat memberikan capability.

42. Runtime Conditions

Runtime condition dapat memengaruhi eligibility.

Contoh:

```
require_screen_off = true

screen = on
```

Result:

```
Deferred
```

Jika:

```
thermal = high
```

dan policy membutuhkan thermal normal:

```
Deferred
```

Runtime readiness tidak boleh diubah menjadi:

```
Excluded
```

jika kondisi memang transient.

43. Permanent vs Transient

Policy result harus dapat membedakan:

```
Permanent
    │
    ├── target class disabled
    ├── package excluded
    └── unsupported target

Transient
    │
    ├── screen on
    ├── user active
    ├── thermal high
    └── storage unavailable
```

Permanent:

```
tidak perlu retry cepat.
```

Transient:

```
scheduler dapat mencoba lagi.
```

44. Policy Decision Metadata

Contoh:

```
PolicyDecision {
    decision
    rule_id
    reason_code
    permanence
    evidence
    policy_generation
}
```

Semua immutable.

45. Policy Generation

Decision harus terikat:

```
ConfigGeneration
```

Contoh:

```
PolicyGeneration = G10
```

Jika config reload:

```
G10 → G11
```

Decision dari G10 tidak boleh digunakan untuk Job G11.

46. Candidate Generation

Policy juga harus mengetahui:

```
CatalogGeneration
```

Jika Candidate berasal dari:

```
CatalogGeneration C10
```

dan current context:

```
C11
```

maka candidate mungkin stale.

Policy tidak boleh secara otomatis menganggap candidate valid.

47. Snapshot Consistency

Policy evaluation membutuhkan:

```
PolicyGeneration
CatalogGeneration
PlatformGeneration
```

Semua harus tercatat.

Contoh:

```
P10 / C20 / R7
```

Jika mismatch:

```
INVALID_POLICY_CONTEXT
```

atau:

```
STALE
```

48. Batch Evaluation

Untuk efisiensi:

```
CandidateStream
   │
   ▼
PolicyEvaluator
   │
   ├── C1 → Eligible
   ├── C2 → Excluded
   ├── C3 → Deferred
   └── C4 → Rejected
```

Batch tidak boleh mengubah semantics dibanding evaluation individual.

49. Batch Determinism

Harus berlaku:

```
evaluate_batch(C1,C2,C3)
    ==
evaluate(C1)
evaluate(C2)
evaluate(C3)
```

Tidak boleh candidate pertama memengaruhi candidate kedua.

50. No Hidden Global State

Dilarang:

```
static mutable policy state
```

Contoh buruk:

```
previous_candidate
global_counter
last_decision
```

Policy Engine harus stateless atau state-nya immutable.

51. Policy Context

Context dapat memiliki:

```
Candidate
EffectivePolicy
TargetDescriptor
PackageMetadata
UserState
RuntimeState
PlatformSnapshot
CatalogSnapshot
ClockSnapshot
```

Semua harus berasal dari authoritative source.

52. Policy Tidak Mengakses Filesystem

Policy Engine tidak boleh:

```
stat(path)
readdir(path)
open(path)
```

Jika metadata diperlukan:

```
Scanner menyediakan Candidate metadata
```

Jika metadata tidak tersedia:

```
policy menghasilkan Unknown/Excluded/Deferred
```

Jangan membuat Policy Engine menjadi scanner kedua.

53. Policy Não Confia em Metadata

Candidate metadata berasal dari Scanner.

Policy boleh menggunakannya sebagai evidence, tetapi Executor/Safety tetap melakukan final validation.

```
Scanner metadata
      │
      ▼
   Policy
      │
      ▼
 Planner
      │
      ▼
 Authorization
      │
      ▼
   Executor
      │
      ▼
final safety
```

54. Candidate Metadata Staleness

Jika Candidate:

```
size = 100 MiB
```

tetapi saat execution:

```
size = 500 MiB
```

Policy tidak boleh menganggap:

```
100 MiB
```

sebagai fakta final.

Final safety/execution tetap menggunakan current validation.

55. Policy dan TOCTOU

Policy evaluation bukan final authorization.

Contoh:

```
scan:
    candidate eligible

policy:
    allow

race:
    target changes

executor:
    final safety rejects
```

Ini normal dan harus didukung.

56. Rule Categories

Rule dapat dikelompokkan:

```
Scope Rules
   │
   ├── user
   ├── package
   └── target

Eligibility Rules
   │
   ├── age
   ├── size
   └── type

Exclusion Rules
   │
   ├── protected package
   ├── protected target
   └── protected scope

Runtime Rules
   │
   ├── idle
   ├── screen
   └── thermal
```

57. Protected Targets

Policy dapat memiliki protected class.

Contoh:

```
SystemData
CredentialData
UserData
ConfigurationData
```

Default:

```
Excluded
```

Protection harus bersifat explicit.

58. Protected Package

Package tertentu dapat selalu dikecualikan.

Contoh:

```
protected_packages
```

Rule:

```
package ∈ protected_packages
    │
    ▼
Excluded
```

Tidak boleh ada generic cleanup rule yang override explicit protection.

59. Configuration Validation

Sebelum Policy Engine digunakan:

```
RawConfig
   │
   ▼
Parse
   │
   ▼
Validate
   │
   ├── rule count
   ├── depth
   ├── enum validity
   ├── duration bounds
   ├── target IDs
   └── conflict validity
   │
   ▼
EffectivePolicy
```

Invalid policy:

```
daemon startup failure
```

atau:

```
reload rejected
```

Tidak boleh policy invalid masuk ke evaluator.

60. Config Reload

Flow:

```
SIGHUP / IPC
      │
      ▼
ConfigLoader
      │
      ▼
Validate
      │
      ├── invalid → reject reload
      │
      ▼
EffectivePolicy G11
      │
      ▼
atomic swap
```

Active Job:

```
tetap menggunakan G10
```

New Job:

```
menggunakan G11
```

61. Failed Reload

Jika config baru invalid:

```
old policy tetap aktif
```

Jangan:

```
invalid config
    │
    ▼
policy = empty
    ✕
```

Atomicity:

```
old valid policy
      │
      ▼
failed reload
      │
      ▼
old valid policy
```

62. Empty Policy

Empty policy harus memiliki semantics eksplisit.

Default conservative:

```
no cleanup target eligible
```

Bukan:

```
empty policy = cleanup everything
```

63. Missing Field

Missing policy field harus memiliki default yang aman.

Contoh:

```
target_class omitted
```

→ disabled

Bukan:

```
omitted = all
```

64. Unknown Enum

Config:

```
target_class = "something_new"
```

Jika binary tidak mengenalnya:

```
reject configuration
```

Bukan:

```
treat as generic target
```

65. Policy Version

EffectivePolicy memiliki:

```
policy_version
```

Contoh:

```
version = 1
```

Version digunakan untuk compatibility dan migration.

66. Migration

Jika config schema berubah:

```
old config
   │
   ▼
migration
   │
   ▼
validated config
   │
   ▼
EffectivePolicy
```

Migration harus deterministic dan tidak memperluas privilege.

67. No Privilege Expansion During Migration

Contoh:

```
old:
    cache_only = true
```

migration tidak boleh menghasilkan:

```
delete_system_data = true
```

Migration hanya mempertahankan atau memperketat semantics kecuali perubahan tersebut eksplisit.

68. Policy Serialization

Domain Policy tidak boleh langsung menjadi wire protocol.

Gunakan:

```
PolicyConfigDto
    │
    ▼
Validator
    │
    ▼
EffectivePolicy
```

IPC client tidak boleh mengirim executable rule object.

69. IPC Policy Update

Jika policy dapat diubah melalui IPC:

```
IPC
  │
  ▼
authorization
  │
  ▼
config validation
  │
  ▼
atomic policy reload
```

IPC tidak boleh:

```
set arbitrary policy
    │
    ▼
bypass validation
```

70. Capability Separation

Policy configuration capability:

```
CONFIGURE_POLICY
```

Cleanup capability:

```
EXECUTE_CLEANUP
```

Keduanya berbeda.

Memiliki capability untuk membaca status tidak berarti boleh mengubah policy.

71. Explain Policy

Explain request:

```
"Mengapa candidate tidak dibersihkan?"
```

Response:

```
decision:
    excluded

    EXCLUDED_PACKAGE

evidence:
    package is explicitly protected

permanence:
    permanent
```

72. Explain Deferred

Contoh:

```
decision:
    deferred

    REQUIRE_IDLE

evidence:
    device currently active

    scheduler may retry after idle event
```

73. Explain Rejected

Contoh:

```
decision:
    rejected

    UNKNOWN_TARGET_CLASS

execution:
    never attempted
```

74. Explain Eligible

Contoh:

```
decision:
    eligible

    APP_CACHE

    none
```

75. Policy Summary

Untuk Job:

```
candidates = 1000

policy results:

    eligible = 700
    excluded = 250
    deferred = 40
    rejected = 10
```

Summary ini harus tersedia tanpa mengirim seluruh Candidate list.

76. Policy Metrics

Metrics:

```
candidates_evaluated
candidates_eligible
candidates_excluded
candidates_deferred
candidates_rejected

rule_match_count
rule_evaluation_errors
policy_reload_success
policy_reload_failure
```

Metrics harus bounded dan tidak menyimpan sensitive path.

77. Policy Audit

Audit penting:

```
policy_loaded
policy_reloaded
policy_reload_rejected
policy_generation_changed
```

Per-candidate decision tidak harus selalu diaudit penuh karena dapat terlalu besar.

Namun security-relevant rejection dapat direkam secara bounded.

78. Sampling

Jika candidate sangat banyak:

```
50.000 decisions
```

audit dapat menggunakan:

```
summary + sampled details
```

Tidak boleh membuat audit storage tidak terbatas.

79. Testing

Minimal:

```
Unit
   ├── rule matching
   ├── precedence
   ├── defaults
   ├── unknown handling
   ├── runtime defer
   └── explain


Integration
   ├── config → policy
   ├── catalog → policy
   └── policy → planner


Property
   ├── deterministic
   ├── batch == individual
   └── no privilege expansion


Fuzz
   ├── policy expression
   ├── rule config
   ├── malformed enums
   └── excessive nesting
```

80. Property: Monotonic Safety

Jika policy menambahkan exclusion:

```
P1
   │
   └── add explicit exclusion X
          │
          ▼
         P2
```

Candidate X tidak boleh berubah:

```
Excluded → Eligible
```

Menambahkan restriction tidak boleh memperluas eligibility.

81. Property: Unknown Is Not Allow

Untuk metadata:

```
unknown
```

dan policy membutuhkan metadata tersebut:

```
result != Eligible
```

kecuali policy secara eksplisit mendefinisikan unknown sebagai eligible.

Default implementation:

```
unknown → conservative
```

82. Property: Protected Target

Jika target ditambahkan ke protected set:

```
target eligible under P1
```

maka:

```
target not eligible under P2
```

dengan:

```
P2 = P1 + protection
```

83. Property: Deterministic Rule Order

Untuk rule set yang sama:

```
same priority
same matcher
same action
```

hasil tidak boleh bergantung pada insertion order jika contract menyatakan ordering ditentukan oleh priority/rule ID.

84. Conflict Detection

Config validator harus mendeteksi conflict jika semantics mengharuskan conflict explicit.

Contoh:

```
same rule:
    Allow
    Reject
    same priority
```

Jika ambiguous:

```
INVALID_POLICY
```

Lebih baik config ditolak daripada menghasilkan keputusan bergantung pada ordering internal.

85. Rule Priority

Priority harus memiliki range bounded.

Contoh:

```
0..1000
```

Jangan menerima integer arbitrarily large jika tidak diperlukan.

86. Rule Identifier Validation

Rule ID harus:

→ bounded length
→ valid character set
→ unique

Duplicate rule ID:

```
invalid policy
```

87. Target ID Validation

Policy hanya boleh mereferensikan:

```
known TargetId
```

Unknown TargetId:

```
configuration error
```

Tidak boleh:

```
unknown target ID → arbitrary path fallback
```

88. Package ID Validation

Package identifiers harus mengikuti domain type.

Policy tidak menerima:

```
arbitrary string path
```

Jika package ID invalid:

```
config validation failure
```

89. User Scope

Policy dapat memiliki:

```
all users
selected users
```

Contoh:

```
users = [0,10]
```

Candidate user:

```
11
```

→ Excluded

Jika user state unknown:

```
Deferred / Excluded
```

sesuai contract.

90. Cross-user Isolation

Policy evaluation tidak boleh mencampurkan candidate:

```
user 0
```

dengan policy evidence:

```
user 10
```

Context harus selalu membawa UserId.

91. Runtime Policy Snapshot

Runtime state:

```
ScreenState
ThermalState
IdleState
UserActivity
StorageState
```

harus memiliki generation/snapshot identity jika diperlukan.

92. Runtime Change During Evaluation

Jika runtime berubah:

```
evaluation started:
    idle

evaluation ended:
    active
```

batch evaluation harus menggunakan snapshot yang sama.

Jangan:

```
Candidate 1 → idle
Candidate 2 → active
Candidate 3 → idle
```

tanpa definisi snapshot boundary.

93. Policy Evaluation Transaction

Untuk satu evaluation batch:

```
capture context
     │
     ▼
evaluate all
     │
     ▼
release context
```

Policy result terikat pada snapshot tersebut.

94. Planner Boundary

Policy menghasilkan:

```
PolicyApprovedCandidate
```

Planner mengubahnya menjadi:

```
PlannedOperation
```

Policy tidak menentukan:

```
exact syscall
FD
unlinkat
retry
execution ordering
```

Planner yang menentukan operation graph.

95. PolicyApprovedCandidate

Object ini harus immutable dan membawa:

```
candidate
policy_generation
decision
rule_id
reason_code
evidence
```

Planner tidak boleh membuat PolicyApprovedCandidate dari raw Candidate tanpa Policy Engine.

96. No Policy Bypass

Dilarang:

```
Candidate
   │
   └──► Planner
```

Yang benar:

```
Candidate
   │
   ▼
Safety
   │
   ▼
Policy
   │
   ▼
PolicyApprovedCandidate
   │
   ▼
Planner
```

97. No Planner Override

Planner tidak boleh berkata:

```
policy = Excluded
    │
    └── "but target is important"
            │
            ▼
         plan anyway
            ✕
```

Jika perlu policy berbeda:

```
create new policy generation
```

98. Policy Engine Failure

Jika evaluator internal error:

```
PolicyEvaluationError
```

Default:

```
no operation generated
```

Jangan:

```
evaluator failed
    │
    ▼
allow candidate
        ✕
```

99. Resource Exhaustion

Jika policy evaluation kehabisan:

```
memory
evaluation budget
recursion budget
```

hasil:

```
fail closed
```

Job dapat:

```
Failed
atau
Partial
```

sesuai lifecycle semantics.

105. Topik Berikutnya

46.md — Safety Policy Interaction, Decision Precedence, Protected Targets, Deny Rules, Policy Exceptions, dan Formal Eligibility Contract

Fokus berikutnya:

```
Candidate
   │
   ├──────────────► Safety
   │                   │
   │                   ▼
   │             SafetyDecision
   │
   └──────────────► Policy
                       │
                       ▼
                 PolicyDecision
                       │
                       ▼
                Decision Combiner
                       │
                       ├── Allow
                       ├── Deny
                       ├── Defer
                       └── Reject
                       │
                       ▼
              PolicyApprovedCandidate
```

Tujuannya adalah mendefinisikan secara formal bagaimana Safety dan Policy berinteraksi sehingga tidak pernah terjadi kondisi:

```
"Policy mengizinkan sesuatu
 yang Safety sebenarnya melarang."
```

Dan bagaimana exception, deny rule, protected target, serta konflik antar-keputusan diselesaikan secara deterministic dan fail-closed.
