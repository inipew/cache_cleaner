Baik. Sekarang kita masuk ke **filesystem engine**, dan menurut saya ini memang bagian paling kritis dari seluruh rewrite.

Repo sekarang sudah memilih pendekatan yang tepat secara konsep: fd-relative syscall seperti `openat`, `fstatat(..., SYMLINK_NOFOLLOW)`, `unlinkat`, serta pemeriksaan `st_dev`.  Dalam rewrite, saya justru akan menjadikan prinsip tersebut sebagai **boundary arsitektur yang tidak boleh ditembus modul lain**.

---

# 20. Filosofi Filesystem Engine

Targetnya bukan sekadar:

> "bisa menghapus file dengan cepat."

Targetnya:

> **"tidak mungkin operasi cleanup keluar dari boundary yang telah diotorisasi."**

Jadi filesystem engine harus memperlakukan path sebagai **input tidak terpercaya**.

Alur:

```text
String / PathBuf
       │
       ▼
  resolve target
       │
       ▼
 TrustedRoot
       │
       ▼
    DirFd
       │
       ▼
  relative lookup
       │
       ▼
   EntryHandle
       │
       ▼
    validate
       │
       ▼
 destructive syscall
```

Bukan:

```text
PathBuf
   ↓
canonicalize
   ↓
delete
```

---

# 21. `TrustedRoot`

Ini type paling fundamental.

Jangan biarkan semua module menggunakan:

```rust
PathBuf
```

untuk root yang dianggap aman.

Buat abstraction:

```rust
pub struct TrustedRoot {
    fd: OwnedFd,
    path: PathBuf,
    device: u64,
}
```

Secara konseptual dia berarti:

> FD ini sudah diverifikasi sebagai root yang boleh menjadi boundary cleanup.

Contohnya:

```rust
pub struct TrustedRoot {
    fd: DirectoryFd,
    identity: RootIdentity,
}
```

dengan:

```rust
pub struct RootIdentity {
    pub device: u64,
    pub inode: u64,
}
```

Kenapa inode juga?

Karena `st_dev` saja tidak cukup untuk mengidentifikasi directory tertentu.

---

# 22. Jangan Berikan Raw FD ke Semua Orang

Saya juga tidak ingin:

```rust
pub struct TrustedRoot {
    pub fd: RawFd,
}
```

karena module lain kemudian bisa melakukan sembarang syscall.

Lebih aman:

```rust
pub struct DirectoryFd {
    fd: OwnedFd,
}
```

dan API terbatas:

```rust
impl DirectoryFd {
    pub fn open_child(...) -> Result<DirectoryFd>;
    pub fn metadata(...) -> Result<Metadata>;
    pub fn read_entries(...) -> Result<...>;
}
```

Dengan demikian filesystem primitive dikontrol satu tempat.

---

# 23. Path Hanya untuk Discovery

Ini rule yang sangat penting:

```text
PathBuf
    = discovery / display
```

sedangkan:

```text
DirectoryFd
EntryHandle
TrustedRoot
```

dipakai untuk:

```text
authorization
validation
destructive operation
```

Contohnya scanner boleh menemukan:

```text
/data/user/0/com.foo/cache/images/a.webp
```

Tetapi executor tidak boleh menerima string itu lalu:

```rust
std::fs::remove_file(path)
```

Executor harus menerima object yang sudah mempunyai hubungan dengan trusted root.

---

# 24. `openat()` sebagai Boundary

Misalkan:

```text
/data/user/0/com.foo/cache
```

sudah menjadi:

```text
TrustedRoot
```

Kemudian ditemukan:

```text
images/a.webp
```

Jangan:

```rust
open("/data/user/0/com.foo/cache/images/a.webp")
```

Tetapi secara konsep:

```rust
root_fd
   │
   └── openat("images")
             │
             └── openat("a.webp")
```

Sehingga lookup tetap **relative terhadap trusted directory**.

Ini jauh lebih cocok untuk menghadapi path manipulation daripada membangun absolute path lalu mempercayainya.

---

# 25. Symlink

Ini harus menjadi hard safety rule.

Contoh:

```text
cache/
└── evil -> /data/important
```

Scanner melihat:

```text
evil
```

dan metadata harus diperoleh dengan mode **NOFOLLOW**.

Hasil:

```rust
FileType::Symlink
```

lalu:

```rust
Decision::Reject(RejectReason::Symlink)
```

Jangan melakukan:

```rust
canonicalize(evil)
```

kemudian berpikir:

> "Oh, ternyata menunjuk ke `/data/important`."

Untuk cleaner privileged, itu sudah terlalu terlambat secara desain.

---

# 26. Parent Symlink Juga Harus Dipikirkan

Bukan hanya leaf.

Misalnya:

```text
cache/
└── foo/
    └── bar
```

Pada waktu scan:

```text
foo = directory
```

Kemudian berubah:

```text
foo -> /data/important
```

Maka:

```text
cache/foo/bar
```

sudah tidak boleh dipercaya hanya karena hasil scan sebelumnya mengatakan `foo` adalah directory.

Karena itu traversal harus menggunakan FD-relative lookup sepanjang chain.

---

# 27. TOCTOU

Ini salah satu masalah terbesar.

TOCTOU:

```text
Time Of Check
      ↓
     check
      ↓
    delay
      ↓
Time Of Use
      ↓
   destructive
```

Contoh:

```text
T0:
foo = regular file

T1:
scanner:
"foo aman"

T2:
foo diganti

T3:
executor:
delete foo
```

Karena itu hasil scanner **bukan authorization permanen**.

Kita butuh:

```text
scan
 ↓
plan
 ↓
revalidate
 ↓
execute
```

Dan untuk operasi yang sangat sensitif:

```text
lookup
 ↓
validate
 ↓
delete
```

sedekat mungkin.

# 28. Candidate Jangan Menyimpan Path Saja

Saya lebih memilih:

```rust
pub struct Candidate {
    pub id: CandidateId,
    pub target: TargetId,

    pub relative_path: RelativePath,

    pub file_type: EntryType,
    pub size: u64,

    pub identity: EntryIdentity,
}
```

Dengan:

```rust
pub struct EntryIdentity {
    pub device: u64,
    pub inode: u64,
}
```

Kemudian saat revalidation:

```rust
current.device == candidate.identity.device
&&
current.inode == candidate.identity.inode
```

Jika berbeda:

```rust
Reject(RejectReason::ChangedSinceScan)
```

Ini bukan pengganti semua race protection, tetapi memberi kita **identity check** yang sangat berguna.

# 29. `RelativePath`

Saya juga ingin membuat type:

```rust
pub struct RelativePath {
    components: Vec<OsString>,
}
```

dan bukan membiarkan:

```rust
PathBuf
```

masuk langsung ke destructive layer.

Validasi harus menolak:

```text
/
../
../../
absolute path
empty component
```

Secara konseptual:

```rust
RelativePath::parse("images/foo.webp")
```

boleh.

Sedangkan:

```rust
RelativePath::parse("../../important")
```

harus gagal **sebelum filesystem lookup**.

---

# 30. Tapi `..` Tetap Jangan Dipercaya

Walaupun `RelativePath` sudah menolak `..`, kita tetap jangan menjadikan parser sebagai satu-satunya defense.

Security boundary harus bertingkat:

```text
Layer 1
RelativePath validation

Layer 2
openat relative traversal

Layer 3
NOFOLLOW

Layer 4
filesystem/device validation

Layer 5
identity revalidation

Layer 6
operation authorization
```

Prinsipnya:

> satu bug di satu layer tidak boleh otomatis berubah menjadi arbitrary deletion.

# 31. File Type Policy

Tidak semua filesystem object boleh dihapus.

Minimal:

```rust
pub enum EntryType {
    RegularFile,
    Directory,
    Symlink,
    Socket,
    Fifo,
    BlockDevice,
    CharDevice,
    Unknown,
}
```

Untuk cleanup biasa:

```text
RegularFile     → potentially allowed
Directory       → potentially allowed
Symlink         → reject
Socket          → reject
FIFO            → reject
BlockDevice     → reject
CharDevice      → reject
Unknown         → reject
```

Jangan pernah membuat:

```rust
if !directory {
    unlink();
}
```

karena itu berarti socket/device/FIFO juga masuk jalur destructive.

# 32. Directory Deletion Harus Terpisah

Saya akan memisahkan:


dari:


dan:

```rust

```

Tiga operasi berbeda.

### File

```text

```

### Empty directory


### Cache root


Tidak ada:

```text
rm -rf
```

di privileged engine.

# 38. "File Sudah Hilang" Bukan Selalu Failure

Cleanup bersifat **idempotent**.

Misalnya planner ingin:

```text
delete foo
```

Tetapi sebelum executor:

```text
another process already deleted foo
```

Hasil ideal:

```text
OperationResult::AlreadyGone
```

bukan daemon crash.

Contoh:

```rust
pub enum OperationResult {
    Removed { bytes: u64 },
    AlreadyGone,
    Skipped { reason: SkipReason },
    Failed(OperationError),
}
```

# 39. Partial Failure Harus Normal

Misalnya plan:

```text

```

hasil:

```text

```


Lebih baik:

```text
completed_with_errors
```

Summary:

```rust
pub struct CleanupSummary {

    pub removed: u64,
    pub already_gone: u64,
    pub skipped: u64,
    pub failed: u64,
    pub bytes_freed: u64,

```

Ini sangat cocok untuk daemon nyata.

## 49. Hal yang Saya Anggap "Non-Negotiable"

Untuk rewrite ini, saya akan menetapkan invariant berikut:

```text
1. Unknown target = deny

2. Symlink = deny

3. Absolute destructive path = deny

4. ".." traversal = deny

5. Cross-device target = deny

6. Protected target = deny

7. Scanner tidak boleh delete

8. Policy tidak boleh delete

9. Planner tidak boleh delete

10. Scheduler tidak boleh delete

11. Hanya executor yang destructive

12. Executor menerima operation, bukan arbitrary path

13. Destructive operation harus revalidate

14. Cache root dipertahankan

15. Deletion harus idempotent

16. Cancellation harus cooperative

17. Budget harus membatasi pekerjaan

18. Partial failure harus didukung

19. Config tidak boleh bypass hard safety

20. Tidak ada shell `rm -rf` untuk privileged cleanup
```

Ini akan menjadi **kontrak arsitektur** project baru.

Dan ini menurut saya lebih penting daripada menentukan crate apa yang dipakai.

---

### Berikutnya

Setelah filesystem engine ini, kita sudah punya fondasi untuk masuk ke **Safety Engine**. Di sana kita bisa merancang lebih dalam:

```text
Candidate
    ↓
BoundaryValidator
    ↓
TargetValidator
    ↓
IdentityValidator
    ↓
FilesystemValidator
    ↓
RuntimeValidator
    ↓
RiskEvaluator
    ↓
Decision
```

termasuk **threat model untuk rooted Android**, multi-user/FBE, `/data/user`, device boundary, mount replacement, race saat directory diganti, dan bagaimana membuat `SafetyDecision` sehingga **config `cache_cleaner` tidak pernah bisa mengubah hard-deny menjadi allow**.
