65.md — Configuration Architecture, Raw Config Validation, Effective Configuration, Generation Binding, Reload Semantics, Defaults, Bounds, Compatibility, Persistence, and Safe Configuration Contract

Tujuan

Dokumen ini mendefinisikan bagaimana configuration diperlakukan sebagai input yang tidak dipercaya sampai melewati validation, normalization, dan construction menjadi immutable EffectiveConfig.

Configuration bukan sekadar file yang dibaca daemon. Configuration menentukan policy, scheduler, resource budget, target enablement, safety constraints, maintenance capability, dan operational behavior. Karena itu perubahan configuration dapat mengubah security-relevant behavior.

Flow utama:

RawConfig
    │
    ▼
Parse
    │
    ▼
Schema Validation
    │
    ▼
Semantic Validation
    │
    ▼
Normalization
    │
    ▼
EffectiveConfig
    │
    ▼
ConfigGeneration
    │
    ├── Scheduler
    ├── Catalog View
    ├── Policy
    ├── Planner
    ├── Authorization
    └── Runtime

1. Configuration Is Untrusted Input

Configuration harus diperlakukan sebagai untrusted input walaupun file dibuat oleh administrator.

Alasannya:

- file dapat rusak
- schema dapat berubah
- nilai dapat terlalu besar
- nilai dapat saling bertentangan
- file dapat diedit ketika daemon berjalan
- deployment dapat membawa configuration lama
- permission file dapat salah

Invalid configuration tidak boleh menghasilkan permissive behavior.

2. Parse != Validate

Berhasil diparse tidak berarti valid.

Contoh:

"max_workers = -1"

mungkin dapat diparse sebagai integer tetapi tidak valid secara semantic.

3. Validation Stages

Gunakan minimal:

Parse
→ StructuralValidation
→ TypeValidation
→ RangeValidation
→ CrossFieldValidation
→ SecurityValidation
→ Normalization
→ EffectiveConfig

4. Structural Validation

Pastikan:

- section yang required tersedia
- field mempunyai type benar
- collection memiliki bentuk yang benar
- tidak ada nested structure yang melanggar schema

5. Range Validation

Semua numeric configuration harus mempunyai bound.

Contoh:

- max_workers
- max_active_cleanup
- max_operations
- max_bytes
- timeout
- retry count
- queue size
- scan depth
- rule count

Tidak boleh ada numeric field yang secara praktis dapat menghasilkan resource exhaustion.

6. Cross-field Validation

Validasi hubungan antar field.

Contoh:

max_active_cleanup <= max_workers

retry_max_attempts > 0

resume threshold tidak boleh lebih rendah dari stop threshold jika semantics membutuhkan hysteresis.

7. Security Validation

Configuration tidak boleh digunakan untuk menonaktifkan platform invariants.

Dilarang:

- disable final safety gate
- allow symlink traversal secara global
- allow arbitrary root
- disable identity validation
- enable arbitrary shell command
- allow arbitrary ioctl
- bypass authorization
- mengubah platform-protected target menjadi allowed

8. EffectiveConfig

Raw configuration tidak boleh digunakan langsung oleh runtime.

EffectiveConfig adalah hasil configuration yang sudah:

- validated
- normalized
- bounded
- defaulted
- immutable
- generation-bound

9. Immutable Configuration

Untuk satu Job:

Job J1
  │
  └── EffectiveConfig G10

Config reload menjadi G11 tidak mengubah G10.

Job J1 tetap menggunakan G10 sampai terminal.

10. ConfigGeneration

Setiap EffectiveConfig memiliki ConfigGeneration typed.

Generation harus monotonically increasing dalam lifecycle persistence yang sama.

11. Generation Tidak Sama Dengan Timestamp

Timestamp berguna untuk audit.

Generation digunakan untuk consistency.

Jangan menentukan stale hanya dengan membandingkan timestamp file configuration.

12. Configuration Reload

Reload harus atomic.

CurrentConfig
    │
    ▼
Read new file
    │
    ▼
Parse
    │
    ▼
Validate
    │
    ▼
Build EffectiveConfig
    │
    ▼
Publish new generation

Jika salah satu tahap gagal:

CurrentConfig tetap aktif.

13. Failed Reload

Jangan mengganti configuration valid dengan:

- empty configuration
- partially parsed configuration
- default-only configuration
- permissive configuration

14. Reload Tidak Memodifikasi Active Jobs

Job yang sudah menggunakan G10 tidak dipindahkan ke G11 secara in-place.

Jika perubahan configuration memengaruhi operation yang belum dieksekusi, Scheduler dapat menandai job stale sesuai policy.

15. Safe Reload Categories

Perubahan configuration dapat diklasifikasikan:

- PresentationOnly
- RuntimeOnly
- PolicyAffecting
- TargetAffecting
- SafetySensitive
- ResourceAffecting

16. PresentationOnly

Contoh:

- log format
- human-readable output preference

Dapat diterapkan tanpa invalidating cleanup plan jika benar-benar tidak memengaruhi semantics.

17. RuntimeOnly

Contoh:

- telemetry interval
- diagnostic verbosity

Perubahan dapat berlaku pada runtime berikutnya tanpa mengubah authority yang sudah diberikan.

18. PolicyAffecting

Contoh:

- minimum age
- enabled target class
- excluded package

Job lama yang belum mutation dapat menjadi stale jika policy decision akan berbeda.

19. TargetAffecting

Contoh:

- target enablement
- target mapping
- storage scope

Perubahan harus memicu catalog/effective target refresh.

20. SafetySensitive

Contoh:

- protected paths
- symlink behavior
- mount boundary policy
- safety limits

Perubahan safety-sensitive harus sangat konservatif.

21. ResourceAffecting

Contoh:

- worker count
- queue size
- metadata budget
- execution timeout

Perubahan dapat mempersempit runtime capacity tetapi tidak boleh memperbesar authority dari AuthorizedPlan secara in-place.

22. Configuration Cannot Expand Existing Authorization

Jika AuthorizedPlan dibuat dengan:

max_bytes = 1 GiB

Reload config menjadi:

max_bytes = 5 GiB

AuthorizedPlan lama tetap:

max_bytes = 1 GiB

Untuk menggunakan 5 GiB harus dibuat plan baru dan authorization baru.

23. Configuration Can Narrow Runtime Capacity

Runtime boleh menerima global safety limit yang lebih kecil dari plan.

EffectiveRuntimeLimit = min(plan_limit, current_global_limit)

Tetapi perubahan tersebut tidak boleh mengubah operation set menjadi lebih luas.

24. Defaults

Default harus conservative.

Contoh:

unknown target = disabled
unknown capability = unavailable
unknown protection = protected/unavailable
missing safety option = safe default
unbounded resource = invalid

25. No Implicit Unlimited

Nilai:

0
null
missing

tidak boleh otomatis berarti unlimited kecuali schema secara eksplisit mendefinisikan semantics tersebut.

26. Optional Field

Optional field harus memiliki semantics yang jelas:

- absent = default
- absent = disabled
- absent = unsupported

Jangan membuat satu field mempunyai arti berbeda di berbagai module.

27. Boolean Safety Options

Boolean seperti:

allow_symlink
force_cleanup
skip_verification

berisiko tinggi dan sebaiknya tidak tersedia jika semantics dapat dimodelkan sebagai typed enum.

28. Prefer Typed Enums

Contoh:

SafetyMode
VerificationLevel
MisfirePolicy
UnknownHandling
MaintenanceMode

lebih aman daripada:

mode = "anything"

29. String Configuration

String configuration harus dibatasi panjangnya.

Contoh:

- package name
- target name
- log message template
- socket path
- profile name

30. Path Configuration

Path dalam configuration tidak otomatis menjadi TrustedRoot.

Configuration hanya dapat memilih target identifier yang sudah dikenal oleh TargetCatalog atau platform adapter.

31. Arbitrary Root Configuration

Dilarang:

cleanup_root = "/"

atau:

cleanup_root = "/data"

sebagai authority langsung.

Jika custom target memang diperlukan, target harus melalui TargetCatalog registration dan Safety validation.

32. Package Lists

Whitelist/denylist package harus:

- valid package name
- bounded count
- bounded string length
- normalized
- deduplicated

33. Package List Cannot Grant Authority

Whitelist hanya dapat mempersempit policy.

Tidak boleh membuat package list sebagai mekanisme untuk membuka protected target.

34. Protected Targets

Platform-invariant protected targets tidak boleh dapat dihapus melalui configuration.

Configuration dapat menambah protection, bukan menghapus platform protection.

35. Rule Configuration

Rule harus memiliki:

- stable rule ID
- bounded priority
- bounded expression depth
- bounded rule count
- typed action

36. Rule Conflicts

Configuration validator harus mendeteksi conflict yang dapat menyebabkan ambiguous decision.

Contoh:

allow protected target

dan:

protected invariant

Hasil tetap protection.

37. Explicit Precedence

Precedence harus didefinisikan oleh schema/domain, bukan urutan field dalam file.

38. Configuration Ordering

Jangan menganggap:

rule pertama = lebih penting

kecuali schema secara eksplisit mendefinisikan priority.

39. Normalization

Normalization dapat meliputi:

- sorting
- deduplication
- canonical representation
- default expansion
- enum conversion

40. Normalization Must Preserve Semantics

Normalization tidak boleh mengubah allow menjadi deny atau sebaliknya kecuali itu memang hasil semantic validation.

41. Deterministic EffectiveConfig

Input configuration yang sama harus menghasilkan EffectiveConfig semantics yang sama.

42. Config Fingerprint

EffectiveConfig dapat memiliki fingerprint untuk:

- audit
- stale detection
- debugging
- result correlation

Fingerprint harus deterministic dan tidak memasukkan ephemeral data secara tidak perlu.

43. Secret Configuration

Jika configuration memiliki secret:

- jangan log raw value
- jangan memasukkannya ke explain output
- jangan memasukkannya ke audit
- jangan memasukkannya ke fingerprint secara plaintext

44. Prefer No Secrets

Daemon cleanup sebaiknya tidak membutuhkan credential untuk fungsi inti.

45. Configuration File Permissions

Configuration yang security-sensitive harus memiliki permission dan ownership yang sesuai dengan deployment model.

46. Symlinked Configuration

Daemon harus mempunyai policy jelas terhadap configuration file yang merupakan symlink.

Untuk security-sensitive deployment, lebih aman menolak symlink configuration atau memverifikasi target dan identity sebelum digunakan.

47. Atomic Configuration Replacement

Deployment sebaiknya menggunakan:

write temporary file
→ fsync
→ atomic rename

daripada menulis active file secara parsial.

48. Partial Read

Jika daemon membaca file saat sedang ditulis:

hasil parse dapat gagal.

Current valid configuration harus tetap dipakai.

49. Configuration Locking

Daemon tidak boleh membutuhkan lock global yang panjang hanya untuk membaca configuration.

Load lalu validate secara local, kemudian atomic publish.

50. Configuration Store

Jika configuration dipersist di database, domain tetap menggunakan EffectiveConfig dan ConfigStore abstraction.

51. File vs Database

File cocok untuk:

- administrator editing
- deployment
- version control

Database cocok untuk:

- runtime overrides
- atomic transactional updates
- generated state

Keduanya tidak boleh menghasilkan dua authoritative configuration source tanpa precedence yang jelas.

52. Single Configuration Authority

Harus ada satu EffectiveConfig builder.

Jangan membuat:

CLI config parser
Scheduler config parser
Engine config parser

yang masing-masing mempunyai semantics berbeda.

53. CLI Configuration

CLI hanya menghasilkan request/override DTO.

CLI tidak boleh memodifikasi global configuration object secara langsung.

54. Configuration Override

Override harus:

- typed
- bounded
- validated
- scoped
- auditable

55. Temporary Override

Jika CLI meminta:

--max-operations 100

itu harus menjadi job-scoped override jika semantics-nya memang hanya untuk job tersebut.

Jangan mengubah persistent global config secara diam-diam.

56. Persistent Change

Perubahan persistent configuration harus melalui command khusus dengan validation dan audit.

57. Configuration Generation After Persistent Change

Setelah commit:

old config
→ new config
→ new ConfigGeneration

58. Crash During Config Update

Jika crash sebelum commit:

old config tetap valid.

Jika crash setelah commit:

new config dapat dipublish saat restart.

59. Atomic Config Commit

Configuration update dan ConfigGeneration harus memiliki consistency boundary yang sama.

60. ConfigGeneration Gap

Jika persisted generation tidak konsisten dengan configuration payload:

RecoveryRequired.

Jangan menebak generation.

61. Schema Version

Configuration schema harus memiliki:

schema_version

62. Schema Version != ConfigGeneration

Schema version menunjukkan bentuk data.

ConfigGeneration menunjukkan revision semantics.

63. Schema Migration

Migration harus:

- deterministic
- bounded
- validated
- atomic bila memungkinkan
- tidak memperluas authority

64. Unsupported Schema

Jika schema terlalu baru:

configuration tidak boleh dipakai.

65. Older Schema

Schema lama dapat dimigrasikan hanya jika migration path eksplisit tersedia.

66. Migration Safety

Migration tidak boleh menghasilkan configuration permissive sebagai fallback.

67. Unknown Field

Unknown field dapat:

- ditolak
- diabaikan jika schema explicitly forward-compatible

Tetapi behavior harus konsisten dan terdokumentasi.

68. Unknown Enum

Unknown enum value harus menyebabkan validation failure atau explicit compatibility mode.

Jangan mengubah unknown menjadi Allow.

69. Numeric Overflow

Parsing numeric field harus checked.

70. Duration Overflow

Konversi duration harus menggunakan checked arithmetic.

71. Byte Size Parsing

Jika configuration mendukung:

10MiB
1GiB

parser harus canonical dan bounded.

72. Negative Duration

Tidak valid kecuali schema secara eksplisit mendefinisikan semantics tertentu.

73. Zero Duration

Harus mempunyai semantics jelas. Jangan otomatis menjadi busy-loop.

74. Minimum Interval

Scheduler interval harus mempunyai minimum bound untuk mencegah event storm.

75. Maximum Interval

Maximum juga perlu bound agar periodic maintenance tidak menjadi effectively unbounded delay jika policy mengharapkan reconciliation.

76. Retry Bounds

Retry count dan backoff harus bounded.

77. Queue Bounds

Queue capacity harus bounded secara hard limit.

78. Worker Bounds

Worker count harus mempunyai hard maximum.

79. Memory Bounds

Planner/scanner memory budget harus mempunyai hard ceiling.

80. Path Length Bounds

Configured path-like fields harus dibatasi panjangnya.

81. Expression Bounds

Rule expression depth dan node count harus bounded.

82. Configuration Health

Runtime dapat memiliki:

ConfigHealth

contoh:

Valid
Degraded
Invalid
RecoveryRequired

83. Invalid Config State

Jika active config menjadi invalid akibat external replacement:

daemon tidak boleh mengubah active EffectiveConfig menjadi invalid object.

84. Active Config Snapshot

Runtime memegang immutable EffectiveConfig.

File di disk bukan active authority sampai berhasil divalidasi dan dipublish.

85. Reload Race

Dua reload request dapat datang bersamaan.

Gunakan serialization atau generation compare-and-swap semantics.

86. Stale Reload

Jika reload A dan B berjalan paralel:

hasil publish harus mengikuti ordering yang explicit.

Jangan membiarkan config lama overwrite config baru hanya karena validation A selesai lebih lambat.

87. Recommended Reload Sequence

read
→ validate
→ acquire publish lock
→ compare source revision
→ assign new generation
→ atomic publish

88. Configuration Events

ConfigChanged adalah trigger untuk:

- rebuild EffectiveConfig
- invalidate affected state
- wake Scheduler

89. Config Event Is Not Authority

Event hanya memberi tahu bahwa configuration mungkin berubah.

Truth berasal dari validated configuration.

90. Job Config Binding

Setiap Job harus menyimpan ConfigGeneration yang digunakan.

91. Plan Config Binding

Plan harus menyimpan ConfigGeneration.

92. Authorization Config Binding

AuthorizedPlan harus menyimpan ConfigGeneration.

93. Execution Check

Executor/Final Safety Gate memastikan configuration generation masih compatible dengan operation contract.

94. Policy-only Change

Jika hanya policy berubah, job lama dapat menjadi stale sebelum mutation.

95. Runtime-only Change

Tidak semua config change harus invalidate plan.

Classification harus eksplisit.

96. Conservative Unknown

Jika dampak configuration change tidak diketahui:

anggap affected dan invalidate destructive work.

97. Explain Configuration

Explain harus dapat menunjukkan:

- ConfigGeneration
- policy profile
- relevant rule IDs
- configuration health

tanpa menampilkan secret.

98. Audit Configuration

Audit dapat mencatat:

- old generation
- new generation
- actor/source
- change class
- result

99. Configuration Diff

Configuration diff untuk audit harus bounded dan sanitized.

100. No Secret Diff

Secret value tidak boleh masuk diff.

101. Configuration Persistence

Persistent config harus memiliki backup/recovery strategy bila deployment membutuhkannya.

102. Backup Is Not Authority

Backup tidak boleh digunakan sebagai active configuration tanpa validation.

103. Startup

Startup sequence:

load
→ parse
→ validate
→ normalize
→ publish EffectiveConfig
→ create PlatformSnapshot
→ build Catalog
→ start Scheduler

104. Startup Failure

Jika no valid configuration tersedia:

- daemon dapat start dalam diagnostic/recovery mode
- destructive execution harus blocked

105. No Permissive Startup

Dilarang:

config missing
→ use unsafe defaults
→ cleanup

106. Read-only Diagnostic Mode

Jika configuration invalid, status/diagnostics boleh tetap tersedia dengan capability terbatas.

107. Configuration Testability

EffectiveConfig harus dapat dibuat dari in-memory test fixture tanpa filesystem dependency.

108. Property Tests

Test invariants seperti:

- invalid range always rejected
- unknown enum never becomes allow
- normalization deterministic
- generation monotonic
- reload failure preserves old config

109. Fuzzing

Parser dan validator harus cocok untuk fuzzing karena configuration adalah input boundary.

110. Fuzz Targets

- parser
- duration parser
- size parser
- rule expression parser
- package list parser
- migration decoder

111. Final Configuration Invariants

1. RawConfig tidak pernah menjadi runtime authority.
2. EffectiveConfig immutable.
3. ConfigGeneration typed dan monotonic.
4. Reload atomic.
5. Invalid reload mempertahankan config lama.
6. Unknown tidak menjadi permissive.
7. Configuration tidak dapat menghapus platform invariants.
8. Configuration tidak dapat memperluas existing authorization.
9. Semua resource dan expression bounded.
10. Job/Plan/Authorization terikat pada configuration generation yang tepat.
