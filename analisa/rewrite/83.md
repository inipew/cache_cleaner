# 83.md — Migration Plan, Incremental Cutover, Compatibility Layer, Data Migration, Rollback, Feature Flags, Observability, and Production Rollout Contract

## Tujuan

Rewrite tidak boleh dilakukan sebagai big-bang replacement. Sistem saat ini sudah memiliki daemon, config, RuleEngine, CleanEngine, IPC, scheduler/runtime state, dan platform-specific logic. Migrasi harus memungkinkan perubahan bertahap dengan safety invariant tetap berlaku di setiap tahap.

Target:

```text
Legacy
  │
  ├── compatibility adapters
  │
  ▼
Typed domain
  │
  ▼
New pipeline
  │
  ▼
Shadow / compare
  │
  ▼
Controlled cutover
  │
  ▼
Legacy removal
```

## 1. No Big Bang

Jangan mengganti seluruh daemon sekaligus.

Setiap tahap harus compile, test, observable, dan rollbackable.

## 2. Safety First

Safety architecture harus masuk lebih awal daripada optimization.

Tidak boleh menunggu seluruh rewrite selesai untuk memperbaiki mutation boundary.

## 3. Migration Order

Urutan utama:

1. typed domain primitives
2. configuration
3. target catalog
4. candidate scanner
5. safety gate
6. policy
7. planner
8. authorization
9. durable lifecycle
10. executor
11. verifier/reconciliation
12. scheduler/resources
13. IPC/CLI
14. Android adapter
15. legacy removal

## 4. Preserve Existing Behavior

Pada tahap awal, behavior yang aman dan sudah digunakan harus dipertahankan kecuali ada explicit safety defect.

## 5. Safety Defect Exception

Jika legacy behavior melanggar safety invariant, migration harus memilih safe refusal daripada backward compatibility.

## 6. Compatibility Layer

Legacy API dapat dibungkus oleh typed domain adapters.

Contoh:

```rust
LegacyConfig -> RawConfig -> EffectiveConfig
LegacyRule -> Target/Candidate discovery
LegacyResult -> JobResult
```

## 7. No Dual Mutation Engines

Selama migration, hanya satu executor boleh memiliki mutation authority.

Legacy cleaner dan new executor tidak boleh melakukan mutation terhadap job yang sama.

## 8. Mutation Boundary Early

Bahkan sebelum seluruh planner selesai, destructive filesystem operation harus diarahkan melalui satu safety-aware boundary.

## 9. Typed IDs First

Ganti string IDs secara bertahap:

- JobId
- OperationId
- AttemptId
- TargetId
- PlanId
- AuthorizationId
- ConfigGeneration
- CatalogGeneration

## 10. Primitive Containment

Legacy primitive fields boleh hidup sementara di adapter, tetapi tidak boleh menyebar ke domain baru.

## 11. Config Migration

Implementasikan:

`RawConfig -> validate -> normalize -> EffectiveConfig`

sebelum policy/planner bergantung pada config.

## 12. Config Generation

Setiap EffectiveConfig mendapatkan ConfigGeneration.

## 13. Reload Compatibility

Legacy reload API tetap dapat dipertahankan sebagai facade yang menghasilkan EffectiveConfig baru.

## 14. Invalid Reload

Invalid reload tidak boleh mengganti active configuration.

## 15. Target Catalog Introduction

Pertama implementasikan TargetCatalog dalam read-only/shadow mode.

## 16. Legacy Rule Comparison

Bandingkan target yang ditemukan legacy RuleEngine dengan TargetCatalog.

Difference harus dicatat.

## 17. Shadow Discovery

Shadow mode tidak boleh melakukan mutation.

## 18. Target Diff

Classify differences:

- expected improvement
- missing target
- extra target
- identity mismatch
- classification mismatch
- unsupported legacy target

## 19. Catalog Cutover

Setelah diff acceptable, TargetCatalog menjadi authoritative source.

## 20. Legacy Rule Removal

Legacy rules tidak boleh menjadi independent safety authority setelah cutover.

## 21. Candidate Scanner

Migrasikan enumeration dari CleanEngine/RuleEngine ke CandidateScanner.

## 22. Candidate Compatibility

Legacy cleaner input dapat dibuat dari Candidate selama migration.

## 23. Candidate Accounting

Pastikan old/new scanner menghasilkan accounting semantics yang comparable.

## 24. Safety Gate

Implementasikan SafetyGate sebelum executor baru.

## 25. Safety Shadow

Legacy operation dapat dievaluasi oleh new SafetyGate tanpa mutation.

## 26. Safety Deny Diff

Jika new safety menolak operation yang legacy akan lakukan, default migration behavior adalah new safety wins.

## 27. Safety Metrics

Catat reason code untuk deny/stale/identity mismatch agar false positives dapat dianalisis.

## 28. Policy Migration

Pindahkan rule decision ke PolicyEngine typed.

## 29. Policy Equivalence

Buat compatibility test untuk keputusan legacy vs new policy.

## 30. Policy Divergence

Perbedaan policy harus explicit, versioned, dan auditable.

## 31. Planner Introduction

Planner menjadi satu-satunya pembuat immutable Plan.

## 32. Deterministic Plan

Plan harus dapat dibandingkan/hash sehingga shadow execution dapat diverifikasi.

## 33. Authorization Introduction

Authorization dibuat setelah Plan final.

## 34. No Preplanned Authority

Jangan memberi broad authorization sebelum planner selesai.

## 35. Executor Cutover

Executor baru mengambil mutation authority hanya setelah SafetyGate dan Authorization aktif.

## 36. Legacy Executor Disable

Legacy mutation path harus dinonaktifkan untuk new jobs.

## 37. Verifier

Setiap mutation harus mendapatkan postcondition verification.

## 38. Unknown Outcome

Jika old executor tidak dapat memberikan mutation certainty, migration wrapper harus memetakan hasil ke Unknown dan memicu reconciliation.

## 39. Durable Job Store

Introduce persistence sebelum jobs perlu survive restart.

## 40. Persistence Backfill

Jika legacy runtime state tidak cukup untuk reconstruct active jobs, jangan mengarang historical state.

Mark sebagai `RecoveryRequired`/equivalent.

## 41. Schema Version

Persistence schema mempunyai explicit version.

## 42. Transactional Migration

Database migrations harus atomic bila backend memungkinkan.

## 43. Backup

Sebelum destructive schema migration, buat recoverable backup sesuai platform/storage capability.

## 44. Rollback Schema

Setiap schema migration harus mempunyai compatibility/rollback strategy atau explicit irreversible declaration.

## 45. Scheduler Migration

Legacy trigger logic dapat mengirim event ke new Scheduler.

## 46. Single Scheduler Authority

Tidak boleh ada dua scheduler yang sama-sama submit destructive jobs.

## 47. Resource Manager

Introduce resource reservations sebelum concurrency limit dipindahkan ke new workers.

## 48. Worker Migration

Worker baru menerima durable Job/Attempt, bukan ad-hoc closure state.

## 49. Worker Ownership

Satu operation hanya mempunyai satu active owner/lease sesuai resource contract.

## 50. IPC Migration

Pertahankan protocol facade sementara CLI/client lama masih digunakan.

## 51. Versioned IPC

Protocol baru harus versioned.

## 52. Capability Mapping

Legacy IPC command harus dipetakan ke typed command dan capability check.

## 53. CLI Migration

CLI lama menjadi adapter ke new IPC contract.

## 54. CLI No Direct Mutation

CLI tidak boleh mempertahankan direct filesystem mutation path setelah cutover.

## 55. Android Adapter Migration

Pindahkan Android/OEM path discovery dan platform assumptions dari generic engine ke adapter.

## 56. Android Shadow Mode

Bandingkan target discovery baru dengan legacy target lists pada supported devices.

## 57. OEM Rollout

Rollout Android adapter berdasarkan compatibility classes, bukan hanya one-device success.

## 58. Feature Flags

Feature flags harus typed dan bounded.

## 59. Safety Feature Flag

Tidak boleh ada flag yang mematikan final SafetyGate di production.

## 60. Force Flag

`force` dapat mempengaruhi user intent/policy hanya jika domain mengizinkan, tetapi tidak boleh bypass identity/safety invariants.

## 61. Rollout Levels

Recommended:

1. disabled
2. observe
3. shadow
4. dry-run
5. limited mutation
6. normal

## 62. Dry Run

Dry-run harus menjalankan discovery, policy, planner, authorization simulation, dan safety checks tanpa mutation.

## 63. Limited Mutation

Limited mode harus memiliki hard upper bounds untuk targets, operations, bytes, dan runtime.

## 64. Canary

Canary deployment harus dapat diidentifikasi dan dirollback secara jelas.

## 65. Kill Switch

Production harus mempunyai administrative kill switch yang menghentikan admission of new destructive jobs.

Kill switch sendiri tidak boleh meninggalkan in-flight operation tanpa recovery semantics.

## 66. Drain Mode

Shutdown/disable mode sebaiknya memiliki drain behavior:

- stop admission
- allow safe completion
- cancel/recover according to operation semantics

## 67. Observability

Migration membutuhkan structured metrics/logs/audit.

## 68. Migration Metrics

Minimal:

- jobs by pipeline version
- safety denials
- target discovery differences
- policy differences
- plan differences
- authorization failures
- executor failures
- unknown outcomes
- reconciliation count
- recovery-required jobs
- resource waits
- IPC compatibility errors

## 69. Version Tagging

Job/Plan/Authorization/Result harus menyimpan implementation/pipeline version yang relevan.

## 70. Reproducibility

Bug report harus dapat dikaitkan dengan:

- config generation
- catalog generation
- plan identity/hash
- target identity
- pipeline version

## 71. Audit

Migration decision harus masuk audit trail.

## 72. Redaction

Audit/log tidak boleh menyimpan secrets atau sensitive data tanpa explicit requirement.

## 73. Error Taxonomy

Selama migration, error mapping harus preserve semantic distinction.

Jangan collapse semua legacy errors menjadi generic failure.

## 74. Unknown Mapping

Legacy "timeout", "process killed", atau "connection lost" tidak otomatis berarti mutation failed.

Map sesuai evidence.

## 75. Retry Migration

Legacy retry behavior harus dinonaktifkan jika tidak sesuai idempotency contract baru.

## 76. Duplicate Job Migration

Legacy duplicate submissions harus dipetakan ke idempotency key/domain identity baru.

## 77. Runtime State Migration

`DaemonRuntimeState` lama harus dipisahkan dari durable Job state.

Runtime state boleh hilang saat restart; durable job state tidak.

## 78. In-memory State

`is_cleaning` boolean tidak boleh menjadi source of truth untuk job ownership setelah rewrite.

## 79. Cancellation Migration

Legacy cancellation harus diterjemahkan ke typed cancellation intent.

## 80. Timeout Migration

Legacy timeout harus dipetakan ke operation/job timeout semantics baru.

## 81. Result Migration

Legacy `CleanResult` harus diadaptasi menjadi immutable `JobResult`/operation result.

## 82. Accounting Migration

Legacy freed bytes harus diverifikasi dan tidak boleh langsung dipercaya sebagai verified accounting.

## 83. UI Compatibility

UI/CLI yang bergantung pada old result fields harus menggunakan versioned adapter.

## 84. Data Retention

Durable job/audit retention harus mempunyai bounded policy.

## 85. Cleanup Retention

Retention cleanup sendiri harus aman dan tidak menghapus active/recovery-critical records.

## 86. Persistence Health

Jika persistence unavailable, destructive admission harus fail-safe atau masuk recovery/degraded mode sesuai contract.

## 87. Startup Modes

Startup dapat mempunyai:

- Normal
- Degraded
- RecoveryRequired
- SafeMode

## 88. SafeMode

SafeMode tidak boleh menjalankan destructive mutation.

## 89. Migration Failure

Jika migration step gagal, current known-safe version tetap aktif jika memungkinkan.

## 90. Rollback Boundary

Rollback harus berhenti pada mutation authority boundary yang aman.

## 91. Never Roll Back Blindly

Jangan downgrade code sambil membiarkan persisted jobs diproses oleh incompatible executor.

## 92. Job Version Compatibility

Executor harus memvalidasi bahwa Job/Plan/Authorization version kompatibel.

## 93. Schema/Code Compatibility

Code version dan persistence schema compatibility harus diuji sebagai matrix.

## 94. Recovery After Rollback

Jika rollback code dilakukan setelah job state berubah, startup harus melakukan compatibility check dan recovery classification.

## 95. Old Data

Legacy data yang tidak dapat dimigrasikan secara aman harus retained/quarantined, bukan silently discarded.

## 96. Quarantine

Invalid/corrupt records dapat dipindahkan ke quarantine store untuk diagnosis.

## 97. No Silent Data Loss

Migration tidak boleh menghapus user/job/audit data tanpa explicit retention policy.

## 98. Performance Migration

Bandingkan legacy vs new:

- scan latency
- memory
- syscall count
- database writes
- CPU
- battery impact
- cleanup throughput

## 99. Performance Guardrail

Safety/consistency improvements tidak boleh dioptimalkan away hanya untuk mengejar legacy throughput.

## 100. Android Battery

Scheduler/worker migration harus diuji terhadap wakeups dan background activity.

## 101. Event Storm

Pastikan migration tidak memperkenalkan duplicate listeners/duplicate schedulers.

## 102. File Descriptor Audit

Setiap migration phase harus diperiksa untuk FD leaks.

## 103. Thread/Task Audit

Pastikan old worker/task tidak hidup bersamaan dengan new worker tanpa explicit ownership.

## 104. Lock Audit

Migrasi lock tidak boleh menciptakan lock inversion antara legacy dan new components.

## 105. Memory Audit

Old/new caches atau catalogs tidak boleh keduanya menahan full dataset tanpa bounded reason.

## 106. Incremental PRs

Recommended implementation dalam PR kecil per architectural boundary.

Contoh:

- PR 1 domain IDs
- PR 2 config
- PR 3 catalog
- PR 4 scanner
- PR 5 safety
- PR 6 policy/planner
- PR 7 authorization
- PR 8 executor/verifier
- PR 9 persistence
- PR 10 scheduler/resources
- PR 11 IPC/CLI
- PR 12 Android adapter
- PR 13 legacy removal

## 107. Commit Discipline

Setiap migration step harus mempunyai commit yang buildable/testable.

## 108. Review Discipline

Safety boundary changes membutuhkan review khusus.

## 109. No Mixed Refactor

Jangan mencampur large formatting changes dengan safety/domain migration sehingga semantic diff sulit diaudit.

## 110. Documentation Sync

Setiap architectural cutover harus memperbarui rewrite docs dan implementation notes.

## 111. Deprecation

Legacy APIs diberi deprecation period yang jelas.

## 112. Removal Criteria

Legacy code boleh dihapus setelah:

- new path authoritative
- compatibility metrics acceptable
- tests cover replacement
- rollback strategy no longer depends on legacy path
- no callers remain

## 113. Search-Based Verification

CI/review dapat mencari penggunaan legacy APIs untuk memastikan migration completion.

## 114. Dead Code

Setelah cutover, dead compatibility code harus dihapus agar tidak menjadi second authority di masa depan.

## 115. Security Review

Setiap cutover destructive boundary harus mendapat security regression review.

## 116. Threat Model Update

Threat model harus diperbarui setelah architecture berubah.

## 117. Incident Rollback

Incident response harus mempunyai procedure:

1. stop admission
2. preserve evidence
3. classify active jobs
4. disable unsafe path
5. reconcile unknown operations
6. rollback/patch
7. resume only after validation

## 118. Recovery-First Rollback

Rollback tidak boleh mengorbankan reconciliation hanya untuk mempercepat restoration.

## 119. Migration Checklist

Setiap phase wajib menjawab:

- Apa authority baru?
- Apa authority lama?
- Apakah keduanya bisa aktif bersamaan?
- Bagaimana mencegah double mutation?
- Bagaimana stale state ditangani?
- Bagaimana rollback?
- Bagaimana observability?
- Bagaimana test coverage?

## 120. Production Gate

Sebelum normal rollout:

- no known safety bypass
- no dual mutation authority
- crash recovery tested
- unknown outcome tested
- target revalidation tested
- config/catalog generation tested
- persistence migration tested
- IPC/CLI compatibility tested
- Android matrix tested as applicable
- resource bounds verified

## 121. Final Architecture

Target production flow:

```text
Input
  ↓
Config Validation
  ↓
Target Catalog Snapshot
  ↓
Candidate Scan
  ↓
Policy
  ↓
Plan
  ↓
Authorization
  ↓
Resource Admission
  ↓
Final Safety/Revalidation
  ↓
Executor
  ↓
Verifier
  ↓
Reconciliation if needed
  ↓
Durable JobResult
  ↓
Audit/Publication
```

## 122. Definition of Done

Rewrite migration dianggap selesai jika:

- typed domain menjadi authoritative
- EffectiveConfig authoritative
- TargetCatalog authoritative
- CandidateScanner authoritative
- SafetyGate mandatory
- PolicyEngine authoritative
- Planner authoritative
- Authorization mandatory
- single Executor mutation boundary
- Verifier mandatory
- unknown outcomes recoverable
- durable job state authoritative
- scheduler/resource ownership authoritative
- IPC versioned
- CLI tidak bypass lifecycle
- Android assumptions berada di adapter
- legacy target rules removed/degraded to non-authoritative compatibility
- legacy mutation path removed
- tests and fuzz/race/crash matrix pass
- rollback/recovery procedure documented

## 123. Final Invariants

1. Migration tidak boleh menurunkan safety.
2. Big-bang replacement dilarang jika incremental cutover memungkinkan.
3. Hanya satu mutation authority boleh aktif untuk operation tertentu.
4. Legacy path tidak boleh menjadi second safety authority setelah cutover.
5. SafetyGate tidak boleh dapat dimatikan oleh feature flag production.
6. Force tidak boleh bypass identity/safety.
7. Unknown outcome harus dipertahankan sebagai unknown sampai ada evidence.
8. Rollback tidak boleh blind-resume persisted jobs.
9. Persistence incompatibility harus menghasilkan recovery/degraded state.
10. Invalid config reload tidak mengganti active config.
11. Stale TargetCatalog tidak boleh menghasilkan mutation.
12. Stale Authorization tidak boleh menghasilkan mutation.
13. CLI/IPC tidak boleh bypass Planner/Authorization/Safety/Executor lifecycle.
14. Android-specific assumptions harus berada di Platform Adapter.
15. Legacy runtime booleans tidak boleh menjadi durable job authority.
16. Migration differences harus observable dan auditable.
17. Security regressions menjadi permanent tests.
18. Legacy code harus dihapus setelah tidak lagi menjadi dependency/authority.
19. Production rollout harus dapat dihentikan tanpa kehilangan recovery information.
20. Rewrite selesai hanya ketika architecture invariants lebih kuat daripada legacy behavior, bukan sekadar ketika compiler/test suite hijau.
