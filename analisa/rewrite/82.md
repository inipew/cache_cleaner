# 82.md — Testing, Property Testing, Fuzzing, Race Testing, Crash Testing, Fault Injection, Security Regression, and Production Validation Contract

## Tujuan

Rewrite cache_cleaner tidak dianggap selesai hanya karena compile dan unit test pass. Sistem melakukan filesystem discovery dan destructive mutation, sehingga correctness harus dibuktikan pada level domain, concurrency, crash recovery, filesystem races, malformed platform data, authorization, dan unknown outcomes.

Testing architecture:

```text
Unit
  ↓
Component
  ↓
Property
  ↓
Fuzz
  ↓
Integration
  ↓
Race / Concurrency
  ↓
Fault Injection
  ↓
Crash / Recovery
  ↓
Filesystem / Platform Matrix
  ↓
Security Regression
  ↓
Soak / Production Validation
```

## 1. Test Pyramid

Test murah dan deterministic harus berada di bawah; environment-dependent tests berada di atas.

## 2. Domain Unit Tests

Typed IDs, value objects, state transitions, policy predicates, generation comparisons, byte/duration bounds wajib diuji tanpa filesystem nyata.

## 3. State Machine Tests

Setiap legal transition harus mempunyai positive test.

## 4. Illegal Transition Tests

Setiap transition yang dilarang harus menghasilkan typed error dan tidak mengubah state.

## 5. Persistence Ordering Tests

Pastikan state transition tidak dipublish sebelum durable write sukses.

## 6. Config Tests

Test parse, validation, normalization, migration, unknown fields, overflow, cross-field constraints, generation changes.

## 7. Target Catalog Tests

Test target identity, discovery, dedupe, availability, mount identity, package/user binding, catalog generation.

## 8. Candidate Tests

Test traversal boundaries, relative paths, metadata, deduplication, limits, symlink handling, and candidate identity.

## 9. Safety Tests

Safety tests harus membuktikan deny-by-default pada malformed/ambiguous input.

## 10. Policy Tests

Policy harus deterministic untuk input yang sama.

## 11. Planner Tests

Test conflict detection, dependency ordering, budgets, deterministic output, and generation binding.

## 12. Authorization Tests

Test capability scope, expiry, generation, operation binding, target binding, and replay resistance.

## 13. Executor Tests

Test successful mutation, partial failure, permission failure, disappearance, race, cancellation, timeout, and ambiguous syscall result.

## 14. Verifier Tests

Test postcondition success, failure, unknown, partial completion, and reconciliation.

## 15. Persistence Tests

Test transactions, uniqueness, CAS, recovery markers, journal replay, corruption detection, and migration.

## 16. Scheduler Tests

Test duplicate triggers, debounce, fairness, starvation, cooldown, resource pressure, manual-vs-automatic precedence.

## 17. Resource Manager Tests

Test reservation, release, timeout, cancellation, fairness, capacity limits, and leak detection.

## 18. IPC Tests

Test malformed frames, version mismatch, oversized request, invalid enum, authentication/authorization boundary, cancellation, duplicate request, and disconnect.

## 19. CLI Tests

CLI must be tested as protocol client, not as direct state mutator.

## 20. Fake Filesystem

Implement a deterministic filesystem abstraction for most unit/component tests.

It must model:

- directories
- files
- symlinks
- permissions
- mount identity
- device identity
- inode identity
- read-only state
- errors
- rename/remove/recreate races

## 21. Real Filesystem Tests

Use temporary directories for integration tests where OS semantics matter.

## 22. Mount Tests

Run privileged mount tests only in isolated CI environments.

## 23. Android Tests

Use fake Android platform adapter for normal CI; real-device tests are an additional matrix.

## 24. Emulator Tests

Android emulator should be used for deterministic platform integration where possible.

## 25. Rooted Device Matrix

Real rooted-device tests should cover multiple kernel/OEM characteristics when project scope requires them.

## 26. Property Testing

Use property-based testing for invariants rather than only examples.

## 27. Path Property

For any candidate accepted by Safety, resolved path must remain inside the trusted boundary under the modeled filesystem semantics.

## 28. Identity Property

Changing target identity while keeping lexical path constant must invalidate the mutation context.

## 29. Generation Property

A stale generation cannot gain authority.

## 30. Scope Property

Changing user/package scope cannot silently retarget an operation.

## 31. Planner Property

Same immutable input snapshot produces equivalent deterministic plan.

## 32. Authorization Property

Changing any authorization-bound field invalidates authorization.

## 33. Executor Property

Executor cannot mutate outside authorized operation scope.

## 34. Verifier Property

Verification success requires actual postcondition evidence.

## 35. Unknown Property

Unknown mutation outcome never becomes success without reconciliation evidence.

## 36. Idempotency Property

Repeating the same idempotent operation after confirmed success does not produce unsafe additional effects.

## 37. Retry Property

Retry classification never retries non-idempotent unknown mutation blindly.

## 38. Resource Property

No reservation remains after terminal job state unless explicitly transferred/recovered.

## 39. Crash Property

Any crash point between intent, mutation, and verification must result in recoverable state.

## 40. Fuzzing Targets

Prioritize parsers and boundary inputs:

- config TOML
- IPC frames
- mountinfo
- package metadata
- paths
- custom target definitions
- policy rules
- persisted records
- scheduler events

## 41. Fuzz Safety

Fuzzing must seek cases where malformed input accidentally becomes an allowed destructive operation.

## 42. Fuzz Parser Limits

Inputs must have bounded size so fuzzing cannot create artificial resource exhaustion that bypasses semantic testing.

## 43. Structured Fuzzing

Use structured generators for valid/near-valid domain objects in addition to arbitrary bytes.

## 44. Path Fuzzing

Generate:

- `.`
- `..`
- repeated separators
- absolute paths
- empty components
- long components
- invalid bytes
- symlink chains
- mount crossings
- Unicode normalization variants

## 45. Symlink Fuzzing

Generate symlink graphs with cycles, escapes, replacement, and nested links.

## 46. Race Testing

Race tests must intentionally change filesystem state between discovery and execution.

## 47. Rename Race

Discover file, rename it, replace with another object, then execute.

Expected: identity mismatch or safe refusal.

## 48. Delete/Recreate Race

Delete discovered path and create a different object at the same path.

Expected: never silently mutate replacement object.

## 49. Mount Swap Race

Unmount/remount target path between planning and execution.

Expected: stale/identity mismatch.

## 50. Permission Race

Change permissions after authorization.

Expected: execution failure/revalidation, never privilege escalation.

## 51. Symlink Race

Replace directory component with symlink between checks.

Expected: final safety gate prevents escape.

## 52. Config Reload Race

Reload config while job moves through lifecycle.

Expected: generation binding prevents silent semantic change.

## 53. Catalog Refresh Race

Refresh catalog while plan is executing.

Expected: generation-aware revalidation.

## 54. Resource Race

Two jobs compete for same resource.

Expected: serialized reservation semantics and no double allocation.

## 55. Authorization Replay Race

Replay authorization concurrently.

Expected: idempotency/consumption semantics prevent unauthorized duplicate mutation.

## 56. Cancellation Race

Cancel immediately before/during/after mutation syscall.

Expected: explicit unknown/reconciliation semantics.

## 57. Timeout Race

Timeout around syscall boundary.

Expected: timeout does not imply mutation did not happen.

## 58. Worker Crash

Kill worker at each lifecycle phase.

Expected: durable recovery state.

## 59. Daemon Crash

Terminate daemon at deterministic journal/state points.

Restart and verify no invalid continuation.

## 60. Crash Matrix

Minimum crash points:

1. before persistence
2. after persistence
3. before authorization
4. after authorization
5. before resource reservation
6. after reservation
7. before executor syscall
8. after syscall submission
9. after partial mutation
10. before verification
11. after verification
12. before terminal publication

## 61. Fault Injection

Filesystem adapter should support deterministic injected errors:

- ENOENT
- EACCES
- EPERM
- EIO
- ENOSPC
- EBUSY
- EINVAL
- EINTR
- ETIMEDOUT

## 62. EINTR

Test retry behavior and ensure retry does not duplicate non-idempotent operations incorrectly.

## 63. ENOSPC

Test journal/result persistence and filesystem mutation under storage pressure.

## 64. EIO

I/O error must not be downgraded to ordinary empty result.

## 65. Partial Delete

Inject failure after N successful deletions.

Verify partial accounting and recovery state.

## 66. Verification Failure

Inject postcondition failure after apparent successful mutation.

Expected explicit reconciliation path.

## 67. Persistence Failure

Inject DB/storage failure at every state transition.

No state publication should occur before required durability.

## 68. Corruption Test

Corrupt individual persisted records and verify startup behavior is fail-safe.

## 69. Schema Migration Test

Run every supported migration from fixture database to current schema.

## 70. Downgrade Test

If downgrade is unsupported, startup must reject incompatible newer schema clearly.

## 71. IPC Protocol Fuzz

Malformed frame must never panic daemon or invoke executor.

## 72. Oversized IPC

Test maximum request/response sizes and allocation behavior.

## 73. Unknown Enum

Unknown protocol enum must be rejected or represented as unknown; never mapped to a permissive default.

## 74. Duplicate Request

Duplicate request ID must be idempotent or explicitly rejected.

## 75. Disconnect

Client disconnect must not automatically cancel durable job unless protocol contract says so.

## 76. Authorization Boundary Test

A client without required capability must be unable to trigger destructive operation through any IPC endpoint.

## 77. CLI Bypass Test

CLI must not expose an alternate path that directly calls executor without normal lifecycle.

## 78. Logging Tests

Ensure secrets, sensitive paths, and credentials are redacted.

## 79. Audit Tests

Every destructive job must have reconstructible audit events.

## 80. Accounting Tests

Freed bytes must be derived from verified observations, not optimistic estimates.

## 81. Metrics Tests

Counters must not double-count retries/duplicate events.

## 82. Determinism Tests

Plan hashes and normalized policy/config representations should be stable across process runs.

## 83. Concurrency Stress

Run many simultaneous jobs/events under bounded resources.

## 84. Loom/Model Checking

For small concurrency primitives, consider model checking or exhaustive interleaving tests.

Especially useful for:

- reservation state
- CAS transitions
- cancellation
- queue ownership
- publication barriers

## 85. Deadlock Detection

Stress lock acquisition and verify global lock ordering.

## 86. Lock Order Contract

Document and test canonical ordering of Job, Resource, Catalog, Config, and persistence locks.

## 87. Starvation Test

Continuous automatic work must not permanently starve manual/admin jobs where fairness promises exist.

## 88. Backpressure Test

Event storms must remain bounded in memory.

## 89. Scheduler Storm

Thousands of duplicate triggers should coalesce without creating thousands of jobs.

## 90. Catalog Storm

Thousands of mount/package events should result in bounded refresh behavior.

## 91. Resource Exhaustion

Test maximum jobs, candidates, operations, bytes, descriptors, and queued events.

## 92. Memory Budget

Measure allocations during large scans.

Candidate enumeration should be streamable where practical.

## 93. File Count Budget

Ensure enormous directories cannot bypass candidate limits.

## 94. Path Length Budget

Reject or safely handle extreme path lengths.

## 95. Time Budget

Scan/planning/execution timeouts must be deterministic and monotonic-clock based.

## 96. Disk Pressure Test

Run daemon while persistent storage is nearly full.

## 97. Thermal Test

If Android thermal state affects scheduling, test transitions and hysteresis.

## 98. Battery/Power Test

Test scheduler behavior under plugged/unplugged transitions if relevant.

## 99. Reboot Test

Execute jobs across simulated/real device reboot and verify recovery semantics.

## 100. Force-stop Test

Force-stop/kill daemon while operation is in-flight and verify recovery.

## 101. Package Lifecycle Test

Install/uninstall/reinstall package while scanning/planning.

## 102. User Lifecycle Test

Create/remove/switch user while catalog is active.

## 103. Mount Lifecycle Test

Mount/unmount/remount storage while daemon runs.

## 104. Filesystem Matrix

At minimum test supported semantics on ext4/f2fs and explicitly classify unsupported filesystems.

## 105. Read-only Matrix

Every destructive path must be tested against readonly mounts.

## 106. Permission Matrix

Test root, non-root, SELinux-denied, directory permissions, immutable objects where applicable.

## 107. Protected Target Regression

Maintain regression fixtures for known dangerous paths.

## 108. Escape Regression

Every discovered path escape bug must become a permanent regression test.

## 109. Authorization Regression

Every authorization bypass becomes a permanent regression test.

## 110. Unknown Outcome Regression

Every mutation uncertainty bug becomes a permanent recovery test.

## 111. Test Data Isolation

Tests must not touch real user data.

## 112. Temp Directory Safety

Integration tests must create dedicated roots and assert deletion stays inside them.

## 113. Test Cleanup

Test cleanup itself must be bounded and tolerate partial failure.

## 114. Parallel Test Isolation

No global fixed paths shared by tests.

## 115. CI Tiers

Recommended:

- fast unit
- component
- property
- fuzz smoke
- integration
- concurrency
- privileged platform
- Android emulator
- device matrix
- long soak

## 116. Sanitizers

Where supported, use AddressSanitizer, ThreadSanitizer, UndefinedBehaviorSanitizer, or equivalent tooling appropriate to Rust/native dependencies.

## 117. Miri

Use Miri where applicable for unsafe Rust abstractions and ownership-sensitive helper code.

## 118. Clippy

CI should enforce appropriate clippy lints.

## 119. Formatting

`cargo fmt --check` is mandatory.

## 120. Dependency Audit

Run dependency vulnerability/license checks according to project policy.

## 121. Unsafe Audit

Every `unsafe` block requires explicit safety rationale and targeted tests.

## 122. Coverage

Coverage is useful but must not replace invariant-based testing.

## 123. Mutation Testing

Consider mutation testing for policy/safety predicates where practical.

## 124. Golden Fixtures

Keep golden plan/result/protocol fixtures versioned.

## 125. Backward Compatibility

Protocol/config/database compatibility tests must cover supported versions.

## 126. Performance Benchmark

Benchmark scan, candidate creation, planning, persistence, and IPC separately.

## 127. Regression Thresholds

Significant performance regressions should fail or at least flag CI according to defined thresholds.

## 128. Soak Test

Run daemon continuously with synthetic event streams and bounded filesystem workload.

## 129. Leak Test

Check file descriptors, tasks, locks/reservations, memory growth, and stale persistence rows.

## 130. Zombie Worker Test

Simulate workers that stop responding without exiting.

Scheduler/recovery must reclaim ownership safely.

## 131. Clock Test

Simulate monotonic time advancement; wall-clock jumps must not break deadlines.

## 132. Reboot/Wall Clock Test

Persisted timestamps must not be interpreted as monotonic instants after reboot.

## 133. Randomized Scheduler

Random event sequences should be used to find illegal lifecycle transitions.

## 134. Stateful Fuzzing

Generate sequences of submit/cancel/reload/mount-change/worker-crash/restart rather than isolated messages.

## 135. Invariant Checker

Tests should contain a reusable global invariant checker that runs after every state transition in model tests.

## 136. Security Threat Cases

Explicitly test:

- path traversal
- symlink escape
- mount escape
- target substitution
- stale authorization
- replay
- confused deputy
- privilege confusion
- IPC spoofing
- resource exhaustion
- log injection
- persistence tampering

## 137. Confused Deputy Test

A less-privileged caller must not use a privileged daemon to perform an operation outside its granted scope.

## 138. TOCTOU Test

Filesystem mutation between safety checks and mutation must be adversarially exercised.

## 139. Fail-Safe Test

For every ambiguous/error condition, verify the resulting action is no broader than the safe baseline.

## 140. Definition of Done

Production readiness requires:

- deterministic unit suite
- component tests
- property tests
- fuzz targets
- race tests
- crash tests
- fault injection
- persistence corruption tests
- IPC fuzzing
- security regression suite
- Android emulator/device tests as applicable
- filesystem matrix
- resource exhaustion tests
- concurrency stress
- soak tests
- CI enforcement

## 141. Release Gate

A release containing changes to Safety, Planner, Authorization, Executor, Target Catalog, persistence, or IPC must run the corresponding expanded test tier.

## 142. Final Invariants

1. Tests must verify safety invariants, not only outputs.
2. Destructive code requires adversarial race tests.
3. Unknown mutation outcomes require recovery tests.
4. Every illegal state transition must be rejected.
5. Every persisted transition must be crash-tested.
6. Fuzzed malformed input must never widen authority.
7. IPC malformed input must never reach Executor.
8. Stale generation must never gain authority.
9. Target replacement at the same path must never be silently accepted.
10. Symlink and mount races must fail safe.
11. Resource exhaustion must remain bounded.
12. Scheduler/event storms must remain bounded.
13. Tests must never mutate real user data.
14. Every discovered security bug becomes a permanent regression test.
15. Production readiness requires integration of safety, persistence, concurrency, and recovery testing—not isolated unit correctness.
