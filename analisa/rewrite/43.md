43.md — Verifier Architecture, Post-Execution Verification, Result Semantics, Idempotency, Unknown Outcome Recovery, dan Job Completion Contract

1. Tujuan

Verifier adalah komponen read-only yang memastikan hasil operasi setelah Executor selesai benar-benar sesuai dengan postcondition yang diharapkan.

Verifier BUKAN:

→ executor kedua
→ retry engine untuk operasi destructive
→ policy engine
→ authorization layer
→ scanner penuh
→ komponen yang boleh memperbaiki kegagalan dengan melakukan mutation

Verifier hanya membaca keadaan aktual dan membandingkannya dengan keadaan yang seharusnya terjadi.

Alur utama:

```
AuthorizedPlan
      │
      ▼
  Executor
      │
      ▼
OperationResult
      │
      ▼
   Verifier
      │
      ├── Verified
      ├── AlreadyGone
      ├── Changed
      ├── NotSatisfied
      └── Unknown
            │
            ▼
    Job Result Aggregator
            │
            ▼
      Job Completion
```

2. Posisi Verifier Dalam Arsitektur

Verifier berada setelah Executor dan sebelum hasil akhir Job.

```
Scanner
   │
   ▼
 Safety
   │
   ▼
 Policy
   │
   ▼
Planner
   │
   ▼
```

Authorization
│
▼
Executor
│
▼
Verifier
│
▼
Result Aggregator
│
▼
Job Completion

Verifier tidak boleh membuat jalur alternatif:

```
Executor ───────► Verifier ───────► Executor
                      ✕
```

Tidak boleh ada:

```
verify()
   │
   └── delete_again()
           ✕
```

Jika verification gagal, hasil harus dicatat sebagai failure, partial success, changed, atau unknown sesuai kontrak.

Recovery mutation harus melalui Job baru dan seluruh pipeline kembali dari awal.

3. Prinsip Dasar

3.1 Read-only

Verifier tidak boleh:

→ unlink
→ rmdir
→ rename
→ chmod
→ chown
→ truncate
→ write
→ mount
→ remount
→ trim
→ mengubah kernel state

Verifier hanya melakukan observasi.

3.2 Postcondition-driven

Verifier tidak bertanya:

```
"Apakah syscall Executor berhasil?"
```

Verifier bertanya:

```
"Apakah keadaan filesystem/platform sekarang memenuhi
 postcondition operasi?"
```

Contoh:

```
unlink()
   │
   ├── syscall success
   ▼
verifier
   │
   ├── object tidak ada
   │      → Verified
   │
   └── object masih ada
          → NotSatisfied
```

3.3 Operation-scoped

Verifier tidak boleh melakukan scan bebas terhadap filesystem.

Verifier hanya boleh memeriksa objek yang berasal dari:

→ AuthorizedPlan
→ PlannedOperation
→ ExecutionOperation
→ trusted scope
→ identity snapshot

Dengan demikian Verifier tidak memperoleh kemampuan membaca path arbitrary.

3.4 Fail closed

Jika Verifier tidak dapat memastikan keadaan akhir:

```
Verified
   │
   │
   ├── tidak dapat memastikan
   ▼
 Unknown
```

Bukan:

```
Unknown → Verified
```

4. Input Contract

Verifier menerima minimal:

```
VerificationInput {
    job_id
    plan_id
    operation_id

    operation
    operation_result

    expected_postcondition

    root_identity
    object_identity

    relevant_generation

    verification_budget

    cancellation_token
}
```

Verifier boleh menerima snapshot tambahan jika diperlukan:

```
PlatformSnapshot
CatalogSnapshot
FilesystemIdentity
RuntimeState
```

Tetapi snapshot tersebut harus immutable untuk satu verification attempt.

5. Output Contract

Hasil verification harus typed.

Contoh:

```
VerificationResult

    ├── Verified
    ├── AlreadySatisfied
    ├── Changed
    ├── NotSatisfied
    ├── Stale
    ├── Cancelled
    ├── BudgetExceeded
    └── Unknown
```

Jangan menggunakan:

```
bool
```

karena:

```
true / false
```

tidak cukup untuk membedakan:

```
sukses
object sudah hilang
object berubah
target stale
verification gagal
hasil tidak diketahui
```

6. OperationResult Berbeda Dengan VerificationResult

Executor menghasilkan:

```
OperationResult
```

Verifier menghasilkan:

```
VerificationResult
```

Keduanya tidak boleh digabung.

Contoh:

```
unlink()
   │
   ▼
syscall = success
   │
   ▼
OperationResult::Applied
   │
   ▼
Verifier
   │
   └── object masih ada
            │
            ▼
    VerificationResult::NotSatisfied
```

Sebaliknya:

```
unlink()
   │
   ▼
syscall = ENOENT
   │
   ▼
OperationResult::AlreadyGone
   │
   ▼
Verifier
   │
   └── object memang tidak ada
            │
            ▼
    VerificationResult::AlreadySatisfied
```

7. Postcondition

Setiap PlannedOperation yang membutuhkan verification harus memiliki postcondition eksplisit.

Contoh:

```
RemoveFile

precondition:
    target exists
    target identity matches

mutation:
    unlinkat(...)

postcondition:
    target does not exist
```

Untuk directory:

```
RemoveDirectory

postcondition:
    directory does not exist
```

Untuk maintenance operation:

```
TrimFilesystem

postcondition dapat berupa:

    operation accepted by platform
```

atau:

```
    platform reports requested maintenance completed
```

Postcondition harus sesuai kemampuan observasi platform.

Jangan membuat postcondition yang tidak bisa diverifikasi secara reliable.

8. Verification Level

Tidak semua operasi membutuhkan tingkat verification yang sama.

Definisikan level:

```
VerificationLevel

    ├── None
    ├── Existence
    ├── Identity
    ├── Type
    ├── Scope
    └── PlatformState
```

Contoh:

```
RemoveFile
    → Existence

RemoveKnownObject
    → Existence + Identity

RemoveDirectory
    → Existence + Type

Maintenance operation
    → PlatformState
```

Default harus conservative.

9. Idempotency

Deletion operation harus diperlakukan sebagai operation yang secara konseptual idempotent terhadap keadaan:

```
target already absent
```

Contoh:

```
sebelum execution:
    file exists

Executor:
    unlink → ENOENT

Verifier:
    file absent
```

Hasil akhir:

```
AlreadySatisfied
```

Bukan otomatis:

```
Failed
```

Karena tujuan operasi adalah:

```
file tidak lagi ada
```

Namun kondisi ini harus dibedakan dari:

```
target berubah menjadi object lain
```

Contoh:

```
original:
    /cache/x
    inode = 100

sebelum mutation:
    inode 100

race:
    original deleted
    new object created
    inode = 200

Verifier:

    path exists
    identity != 100

result:

    Changed
```

Bukan:

```
Verified
```

10. Identity Verification

Identity snapshot harus digunakan jika operation memerlukan identity binding.

Contoh:

```
Candidate
    │
    ▼
identity:
    dev = D1
    inode = I1
    type = RegularFile
    generation = G1
```

Setelah execution:

```
path exists
    │
    ├── dev/inode/type sama
    │       → sesuai
    │
    └── berbeda
            → Changed
```

Identity tidak boleh digantikan hanya dengan path string.

11. Path Tidak Sama Dengan Object

Verifier harus memahami:

```
path ≠ object
```

Contoh:

```
/cache/a
```

Pada scan:

```
/cache/a → inode 100
```

Setelah execution/race:

```
/cache/a → inode 200
```

Walaupun path sama:

```
object berbeda
```

Maka hasil:

```
Changed
```

12. Symlink

Verifier harus mempertahankan semantics no-follow.

Jika target expected adalah regular file:

```
/cache/a → regular file
```

kemudian menjadi:

```
/cache/a → symlink
```

hasil:

```
TypeChanged
```

Bukan:

```
Verified
```

Verifier tidak boleh mengikuti symlink untuk menemukan "apa yang ada di baliknya" jika operation contract menggunakan no-follow semantics.

13. Hard Link

Hard link harus diperlakukan berdasarkan identity object, bukan hanya pathname.

Contoh:

```
/cache/a ─┐
          ├── inode 100
/cache/b ─┘
```

Jika operation menghapus:

```
/cache/a
```

Maka:

```
/cache/a → hilang
/cache/b → tetap ada
```

Verification terhadap `/cache/a`:

```
Verified
```

Tidak boleh menganggap seluruh inode telah hilang dari filesystem.

14. Directory Verification

Directory memiliki risiko khusus.

Contoh:

```
/cache/x/
```

Executor mencoba menghapus directory.

Jika masih memiliki child:

```
rmdir → ENOTEMPTY
```

Maka Executor menghasilkan:

```
NotEmpty
```

Verifier tidak boleh kemudian menghapus child secara otomatis.

Tidak boleh:

```
rmdir failed
   │
   ▼
recursive delete
   ✕
```

Jika recursive cleanup memang merupakan policy yang diizinkan, child deletion harus sudah menjadi operasi eksplisit di Plan.

15. Dependency-aware Verification

Operation graph:

```
delete child A
      │
      ▼
delete child B
      │
      ▼
delete directory X
```

Verification harus memperhatikan dependency.

Jika:

```
child A = NotSatisfied
```

maka:

```
delete directory X
```

mungkin secara otomatis tidak dapat dianggap sebagai independent failure.

Result aggregator harus mempertahankan dependency information.

16. Partial Success

Satu Job dapat memiliki:

```
1000 operations
```

misalnya:

```
997 Verified
  2 AlreadySatisfied
  1 NotSatisfied
```

Job tidak boleh dianggap:

```
Failed
```

secara penuh.

Hasil harus dapat merepresentasikan:

```
CompletedWithPartialSuccess
```

Contoh klasifikasi:

```
all operations satisfied
    → Completed

sebagian satisfied
    → CompletedPartial

tidak ada operation berhasil
    → Failed
```

Tetapi klasifikasi akhir harus mempertimbangkan policy Job.

17. Result Aggregation

Verifier menghasilkan result per operation.

```
Operation 1 → Verified
Operation 2 → Verified
Operation 3 → Changed
Operation 4 → AlreadySatisfied
Operation 5 → Unknown
```

Kemudian aggregator:

```
OperationResults
      │
      ▼
ResultAggregator
      │
      ├── counts
      ├── bytes
      ├── failures
      ├── unknowns
      ├── cancellations
      └── dependency impact
              │
              ▼
         JobResult
```

JobResult tidak boleh hanya berupa:

```
success = true
```

18. JobResult

JobResult minimal harus memuat:

```
JobResult {
    job_id
    plan_id

    final_state

    operation_count
    verified_count
    already_satisfied_count
    changed_count
    not_satisfied_count
    unknown_count
    cancelled_count

    bytes_requested
    bytes_effectively_removed

    started_at
    finished_at

    failure_summary
    verification_summary
}
```

Nilai counter harus konsisten.

Contoh invariant:

```
operation_count
=
verified
+ already_satisfied
+ changed
+ not_satisfied
+ unknown
+ cancelled
+ other_terminal_results
```

19. Unknown Outcome

Unknown adalah keadaan penting.

Contoh:

```
Executor
   │
   ▼
unlink()
   │
   └── connection / process failure
             │
             ▼
        outcome unknown
```

Tidak boleh langsung disimpulkan:

```
failed
```

atau:

```
success
```

Karena mutation mungkin sudah terjadi sebelum error diterima.

20. Unknown Outcome Recovery

Untuk operation:

```
mutation outcome = Unknown
```

Recovery pertama harus read-only verification.

```
Unknown
   │
   ▼
Verifier
   │
   ├── target absent
   │       → AlreadySatisfied
   │
   ├── target unchanged
   │       → NotSatisfied / retryable by new Job
   │
   ├── target changed
   │       → Changed
   │
   └── cannot determine
           → Unknown
```

Tidak boleh langsung melakukan mutation kedua dari Executor yang sama.

21. Retry

Retry destructive operation hanya boleh dilakukan melalui lifecycle Job yang baru atau retry attempt yang secara eksplisit membuat Plan baru.

Bukan:

```
Executor
   │
   └── error
         │
         └── unlink lagi
                ✕
```

Yang benar:

```
Job
 │
 ├── Execute
 │
 ├── Verify
 │
 └── Unknown
        │
        ▼
    mark retryable
        │
        ▼
    Scheduler
        │
        ▼
    new attempt
        │
        ▼
    new Scan
        │
        ▼
    new Plan
        │
        ▼
    new Authorization
        │
        ▼
    new Execute
```

22. Stale Verification

Verification dapat menjadi stale jika:

→ catalog generation berubah
→ platform generation berubah
→ storage identity berubah
→ target mount berubah
→ user storage state berubah
→ trusted root identity berubah

Contoh:

```
Plan generation = G10

execution selesai

storage event
    │
    ▼
generation = G11
```

Maka verification yang bergantung pada G10 dapat menghasilkan:

```
Stale
```

Stale bukan sama dengan:

```
NotSatisfied
```

Karena masalahnya adalah validity context, bukan semata-mata target state.

23. Verification Race

Verification sendiri dapat mengalami race.

Contoh:

```
Verifier membaca:

    target absent
```

Kemudian object dibuat ulang sesaat setelah verification.

Maka hasil:

```
Verified at observation time
```

Tetapi jangan mengklaim:

```
object will never exist again
```

Verifier hanya memverifikasi postcondition pada observation point yang didefinisikan oleh contract.

24. Observation Point

Setiap verification memiliki observation boundary.

Konsep:

```
mutation
   │
   ▼
verification read
   │
   ▼
observation point
   │
   ▼
result
```

Result berarti:

```
"postcondition terpenuhi pada observation point"
```

bukan:

```
"filesystem dijamin tetap seperti itu selamanya"
```

25. Cancellation

Cancellation sebelum verification:

```
Execute
   │
   ▼
cancelled
   │
   └── verification may be skipped
           │
           ▼
        Cancelled
```

Cancellation selama verification:

```
verifier harus berhenti pada safe boundary.
```

Tidak boleh:

```
cancellation
   │
   └── ignored until entire filesystem scan
```

Verification harus bounded.

26. Verification Budget

Verifier memiliki budget sendiri.

Contoh:

```
max_metadata_reads
max_entries
max_duration
```

Verifier tidak boleh melakukan verification yang tidak terbatas hanya karena Executor telah selesai.

Jika budget habis:

```
BudgetExceeded
```

Kemudian JobResult harus menjelaskan:

```
execution may have succeeded
but complete verification was not performed
```

27. Tidak Ada Recursive Verification Bebas

Verifier tidak boleh melakukan:

```
verify(root)
```

kemudian scan seluruh subtree tanpa batas.

Jika operation hanya:

```
delete /cache/a
```

maka verification cukup:

```
verify /cache/a
```

Untuk directory deletion, verifier hanya melakukan observasi yang diperlukan untuk memastikan postcondition.

28. Filesystem Abstraction

Verifier tidak boleh memanggil raw syscall secara langsung.

Gunakan abstraction:

```
FilesystemReader
```

contoh:

```
metadata_at(...)
stat_at_no_follow(...)
exists_at(...)
identify(...)
read_mount_identity(...)
```

Dependency:

```
Verifier
   │
   ▼
FilesystemReader
   │
   ▼
Platform adapter
   │
   ▼
OS
```

Verifier tidak mengetahui detail syscall.

29. Resource Ownership

FD yang digunakan Verifier harus memiliki ownership jelas.

Contoh:

```
VerificationContext
      │
      ├── root_fd
      ├── parent_fd
      └── target observation
```

Lifetime:

```
acquire
   │
   ▼
verify
   │
   ▼
close
   │
   ▼
release
```

Tidak boleh ada FD leak akibat verification failure, cancellation, atau panic.

30. Safety Boundary Tetap Berlaku

Verifier bukan pengganti Safety Layer.

Walaupun verifier read-only, traversal tetap harus:

```
TrustedRoot
    │
    ▼
FD-relative
    │
    ▼
no-follow
    │
    ▼
bounded observation
```

Jangan membuat helper:

```
verify_absolute_path("/data/...")
```

karena akan membuka arbitrary path access.

31. Separation of Concerns

Pembagian tanggung jawab:

```
Executor
    → melakukan mutation

Verifier
    → memeriksa postcondition

ResultAggregator
    → menggabungkan operation result

Scheduler
    → menentukan retry/defer/new attempt

Policy
    → menentukan apakah operation memang diizinkan

Reporter
    → menyajikan hasil
```

Tidak boleh:

```
Verifier → Scheduler
              ✕
```

Verifier hanya menghasilkan fakta.

32. Verification Facts vs Policy Decision

Verifier mengatakan:

```
target absent
```

Policy/Job layer yang menentukan arti bisnisnya.

Contoh:

```
target absent
    │
    ├── remove operation
    │       → success
    │
    └── preserve operation
            → tidak relevan
```

Verifier tidak boleh mengetahui:

```
"apakah user ingin cache dibersihkan"
```

Ia hanya memverifikasi keadaan.

33. Final Job State

State terminal harus konsisten dengan hasil.

Contoh:

```
semua operation satisfied
        │
        ▼
   Completed


sebagian satisfied
        │
        ▼
  CompletedPartial


cancellation requested
        │
        ▼
    Cancelled


fatal execution / verification failure
        │
        ▼
     Failed


context invalid
        │
        ▼
     Stale


shutdown sebelum completion
        │
        ▼
     Stopped
```

Jangan menghasilkan state:

```
Completed
```

jika terdapat operation yang diwajibkan sukses tetapi belum diverifikasi dan policy mengharuskan verification.

34. Completion Contract

Job hanya boleh masuk terminal success state setelah:

```
Executor selesai
      │
      ▼
semua required verification selesai
      │
      ▼
ResultAggregator selesai
      │
      ▼
JobResult immutable
      │
      ▼
state transition atomic
      │
      ▼
   Completed
```

JobResult harus immutable setelah Job memasuki terminal state.

35. Atomic Completion

Jangan melakukan:

```
set state = Completed
      │
      ▼
generate result
```

Karena crash di tengah dapat menghasilkan:

```
Completed
tetapi Result belum ada.
```

Yang benar:

```
build JobResult
      │
      ▼
validate JobResult
      │
      ▼
atomically publish result + terminal state
```

36. Crash Semantics

Jika process crash:

```
Execute
   │
   ▼
mutation mungkin terjadi
   │
   ▼
crash sebelum verification
```

Setelah restart:

```
jangan menganggap operation gagal dan mengulang mutation secara buta.
```

Recovery harus:

```
Job journal / persisted state
        │
        ▼
  identify unfinished operation
        │
        ▼
   read-only inspection
        │
        ▼
      verify
        │
        ├── satisfied
        │
        ├── changed
        │
        └── unknown
        │
        ▼
   create new attempt if needed
```

37. Persistence Boundary

Jika runtime membutuhkan crash recovery, persistence hanya boleh menyimpan state yang diperlukan.

Contoh:

```
JobId
PlanId
OperationId
AttemptId
operation state
execution result
verification result
generation
timestamps
```

Jangan menyimpan arbitrary filesystem state sebagai authority permanen.

Filesystem tetap menjadi source of truth untuk kondisi aktual.

38. Result Ordering

Result operation harus deterministic.

Jika Plan:

```
O1
O2
O3
```

Result harus dapat direpresentasikan secara stabil:

```
O1 → result
O2 → result
O3 → result
```

Tidak boleh bergantung pada urutan thread completion.

Execution concurrency dapat berbeda, tetapi result presentation dan aggregation harus deterministic.

39. Concurrent Verification

V1 default:

```
verify operations sequentially
```

Alasannya:

→ sederhana
→ resource usage predictable
→ mudah cancellation
→ mudah audit
→ mengurangi metadata pressure

Jika nantinya parallel verification diperlukan:

```
bounded worker pool
    │
    ├── V1
    ├── V2
    └── V3
```

Tetap harus:

→ bounded
→ cancellation-aware
→ deterministic aggregation
→ tidak mengubah mutation semantics

40. Error Taxonomy

Verifier error harus typed.

Contoh:

```
VerificationError

    ├── TargetMissing
    ├── IdentityChanged
    ├── TypeChanged
    ├── ScopeChanged
    ├── RootChanged
    ├── MountChanged
    ├── MetadataReadFailed
    ├── PermissionDenied
    ├── StaleGeneration
    ├── Cancelled
    ├── BudgetExceeded
    └── Unknown
```

Jangan mengubah seluruh error menjadi:

```
VerificationFailed
```

karena informasi tersebut dibutuhkan Scheduler, Reporter, dan audit.

41. Permission Denied

Jika Executor berhasil tetapi Verifier tidak memiliki permission membaca metadata:

```
mutation = Applied
verification = Unknown
```

Bukan:

```
mutation = Failed
```

dan bukan:

```
verification = Verified
```

Hal ini penting agar system tidak memalsukan kepastian.

42. Telemetry

Verifier harus menghasilkan telemetry bounded.

Contoh:

```
verification_started
verification_completed
verification_already_satisfied
verification_changed
verification_not_satisfied
verification_unknown
verification_budget_exceeded
verification_stale
verification_duration
```

Jangan mencatat arbitrary filesystem content.

43. Logging

Log minimal:

```
job_id
plan_id
operation_id
operation_type
verification_result
reason_code
duration
```

Path harus mengikuti logging privacy policy.

Jika path sensitif, gunakan:

```
normalized relative path
hashed identifier
target id
package id jika diizinkan
```

Jangan log:

```
full arbitrary path
file content
environment secrets
```

44. Explainability

User harus dapat memahami:

```
"mengapa Job dianggap partial?"
```

Contoh:

```
Job completed partially.

997 operations verified.
2 targets were already absent.
1 target changed before verification.
```

Atau:

```
Job could not be fully verified.

3 operations have unknown outcome
because filesystem metadata became unavailable.
```

Explainability berasal dari typed result, bukan string error yang dibentuk secara acak.

45. Result Aggregation Rules

Contoh baseline:

```
Verified
    → success

AlreadySatisfied
    → success

Changed
    → partial/failure depending on policy

NotSatisfied
    → partial/failure

Unknown
    → partial/failed depending on required verification

Cancelled
    → Cancelled

Stale
    → Stale

BudgetExceeded
    → partial/failed depending on verification requirement
```

Tidak boleh ada satu mapping universal yang mengabaikan operation semantics.

46. Operation-level Success

Definisikan:

```
OperationSuccess
```

sebagai keadaan ketika postcondition operation terpenuhi.

Contoh:

```
unlink returned ENOENT
+
target absent

→ OperationSuccess
```

Ini menunjukkan perbedaan antara:

```
syscall success
```

dan:

```
operation success
```

47. Job-level Success

Job success adalah aggregation dari OperationSuccess sesuai Job policy.

Contoh:

```
100 operations
100 operation success

→ Completed
```

Sedangkan:

```
100 operations
 98 operation success
  2 unknown
```

tidak otomatis:

```
Completed
```

Karena required verification policy dapat mengharuskan:

```
CompletedPartial
atau
Failed
```

48. No Silent Success

Dilarang:

```
operation failed
    │
    ▼
verifier tidak dijalankan
    │
    ▼
job marked Completed
        ✕
```

Dilarang juga:

```
verification unknown
    │
    ▼
treat as success
        ✕
```

Semua ketidakpastian harus terlihat dalam result.

49. No Automatic Repair

Verifier menemukan:

```
target masih ada
```

Verifier tidak boleh:

```
delete(target)
retry(target)
rename(target)
chmod(target)
```

Ia hanya menghasilkan:

```
NotSatisfied
```

Recovery dilakukan oleh orchestration layer melalui attempt baru.

50. Testing Architecture

Verifier harus memiliki test suite sendiri.

Minimal:

```
Unit Tests
   │
   ├── postcondition
   ├── identity
   ├── type
   ├── already absent
   ├── changed object
   ├── symlink
   ├── hard link
   ├── directory
   ├── cancellation
   └── budget


Race Tests
   │
   ├── delete before verify
   ├── replace before verify
   ├── recreate target
   ├── mount change
   └── root identity change


Property Tests
   │
   ├── result aggregation
   ├── terminal state mapping
   └── counter invariants


Fuzz Tests
   │
   ├── malformed metadata
   ├── invalid operation descriptor
   ├── path components
   └── synthetic filesystem responses
```

51. Fake Filesystem

Gunakan FakeFilesystem untuk test deterministic.

Contoh:

```
FakeFS

/cache/
   ├── a
   ├── b
   └── c
```

Test:

```
operation = remove /cache/a

simulated executor result = Applied

fake mutation:
    remove /cache/a

verifier:
    expected absent

result:
    Verified
```

Kemudian race:

```
executor result = Applied

fake fs:
    remove a
    create a with new identity

verifier:
    Changed
```

52. Result Aggregator Property Test

Untuk setiap operation result:

```
aggregate(results)
```

harus memenuhi:

```
total == sum(all categorized results)
```

Dan:

```
aggregate(results)
== aggregate(shuffled(results))
```

Dengan kata lain:

```
result aggregation commutative terhadap ordering
```

kecuali jika dependency semantics memang menentukan ordering.

53. Determinism

Untuk input yang sama:

```
Plan
OperationResults
Policy
VerificationSnapshot
```

hasil harus sama.

```
same input
    │
    ├── run 1 → JobResult A
    ├── run 2 → JobResult A
    └── run 3 → JobResult A
```

Tidak boleh bergantung pada:

→ thread scheduling
→ HashMap iteration order
→ wall-clock ordering
→ random IDs

54. Clock Semantics

Durasi verification menggunakan:

```
MonotonicClock
```

Timestamp audit menggunakan:

```
WallClock
```

Jangan menghitung timeout menggunakan wall clock karena clock dapat berubah.

55. Budget Accounting

Verifier harus melaporkan:

```
metadata reads
entries observed
verification duration
```

Contoh:

```
VerificationBudget {
    max_metadata_reads
    max_duration
}
```

Jika budget:

```
1000 metadata reads
```

dan verifier membutuhkan:

```
1001
```

hasil:

```
BudgetExceeded
```

bukan:

```
loop until complete
```

56. Memory Bound

Verifier tidak boleh menyimpan seluruh filesystem tree.

Gunakan:

```
operation-by-operation verification
```

atau:

```
bounded result buffer
```

Memory usage harus predictable terhadap:

```
operation count
batch size
configured limits
```

57. Interaction Dengan Scheduler

Verifier tidak menjadwalkan ulang Job.

Flow:

   │

   │
   ▼

   │
   ▼

   ├── retry new attempt
   ├── mark stale

Separation ini wajib.

58. Interaction Dengan Reporter

Reporter menerima:

```
JobResult
```

Reporter tidak membaca filesystem untuk mencari kebenaran tambahan.

```
Verifier
   │
   ▼

   │
   ▼
Reporter
```

Dengan demikian laporan dapat direproduksi dari result.
