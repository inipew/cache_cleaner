40.md

Planner Contract, Operation Graph, Dependency Ordering, Conflict Detection, Budget Allocation, dan Deterministic Execution Plan

1. Tujuan

Planner bertanggung jawab mengubah candidate yang sudah lolos Safety dan Policy menjadi rencana operasi yang eksplisit, deterministik, dan dapat diaudit.

Planner tidak melakukan mutation.

Planner tidak melakukan filesystem cleanup.

Planner tidak menentukan policy.

Planner tidak memberikan authorization.

Alur:

Candidate
→ SafetyValidatedCandidate
→ PolicyApprovedCandidate
→ Planner
→ PlannedOperation
→ Authorization
→ AuthorizedPlan
→ Final Safety Gate
→ Executor

Planner harus menghasilkan plan yang dapat dijelaskan tanpa menjalankannya.

2. Prinsip Dasar

Planner harus bersifat:

pure sebisa mungkin

deterministik

read-only

bounded

immutable pada output

tidak bergantung pada wall-clock secara langsung

tidak melakukan syscall destructive

tidak memanggil shell

tidak mengubah filesystem

Tidak boleh ada logic seperti:

jika file besar maka langsung hapus

jika directory maka recursive delete

jika gagal maka force delete

Keputusan tersebut harus berasal dari Policy atau Safety contract.

3. Input Planner

Planner menerima minimal:

JobContext

PolicyApprovedCandidate

CatalogSnapshot

PlatformSnapshot

ConfigSnapshot

ScanReport

ScanBudget result

CleanupBudget

PlannerLimits

CancellationToken

Planner harus menggunakan snapshot yang sama dengan tahap sebelumnya.

Planner tidak boleh mengambil konfigurasi global terbaru secara diam-diam.

Jika config berubah selama planning, generation mismatch harus menghasilkan Stale dan plan tidak boleh diteruskan.

4. Output Planner

Output utama:

PlanId

JobId

source generations

planned operations

dependencies

estimated bytes

estimated operation count

budget reservation

warnings

planner metadata

Plan harus immutable setelah dibuat.

Jika perlu mengubah plan, buat Plan baru.

Jangan memodifikasi AuthorizedPlan yang sedang digunakan oleh Executor.

5. PlannedOperation

Setiap PlannedOperation harus mempunyai identity sendiri.

Minimal:

OperationId

TargetId

Candidate identity

relative path

operation type

expected object type

expected identity

estimated bytes

dependencies

reason code

policy decision reference

planner generation

priority

PlannedOperation bukan authorization.

PlannedOperation hanya menyatakan:

“Jika authorization dan final safety validation berhasil, operation ini direncanakan.”

6. Operation Type

Operation type harus eksplisit.

Contoh:

RemoveFile

RemoveEmptyDirectory

TrimTarget

MaintenanceAction

Namun filesystem deletion dan kernel/platform maintenance tidak boleh disatukan menjadi primitive generic.

Contoh:

RemoveFile

berbeda dari:

TrimFilesystem

berbeda dari:

CompactMemory

berbeda dari:

F2fsMaintenance

Perbedaan ini penting agar Executor tidak perlu menebak maksud operation.

7. Tidak Ada Generic Delete

Planner tidak boleh menghasilkan:

Delete(path)

dengan semantics yang berubah tergantung object type.

Operation harus menyatakan apa yang dimaksud.

Contoh:

RemoveFile(candidate)

lebih aman daripada:

Delete(candidate.path)

Karena Executor dapat memverifikasi bahwa operation memang ditujukan untuk RegularFile.

8. Deterministic Planning

Input yang sama harus menghasilkan plan yang sama.

Jika:

candidate set sama

policy sama

config generation sama

catalog generation sama

platform snapshot sama

budget sama

planner version sama

maka urutan dan isi plan harus sama.

Planner tidak boleh bergantung pada:

filesystem iteration order

HashMap random order

current wall-clock

thread scheduling

unspecified concurrency order

9. Candidate Ordering

Candidate harus diurutkan menggunakan comparator yang eksplisit.

Contoh ordering:

TargetId

PackageId

UserId

RelativePath

ObjectType

ObjectIdentity

OperationType

Ordering hanya digunakan untuk determinism.

Ordering bukan security authorization.

10. Operation Identity

OperationId harus stabil dalam satu plan.

OperationId dapat diturunkan dari:

PlanId

candidate identity

operation type

relative path

atau identifier lain yang dijamin unik.

Jangan menggunakan timestamp saja.

Jangan menggunakan random value jika determinism dibutuhkan.

PlanId sendiri boleh random, tetapi urutan dan operation set harus tetap deterministik.

11. Duplicate Candidate

Planner harus menangani duplicate candidate.

Duplicate dapat terjadi karena:

scanner overlap

multiple discovery sources

hard link

directory traversal edge case

repeated event

re-scan merge

Planner harus memiliki deduplication rule yang jelas.

Candidate yang memiliki identity dan target scope sama tidak boleh menghasilkan destructive operation ganda secara tidak sengaja.

12. Hard Link dan Planning

Dua path dapat menunjuk object identity yang sama.

Planner harus menentukan apakah dua candidate tersebut:

merupakan dua directory entries yang memang boleh dihapus masing-masing

atau merupakan duplicate object candidate yang tidak boleh menghasilkan operation ganda

Keputusan harus mengikuti semantics operation.

Untuk unlink, directory entry adalah target operation.

Karena itu Planner tidak boleh sembarang deduplicate berdasarkan inode saja.

Identity object digunakan untuk safety.

Path entry identity digunakan untuk menentukan namespace operation.

13. Conflict Detection

Planner harus mendeteksi operation yang konflik.

Contoh:

RemoveFile:

a/b/c

dan

RemoveDirectory:

a/b

Jika directory a/b dihapus lebih dahulu, operation c menjadi invalid.

Planner harus membuat dependency:

RemoveFile(a/b/c)
→ RemoveEmptyDirectory(a/b)

Dengan demikian child harus diproses sebelum parent.

14. Parent-Child Ordering

Untuk operasi deletion:

child operation harus mendahului parent operation.

Contoh:

a

a/b

a/b/c

Urutan:

remove c

remove b

remove a

bukan:

remove a

remove b

remove c

Planner tidak boleh mengandalkan Executor untuk menemukan ordering tersebut.

15. Dependency Graph

Plan harus dapat direpresentasikan sebagai Directed Acyclic Graph.

Node:

PlannedOperation

Edge:

operation A harus selesai sebelum operation B

Contoh:

RemoveFile(x/y/z)
→ RemoveEmptyDirectory(x/y)

Graph harus acyclic.

Jika Planner menemukan cycle, plan harus ditolak.

Planner tidak boleh mencoba menyelesaikan cycle dengan arbitrary ordering.

16. Dependency Reasons

Setiap dependency harus mempunyai reason.

Contoh:

ParentAfterChild

SharedResource

TargetOrdering

MaintenancePrerequisite

VerificationDependency

Dependency reason berguna untuk:

debugging

explain command

telemetry

test

future planner optimization

17. Conflict Types

Planner minimal harus mengenali:

same operation duplicate

same path conflicting operation

parent-child conflict

same target conflicting maintenance

resource conflict

budget conflict

generation conflict

unsupported operation conflict

Contoh:

RemoveFile(x)

RemoveFile(x)

duplicate.

Contoh lain:

RemoveFile(x)

RemoveDirectory(x)

conflict.

18. Conflict Resolution

Planner tidak boleh diam-diam memilih salah satu operation ketika conflict ditemukan.

Default behavior:

reject plan

atau remove duplicate jika duplicate memang secara eksplisit didefinisikan sebagai safe deduplication.

Untuk conflict nyata, hasil:

PlanningConflict

Plan tidak boleh dieksekusi.

19. Budget

Planner harus menghormati CleanupBudget.

Budget minimal:

max_operations

max_bytes

max_duration

max_metadata_cost jika relevan

Budget bukan sekadar limit Executor.

Planner harus menghitung estimasi sebelum authorization.

Jika candidate melebihi budget, planner harus menghasilkan hasil yang jelas.

Pilihan yang dapat digunakan:

truncate deterministically

defer remainder

reject plan

Pilihan harus ditentukan oleh policy/config.

20. Deterministic Budget Selection

Jika hanya sebagian candidate dapat diproses karena budget, pemilihan harus deterministik.

Contoh:

urutkan candidate

ambil sampai max_operations

ambil sampai max_bytes

candidate yang tersisa menjadi Deferred

Jangan menggunakan urutan filesystem discovery.

Jangan memilih secara random.

Jangan memilih berdasarkan thread arrival order.

21. Byte Budget

Estimated bytes harus berasal dari metadata candidate.

Planner tidak boleh membaca ulang arbitrary filesystem hanya untuk membuat plan jika informasi tersebut sudah tersedia.

Jika size tidak diketahui atau stale:

planner dapat menolak candidate

atau memberikan unknown cost

tetapi Executor tidak boleh menganggap unknown sebagai zero.

22. Unknown Cost

Unknown cost harus direpresentasikan secara eksplisit.

Contoh:

Known(bytes=4096)

Unknown

Tidak boleh:

Unknown → 0

Karena hal tersebut dapat membuat budget enforcement salah.

Jika policy mensyaratkan known size, candidate Unknown harus ditolak.

23. Operation Count Budget

Planner menghitung jumlah PlannedOperation.

Jika:

max_operations = 5000

dan terdapat 12000 candidate,

plan tidak boleh menghasilkan 12000 operation lalu berharap Executor berhenti pada 5000.

Planner harus membuat plan yang sudah mematuhi limit.

24. Duration Budget

Planner dapat menggunakan estimated execution cost.

Namun estimation tidak boleh dianggap sebagai guarantee.

Executor tetap wajib mempunyai runtime timeout dan budget enforcement.

Planner hanya membuat plan yang masuk batas yang telah disepakati.

25. Planner Tidak Menentukan Runtime Readiness

Planner tidak boleh memutuskan:

screen sedang off

thermal aman

device idle

user unlocked

storage tersedia

Hal tersebut merupakan responsibility Runtime, Scheduler, dan Platform snapshot.

Planner hanya menggunakan snapshot yang diberikan.

Jika snapshot tidak sesuai generation, plan stale.

26. Config Generation

Planner harus menyimpan ConfigGeneration pada plan.

Jika config berubah setelah plan dibuat:

plan lama tidak boleh digunakan untuk destructive execution.

Scheduler harus menandainya Stale.

Plan baru harus dibuat menggunakan ConfigSnapshot baru.

27. Catalog Generation

Target catalog dapat berubah karena:

package install

package uninstall

user state

storage state

mount change

package metadata update

Planner harus menyimpan CatalogGeneration.

Jika generation berubah sebelum execution:

plan menjadi Stale.

28. Platform Generation

Platform state juga dapat berubah.

Contoh:

storage

thermal state

user state

mount state

device capability

Planner harus mencatat PlatformGeneration atau equivalent snapshot identity.

Perubahan yang memengaruhi operation harus membuat plan stale.

29. Maintenance Operations

Planner harus membedakan cleanup filesystem dari maintenance operation.

Contoh:

RemoveFile

dan:

TrimFilesystem

tidak boleh menjadi node yang sama.

Maintenance operation biasanya mempunyai:

target device

required capability

precondition

estimated cost

exclusive resource

verification rule

30. Exclusive Operations

Beberapa operation dapat membutuhkan exclusive access.

Contoh:

filesystem maintenance

mount-level operation

storage-wide optimization

Planner harus membuat resource dependency.

Contoh:

TrimFilesystem(device X)

tidak boleh berjalan bersamaan dengan operation lain yang menurut platform contract membutuhkan exclusive filesystem state.

31. Operation Scope

Setiap operation harus memiliki scope eksplisit.

Contoh:

PackageScope

UserScope

TargetScope

FilesystemScope

DeviceScope

Planner tidak boleh menghasilkan operation yang scope-nya lebih luas daripada candidate dan authorization.

Candidate pada:

package cache

tidak boleh berubah menjadi:

entire filesystem maintenance

32. Scope Escalation

Scope escalation adalah security violation.

Contoh:

Candidate:

/data/user/0/package/cache/a

Plan:

RemoveFile(/data/user/0/package/cache/a)

valid.

Candidate yang sama tidak boleh menghasilkan:

RemoveTree(/data/user/0/package)

tanpa explicit policy dan authorization yang berbeda.

Planner harus memastikan operation scope ≤ authorized scope.

33. Path Representation

Planner menggunakan RelativePath dan TargetId.

Planner tidak menjadikan absolute path sebagai authority.

Absolute path hanya dapat muncul pada:

diagnostics

human-readable explain output

platform-specific adapter boundary

Bahkan pada diagnostics, path harus mengikuti logging policy.

34. Operation Reason

Setiap operation harus memiliki reason code.

Contoh:

ExpiredByAge

ExceededRetention

TemporaryArtifact

PolicySelected

MaintenanceRequired

Reason harus berasal dari policy/planning decision, bukan Executor.

Hal ini memungkinkan explain command menjawab:

“Kenapa object ini masuk plan?”

35. Explainability

Planner harus dapat menjelaskan:

candidate berasal dari target mana

policy rule mana yang memilihnya

operation apa yang direncanakan

berapa estimated bytes

dependency apa yang dimiliki

kenapa operation ditolak

kenapa candidate deferred

Planner metadata harus cukup untuk menghasilkan explanation tanpa menjalankan operation.

36. Partial Plan

Planner boleh menghasilkan partial plan hanya jika semantics-nya eksplisit.

Contoh:

5000 operation budget

10000 candidate

Plan:

5000 planned

5000 deferred

Deferred candidate tidak dianggap approved for execution.

Job berikutnya dapat melakukan scan/plan baru.

Jangan menyimpan deferred candidate sebagai implicit authorization.

37. Plan Immutability

Setelah Plan dibuat:

operations tidak berubah

dependencies tidak berubah

budget reservation tidak berubah

generation tidak berubah

target scope tidak berubah

Jika ada perubahan:

buat Plan baru.

Hal ini penting agar Authorization dapat mengotorisasi object yang benar-benar akan dieksekusi.

38. Plan Serialization

Jika plan perlu disimpan atau dikirim melalui IPC, gunakan DTO khusus.

Jangan serialize internal domain object secara langsung.

Serialized plan harus memiliki:

protocol version

plan identity

job identity

generation

operation type

typed identifiers

bounded fields

integrity metadata jika diperlukan

Deserializer harus tetap memvalidasi invariant.

39. Plan Expiration

AuthorizedPlan harus memiliki expiration atau validity boundary bila diperlukan.

Planner menghasilkan plan timestamp/monotonic reference melalui Clock abstraction.

Executor tidak boleh menjalankan plan yang sudah melewati validity window.

Expired plan:

Stale

bukan:

retry silently.

40. Cancellation During Planning

Planner harus cooperative terhadap cancellation.

Cancellation diperiksa:

sebelum planning

antara batch candidate

sebelum graph construction

sebelum final plan creation

Jika cancellation terjadi:

planner berhenti

tidak membuat executable plan

job menjadi Cancelled atau Deferred sesuai scheduler semantics

41. Bounded Planning

Planner harus mempunyai limit terhadap:

candidate count

operation count

dependency count

graph size

memory usage

path length

reason metadata

Plan yang terlalu besar harus ditolak atau dipecah menggunakan semantics yang telah ditentukan.

Tidak boleh ada unbounded graph construction.

42. Graph Validation

Sebelum Plan diterima:

semua OperationId unik

semua dependency mengarah ke operation yang ada

tidak ada self-dependency

tidak ada cycle

semua operation mempunyai target

semua operation mempunyai operation type

semua expected identity valid

semua generation konsisten

semua budget berada dalam batas

Semua invariant harus diverifikasi sebelum Authorization.

43. Topological Ordering

Executor sebaiknya menerima order yang sudah ditentukan Planner.

Planner melakukan topological sort terhadap dependency graph.

Jika terdapat lebih dari satu valid ordering, gunakan deterministic tie-breaker.

Contoh:

OperationId ascending

atau comparator operation yang ditentukan.

Dengan demikian dua execution terhadap input yang sama menghasilkan ordering yang sama.

44. Failure pada Graph

Jika graph memiliki cycle:

PlanningCycleDetected

Jika dependency missing:

InvalidPlan

Jika operation conflict:

PlanningConflict

Jika budget tidak cukup:

BudgetExceeded

Jika generation berubah:

Stale

Planner tidak boleh menghasilkan plan parsial yang tampak executable setelah failure.

45. Authorization Boundary

Planner berhenti sebelum authorization.

Planner menghasilkan:

PlannedPlan

Authorization menghasilkan:

AuthorizedPlan

Perbedaan penting:

PlannedPlan = apa yang ingin dilakukan sistem.

AuthorizedPlan = apa yang diizinkan dilakukan sistem.

Executor hanya menerima AuthorizedPlan.

46. Authorization Tidak Mengubah Plan

Authorization tidak boleh memodifikasi plan secara diam-diam.

Jika authorization ingin mengurangi operation:

buat AuthorizedPlan baru yang immutable dengan subset operation yang memang authorized.

Namun idealnya Planner sudah menghasilkan plan sesuai policy.

Authorization hanya memverifikasi:

scope

policy

capability

generation

budget

request identity

permission

47. Planner dan Safety

Planner boleh menggunakan hasil SafetyValidatedCandidate.

Namun Planner tidak boleh menganggap safety validation tersebut berlaku selamanya.

SafetyValidatedCandidate adalah snapshot.

Final Safety Gate tetap wajib sebelum mutation.

Planner tidak boleh membuat shortcut:

“sudah safety validated, jadi Executor tidak perlu revalidate.”

48. Planner dan Filesystem

Planner sebisa mungkin tidak melakukan filesystem mutation.

Read-only metadata lookup hanya boleh dilakukan jika memang dibutuhkan dan harus melalui abstraction.

Planner tidak boleh:

unlink

rename

chmod

chown

mount

umount

write sysfs

execute shell

Planner adalah decision construction layer.

50. Property Tests

Property penting:

input sama menghasilkan plan sama

dependency graph selalu valid

plan tidak melebihi operation budget

plan tidak melebihi byte budget

51. Fuzz Testing

Fuzz input:

candidate metadata

relative paths

operation combinations

dependency graph

budget values

generation values

operation types

unknown enum values

very large candidate sets

Fuzz invariant:

tidak panic

tidak infinite loop

tidak unbounded allocation

tidak menghasilkan graph invalid sebagai valid

tidak menghasilkan operation di luar scope

tidak menghasilkan mutation

52. Performance

Planner harus bekerja dalam memory budget yang terukur.

Untuk jumlah candidate besar:

gunakan streaming jika memungkinkan

hindari duplicate copy

gunakan bounded collections

gunakan stable ordering strategy

batasi dependency expansion

Planner tidak boleh mengorbankan safety hanya demi throughput.

Jika resource tidak cukup:

PlanningResourceLimit

bukan:

continue without validation.

53. Observability

Planner harus menghasilkan telemetry:

candidate count

selected count

deferred count

rejected count

estimated bytes

operation count

dependency count

planning duration

budget utilization

conflict count

stale detection

reason distribution

Tidak perlu mencatat seluruh path jika tidak diperlukan.

54. Audit Trail

Plan harus dapat direkonstruksi secara konseptual.

Audit metadata minimal:

JobId

PlanId

ConfigGeneration

CatalogGeneration

PlatformGeneration

planner version

candidate source

operation count

budget

Jika audit persistence digunakan, data harus bounded dan tidak menjadi dependency untuk safety correctness.

55. Planner Version

Planner behavior dapat berubah antar versi implementation.

Plan metadata sebaiknya menyimpan planner version.

Jika format atau semantics berubah secara incompatible:

plan lama tidak boleh dieksekusi oleh Executor baru tanpa compatibility contract.

Lebih aman:

mark stale

re-plan

authorize ulang.

56. Scheduler Integration

Scheduler bertanggung jawab:

memasukkan job ke Planning

memberikan resource

menghentikan planning ketika cancelled

menerima PlanningResult

mengirim plan ke Authorization

Planner tidak boleh mengubah JobState secara langsung.

Planner hanya mengembalikan result.

57. Error Ownership

Planner menghasilkan typed errors.

Scheduler memutuskan job state.

Contoh:

PlanningConflict
→ Failed

BudgetExceeded
→ Deferred atau CompletedPartial sesuai policy

Cancelled
→ Cancelled

Stale
→ Stale

ResourceLimit
→ Deferred atau Failed

Planner tidak boleh memanggil Scheduler untuk mengubah state secara langsung.

58. Complete Planning Flow

Job:

CheckingReadiness

→ Preparing

→ Scanning

→ Validating

→ Planning

Planner menerima immutable inputs.

Candidate diurutkan.

Candidate conflict diperiksa.

Budget dihitung.

Operation dibuat.

Dependency graph dibuat.

Graph divalidasi.

Topological ordering dibuat.

Plan immutable dibuat.

Plan dikirim ke Authorization.

Jika semua berhasil:

Planning selesai.

61. Keputusan Arsitektur

Planner adalah pure decision-construction layer.

Planner tidak melakukan mutation.

Planner tidak memberikan authorization.

Planner tidak mengambil keputusan runtime readiness.

PlannedOperation harus typed dan immutable.

Operation dependency direpresentasikan sebagai DAG.

Child operation harus mendahului parent operation.

Conflict harus ditolak, bukan diselesaikan secara diam-diam.

Budget harus diterapkan saat planning.

Partial selection harus deterministic.

Plan menyimpan ConfigGeneration, CatalogGeneration, dan PlatformGeneration.

Stale generation menghasilkan plan yang tidak executable.

Executor menerima hanya AuthorizedPlan dengan ordering yang sudah ditentukan.

Final Safety Gate tetap wajib walaupun Planner menggunakan SafetyValidatedCandidate.

Dengan demikian Planner menjadi batas yang jelas antara “object yang ditemukan dan diizinkan oleh policy” dengan “operasi konkret yang nantinya dapat dimintakan authorization dan dieksekusi”.
