# 1103. Kernel dan System Maintenance

Lanjut.

Setelah `runtime/` dan event loop, kita masuk ke bagian yang paling sensitif berikutnya:

```text
src/kernel/
```

Tetapi sebelum mendesain API, kita harus menetapkan satu prinsip:

> **System maintenance bukan filesystem cleanup.**

Filesystem cleanup melakukan operasi terhadap object:

```text
file
directory
directory entry
```

Sedangkan kernel/system maintenance mengubah atau meminta perubahan terhadap:

```text
filesystem state
block-device state
memory compression state
scheduler state
I/O scheduling state
CPU governor
cgroup placement
kernel maintenance knobs
```

Karena itu kedua domain ini tidak boleh dilebur menjadi satu `Executor`.

---

# 1104. Mengapa kernel layer harus dipisahkan?

Jika kita membuat:

```rust
enum Operation {
    RemoveFile,
    RemoveDirectory,
    Trim,
    ZramReset,
    F2fsGc,
    SetGovernor,
    SetIoPriority,
}
```

maka secara konseptual semua terlihat sama.

Padahal semantics-nya sangat berbeda.

`RemoveFile`:

```text
object-level destructive operation
```

sedangkan:

```text
FITRIM
F2FS GC
ZRAM maintenance
scheduler tuning
governor changes
```

adalah:

```text
system-state operation
```

Maka:

```text
filesystem executor
        ≠
kernel maintenance executor
```

---

# 1105. Struktur `kernel/`

Struktur awal:

```text
src/kernel/
├── mod.rs
├── capabilities.rs
├── maintenance.rs
├── precondition.rs
├── operation.rs
├── executor.rs
├── verifier.rs
├── error.rs
│
├── f2fs.rs
├── trim.rs
├── zram.rs
├── scheduler.rs
├── io.rs
├── governor.rs
└── cgroup.rs
```

Pembagian:

```text
capabilities.rs
    capability detection

maintenance.rs
    maintenance orchestration

precondition.rs
    runtime/system checks

operation.rs
    typed maintenance operations

executor.rs
    actual kernel/system calls

verifier.rs
    post-condition verification

f2fs.rs
    F2FS-specific operations

trim.rs
    FITRIM

zram.rs
    ZRAM

scheduler.rs
    CPU scheduling policy

io.rs
    I/O priority / scheduler interaction

governor.rs
    CPU frequency governor

cgroup.rs
    cgroup placement/control
```

# 1106. Jangan membuat `KernelManager` God Object

Jangan:

```rust
pub struct KernelManager {
    f2fs: ...,
    zram: ...,
    trim: ...,
    cgroup: ...,
    governor: ...,
    scheduler: ...,
    io: ...,
}
```

lalu:

```rust
kernel_manager.optimize_everything();
```

Ini terlalu tinggi levelnya dan membuat semantics sulit diaudit.

Lebih baik:

```text
MaintenancePlanner
        ↓
MaintenanceOperation
        ↓
MaintenanceAuthorization
        ↓
MaintenanceExecutor
        ↓
MaintenanceVerifier
```

dengan adapter per subsystem.

---

# 1107. Maintenance bukan "optimize"

Hindari API seperti:

```rust
optimize_system();
```

Karena kata `optimize` tidak memiliki semantics yang dapat diaudit.

Gunakan operasi eksplisit:

```rust
TrimFilesystem
RunF2fsMaintenance
RefreshZram
ApplyIoPolicy
ApplyCpuGovernor
ApplyCgroupPolicy
```

Setiap operation harus mempunyai:

```text
precondition
capability
authorization requirement
side effects
verification
failure semantics
```

# 1108. `MaintenanceOperation`

Model awal:

```rust
pub enum MaintenanceOperation {
    Trim(TrimRequest),
    F2fs(F2fsRequest),
    Zram(ZramRequest),
    Io(IoRequest),
    Scheduler(SchedulerRequest),
    Governor(GovernorRequest),
    Cgroup(CgroupRequest),
}
```

Namun enum ini bukan command langsung ke kernel.

Ia adalah:

```text
planned operation
```

yang masih harus melewati:

```text
authorization
precondition
execution
verification
```

# 1109. Operation identity

Setiap operation membutuhkan ID:

```rust
pub struct MaintenanceOperationId(pub u64);
```

dan:

```rust
pub struct PlannedMaintenance {
    pub id: MaintenanceOperationId,
    pub operation: MaintenanceOperation,
    pub reason: MaintenanceReason,
```

Ini penting untuk audit.

Contoh:

```text
operation=42
type=Trim
reason=post_cleanup
capability=FilesystemTrim
```

Jangan hanya:

```rust
reason: String
```

Gunakan typed enum:

```rust
pub enum MaintenanceReason {
```

Dengan demikian policy dapat membedakan:

```text
scheduled maintenance
```

```text
manual maintenance
```

# 1111. Capability detection

Kernel operation tidak boleh diasumsikan tersedia.

Gunakan:

```rust
pub struct KernelCapabilities {
    pub trim: TrimCapability,
    pub f2fs: F2fsCapability,
    pub zram: ZramCapability,
    pub io: IoCapability,
    pub scheduler: SchedulerCapability,
    pub governor: GovernorCapability,
    pub cgroup: CgroupCapability,
}
```

Jangan:

```text
if android_api >= 35 {
    f2fs = true
}
```

Karena capability kernel/device/config dapat berbeda walaupun Android API sama.

---

# 1112. Capability berarti "dapat digunakan"

Bedakan:

```text
feature exists
```

dengan:

```text
feature is safely usable
```

Contoh:

```text
F2FS interface exists
```

belum berarti:

```text
cleaner boleh menggunakannya
```

Capability harus mempertimbangkan:

```text
kernel support
filesystem type
required interface
permissions
device identity
runtime state
```

# 1113. Capability states

Gunakan:

```rust
pub enum CapabilityState {
    Available,
    Unavailable,
    Unsupported,
    PermissionDenied,
    Degraded,
    Unknown,
}
```

Ini lebih informatif daripada:

```rust
bool
```

Contoh:

```text
TRIM:
    Available

F2FS:
    Unsupported

ZRAM:
    PermissionDenied
```

---

# 1114. `Unknown` harus fail closed

Jika capability tidak dapat dipastikan:

```text
Unknown
```

jangan diubah menjadi:

```text
Available
```

Untuk destructive/system-changing maintenance:

```text
Unknown → skip/defer
```

# 1115. Capability snapshot

Capability detection dilakukan saat startup:

```text
startup
   ↓
detect
   ↓
KernelCapabilitySnapshot
```

Tetapi capability tertentu dapat berubah.

Maka gunakan generation:

```rust
pub struct CapabilityGeneration(pub u64);
```

Contoh:

```text
generation 5
```

setelah system state berubah:

```text
generation 6
```

# 1116. Capability refresh

Tidak perlu refresh seluruh capability setiap event.

Gunakan invalidation:

```text
StorageChanged
    ↓
invalidate storage-dependent capabilities
```

Kemudian subsystem melakukan refresh ketika dibutuhkan.

# 1117. Capability detection tidak boleh melakukan maintenance

Salah:

```text
detect_f2fs()
    ↓
if available
    ↓
run_gc()
```

Benar:

```text
detect_f2fs()
    ↓
F2fsCapability::Available
```

Kemudian planner memutuskan apakah maintenance diperlukan.

```text
filesystem type
```

Jika:

```text
ext4
```

maka:

# 1120. Maintenance target

Jangan menerima arbitrary path dari IPC:

```rust
Trim(PathBuf)
```

Gunakan:

```rust
pub struct MaintenanceTarget {
    pub target_id: TargetId,
    pub device: TrustedDevice,

```

Resolver internal yang mengubah:

```text
TargetId
```

menjadi:

```text
TrustedDevice
```

# 1121. Path bukan authority

Prinsip dari filesystem layer tetap berlaku:

```text
Path
    = description

FD / trusted device identity
    = authority
```

Dokumen filesystem sebelumnya sudah menetapkan bahwa destructive filesystem access harus menggunakan trusted root, FD-relative traversal, identity/type/device validation, dan bukan `PathBuf` sebagai security boundary.

Prinsip yang sama diterapkan ke maintenance.

---

# 1122. `Trim`

FITRIM adalah operasi terhadap filesystem yang meminta kernel melakukan discard/trim terhadap range yang dapat dibuang.

Secara arsitektur:

```text
Target
   ↓
resolve filesystem
   ↓
validate filesystem/device
   ↓
check TRIM capability
   ↓
build TrimRequest
   ↓
authorize
   ↓
execute
   ↓
verify/report
```

Tidak:

```text
cleanup
   ↓
shell("fstrim ...")
```

---

# 1123. Jangan menggunakan shell untuk maintenance

Hindari:

```rust
Command::new("fstrim")
```

atau:

```rust
sh -c "..."
```

untuk privileged maintenance.

Masalahnya:

```text
PATH resolution
environment
argument injection
binary replacement
SELinux context
error mapping
process lifecycle
```

Gunakan syscall/ioctl atau adapter native yang sesuai.

---

# 1124. `TrimRequest`

Model:

```rust
pub struct TrimRequest {
    pub target: TrustedFilesystem,
    pub minimum_extent: u64,
}
```

Jangan menerima:

```rust
device_path: String
```

dari caller.

---

# 1125. Trim precondition

Sebelum execute:

```text
filesystem mounted?
filesystem type supported?
target identity unchanged?
capability available?
screen off?
thermal safe?
storage state valid?
```

Policy akhir bergantung pada deployment.

Namun executor harus tetap memvalidasi invariant yang menjadi tanggung jawabnya.

---

# 1126. Trim bukan delete

Ini penting:

```text
delete file
```

mengubah namespace filesystem.

Sedangkan:

```text
FITRIM
```

meminta filesystem/device melepaskan block range yang tidak lagi digunakan.

Karena itu:

```text
cleanup deletion
```

dapat terjadi tanpa:

```text
TRIM
```

dan sebaliknya.

---

# 1127. Post-cleanup TRIM

Jangan otomatis:

```text
delete 1 file
→ FITRIM
```

karena terlalu mahal.

Policy sebaiknya menggunakan threshold:

```text
bytes_deleted >= threshold
```

atau:

```text
cleanup operation count >= threshold
```

atau:

```text
scheduled maintenance window
```

---

# 1128. Trim budget

Maintenance juga membutuhkan budget.

Contoh:

```rust
pub struct MaintenanceBudget {
    pub max_duration: Duration,
    pub max_operations: u32,
}
```

Jangan mengasumsikan:

```text
maintenance = unlimited
```

# 1129. F2FS

F2FS-specific maintenance harus dipisahkan dari generic filesystem maintenance.

```text
F2FS
    ├── capability
    ├── interface discovery
    ├── precondition
    ├── operation
    ├── verification
    └── error mapping
```

Jangan membuat:

```rust
if fs_type == "f2fs" {
    write("/sys/...")
}
```

langsung dari scheduler.

---

# 1130. F2FS interface discovery

F2FS operation membutuhkan interface yang benar-benar tersedia pada device.

Maka capability detection:

```text
filesystem = F2FS
        ↓
locate supported maintenance interface
        ↓
validate type/permissions
        ↓
F2fsCapability
```

Jika interface tidak ada:

```text
Unsupported
```

bukan:

```text
panic
```

# 1131. `gc_urgent`

Jika deployment memilih memakai F2FS urgent GC, operation harus typed:

```rust
pub struct F2fsGcRequest {
    pub target: TrustedFilesystem,
    pub mode: F2fsGcMode,
}
```

misalnya:

```rust
pub enum F2fsGcMode {
    Conservative,
    Urgent,
}
```

Tetapi jangan langsung mengekspos string kernel knob ke caller.

---

# 1132. Jangan expose raw kernel knobs

Jangan:

```rust
SetSysfs {
    path: PathBuf,
    value: String,
}
```

Ini pada dasarnya adalah:

```text
privileged arbitrary write primitive
```

dan sangat berbahaya.

Gunakan:

```rust
F2fsGcRequest
GovernorRequest
IoRequest
```

dengan field yang tervalidasi.

---

# 1133. Maintenance interface authority

Setiap adapter hanya boleh menulis ke interface yang sudah dikompilasi/didefinisikan sebagai trusted.

Misalnya:

```rust
struct F2fsInterface {
    fd: OwnedFd,
}
```

atau typed trusted path yang dibuat internal.

Tidak boleh:

```rust
F2fsInterface::from_user_path(...)
```

---

# 1134. F2FS operation tidak boleh diasumsikan reversible

Ini penting.

Jika:

```text
gc_urgent
```

sudah diminta:

```text
kernel may continue work
```

setelah syscall kembali.

Jangan menjanjikan:

```text
rollback
```

seolah-olah database transaction.

Maka semantics:

```text
apply
   ↓
observe result
   ↓
report
```

bukan:

```text
apply
   ↓
rollback
```

kecuali interface memang menyediakan mekanisme restoration yang nyata.

---

# 1135. ZRAM

ZRAM harus diperlakukan sangat hati-hati.

Ini bukan:

```text
"clear cache"
```

ZRAM adalah compressed RAM block device dan state-nya berhubungan langsung dengan memory subsystem.

Maka jangan membuat:

```text
cleanup profile = deep
    ↓
reset zram
```

secara otomatis.

---

# 1136. ZRAM operation harus explicit

Gunakan:

```rust
pub enum ZramOperation {
    ReadStatus,
    Reset,
}
```

`Reset` harus memiliki authorization capability tersendiri.

---

# 1137. ZRAM precondition

Sebelum reset:

```text
zram exists
zram is known device
swap relationship known
current state safe
policy allows reset
```

Jika state tidak diketahui:

```text
defer
```

---

# 1138. ZRAM reset bukan normal cleanup

Saya merekomendasikan:

```text
normal scheduled cleanup
    ✗ ZRAM reset
```

dan:

```text
explicit maintenance profile
    ✓ ZRAM reset
```

Dengan begitu tidak ada kejutan bahwa cache cleaner tiba-tiba memodifikasi memory subsystem.

---

# 1139. ZRAM verification

Setelah operation:

```text
read zram state
```

dan pastikan state sesuai expected post-condition.

Contoh:

```text
before:
active

operation:
reset

after:
reset/idle
```

Jika hasil tidak dapat diverifikasi:

```text
Unknown
```

bukan:

```text
Success
```

---

# 1140. CPU governor

Governor juga merupakan system state.

Jangan:

```rust
set_governor("performance")
```

dari arbitrary string.

Gunakan:

```rust
pub enum CpuGovernor {
    Performance,
    Powersave,
    Schedutil,
}
```

Tetapi daftar valid tetap harus capability-driven.

---

# 1141. Governor policy

Cleaner tidak seharusnya mengubah governor hanya karena:

```text
cleanup started
```

kecuali deployment memang mendefinisikan policy tersebut.

Lebih aman:

```text
cleanup
    ↓
scheduler priority / IO priority
```

daripada mengubah global CPU governor.

---

# 1142. Jika governor diubah, wajib restoration

Jika:

```text
before = Schedutil
```

dan maintenance:

```text
temporary = Performance
```

maka:

```text
apply
   ↓
operation
   ↓
restore = Schedutil
```

Harus menggunakan RAII-like guard:

```rust
pub struct GovernorGuard {
    original: GovernorState,
}
```

---

# 1143. Restoration harus terjadi pada error

Tidak hanya:

```text
success
```

tetapi juga:

```text
failure
panic
cancellation
shutdown
```

Konsep:

```text
acquire temporary state
       ↓
RAII guard
       ↓
operation
       ↓
guard Drop → restore
```

Namun restoration error harus dicatat secara eksplisit.

---

# 1144. Restoration failure

Jika:

```text
temporary governor = Performance
```

kemudian restore gagal:

```text
restore → error
```

jangan laporkan:

```text
job = Success
```

Gunakan:

```text
CompletedWithDegradedState
```

atau failure class yang sesuai.

---

# 1145. I/O priority

I/O tuning juga harus typed.

Misalnya:

```rust
pub enum IoPriority {
    Idle,
    BestEffort { class: u8, level: u8 },
}
```

Tetapi executor harus memvalidasi range.

Jangan menerima:

```rust
class: u8
level: u8
```

tanpa validation.

---

# 1146. I/O priority scope

Jangan mengubah priority seluruh system jika tidak diperlukan.

Lebih baik:

```text
maintenance worker
    ↓
specific process/thread
```

daripada:

```text
system-wide priority
```

Jika system-wide modification memang diperlukan, harus menjadi operation dengan authorization terpisah.

---

# 1147. Scheduler policy

`SCHED_IDLE` dapat berguna untuk pekerjaan background.

Namun scheduler policy harus dibedakan dari:

```text
CPU governor
```

Model:

```rust
pub enum CpuSchedulingPolicy {
    Normal,
    Idle,
}
```

---

# 1148. Worker scheduling

Cleaner worker dapat dijalankan dengan:

```text
low CPU priority
+
low I/O priority
```

agar maintenance tidak mengganggu foreground workload.

Ini lebih baik daripada mengubah system-wide scheduler state.

---

# 1149. cgroup

cgroup juga harus dianggap sebagai resource boundary.

Cleaner sebaiknya dapat ditempatkan pada:

```text
dedicated cgroup
```

dengan limits:

```text
CPU
IO
memory
```

tetapi cgroup setup harus terjadi pada lifecycle yang tepat.

---

# 1150. cgroup ownership

Jangan mengubah cgroup milik aplikasi lain.

Cleaner hanya boleh:

```text
create/own cleaner cgroup
```

atau:

```text
join explicitly designated maintenance cgroup
```

yang identity-nya telah divalidasi.

---

# 1151. cgroup path

Jangan menerima:

```rust
CgroupPath(String)
```

dari IPC.

Gunakan:

```rust
pub struct TrustedCgroup {
    fd: OwnedFd,
    identity: CgroupIdentity,
}
```

Jika kernel/environment tidak mendukung model FD yang dibutuhkan, gunakan resolver internal dengan strict fixed namespace.

---

# 1152. cgroup setup timing

Idealnya:

```text
daemon startup
    ↓
create/resolve maintenance cgroup
    ↓
validate limits
    ↓
workers join
```

Bukan:

```text
cleanup sedang berjalan
    ↓
buat cgroup
    ↓
pindahkan worker
```

karena state execution menjadi lebih kompleks.

---

# 1153. cgroup failure

Jika cgroup optional:

```text
cgroup unavailable
    ↓
degraded
```

tetapi jangan:

```text
cgroup unavailable
    ↓
worker mendapat full system priority
```

Jika deployment mengharuskan cgroup sebagai safety requirement:

```text
not available
    ↓
maintenance not ready
```

```rust
pub struct MaintenanceReadiness {
```

dan:

# 1155. Precondition vs Policy

Ini harus dipisahkan.

### Policy

```text
"TRIM dijalankan setelah >1 GiB data dibersihkan."
```

### Precondition

```text
"target filesystem masih sama."
```

Policy adalah keputusan bisnis/application.

Precondition adalah invariant execution.

---

# 1156. Executor tidak membuat policy

Executor tidak boleh:

```rust
if bytes_deleted > 1_GIB {
    trim();
}
```

Itu scheduler/planner.

Executor hanya:

```text
given authorized TrimOperation
    ↓
validate executor preconditions
    ↓
execute
```

---

# 1157. Maintenance planning

Flow:

```text
CleanupResult
     ↓
MaintenancePolicy
     ↓
MaintenanceCandidate
     ↓
MaintenancePlanner
     ↓
MaintenancePlan
```

Misalnya:

```text
deleted = 2.4 GiB
filesystem = F2FS
trim capability = available
runtime = ready
```

menghasilkan:

```text
Trim
```

Tetapi:

```text
deleted = 100 MiB
```

mungkin:

```text
NoMaintenance
```

---

# 1158. Maintenance plan

Gunakan:

```rust
pub struct MaintenancePlan {
    pub operations: Vec<PlannedMaintenance>,
    pub generation: u64,
}
```

Plan tetap immutable setelah authorization.

---

# 1159. Authorization

Authorization tetap dilakukan sebelum execution.

Flow:

```text
MaintenancePlan
      ↓
RequiredCapabilities
      ↓
CallerCapabilities
      ↓
authorize
```

Jika:

```text
plan:
    Trim
    ZramReset
```

dan caller hanya memiliki:

```text
Trim
```

maka untuk v1:

```text
whole plan rejected
```

bukan silently strip ZRAM.

Ini konsisten dengan prinsip authorization ganda yang sudah ditetapkan di `app/`: request authorization dan plan authorization harus dipisahkan.

---

# 1160. Maintenance authorization bukan Linux UID check saja

Jangan:

```rust
if uid == 0 {
    allow();
}
```

Semata.

Gunakan:

```text
peer identity
+
daemon capability
+
operation capability
+
runtime state
```

Root caller tetap harus melewati daemon authorization boundary.

---

# 1161. Plan immutability

Setelah:

```text
authorized
```

jangan mengubah:

```text
MaintenancePlan
```

Misalnya:

```text
authorized:
    Trim(device A)
```

tidak boleh berubah menjadi:

```text
Trim(device B)
```

karena capability atau target harus tetap terikat dengan snapshot authorization.

# 1162. Maintenance execution context

Gunakan:

```rust
pub struct MaintenanceContext {
    pub operation_id: MaintenanceOperationId,
    pub target: TrustedMaintenanceTarget,
    pub capability_generation: CapabilityGeneration,
    pub cancellation: CancellationToken,
    pub deadline: MonotonicTimestamp,
}
```

---

# 1163. Cancellation

Cancellation harus diperiksa:

```text
before operation
```

dan pada boundary yang aman.

Namun jangan mencoba membatalkan syscall yang tidak dapat dibatalkan secara aman.

Contoh:

```text
ioctl
```

sudah dipanggil:

```text
cannot necessarily rollback
```

Maka cancellation semantics harus:

```text
cancel before syscall
```

bukan:

```text
cancel halfway through kernel operation
```

---

# 1164. Maintenance timeout

Setiap operation memiliki:

```rust
pub struct MaintenanceTimeout {
    pub deadline: MonotonicTimestamp,
}
```

Tetapi timeout tidak berarti:

```text
kill syscall
```

Timeout berarti:

```text
do not start next operation
```

dan jika current operation sudah berada di kernel:

```text
wait for safe return
```

sesuai kemampuan API.

---

# 1165. Operation ordering

Maintenance operations memiliki dependency.

Contoh:

```text
delete
   ↓
trim
```

harus:

```text
cleanup complete
    ↓
trim
```

Tidak:

```text
trim
    ↓
delete
```

karena block yang baru menjadi free belum tentu dapat di-trim sebelum deletion.

# 1166. Dependency graph

```text

    ↓

    ↓

```

Jika ada:

```text

```

policy menentukan apakah:

```text

```

atau:

```text
after trim
```

berdasarkan semantics deployment.

Jangan mengandalkan urutan vector secara implisit.

# 1167. Maintenance transaction

Jangan menyebut seluruh maintenance sebagai:

jika tidak ada rollback.

dengan:

# 1170. Verification

```text
→ automatically call Success
```

# 1171. Trim verification

Trim tidak selalu memiliki cara sederhana untuk membuktikan bahwa physical discard benar-benar selesai seperti yang diinginkan application.

Maka:

```text

```

dapat menjadi:

```text

```

daripada membuat klaim:

```text

```

# 1172. F2FS verification

```text

```

gunakan.

Jika tidak:

```text
Applied

```

Jangan membuat fake verification.

# 1173. ZRAM verification

ZRAM lebih mudah jika state interface dapat dibaca.

Sebelum:

```text

```

setelah:

```text

```

Kemudian:

```text
expected != actual
```

→ `VerificationFailed`.

# 1174. Governor verification

Sebelum:

```text

```

set:

```text
temporary = performance
```

setelah operation:

```text

```

Kemudian read kembali.

Jika:

```text

```

maka:

```text

```

Ini lebih serius daripada operation failure biasa.

# 1192. Cooldown

# 1270. Tahap berikutnya

Setelah `kernel/` selesai, saya **tidak** menyarankan langsung menulis implementasi.

Masih ada satu layer penting yang harus dipakukan:

```text
src/security/
```

atau security boundary lintas layer.

Dokumen berikutnya sebaiknya membahas:

```text
Security Architecture
    ├── process identity
    ├── SO_PEERCRED
    ├── UID/GID
    ├── SELinux assumptions
    ├── IPC authentication
    ├── authorization model
    ├── capability model
    ├── privilege separation
    ├── runtime file permissions
    ├── daemon lock
    ├── config trust boundary
    ├── symlink/path attacks
    ├── confused deputy
    ├── resource exhaustion
    ├── replay/duplicate commands
    ├── request limits
    ├── audit trail
    └── fail-closed behavior
```

Ini penting karena security saat ini sudah tersebar di `fs`, `IPC`, `app`, `authorization`, dan `kernel`.

Kita perlu menyatukannya menjadi satu **threat model dan security contract**, tanpa membuat `security/` menjadi God Module.

Setelah itu barulah kita dapat membuat **final module tree + trait/API contract + dependency graph**, dan baru dari sana masuk ke tahap implementasi Rust secara bertahap.
