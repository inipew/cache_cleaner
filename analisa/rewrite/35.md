Runtime Implementation Contract dan Integrasi Event-Driven

Setelah struktur application layer dan runtime event loop ditetapkan, tahap berikutnya bukan menambah subsystem baru secara sembarangan, tetapi menetapkan kontrak implementasi agar seluruh komponen dapat bekerja dalam satu event-driven control plane yang deterministik, aman, dan mudah diuji.

Runtime harus menjadi lapisan yang menghubungkan sumber event sistem dengan application controller dan scheduler.

Runtime tidak boleh menjadi tempat pengambilan keputusan kebijakan cleanup.

Runtime hanya bertugas menerima event, mendekode event, melakukan normalisasi, menjaga lifecycle resource, kemudian meneruskan event tersebut ke application layer.

Dengan demikian pembagian tanggung jawab tetap jelas:

Runtime menerima event.

ApplicationController menentukan tindakan aplikasi.

Scheduler menentukan kapan job dapat dijalankan.

Policy menentukan apa yang diperbolehkan.

Safety menentukan apakah operasi aman dilakukan.

Planner menentukan operasi konkret.

Executor melakukan operasi yang telah diotorisasi.

Filesystem dan kernel abstraction melakukan interaksi dengan sistem.

Tidak boleh ada jalur dari event loop langsung menuju executor.

Prinsip utama

Runtime harus bersifat event-driven.

Event loop tidak boleh melakukan pekerjaan cleanup secara langsung.

Event loop tidak boleh melakukan filesystem traversal yang berpotensi lama.

Event loop tidak boleh melakukan unlink, rename, truncate, mount operation, sysfs write, zram configuration, trim, atau operasi kernel maintenance lainnya.

Event loop juga tidak boleh menunggu worker selesai secara synchronous.

Semua pekerjaan yang berpotensi blocking atau memerlukan waktu signifikan harus dipindahkan ke worker atau job execution layer.

Event loop hanya mengelola control flow.

Event ordering

Event loop harus memiliki aturan ordering yang eksplisit.

Event yang berkaitan dengan lifecycle dan safety harus diproses lebih dahulu dibanding event pekerjaan biasa.

Prioritas minimum:

Shutdown

Fatal runtime event

Storage invalidation

User lock/unlock

Thermal safety event

Screen state

Configuration reload

Worker completion

IPC request

Timer

Background maintenance trigger

Tujuan ordering ini bukan untuk menjamin semua event diproses dalam urutan absolut yang sama pada setiap sistem.

Tujuannya adalah mencegah event maintenance biasa mengalahkan event yang membuat environment menjadi tidak aman.

Contoh:

Timer cleanup masuk.

Pada waktu hampir bersamaan storage berubah.

Runtime harus memastikan StorageChanged diproses sebelum scheduler menganggap timer tersebut sebagai izin untuk menjalankan cleanup.

Timer event tidak boleh dianggap sebagai authorization.

Timer hanya merupakan trigger.

Readiness harus diperiksa kembali setelah event diterima.

Event coalescing

Beberapa event dapat terjadi sangat cepat dan tidak semuanya perlu diproses satu per satu.

Contohnya:

ScreenOn

ScreenOn

ScreenOn

dapat direduksi menjadi satu state transition yang relevan.

Demikian pula:

StorageChanged

StorageChanged

MountChanged

dapat menyebabkan satu invalidation sequence jika state akhirnya sama-sama menunjukkan bahwa catalog lama tidak lagi dapat dipercaya.

Namun coalescing tidak boleh menghilangkan event yang mempunyai efek safety.

Shutdown tidak boleh di-coalesce menjadi event biasa.

Cancellation tidak boleh hilang hanya karena terdapat event lain.

Configuration reload harus tetap menghasilkan generation baru.

Worker completion tidak boleh dibuang apabila event tersebut diperlukan untuk mengubah state job.

State-based processing

Runtime sebaiknya tidak diperlakukan sebagai queue command sederhana.

Event harus menghasilkan perubahan state.

Sebagai contoh:

ScreenOn

mengubah runtime/application state menjadi ScreenOn.

Kemudian scheduler dapat mengetahui bahwa cleanup yang mensyaratkan ScreenOff tidak boleh dijalankan.

Ketika ScreenOff:

scheduler mendapatkan kesempatan untuk mengevaluasi kembali job yang tertunda.

Dengan demikian runtime tidak perlu mengirim command:

RunCleanupNow

Runtime hanya mengirim:

ScreenStateChanged(ScreenOff)

Scheduler kemudian mengambil keputusan.

Hal yang sama berlaku untuk thermal state.

Runtime tidak mengatakan:

StopCleanupJobBecauseThermalHigh

Runtime hanya mengatakan:

ThermalChanged(High)

Application layer menentukan bahwa active cleanup yang tidak aman harus dibatalkan atau dihentikan sesuai policy.

Separation antara event dan command

SystemEvent dan AppCommand memiliki fungsi berbeda.

SystemEvent adalah fakta yang berasal dari runtime atau sistem.

AppCommand adalah intent yang berasal dari user, CLI, IPC, scheduler, atau application logic.

Contoh:

SystemEvent::ScreenOn

SystemEvent::StorageChanged

SystemEvent::TimerElapsed

SystemEvent::Signal(SIGHUP)

sedangkan:

AppCommand::StartCleanup

AppCommand::CancelJob

AppCommand::ReloadConfig

AppCommand::Status

AppCommand::Explain

AppCommand::Shutdown

Runtime boleh menghasilkan AppCommand hanya untuk event lifecycle tertentu jika kontraknya memang ditetapkan.

Namun secara umum lebih baik:

Runtime → SystemEvent → ApplicationController

daripada:

Runtime → direct command → subsystem.

Tujuannya agar application state tetap menjadi single source of truth.

Timer contract

Timer tidak boleh menjadi scheduler itu sendiri.

Timer hanya menyediakan wake-up event.

Scheduler tetap memiliki responsibility untuk menentukan apakah sebuah job sudah eligible.

Contoh:

timer interval 6 jam tercapai.

Runtime menghasilkan:

TimerElapsed(timer_id)

Scheduler kemudian memeriksa:

Jika kondisi tidak terpenuhi, timer event hanya menghasilkan Deferred atau Noop.

Timer tidak boleh memaksa cleanup.

Timer drift

Periodic timer harus memiliki definisi drift yang jelas.

Jika timer seharusnya berjalan setiap enam jam, implementation tidak boleh secara sederhana melakukan:

next = now + interval

setelah setiap event apabila event dapat terlambat diproses.

Pendekatan tersebut dapat menyebabkan drift kumulatif.

Scheduler sebaiknya menggunakan logical schedule berdasarkan monotonic time atau wall-clock policy yang telah ditentukan.

Monotonic clock digunakan untuk interval dan timeout.

Wall clock digunakan untuk informasi waktu yang perlu direpresentasikan kepada user atau policy berbasis tanggal/waktu kalender.

Kedua clock tidak boleh dicampur secara sembarangan.

Minimal terdapat:

Dengan fake clock, test dapat mensimulasikan:

Signal handling

Signal handler tidak boleh melakukan pekerjaan berat.

Signal handler hanya boleh melakukan minimal notification kepada event loop.

SIGHUP berarti request reload configuration.

SIGTERM berarti request graceful shutdown.

SIGINT dapat diperlakukan sebagai shutdown request jika binary digunakan secara interactive.

SIGCHLD tidak boleh diasumsikan sebagai satu-satunya mekanisme worker state apabila worker dikelola oleh internal runtime abstraction.

Signal handler tidak boleh:

membaca configuration file

mengakses filesystem target

menghentikan executor secara langsung

melakukan logging kompleks

mengambil lock yang berpotensi blocking

melakukan allocation besar

memanggil arbitrary application logic

Semua pekerjaan tersebut dilakukan setelah signal diterima event loop.

Graceful shutdown

Shutdown harus memiliki lifecycle eksplisit.

State minimal:

Running

Stopping

Stopped

Ketika SIGTERM diterima:

Runtime menerima ShutdownRequested.

ApplicationController masuk ke state stopping.

Scheduler berhenti membuat job baru.

Pending jobs tidak dimulai.

Active job menerima cancellation request sesuai contract.

Worker diberi waktu untuk melakukan cooperative shutdown.

Event loop tetap hidup selama diperlukan untuk menerima worker completion atau timeout.

Setelah seluruh worker selesai atau grace period habis, runtime menutup resource.

Jika worker tidak dapat berhenti dalam grace period, runtime harus mengikuti shutdown policy yang sudah ditentukan.

Namun forced termination tidak boleh meninggalkan state seolah-olah job telah berhasil.

Job terakhir harus tercatat sebagai cancelled, interrupted, atau failed sesuai kondisi sebenarnya.

Shutdown idempotency

Shutdown request kedua tidak boleh menyebabkan state corruption.

Contoh:

SIGTERM

Tidak boleh terjadi double free.

Tidak boleh ada dua shutdown sequence berjalan bersamaan.

Tidak boleh ada job baru yang dibuat setelah shutdown state ditetapkan.

Ketika socket readable:

Kemudian menghasilkan application-level request.

Tidak boleh ada:

Semua request tetap melewati application flow.

Partial frame

Unix socket tidak menjamin satu read menghasilkan satu message.

Karena itu IPC runtime harus mendukung:

Parser harus mempertahankan buffer connection state.

Parser tidak boleh menganggap satu read sebagai satu command.

Backpressure

IPC writer juga harus memperhatikan partial write.

Jika socket tidak writable:

message harus tetap berada di bounded output buffer.

Output buffer harus memiliki batas.

Client yang tidak membaca response tidak boleh menyebabkan memory growth tanpa batas.

Jika buffer mencapai batas:

connection dapat ditutup secara terkontrol.

Hal ini penting terutama untuk client yang malicious atau buggy.

Runtime tidak boleh membiarkan satu IPC client menghabiskan seluruh memory daemon.

Cancellation

Cancellation harus cooperative tetapi memiliki batas yang jelas.

CancelJob menghasilkan cancellation token atau cancellation state yang dapat dibaca worker.

Worker harus memeriksa cancellation pada boundary yang sesuai.

Contoh boundary:

setiap batch scan

setiap batch metadata read

sebelum operation destructive

setelah operation destructive

sebelum retry

sebelum expensive verification

Cancellation tidak boleh menyebabkan worker langsung melakukan arbitrary cleanup rollback.

Rollback hanya boleh dilakukan jika operation tersebut memang transactionally reversible dan kontraknya sudah ditentukan.

Untuk destructive filesystem operation, cancellation yang diterima setelah operation dimulai tidak selalu berarti operation dapat dibatalkan.

Yang penting:

setelah cancellation terlihat, tidak boleh ada destructive operation baru yang tidak diperlukan untuk menyelesaikan state yang sudah berjalan.

Hal ini harus diuji secara eksplisit.

Runtime timeout

Setiap job memiliki timeout yang berbeda dengan event loop timeout.

Event loop timeout adalah mekanisme runtime untuk mencegah resource menunggu tanpa batas.

Job timeout adalah policy execution boundary.

Contohnya:

IPC read timeout

worker startup timeout

scan max duration

cleanup max duration

shutdown grace period

Timeout tidak boleh diperlakukan sama.

Ketika scan timeout terjadi:

Scanner berhenti sesuai cancellation contract.

ApplicationController menerima ScanTimedOut.

Job menjadi Failed atau Deferred sesuai policy.

Tidak boleh ada executor yang berjalan seolah-olah scan berhasil.

Runtime lock

Daemon harus mencegah dua instance privileged berjalan bersamaan.

RuntimeLock digunakan untuk single-instance guarantee.

Lock acquisition harus dilakukan sedini mungkin sebelum membuka resource yang memerlukan exclusive daemon lifecycle.

Jika lock gagal:

daemon harus keluar dengan status yang dapat didiagnosis.

Tidak boleh menjalankan second controller instance.

Lock file atau lock mechanism tidak boleh dianggap sebagai security boundary untuk target filesystem.

Lock hanya menjamin single daemon instance.

Filesystem safety tetap berlaku terpisah.

Contoh:

RuntimePaths tidak boleh menyediakan arbitrary target filesystem path kepada executor.

Event dapat berasal dari:

Runtime tidak perlu memahami detail policy cleanup.

Runtime hanya menghasilkan normalized event.

Jika catalog generation berubah:

catalog lama tidak boleh digunakan untuk job baru.

UEVENT handling

Uevent parser harus bersifat defensive.

Input kernel event tidak boleh dianggap selalu valid.

Parser harus menangani:

missing key

unknown key

duplicate key

invalid value

unexpected encoding

oversized payload

unknown event type

partial data

Unknown event tidak boleh menyebabkan daemon crash.

Event yang tidak relevan dapat diabaikan.

Event yang berpotensi mempengaruhi safety tetapi tidak dapat diklasifikasikan dengan yakin harus menghasilkan conservative invalidation atau rescan trigger.

Lebih baik melakukan rescan daripada mempertahankan state yang sudah tidak dapat dipercaya.

Runtime failure policy

Runtime harus membedakan:

recoverable event source failure

temporary source failure

fatal runtime failure

Contoh:

Timer initialization gagal.

Jika timer merupakan fitur optional, daemon mungkin masih dapat hidup dengan scheduler disabled.

Jika IPC listener gagal dibuat dan daemon memang membutuhkan IPC sebagai control interface utama, startup dapat dianggap fatal.

Jika satu uevent source tidak tersedia tetapi platform abstraction dapat mendeteksi storage state dengan metode lain, runtime dapat berjalan degraded.

Semua keputusan tersebut harus explicit.

Jangan menggunakan:

unwrap()

expect()

panic()

sebagai mekanisme normal untuk runtime failure.

Panic policy

Panic dalam runtime production path harus dianggap bug.

Boundary parser harus diuji agar malformed input tidak menghasilkan panic.

Jika panic terjadi pada worker, worker lifecycle harus ditangani secara eksplisit.

Panic worker tidak boleh membuat application layer menganggap job sukses.

Jika panic terjadi pada event loop sendiri, daemon berpotensi kehilangan seluruh control plane.

Karena itu event loop harus dibuat sesederhana mungkin dan dependency-nya minimal.

Resource ownership

Setiap file descriptor harus mempunyai owner yang jelas.

EventLoop memiliki epoll/poll mechanism.

IpcListener memiliki listening socket.

IpcConnection memiliki client socket.

Timer memiliki timer descriptor.

SignalSource memiliki signal descriptor.

UeventSource memiliki source descriptor.

WorkerNotification memiliki notification descriptor.

Ownership harus eksplisit sehingga shutdown dapat menutup resource dalam urutan yang deterministic.

Tidak boleh ada raw file descriptor yang tersebar tanpa owner.

FD lifecycle

Setiap FD yang dibuat harus:

dibuat dengan flag yang aman bila tersedia

tidak diduplikasi tanpa alasan

tidak dikembalikan sebagai integer mentah ke domain layer

Jika FD berpindah ownership, ownership transfer harus eksplisit.

Ini penting untuk mencegah:

double close

use-after-close

FD leak

FD reuse bug

salah menggunakan FD milik connection lain

Startup sequence

Urutan startup yang direkomendasikan:

Process start.

Initialize minimal logging.

Acquire RuntimeLock.

Load bootstrap configuration.

Initialize platform abstraction.

Detect runtime capabilities.

Initialize IPC listener.

Initialize timer source.

Initialize signal source.

Initialize system event sources.

Initialize worker notification source.

Construct ApplicationController.

Load validated configuration snapshot.

Construct Scheduler.

Perform initial runtime state discovery.

Publish initial readiness state.

Enter EventLoop.

Initial discovery harus tetap mengikuti rule bahwa informasi sistem dapat berubah sewaktu-waktu.

Initial state bukan jaminan permanen.

Cleanup pertama tetap harus melakukan readiness dan safety validation.

Shutdown sequence

Urutan shutdown:

Receive shutdown request.

Transition runtime to Stopping.

Stop accepting new IPC requests.

Tell scheduler to stop dispatching new jobs.

Cancel queued work.

Request cancellation for active jobs.

Continue event loop while waiting for worker state changes.

Collect worker termination results.

Close IPC connections.

Close event sources.

Flush essential telemetry.

Release runtime lock.

Exit process.

Jika shutdown timeout:

record incomplete shutdown.

mark affected jobs appropriately.

terminate according to runtime policy.

Shutdown tidak boleh menulis status Completed untuk job yang belum diverifikasi.

Implementasi event loop

Setelah budget tercapai, event loop kembali melakukan polling dan memberikan kesempatan kepada source lain.

Fairness

Fairness diperlukan agar event loop tidak starvation.

Tetapi fairness tidak boleh mengalahkan priority.

Urutan ideal:

critical system event

lifecycle event

worker completion

IPC control request

timer

non-critical progress

Dengan demikian shutdown atau storage invalidation tidak tertunda hanya karena IPC client sedang aktif.

Runtime tidak menentukan cleanup policy

Ini harus ditegaskan kembali karena runtime sering menjadi tempat arsitektur mulai bocor.

Runtime tidak boleh mempunyai function seperti:

cleanup_cache()

delete_old_files()

scan_app_cache()

run_maintenance()

trim_storage()

reset_zram()

Runtime hanya memiliki mekanisme:

emit_event()

dispatch_event()

schedule_wakeup()

register_source()

remove_source()

start_worker()

request_shutdown()

Dengan demikian tanggung jawabnya tetap sempit.

Boundary terakhir

Setelah 35.md, runtime sudah memiliki kontrak implementasi yang cukup jelas:

system event masuk melalui runtime.

event dinormalisasi.

application layer menerima event.

scheduler/application state melakukan keputusan.

job dibuat jika readiness terpenuhi.

worker menjalankan scan dan decision pipeline.

safety dan policy tetap menjadi gate.

authorized plan baru boleh mencapai executor.

executor melakukan operation melalui filesystem/kernel abstraction.

verification menentukan hasil.

report memperbarui job state.

scheduler menentukan langkah berikutnya.

Tidak ada shortcut dari runtime, IPC, scheduler, maupun CLI menuju executor.

Kesimpulan

Runtime adalah control-plane infrastructure, bukan cleanup engine.

Tujuan runtime bukan melakukan pekerjaan sebanyak mungkin, tetapi memastikan sistem menerima event dengan benar, menjaga lifecycle resource, menghindari starvation, dan meneruskan fakta sistem kepada application layer secara aman.

Jika kontrak ini dipatuhi, maka implementasi daemon dapat berkembang tanpa membuat event loop berubah menjadi God Object.
