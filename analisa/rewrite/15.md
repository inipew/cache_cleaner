Lanjut. Sekarang kita masuk ke **Scanner + Walker**, dan ini memang salah satu bagian paling kritis dari rewrite.

Untuk cleaner privileged, saya ingin prinsip berikut menjadi kontrak:

> **Scanner hanya menemukan dan membuktikan objek; Scanner tidak pernah menghapus.**

Dan:

> **Path adalah identifier untuk display, bukan authority untuk destructive operation.**

---

# 1. Pisahkan Scanner dan Walker

Jangan buat satu module:

```text
scanner.rs
    scan_and_delete()
```

Kita pisahkan:

```text
scanner/
├── scanner.rs
├── walker.rs
├── entry.rs
├── metadata.rs
├── identity.rs
├── size.rs
├── budget.rs
└── error.rs
```

Tanggung jawab:

```text
Walker
    ↓
filesystem traversal

Scanner
    ↓
interpret traversal result menjadi Candidate
```

Jadi:

```text
Filesystem
    ↓
Walker
    ↓
RawEntry
    ↓
Scanner
    ↓
Candidate
```

---

# 2. Walker tidak tahu policy

Walker tidak boleh tahu:

```text
age > 7 days
cache = enabled
profile = deep
```

Walker hanya tahu:

```text
"ada entry ini"
```

Misalnya:

```rust
pub struct RawEntry {
    pub name: OsString,
    pub file_type: EntryType,
    pub identity: ObjectIdentity,
    pub size: Option<u64>,
    pub modified: Option<SystemTime>,
}
```

---

# 3. Scanner juga tidak boleh menghapus

Flow:

```text
scan()
    ↓
Candidate[]
```

bukan:

```text
scan()
    ↓
if old
    ↓
unlink()
```

Ini sengaja.

Dengan begitu:

```text
clean
dry-run
explain
diagnostics
tests
```

semuanya bisa memakai scanner yang sama.

---

# 4. Root scanner

Scanner menerima:

```rust
pub struct ScanRequest {
    pub root: TargetRoot,
    pub budget: ScanBudget,
    pub cancellation: CancellationToken,
}
```

Kemudian:

```rust
pub struct ScanResult {
    pub candidates: Vec<Candidate>,
    pub visited_entries: usize,
    pub visited_bytes: u64,
    pub truncated: bool,
}
```

# 5. Scan budget

```rust
pub struct ScanBudget {
    pub max_entries: usize,
    pub max_depth: usize,
    pub max_duration: Duration,
}
```

Saya juga akan mempertimbangkan:

```rust
pub struct ScanBudget {
    pub max_entries: usize,
    pub max_depth: usize,
    pub max_duration: Duration,
    pub max_metadata_reads: usize,
}
```

Karena metadata operation sendiri bisa mahal.

---

# 6. `read_dir()` bukan security boundary

`std::fs::read_dir()` boleh digunakan untuk tooling biasa.

Tetapi untuk privileged recursive deletion, kita ingin kontrol yang lebih eksplisit:

```text
trusted root FD
    ↓
enumerate child
    ↓
open parent relative
    ↓
fstatat(... NOFOLLOW)
```

Tujuannya supaya traversal tidak bergantung pada string path yang dapat berubah.

---

# 7. Root harus sudah trusted

Scanner menerima:

```rust
pub struct TrustedRoot {
    pub identity: ObjectIdentity,
    pub display_path: PathBuf,
}
```

Tetapi `display_path` bukan authority.

Authority berasal dari:

```text
FD / validated filesystem object
+
identity
```

---

# 8. Object identity

Minimal:

```rust
pub struct ObjectIdentity {
    pub dev: u64,
    pub ino: u64,
}
```

Pada platform yang memungkinkan, metadata tambahan bisa disimpan:

```rust
pub struct ObjectIdentity {
    pub dev: u64,
    pub ino: u64,
    pub mode: FileMode,
}
```

Tetapi `{dev, ino}` tetap menjadi identity utama.

---

# 9. Kenapa `ino` saja tidak cukup?

Karena inode hanya unik dalam konteks filesystem/device.

Contoh:

```text
/dev/block/A
    inode 123

/dev/block/B
    inode 123
```

Jadi:

```text
(dev, ino)
```

lebih tepat.

Dan kita tetap menggunakan:

```text
trusted root device
```

untuk memastikan traversal tidak keluar filesystem.

---

# 10. Device boundary

Saat scanner menemukan:

```text
child.st_dev != root.st_dev
```

jangan masuk.

```rust
if child.dev != root.device {
    return SkipReason::CrossDevice;
}
```

Ini berlaku walaupun:

```text
directory terlihat berada di bawah root
```

karena mount point bisa muncul di dalam hierarchy.

---

# 11. Symlink

Ini hard rule.

Jika:

```text
entry = symlink
```

maka:

```text
do not follow
```

Bukan:

```text
readlink()
→ resolve
→ follow
```

Dan normal cleanup juga tidak menghapus symlink secara otomatis.

Untuk scanner:

```rust
EntryType::Symlink
```

→ reject / skip.

---

# 12. `O_NOFOLLOW`

Ketika membuka directory child:

```text
openat(parent_fd, child, O_DIRECTORY | O_NOFOLLOW)
```

Jika child adalah symlink:

```text
open → fail
```

Ini sangat bagus karena filesystem kernel sendiri ikut menegakkan boundary.

Tetapi tetap:

```text
fstat
```

dan validate.

Defense in depth.

---

# 13. `AT_SYMLINK_NOFOLLOW`

Untuk metadata:

```text
fstatat(
    parent_fd,
    name,
    AT_SYMLINK_NOFOLLOW
)
```

Kita ingin metadata **object itu sendiri**, bukan target symlink.

---

# 14. Jangan gunakan `canonicalize()`

Pattern:

```rust
let real = fs::canonicalize(path)?;
fs::remove_file(real)?;
```

tidak cukup aman untuk privileged cleanup.

Masalahnya:

```text
T0:
    canonicalize

T1:
    attacker/process changes path

T2:
    delete
```

Canonical path bukan capability.

---

# 15. FD-relative traversal

Model:

```text
root_fd
  │
  ├── child A
  ├── child B
  └── directory C
          │
          ├── x
          └── y
```

Untuk masuk C:

```text
root_fd
    ↓
openat(root_fd, "C", ...)
    ↓
C_fd
```

Kemudian:

```text
fstatat(C_fd, "x", ...)
```

bukan:

```text
stat("/root/C/x")
```

---

# 16. Rust abstraction

Saya akan membuat:

```rust
pub struct DirectoryHandle {
    fd: OwnedFd,
    identity: ObjectIdentity,
}
```

Dan:

```rust
impl DirectoryHandle {
    pub fn open_child(
        &self,
        name: &OsStr,
    ) -> Result<DirectoryHandle>;
}
```

Ini menyembunyikan syscall details dari Scanner.

---

# 17. Jangan expose raw `RawFd`

Sebisa mungkin:

```rust
OwnedFd
```

daripada:

```rust
RawFd
```

karena ownership menjadi eksplisit.

Kalau membutuhkan libc syscall:

```rust
AsRawFd
```

hanya pada boundary.

---

# 18. `unsafe` boundary

Misalnya:

```rust
fn fstatat_nofollow(...) -> Result<Metadata> {
    // SAFETY:
    // ...
}
```

Semua `unsafe` sebaiknya terkonsentrasi:

```text
scanner/
    ❌ banyak unsafe

sys/
    syscall.rs
```

Lebih baik:

```text
fs/
├── handle.rs
├── metadata.rs
└── syscalls.rs
```

dan `unsafe` hanya di `syscalls.rs`.

---

# 19. Jangan membuat abstraction terlalu generic

Hindari:

```rust
pub fn syscall<T>(
    number: libc::c_long,
    args: &[T],
)
```

Ini membuat:

```text
"syscall anything"
```

Lebih baik typed:

```rust
pub fn stat_at_nofollow(...) -> Result<Metadata>
pub fn unlink_at(...) -> Result<()>
pub fn open_dir_at(...) -> Result<DirectoryHandle>
```

Boring, tetapi jauh lebih aman.

# 20. Entry model

Saya sarankan:

```rust
pub enum EntryType {
    RegularFile,
    Directory,
    Symlink,
    Socket,
    Fifo,
    BlockDevice,
    CharDevice,
    Unknown,
}
```

Scanner kemudian punya rule:

```text
RegularFile
    → candidate evaluation

Directory
    → recurse

Symlink
    → reject/skip

Socket/FIFO/device
    → reject/skip
```

# 21. Directory traversal

Pseudo-flow:

```text
scan(root)
    ↓
open root
    ↓
walk(root)
    ↓
for each entry:
    cancellation?
        yes → stop

    budget?
        exceeded → truncate

    stat nofollow
        ↓
    same device?
        no → skip

    type?
        file → inspect
        dir  → recurse
        symlink → skip
        other → skip
```

---

# 22. Cancellation boundary

Jangan hanya check:

```text
sebelum scan
```

Check:

```text
sebelum open
sebelum metadata
setiap N entries
sebelum recurse
sesudah recurse
```

Misalnya:

```rust
if cancellation.is_cancelled() {
    return Err(ScanError::Cancelled);
}
```

---

# 23. Jangan check cancellation setiap syscall secara obsesif

Ada tradeoff.

Untuk directory besar:

```text
100k entries
```

check setiap entry masih reasonable.

Tetapi jika overhead terbukti besar:

```text
check every 32/64 entries
```

bisa digunakan.

Namun sebelum expensive recursion:

```text
always check
```

---

# 24. Depth limit

Contoh:

```text
root/
 └── a/
      └── b/
           └── c/
                ...
```

Tanpa limit, malformed filesystem tree atau pathological data bisa membuat scan terlalu mahal.

```rust
if depth > budget.max_depth {
    return SkipReason::DepthExceeded;
}
```

Default bisa cukup tinggi, tetapi harus bounded.

---

# 25. Apakah directory symlink perlu dicek?

Ya.

Jangan pernah:

```text
if entry.is_dir() {
    recurse
}
```

karena semantics high-level API dapat mengikuti symlink.

Kita ingin:

```text
lstat/fstatat NOFOLLOW
```

dan hanya:

```text
S_IFDIR
```

yang benar-benar directory.

---

# 26. Hard links

Ini kasus menarik.

Misalnya:

```text
cache/a
cache/b
```

adalah hard link ke inode sama:

```text
(dev=8, ino=100)
```

Kalau kita delete `a`, `b` masih ada.

Planner boleh deduplicate:

```text
same object identity
```

tetapi tidak boleh menganggap:

```text
remove a
→ object fully gone
```

Jadi reporting:

```text
directory entry removed
```

lebih akurat daripada:

```text
physical storage definitely freed
```

---

# 27. Size accounting

Candidate:

```rust
pub struct Candidate {
    pub identity: ObjectIdentity,
    pub logical_size: u64,
}
```

Tetapi logical size bukan selalu:

```text
bytes physically freed
```

Sparse files misalnya.

Jadi gunakan terminology:

```text
estimated_reclaimable_bytes
```

bukan:

```text
guaranteed_freed_bytes
```

---

# 28. Directory size

Jangan menjumlahkan:

```text
directory metadata size
```

sebagai reclaimable data secara naif.

Untuk directory:

```text
size = descendants
```

jika ingin estimate recursive.

Scanner dapat mengumpulkan:

```rust
pub struct TreeStats {
    pub files: usize,
    pub directories: usize,
    pub logical_bytes: u64,
}
```

---

# 29. Scanner result tidak harus menyimpan semua candidate

Ini penting untuk memory.

Kalau:

```text
500k candidates
```

menyimpan seluruh metadata bisa besar.

Kita punya dua mode:

```text
Dry-run / explain
    → collect candidates

Automatic cleanup
    → streaming candidate evaluation
```

Tetapi planner membutuhkan deterministic plan.

Untuk v1, saya justru menyarankan:

```text
bounded Vec<Candidate>
```

dan kalau melebihi budget:

```text
scan truncated
```

bukan unlimited streaming.

---

# 30. Scan truncation harus terlihat

Jangan:

```text
max_entries reached
→ silently stop
→ report success
```

Harus:

```rust
pub enum ScanCompletion {
    Complete,
    BudgetExceeded,
    Cancelled,
}
```

Report:

```text
Scanned:
    100,000 / 100,000 entries

Status:
    truncated

Plan:
    partial
```

Kemudian Scheduler/Policy dapat memutuskan apakah partial plan boleh dieksekusi.

Untuk automatic cleanup, saya cenderung:

```text
truncated scan
    → do not execute destructive plan
```

atau hanya execute jika semantics-nya sangat jelas.

---

# 31. Kenapa?

Bayangkan:

```text
max_scan_entries = 1000
```

directory berisi:

```text
1,000,000 files
```

Scanner menemukan 1000 file tua pertama.

Kalau langsung delete:

```text
hanya subset arbitrary
```

Bisa menyebabkan behavior tidak deterministic berdasarkan directory ordering.

Lebih baik:

```text
scan incomplete
    ↓
no destructive plan
    ↓
retry later / larger bounded scan
```

---

# 32. Directory enumeration ordering

Filesystem tidak menjamin order yang stabil.

Jadi:

```text
first 1000
```

bukan policy yang bagus.

Kalau scan truncated:

```text
partial = true
```

dan jangan berpura-pura seluruh target telah dievaluasi.

# 33. Metadata race

Saat scan:

```text
stat(file)
```

kemudian file berubah.

Misalnya:

```text
T0:
    size = 10 MB
    mtime = old

T1:
    app writes file

T2:
    planner sees old metadata
```

Ini alasan kita membutuhkan:

```text

```

di executor.

# 45. Contoh nyata

Misalnya:

```text
/data/user/0/foo/cache/
├── old.tmp
├── recent.tmp
├── link
├── mounted/
│   └── other
└── nested/
    └── old.dat
```

Walker melihat:

```text
old.tmp
    RegularFile
    same dev

recent.tmp
    RegularFile
    same dev

link
    Symlink
    skip

mounted
    Directory
    different dev
    skip

nested
    Directory
    same dev

nested/old.dat
    RegularFile
    same dev
```

```text

```


Jika:

```text

```

hilang sebelum recurse:

```text

→ ENOENT
```

Ini bukan fatal.

Scanner dapat:

```text

```


# 50. Scanner invariant

Ini kontrak yang saya ingin tulis di test:

```text
1. Scanner never deletes.

2. Scanner never follows symlinks.

3. Scanner never crosses device boundary.

4. Scanner uses FD-relative traversal for privileged targets.

5. Scanner records object identity.

6. Scanner records target provenance.

7. Scanner enforces bounded depth.

8. Scanner enforces bounded entry count.

9. Scanner enforces cancellation.

10. Scanner reports truncation explicitly.

11. Scanner treats filesystem races as expected failure modes.

12. Scanner does not trust path strings as authority.

13. Scanner does not make policy decisions.

14. Scanner does not execute kernel maintenance.

15. Scanner never expands Target Catalog scope.
```

# 52. Boundary lengkap

Sekarang bagian filesystem kita punya:

```text
             TargetRoot
                 │
                 ▼
             Scanner
                 │
                 ▼
              Walker
                 │
        ┌────────┼────────┐
        ▼        ▼        ▼
      openat   statat   readdir
        │        │        │
        └────────┼────────┘
                 ▼
             RawEntry
                 │
                 ▼
             Candidate
                 │
                 ▼
              Safety
                 │
                 ▼
              Policy
                 │
                 ▼
              Planner
                 │
                 ▼
             Executor
                 │
                 ▼
              unlinkat
```

Yang sangat saya suka dari desain ini adalah **Scanner dan Executor sekarang benar-benar terpisah**. Kalau scanner punya bug policy, dia tidak bisa langsung menghapus apa pun. Kalau executor menerima sesuatu, dia tetap harus menerima `AuthorizedPlan` dan melakukan revalidation.

## Berikutnya

Bagian berikutnya yang paling tepat adalah **Executor filesystem secara konkret**.

Kita akan membedah sampai level function:

```text
remove_file()
remove_empty_directory()
remove_tree()
open_parent()
validate_identity()
validate_root()
unlink_at()
handle_enoent()
handle_race()
```

termasuk bagaimana membuat **safe recursive deletion tanpa `remove_dir_all()`**, bagaimana dependency Planner diterjemahkan menjadi urutan `unlinkat()`, bagaimana menangani hard link, directory berubah menjadi symlink, `ENOENT`, `ELOOP`, `EXDEV`, `EBUSY`, `EACCES`, cancellation di tengah recursive delete, dan bagaimana memastikan **tidak ada satu pun code path yang bisa berubah menjadi `rm -rf` terselubung**.
