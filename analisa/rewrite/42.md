42.md

Executor Architecture, Mutation Boundary, Operation Execution Contract, FD Ownership, Atomic Destructive Operations, Cancellation During Execution, Error Mapping, dan Verification Handoff

1. Tujuan

Executor adalah satu-satunya layer utama yang bertanggung jawab melakukan mutation terhadap filesystem setelah seluruh decision dan authorization gate berhasil.

Executor tidak menentukan:

object mana yang seharusnya dihapus

apakah object memenuhi retention policy

apakah target diizinkan

apakah client mempunyai permission

apakah plan masih policy-compliant

Keputusan tersebut sudah selesai sebelum Executor menerima operation.

▼

│
▼
Verifier

2. Mutation Boundary

Executor menjadi mutation boundary.

Sebelum boundary:

filesystem harus dianggap read-only.

Setelah boundary:

mutation diperbolehkan tetapi hanya terhadap AuthorizedPlan yang telah melewati Final Safety Gate.

Komponen lain tidak boleh melakukan destructive mutation secara tersembunyi.

             READ ONLY

4. AuthorizedPlan sebagai Authority

AuthorizedPlan adalah authority yang dapat digunakan Executor.

Tetapi AuthorizedPlan bukan bukti bahwa filesystem state masih sama.

Karena itu:

AuthorizedPlan
≠

Executor tetap harus menjalankan Final Safety Gate sebelum mutation.

1. Periksa job state.

2. Periksa cancellation.

4. Periksa generation.

5. Periksa budget.

7. Revalidate root.

8. Revalidate parent.

9. Revalidate target identity.

11. Revalidate boundary.

14. Ambil syscall result.

15. Buat OperationResult.

16. Serahkan result ke Verifier.

17. Lanjutkan operation berikutnya hanya jika dependency dan job state mengizinkan.

18. One Operation at a Time

Executor harus mempunyai semantics yang jelas mengenai concurrency.

Default untuk destructive cleanup:

satu active mutation stream per job.

Contoh:

Operation A
↓
Final Safety
↓
Mutation
↓
Result
↓
Operation B
↓
Final Safety
↓
Mutation

Jangan langsung menjalankan ribuan deletion secara parallel hanya demi throughput.

Concurrency dapat ditambahkan kemudian jika safety contract sudah membuktikan bahwa:

scope tidak conflict

FD ownership aman

budget atomic

ordering tetap benar

cancellation tetap bounded

error handling deterministik

7. Operation Dependency

Executor harus mengikuti dependency graph yang dibuat Planner.

Contoh:

RemoveFile
↓
RemoveFile
↓
RemoveEmptyDirectory(parent)

Executor tidak boleh mengubah dependency order berdasarkan filesystem result tanpa contract.

Jika dependency gagal dan dependent operation menjadi invalid, Scheduler harus menentukan apakah:

job berhenti

operation di-skip

plan menjadi stale

atau partial completion diperbolehkan.

8. FD Ownership

Setiap file descriptor harus mempunyai owner yang jelas.

Contoh:

Runtime
└── epoll FD

Scanner
└── traversal FDs

Executor
├── root FD
├── parent FD
└── temporary resolution FDs

Executor tidak boleh menutup FD milik Runtime atau Scanner.

FD ownership harus eksplisit:

CreatedBy

OwnedBy

ClosedBy

TransferredTo

9. FD Lifetime

FD harus hidup sesingkat mungkin.

Ideal:

open root
↓
resolve parent
↓
validate
↓
mutation
↓
close temporary FD

Jangan mempertahankan ribuan directory FD sepanjang satu job jika tidak dibutuhkan.

Long-lived FD hanya digunakan jika memang diperlukan oleh architecture.

10. FD Leak Prevention

Setiap error path harus menutup FD.

Contoh:

open root
↓
open parent
↓
validation fails
↓
close parent
↓
close root
↓
return error

Bukan:

validation fails
↓
return error
↓
FD leaked

11. RAII / Scoped Ownership

Implementasi sebaiknya menggunakan scoped ownership abstraction untuk FD.

Konseptual:

ScopedFd
├── owns fd
├── closes automatically
└── cannot be copied accidentally

Transfer ownership harus eksplisit.

14. No Arbitrary Path API

Filesystem abstraction tidak boleh menyediakan destructive API umum seperti:

remove(path)

remove_tree(path)

force_remove(path)

Executor API juga tidak boleh:

execute_delete(path)

Sebaliknya:

execute(RemoveFileOperation)

Operation sudah membawa typed target information.

15. Final Safety Gate

Sebelum mutation:

┌─────────────────────────────┐
│      Final Safety Gate      │
├─────────────────────────────┤
│ TrustedRoot                 │
│ Root identity               │
│ RelativePath                │
│ Parent identity             │
│ Target identity             │
│ Object type                 │
│ Filesystem boundary         │
│ Mount identity              │
│ Generation                  │
│ Authorization validity      │
│ Cancellation                │
└──────────────┬──────────────┘
│
ALL VALID
│
▼
Mutation

Jika satu saja gagal:

NO MUTATION.

16. Mutation Primitive

Mutation primitive harus sesempit mungkin.

Untuk regular file:

validated parent FD
+
validated final component
+
expected identity/type
→
unlink operation

Untuk directory:

validated parent FD
+
validated final component
+
directory identity/type
→
directory removal primitive

Tidak boleh ada automatic fallback:

unlink failed
→ recursive delete

17. Atomicity

Executor harus menggunakan primitive filesystem yang paling dekat dengan atomic namespace operation yang tersedia.

Tujuannya:

validation
↓
mutation

memiliki race window sekecil mungkin.

Tidak mungkin menghilangkan seluruh race, sehingga Final Safety Gate dan filesystem primitive harus dirancang bersama.

18. Validation-to-Mutation Gap

Setelah final validation, Executor tidak boleh melakukan pekerjaan yang tidak diperlukan sebelum mutation.

Buruk:

Final Safety
↓
sleep
↓
logging network
↓
large allocation
↓
mutation

Lebih baik:

Final Safety
↓
minimal preparation
↓
mutation

Logging dan telemetry yang tidak diperlukan untuk correctness dilakukan setelah operation atau melalui bounded local mechanism.

19. Cancellation Before Mutation

Urutan:

check cancellation
↓
Final Safety
↓
check cancellation
↓
mutation

Jika cancellation diterima sebelum mutation:

operation tidak dijalankan.

Jika cancellation terjadi setelah mutation berhasil:

result tetap:

Removed

bukan:

Cancelled

20. Cancellation During Syscall

Tidak semua syscall dapat dihentikan secara instan.

Executor harus menggunakan blocking boundaries yang terkontrol.

Jika syscall dapat dibatalkan/interrupted:

return typed cancellation/interruption result

Jika mutation sudah terjadi:

report actual result

Cancellation tidak boleh menyebabkan Executor mengulangi mutation secara membabi buta.

21. Retry Safety

Destructive operation tidak boleh di-retry hanya berdasarkan:

“syscall returned error”

Retry harus bergantung pada error classification.

Contoh:

AlreadyGone
→ no-op

PermissionDenied
→ biasanya no retry

Interrupted sebelum mutation
→ dapat retry jika primitive contract menjamin belum terjadi mutation

UnknownOutcome
→ jangan retry otomatis

22. Unknown Outcome

Jika Executor tidak dapat memastikan apakah mutation terjadi, hasil harus:

UnknownOutcome

Bukan:

Failed → retry

Contoh:

syscall terinterupsi setelah kernel mungkin sudah melakukan mutation.

Executor tidak boleh menganggap operation pasti belum terjadi.

Verifier/Scheduler harus menangani state tersebut secara konservatif.

23. Error Mapping

Raw errno atau platform error tidak boleh bocor sebagai satu-satunya API.

Contoh mapping konseptual:

ENOENT
→ AlreadyGone

EACCES
→ PermissionDenied

EPERM
→ PermissionDenied atau OperationDenied

ELOOP
→ SymlinkRejected

EXDEV
→ MountBoundary atau CrossFilesystem

ENOTDIR
→ TypeChanged

EINTR
→ Interrupted

EBUSY
→ ResourceBusy

unknown
→ UnknownFailure

Mapping harus platform-specific tetapi output domain tetap typed.

24. AlreadyGone

Jika target sudah tidak ada:

Executor tidak mencari replacement.

Tidak ada:

same filename search

inode guess

directory rescan lalu delete

Hasil:

AlreadyGone

Scheduler dapat menghitungnya sebagai no-op.

25. PermissionDenied

Jika permission berubah:

operation gagal.

Executor tidak boleh mencoba:

chmod

sudo

setuid

root shell

SELinux bypass

force flag

Operation harus berhenti sesuai error policy.

26. TypeChanged

Jika object type berubah:

expected:

RegularFile

actual:

Directory

Result:

TypeChanged

Tidak ada fallback ke recursive deletion.

27. Symlink Detected

Jika operation mengharapkan regular file tetapi final component menjadi symlink:

SymlinkRejected

Executor tidak boleh mengikuti target symlink.

28. Root Changed

Jika root identity berbeda:

RootChanged

Seluruh remaining operation pada target tersebut harus dianggap stale.

Jangan mencoba menemukan root baru berdasarkan path yang sama.

29. Filesystem Changed

Jika filesystem identity berubah:

FilesystemChanged

Plan tidak boleh dilanjutkan menggunakan snapshot lama.

Scheduler harus melakukan revalidation/replan sesuai state machine.

32. Bytes Accounting

Untuk deletion, byte accounting harus jelas.

Jika file metadata mengatakan:

size = 4096

dan unlink berhasil:

actual freed bytes mungkin tidak selalu dapat diketahui secara langsung.

Karena itu bedakan:

EstimatedBytes

ReportedBytes

ActualFreedBytes

Jangan mengklaim:

4096 bytes freed

hanya karena file size 4096.

Hard links dapat membuat disk space tidak langsung bebas.

33. Budget Enforcement Saat Execution

Planner sudah membuat budget.

Authorization sudah memvalidasi budget.

Executor tetap harus enforce runtime budget.

Contoh:

Plan budget:

max_operations = 5000

Executor counter:

0
1
2
...
5000

Setelah mencapai limit:

stop

Jangan:

execute 5001
→ kemudian reject report.

34. Runtime Budget

Executor harus memantau:

operation count

elapsed duration

bytes processed/estimated cost

memory/queue limits

Jika runtime budget terlampaui:

remaining operations tidak dijalankan.

Job result mengikuti policy:

CompletedPartial

Deferred

Failed

atau equivalent.

35. Per-Operation Timeout

Operation dapat memiliki timeout bila platform primitive memungkinkan.

Timeout harus menggunakan monotonic clock.

Wall clock tidak digunakan untuk elapsed duration.

38. Verifier Responsibility

Verifier memeriksa hasil operation sesuai contract.

Verifier tidak boleh:

melakukan cleanup tambahan

memperbaiki operation

retry arbitrary mutation

memperluas scope

Verifier harus read-only.

39. Verification Levels

Verification dapat mempunyai beberapa level:

Level 0
Syscall result saja.

Level 1
Basic post-condition.

Level 2
Identity/post-state verification.

Level 3
Target-level consistency.

Tidak semua operation membutuhkan level tertinggi.

Policy harus menentukan verification requirement.

40. Remove File Verification

Untuk RemoveFile:

mutation success
↓
target lookup
↓
target absent
↓
verified removed

Jika target masih ada:

VerificationFailed

Executor tidak boleh otomatis menghapus ulang tanpa explicit retry semantics.

41. Verification Race

Target dapat berubah lagi setelah deletion.

Karena itu Verifier harus membedakan:

object still exists

different object exists

operation result indicates success

state cannot be determined

Verification failure tidak selalu berarti Executor salah.

Filesystem adalah concurrent environment.

42. Idempotency

Operation harus mempunyai semantics idempotency yang jelas.

RemoveFile:

target already absent
→ AlreadyGone

Ini memungkinkan retry terbatas terhadap known-safe state.

Namun:

UnknownOutcome

tidak otomatis dianggap idempotent.

43. Retry Policy

Retry hanya boleh dilakukan untuk error yang diketahui aman.

Contoh:

AlreadyGone
→ no retry

Interrupted before mutation
→ retry mungkin diperbolehkan

ResourceBusy
→ retry mungkin dengan backoff

PermissionDenied
→ no automatic retry

ChangedSinceScan
→ replan

RootChanged
→ new catalog/plan

UnknownOutcome
→ conservative recovery

44. Partial Execution

Jika 100 operation direncanakan:

Operation 1 ✓
Operation 2 ✓
Operation 3 ✗
Operation 4 ...

Scheduler harus menentukan apakah execution:

stop immediately

skip failed operation

continue independent operations

Keputusan harus berasal dari execution policy.

Namun security failure seperti:

RootChanged

OutsideRoot

Scope violation

harus mempunyai behavior konservatif dan biasanya menghentikan scope terkait.

45. Independent Operations

Operation yang tidak memiliki dependency dapat secara teori dilanjutkan setelah failure.

Contoh:

Target A
├── operation 1
└── operation 2

Target B
└── operation 3

Jika operation 1 gagal karena AlreadyGone, operation 2 dapat dilanjutkan.

Tetapi jika root Target A berubah:

semua operation pada root tersebut harus menjadi stale.

46. Security Failure Propagation

Jika:

RootChanged(Target A)

maka:

Target A
├── op1 → stale
├── op2 → stale
└── op3 → stale

Target B yang independent tidak otomatis menjadi stale kecuali shared filesystem/platform state juga berubah.

54. File Contents

RemoveFile tidak boleh membuka dan membaca isi file.

55. Special Files

56. Directory Handling

75. Keputusan Arsitektur

Executor adalah mutation boundary.

Executor hanya menerima AuthorizedPlan.

Final Safety Gate wajib dilakukan sebelum setiap destructive operation.

Filesystem mutation dilakukan menggunakan primitive yang sempit dan FD-relative.

Absolute path bukan authority.

Object identity dan object type tetap harus diverifikasi.

Executor tidak melakukan policy decision.

Executor tidak melakukan authorization.

Executor tidak melakukan automatic repair.

Unknown mutation outcome diperlakukan secara konservatif.

Cancellation tidak boleh mengaburkan apakah mutation sudah terjadi.

Budget tetap enforced pada runtime.

Verifier dipisahkan dari Executor.

Hasil Executor selalu berupa typed OperationResult.

Struktur akhir execution:

```
    AuthorizedPlan
          │
          ▼
   ┌───────────────┐
   │ Final Safety  │
   └───────┬───────┘
           │
      safety OK
           │
           ▼
   ┌───────────────┐
   │   Executor    │
   └───────┬───────┘
           │
    mutation primitive
           │
           ▼
   ┌───────────────┐
   │    Verifier   │
   └───────┬───────┘
           │
           ▼
   OperationResult
           │
           ▼
       Scheduler
```

Dengan ini, Executor tidak lagi menjadi “tempat kode hapus file”, tetapi menjadi execution boundary yang sangat terbatas: menerima authority yang sudah lengkap, melakukan final verification, menjalankan primitive mutation, lalu melaporkan hasil sebenarnya.
