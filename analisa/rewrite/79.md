# 79.md — IPC Protocol, Request/Response Model, Framing, Authentication, Authorization Boundary, Streaming, Cancellation, and Compatibility Contract

## Tujuan

IPC adalah untrusted input boundary. Client/CLI/UI tidak boleh dapat memanipulasi internal state machine, capability, TargetDescriptor, atau Executor secara langsung.

## 1. Boundary

```text
IPC Client → Decode → Authenticate → Validate → Command Handler → Domain Service
```

Tidak ada IPC path langsung ke filesystem mutation.

## 2. Protocol Version

Every request/response has explicit protocol version.

Protocol version != config schema version != catalog generation.

## 3. Framing

Message framing must be unambiguous and bounded.

For Unix sockets, use length-delimited frames or newline-delimited bounded messages with strict size limits.

## 4. Maximum Message Size

Reject oversized frames before allocating large buffers.

## 5. Decode

Decode into IPC DTO, never directly into privileged domain object.

## 6. Unknown Fields

Compatibility policy must be explicit. Unknown security-sensitive fields must not be interpreted permissively.

## 7. Unknown Enum

Unknown command/enum returns structured protocol error.

## 8. RequestId

Every request has RequestId for correlation.

RequestId is not JobId.

## 9. CorrelationId

Long-running operations may carry CorrelationId across logs/events.

## 10. JobId

Server-generated JobId identifies durable work.

Client must not choose arbitrary JobId as authority.

## 11. Idempotency Key

Client may provide idempotency key for duplicate-submit safety.

## 12. Authentication

IPC transport must establish caller identity according to platform mechanism.

On Unix/Android, prefer OS credential/peer identity mechanisms over shared plaintext secrets where available.

## 13. Transport Security

Local IPC is not automatically trusted merely because it is local.

## 14. Caller Identity

Authorization decisions must bind to authenticated caller identity/scope.

## 15. Capability Boundary

IPC command can request an action; it cannot supply its own capability proof.

## 16. No Client-Supplied Safety Proof

Client must never be able to submit `safety_verified=true` and bypass server Safety.

## 17. No Client-Supplied Authorization

Client cannot submit arbitrary AuthorizationId as permission to perform a different request.

Authorization must be server-created and request-bound.

## 18. Request Validation

Validate:

- command
- argument types
- bounds
- paths
- package/user scope
- idempotency key
- timeout
- requested target filters

## 19. Path Input

IPC path is untrusted locator input.

It must go through Target/Safety resolution.

## 20. Package Input

Package name must use typed PackageName validation.

## 21. User Input

UserId must be validated against platform/user scope.

## 22. Command Categories

Commands should be separated:

- read/query
- submit job
- cancel
- status
- recovery/admin
- configuration
- diagnostics

## 23. Read Commands

Read-only queries must not mutate state.

## 24. Submit

Submit returns durable acceptance only after Job persistence succeeds.

## 25. Status

Status returns snapshot DTO, not mutable internal references.

## 26. Cancel

Cancel is a lifecycle request and must be persisted before successful acknowledgement.

## 27. Recovery Commands

Recovery/admin commands require elevated capability and explicit audit trail.

## 28. Configuration Commands

Config update uses parse → validate → atomic replace. Invalid config must not replace current valid config.

## 29. Diagnostic Commands

Diagnostics must redact secrets and minimize sensitive paths.

## 30. Streaming

Long-running scan/status operations should use bounded streaming/event subscription instead of one enormous response.

## 31. Backpressure

Client that cannot consume events must not block core worker execution indefinitely.

## 32. Event Buffer

Use bounded per-client buffers.

## 33. Slow Client

Drop/coalesce non-authoritative progress events when buffer is full; never drop required terminal event without durable replay mechanism.

## 34. Replay

Client can resume from event sequence/cursor.

## 35. Event Sequence

Use durable EventId/sequence, not timestamps.

## 36. Duplicate Events

Clients must tolerate duplicate events.

## 37. Event Ordering

Ordering is guaranteed only within documented scope, usually JobId/stream sequence.

## 38. Cancellation Connection Loss

Disconnect does not imply cancellation.

Job continues unless explicit cancel command is accepted.

## 39. Client Crash

Server-owned Job remains durable.

## 40. Server Crash

Client must be able to reconnect and query durable Job state.

## 41. Timeout

IPC request timeout is not automatically Job timeout.

A synchronous request may time out while server Job continues.

## 42. Job Deadline

If caller requests a Job deadline, it must be represented as domain deadline and enforced by scheduler/lifecycle.

## 43. Error Model

Errors must be structured, e.g.:

```rust
pub enum IpcError {
    InvalidRequest,
    Unauthorized,
    Forbidden,
    Busy,
    NotFound,
    Conflict,
    Stale,
    ResourceExhausted,
    Cancelled,
    Timeout,
    Internal,
}
```

## 44. Error Leakage

Do not expose privileged filesystem details to unauthorized callers.

## 45. Error Stability

Error codes should be stable API contract; human messages can evolve.

## 46. Retry Hint

Server may return explicit retryability and bounded retry-after metadata.

## 47. No Implicit Retry

Client must not assume every error is safe to retry.

## 48. Unknown Outcome

If submit acknowledgement is lost after server persistence, client should retry with same idempotency key.

## 49. Mutation Unknown

IPC status must expose `RecoveryRequired`/unknown outcome without claiming success/failure prematurely.

## 50. Serialization

Use versioned DTOs distinct from domain entities.

## 51. Path Serialization

Do not serialize OS handles, file descriptors, or internal pointers.

## 52. Target Serialization

Target reference must contain stable typed identity/reference, not raw authority.

## 53. Authorization Serialization

Authorization DTO should expose status/scope needed by client, not internal secret material.

## 54. Config Serialization

Return effective sanitized config, not secret-bearing raw config.

## 55. Audit Serialization

Expose only audit data caller is permitted to see.

## 56. Rate Limits

IPC must have bounded request rates for expensive operations.

## 57. Request Concurrency

Limit concurrent expensive requests per caller and globally.

## 58. DoS Protection

A caller must not exhaust worker, memory, scan, or event-buffer resources through IPC.

## 59. Unix Socket Permissions

Socket file mode/ownership must be restrictive and documented.

## 60. Android IPC

If Binder or another Android-native transport is introduced, caller UID/package identity should be derived from the transport rather than request payload.

## 61. CLI Compatibility

CLI should be a client of the same IPC/domain contract where practical, not a second implementation of cleaning semantics.

## 62. In-Process Mode

If CLI can execute embedded engine directly, it must still use the same domain validation and safety boundaries.

## 63. Version Negotiation

Optional protocol feature negotiation must be bounded and deterministic.

## 64. Downgrade

Do not silently downgrade security-sensitive features.

## 65. Replay Protection

Commands with side effects use idempotency keys/nonce semantics as required.

## 66. Audit

Every privileged command should create an audit record with caller identity, RequestId, command, decision, and outcome.

## 67. Shutdown

Shutdown command is privileged and should follow daemon lifecycle rules.

## 68. Restart

Restart command must not fabricate Job completion.

## 69. Subscription Lifecycle

Subscriptions have explicit open/close state and bounded resources.

## 70. Heartbeat

Optional IPC heartbeat only indicates transport liveness; it does not replace worker lease.

## 71. Client Liveness

Long-running Job ownership must not depend on client connection liveness unless explicitly designed.

## 72. Security Context

Authenticated caller context should be immutable for request processing.

## 73. Scope

Every command is evaluated within explicit caller scope.

## 74. Scope Escalation

A client cannot change its scope by passing a different user/package/target in payload.

## 75. Confused Deputy

Server must ensure the caller's authority applies to the requested target, not merely that server itself can access it.

## 76. Definition of Done

IPC is production-ready if:

- framing bounded
- DTO/domain separation exists
- caller identity authenticated
- authorization server-side
- no client safety bypass
- durable submit acknowledgement
- idempotent duplicate submit
- cancellation durable
- disconnect safe
- event streaming bounded
- replay cursor exists
- structured stable errors
- rate limits exist
- privileged commands audited
- protocol compatibility/versioning explicit

## 77. Final Invariants

1. IPC is untrusted input.
2. Client cannot grant itself capability.
3. Client cannot bypass Safety.
4. Client cannot mutate lifecycle state directly.
5. RequestId != JobId.
6. Disconnect != cancellation.
7. Request timeout != Job timeout.
8. Duplicate submit is idempotent.
9. Unknown mutation remains unknown/recovery-required.
10. Events are bounded and replayable where required.
11. Caller identity comes from trusted transport context.
12. Scope cannot be escalated by payload.
13. Error codes are structured and stable.
14. Privileged operations are auditable.
15. IPC cannot become a confused deputy.
