# 76.md — Durable Job/Operation Store, Crash Consistency, Idempotency, Journal, Recovery, and Persistence Contract

## Tujuan

Persistence bukan sekadar tempat menyimpan history. Durable store adalah bagian dari correctness model karena Job/Attempt/Operation harus tetap dapat direkonstruksi setelah process crash, device reboot, worker death, atau mutation outcome yang tidak diketahui.

Pipeline persistence:

```text
Domain State
    ↓
Validated Transition
    ↓
Durable Commit
    ↓
Publication/Event
```

State tidak boleh dipublikasikan sebagai committed sebelum durable commit berhasil.

## 1. Source of Truth

Durable store adalah source of truth untuk lifecycle Job, Attempt, Operation, Authorization reference, reconciliation state, dan recovery metadata.

## 2. Memory Is Cache

`DaemonRuntimeState`, in-memory queues, channels, UI state, dan worker-local maps bukan source of truth.

## 3. Persistence Failure

Jika durable write gagal, transition tidak boleh dianggap berhasil.

## 4. Transaction Boundary

Perubahan state yang saling bergantung harus atomic dalam satu transaction atau menggunakan explicit journal protocol.

## 5. Job Identity

Primary identity: `JobId`.

Submit ulang dengan idempotency key yang sama tidak boleh membuat Job baru secara diam-diam.

## 6. Attempt Identity

Setiap execution attempt mempunyai `AttemptId` unik.

Retry tidak boleh overwrite attempt lama.

## 7. Operation Identity

Setiap mutation mempunyai `OperationId` unik dan immutable.

## 8. State Version

Job dan Operation mempunyai monotonic state version untuk optimistic concurrency.

## 9. Compare-And-Set

Transition harus dapat dieksekusi sebagai CAS:

```text
UPDATE job
SET state = ?, state_version = state_version + 1
WHERE job_id = ? AND state = ? AND state_version = ?
```

Jika affected rows != 1, caller harus memperlakukan state sebagai stale/conflict.

## 10. Event Sequence

Gunakan sequence monotonik untuk audit/event ordering. Wall-clock timestamp tidak boleh menjadi ordering authority.

## 11. Wall Clock

Timestamp hanya metadata observability.

## 12. Monotonic Time

Deadline/timeout dihitung dari monotonic clock dan direkonstruksi secara aman setelah restart.

## 13. Persisted Deadline

Persist absolute wall-clock deadline hanya sebagai recovery hint; jangan menganggapnya sebagai monotonic guarantee.

## 14. Recommended Tables

Minimal logical tables:

- `jobs`
- `attempts`
- `operations`
- `operation_events`
- `authorizations`
- `idempotency_keys`
- `recovery_records`
- `store_meta`

## 15. jobs

Minimal fields:

```text
job_id
idempotency_key
kind
state
state_version
config_generation
catalog_generation
created_at
updated_at
terminal_at
request_digest
result_digest
failure_class
```

## 16. attempts

```text
attempt_id
job_id
attempt_no
state
state_version
worker_id
started_at
finished_at
lease/heartbeat metadata
failure_class
```

## 17. operations

```text
operation_id
job_id
attempt_id
target_id
operation_kind
relative_path
planned_size
state
state_version
mutation_started
mutation_completed
outcome_class
```

Sensitive absolute paths should be minimized in persistent records.

## 18. Operation Event Journal

Events should be append-only and immutable.

Examples:

- operation prepared
- mutation intent persisted
- mutation started
- syscall outcome observed
- verification completed
- reconciliation completed

## 19. Mutation Intent

Before an irreversible mutation, persist enough information to answer:

> Did the process definitely reach the mutation boundary?

## 20. Unknown Outcome

If crash occurs after mutation may have started but before outcome persistence, state becomes `Unknown`/`RecoveryRequired`, never automatically `Failed`.

## 21. Recovery Record

Recovery record must identify:

- JobId
- AttemptId
- OperationId
- target identity
- expected precondition
- expected postcondition
- mutation class
- verification strategy

## 22. Recovery Is Deterministic

Recovery must use persisted intent and current observation, not reconstruct a new destructive plan blindly.

## 23. No Blind Replay

Unknown mutation must not simply be executed again.

## 24. Idempotency

Delete-like operation should be modeled so that already-absent object can be distinguished from unknown outcome.

## 25. Request Idempotency

Persist idempotency key before exposing accepted Job state.

## 26. Duplicate Submit

Same key + same request digest returns existing Job.

Same key + different request digest is rejected as conflict.

## 27. Key Scope

Idempotency key namespace must include caller/security scope where necessary.

## 28. Retention

Idempotency records need bounded retention, but active jobs must never be garbage-collected.

## 29. Terminal Immutability

`Completed`, `Failed`, `Cancelled`, `TimedOut`, and `RecoveryRequired` terminal records cannot be silently rewritten.

Administrative correction must be a new event/record.

## 30. Result Publication

Result publication occurs only after durable terminal state.

## 31. Audit

Audit events must contain correlation identifiers and transition reason without leaking secrets.

## 32. Serialization

Persistence DTO must be versioned and separate from domain structs.

## 33. Schema Version

`SchemaVersion` identifies storage format; it is not Job state version or ConfigGeneration.

## 34. Migration

Storage migrations must be transactional or have explicit crash-recovery semantics.

## 35. Unknown Enum

Unknown persisted enum values must fail safely during migration/read rather than silently mapping to permissive behavior.

## 36. Checksums/Digests

Request/plan/result digests may detect corruption or accidental mismatch. They are integrity aids, not cryptographic authorization by themselves.

## 37. SQLite

If SQLite is used, enable WAL where appropriate, foreign keys, busy handling, bounded transactions, and explicit synchronous durability appropriate to the safety requirement.

## 38. Transaction Size

Do not keep filesystem scanning or mutation inside a database transaction.

Persist metadata before/after external work and use journal semantics for the gap.

## 39. External Side Effects

Database transaction cannot atomically include filesystem mutation. Therefore mutation intent and reconciliation are mandatory.

## 40. Commit Ordering

For destructive operation:

```text
validate
→ persist operation intent
→ commit
→ execute mutation
→ persist observed outcome
→ verify
→ persist terminal operation
```

## 41. Crash Windows

Test crashes at every boundary above.

## 42. Worker Lease

Running attempts require lease/heartbeat metadata so restart can distinguish active/stale workers.

## 43. Lease Expiration

Expired lease does not prove operation failed. It proves ownership is stale.

## 44. Recovery Ownership

Recovery manager must acquire exclusive recovery ownership before inspecting/resolving a stale attempt.

## 45. Duplicate Recovery

Two recovery workers must not reconcile the same AttemptId concurrently.

## 46. Store Locking

Use database constraints/transactions for authoritative concurrency control rather than process-local mutexes alone.

## 47. Corruption

Store corruption must enter safe recovery mode; do not fabricate valid state.

## 48. Startup Recovery

Startup sequence:

```text
open store
→ validate schema
→ load unfinished jobs
→ detect stale leases
→ classify recovery requirements
→ publish recovered snapshot
→ start scheduler/workers
```

## 49. RecoveryRequired

Jobs whose mutation outcome cannot be established remain `RecoveryRequired` until reconciliation succeeds or an explicit terminal administrative decision is recorded.

## 50. Cancellation Persistence

Cancellation request must be durable before it is reported as accepted.

## 51. Cancellation Race

A persisted cancellation request does not retroactively cancel a mutation already committed to execution.

## 52. Shutdown

Graceful shutdown persists state before worker ownership is released.

## 53. SIGKILL / Power Loss

Design must assume no cleanup handler executes.

## 54. Atomic File Store

If any non-database state is persisted in files, use temp-file + fsync + rename + parent-directory durability as appropriate.

## 55. No Partial Config

A config write must never leave an unreadable active config after crash.

## 56. Retention

History retention must never remove records required for active recovery.

## 57. Garbage Collection

GC can delete only records proven unreachable from active/recoverable state.

## 58. Referential Integrity

Operation → Attempt → Job references must be enforced.

## 59. Foreign Keys

Use database foreign keys where supported.

## 60. Orphan Handling

Orphans found during startup are an integrity event, not silently deleted.

## 61. Monotonic Counters

Attempt number/event sequence must not be reused after crash.

## 62. Result Accounting

Freed bytes and counts should be persisted as immutable operation evidence, then aggregated into JobResult.

## 63. Aggregate Rebuild

Job totals should be reconstructable from operation records where practical.

## 64. Audit Rebuild

Audit trail should permit explaining why a destructive operation happened.

## 65. Privacy

Do not persist unnecessary filenames, package data, file contents, or sensitive metadata.

## 66. Path Redaction

Logs may use hashed/relative identifiers when full paths are unnecessary.

## 67. Store Access Layer

Domain services should depend on repository traits, not raw SQL scattered across workers.

## 68. Repository API

Recommended methods:

```rust
create_job()
load_job()
transition_job()
create_attempt()
transition_attempt()
create_operation()
append_operation_event()
mark_mutation_started()
record_observation()
record_verification()
claim_recovery()
complete_recovery()
```

## 69. Atomic Multi-Entity Transition

If a Job transition and Attempt creation must be observed together, persist them in one transaction.

## 70. Outbox

Events destined for IPC/UI/notifications should use an outbox or durable event queue when delivery matters.

## 71. At-Least-Once Events

Consumers must tolerate duplicate events.

## 72. Event Idempotency

Every published event needs stable EventId.

## 73. Publication Cursor

Consumers should maintain cursor/sequence rather than relying on timestamps.

## 74. Backpressure

Outbox growth must be bounded with explicit retention/compaction rules.

## 75. Definition of Done

Durable store is production-ready when:

- lifecycle state survives restart
- state transitions use CAS/versioning
- mutation intent is durable
- unknown outcomes are represented
- recovery is exclusive and deterministic
- duplicate submission is idempotent
- terminal state is immutable
- event publication is after durable commit
- schema migration is crash-safe
- active records cannot be garbage-collected
- store corruption fails safe
- crash-window tests exist

## 76. Final Invariants

1. Memory is never the source of truth for active Job state.
2. Failed durable transition is not a successful transition.
3. Job, Attempt, and Operation identities are distinct.
4. State versions are monotonic.
5. Duplicate request with same idempotency key is safe.
6. Same idempotency key with different request is rejected.
7. Mutation intent precedes mutation.
8. Unknown mutation outcome is never converted to Failed automatically.
9. Unknown outcome is never replayed blindly.
10. Recovery ownership is exclusive.
11. Terminal results are immutable.
12. Events are durable before reliable publication.
13. External filesystem mutation is never assumed atomic with DB transaction.
14. Crash recovery is based on evidence, not guesswork.
15. Persistence corruption never grants destructive authority.
