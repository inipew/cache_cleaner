# 91.md — Security Model, Trust Boundaries, dan Privilege Separation

## Tujuan

Cache cleaner berjalan dekat filesystem dan, pada Android, berpotensi memiliki privilege tinggi. Karena itu security tidak boleh dianggap sebagai fitur tambahan. Security harus menjadi bagian dari domain contract: siapa yang boleh meminta, apa yang boleh dilakukan, terhadap target mana, dengan authority apa, dan bagaimana privilege dibatasi.

Prinsip utama:

```text
untrusted input
    ↓
validate
    ↓
authenticate/identify
    ↓
authorize
    ↓
safety gate
    ↓
least-authority execution
```

## 1. Threat Model

Threat model minimal mencakup:

- local unprivileged process
- compromised client
- malformed IPC request
- malicious path input
- symlink/path traversal
- target replacement race
- stale authorization
- corrupted durable state
- compromised plugin/helper
- accidental operator misuse

Daemon tidak boleh mengasumsikan semua client adalah trusted hanya karena IPC berjalan lokal.

## 2. Trust Boundaries

Boundary utama:

```text
CLI/UI/client
      │
      ▼
     IPC
      │
      ▼
 daemon domain
      │
 ┌────┴────┐
 ▼         ▼
durable   platform
store     adapter
      │
      ▼
 filesystem / kernel
```

Setiap crossing boundary harus memvalidasi data dan authority.

## 3. IPC Is Untrusted

IPC client tidak boleh menentukan:

- authorization granted
- safety result
- trusted root
- target identity
- executor permission

Client hanya mengajukan intent.

## 4. Authentication vs Authorization

Authentication/identity menjawab:

> siapa yang meminta?

Authorization menjawab:

> apa yang boleh dilakukan identity tersebut?

Keduanya tidak boleh dicampur menjadi satu boolean `is_admin`.

## 5. Capability-Based Authority

Executor menerima capability yang sempit, misalnya:

```text
DeleteTargetCapability
scope = TargetIdentity
operation = Delete
expires = ...
generation = ...
```

Bukan raw global filesystem privilege.

## 6. Least Privilege

Daemon sebaiknya memisahkan:

- control plane
- planning
- scanning
- privileged mutation

Jika platform memungkinkan, bagian non-privileged sebaiknya tetap non-privileged.

## 7. Privilege Boundary

Jika privileged helper diperlukan, protocol helper harus:

- typed
- minimal
- authenticated
- scoped
- bounded
- auditable

Jangan membuat helper menerima arbitrary shell command.

## 8. No Shell by Default

Filesystem mutation sebaiknya menggunakan direct syscall/API.

Jangan mengubah user-controlled path menjadi command string.

Contoh berbahaya:

```text
rm -rf <input>
```

Contoh yang lebih aman:

```text
openat/unlinkat with validated descriptor context
```

## 9. Path Input

Path dari IPC/CLI dianggap untrusted data.

Normalisasi string bukan safety proof.

Safety menggunakan trusted root, object identity, mount identity, dan FD-relative resolution sesuai target contract.

## 10. Symlink Attack

Symlink dapat mengubah destination antara validation dan mutation.

Operation contract harus menentukan no-follow semantics dan menggunakan APIs yang mencegah traversal keluar dari trusted boundary.

## 11. TOCTOU

Pola berbahaya:

```text
check path
→ later mutate path
```

Jika filesystem dapat berubah di antaranya, check lama tidak cukup.

Gunakan descriptor-relative operation dan revalidation dekat mutation boundary.

## 12. Target Identity

Path identity tidak selalu cukup.

Target descriptor sebaiknya dapat menyimpan identity seperti:

- device/mount identity
- inode/object identity
- generation
- expected type

## 13. Mount Boundary

Trusted root tidak otomatis berarti seluruh descendant aman.

Cross-mount traversal harus sesuai policy.

Mount identity perlu diverifikasi ketika contract membutuhkannya.

## 14. Authorization Freshness

Authorization harus valid pada saat mutation.

Authorization yang diberikan lima menit lalu tidak otomatis berlaku setelah:

- config generation berubah
- catalog generation berubah
- target identity berubah
- scope berubah
- lease expired

## 15. Safety Tidak Bisa Dibypass

Flag seperti:

```text
--force
--yes
--root
```

tidak boleh bypass hard safety invariant.

Force dapat mengubah user confirmation/policy choice, tetapi tidak boleh mengubah trusted-root boundary atau authorization contract secara sembarangan.

## 16. Sensitive Operations

Operations harus diklasifikasikan berdasarkan risk:

```text
ReadOnly
Reversible
Destructive
Privileged
Maintenance
```

Higher-risk operation membutuhkan stronger authorization/safety.

## 17. Dangerous Target Classes

Target catalog harus dapat menandai target yang tidak boleh dibersihkan atau memerlukan explicit policy.

Contoh kategori:

- system-critical
- user data
- application state
- temporary/cache
- unknown

Unknown default-nya conservative.

## 18. Deny by Default

Jika safety metadata tidak lengkap atau target classification tidak dikenal:

```text
no mutation
```

Daemon lebih baik melewatkan candidate daripada menghapus object yang tidak dapat dibuktikan aman.

## 19. Configuration Security

Configuration bukan sekadar preference.

Config yang menentukan destructive policy harus dianggap security-sensitive.

File permission, ownership, format validation, and atomic update harus diperhatikan.

## 20. Config Source Trust

Jangan membaca configuration dari arbitrary path yang diberikan untrusted client lalu memperlakukannya sebagai daemon authority.

Active config source ditentukan oleh daemon/system policy.

## 21. Secret Handling

Jika konfigurasi mempunyai credential/token, jangan:

- log value
- include value in error strings
- send through broad IPC response
- persist unnecessarily

Gunakan redaction.

## 22. Logging Security

Log dapat berisi:

- path
- package information
- mount information
- request identity

Logging policy harus mencegah accidental disclosure dan injection.

Structured logging lebih aman daripada concatenating arbitrary user strings ke command-like logs.

## 23. Log Injection

User-controlled names dapat mengandung newline/control characters.

Structured logger/escaping harus memastikan satu event tetap satu event.

## 24. Audit

Security-relevant action sebaiknya dapat ditelusuri:

```text
who
what
target identity
when
authorization
result
```

Audit record tidak boleh menyimpan secret.

## 25. Replay Protection

IPC request dengan idempotency key/nonce dapat mencegah replay yang tidak diinginkan.

Replay handling harus konsisten dengan `87.md`.

## 26. Rate Limiting

Authentication/authorization failure dan destructive request dapat dibatasi agar client tidak menghasilkan request storm.

Rate limiting bukan security boundary tunggal.

## 27. IPC Socket Security

Local IPC transport harus memakai OS-level access control bila tersedia.

Filesystem socket permission saja tidak boleh menjadi satu-satunya assumption jika deployment memiliki stronger identity mechanism.

## 28. Client Identity

Jika platform menyediakan peer credentials, daemon dapat menggunakannya untuk mengidentifikasi caller.

Jangan mempercayai field `uid` yang dikirim client sendiri.

## 29. Android Identity

Pada Android, identity/caller model harus mengikuti mekanisme platform yang benar. Root privilege tidak boleh membuat daemon menganggap semua application caller setara.

## 30. Privilege Drop

Jika daemon hanya membutuhkan privilege tinggi pada mutation phase, privilege exposure sebaiknya diminimalkan.

Architecture dapat menggunakan privileged adapter/helper daripada menjalankan seluruh control plane sebagai unrestricted root.

## 31. Memory Safety

Rust memberikan memory safety pada safe code, tetapi:

- `unsafe`
- FFI
- ioctl
- raw FD
- raw pointers

tetap menjadi security-sensitive boundaries.

## 32. Unsafe Code Policy

Setiap `unsafe` block harus mempunyai alasan dan invariant lokal.

Hindari satu module besar berisi semua unsafe syscall wrappers.

Lebih baik typed safe wrapper:

```text
raw syscall
→ validate return
→ typed object
→ domain code
```

## 33. FFI

FFI boundary harus memvalidasi:

- pointer validity
- length
- ownership
- lifetime
- return codes

Jangan membiarkan FFI types bocor ke domain layer.

## 34. Resource Exhaustion

Security juga mencakup DoS melalui:

- huge path
- huge candidate set
- recursive tree
- many IPC requests
- many concurrent jobs
- malformed database records

Semua harus mempunyai bounds.

## 35. Archive / Special File Safety

Jika scanner mendukung archive atau special file classification, jangan mengikuti arbitrary links/device nodes/FIFO sebagai normal file.

Target type harus diverifikasi sebelum mutation.

## 36. Package/Application Data

Android application directories dapat mempunyai ownership/permission semantics yang berbeda.

Daemon harus menggunakan target catalog + platform adapter daripada hard-coded assumption bahwa semua app cache dapat dihapus.

## 37. SELinux

Root bukan berarti seluruh SELinux policy dapat diabaikan.

Operation failure karena SELinux harus menjadi explicit platform/security result, bukan diperlakukan sebagai permission error generik tanpa context.

## 38. Update Security

Binary/config/schema upgrade harus mencegah downgrade yang dapat merusak security invariants.

Migration code sendiri adalah privileged code dan harus diuji.

## 39. Dependency Security

Dependency dengan unsafe/native code memiliki attack surface tambahan.

Lockfile harus dipertahankan dan dependency update perlu review.

## 40. Supply Chain

Release sebaiknya memiliki:

- reproducible build bila feasible
- signed artifact/update metadata bila deployment membutuhkan
- pinned dependency versions
- integrity verification

## 41. Secure Failure

Security failure harus fail-closed:

```text
authorization unavailable
→ no destructive mutation

safety unavailable
→ no destructive mutation

target identity unverifiable
→ no destructive mutation
```

## 42. Recovery Security

Recovery tidak boleh menjadi privilege escalation path.

State lama tidak otomatis memberikan authority baru.

Recovery tetap harus memperoleh current authorization/safety untuk mutation baru.

## 43. Debug Mode

Debug mode tidak boleh menonaktifkan hard safety/authorization tanpa explicit development-only mechanism.

Production binary sebaiknya tidak mempunyai hidden bypass.

## 44. Test Security Boundary

Minimal test:

- traversal
- symlink race
- target replacement
- malformed IPC
- unauthorized request
- stale capability
- expired capability
- config permission violation
- corrupt state
- resource exhaustion
- replay

## 45. Definition of Done

Security model production-ready jika:

- trust boundaries jelas
- IPC dianggap untrusted
- identity dan authorization terpisah
- capability scoped
- no arbitrary shell execution
- TOCTOU ditangani
- target identity digunakan
- force tidak bypass hard safety
- config authority terlindungi
- secret redaction tersedia
- audit trail tersedia
- caller identity tidak berasal dari client payload
- privilege exposure dibatasi
- unsafe/FFI boundaries typed
- resource exhaustion bounded
- recovery tidak menjadi privilege escalation

## Final Invariants

1. Client tidak pernah menjadi authority.
2. IPC selalu dianggap untrusted.
3. Authentication berbeda dari authorization.
4. Authorization berbeda dari safety.
5. Raw root privilege bukan capability model.
6. Target path bukan satu-satunya identity.
7. TOCTOU tidak boleh dibiarkan pada destructive path.
8. Force tidak boleh bypass hard safety.
9. Unknown target default-nya tidak boleh dimutasi.
10. Config authority harus trusted.
11. Secret tidak boleh masuk log.
12. Caller identity tidak boleh berasal dari self-reported client field.
13. Recovery tidak memberikan authority baru.
14. Privileged code harus sesempit mungkin.
15. Unsafe/FFI harus mempunyai invariant lokal.
16. Resource exhaustion harus bounded.
17. Security failure destructive harus fail-closed.
18. Replay harus ditangani.
19. Audit harus dapat menghubungkan actor, operation, target, dan result.
20. Tidak ada hidden production bypass.
