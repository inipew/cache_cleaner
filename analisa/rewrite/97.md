# 97.md — Upgrade, Rollback, Compatibility, dan Release Safety

## Tujuan

Upgrade daemon yang mengelola durable jobs dan filesystem mutation harus diperlakukan sebagai perubahan sistem, bukan sekadar mengganti binary.

Target:

```text
upgrade
→ preserve durable state
→ preserve safety invariants
→ preserve recovery ability
→ activate new behavior atomically
```

## 1. Version Dimensions

Bedakan:

- BinaryVersion
- SchemaVersion
- ProtocolVersion
- PolicyVersion
- PlanVersion
- TargetCatalogVersion

Tidak boleh ada satu angka `version` yang mewakili semuanya.

## 2. Compatibility Matrix

Release harus mendefinisikan compatibility antara binary, schema, protocol, dan persisted plans.

Contoh:

```text
new binary + old schema = supported via migration
new binary + old protocol = maybe supported
old binary + new schema = usually unsupported
```

## 3. Admission Freeze

Untuk migration berisiko:

```text
stop new mutation admission
→ recover active work
→ migrate
→ validate
→ start new binary
```

## 4. Active Operation

Upgrade tidak boleh menghapus atau mengubah unresolved operation menjadi success.

Recovery setelah upgrade membaca durable evidence yang ada.

## 5. Graceful Shutdown Is Optimization

Graceful shutdown mempercepat restart, tetapi correctness tidak boleh bergantung padanya.

Crash pada titik mana pun harus mengikuti recovery contract.

## 6. Atomic Binary Activation

Deployment harus memastikan daemon menjalankan binary lama atau baru secara valid, bukan partially replaced executable/runtime.

## 7. Config Compatibility

New binary harus memvalidasi config schema dan semantics.

Invalid configuration tidak boleh mengaktifkan destructive work.

## 8. Policy Compatibility

Jika policy semantics berubah, historical operation tetap merekam policy version yang digunakan.

New work menggunakan policy baru setelah activation boundary.

## 9. Plan Compatibility

Persisted plan dari binary lama hanya boleh dieksekusi jika plan schema dan semantics compatible.

Jika tidak:

```text
stale/incompatible
→ replan
```

## 10. Protocol Compatibility

IPC clients dapat berasal dari binary berbeda selama restart/update.

Protocol negotiation/versioning harus mencegah client mengirim request yang daemon tidak pahami.

## 11. Feature Negotiation

Capability discovery harus explicit.

Client tidak boleh mengandalkan version string saja untuk menentukan feature availability.

## 12. Database Migration

Migration harus mengikuti `93.md`:

```text
validate
→ transactional migration
→ integrity check
→ activate
```

## 13. Rollback

Rollback hanya aman jika schema/policy/protocol state masih compatible.

Jangan menganggap:

```text
new binary → old binary
```

selalu reversible.

## 14. Rollback With Migrated Schema

Jika schema telah forward-migrated, pilihan yang aman biasanya:

- keep new binary
- provide explicit downgrade migration
- restore verified backup

Bukan silent schema mutation.

## 15. Failed Upgrade

Jika new binary gagal startup:

```text
preserve durable state
→ report failure
→ supervisor backoff
→ rollback only if compatibility contract permits
```

## 16. Crash Loop Protection

Repeated startup failures harus menghasilkan bounded retry/backoff.

Jika diperlukan, enter recovery/manual intervention state.

## 17. Artifact Integrity

Release artifact sebaiknya memiliki integrity verification dan, untuk deployment yang memerlukannya, signature verification.

## 18. Dependency Reproducibility

Lockfile dan build metadata perlu dipertahankan agar release dapat direproduksi/ditelusuri.

## 19. Migration Marker

Upgrade/migration state harus durable.

Jangan mengandalkan marker di RAM atau log.

## 20. Release Transaction

Conceptual release transaction:

```text
stage new binary/config
→ validate compatibility
→ freeze admission
→ durable checkpoint
→ activate
→ health/readiness check
→ resume admission
```

## 21. Health Gate

New binary tidak boleh dianggap successful hanya karena process started.

Minimal health gate memeriksa:

- durable store
- migration
- IPC
- platform adapter
- recovery
- scheduler readiness

## 22. Automatic Rollback

Automatic rollback harus conservative.

Jika outcome operation/upgrade masih ambiguous, jangan menggabungkan rollback dengan filesystem mutation recovery tanpa evidence.

## 23. Config Rollback

Config rollback harus atomic dan schema-valid.

Policy rollback tidak boleh memutar kembali hard safety boundary.

## 24. Database Backup

Backup sebelum upgrade dapat membantu, tetapi restore harus diverifikasi.

Restore database saja tidak otomatis restore filesystem state.

## 25. Filesystem State

Database dan filesystem adalah consistency domains terpisah.

Rollback database tidak boleh membuat daemon menganggap filesystem kembali ke state lama.

## 26. Operation Journal

Historical journal harus dipertahankan selama retention period yang diperlukan untuk recovery/audit.

## 27. Idempotency Records

Upgrade tidak boleh menghapus idempotency records yang masih diperlukan untuk mencegah duplicate Job.

## 28. Lease Records

Stale lease dapat direcover setelah restart berdasarkan owner identity/epoch/timeout semantics.

## 29. Versioned Executor

Executor dapat menyimpan implementation version pada Attempt.

Ini membantu diagnosis ketika behavior berubah antar release.

## 30. Compatibility Failure

Jika persisted state tidak compatible:

```text
no destructive execution
→ degraded/recovery mode
→ diagnostic information
```

## 31. Rollout Strategy

Untuk production deployment, gunakan staged rollout bila deployment environment memungkinkan.

Contoh:

```text
canary
→ observe
→ wider rollout
→ full rollout
```

## 32. Device Diversity

Android filesystem/vendor behavior dapat berbeda.

Release acceptance harus mempertimbangkan device/Android/filesystem matrix.

## 33. Upgrade During Idle

Ideal upgrade window adalah ketika tidak ada active mutation.

Namun correctness tetap harus aman jika upgrade terjadi ketika Job queued/active.

## 34. Upgrade During Suspend

Upgrade mechanism tidak boleh mengasumsikan scheduler aktif ketika device suspended.

Activation harus mengikuti platform lifecycle.

## 35. Rollback During Recovery

Rollback saat operation Unknown sedang direcover sangat sensitif.

Recovery evidence harus dipertahankan dan new binary harus mampu melanjutkan/reclassify dengan aman.

## 36. Schema Downgrade

Downgrade schema hanya jika information-preserving dan explicitly tested.

Jika tidak, old binary harus dianggap incompatible.

## 37. Release Notes

Release notes harus mencatat:

- schema changes
- policy changes
- safety changes
- protocol changes
- migration requirements
- rollback limitations

## 38. Test Matrix

Test release dengan:

- clean install
- upgrade idle
- upgrade queued
- upgrade active operation
- crash during activation
- crash during migration
- rollback
- stale client
- old config
- old durable state

## 39. Definition of Done

Upgrade/rollback production-ready jika:

- version dimensions separated
- compatibility matrix documented
- admission freeze tersedia
- active operations recoverable
- migration atomic
- rollback limitations explicit
- health gate tersedia
- crash loop controlled
- artifact integrity verified
- database/filesystem consistency distinction preserved
- old clients handled explicitly
- device diversity tested

## Final Invariants

1. Upgrade bukan sekadar binary replacement.
2. Durable state harus survive upgrade.
3. Version dimensions harus terpisah.
4. New binary tidak boleh mutate sebelum compatibility/migration valid.
5. Graceful shutdown bukan correctness requirement.
6. Rollback tidak boleh diasumsikan reversible.
7. Database restore bukan filesystem rollback.
8. Unknown operation tetap Unknown sampai evidence tersedia.
9. Idempotency records harus dipertahankan.
10. Lease recovery harus explicit.
11. New binary harus melewati readiness gate.
12. Crash loop harus bounded.
13. Security/safety invariants tidak boleh melemah karena rollback.
14. Protocol compatibility harus explicit.
15. Persisted plan harus compatible atau direplan.
16. Release artifact harus dapat diverifikasi.
17. Migration marker harus durable.
18. Upgrade saat active work harus recoverable.
19. Device/filesystem diversity harus masuk release testing.
20. Compatibility failure fail-closed terhadap destructive work.
