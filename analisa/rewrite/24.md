Lanjut ke **Authorization boundary**. Ini layer yang memastikan bahwa request memang boleh meminta suatu operasi, lalu menghasilkan `AuthorizedPlan` yang boleh masuk ke Executor.

Prinsip utamanya:

> **Authorization menentukan “siapa boleh meminta apa”; Safety menentukan “apa yang aman disentuh”. Authorization tidak pernah menggantikan Safety.**

---

# 423. Struktur

Saya sarankan authorization tetap kecil dan tidak dibuat sebagai subsystem besar:

```text
src/safety/
├── authorization.rs
├── capability.rs
└── proof.rs

src/ipc/
├── auth.rs
├── permissions.rs
└── protocol.rs
```

Pembagian:

```text
IPC
  ↓
PeerIdentity
  ↓
Role
  ↓
Capabilities
  ↓
Authorization
  ↓
AuthorizedPlan
  ↓
Executor
```

---

# 424. `PeerIdentity`

Credential berasal dari kernel, bukan dari payload IPC.

```rust
pub struct PeerIdentity {
    pub pid: u32,
    pub uid: u32,
    pub gid: u32,
}
```

Request seperti ini **tidak boleh dipercaya**:

```json
{
  "role": "root"
}
```

atau:

```json
{
  "uid": 0
}
```

Authority berasal dari `SO_PEERCRED`.

---

# 425. Role

Untuk v1:

```rust
pub enum Role {
    Root,
    System,
    Shell,
    Unknown,
}
```

Mapping dilakukan dari credential aktual.

Misalnya secara konseptual:

```text
uid 0       → Root
system uid  → System
shell uid   → Shell
lainnya     → Unknown
```

Jangan menyebarkan angka UID Android ke seluruh codebase.

Buat satu resolver:

```rust
pub trait RoleResolver {
    fn resolve(&self, peer: &PeerIdentity) -> Role;
}
```

---

# 426. Capability

Role sebaiknya tidak langsung dipakai sebagai authorization logic.

Gunakan capability:

```rust
pub enum Capability {
    ReadStatus,
    Explain,
    StartCleanup,
    DeepCleanup,
    Trim,
    ZramMaintenance,
    ReloadConfig,
    RestartDaemon,
    StopDaemon,
```

Kemudian:

```text
Role → CapabilitySet
```

# 428. Root bukan super-bypass

Ini harus menjadi invariant eksplisit:

```text
Root
  ↓

  ↓

  ↓

  ↓
```

Bukan:


# 429. Jangan beri capability `BypassSafety`

Jangan pernah membuat:

atau:

```rust

```

Bahkan untuk Root.

Karena sekali capability ini ada, layer Executor akhirnya perlu menerima special case:

# 433. Tetapi authorization juga perlu diperiksa lagi

# 436. Executor API

Ini sekarang menjadi:

# 437. Kenapa ini penting?

Karena compile-time API sudah mengomunikasikan:

```text
Candidate
    ≠

    ≠
AuthorizedPlan
```

Jadi developer tidak bisa dengan mudah melewati tahap:


# 438. Authorization terhadap plan

Misalnya request:

```text
Normal cleanup
```

Plan:

```text
RemoveFile
RemoveFile
Trim
```

Jika caller hanya punya:

```text
StartCleanup
```

maka:

```text
file operations → allowed
Trim            → denied
```

Plan tidak boleh masuk Executor dalam keadaan setengah authorized.

---

# 439. Pilihan desain

Ada dua pendekatan:

### A. Reject entire plan

Jika satu operation tidak authorized:

```text
Plan:
  file delete
  file delete
  trim

caller lacks Trim
```

→ reject seluruh plan.

### B. Remove unauthorized operations

Plan diubah menjadi:

```text
file delete
file delete
```

Saya merekomendasikan **A** untuk v1.

Karena Authorization tidak boleh diam-diam mengubah plan setelah plan dibuat.

Jika request tidak valid:

```text
reject request
```

atau:

```text
rebuild plan dengan capability yang tersedia
```

tetapi jangan mutate `CleanupPlan`.

# 448. Disconnect semantics

Jika client:

```text

```

kemudian socket disconnect:

```text
client dies
```

job tetap berjalan.

Karena:

```text
IPC connection
```

bukan ownership dari:

```text
Job
```

Scheduler memiliki Job.

# 449. Cancel berbeda

Client secara eksplisit:


→ Scheduler memberi:

```text
CancellationToken
```

→ worker berhenti pada safe boundary.


# 456. Invariant paling penting

Saya akan tulis ini sebagai komentar arsitektur di source:

```text
Authorization never grants permission to violate safety invariants.

A privileged caller may request a privileged operation,
but the operation must still be represented by a valid plan,
validated against trusted targets, and revalidated at execution time.
```

```text
                     │

                 Scheduler
                     │

                     │
                     ▼

                     │

                     │
                     ▼

                     │
                     ▼

                     │
                     ▼

                     │

                     │
                     ▼

                     │
                     ▼

                     │
```

Ada satu hal yang sengaja saya pertahankan: **authorization muncul dua kali secara konseptual**, tetapi bukan berarti kita melakukan login dua kali. Yang pertama adalah **request admission** agar pekerjaan boleh dimulai; yang kedua adalah **binding capability ke immutable plan** sebelum plan masuk ke destructive boundary.

**Tahap berikutnya paling penting secara teknis: kita bedah `executor/filesystem/` sampai level syscall—`openat`, `fstatat(AT_SYMLINK_NOFOLLOW)`, `unlinkat`, directory traversal, identity revalidation, race handling, `openat2` fallback, cancellation, dan mapping `errno` menjadi `OperationResult`.**
