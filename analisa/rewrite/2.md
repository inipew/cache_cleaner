Iya. Kalau benar-benar mau **rewrite total**, pembahasan sebelumnya baru level *arsitektur*. Yang masih perlu dibedah justru bagian paling penting: **kontrak fungsi, data flow, logic tiap fungsi, invariant, error handling, dan hubungan antar-fungsi**.

Saya akan membahasnya dalam beberapa lapisan.

## 1. Fungsi inti cleaning engine

Ini harus menjadi pusat desain.

```text
scan()
  ↓
classify()
  ↓
validate()
  ↓
plan()
  ↓
execute()
  ↓
verify()
  ↓
report()
```

Masing-masing perlu kita definisikan sampai level API.

### `scan_candidates()`

Tugas:

* membuka root directory
* traversal
* membaca metadata
* menghitung size
* mendeteksi file/dir/symlink
* menangani permission error
* menghormati cancellation
* tidak pernah melakukan delete

Contoh kontrak:

```rust
pub trait Scanner {
    fn scan(
        &self,
        root: &ScanRoot,
        options: &ScanOptions,
    ) -> Result<Vec<Candidate>, ScanError>;
}
```

Yang perlu dibahas lebih jauh:

```text
- DFS atau iterative stack?
- symlink diperlakukan bagaimana?
- hardlink?
- mount point?
- bind mount?
- permission denied?
- directory berubah saat traversal?
- file hilang di tengah scan?
- maximum depth?
- maximum candidates?
- size accounting?
```

Ini salah satu fungsi paling kritis.

---

# 2. `classify_candidate()`

Scanner hanya mengatakan:

> "Saya menemukan `/foo/bar`."

Classifier menentukan:

> "Ini cache jenis apa?"

Misalnya:

```rust
pub enum TargetKind {
    AppCache,
    AppCodeCache,
    PackageCache,
    FrameworkCache,
    Temporary,
    Unknown,
}
```

Lalu:

```rust
fn classify_candidate(
    candidate: &RawCandidate,
    context: &SystemContext,
) -> Classification;
```

Logic-nya perlu kita desain secara eksplisit.

Contoh:

```text
/data/user/0/<package>/cache
        ↓
AppCache

/data/user_de/0/<package>/cache
        ↓
AppCache / DE

/data/dalvik-cache
        ↓
FrameworkCache

unknown location
        ↓
Unknown
```

Dan:

**Unknown harus default deny**, bukan default allow.

---

# 3. `validate_candidate()`

Ini sebenarnya lebih penting daripada delete.

```rust
fn validate_candidate(
    candidate: &Candidate,
    context: &SafetyContext,
) -> ValidationResult;
```

Harus menjawab:

```text
Apakah path valid?
Apakah masih berada di root?
Apakah device sama?
Apakah symlink?
Apakah filesystem diizinkan?
Apakah user valid?
Apakah storage unlocked?
Apakah umur memenuhi policy?
Apakah target sedang digunakan?
Apakah ada restriction?
```

Output jangan cuma:

```rust
bool
```

Tetapi:

```rust
pub enum Validation {
    Allowed,
    Rejected(RejectReason),
}
```

supaya `explain` bisa mengatakan **kenapa**.

# 4. `build_cleanup_plan()`

Ini fungsi yang menurut saya perlu dijadikan centerpiece.

```rust
fn build_cleanup_plan(
    candidates: Vec<ValidatedCandidate>,
    policy: &CleanupPolicy,
) -> CleanupPlan;
```

Misalnya:

```text
Candidate A → delete
Candidate B → skip: too young
Candidate C → delete
Candidate D → skip: CE locked
Candidate E → defer
```

Hasil:

```rust
CleanupPlan {
    operations: ...,
    skipped: ...,
    deferred: ...,
    estimated_freed: ...,
}
```

Dengan ini kita bisa mendapatkan:

```bash
cleaner scan
cleaner clean --dry-run
cleaner explain
```

dari pipeline yang sama.

# 6. `remove_directory()` perlu dibahas sangat detail

Ini kemungkinan salah satu fungsi **paling sensitif dalam seluruh project**.

Bukan sekadar:

```rust
std::fs::remove_dir_all()
```

Kita perlu menentukan:

```text
openat()
fstatat()
getdents()
unlinkat()
O_DIRECTORY
O_NOFOLLOW
AT_SYMLINK_NOFOLLOW
```

dan behavior ketika:

```text
directory berubah
file hilang
symlink muncul
mount muncul
permission berubah

```

Bahkan sebaiknya ada invariant:

> Setelah `DirectoryHandle` dibuka, seluruh traversal dan deletion dilakukan relatif terhadap handle tersebut.

Ini layak kita desain sampai pseudo-code/syscall sequence.

# 10. Safety guard

Selain policy, ada **hard safety rules** yang tidak boleh dikonfigurasi.

Contoh:

```text
NEVER follow symlink
NEVER cross device boundary
NEVER delete outside trusted root
NEVER delete unknown target
NEVER operate on locked CE
NEVER execute unauthorized IPC command
```

Ini jangan dijadikan:

```toml
allow_cross_device = true
```

Tidak boleh.

Hard safety ≠ configurable policy.

# 24. Saya akan buat "function inventory"

Untuk rewrite serius, kita sebaiknya punya dokumen seperti:

| Module     | Function       | Tipe        | Side Effect | Safety   |
| ---------- | -------------- | ----------- | ----------- | -------- |
| scanner    | `scan()`       | core        | read FS     | high     |
| scanner    | `walk()`       | core        | read FS     | critical |
| classifier | `classify()`   | pure        | none        | medium   |
| safety     | `validate()`   | pure/read   | none        | critical |
| planner    | `build()`      | pure        | none        | critical |
| executor   | `remove()`     | destructive | delete      | critical |
| verifier   | `verify()`     | read        | none        | high     |
| scheduler  | `should_run()` | pure        | none        | high     |
| ipc        | `authorize()`  | pure        | none        | critical |
| kernel     | `trim()`       | destructive | kernel      | critical |

Kemudian kita bisa menentukan mana yang:

```text
PURE
READ-ONLY
MUTATING
DESTRUCTIVE
PRIVILEGED
```

Saya sangat merekomendasikan klasifikasi ini.

# 25. Bahkan function naming bisa kita standarkan

Misalnya:

### `get_*`

Untuk retrieval sederhana:

```rust
get_user()
get_config()
```

### `read_*`

Untuk membaca state external:

```rust
read_thermal_state()
read_f2fs_state()
```

### `detect_*`

Untuk capability/environment:

```rust
detect_filesystem()
detect_capabilities()
```

### `is_*`

Untuk predicate:

```rust
is_unlocked()
is_safe_target()
is_supported()
```

### `validate_*`

Untuk safety validation:

```rust
validate_target()
validate_plan()
```

### `build_*`

Untuk membuat immutable object:

```rust
build_plan()
build_context()
```

### `execute_*`

Untuk mutating action:

```rust
execute_plan()
execute_operation()
```

### `restore_*`

Untuk rollback/state restoration:

```rust
restore_scheduler()
restore_f2fs_state()
```

Dengan konvensi seperti ini codebase terasa jauh lebih konsisten.

## Urutan pembahasan yang paling masuk akal

Kalau kita lanjut secara serius, saya sarankan **jangan langsung coding**.

Kita bedah dalam urutan:

```text
1. Domain model
       ↓
2. Semua fungsi core
       ↓
3. Filesystem walker
       ↓
4. Safety/security logic
       ↓
5. Cleaning planner
       ↓
6. Executor
       ↓
7. Scheduler/state machine
       ↓
8. Android abstraction
       ↓
9. Kernel abstraction
       ↓
10. IPC protocol
       ↓
11. CLI
       ↓
12. Daemon lifecycle
       ↓
13. Error model
       ↓
14. Logging/metrics
       ↓
15. Testing strategy
       ↓
16. Baru implementasi
```

**Dan saya rasa langkah berikutnya paling penting adalah nomor 1–2:** kita buat **inventaris seluruh fungsi dari project lama**, lalu saya petakan satu per satu menjadi:

```text
OLD FUNCTION
    ↓
masih diperlukan?
    ↓
dipindah ke mana?
    ↓
nama baru
    ↓
signature baru
    ↓
input/output
    ↓
side effect
    ↓
safety requirement
    ↓
test yang wajib
```

Dari situ kita bisa sampai ke level yang sangat konkret, misalnya menentukan **`Scanner`, `Walker`, `Candidate`, `Policy`, `Validator`, `CleanupPlan`, `Executor`, `RuntimeContext`, dan seluruh method-nya satu per satu**, bukan lagi sekadar diagram arsitektur.
