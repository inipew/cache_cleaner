# 78.md — Resource Manager, Concurrency, Locks, Budgets, Reservations, Fairness, and Deadlock Safety Contract

## Tujuan

ResourceManager mengatur konsumsi resource daemon secara global. Ia mencegah scan, delete, reclaim, maintenance, dan worker concurrency saling membebani filesystem/device atau membuat deadlock.

## 1. Resource Types

Minimal resource classes:

- worker slots
- scan slots
- mutation slots
- storage/volume slots
- IO budget
- memory budget
- operation budget
- maintenance exclusivity

## 2. Typed ResourceId

Resource identity harus typed.

## 3. ReservationId

Setiap reservation memiliki typed ReservationId.

## 4. Reservation Lifecycle

```text
Requested → Granted → Active → Released
                    ↘ Cancelled
                    ↘ Expired
```

## 5. Reservation Is Durable When Needed

Long-lived reservations that affect crash recovery must have durable ownership/lease metadata.

## 6. Admission

Resource admission terjadi sebelum worker mulai resource-intensive execution.

## 7. No Implicit Unlimited

Missing resource limit berarti configured default, bukan infinity.

## 8. Global Limits

Global concurrency must be bounded.

## 9. Per-Resource Limits

Storage/device can have independent concurrency limits.

## 10. Per-Job Limit

A single Job must not consume the entire daemon capacity unless explicitly configured and safely bounded.

## 11. Weighted Resources

Large operations can consume more budget than small ones.

## 12. Byte Budget

Use typed `ByteCount`, not arbitrary `u64` across domain code.

## 13. Operation Cost

Planner should estimate cost where possible; Executor reports actual usage.

## 14. Reservation vs Usage

Reservation is admission guarantee. Usage is observed consumption.

They must not be conflated.

## 15. Budget Overshoot

External filesystem behavior can exceed estimates. ResourceManager must retain emergency headroom.

## 16. Memory Budget

Scan metadata accumulation must be bounded and preferably streaming.

## 17. Candidate Limit

Maximum candidate count per Job must be enforced.

## 18. Path Length Limit

Candidate path length must be bounded.

## 19. Directory Entry Limit

Scanner must have bounded traversal work.

## 20. Queue Limit

Resource pressure can apply backpressure to scheduler queue.

## 21. Lock Classes

Recommended ordering:

```text
Global admission
→ storage resource
→ target lock
→ operation-local lock
```

Never acquire in reverse order.

## 22. Lock Hierarchy

Every lock class must have documented ordering.

## 23. Deadlock Prevention

Avoid nested dynamic locks where possible.

## 24. Try-Lock

For high-contention optional resources, try-lock + defer can prevent scheduler stalls.

## 25. No Filesystem Lock as DB Lock

Filesystem locks must not be treated as authoritative lifecycle state.

## 26. Process Lock

Daemon singleton lock may protect duplicate daemon instances, but it is not operation ownership.

## 27. Worker Ownership

Worker lease identifies execution ownership.

## 28. Reservation Ownership

Reservation must be bound to JobId/AttemptId where appropriate.

## 29. Lease

Resource reservation may expire if owner dies.

## 30. Expiry Safety

Expired reservation cannot permit new mutation by stale owner.

## 31. Stale Owner

Worker must verify ownership before long operation and at safe boundaries.

## 32. Cancellation

Cancellation should release waiting reservations without blocking on unrelated work.

## 33. Release Idempotency

Calling release twice must be harmless.

## 34. Reservation Identity

A stale ReservationId must not release another Job's reservation.

## 35. Resource Generation

Reservation may carry ResourceGeneration when topology/capacity can change.

## 36. Storage Identity

Per-volume resource should bind to StorageIdentity, not path string.

## 37. Mount Identity

When mount-specific serialization is required, use MountIdentity.

## 38. Same Path Different Mount

Never share a lock merely because lexical path is equal if mount identity differs.

## 39. Same Storage Different Targets

Multiple targets on same storage may share IO budget even if target locks differ.

## 40. Target Exclusivity

Destructive operations on the same target may require exclusive target lock.

## 41. Read vs Write

Scanning can sometimes run concurrently with scanning but should be coordinated with mutation to avoid unstable results.

## 42. Mutation Exclusion

Planner should prefer exclusive mutation reservation for target scopes that cannot safely overlap.

## 43. Verification Resource

Verification must retain enough target/resource ownership to prove the operation it verifies.

## 44. Release Timing

Do not release required resource before verification completes.

## 45. Unknown Outcome

Unknown operation retains recovery ownership/resource constraints until reconciliation determines safe disposition.

## 46. Recovery Reservation

Recovery may use a separate reservation class with bounded priority.

## 47. Starvation

High-priority recovery must not starve normal operation forever.

## 48. Fairness

Use FIFO/aging/weighted fairness where required.

## 49. Priority

Priority influences queue ordering, not safety.

## 50. Resource Preemption

Preemption should occur only at safe cancellation boundaries.

## 51. Non-Preemptible Mutation

Once destructive syscall has begun, resource manager cannot forcibly preempt it.

## 52. Preemption State

Worker should report `Preempted` only after operation reaches a safe boundary.

## 53. Maintenance Exclusivity

Operations such as filesystem-wide maintenance may require exclusive storage reservation.

## 54. TRIM

TRIM should serialize appropriately with destructive operations on the same device.

## 55. F2FS Maintenance

Filesystem maintenance should use explicit capability/resource requirements.

## 56. ZRAM

ZRAM operations have system-wide effects and should not be scheduled like ordinary target deletion.

## 57. Sysfs

Sysfs mutation must have dedicated resource/capability class.

## 58. Resource Scope

Resource scope may be:

- global
- storage
- mount
- target
- worker

## 59. Hierarchical Accounting

Child resource usage must not exceed parent budget.

## 60. Atomic Reservation

If a Job needs multiple resources, admission should be atomic where possible.

## 61. Partial Reservation

Do not hold resource A indefinitely while waiting for resource B.

Use all-or-nothing reservation or ordered acquisition with bounded timeout.

## 62. Timeout

Waiting for resource must have deadline/cancellation support.

## 63. Busy Loop

Resource waiters must use event notification or bounded backoff, not spin.

## 64. Wakeup

Release should notify eligible waiters.

## 65. Throttling

IO budget may be token-bucket/leaky-bucket style or another deterministic bounded mechanism.

## 66. Token Accounting

Tokens must use typed units and checked arithmetic.

## 67. Refill Clock

Rate limiter should use monotonic time.

## 68. Clock Jump

Wall-clock adjustment must not create token explosion.

## 69. Burst

Burst capacity must be explicit and bounded.

## 70. Fairness Across Jobs

One huge Job must not monopolize IO tokens indefinitely.

## 71. Chunking

Executor should process bounded operation batches where semantics permit.

## 72. Scan Streaming

Scanner should emit candidates incrementally instead of collecting unbounded vectors.

## 73. Backpressure Pipeline

```text
Scanner → bounded channel → Planner/consumer
```

Producer must slow when consumer is full.

## 74. Channel Ownership

Channel closure must have explicit semantics for cancellation and worker shutdown.

## 75. Resource Error Classes

Distinguish:

- unavailable
- exhausted
- timeout
- cancelled
- stale owner
- conflict

## 76. Retry

Resource exhaustion may be retryable; safety/identity conflict is not an ordinary resource retry.

## 77. Metrics

Track:

- reservation wait time
- active reservations
- utilization
- throttled bytes
- rejected admissions
- expired leases
- contention
- queue depth

## 78. Diagnostics

Every wait should expose reason/resource identity in structured diagnostics.

## 79. Security

ResourceManager must not grant capability. It only admits resource usage.

## 80. Authorization Interaction

Authorized operation still needs ResourceManager admission.

## 81. Safety Interaction

Safety proof must remain valid through resource wait if target identity can change. Revalidate at final mutation boundary.

## 82. Generation Changes

Resource topology changes may invalidate reservation. The worker must re-check required generation/identity.

## 83. Config Reload

Changing resource limits should affect new admissions; running operations should follow explicit runtime contract.

## 84. Runtime Limits

Do not dynamically raise a limit beyond validated config without generation/audit semantics.

## 85. Shutdown

No new reservations after StopAdmission.

## 86. Drain

Existing reservations are released as workers reach safe terminal boundaries.

## 87. Crash

Worker death leaves stale leases that recovery must reclaim.

## 88. Reclaim

Reclaiming stale reservation requires identity/lease validation.

## 89. Double Ownership

Two workers must never simultaneously hold authoritative ownership of the same reservation.

## 90. Store Failure

If durable reservation state is required and store write fails, admission fails closed.

## 91. Resource Manager API

Recommended:

```rust
request(spec) -> Reservation
release(reservation_id)
renew(reservation_id)
check(reservation_id)
usage(resource_id)
```

## 92. RAII

In-process resources may use RAII guards, but durable ownership still needs explicit persistence where required.

## 93. Guard Drop

Dropping a guard should release local resource, but must not silently mark a durable mutation successful.

## 94. Test: Contention

Test N workers contending for one target/storage.

## 95. Test: Deadlock

Use stress tests with randomized acquisition/release order and assert no deadlock.

## 96. Test: Cancellation

Cancel while waiting, while admitted, and immediately before execution.

## 97. Test: Crash

Kill worker after reservation and verify lease recovery.

## 98. Test: Overflow

Fuzz token/byte arithmetic near integer limits.

## 99. Definition of Done

ResourceManager production-ready jika:

- all resource classes typed
- limits bounded
- reservation identity exists
- lease/recovery defined
- lock ordering documented
- no partial multi-resource hold indefinitely
- waiting cancellable
- IO throttling monotonic/bounded
- target/storage identity-aware
- unknown mutation retains required ownership
- shutdown drains safely
- metrics available
- contention/deadlock/crash tests pass

## 100. Final Invariants

1. Resource admission never grants authorization.
2. Authorization never bypasses resource limits.
3. Reservations have unique identity.
4. Release is idempotent.
5. Stale owner cannot release another reservation.
6. Resource waits are cancellable.
7. Resource waits are bounded.
8. Lock ordering is deterministic.
9. Multi-resource acquisition cannot create indefinite partial ownership.
10. Storage locks bind to storage identity, not only path.
11. Mutation resources remain valid until required verification/reconciliation.
12. Unknown mutation retains recovery ownership as needed.
13. Resource generation changes trigger revalidation.
14. Shutdown stops new admission first.
15. Resource arithmetic is checked and bounded.
