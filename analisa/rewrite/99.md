# 99.md — Storage, Filesystem, Mount, dan Android Compatibility Matrix

## Tujuan

Cache cleaner bekerja pada filesystem yang behavior-nya tidak identik. Android device dapat menggunakan ext4, F2FS, emulated storage, overlay/bind mounts, vendor-specific layouts, dan berbagai permission/SELinux constraints.

Safety contract harus ditentukan berdasarkan capability dan observed identity, bukan asumsi bahwa semua storage sama.

## 1. Compatibility Dimensions

Evaluasi berdasarkan:

```text
Android version
Kernel
Filesystem
Mount topology
Storage type
SELinux context
UID/GID ownership
Encryption state
Device/vendor behavior
```

## 2. Filesystem Classes

Minimal matrix:

```text
ext4
f2fs
emulated/fuse-backed storage
overlay/bind mount
unknown filesystem
```

Unknown filesystem tidak boleh otomatis mendapat strongest destructive behavior.

## 3. ext4

Pertimbangkan:

- directory semantics
- inode identity
- mount identity
- permission behavior
- fsync/durability semantics

Jangan menganggap semua ext4 mount mempunyai identical mount topology.

## 4. F2FS

F2FS-specific behavior dapat mempengaruhi:

- metadata performance
- write amplification
- discard/TRIM behavior
- fsync cost

Performance tuning tidak boleh mengubah safety contract.

## 5. Emulated Storage

Emulated storage dapat memiliki abstraction layer berbeda dari direct block filesystem.

Path appearance bukan bukti bahwa operation semantics sama dengan direct ext4/F2FS path.

## 6. FUSE / User-space Filesystem

FUSE-backed paths dapat memiliki:

- different permission semantics
- latency
- incomplete ioctl support
- different rename/delete behavior

Platform adapter harus menyatakan capabilities.

## 7. Overlay

Overlay filesystem mempunyai upper/lower layer semantics.

Mutation terhadap apparent path harus mengetahui layer/context yang sebenarnya relevan.

Jika identity/safety tidak dapat dibuktikan, reject mutation.

## 8. Bind Mount

Bind mount membuat path dapat menunjuk object yang sama dari lokasi berbeda.

Trusted root checks harus mempertimbangkan mount topology.

## 9. Mount Identity

Target context dapat menyimpan mount identity/generation.

Unmount/remount dapat membuat previous descriptor/path assumptions stale.

## 10. Device Identity

Filesystem identity sebaiknya dapat menggunakan device/superblock/object identity bila diperlukan.

## 11. Inode Identity

Inode/object identity membantu mendeteksi path replacement.

Tetapi inode identity harus dipahami sesuai filesystem semantics dan tidak boleh dianggap global immutable identity tanpa caveat.

## 12. Symlink Semantics

Destructive traversal harus mempunyai explicit no-follow policy.

Symlink encountered pada protected root/target harus diperlakukan sesuai safety classification, bukan otomatis follow.

## 13. Hard Links

Hard links dapat membuat satu inode memiliki multiple names.

Deleting one directory entry tidak sama dengan deleting logical object globally.

Candidate/accounting model harus memahami semantics tersebut.

## 14. Special Files

Device nodes, FIFO, socket, dan special filesystem entries bukan normal cache files.

Default policy harus conservative.

## 15. Sparse Files

Logical size dan physical blocks berbeda.

Metrics harus mendefinisikan apakah `freed_bytes` berarti logical size atau estimated physical reclaim.

## 16. Quotas

Filesystem/user/project quotas dapat membuat free-space change berbeda dari logical deletion size.

Accounting harus menyatakan semantics secara eksplisit.

## 17. Compression

Filesystem compression dapat membuat physical reclaim berbeda dari logical bytes.

Jangan menjanjikan exact freed physical bytes hanya berdasarkan file size.

## 18. Encryption

Android file-based encryption dapat mempengaruhi accessibility berdasarkan user/profile/unlock state.

Unavailable encrypted path bukan otomatis corruption.

## 19. User/Profile Scope

Storage context harus memasukkan user/profile identity jika relevant.

Cross-user cleanup harus explicit authorization.

## 20. SELinux

SELinux denial adalah platform authorization/capability failure.

Daemon harus membedakannya dari target absence bila possible.

## 21. Permission Model

`root` atau process UID tertentu tidak menjamin semua operations berhasil.

Adapter harus report actual capability.

## 22. Read-Only Mount

Read-only mount harus membuat destructive operations unavailable.

Planner/executor tidak boleh mencoba mutation berulang kali hanya karena policy mengatakan target eligible.

## 23. Noexec / Nodev / Nosuid

Mount flags dapat mempengaruhi operation semantics/security.

Catalog dapat menyimpan relevant mount flags.

## 24. Filesystem Errors

Error seperti:

```text
ENOENT
EACCES
EROFS
EBUSY
ESTALE
EIO
ENOSPC
```

harus dipetakan ke domain error dengan semantics yang tepat.

## 25. EIO

I/O error adalah high-risk filesystem condition.

Jangan langsung retry destructive mutation tanpa revalidation.

## 26. ESTALE

Stale handle/descriptor dapat muncul pada beberapa filesystem/topology.

Reopen/revalidate hanya jika operation contract mengizinkan; jangan menganggap stale descriptor aman untuk reuse.

## 27. EBUSY

Busy target dapat berarti mount/process dependency.

Classify as unavailable/conflict sesuai context, bukan generic failed.

## 28. ENOSPC

Persistence store dan target filesystem dapat mengalami ENOSPC.

Durable intent/accounting failure harus dibedakan dari filesystem mutation result.

## 29. Database Filesystem

Durable DB sebaiknya ditempatkan pada storage yang sesuai reliability requirements.

Jangan menyimpan critical state di volatile temporary directory tanpa explicit contract.

## 30. fsync Semantics

Durability requirements harus disesuaikan dengan actual filesystem and storage behavior.

`fsync` adalah syscall contract, bukan jaminan universal terhadap semua hardware failure scenario.

## 31. Atomic Rename

Rename dapat menjadi atomic dalam filesystem context tertentu, tetapi durability setelah crash memerlukan persistence ordering yang benar.

## 32. Directory Durability

Jika contract membutuhkan durability of directory entry update, parent directory persistence harus dipertimbangkan.

## 33. Mount Namespace

Process dapat berada pada mount namespace berbeda.

Path yang terlihat oleh daemon harus diuji dalam namespace tempat mutation dilakukan.

## 34. Namespace Identity

Target identity dapat memerlukan mount namespace/context reference agar path assumptions tidak salah.

## 35. Root Namespace Assumption

Jangan menganggap root process otomatis melihat global filesystem topology.

Container/chroot/namespace/vendor environment dapat mengubah visibility.

## 36. Android Vendor Layout

Hard-coded paths harus diperlakukan sebagai catalog entries dengan applicability conditions.

Vendor path tidak boleh menjadi universally trusted root hanya karena populer pada satu device family.

## 37. API Level Differences

Platform adapter harus version-gate behavior jika Android API level mengubah filesystem/storage semantics.

## 38. Capability Discovery

Daripada:

```text
if android_version >= X { assume_supported }
```

lebih aman:

```text
discover capability
→ validate
→ execute only if capability contract satisfied
```

## 39. Mount Change Invalidation

Mount event harus meningkatkan catalog/context generation atau invalidation marker.

Existing plan terhadap affected mount menjadi stale.

## 40. Storage State Change

Storage becoming unavailable/readonly harus mengubah admission.

Scheduler dapat defer work sampai capability kembali.

## 41. Filesystem Type Detection

Detection result harus diperlakukan sebagai observation.

Jika detection ambiguous, safety harus conservative.

## 42. Cross-Filesystem Move

Jika future version mendukung move/rename across filesystem, operation bukan atomic rename.

Itu harus menjadi operation graph berbeda dengan explicit partial-failure recovery.

## 43. Delete Semantics

`unlink`/directory removal dan recursive tree removal mempunyai failure semantics berbeda.

Recursive delete harus durable/chunked bila skalanya besar.

## 44. Reclaim Metrics

Bedakan:

```text
logical_deleted_bytes
estimated_reclaimed_bytes
filesystem_free_space_delta
```

Ketiganya tidak selalu sama.

## 45. Compatibility Test Matrix

Minimal test matrix:

| Dimension | Cases |
|---|---|
| Filesystem | ext4, F2FS, FUSE/emulated, unknown |
| Mount | rw, ro, bind, overlay where applicable |
| Object | regular, dir, symlink, hardlink, special |
| State | mounted, unmounted, replaced |
| Permission | allowed, denied, SELinux denied |
| Storage | healthy, full, I/O error |
| Android | supported API/device ranges |
| Lifecycle | boot, screen-off, suspend/resume |

## 46. Unsupported Combination

Jika combination belum diuji atau capability tidak dapat dibuktikan:

```text
No destructive mutation
```

## 47. Real Device Matrix

CI unit tests tidak cukup untuk semua filesystem/vendor behavior.

Dedicated real-device test matrix dibutuhkan untuk release-critical paths.

## 48. Definition of Done

Compatibility production-ready jika:

- filesystem capabilities explicit
- mount identity handled
- namespace considered
- symlink/special files safe
- read-only detected
- SELinux errors classified
- Android API/device differences handled
- vendor paths conditional
- storage failures mapped
- unsupported combinations fail-closed
- real-device matrix exists

## Final Invariants

1. Filesystem type bukan satu-satunya safety signal.
2. Mount topology bagian dari target context.
3. Namespace dapat mengubah path visibility.
4. Path bukan permanent object identity.
5. Symlink traversal harus explicit.
6. Special files default conservative.
7. Read-only storage tidak boleh dimutasi.
8. SELinux denial bukan sekadar generic failure.
9. I/O error tidak boleh blind retry.
10. Stale descriptor harus direvalidate.
11. Android user/profile scope harus dipertahankan.
12. Vendor paths harus conditional.
13. Capability discovery lebih penting daripada version assumption.
14. Mount changes invalidate stale plans.
15. Logical deletion bytes tidak sama dengan physical reclaim.
16. Database/filesystem durability tetap dua domain.
17. Unsupported combination fail-closed.
18. Cross-filesystem mutation memerlukan operation model berbeda.
19. Real-device testing diperlukan untuk filesystem/platform-critical behavior.
20. Compatibility matrix adalah bagian dari production contract.
