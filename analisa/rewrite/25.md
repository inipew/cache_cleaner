Lanjut. Sekarang kita masuk ke **`Executor`**, yaitu boundary paling sensitif di seluruh arsitektur.

Kalau layer sebelumnya menentukan:

```text
Scanner  = apa yang ditemukan?
Safety   = aman disentuh?
Policy   = layak dibersihkan?
Planner  = operasi apa yang akan dilakukan?
Auth     = caller boleh?
```

maka Executor hanya menjawab:

> **Bagaimana menjalankan operation yang sudah authorized tanpa memperluas scope-nya?**

---

# 459. Struktur Executor

```text id="e7k2m4"
src/executor/
├── mod.rs
├── executor.rs
├── context.rs
├── dispatch.rs
├── result.rs
├── error.rs
│
├── filesystem/
│   ├── mod.rs

│   ├── traversal.rs
│   ├── revalidate.rs

│
└── maintenance/

    ├── trim.rs
```

Executor boleh bergantung pada:

```text id="p8n3x5"
domain
fs
kernel
platform
```

Tetapi **tidak boleh meminta Scanner/Policy untuk mencari target baru**.

---

# 460. API utama

Saya ingin boundary-nya sekeras mungkin:

```rust id="m4q9r2"
pub struct Executor;

impl Executor {
    pub fn execute(
        &self,
        plan: &AuthorizedPlan,
        context: &ExecutionContext,
    ) -> ExecutionReport {
        // ...
    }
}
```

Tidak ada API:

```rust id="x7p2k8"
execute_path(path)
delete_directory(path)
clean_target(path)
```

---

# 461. `ExecutionContext`

```rust id="q3m8v1"
pub struct ExecutionContext {
    pub cancellation: CancellationToken,
    pub limits: ExecutionLimits,
    pub dry_run: bool,
}
```

Mungkin juga:

```rust id="n6r2p7"
pub struct ExecutionLimits {
    pub max_operations: usize,
    pub max_bytes: u64,
}
```

Tetapi limit di Executor adalah **defense-in-depth**, bukan mekanisme utama planning.

---

# 462. Executor tidak mempercayai plan secara buta

Ada dua jenis validasi:

```text id="x8q4m1"
Plan validation
    ↓
Authorization
    ↓
Execution-time revalidation
```

Kenapa?

Karena filesystem bisa berubah.

Misalnya:

```text id="p7n3r9"
T0:
cache/a → inode 100
```

Planner membuat:

```text id="m4q8x2"
RemoveFile(cache/a, inode=100)
```

Kemudian:

```text id="k9r1v5"
T1:
cache/a → inode 200
```

Executor **tidak boleh menghapus inode 200**.

---

# 463. Revalidation

Flow RemoveFile:

```text id="v2m7q8"
AuthorizedPlan
      │
      ▼
TrustedRoot
      │
      ▼
open parent directory
      │
      ▼
fstatat(final, NOFOLLOW)
      │
      ▼
identity check
      │
      ▼
type check
      │
      ▼
device check
      │
      ▼
unlinkat(parent, final)
```

---

# 464. Tidak menggunakan absolute path

Misalnya candidate:

```text id="q8m3p6"
TargetRoot:
    /data/user/0/com.foo/cache

RelativePath:
    images/a.tmp
```

Executor tidak melakukan:

```rust id="r4x7n2"
remove_file("/data/user/0/com.foo/cache/images/a.tmp")
```

Melainkan:

```text id="m9p2q5"
TrustedRoot FD
   ↓
openat(root_fd, "images")
   ↓
parent_fd
   ↓
unlinkat(parent_fd, "a.tmp")
```

---

# 465. Kenapa FD-relative?

Karena string path dapat berubah konteks.

FD memberikan kita reference ke directory object yang sudah dibuka.

Dengan:

```text id="x3n8m1"
root_fd
```

kita dapat membatasi operasi terhadap namespace target tersebut.

---

# 466. `TrustedRoot`

Kita sudah punya konsep:

```rust id="p7m2x9"
pub struct TrustedRoot {
    directory: DirectoryHandle,
    identity: ObjectIdentity,
    display_path: PathBuf,
}
```

Yang penting:

```text id="q4n8r1"
display_path ≠ authority
```

Authority adalah:

```text id="m2x7p5"
DirectoryHandle + ObjectIdentity
```

---

# 467. Membuka root

Secara konseptual:

```text id="x8q3m6"
open(
    configured_target,
    O_DIRECTORY |
    O_CLOEXEC |
    O_NOFOLLOW
)
```

Kemudian:

```text id="r5n1p8"
fstat(root_fd)
```

dan pastikan:

```text id="k7m4q2"
is directory
```

serta identity-nya cocok dengan trusted target.

---

# 468. Jangan gunakan `canonicalize()`

Pattern seperti:

```rust id="v3p8m1"
let real = fs::canonicalize(path)?;
fs::remove_file(real)?;
```

tidak boleh ada di Executor.

Karena canonicalization dan deletion adalah dua operasi terpisah.

Filesystem bisa berubah di antara keduanya.

---

# 469. `openat` traversal

Untuk:

```text id="n9q2m7"
images/2026/tmp/a.bin
```

Executor membuka:

```text id="p4x8r1"
root
 ↓
images
 ↓
2026
 ↓
tmp
 ↓
parent_fd
```

Setiap directory component:

```text id="m6q3v9"
O_DIRECTORY
O_NOFOLLOW
```

Kemudian validasi.

---

# 470. `..` tidak pernah diterima

`RelativePath` sudah menolak:

```text id="x2n7p4"
..
```

Jadi:

```text id="q8m3r1"
../../system
```

tidak pernah mencapai syscall layer.

Ini defense pertama.

---

# 471. Symlink

Misalnya:

```text id="k4p9m2"
cache/link → /data/system
```

Scanner:

```text id="n7x3q8"
entry_type = Symlink
```

→ tidak menjadi Candidate.

Kalau somehow masuk ke Executor:

```text id="m2r8p5"
fstatat(..., AT_SYMLINK_NOFOLLOW)
```

mengidentifikasi symlink.

→ reject.

Symlink tidak pernah di-follow.

---

# 472. Broken symlink

Sama.

```text id="q6n1x9"
link → /nonexistent
```

jangan mencoba:

```text id="x4p7m2"
follow → target
```

Broken symlink tetap:

```text id="r8m3q1"
Symlink
```

→ reject.

---

# 473. Special file

Executor juga tidak boleh menghapus:

```text id="n2k7v5"
socket
FIFO
block device
char device
```

kecuali ada operation type yang secara eksplisit mendukungnya.

Untuk cache cleaner:

> Tidak ada.

Jadi:

```text id="p4x8m1"
UnsupportedFileType
```

---

# 474. Identity check

Candidate menyimpan:

```rust id="q9m3r7"
ObjectIdentity {
    device,
    inode,
}
```

Executor mengambil metadata aktual:

```text id="x5p2n8"
actual.device
actual.inode
```

dan membandingkan.

Jika:

```text id="m7q4r1"
actual != expected
```

→ jangan delete.

---

# 475. Identity bukan authorization permanen

Penting:

```text id="n8x2p5"
inode = 123
```

bukan capability global.

Identity hanya menjawab:

> “Apakah object yang sekarang berada di entry ini masih object yang saya lihat saat scan?”

Jadi harus dikombinasikan dengan:

```text id="q3m7v9"
trusted root
relative path
device
entry type
NOFOLLOW
```

---

# 476. Device boundary

Misalnya target:

```text id="x8p2m4"
device = 42
```

Entry actual:

```text id="r5n7q1"
device = 99
```

→ reject.

Ini mencegah traversal keluar filesystem target melalui mount boundary.

---

# 477. `unlinkat`

Untuk regular file:

```text id="m4q8x2"
unlinkat(parent_fd, name, 0)
```

Untuk empty directory:

```text id="p7n3r9"
unlinkat(parent_fd, name, AT_REMOVEDIR)
```

Perbedaan flag ini harus tetap explicit.

---

# 478. RemoveFile tidak boleh berubah menjadi RemoveDirectory

Jika plan:

```text id="x3m8q1"
RemoveFile(cache/a)
```

ternyata `a` adalah directory:

```text id="n7p2r6"
TypeChanged
```

→ reject/skip.

Jangan melakukan:

```text id="q5m9v3"
AT_REMOVEDIR
```

secara otomatis.

---

# 479. RemoveEmptyDirectory juga tidak recursive

Plan:

```text id="k8r2x5"
RemoveEmptyDirectory(old)
```

Executor:

```text id="m4p7n1"
unlinkat(old, AT_REMOVEDIR)
```

Jika:

```text id="x9q3m6"
ENOTEMPTY
```

hasil:

```text id="DirectoryNotEmpty"
```

Bukan:

```text id="delete_children_first"
```

---

# 480. Ini invariant yang sangat penting

> **Executor tidak boleh mengubah operation type berdasarkan filesystem state.**

Artinya:

```text id="p2m8r4"
RemoveFile → RemoveTree
```

tidak pernah valid.

---

# 481. Recursive traversal

Walaupun v1 tidak perlu `RemoveTree` publik, mungkin nantinya kita membutuhkan recursive operation untuk target tertentu.

Jika nanti ditambahkan, jangan:

```rust id="x7q3m1"
std::fs::remove_dir_all(...)
```

Sebaliknya:

```text id="n8p4r2"
open directory
   ↓
enumerate entries
   ↓
validate each entry
   ↓
remove files
   ↓
remove empty children
   ↓
remove directory
```

Tetapi scope recursive harus berasal dari **typed operation** yang explicit.

---

# 482. Kenapa `remove_dir_all()` dilarang?

Karena ia menyembunyikan terlalu banyak semantics:

```text id="m5x8q2"
traversal
symlink behavior
mount boundaries
error handling
ordering
race behavior
```

Untuk privileged daemon, kita ingin semua itu terlihat dan dapat diuji.

---

# 483. Enumeration

Jangan mengandalkan:

```rust id="q4n7m1"
std::fs::read_dir("/proc/self/fd/...")
```

karena kita akhirnya kembali ke string-path semantics.

Lebih baik low-level directory enumeration:

```text id="x8p3r5"
fdopendir
readdir
```

atau wrapper `getdents64`.

---

# 484. `fdopendir` ownership

Ada detail Rust/Unix penting.

`fdopendir()` mengambil ownership FD.

Jangan sampai:

```text id="m7q2n9"
OwnedFd
   +
DIR*
```

keduanya mengira mereka memiliki FD yang sama.

Solusinya:

```text id="p3r8x1"
dup(fd)
   ↓
fdopendir(dup_fd)
```

sehingga ownership jelas.

---

# 485. Alternatif `getdents64`

Kita bisa membuat wrapper:

```rust id="n6m2q8"
pub struct DirectoryEntries {
    fd: BorrowedFd<'_>,
}
```

dan syscall wrapper:

```text id="x4p9r1"
getdents64(fd)
```

Lebih kompleks, tetapi ownership lebih mudah dikontrol.

Untuk v1 saya cenderung:

> gunakan abstraction directory enumeration yang paling sederhana dan well-tested, lalu isolasikan unsafe di satu file.

---

# 486. `unsafe` policy

Hanya low-level syscall adapter:

```text id="q8m3p2"
fs/syscalls/*
```

yang boleh membutuhkan `unsafe`.

Misalnya:

```rust id="m7x4r9"
unsafe {
    libc::openat(...)
}
```

harus memiliki:

```rust id="p2n8q5"
// SAFETY:
// - fd is a valid borrowed directory fd.
// - path contains no NUL bytes.
// - flags prevent symlink traversal.
// - ownership remains with OwnedFd.
```

---

# 487. Jangan spread `unsafe`

Jangan:

```text id="x3r7m1"
executor.rs → unsafe
scanner.rs  → unsafe
planner.rs  → unsafe
policy.rs   → unsafe
```

Idealnya:

```text id="n9q2p6"
executor
   ↓
fs abstraction
   ↓
syscall adapter
   ↓
unsafe
```

---

# 488. Error mapping

Executor jangan mengembalikan raw errno ke seluruh application.

Gunakan semantic error:

```rust id="k4m8x2"
pub enum OperationError {
    PermissionDenied,
    Busy,
    DirectoryNotEmpty,
    CrossDevice,
    Symlink,
    IdentityChanged,
    TypeChanged,
    InvalidTarget,
    InvalidRoot,
    Io,
    Cancelled,
}
```

---

# 489. `ENOENT`

Ini kasus normal.

File mungkin sudah dihapus proses lain:

```text id="q7p3n1"
Scanner → sees a
Planner → plans a
Other process → deletes a
Executor → ENOENT
```

Hasil:

```rust id="x8m2r6"
OperationResult::AlreadyGone
```

Bukan job failure fatal.

---

# 490. `EACCES` / `EPERM`

→

```text id="m5q8p2"
OperationError::PermissionDenied
```

Tidak boleh mencoba:

```text id="r3n7x1"
chmod
chown
restorecon
```

untuk memaksa operasi berhasil.

---

# 491. `ELOOP`

Biasanya indikasi symlink traversal:

```text id="q4m8v2"
OperationError::Symlink
```

Fail closed.

---

# 492. `EXDEV`

→

```text id="n7p2m9"
OperationError::CrossDevice
```

Walaupun unlink sendiri biasanya tidak melakukan cross-device move, error ini tetap berguna sebagai defensive mapping pada traversal/maintenance.

---

# 493. `EBUSY`

→

```text id="x5r8q1"
OperationError::Busy
```

Scheduler dapat memutuskan retry nanti.

Executor tidak melakukan busy-loop.

---

# 494. Retry

Executor tidak memiliki:

```text id="m2q7p4"
for _ in 0..100 {
    retry();
}
```

Retry adalah tanggung jawab Scheduler.

Executor hanya:

```text id="p8n3x6"
Failed(Busy)
```

Scheduler kemudian:

```text id="q4m7r1"
Later(5s)
```

atau membatalkan job.

---

# 495. Cancellation

Cancellation harus diperiksa:

```text id="x9p2m5"
before operation
during traversal
between entries
after expensive maintenance step
```

Contoh:

```rust id="m3q8r1"
if context.cancellation.is_cancelled() {
    return OperationResult::Skipped {
        reason: SkipReason::Cancelled,
    };
}
```

---

# 496. Safe cancellation point

Jangan menganggap cancellation dapat menghentikan syscall yang sedang berjalan secara sempurna.

Modelnya:

```text id="p7m2x8"
check
 ↓
perform bounded operation
 ↓
check
 ↓
next operation
```

Jadi cancellation latency dibatasi oleh operation granularity.

---

# 497. Jangan cancel di tengah state filesystem yang tidak konsisten

Untuk satu unlink:

```text id="q8r3n1"
check cancellation
unlinkat
result
```

Tidak ada kebutuhan rollback.

Untuk sequence:

```text id="m5x7p2"
delete a
delete b
delete c
```

cancel setelah `b` menghasilkan partial success.

Itu normal.

---

# 498. Partial success

Report:

```rust id="n4q8m1"
pub struct ExecutionReport {
    pub planned: usize,
    pub completed: usize,
    pub removed: usize,
    pub already_gone: usize,
    pub skipped: usize,
    pub failed: usize,
    pub removed_bytes: u64,
}
```

Misalnya:

```text id="x7p2r5"
planned       10
removed        7
already_gone   1
skipped        1
failed         1
```

Ini jauh lebih informatif daripada:

```text id="m3q8n1"
ERROR: cleanup failed
```

---

# 499. `removed_bytes`

Jangan selalu:

```text id="p6r2x9"
removed_bytes += candidate.size
```

Karena operation bisa gagal atau file sudah gone.

Hanya:

```text id="q8m4v1"
successful unlink
```

yang menghitung reclaim estimate aktual dari metadata yang tervalidasi.

Tetap sebut sebagai **logical bytes removed**, bukan physical disk space guaranteed.

---

# 500. Verification

Setelah `unlinkat` sukses, verification sederhana:

```text id="x2p7m5"
fstatat(parent, name, NOFOLLOW)
```

→ `ENOENT` adalah expected.

Namun verification tidak selalu perlu melakukan extra syscall untuk setiap file jika overhead terlalu besar.

Kita bisa punya:

```text id="m8q3r1"
VerificationPolicy
```

misalnya:

```text
Normal → verify operation result
Debug  → stronger verification
```

Tetapi untuk v1, unlink success sudah cukup sebagai syscall-level result, sedangkan verification dapat dilakukan untuk plan-level checks.

---

# 501. Verifier bukan Executor

Saya ingin pisahkan:

```text id="n5x8q2"
Executor
  ↓
ExecutionReport
  ↓
Verifier
```

Verifier tidak menghapus apa pun.

Ia hanya memeriksa:

```text
expected result
actual result
```

---

# 502. Plan-level verification

Contoh:

```text id="p4m7r1"
planned:
  remove 100 MB

actual:
  removed 80 MB
  already gone 20 MB
```

Verifier dapat menyimpulkan:

```text id="q8n3x5"
operation success = true
reclaim = 80 MB
```

# 505. F2FS

Jangan percaya:


# 506. RAII untuk F2FS state

Jika operation memerlukan temporary state:

```text id="q8p3m6"

      ↓
perform operation
      ↓
restore
```


Bukan:

# 507. ZRAM

Tidak boleh:


Misalnya:

```text id="q4m8x1"

  delete cache/a

```

Trim tidak boleh berkata:

```text id="n6p2r7"

```

Scope tetap:

```text id="m8x3q5"

```

# 509. Executor invariant final

Saya akan jadikan checklist code review:

```text id="r2n7m4"
1. Executor only accepts AuthorizedPlan.
2. No arbitrary filesystem paths from IPC.
3. No target discovery.
4. No policy decisions.
5. No safety bypass.
6. Root FD is trusted boundary.
7. Parent traversal is FD-relative.
8. No "..".
9. No symlink following.
10. No cross-device traversal.
11. Identity is revalidated.
12. Entry type is revalidated.
13. Root identity is revalidated.
14. RemoveFile never becomes recursive deletion.
15. RemoveEmptyDirectory never becomes recursive deletion.
16. No canonicalize + delete.
17. No rm -rf.
18. ENOENT is idempotent.
19. Cancellation is cooperative.
20. Retry belongs to Scheduler.
21. Partial execution is explicit.
22. Maintenance is typed and scoped.
23. Unsafe is isolated.
24. Invalid plan is rejected, never repaired.
```

## Next stage

Setelah Executor filesystem boundary selesai, urutan yang paling masuk akal adalah **`Scheduler + Runtime Event Loop`** secara implementatif.

Di sana kita akan menggabungkan:

```text
epoll
timerfd
signalfd
uevent/netlink
IPC socket
cancellation
screen state
thermal
storage/FBE state
idle detection
cgroup/resource governor
```

menjadi satu **single-owner state machine**, sehingga daemon tidak berubah menjadi kumpulan thread yang saling mengubah state secara race-prone.

Target akhirnya:

```text id="q8m2r5"
                 ┌──────────────┐
                 │  Event Loop  │
                 └──────┬───────┘
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
       timerfd        signalfd      uevent
          │             │             │
          └─────────────┼─────────────┘
                        ▼
                 SystemEvent
                        ▼
                    Scheduler
                        ▼
              Job State Machine
                        ▼
              Cleanup Worker
                        ▼
            Scanner → ... → Executor
                        │
                        ▼
                    JobEvent
                        │
                        └──────→ Scheduler
```

Itu bagian yang akan menentukan apakah daemon baru ini benar-benar **robust saat screen-on, thermal spike, user interaction, FBE lock/unlock, config reload, shutdown, dan job cancellation**, bukan sekadar aman saat kondisi normal.
