# 85.md — Failure Model, Fault Domains, Fault Injection, dan Recovery Semantics

## Tujuan

Setelah scheduler, power behavior, lifecycle, safety, execution, verification, dan durable state didefinisikan, pertanyaan berikutnya bukan lagi bagaimana cleanup berjalan ketika semuanya normal, tetapi apa yang terjadi ketika salah satu bagian sistem berhenti bekerja di tengah jalan.

Cache cleaner adalah daemon yang dapat hidup lama, menyentuh filesystem dengan privilege tinggi, dan dapat mengalami process death, storage error, suspend, mount change, atau power loss tanpa sempat menyelesaikan lifecycle normal. Karena itu failure harus diperlakukan sebagai bagian dari domain model, bukan sebagai exception yang ditambahkan setelah implementation selesai.

Prinsip dasarnya:

```text
failure
  ↓
classify
  ↓
known atau uncertain?
  ↓
preserve durable evidence
  ↓
reconcile bila mutation mungkin sudah terjadi
  ↓
retry hanya jika aman
  ↓
otherwise RecoveryRequired
```

Tujuan recovery bukan membuat daemon selalu berhasil. Tujuannya adalah **tidak membuat daemon mengambil keputusan yang tidak didukung evidence**.

---

## 1. Failure Bukan Satu Jenis

Jangan menggunakan satu kategori `Error` untuk seluruh kegagalan lalu membiarkan caller menebak semantics-nya.

Secara konseptual failure perlu dibedakan menjadi beberapa kelompok:

```text
Input failure
Configuration failure
Policy failure
Safety failure
Authorization failure
Resource failure
Platform failure
Filesystem failure
Execution failure
Verification failure
Persistence failure
IPC failure
Process failure
Power/lifecycle interruption
Unknown outcome
```

Dua error dengan errno yang sama dapat mempunyai recovery semantics berbeda tergantung pada phase dan apakah mutation sudah mungkin terjadi.

Contohnya `EIO` sebelum syscall mutation dan `EIO` setelah syscall mutation tidak boleh otomatis diperlakukan sama.

---

## 2. Phase Adalah Bagian dari Failure Context

Failure harus selalu dikaitkan dengan lifecycle context.

Minimal context:

```text
JobId
AttemptId
OperationId jika ada
phase
state
error class
platform evidence
config generation
catalog generation
resource ownership
mutation boundary status
```

Contoh:

```text
Attempt A1
Operation O7
phase = Executing
mutation_boundary = entered
error = I/O error
```

jauh lebih informatif daripada:

```text
Error: I/O error
```

Recovery decision harus menggunakan context tersebut.

---

## 3. Mutation Boundary Menentukan Severity Recovery

Salah satu pembeda paling penting adalah apakah operation sudah melewati mutation boundary.

```text
Before mutation
    ↓
failure
    ↓
known failure / retryable
```

sedangkan:

```text
Mutation may have started
    ↓
process/error
    ↓
UNKNOWN
    ↓
reconcile
```

Tidak semua error setelah masuk `Executing` otomatis unknown, tetapi setiap failure yang membuat daemon tidak dapat membuktikan apakah mutation telah terjadi harus diperlakukan sebagai unknown.

---

## 4. Known Failure

Failure dapat diklasifikasikan sebagai known ketika evidence cukup untuk menyatakan bahwa expected mutation tidak terjadi atau postcondition secara jelas tidak terpenuhi dan tidak ada unresolved mutation.

Contoh:

```text
authorization rejected
invalid configuration
safety gate denied
resource unavailable before execution
permission denied before mutation
unsupported operation
```

Known failure dapat langsung menuju `Failed`, `Cancelled`, atau retryable state sesuai policy.

---

## 5. Unknown Outcome

Unknown berarti daemon tidak dapat menentukan actual state secara aman.

Contoh klasik:

```text
send unlink syscall
        ↓
process crash
        ↓
no receipt
```

Yang tidak diketahui bukan sekadar "apakah fungsi Rust mengembalikan Ok", tetapi apakah filesystem sudah berubah sebelum process mati.

Karena itu:

```text
missing receipt != failed mutation
```

dan:

```text
worker crash != operation did not happen
```

---

## 6. Unknown Harus Menjadi Durable Fact

Unknown tidak boleh hanya hidup di memory.

Jika process mati setelah mutation mungkin terjadi, durable state harus menyimpan evidence terakhir yang tersedia sehingga restart dapat membedakan:

```text
never started
```

dari:

```text
may have started
```

Minimal information yang relevan:

- OperationId
- AttemptId
- mutation boundary state
- executor journal state jika tersedia
- last durable transition
- expected identity
- target identity
- plan/config/catalog generation
- timestamps

---

## 7. Executor Journal Adalah Evidence, Bukan Hasil Akhir

Executor dapat mencatat boundary seperti:

```text
Prepared
MutationIntentRecorded
MutationStarted
ReceiptRecorded
```

Journal membantu recovery memahami crash window.

Tetapi journal tidak boleh dianggap sebagai proof filesystem state.

Contoh:

```text
MutationStarted
```

berarti syscall mungkin sudah dimulai, bukan berarti object pasti sudah terhapus.

Final truth tetap berasal dari fresh observation dan verifier.

---

## 8. Failure Classification Harus Deterministik

Untuk input evidence yang sama, classification harus menghasilkan keputusan yang sama.

Contoh:

```text
phase = Planning
mutation = not entered
error = invalid target
```

selalu menghasilkan failure sebelum mutation.

Sedangkan:

```text
phase = Executing
mutation = started
receipt = absent
```

selalu menghasilkan Unknown/Reconciling.

Jangan biarkan hasil bergantung pada timing incidental atau branch implementation tertentu.

---

## 9. Filesystem Failure

Filesystem failure harus mempertimbangkan keadaan filesystem, bukan hanya errno.

Beberapa contoh:

```text
ENOENT
EACCES
EPERM
EBUSY
EROFS
ENOSPC
EDQUOT
EIO
ESTALE
EINTR
ENOTDIR
EISDIR
```

Semantics-nya berbeda.

`ENOENT` sebelum mutation dapat berarti target sudah tidak ada dan mungkin merupakan idempotent success, sedangkan `EIO` setelah mutation start dapat menjadi Unknown.

`EROFS` biasanya known non-mutation failure, tetapi jika error terjadi setelah boundary yang ambiguous, reconciliation tetap diperlukan.

---

## 10. Mount Failure

Mount state dapat berubah selama Job berjalan.

Contoh:

```text
Target discovered on mount A
        ↓
unmount
        ↓
mount B appears at same path
```

Path yang sama tidak membuktikan storage yang sama.

Jika target identity atau mount identity berubah, execution context menjadi stale.

Jangan melanjutkan mutation hanya karena pathname masih terlihat valid.

---

## 11. Target Identity Failure

Jika expected identity tidak lagi cocok dengan actual object:

```text
expected inode/file identity
actual different identity
```

maka operation tidak boleh diarahkan ke object baru secara otomatis.

Classification dapat berupa:

```text
Stale
Failed
Unknown
```

tergantung evidence dan operation semantics.

Yang dilarang adalah menganggap object baru sebagai object lama hanya karena path sama.

---

## 12. Permission Failure

Permission failure harus fail-closed ketika evidence tidak cukup.

Jangan melakukan fallback seperti:

```text
permission denied
    ↓
try parent
    ↓
try different path
    ↓
run arbitrary privileged command
```

Fallback yang memperluas authority dapat mengubah safety failure menjadi security problem.

Permission yang diperlukan harus berasal dari capability/authorization model yang sudah ditentukan sebelumnya.

---

## 13. Resource Failure

Resource failure tidak selalu berarti Job gagal.

Contohnya:

```text
memory budget unavailable
I/O concurrency full
exclusive target lock busy
worker capacity exhausted
```

Jika mutation belum dimulai, Job dapat tetap `WaitingResources` atau kembali ke queue.

Resource admission tidak boleh dianggap sebagai authorization.

---

## 14. Timeout

Timeout harus diklasifikasikan berdasarkan phase.

```text
queue timeout
scan timeout
planning timeout
resource wait timeout
execution timeout
verification timeout
reconciliation timeout
```

Timeout pada scanning biasanya tidak mempunyai mutation ambiguity.

Timeout setelah mutation start dapat menghasilkan Unknown.

Timeout verification dapat menghasilkan Unknown jika postcondition belum dapat dibuktikan.

Karena itu:

```text
timeout != failed
```

secara umum.

---

## 15. Cancellation

Cancellation adalah request untuk menghentikan pekerjaan, bukan bukti bahwa mutation berhenti.

Sebelum mutation:

```text
cancel
 ↓
Cancelled
```

Setelah mutation boundary:

```text
cancel
 ↓
finish safe critical section
 ↓
verify/reconcile
 ↓
terminal classification
```

Cancellation tidak boleh menjadi shortcut untuk menghindari verification.

---

## 16. Process Crash

Process crash adalah salah satu failure utama yang harus dapat direcovery tanpa asumsi bahwa memory state masih ada.

Recovery startup secara konseptual:

```text
start
 ↓
load durable state
 ↓
find non-terminal attempts
 ↓
find owned resources
 ↓
inspect executor journal
 ↓
reconcile affected operations
 ↓
release stale resources
 ↓
resume / retry / fail / RecoveryRequired
```

Process crash bukan alasan untuk mengulang seluruh Job dari awal secara buta.

---

## 17. SIGKILL Tidak Boleh Menghancurkan Semantics

Daemon harus diasumsikan dapat menerima:

```text
SIGTERM
SIGINT
SIGKILL
OOM kill
```

`SIGTERM` memungkinkan graceful shutdown.

`SIGKILL` tidak.

Karena itu correctness tidak boleh bergantung pada shutdown handler semata.

Durable state harus cukup kuat sehingga recovery tetap dapat dilakukan setelah abrupt termination.

---

## 18. Power Loss

Power loss adalah bentuk crash paling keras.

Tidak ada jaminan bahwa:

- process shutdown handler berjalan
- buffered log ter-flush
- memory state tersimpan
- in-memory queue masih tersedia

Karena itu persistence boundary harus dirancang secara eksplisit.

Untuk setiap mutation penting harus dapat dijawab:

> Jika listrik hilang tepat setelah titik ini, apa yang dapat diketahui saat boot berikutnya?

Jika jawabannya "tidak tahu", state harus mengarah ke Unknown dan mempunyai reconciliation path.

---

## 19. Crash Matrix

Setiap operation mutation harus mempunyai crash matrix.

Contoh konseptual:

```text
Point                         Recovery
------------------------------------------------
Before prepare                discard/retry
After plan persisted          resume preparation
After authorization           revalidate authorization
Before mutation intent        retry if valid
After mutation intent         inspect journal
After mutation start          UNKNOWN → reconcile
After receipt                 verify
After verify                  persist result
After result commit           terminal immutable
```

Matrix aktual harus dibuat per operation type jika crash semantics-nya berbeda.

---

## 20. Database/Persistence Failure

Persistence failure sendiri dapat menciptakan inconsistency.

Contohnya:

```text
filesystem mutation succeeded
        ↓
DB commit failed
```

Filesystem tidak dapat di-rollback hanya karena database gagal.

Karena itu recovery harus mampu menemukan mutation yang durable di filesystem tetapi state DB belum final.

Persistence failure setelah mutation boundary harus diperlakukan sebagai recovery condition, bukan sekadar retry database lalu mengulang mutation.

---

## 21. Publication Failure

Jika state sudah committed tetapi event publication gagal:

```text
persist
 ↓
commit
 ↓
publish fails
```

durable state tetap authoritative.

Outbox/replay dapat menerbitkan event kemudian.

Jangan melakukan mutation ulang hanya karena subscriber tidak menerima event.

---

## 22. IPC Failure

Client dapat mati kapan saja:

```text
request received
request parsed
job created
client disconnects
```

Disconnect client tidak boleh otomatis membatalkan Job kecuali contract secara eksplisit mendefinisikan request sebagai client-owned ephemeral operation.

Sebaliknya:

```text
client sends cancel
client disconnects
```

cancellation request yang sudah diterima harus tetap memiliki semantics durable sesuai contract.

---

## 23. Duplicate Request

Crash/retry di sisi client dapat menghasilkan request yang sama lebih dari sekali.

Contoh:

```text
client submits Job
 ↓
server commits
 ↓
reply lost
 ↓
client retries
```

Server harus menggunakan request/idempotency identity untuk mencegah duplicate logical Job jika semantics request mengharuskannya.

Idempotency contract akan dibahas lebih lanjut pada dokumen berikutnya.

---

## 24. Event Loss

Event-driven scheduler tidak boleh menganggap event delivery sempurna.

Jika event hilang:

```text
event missed
 ↓
sparse reconciliation
 ↓
refresh snapshot/generation
 ↓
recover desired state
```

Event adalah trigger/hint, sedangkan authoritative state berasal dari snapshot/platform/storage.

---

## 25. Event Storm

Event storm adalah failure mode operasional karena scheduler dapat terus bangun tanpa menghasilkan progress.

Contoh:

```text
thermal change × 1000
power change × 500
mount change × 100
```

Scheduler harus:

- coalesce
- bounded drain
- limit evaluation rate
- collapse equivalent desired states
- fall back to reconciliation

Jangan memproses event satu per satu tanpa batas hanya demi mempertahankan urutan yang tidak mempunyai nilai domain.

---

## 26. Worker Failure

Worker dapat:

- panic
- crash
- hang
- kehilangan IPC/resource handle
- timeout
- berhenti mengirim heartbeat

Worker failure sebelum mutation lebih mudah dipulihkan.

Worker failure setelah mutation boundary harus mengikuti Unknown/Reconciliation semantics.

Worker baru harus menggunakan WorkerId baru. Message dari worker lama tidak boleh dapat mengubah state secara tidak sah.

---

## 27. Panic Tidak Boleh Menjadi Recovery Mechanism

Rust panic harus dianggap process/worker failure, bukan domain transition.

Jangan menggunakan:

```rust
panic!("cleanup failed")
```

sebagai cara normal untuk menyatakan failure.

Domain layer harus menghasilkan typed failure yang dapat diklasifikasikan dan dipersist.

Panic tetap harus ditangani pada boundary yang tepat agar crash worker tidak menyebabkan silent corruption pada Job state.

---

## 28. Memory Pressure

Android dapat membunuh process karena memory pressure.

Scanner dan planner karena itu harus mempunyai bounded memory behavior.

Failure seperti allocation failure atau OOM kill tidak boleh diasumsikan dapat menjalankan cleanup handler.

Durable checkpoints dan bounded work unit membantu memastikan restart dapat melakukan recovery tanpa mengulang mutation secara buta.

---

## 29. Thermal dan Battery Pressure

Thermal/battery condition dapat berubah ketika Job berjalan.

Perubahan tersebut dapat menyebabkan policy berubah dari:

```text
Allowed
```

menjadi:

```text
Deferred
```

atau membatalkan admission untuk operation berikutnya.

Namun policy change tidak boleh memperluas authority yang sudah ada.

Jika mutation critical section sedang berjalan, perubahan thermal tidak boleh membuat executor meninggalkan operation pada titik yang menghasilkan ambiguous filesystem state tanpa reconciliation.

---

## 30. Suspend di Tengah Job

Suspend bukan crash, tetapi semantics-nya serupa dalam hal dunia dapat berubah tanpa daemon melihat setiap event.

Setelah resume:

```text
resume
 ↓
refresh relevant platform state
 ↓
check generation/identity
 ↓
revalidate
 ↓
continue, defer, or reconcile
```

Job yang lama tidak boleh diasumsikan masih valid hanya karena process tetap hidup.

---

## 31. Recovery Tidak Sama dengan Retry

Ini harus menjadi invariant kuat.

```text
Recovery
    ↓
menentukan actual state
```

sedangkan:

```text
Retry
    ↓
melakukan execution kembali
```

Recovery harus terjadi lebih dahulu ketika mutation outcome tidak diketahui.

Jangan:

```text
Unknown
 ↓
retry delete
```

sebelum mengetahui apakah object original sudah terhapus atau path telah digunakan object lain.

---

## 32. Recovery Harus Read-First

Default reconciliation bersifat observational:

```text
load evidence
 ↓
inspect target
 ↓
verify identity
 ↓
classify
```

Mutation baru boleh dilakukan setelah:

- actual state diketahui cukup
- operation idempotency mengizinkan
- target masih valid
- safety gate lulus
- authorization masih valid atau diterbitkan ulang

---

## 33. Recovery Tidak Boleh Memperluas Scope

Recovery terhadap:

```text
Operation O1
```

tidak boleh berubah menjadi:

```text
scan seluruh filesystem
and delete anything matching rule
```

Recovery tetap terikat pada original operation identity, target, scope, dan safety constraints.

Jika original intent tidak lagi dapat direkonstruksi secara aman, gunakan `RecoveryRequired` daripada membuat intent baru secara implisit.

---

## 34. Recovery Budget

Recovery juga harus bounded.

Harus ada limit untuk:

- number of attempts
- verification retries
- reconciliation duration
- filesystem traversal
- memory
- I/O
- startup recovery time

Daemon tidak boleh boot lalu menghabiskan seluruh startup time untuk satu corrupted Job tanpa batas.

---

## 35. Recovery Ordering

Jika ada banyak Job yang interrupted, recovery perlu deterministic ordering.

Salah satu model:

```text
critical unresolved mutation
        ↓
resource ownership cleanup
        ↓
operation reconciliation
        ↓
job aggregation
        ↓
ordinary queued work
```

Jangan menjalankan cleanup baru sebelum unresolved mutation lama yang berpotensi konflik diselesaikan.

---

## 36. Stale Resource Recovery

Jika process mati ketika memegang resource reservation:

```text
Attempt A1 owns resource R
 ↓
process dies
```

resource state harus dapat dideteksi stale berdasarkan durable ownership/lease/epoch.

Resource manager tidak boleh menganggap reservation lama masih aktif selamanya.

Sebaliknya, jangan langsung merebut resource jika owner lama mungkin masih hidup. Gunakan liveness/epoch semantics yang explicit.

---

## 37. Recovery Epoch

Salah satu mekanisme yang dapat digunakan adalah process/recovery epoch.

Contoh:

```text
Daemon instance 41
Worker epoch 8
```

Setelah restart:

```text
Daemon instance 42
```

Message/resource ownership dari instance lama dapat ditolak karena epoch tidak lagi valid.

Ini mencegah stale worker atau stale callback mengubah durable state setelah recovery.

---

## 38. Recovery Harus Idempotent

Recovery sendiri dapat crash.

Maka:

```text
recover
 ↓
crash
 ↓
recover again
```

harus tetap aman.

Setiap recovery step harus memiliki durable progress atau dapat diulang tanpa menghasilkan mutation ganda.

Recovery bukan proses sekali jalan yang bergantung pada process tetap hidup sampai selesai.

---

## 39. Fault Injection Adalah Bagian dari Implementation

Failure model tidak cukup ditulis.

Setiap crash boundary penting harus dapat diuji dengan fault injection.

Contoh:

```text
inject failure before journal
inject failure after journal
inject failure before syscall
inject failure after syscall start
inject failure before receipt
inject failure before verification
inject failure before DB commit
inject failure after DB commit
inject failure before publication
```

Test harus memastikan recovery menghasilkan state yang benar dan tidak melakukan duplicate mutation.

---

## 40. Fault Injection Tidak Boleh Menggunakan Production Kill Secara Sembarangan

Untuk unit/integration test, gunakan explicit injection point.

Contoh abstraksi:

```rust
trait FaultInjector {
    fn checkpoint(&self, point: FaultPoint) -> Result<(), InjectedFault>;
}
```

Production implementation harus no-op atau disabled secara aman.

Test implementation dapat menghasilkan:

```text
ReturnError
PanicWorker
AbortProcess
SimulatedPowerLoss
Delay
DropReceipt
DropPublication
```

---

## 41. Fault Point Harus Stable

Fault point sebaiknya diberi stable identifier, bukan bergantung pada line number source code.

Contoh:

```text
executor.before_mutation
executor.after_mutation_start
executor.before_receipt_commit
verifier.before_after_snapshot
store.before_commit
store.after_commit
outbox.before_publish
```

Dengan demikian test tetap bermakna setelah refactor internal.

---

## 42. Crash Injection Matrix

Minimal integration test perlu menguji setiap mutation operation terhadap fault point utama.

Bentuknya:

```text
Operation × FaultPoint × Restart
```

Kemudian assert:

- no unsafe duplicate mutation
- no false success
- no false failure
- no lost terminal result
- no leaked resource
- no invalid authorization reuse
- no incorrect accounting

---

## 43. Filesystem Fault Injection

Selain process crash, test perlu mensimulasikan filesystem condition:

- target disappears
- target replaced
- rename race
- permission change
- read-only remount
- mount replacement
- I/O error
- ENOSPC
- stale handle
- directory mutation during scan

Tidak semua dapat disimulasikan hanya dengan temporary directory biasa; beberapa membutuhkan Linux namespace, FUSE/test adapter, mock platform adapter, atau privileged integration environment.

---

## 44. Deterministic Recovery Test

Recovery test harus menghasilkan hasil yang deterministic.

Pattern:

```text
fixture
 ↓
create durable state
 ↓
inject failure at point X
 ↓
restart
 ↓
reconcile
 ↓
assert state/result/filesystem
```

Fixture harus dapat direproduksi.

Randomized fault injection boleh ditambahkan kemudian sebagai stress layer, tetapi deterministic cases harus menjadi baseline.

---

## 45. Property yang Harus Selalu Benar

Beberapa property penting:

1. Unknown tidak pernah otomatis menjadi success.
2. Unknown tidak pernah otomatis menjadi retry.
3. Replacement object tidak pernah memenuhi identity original.
4. Recovery tidak memperluas scope.
5. Retry tidak membuat duplicate logical operation.
6. Terminal state tidak berubah secara silent.
7. Resource reservation tidak bocor setelah recovery.
8. Accounting tidak double count.
9. Stale worker tidak dapat mengubah current state.
10. Process restart tidak menghapus durable evidence.
11. Power loss tidak boleh menghasilkan false success.
12. Failed-before-mutation tidak memerlukan filesystem rollback.
13. Mutation-ambiguous failure selalu mempunyai reconciliation path atau RecoveryRequired.

---

## 46. Definition of Done

Failure/recovery layer dapat dianggap siap ketika sistem mempunyai:

- typed failure classification
- phase-aware failure context
- explicit mutation boundary
- durable unknown outcome
- executor journal/evidence boundary
- crash matrix
- process-crash recovery
- power-loss semantics
- stale resource recovery
- worker epoch/liveness handling
- bounded reconciliation
- bounded retry
- read-first recovery
- idempotent recovery
- fault injection framework
- deterministic crash tests
- filesystem race tests
- event storm tests
- persistence failure tests
- no false success
- no blind retry
- no arbitrary recovery mutation

---

## 47. Invariants Final

Failure model harus mempertahankan invariant berikut:

1. Failure selalu memiliki context.
2. Mutation boundary membedakan failure semantics.
3. Missing receipt bukan bukti mutation gagal.
4. Unknown adalah first-class durable state.
5. Unknown tidak sama dengan Failed.
6. Unknown tidak sama dengan Completed.
7. Recovery dilakukan sebelum retry ketika mutation outcome tidak diketahui.
8. Recovery bersifat read-first.
9. Recovery tidak boleh memperluas operation scope.
10. Retry hanya boleh jika idempotency dan safety mengizinkan.
11. SIGKILL tidak boleh menghancurkan recovery semantics.
12. Power loss harus dianggap mungkin terjadi pada setiap persistence boundary.
13. Persistence failure setelah mutation tidak boleh memicu blind mutation retry.
14. Event loss harus dapat ditangani melalui reconciliation.
15. Event storm harus dicoalesce dan dibatasi.
16. Stale worker tidak boleh mengubah state current.
17. Stale resource ownership harus dapat direcovery secara aman.
18. Recovery sendiri harus idempotent.
19. Recovery harus bounded.
20. Fault injection harus mencakup crash window kritis.
21. Crash tests harus memverifikasi filesystem state dan durable state.
22. Verification tetap menjadi sumber proof untuk final mutation outcome.
23. Accounting harus idempotent terhadap restart/retry/recovery.
24. RecoveryRequired lebih aman daripada membuat asumsi yang tidak terbukti.
25. Sistem tidak boleh mengorbankan safety demi meningkatkan recovery success rate.
