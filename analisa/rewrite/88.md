# 88.md — Resource Lifetime, FD/Handle Ownership, dan Resource Safety

## Tujuan

Filesystem safety tidak berhenti pada path validation. Setelah target dianggap aman, daemon masih harus mengelola file descriptor, directory handle, mount reference, reservation, memory, dan resource lain dengan lifecycle yang jelas.

Prinsipnya:

```text
Acquire
  ↓
Validate
  ↓
Use
  ↓
Verify
  ↓
Release
```

Setiap resource harus mempunyai owner, lifetime, dan aturan recovery.

## 1. Resource Identity

Resource tidak boleh hanya direpresentasikan sebagai angka atau raw handle tanpa ownership context.

Contoh resource:

- file descriptor
- directory FD
- mount identity/reference
- memory budget
- I/O permit
- execution reservation
- worker lease
- IPC connection

## 2. Ownership

Setiap resource yang dipakai operation harus dapat ditelusuri ke:

```text
JobId
AttemptId
OperationId
WorkerId
```

Tidak boleh ada anonymous reservation yang tidak jelas siapa pemiliknya.

## 3. RAII

Rust ownership sebaiknya menjadi mekanisme utama lifecycle resource.

Contoh konseptual:

```rust
let dir = open_target()?;
let reservation = resources.reserve(...)?;

execute(&dir)?;
verify(&dir)?;

// Drop releases resources
```

Manual cleanup hanya diperlukan untuk resource yang memang mempunyai lifecycle eksternal.

## 4. FD Ownership

Module yang membuka FD sebaiknya menentukan dengan jelas siapa yang bertanggung jawab menutupnya.

Jangan mengembalikan raw integer FD jika typed owner seperti `OwnedFd` dapat digunakan.

## 5. Borrowed vs Owned Handle

Bedakan:

```text
BorrowedFd
OwnedFd
```

Borrowed handle tidak boleh hidup lebih lama dari owner.

Owned handle bertanggung jawab terhadap close.

## 6. Directory FD

Untuk operasi filesystem sensitif, directory FD dapat menjadi anchor untuk operasi relatif:

```text
open parent
  ↓
openat / unlinkat / renameat
```

Hal ini mengurangi ketergantungan pada path string global.

## 7. FD Bukan Safety Proof

Memiliki FD tidak berarti operation otomatis aman.

Sebelum mutation tetap perlu memastikan:

- target identity
- mount identity
- authorization
- safety conditions
- operation semantics

FD adalah capability terhadap object/kernel state, bukan pengganti seluruh safety gate.

## 8. FD Lifetime dan Mount Changes

Mount dapat berubah selama operation berjalan.

Karena itu executor/verifier harus mengetahui apakah FD yang sudah dibuka tetap valid untuk semantics operation.

Jika mount identity berubah atau assumptions invalid:

```text
stop
→ Unknown/Stale
→ reconcile
```

Jangan meneruskan mutation hanya karena FD masih numerically valid.

## 9. Close Semantics

Close failure harus dinilai sesuai resource.

Untuk ordinary read-only FD, close error biasanya tidak mengubah operation result.

Untuk resource yang close mempunyai semantic commit, error harus diperlakukan berbeda dan didefinisikan secara explicit.

Jangan menerapkan satu aturan close error untuk semua resource.

## 10. FD Leak Prevention

Setiap error path harus melepaskan owned resource.

Rust RAII sangat cocok untuk memastikan:

```text
success
error
panic/unwind
cancellation
```

tetap menghasilkan Drop.

Jika process termination tidak memberi kesempatan Drop, durable resource ownership harus dapat direcover setelah restart.

## 11. Resource Manager vs OS Resource

Resource Manager mengatur logical admission.

Kernel tetap mengatur actual OS resources.

Contoh:

```text
ResourceManager says 8 FD budget
OS says EMFILE
```

Daemon harus menangani keduanya.

Logical reservation bukan jaminan kernel resource tersedia.

## 12. Reservation Lifetime

Reservation sebaiknya:

```text
created
→ owned
→ consumed/held
→ released
```

Status reservation harus dapat diketahui durable jika reservation tersebut dapat menghambat recovery.

## 13. Reservation Scope

Reservation sebaiknya sesingkat kebutuhan sebenarnya.

Queued Job tidak boleh memegang exclusive resource yang baru diperlukan saat execution.

Planning dapat mempunyai budget sendiri tanpa memegang mutation lock.

## 14. Resource Hierarchy

Untuk menghindari deadlock, urutan acquisition harus konsisten.

Contoh konseptual:

```text
Global admission
    ↓
Filesystem resource
    ↓
Target resource
    ↓
Operation-local resource
```

Tidak boleh ada path lain yang mengambil urutan terbalik tanpa alasan.

## 15. No Lock Across Blocking Wait

Jangan menahan lock eksklusif ketika worker sedang:

- menunggu IPC
- menunggu resource lain
- menunggu scheduler
- melakukan long sleep

Acquire sedekat mungkin dengan mutation/critical observation.

## 16. Cancellation

Cancellation harus melepaskan resource yang tidak lagi diperlukan.

Jika cancellation datang ketika critical mutation sedang berjalan, executor boleh menunda cancellation sampai safe point lalu melakukan verification.

## 17. Timeout

Timeout tidak boleh meninggalkan resource reservation.

Timeout handler harus mempunyai cleanup path yang sama dengan terminal failure/recovery.

## 18. Worker Crash

Worker crash dapat meninggalkan resource yang tidak sempat di-drop.

Karena itu resource recovery harus membedakan:

```text
process-local resource
```

dan:

```text
durable/external reservation
```

OS biasanya membersihkan FD ketika process mati. Durable reservation tidak demikian.

## 19. Process Death

FD biasa akan ditutup oleh kernel ketika process mati.

Jangan membuat database state seolah FD masih hidup setelah process restart.

Recovery harus membuat resource ownership baru.

## 20. Stale Reservation

Reservation durable harus memiliki owner identity dan, bila perlu, lease expiry.

PID saja tidak cukup.

Recovery harus membuktikan owner lama sudah tidak aktif sebelum reclaim reservation.

## 21. Memory Budget

Scanner dan planner tidak boleh menganggap RAM tidak terbatas.

Large candidate set sebaiknya dapat diproses sebagai stream/chunk jika diperlukan.

Memory reservation harus bounded.

## 22. File Descriptor Budget

Traversal besar dapat membuka banyak FD.

Default harus menghindari menyimpan seluruh tree FD sekaligus.

Gunakan bounded descriptor concurrency.

## 23. I/O Budget

Resource Manager dapat membatasi concurrent filesystem operations.

Tujuannya bukan hanya throughput, tetapi menjaga:

- latency
- thermal impact
- battery impact
- contention

## 24. Verification Resource

Verifier juga membutuhkan resource budget.

Jangan memberikan executor unlimited resource lalu verifier tidak memiliki kesempatan untuk menyelesaikan postcondition.

## 25. Resource Priority

Safety-critical verification/recovery dapat diberi prioritas atas new optional cleanup work.

Namun priority tidak boleh bypass safety atau authorization.

## 26. Resource Preemption

Preemption harus membedakan phase.

Non-mutating scan dapat dihentikan lebih mudah.

Critical mutation sequence tidak boleh dipotong sembarangan.

Setelah preemption di mutation boundary:

```text
verify/reconcile first
```

## 27. Resource Fairness

Job yang terus menghasilkan pekerjaan tidak boleh memonopoli resource selamanya.

Gunakan bounded work units dan cooperative scheduling.

## 28. FD-relative Safety

Jika operation membutuhkan parent directory identity, parent FD dapat dipertahankan sepanjang critical sequence.

Contoh:

```text
open trusted root
→ open parent directory
→ verify identity
→ perform relative mutation
→ verify
```

## 29. Rename dan Handle Stability

Rename tidak selalu invalidasi open FD.

Operation semantics harus menentukan apakah identity atau path adalah invariant.

Jika identity-based, handle dapat membantu mempertahankan reference terhadap object.

Jika path-based, rename dapat menjadi stale condition.

## 30. Symlink Handling

Jangan membuka symlink secara tidak sengaja ketika operation membutuhkan target object.

Gunakan flags/API yang sesuai untuk no-follow semantics.

## 31. Mount Boundary

Trusted root harus tetap berada pada mount yang diizinkan.

FD-relative traversal tidak boleh dipakai sebagai alasan untuk mengabaikan mount boundary.

## 32. Handle Validation

Platform adapter harus menyediakan cara untuk memperoleh identity yang dibutuhkan dari handle/object.

Generic domain code tidak boleh mengandalkan platform-specific ioctl/syscall secara langsung.

## 33. Resource Release Ordering

Release harus mengikuti dependency.

Contoh:

```text
finish verification
→ release target lock
→ release filesystem budget
→ release job reservation
→ publish terminal result
```

Jangan publish resource availability sebelum resource benar-benar dilepas.

## 34. Publication vs Resource Release

Terminal state sebaiknya tidak memberi kesan bahwa resource sudah tersedia jika release belum terjadi.

Durable state dan resource release ordering harus didefinisikan bersama.

## 35. IPC Connection Lifetime

IPC connection harus bounded.

Request handler tidak boleh memegang connection resource selama full background Job.

Response cukup mengembalikan JobId dan status/result query.

## 36. Blocking Wait

Resource wait harus blocking/event-driven.

Jangan:

```text
try acquire
sleep
try acquire
sleep
```

Gunakan notification ketika resource berubah.

## 37. Shutdown

Shutdown harus membangunkan waiter dan memungkinkan resource release secara teratur.

Shutdown timeout tidak boleh membuat durable resource ownership dianggap bersih tanpa recovery evidence.

## 38. Resource Leak Detection

Metrics/debug build dapat mencatat:

- active FD count
- active reservations
- held locks
- outstanding permits
- owner identity

Namun telemetry sendiri tidak boleh menjadi source of correctness.

## 39. Resource Invariants

Minimal:

```text
resource has one owner
owner has bounded lifetime
release is deterministic
stale ownership is recoverable
```

## 40. Definition of Done

Resource management production-ready jika:

- owned vs borrowed handle jelas
- RAII digunakan
- FD budget bounded
- memory budget bounded
- I/O concurrency bounded
- lock hierarchy explicit
- no lock across indefinite wait
- cancellation/timeout release resources
- crash recovery menangani durable reservations
- mount/identity semantics jelas
- resource wait event-driven
- shutdown membangunkan waiters
- resource metrics tersedia untuk diagnosis

## Final Invariants

1. Setiap resource memiliki owner.
2. Owner memiliki lifecycle yang jelas.
3. Raw FD tidak boleh menjadi ownership abstraction utama.
4. FD tidak menggantikan safety gate.
5. Mount identity tetap harus diverifikasi.
6. Resource wait tidak boleh polling.
7. Reservation tidak boleh dipegang terlalu awal.
8. Lock hierarchy harus konsisten.
9. Lock tidak boleh ditahan selama indefinite wait.
10. Cancellation harus melepaskan resource yang aman dilepas.
11. Timeout tidak boleh menyebabkan reservation leak.
12. Process death tidak membuat FD durable secara semu.
13. Durable reservation harus dapat direcover.
14. PID saja bukan ownership proof.
15. Memory/FD/I/O budget harus bounded.
16. Verification harus mendapat resource budget.
17. Critical mutation tidak boleh dipreempt sembarangan.
18. Resource release ordering harus explicit.
19. Resource availability tidak boleh dipublish sebelum release.
20. Resource lifecycle harus aman terhadap crash dan restart.
