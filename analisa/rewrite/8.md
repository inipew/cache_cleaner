Lanjut. Sekarang kita masuk ke bagian yang sangat penting: **Planner + Operation Model**. Di sinilah hasil `Safety` dan `Policy` diubah menjadi daftar aksi yang benar-benar boleh dieksekusi.

Untuk rewrite ini, saya sarankan prinsip utamanya:

> **Executor tidak boleh menerima `Candidate` mentah. Executor hanya menerima `AuthorizedPlan`.**

Ini membuat jalur dari “menemukan file” → “menghapus file” sangat jelas dan sulit disalahgunakan.

---

# 1. Posisi Planner dalam arsitektur

Alurnya:

```text
Scanner
   ↓
Candidate
   ↓
Safety Engine
   ↓
SafetyValidated
   ↓
Policy Engine
   ↓
PolicyApproved
   ↓
Planner
   ↓
CleanupPlan
   ↓
Authorization
   ↓
AuthorizedPlan
   ↓
Executor
```

Jadi Planner **tidak melakukan delete**.

Planner hanya menjawab:

> “Dengan semua candidate yang sudah lolos safety dan policy, operasi apa yang seharusnya dilakukan, dalam urutan apa, dengan budget berapa?”

---

# 2. Tanggung jawab Planner

Planner sebaiknya hanya mempunyai beberapa tanggung jawab:

```text
1. memilih operasi
2. deduplicate target
3. membuat dependency
4. menentukan ordering
5. menghitung estimasi
6. menerapkan budget
7. memvalidasi plan
8. menghasilkan immutable CleanupPlan
```

Yang **bukan** tanggung jawab Planner:

```text
- open file
- unlink file
- remove directory
- trigger F2FS
- trim block device
- ubah cgroup
- cek screen state secara langsung
- mengakses Android framework
```

Itu milik layer lain.

---

# 3. Operation Model

Saya akan membuat `Operation` sebagai tipe domain yang eksplisit.

Misalnya:

```rust
pub enum Operation {
    RemoveFile(RemoveFile),
    RemoveEmptyDirectory(RemoveEmptyDirectory),

    TrimFilesystem(TrimFilesystem),

    F2fsMaintenance(F2fsMaintenance),

    ZramMaintenance(ZramMaintenance),

    FrameworkMaintenance(FrameworkMaintenance),
}
```

Tetapi jangan berhenti di enum tersebut. Setiap operasi perlu mempunyai metadata.

Contohnya:

```rust
pub struct PlannedOperation {
    pub id: OperationId,
    pub operation: Operation,
    pub target: OperationTarget,
    pub expected_effect: ExpectedEffect,
    pub cost: OperationCost,
    pub preconditions: Vec<Precondition>,
    pub dependencies: Vec<OperationId>,
}
```

Dengan demikian sebuah operation bukan sekadar:

```text
delete("/some/path")
```

tetapi:

```text
Operation #42

Target:
    user 0
    package com.example.app
    relative path cache/foo.tmp

Kind:
    RemoveFile

Expected:
    free approximately 128 KiB

Preconditions:
    root identity unchanged
    device unchanged
    object identity unchanged
    object is regular file
    object is not symlink

Dependencies:
    none
```

Ini jauh lebih aman.

---

# 4. Bedakan OperationKind dan Target

Jangan membuat tipe seperti:

```rust
RemoveFile {
    path: PathBuf
}
```

karena `PathBuf` terlalu powerful untuk privileged code.

Lebih baik:

```rust
pub enum OperationTarget {
    Entry(ValidatedEntry),
    Directory(TrustedDirectory),
    Filesystem(FilesystemId),
    Zram(ZramDevice),
    Framework(FrameworkTarget),
}
```

Dan:

```rust
pub enum OperationKind {
    RemoveFile,
    RemoveEmptyDirectory,
    TrimFilesystem,
    F2fsMaintenance,
    ZramMaintenance,
    FrameworkMaintenance,
}
```

Kemudian `Operation` menggabungkan keduanya.

---

# 5. File deletion harus berbeda dengan directory deletion

Ini penting.

Jangan membuat satu operasi generik:

```rust
Delete(path)
```

Karena semantics-nya berbeda.

Gunakan:

```rust
RemoveFile
```

untuk regular file.

Dan:

```rust
RemoveEmptyDirectory
```

untuk directory yang sudah dipastikan kosong.

Sementara:

```rust
PurgeDirectoryContents
```

boleh ada sebagai operasi khusus, tetapi saya akan **sangat konservatif** dalam menggunakannya.

---

# 6. Kenapa `PurgeDirectoryContents` berbahaya?

Misalnya:

```text
/cache/
    old.tmp
    recent.tmp
    protected/
    active.lock
```

Kalau Planner mengatakan:

```text
PurgeDirectoryContents(/cache)
```

maka executor bisa saja menghapus semuanya.

Padahal:

```text
old.tmp       → eligible
recent.tmp    → terlalu baru
protected/    → protected
active.lock   → sedang digunakan
```

Karena itu default rewrite saya:

```text
scan
 ↓
candidate per entry
 ↓
policy per entry
 ↓
operation per entry
```

Bukan:

```text
directory → rm everything
```

`PurgeDirectoryContents` hanya boleh digunakan jika Target Catalog secara eksplisit mendefinisikan bahwa **seluruh isi root adalah disposable**, dan safety/policy sudah membuktikannya.

---

# 7. Parent-child dependency

Ini salah satu bagian paling penting dalam Planner.

Misalnya:

```text
cache/
├── a.tmp
└── old/
    ├── b.tmp
    └── c.tmp
```

Planner menghasilkan:

```text
OP1 RemoveFile(cache/a.tmp)

OP2 RemoveFile(cache/old/b.tmp)

OP3 RemoveFile(cache/old/c.tmp)

OP4 RemoveEmptyDirectory(cache/old)
```

Maka dependency:

```text
OP2 ─┐
OP3 ─┴──→ OP4
```

Artinya:

```text
b.tmp
c.tmp
   ↓
old/
```

Directory hanya boleh dihapus setelah children selesai.

---

# 8. Jangan menggunakan ordering berdasarkan string path

Kesalahan yang sering terjadi:

```rust
operations.sort_by(|a, b| a.path.cmp(&b.path));
```

Ini bukan dependency system.

Ordering harus berdasarkan **struktur filesystem**.

Secara konsep:

```text
depth 3
   ↓
depth 2
   ↓
depth 1
```

atau dependency graph.

Lebih kuat:

```rust
pub struct OperationGraph {
    operations: Vec<PlannedOperation>,
}
```

Kemudian lakukan topological ordering.

Dengan ini kalau suatu saat operasi bertambah:

```text
scan
remove child
remove parent
trim filesystem
f2fs maintenance
```

dependency tetap eksplisit.

---

# 9. Jangan mencampur filesystem cleanup dengan kernel maintenance

Saya sarankan tiga kelas operasi:

```rust
pub enum OperationClass {
    Filesystem,
    KernelMaintenance,
    FrameworkMaintenance,
}
```

Contohnya:

### Filesystem

```text
RemoveFile
RemoveEmptyDirectory
PurgeDirectoryContents
```

### Kernel

```text
TrimFilesystem
F2fsMaintenance
ZramMaintenance
```

### Android/framework

```text
FrameworkMaintenance
```

Ini membantu policy dan authorization.

Misalnya:

```text
deep cleanup
```

tidak otomatis berarti:

```text
boleh melakukan semua KernelMaintenance
```

# 10. Urutan operasi

Default ordering yang saya rekomendasikan:

```text
Phase 1
Read-only preparation

Phase 2
Filesystem deletion

Phase 3
Filesystem cleanup / empty directories

Phase 4
Optional TRIM

Phase 5
Optional F2FS maintenance

Phase 6
Optional ZRAM maintenance

Phase 7
Verification
```

Secara sederhana:

```text
delete
  ↓
verify filesystem state
  ↓
trim
  ↓
F2FS maintenance
  ↓
verify
```

Kenapa?

Karena tidak ada gunanya menjalankan maintenance filesystem sebelum pekerjaan filesystem selesai.

---

# 11. Tetapi F2FS jangan diperlakukan sebagai "delete"

F2FS maintenance seperti `gc_urgent` bukan operasi filesystem biasa.

Jadi:

```rust
Operation::F2fsMaintenance(...)
```

harus mempunyai policy dan safety berbeda.

Contoh:

```rust
pub struct F2fsMaintenance {
    pub filesystem: FilesystemId,
    pub mode: F2fsMaintenanceMode,
}
```

Dan:

```rust
pub enum F2fsMaintenanceMode {
    UrgentGc,
}
```

Executor kemudian tahu:

```text
ini bukan file deletion
ini kernel/filesystem maintenance
```

Hal ini penting untuk audit dan logging.

---

# 12. Budget Planner

Planner juga harus membatasi workload.

Contoh config:

```rust
pub struct PlanBudget {
    pub max_operations: u32,
    pub max_bytes: u64,
    pub max_scan_entries: u64,
    pub max_duration: Duration,
}
```

Misalnya:

```text
max_operations = 10_000
max_bytes       = 2 GiB
max_duration    = 30 sec
```

Planner tidak boleh menghasilkan:

```text
20.000 operations
```

hanya karena 20.000 file lolos policy.

---

# 13. Bedakan scan budget dan delete budget

Ini dua hal berbeda.

Misalnya:

```text
scan:
    1.000.000 entries

delete:
    maksimal 5.000 entries
```

Scanner boleh menemukan banyak candidate, tetapi Planner hanya memilih yang sesuai budget.

```text
ScanBudget
    ↓
Candidate list
    ↓
Policy
    ↓
PlanBudget
    ↓
CleanupPlan
```

Ini mencegah scan besar otomatis menjadi deletion besar.

---

# 14. Estimate freed space

Planner perlu membuat estimasi:

```rust
pub struct PlanEstimate {
    pub operations: usize,
    pub bytes_reclaimable: u64,
    pub directories: usize,
    pub estimated_duration: Duration,
}
```

Misalnya:

```text
Operations:       1,245
Files:            1,210
Directories:         35
Estimated bytes:  742 MiB
Estimated time:   4.2 s
```

Nilai ini dipakai oleh:

```text
status
explain
dry-run
logging
telemetry
```

---

# 15. Estimated bytes bukan guaranteed bytes

Penting sekali.

Kalau scanner melihat:

```text
foo.tmp = 100 MB
```

tidak berarti setelah delete pasti:

```text
+100 MB free
```

Filesystem metadata, shared blocks, compression, sparse files, dan keadaan lain bisa membuat angka berbeda.

Jadi namanya:

```rust
estimated_bytes
```

bukan:

```rust
guaranteed_freed_bytes
```

Setelah executor selesai, baru report:

```rust
actual_bytes_freed
```

kalau bisa diukur secara reliable.

---

# 16. Deduplication

Candidate bisa duplicate secara logis.

Contoh:

```text
Candidate A → inode 123
Candidate B → inode 123
```

Planner tidak boleh menghasilkan:

```text
unlink inode 123
unlink inode 123
```

Identitas objek dapat direpresentasikan dengan:

```rust
pub struct ObjectIdentity {
    pub dev: u64,
    pub ino: u64,
}
```

Namun identity ini jangan dianggap sebagai satu-satunya safety mechanism.

Ia dipakai untuk:

```text
dedup
tracking
revalidation
reporting
```

sedangkan actual deletion tetap memakai FD-relative + `NOFOLLOW` + validation.

---

# 17. Parent purge harus menghapus child operations

Misalnya Planner menemukan:

```text
PurgeDirectoryContents(cache/)
RemoveFile(cache/a)
RemoveFile(cache/b)
RemoveFile(cache/c)
```

Ini redundant.

Planner harus memilih salah satu model.

### Model A — individual

```text
RemoveFile a
RemoveFile b
RemoveFile c
```

### Model B — purge

```text
PurgeDirectoryContents cache/
```

Jangan:

```text
PurgeDirectoryContents cache/
RemoveFile a
RemoveFile b
```

karena executor menjadi tidak deterministik dan report menjadi kacau.

---

# 18. CleanupPlan harus immutable

Setelah:

```rust
let plan = planner.build(...)?;
```

plan sebaiknya tidak diubah lagi.

```rust
pub struct CleanupPlan {
    pub id: PlanId,
    pub operations: Vec<PlannedOperation>,
    pub estimate: PlanEstimate,
    pub summary: PlanSummary,
}
```

Jika policy berubah:

```text
old plan
   ↓
discard
   ↓
build new plan
```

Bukan:

```text
old plan
   ↓
mutate operation #42
```

Ini membuat audit jauh lebih sederhana.

---

# 19. Plan validation

Sebelum Plan keluar dari Planner:

```rust
pub fn validate_plan(plan: &CleanupPlan) -> Result<(), PlanError>
```

Harus memeriksa misalnya:

```text
✓ operation IDs unique
✓ dependencies exist
✓ no dependency cycle
✓ target valid
✓ no duplicate object
✓ operation count within budget
✓ bytes within budget
✓ no unsafe operation
✓ no conflicting operations
```

Contoh conflict:

```text
RemoveFile(foo)
RemoveEmptyDirectory(parent_of_foo)
```

Tanpa dependency → invalid.

Dengan dependency:

```text
RemoveFile(foo)
    ↓
RemoveEmptyDirectory(parent)
```

→ valid.

# 20. Revalidation sebelum execution

Ini sangat penting.

Plan dibuat pada:

```text
T0
```

Execution mungkin dimulai pada:

```text
T1
```

Di antara keduanya file dapat berubah.

Contoh:

```text
T0:
foo.tmp = regular file

T1:
foo.tmp → symlink
```

Planner tidak boleh percaya data T0 begitu saja.

Executor melakukan:

```text
lookup relative to trusted root
        ↓
NOFOLLOW
        ↓
fstat
        ↓
identity validation
        ↓
type validation
        ↓
delete
```

Jadi ada dua lapisan:

```text
Planning-time validation
+
Execution-time validation
```

# 22. Idempotency

Cleanup daemon harus menganggap filesystem sebagai environment yang berubah.

Misalnya:

```text
Planner:
    delete foo.tmp

Executor:
    foo.tmp sudah dihapus oleh aplikasi
```

Itu bukan necessarily error fatal.

Hasil:

```rust
pub enum OperationResult {
    Removed,
    AlreadyGone,
    Skipped,
    Failed(OperationError),
}
```

Sehingga:

```text
ENOENT
```

dapat dipetakan ke:

```text
AlreadyGone
```

bukan langsung:

```text
Daemon failed
```

---

# 23. Partial failure adalah normal

Misalnya 1.000 file:

```text
990 removed
5 already gone
3 skipped
2 failed
```

Jangan mengembalikan:

```text
cleanup failed
```

saja.

Report harus:

```rust
pub struct ExecutionSummary {
    pub planned: usize,
    pub removed: usize,
    pub already_gone: usize,
    pub skipped: usize,
    pub failed: usize,
    pub bytes_freed: u64,
}
```

Kemudian status keseluruhan:

```rust
pub enum JobOutcome {
    Success,
    PartialSuccess,
    Cancelled,
    Failed,
}
```

# 24. Retry policy

Tidak semua error layak diulang.

Contoh:

```text
ENOENT
    → AlreadyGone

EACCES
    → jangan retry langsung

EBUSY
    → mungkin defer

EIO
    → jangan agresif retry

screen ON
    → cancel/pause

thermal high
    → defer
```

Model:

```rust
pub enum RetryPolicy {
    Never,
    Later(Duration),
    Limited {
        max_attempts: u8,
        backoff: Duration,
    },
}
```

Tetapi retry juga harus dikendalikan Scheduler, bukan loop liar di Executor.

# 25. Cancellation

Cancellation harus bisa terjadi:

```text
sebelum plan
saat scan
saat planning
sebelum execute
di tengah execute
sebelum kernel maintenance
```

Misalnya:

```rust
pub struct CancellationToken {
    ...
}
```

Executor:

```rust
for operation in plan.operations() {
    cancellation.check()?;
    execute_operation(operation)?;
}
```

Untuk recursive deletion:

```rust
for entry in directory {
    cancellation.check()?;
    remove_entry(entry)?;
}
```

Jangan menunggu seluruh tree selesai baru mengecek cancellation.

# 30. Boundary paling penting: AuthorizedPlan

Setelah Planner selesai, saya ingin satu boundary lagi:

```text
CleanupPlan
     ↓
Authorization
     ↓
AuthorizedPlan
```

Contoh:

```rust
pub struct AuthorizedPlan {
    plan: CleanupPlan,
    authorization: AuthorizationProof,
}
```

Executor API:

```rust
pub fn execute(
    &self,
    plan: &AuthorizedPlan,
    context: &ExecutionContext,
) -> ExecutionReport
```

Bukan:

```rust
pub fn execute(path: PathBuf)
```

dan bahkan bukan:

```rust
pub fn execute(candidate: Candidate)
```

Dengan desain ini, secara arsitektural kita memaksa:

```text
Discovery
    ≠
Authorization
    ≠
Execution
```

# 32. Selanjutnya: Executor

Bagian berikutnya justru yang paling sensitif karena di sinilah operasi destruktif benar-benar terjadi.

Kita akan membedah:

```text
Executor
├── execution context
├── operation dispatcher
├── fd-relative deletion
├── directory walker
├── race handling
├── symlink defense
├── mount/device boundary
├── cancellation
├── partial failure
├── error classification
├── F2FS executor
├── TRIM executor
├── ZRAM executor
└── verification
```

Terutama kita perlu merancang **`remove_tree()` yang aman tanpa `rm -rf`, tanpa `canonicalize()`, tanpa mengikuti symlink, dan tetap bekerja pada filesystem Android yang nyata**. Itu akan menjadi salah satu bagian paling penting dari rewrite ini.
