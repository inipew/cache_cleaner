72.md — Planner, Operation Graph, Dependency Ordering, Conflict Detection, Budgeting, Determinism, Idempotency, and Commit Contract

Tujuan

Planner mengubah candidate + policy decision + target/safety metadata menjadi immutable Plan yang berisi PlannedOperation. Planner tidak melakukan mutation.

Pipeline:

Catalog → Scan → Candidate → Policy → Planner → Authorization → Safety → Executor

1. Planner Responsibility

Planner menjawab operation apa yang seharusnya dilakukan, dalam urutan apa, dengan scope dan budget apa.

2. Planner Is Pure-ish

Planner harus sebisa mungkin deterministic dan tidak mempunyai mutation side effect.

3. Inputs

Planner menerima:

- immutable candidate snapshot/stream
- policy decisions
- TargetCatalogSnapshot
- EffectiveConfig
- runtime constraints
- resource constraints

4. Output

```rust
pub struct Plan {
    pub id: PlanId,
    pub job_id: JobId,
    pub config_generation: ConfigGeneration,
    pub catalog_generation: CatalogGeneration,
    pub operations: Arc<[PlannedOperation]>,
    pub budget: PlanBudget,
}
```

5. Plan Immutable

Setelah publication, Plan tidak boleh dimutasi.

6. Operation Identity

Setiap PlannedOperation mempunyai OperationId unique dalam Job.

7. Candidate-to-Operation

Hanya candidate yang Policy-allowed yang dapat menjadi operation.

8. Denied Candidate

Deny/skip candidate tidak menghasilkan destructive operation.

9. Unknown Candidate

Unknown tidak menghasilkan destructive operation.

10. Operation Kind

Use typed enum:

- DeleteFile
- DeleteDirectory
- Reclaim
- Maintenance
- Other supported operations

11. Operation Scope

Operation harus menyimpan TargetId dan relative path/reference.

12. No Raw Authority Path

Absolute path tidak boleh menjadi operation authority.

13. Target Binding

Operation harus bind ke target identity/generation.

14. Config Binding

Operation harus bind ke ConfigGeneration jika policy/config memengaruhi semantics.

15. Candidate Binding

Operation harus menyimpan CandidateId/observation identity.

16. Safety Requirements

Operation mendeklarasikan required safety class/capabilities, tetapi tidak menghasilkan SafetyProof sendiri.

17. Authorization Requirements

Operation mendeklarasikan capability yang diperlukan.

18. Dependency Graph

Operations dapat membentuk DAG.

19. Why DAG

Parent/child filesystem operations membutuhkan ordering.

20. Acyclic Requirement

Planner harus memastikan graph tidak mempunyai cycle.

21. Cycle Failure

Cycle adalah planner error, bukan best-effort execution.

22. Parent-Child Delete

Untuk recursive semantics, child delete biasanya mendahului parent directory deletion.

23. Directory Non-empty

Planner tidak boleh menjanjikan parent delete berhasil sebelum child dependencies selesai.

24. Independent Operations

Unrelated operations dapat parallelize sesuai ResourceManager limits.

25. Ordering Key

Deterministic ordering harus menggunakan stable keys: target identity + relative path + operation kind + tie-breaker.

26. Stable Plan

Same immutable inputs produce same operation graph/order.

27. Plan Fingerprint

Recommended plan fingerprint untuk audit/reproducibility.

28. Fingerprint Inputs

Fingerprint mencakup generation, operation identities, target identities, dan relevant parameters.

29. No Runtime Nondeterminism

Random UUID boleh digunakan untuk identity, tetapi ordering/fingerprint semantics harus deterministic where required.

30. Operation ID

OperationId dapat deterministic within plan atau unique random; jika random, logical identity tetap harus stable untuk persistence/retry.

31. Logical Operation Key

Recommended separate LogicalOperationKey dari AttemptId.

32. Attempt Separation

Retry operation tidak membuat operation scope baru; ia membuat AttemptId baru.

33. Idempotency

Operation semantics harus idempotent atau mempunyai explicit reconciliation strategy.

34. Delete Idempotency

Deleting already-gone object dapat dianggap satisfied sesuai verifier semantics.

35. Replacement Safety

Already-gone path yang sekarang menunjuk object lain tidak boleh dianggap satisfied.

36. Conflict Detection

Planner harus mendeteksi operation overlap.

37. Exact Duplicate

Duplicate operation terhadap identity yang sama harus deduplicated.

38. Parent/Child Conflict

Delete parent + delete child dapat redundant/conflicting tergantung operation semantics.

39. Target Conflict

Operations pada target berbeda tidak boleh dianggap overlapping hanya karena same relative path.

40. Storage Conflict

Operations pada same storage dapat memerlukan serialized resource lock.

41. Protected Conflict

Jika operation conflict dengan protected target, planning harus deny/fail.

42. Rename Conflict

If rename supported, source/destination overlap must be explicit.

43. Reclaim Conflict

Reclaim/trimming operation may conflict with concurrent file mutations and require exclusive resource class.

44. Maintenance Conflict

Filesystem maintenance operation must not run concurrently with incompatible cleanup mutations.

45. Resource Estimate

Each operation should expose estimated resource cost:

- I/O bytes
- CPU
- memory
- open handles
- storage impact

46. Estimate Is Not Actual

Estimate digunakan admission/planning, bukan accounting final.

47. Byte Budget

Plan harus mempunyai max bytes/objects berdasarkan config/policy.

48. Count Budget

Number of operations harus bounded.

49. Memory Budget

Plan materialization harus mengikuti ResourceManager budget.

50. Time Budget

Plan dapat mempunyai deadline/max runtime.

51. Budget Truncation

Jika candidate melebihi budget, planner harus deterministic memilih subset atau menghasilkan explicit budget-exceeded result.

52. No Arbitrary Truncation

Jangan truncate berdasarkan iteration order yang tidak deterministic.

53. Priority Selection

Jika partial plan diizinkan, selection harus berdasarkan explicit priority/stable ordering.

54. All-or-Nothing

Certain job intents dapat membutuhkan complete plan; budget overflow harus fail admission/planning.

55. Best-effort

Best-effort plan harus menandai omitted candidates.

56. Omitted != Failed

Candidate yang tidak masuk karena budget harus distinct dari execution failure.

57. Policy Changes

Planner harus menolak policy decisions dari generation incompatible.

58. Catalog Changes

Planner harus revalidate catalog generation before plan publication.

59. Config Changes

Jika config changes affecting policy/resource, plan harus stale.

60. Runtime Changes

Runtime pressure/thermal changes dapat menyebabkan plan defer atau resource downgrade.

61. Plan Publication Barrier

Plan hanya published setelah graph validation, budget validation, generation validation, and operation validation selesai.

62. No Partial Publication

Caller melihat complete valid plan atau failure.

63. Plan Validation

Validate:

- identity uniqueness
- generation consistency
- target existence in snapshot
- operation support
- dependency DAG
- budget
- scope boundaries

64. Scope Validation

Every operation must remain within TargetDescriptor scope.

65. Capability Validation

Operation required capabilities must be available in target descriptor.

66. Authorization Later

Capability availability does not mean job authorization; Authorization remains later stage.

67. Safety Later

Planner does not generate SafetyProof.

68. Candidate Freshness

Planner should reject obviously stale scan generation.

69. Stale Candidate

Stale candidate dapat trigger rescan rather than unsafe plan.

70. Rescan Policy

Rescan request harus bounded agar stale loops tidak terjadi.

71. Plan Retry

Planning retry must have bounded count/backoff and new plan identity if semantic inputs changed.

72. Plan Version

Plan schema/version harus explicit.

73. Plan Serialization

Persistence DTO must not be treated as executable Plan without validation.

74. No Arbitrary Deserialization

Never deserialize an operation and directly execute it.

75. Operation Parameters

Parameters must be typed and bounded.

76. Delete Parameters

Delete operation dapat menyimpan expected type and recursive flag, not arbitrary shell command.

77. Shell Avoidance

Planner tidak boleh menghasilkan shell command string sebagai authority.

78. Syscall-level Executor

Executor menerima typed operation.

79. Command Injection

No candidate path may become shell command interpolation.

80. Relative Path Encoding

Serialization must preserve exact filesystem bytes where supported.

81. Invalid Paths

Invalid RelativePath cannot enter plan.

82. Special Files

Planner harus menolak destructive operation pada unsupported special file types.

83. Symlink

Symlink operation requires explicit operation semantics; default deny.

84. Directory Operation

Directory delete requires explicit recursive semantics.

85. Recursive Budget

Recursive operation must have object/byte/depth limits.

86. Depth

Plan should store max depth if recursive.

87. Cross-mount

Plan must encode mount boundary requirements.

88. Target Revalidation Requirement

Plan should require final SafetyGate verification before every destructive operation.

89. Multi-operation Safety

One operation's safety proof cannot automatically authorize another operation.

90. Transaction Semantics

Filesystem cleanup is not assumed transactional.

91. Partial Execution

Plan must support partial completion and reconciliation.

92. Checkpoint

Executor/Store records operation state after each meaningful boundary.

93. Operation State

At minimum:

Pending → Ready → Executing → Verifying → terminal.

94. Planner Does Not Set Execution State

Planner only creates planned operations.

95. Dependency Readiness

Executor can run operation only after dependencies terminal-success/satisfied according to graph semantics.

96. Failed Dependency

Dependent operation normally becomes blocked/skipped, not blindly executed.

97. Already Satisfied Dependency

Verifier may classify dependency satisfied without actual mutation if object was already gone.

98. Dependency Result

Dependency semantics must be typed.

99. Parallelism

Independent operations can be parallelized if resource locks permit.

100. Deterministic Parallelism

Parallel execution must not change logical result ordering or accounting.

101. Lock Keys

Plan should expose resource lock keys for ResourceManager.

102. Lock Granularity

Prefer target/storage-scoped locks over global lock, while preserving safety.

103. Lock Ordering

Planner/ResourceManager must use deterministic lock ordering to avoid deadlock.

104. Admission

Plan must be admissible under current resource constraints or marked waiting.

105. Resource Wait

Waiting for resource is not plan failure.

106. Cancellation

Plan must be cancellable before execution.

107. Timeout

Plan deadline should propagate to execution context.

108. Expired Plan

Expired plan cannot be newly executed.

109. Generation Expiry

Generation mismatch must be checked before execution.

110. Authorization Expiry

Authorization may have expiry; planner must not assume indefinite permission.

111. Audit

Plan creation event records input generations, counts, budget, and fingerprint.

112. Privacy

Do not dump all candidate paths into standard audit logs.

113. Explain Plan

CLI/UI may request human-readable plan explanation.

114. Explain != Execute

Explain command must be read-only.

115. Dry Run

Dry run produces Plan/decision but must not enter mutation executor.

116. Dry Run Fidelity

Dry-run output should use same scanner/policy/planner path as real execution, excluding mutation.

117. Plan Cache

Plan caching is dangerous because filesystem state changes; cached plan must be generation/identity-bound.

118. Cache Invalidation

Any target topology or policy change invalidates affected cached plans.

119. No Infinite Replan

Repeated stale plans require bounded retry and eventual RecoveryRequired/manual intervention.

120. Failure Classification

Planner errors should distinguish:

- invalid input
- stale snapshot
- conflict
- budget exceeded
- unsupported operation
- internal error
- cancellation
- timeout

121. Internal Error

Internal planner error cannot produce executable partial plan.

122. Property Testing

Properties:

- no operation outside target
- no duplicate logical operations
- DAG acyclic
- generation consistent
- budget respected
- deterministic output

123. Fuzzing

Fuzz candidate combinations, dependency graph creation, path data, and budget boundaries.

124. Graph Testing

Generate random dependency graphs and assert cycle detection/topological order.

125. Overflow Testing

Test byte/count/depth arithmetic near integer limits.

126. Race Testing

Change catalog/config after scan and before plan publication.

127. Definition of Done

Planner production-ready jika:

- immutable Plan
- typed operations
- deterministic ordering
- dependency DAG
- conflict detection
- bounded budgets
- generation binding
- scope/capability validation
- no shell authority
- recursive limits
- resource lock metadata
- cancellation/deadline
- partial execution semantics
- persistence-ready operation identity
- audit/fingerprint
- property/fuzz/race tests

128. Final Invariants

1. Planner tidak melakukan mutation.
2. Candidate bukan operation sampai planner membuat typed operation.
3. Plan immutable setelah publication.
4. OperationId unique dalam Job.
5. ConfigGeneration konsisten.
6. CatalogGeneration konsisten.
7. Operation selalu bind ke target.
8. Operation tidak boleh keluar dari target scope.
9. Unknown policy tidak menghasilkan destructive operation.
10. Protected target tidak dapat masuk destructive plan tanpa explicit permitted semantics.
11. Dependency graph harus acyclic.
12. Ordering deterministic.
13. Budget selalu bounded.
14. Overflow tidak boleh wrap.
15. Cross-mount semantics explicit.
16. Symlink semantics explicit.
17. Recursive operation mempunyai depth/count/byte limits.
18. Planner tidak menghasilkan shell command authority.
19. SafetyProof dibuat kemudian oleh SafetyGate.
20. Authorization dibuat kemudian oleh Authorization layer.
21. Stale generation tidak boleh dieksekusi.
22. Plan expiry tidak boleh dilewati.
23. Partial plan harus explicit.
24. Dependency failure tidak boleh diam-diam dieksekusi.
25. Resource lock ordering harus deterministic.
26. Plan publication atomic.
27. Plan provenance dapat diaudit.
28. Cached plan harus identity/generation-bound.
29. Planner error tidak menghasilkan executable partial plan.
30. Executor tidak boleh memperluas scope Plan.
