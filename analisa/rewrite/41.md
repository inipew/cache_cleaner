Authorization Layer, Capability Model, Policy Decision, Scope Enforcement, Generation Binding, dan Final Authorization Contract

1. Tujuan

Authorization Layer adalah boundary terakhir yang menentukan apakah PlannedPlan benar-benar boleh menjadi AuthorizedPlan.

Planner menjawab:

“Operasi apa yang direncanakan?”

Authorization menjawab:

“Operasi mana yang benar-benar diizinkan?”

Safety menjawab:

“Apakah operasi tersebut aman terhadap filesystem saat akan dijalankan?”

Executor menjawab:

“Bagaimana operasi yang sudah authorized dijalankan?”

Flow:

Candidate

▼

▼

▼

▼

│
▼

│
├── REJECT ──► no execution
│
▼

▼

│

2. Prinsip Utama

Authorization harus:

eksplisit

deterministik

immutable pada output

scope-limited

generation-bound

capability-aware

fail closed

tidak melakukan mutation

tidak mengubah filesystem

tidak memanggil shell

tidak menerima arbitrary client authority

Authorization tidak boleh menjadi tempat untuk “force” operation.

Tidak boleh ada:

authorize_anything()

force_authorize()

authorize_path(path)

authorize_without_safety()

authorize_as_root()

3. PlannedPlan vs AuthorizedPlan

PlannedPlan berarti:

“Planner mengusulkan sekumpulan operation.”

AuthorizedPlan berarti:

“System telah memberikan permission untuk sekumpulan operation tertentu.”

Perbedaan ini harus terlihat dalam type system.

Contoh konseptual:

PlannedPlan
↓
AuthorizationDecision
↓
AuthorizedPlan

Executor tidak boleh menerima PlannedPlan.

Executor hanya menerima AuthorizedPlan.

10. Scope Escalation

Authorization wajib menolak scope escalation.

Contoh:

Package A
→ cache

Contoh lain:

/cache

valid.

/cache/../other/file

12. Policy vs Authorization

Policy menentukan eligibility.

Authorization menentukan permission.

Contoh:

File berumur 30 hari.

Approved

CanRemoveFile = false

Final:

Rejected

Sebaliknya:

Policy:

Approved

Authorization:

Approved

Safety:

ChangedSinceScan

Final:

Rejected sebelum mutation.

18. Authorization Expiration

AuthorizedPlan dapat memiliki expiration.

Contoh:

authorized_at = T1

expires_at = T1 + validity window

Jika Executor menerima plan setelah expiration:

Expired

Operation tidak dijalankan.

Expiration bukan pengganti Final Safety Gate.

Keduanya berbeda.

19. Authorization Time

Wall clock tidak boleh menjadi satu-satunya basis security decision.

Jika expiration membutuhkan monotonic duration:

gunakan MonotonicClock.

Wall clock dapat digunakan untuk audit timestamp.

Konsep:

WallClock
→ audit/logging

MonotonicClock
→ timeout/expiration duration

20. Request Identity

Contoh:

Client tidak boleh mengirim:

Server harus mendapatkan identity dari transport/runtime.

23. Authorization Formula

Secara konseptual:

Authorized =
ValidPlan
AND PolicyApproved
AND CapabilityAvailable
AND ScopeAllowed
AND GenerationMatch
AND RuntimeReady
AND NotExpired
AND NotCancelled

Namun implementasi jangan hanya menggunakan boolean.

Setiap kondisi harus menghasilkan typed reason ketika gagal.

24. Invalid Plan

Contoh:

25. Budget Authorization

Authorization harus memastikan plan masih berada dalam authorized budget.

Planner:

estimated operations = 1000

Authorization budget:

max operations = 500

Maka:

REJECT

Planner seharusnya sudah mengetahui budget, tetapi Authorization tetap melakukan enforcement.

Defense in depth.

26. Budget Tidak Boleh Diperbesar

Jika Planner menghasilkan:

max_bytes = 1 GiB

Authorization tidak boleh mengubahnya menjadi:

max_bytes = 2 GiB

kecuali itu adalah proses explicit re-planning dan re-authorization.

Authorization hanya boleh mempersempit authority, bukan memperluasnya.

27. Capability Narrowing

Tidak perlu memberikan seluruh capability set kepada Executor.

28. Least Authority

Executor harus mendapatkan authority minimum yang diperlukan.

Contoh:

29. Capability Token

Jika implementation menggunakan capability object/token, token harus:

├── Generation

30. No String Capability

Gunakan enum/type yang jelas.

63. Keputusan Arsitektur

Authorization adalah boundary antara PlannedPlan dan AuthorizedPlan.

Capability berasal dari server-side/platform state, bukan client.

Authorization menggunakan least authority.

Scope harus eksplisit dan tidak boleh mengalami escalation.

Authorization hanya boleh mempersempit authority, bukan memperluasnya.

Generation harus terikat pada AuthorizedPlan.

Expired atau stale plan tidak boleh dieksekusi.

Authorization tidak melakukan mutation.

Executor tidak boleh menerima PlannedPlan.

Final Safety Gate tetap wajib setelah Authorization.

Tidak ada bypass melalui CLI, IPC, scheduler, debug mode, atau configuration.

Struktur authority akhirnya menjadi:

Request
│
▼
Policy
│
▼
Plan
│
▼
Authorization
│
▼
AuthorizedPlan
│
▼
Final Safety
│
▼
Mutation

Dengan ini, sistem memiliki pemisahan yang jelas antara:

“boleh dilakukan menurut policy”

dan

“diizinkan dilakukan oleh sistem”

serta

“aman dilakukan terhadap filesystem saat ini”.
