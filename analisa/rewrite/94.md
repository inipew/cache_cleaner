# 94.md — Configuration, Policy Migration, dan Runtime Reconfiguration

## Tujuan

Configuration menentukan behavior daemon, tetapi perubahan config dapat terjadi ketika Job sedang queued, planning, waiting resource, atau bahkan setelah plan dibuat.

Karena itu config harus diperlakukan sebagai versioned input terhadap decision, bukan global mutable state yang bebas berubah di tengah execution.

## 1. Configuration Layers

Pisahkan:

```text
Defaults
System configuration
User configuration
Runtime overrides
Policy constraints
```

Layer yang lebih lemah tidak boleh mengoverride hard safety constraint.

## 2. Typed Configuration

Config domain sebaiknya memakai typed value:

- Duration
- ByteSize
- Percentage
- Temperature
- RetryLimit
- ConcurrencyLimit
- Path/Target reference

Hindari primitive-heavy configuration yang membuat invalid state mudah dibuat.

## 3. Validation

Config harus divalidasi sebelum menjadi active config.

Validation meliputi:

- syntax
- type/range
- semantic consistency
- target references
- policy constraints
- resource limits

## 4. Atomic Activation

Config baru tidak boleh terlihat sebagian.

Model:

```text
parse
→ validate
→ persist
→ commit
→ increment ConfigGeneration
→ activate atomically
```

## 5. ConfigGeneration

Setiap active config mempunyai generation.

Plan menyimpan generation yang digunakan.

Jika generation berubah sebelum mutation:

```text
stale plan
→ re-evaluate/replan
```

## 6. Running Operation

Config change tidak otomatis mengubah mutation yang sedang berlangsung.

Operation mempertahankan execution contract yang sudah authorized.

Namun safety-critical context tetap dapat diinvalidasi oleh external state changes.

## 7. Policy vs Safety

Config dapat mengatur policy seperti:

```text
max candidates
min age
cleanup schedule
```

Tetapi tidak boleh mengubah hard safety boundary seperti trusted-root requirement hanya melalui ordinary preference.

## 8. Force Settings

`force`/confirmation behavior harus explicit policy.

Tidak boleh berubah menjadi hidden global bypass.

## 9. Runtime Reload

Reload harus menjadi state transition:

```text
ReloadRequested
→ parse
→ validate
→ persist/activate
→ ConfigGeneration++
→ reevaluate scheduler
```

Bukan sekadar mengganti `Arc<RwLock<Config>>` lalu berharap semua subsystem konsisten.

## 10. Snapshot Semantics

Scheduler/planner/executor menerima config snapshot.

Jangan membaca mutable config berkali-kali selama satu logical decision dan menghasilkan behavior campuran.

## 11. Policy Snapshot

Policy evaluation harus dapat direproduksi dari:

```text
ConfigGeneration
PolicyVersion
Target/Candidate context
Platform snapshot
```

## 12. Existing Job

Queued Job dapat:

- tetap memakai config generation saat creation
- atau di-replan memakai latest config

Choice harus explicit per Job class.

## 13. Scheduled Work

Scheduled maintenance biasanya lebih cocok menggunakan latest eligible policy saat execution, bukan stale config dari berhari-hari lalu.

## 14. Manual Work

Manual request dapat membawa explicit scope/parameters, tetapi tetap tunduk pada current safety and authorization.

## 15. Config Migration

Schema migration berbeda dari semantic policy migration.

Contoh:

```text
v1: cleanup_interval_minutes
v2: schedule.duration
```

Migration harus mempertahankan intended behavior atau menghasilkan explicit changed semantics.

## 16. Unit Conversion

Migration harus berhati-hati terhadap unit.

Contoh:

```text
seconds ↔ milliseconds
bytes ↔ KiB
Celsius ↔ deci-Celsius
```

Gunakan typed conversion, bukan numeric cast tanpa context.

## 17. Removed Settings

Setting yang dihapus harus mempunyai migration policy:

- map to replacement
- retain as deprecated
- ignore
- reject

Jangan silently change destructive behavior.

## 18. Renamed Settings

Rename harus mempertahankan semantic value.

Jika semantics berubah, treat sebagai new setting + explicit migration.

## 19. Invalid Runtime Reload

Config invalid tidak boleh menggantikan active valid config.

Behavior:

```text
reload fails
→ keep previous active config
→ report error
```

## 20. Persist Failure

Jika config persistence gagal:

```text
do not advertise activation
```

In-memory temporary override dapat digunakan hanya jika contract memang mendukung non-durable mode.

## 21. Config and Crash

Activation boundary harus crash-safe:

```text
old config
or
new valid config
```

bukan partial file.

## 22. File Update

Gunakan atomic replacement semantics sesuai platform/storage:

```text
write temp
→ flush/fsync as required
→ atomic rename
→ durable parent update as required
```

## 23. Config Permissions

Active config harus mempunyai ownership/permission yang sesuai deployment.

Daemon tidak boleh membaca arbitrary world-writable config sebagai authority.

## 24. Config Source

Source authority harus diketahui.

Jika ada multiple files:

```text
system
user
runtime
```

precedence harus deterministic dan dapat dijelaskan.

## 25. Environment Variables

Environment override harus dibatasi pada settings yang memang diizinkan.

Jangan membiarkan arbitrary environment variable mengubah security-critical target roots.

## 26. CLI Overrides

CLI override hanya berlaku pada request/session jika contract demikian.

Jangan otomatis menulis override menjadi permanent configuration.

## 27. IPC Overrides

Remote/local IPC client tidak boleh mengubah persistent policy tanpa authorization yang sesuai.

## 28. Secret Configuration

Secret settings harus mempunyai lifecycle terpisah jika memungkinkan.

Config dump/status harus meredact secret.

## 29. Config Diff

Operator dapat melihat diff antara active dan proposed config.

Diff harus menampilkan semantic changes, bukan hanya raw text.

## 30. Dry Run

Config change dapat mempunyai validation/dry-run mode yang tidak mengaktifkan mutation.

Dry-run tidak boleh menjalankan destructive executor.

## 31. Revalidation After Reload

Config reload dapat membuat queued plan stale.

Scheduler harus menentukan impacted Jobs berdasarkan generation/dependency.

## 32. Policy Change During Execution

Policy change tidak otomatis membatalkan completed mutations.

Current operation follows its explicit contract; future work follows new policy.

## 33. Safety Overrides

Tidak boleh ada config field yang membuat safety engine menerima arbitrary trusted roots tanpa independent trust validation.

## 34. Default Changes

Perubahan default antar release adalah behavioral migration.

Release notes/tests harus mengidentifikasi perubahan tersebut.

## 35. Configuration Compatibility

Maintain compatibility matrix untuk:

```text
config schema
binary version
policy version
```

## 36. Configuration Rollback

Rollback config harus atomic.

Jika rollback membuat policy invalid terhadap current target catalog/platform capability, reject.

## 37. Policy Versioning

Policy semantics sebaiknya mempunyai explicit version ketika behavior dapat mempengaruhi historical/replay semantics.

## 38. Reproducibility

Untuk audit, simpan reference terhadap:

```text
ConfigGeneration
PolicyVersion
```

bukan full config blob di setiap operation jika tidak diperlukan.

## 39. Configuration Observability

Expose:

- active generation
- schema version
- policy version
- source
- last reload result
- last migration

Jangan expose secret.

## 40. Definition of Done

Config/policy management production-ready jika:

- config typed
- validation explicit
- activation atomic
- ConfigGeneration tersedia
- policy version tersedia
- snapshot semantics jelas
- reload transactional
- invalid reload mempertahankan config lama
- persistence failure tidak false-advertise activation
- migration unit-safe
- config permissions terlindungi
- source precedence deterministic
- runtime overrides scoped
- security settings tidak arbitrary
- rollback explicit
- behavior changes versioned
- operation reproducibility tersedia

## Final Invariants

1. Active config selalu valid.
2. Invalid reload tidak menggantikan active config.
3. Config activation atomic.
4. ConfigGeneration membedakan context lama dan baru.
5. Policy version terpisah dari schema version.
6. Plan tidak boleh diam-diam memakai mixed config.
7. Running mutation tidak berubah semantics secara arbitrer karena reload.
8. Safety boundary tidak dapat diubah lewat preference biasa.
9. Unit conversion harus typed.
10. Removed setting memiliki migration semantics.
11. Config persistence failure tidak boleh dianggap success.
12. Config source authority harus jelas.
13. CLI/IPC override tidak otomatis menjadi permanent config.
14. Secret tidak boleh muncul dalam config dump/log.
15. Dry-run tidak menjalankan destructive mutation.
16. Config rollback harus atomic dan valid.
17. Default changes diperlakukan sebagai behavioral migration.
18. Operation dapat mengidentifikasi ConfigGeneration dan PolicyVersion.
19. Config behavior harus deterministic.
20. Security-critical configuration fail-closed.
