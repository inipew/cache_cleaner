Lanjut ke **Kernel / Resource Governor**.

Ini layer yang memastikan cleaner bukan cuma **aman terhadap filesystem**, tetapi juga **aman terhadap performa device**. Targetnya bukan membuat cleanup secepat mungkin, melainkan:

> **cleanup berjalan ketika aman, dengan resource footprint serendah mungkin, dan berhenti ketika device membutuhkan resource tersebut.**

# 569. Pisahkan `ResourceGovernor` dari Scheduler

Scheduler menentukan:

```text id="m3q8p1"
"apakah cleanup boleh berjalan?"
```

ResourceGovernor menentukan:

```text id="x7n2r5"
"kalau berjalan, bagaimana resource-nya dibatasi?"
```

Contoh:

```text id="q4m8x8"
Scheduler:
    Ready

Governor:
    CPU = idle
    IO  = idle
    memory = bounded
```

# 570. API utama

Tetapi jangan membuat satu fungsi raksasa:



# 572. CPU scheduling

Ada beberapa mekanisme:

```text id="x8q2m4"

```

Jangan menganggap semuanya tersedia pada setiap Android device.

```rust id="n5p7r2"
pub struct KernelCapabilities {

```

# 573. Prioritas CPU

Preferensi:

```text id="m8q3x1"
1. SCHED_IDLE / equivalent scoped mechanism
2. cgroup CPU controls
3. nice +19
4. no extra manipulation
```

Tetapi jangan menerapkan semua sekaligus tanpa alasan.

# 574. Nice

Fallback sederhana:

```text id="p4r7n2"
nice = +19
```

Tujuannya:

> cleanup kalah prioritas terhadap workload normal.

Tetapi nice bukan hard resource limit.

# 575. `SCHED_IDLE`

Jika tersedia dan sesuai workload, cleanup dapat berjalan dengan scheduling class idle.

Ini cocok karena cleaner bukan latency-sensitive workload.

Tetapi jangan menjadikan kegagalan `SCHED_IDLE` sebagai fatal:

```text id="x3m8q7"
SCHED_IDLE unavailable
      ↓
nice fallback
```


kita dapat memberi cleaner scope resource tersendiri.

Tetapi:

> **Jangan membuat atau merombak hierarchy Android secara agresif.**

Cleaner sebaiknya mendapatkan scope yang:

Jangan melakukan:

hanya demi cleanup.

# 579. CPU cgroup

Kalau tersedia, CPU budget dapat dipakai sebagai tambahan.

Namun perlu dibedakan:

```text id="m3q7x8"
CPU weight

```

Masing-masing memiliki semantics berbeda.

Untuk v1:

> prefer low-priority scheduling daripada membuat CPU quota agresif yang bisa menyebabkan cleanup menggantung terlalu lama.

# 580. I/O priority

Gunakan:


jika tersedia.

Tujuan:

```text id="n8m3q1"
foreground I/O
   >
system I/O
   >
cleanup I/O
```

secara scheduling priority.

---

# 581. Jangan pakai realtime I/O

Tidak boleh:

```text id="x4q8m2"
IOPRIO_CLASS_RT
```

untuk cleaner.

Tidak ada alasan cache cleaner mendapatkan real-time I/O priority.

---

# 582. Cgroup I/O

Jika cgroup v2 dan `io` controller tersedia, dapat digunakan sebagai additional guard.

Tetapi sekali lagi:

```text id="m7p3r8"
capability detection
      ↓
apply only if safe
```

Jangan membuat assumption berdasarkan Android version.

---

# 583. ResourceGuard

Perubahan resource state harus RAII.

Contoh:

```rust id="q5m8x1"
let guard = ResourceGuard::enter(&governor)?;
```

Kemudian:

```text id="x7r2n4"
cleanup
```

dan ketika scope selesai:

```text id="m3p8q6"
Drop(ResourceGuard)
```

mengembalikan state.

---

# 584. Tetapi ada aturan penting

ResourceGuard hanya boleh restore:

> **state yang cleaner sendiri ubah.**

Misalnya sebelum cleanup:

```text id="n8q2r5"
nice = 0
```

cleaner:

```text id="p4m7x1"
nice = +19
```

→ restore ke 0.

Tetapi kalau external process mengubah nice saat cleaner berjalan, jangan blindly restore berdasarkan asumsi lama.

---

# 585. Ownership of state

Lebih aman menyimpan:

```rust id="x8m3q2"
pub struct AppliedResourceChange {
    original: ResourceState,
    applied: ResourceState,
}
```

Saat restore:

```text id="q7p2n8"
current == applied?
       │
   yes ─┴─→ restore original
       │
      no
       ↓
external change detected
       ↓
do not overwrite
```

Ini mencegah cleaner merusak perubahan milik proses lain.

# 586. PSI

PSI = Pressure Stall Information.

Kita dapat memonitor:

```text id="m5r8x2"
/proc/pressure/cpu
/proc/pressure/io
/proc/pressure/memory
```

Tetapi PSI bukan:

```text id="x4q7n1"
single "device busy" number
```

Ada beberapa dimensi dan semantics.

---

# 587. Jangan gunakan PSI sebagai satu-satunya gate

Contoh buruk:

```text id="p8m2r5"
if cpu_pressure < 10% {
    cleanup();
}
```

Tidak cukup.

Kita ingin:

```text id="n3x7q1"
screen
+
user activity
+
thermal
+
storage
+
PSI
+
job budget
```

---

# 588. PSI digunakan untuk adaptation

Misalnya:

```text id="m7q3p8"
Normal pressure
    ↓
continue

High IO pressure
    ↓
pause/cancel

High memory pressure
    ↓
cancel

Critical thermal
    ↓
cancel immediately at safe boundary
```

---

# 589. Bedakan pause dan cancel

Untuk v1 saya justru menyarankan **cancel + fresh retry** daripada kompleksitas pause/resume.

Karena plan dapat menjadi stale.

Jadi:

```text id="x8p2m4"
Pressure high
    ↓
cancel job
    ↓
new scan later
```

lebih mudah diverifikasi.

# 590. Thermal

Thermal controller membaca state platform/kernel.

Abstraction:

```rust id="q4m8r1"
    Normal,
    Warm,
    Hot,
    Critical,
    Unknown,
```

Scheduler memakai hasilnya.

Kernel layer bertugas:


# 591. Thermal policy

Contoh:


# 595. RAII untuk F2FS

# 625. Invariant Kernel layer

Saya akan menetapkan:

```text id="m7q2x9"
1. Never modify global kernel state without explicit operation.
2. Prefer scoped changes.
3. Restore only state owned by cleaner.
4. Never assume kernel capabilities from Android API level.
5. Detect capabilities at runtime.
6. Never increase privilege to make optimization work.
7. Never use realtime CPU/I/O priority.
8. Resource pressure may cancel work.
9. Unknown thermal/pressure state is conservative.
10. Kernel maintenance never expands filesystem scope.
11. F2FS operations require actual F2FS capability.
12. TRIM target must be trusted/typed.
13. ZRAM target must be trusted/typed.
14. Maintenance failure must not erase filesystem-cleanup results.
15. Resource tuning must never compromise IPC responsiveness.
16. No busy-loop polling.
17. No arbitrary sysfs path from config/IPC.
```

1. **`platform/`** — Android users, packages, FBE, storage, properties, SELinux, filesystem discovery.
2. **`fs/` low-level implementation** — konkretisasi `openat`/`fstatat`/`unlinkat` dan `openat2`.
3. **`ipc/` protocol** — framing, `SO_PEERCRED`, request/response, capability authorization.
4. **`config/`** — schema, validation, reload, hard limits.
5. **`telemetry/`** — logging, explain, metrics, audit tanpa membocorkan data.
6. Terakhir **`app/` + `main.rs`** — menyatukan semuanya menjadi daemon executable.

Saya sarankan setelah ini kita masuk ke **`platform/`**, karena layer itu adalah yang paling menentukan bagaimana desain generik di atas dipetakan secara aman ke **Android multi-user + DE/CE/FBE + package identity + filesystem discovery**, tanpa mencemari domain dengan path/path Android.
