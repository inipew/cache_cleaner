48.md — Target Catalog Runtime Integration, Android Package Discovery, User/Package/Storage Mapping, Target Identity, Catalog Generation, Target Availability, and Catalog Refresh Contract

Tujuan

Dokumen ini mengunci hubungan antara PlatformSnapshot dengan Target Catalog.

PlatformSnapshot menyediakan fakta tentang sistem.

Target Catalog mengubah fakta tersebut menjadi daftar target cleanup yang tervalidasi dan typed.

Alur:

```
Android / Linux
     │
     ▼
Platform Adapters
     │
     ▼
PlatformSnapshot
     │
     ▼
TargetCatalogBuilder
     │
     ▼
CatalogSnapshot
     │
     ├── TargetId
     ├── PackageId
     ├── UserId
     ├── TargetClass
     ├── TrustedRoot
     ├── StorageClass
     └── Availability
            │
            ▼
         Scanner
```

1. Prinsip Utama

Target Catalog bukan scanner.

Target Catalog bukan policy engine.

Target Catalog bukan executor.

Target Catalog menjawab:

```
"Target cleanup apa yang saat ini diketahui,
 valid secara platform,
 dan dapat diberikan kepada pipeline?"
```

Catalog tidak menjawab:

```
"Apa yang harus dihapus?"
```

Jawaban tersebut milik Policy + Planner.

2. Catalog Sebagai Translation Boundary

Platform:

```
raw platform facts
```

Catalog:

```
typed cleanup targets
```

Scanner:

```
object discovery
```

Policy:

```
eligibility
```

Contoh:

```
PlatformSnapshot
    │
    ▼
Package P
User 0
Storage CE
    │
    ▼
Catalog
    │
    ▼
TargetId = AppCache(P, User0)
```

3. CatalogSnapshot

CatalogSnapshot adalah immutable representation dari target yang tersedia pada satu generation.

Contoh:

```
CatalogSnapshot {
    generation
    platform_generation
    targets[]
    created_at
    validity
}
```

4. CatalogGeneration

Setiap CatalogSnapshot memiliki:

```
CatalogGeneration
```

Contoh:

```
CatalogGeneration = 100
```

Jika target topology berubah:

```
CatalogGeneration = 101
```

5. PlatformGeneration vs CatalogGeneration

Keduanya berbeda.

PlatformGeneration:

```
perubahan fakta platform
```

CatalogGeneration:

```
perubahan daftar target yang tersedia
```

Contoh:

```
thermal state berubah
```

PlatformGeneration:
11 -> 12

CatalogGeneration:
tetap 20

Karena target cleanup tidak berubah.

6. Material Catalog Change

CatalogGeneration harus berubah jika:

```
package installed
package removed
user added
user removed
target root changed
storage class changed
mount boundary changed
target availability changed
package identity changed
```

7. Non-Material Platform Change

Tidak semua platform change harus membuat catalog generation berubah.

Contoh:

```
thermal state
```

dapat mengubah readiness tanpa mengubah target catalog.

8. Catalog Builder

TargetCatalogBuilder menerima:

```
PlatformSnapshot
```

dan menghasilkan:

```
CatalogSnapshot
```

9. Builder Harus Read-Only

CatalogBuilder tidak boleh:

```
create directory
delete file
modify package
mount storage
change permission
```

10. Builder Must Not Scan Entire Tree

Catalog discovery bukan filesystem recursive scan.

Builder hanya menemukan target roots berdasarkan platform/catalog metadata.

Contoh:

```
package metadata
    │
    ▼
known cache root
```

Kemudian Scanner melakukan recursive traversal.

11. Target Identity

Target harus menggunakan:

```
TargetId
```

bukan arbitrary string path.

12. TargetId

TargetId harus stable dan typed.

Contoh konseptual:

```
AppCache {
    package_id
    user_id
}
```

13. TargetId Tidak Sama Dengan Path

Path dapat berubah.

Target identity harus tetap berdasarkan semantic identity.

Contoh:

```
PackageId + UserId + TargetClass
```

14. TargetClass

TargetClass mendeskripsikan semantic role.

Contoh:

```
AppCache
AppCodeCache
AppTemporary
SystemCache
RuntimeTemporary
Other
```

15. Unknown TargetClass

Unknown target class tidak boleh otomatis menjadi cleanup target.

Default:

```
Unavailable
```

Excluded

16. TargetDescriptor


17. TrustedRoot

TargetDescriptor harus mengacu pada TrustedRoot yang sudah tervalidasi.

Catalog tidak boleh membuat:

```

```

18. Root Construction

TrustedRoot harus dibuat melalui trusted platform/catalog constructor.

Contoh konseptual:

```

    │
    ▼

    │
    ▼

```

19. Root Identity

TrustedRoot menyimpan identity information yang diperlukan Safety.

Contoh:

```

inode/object identity
filesystem identity
mount identity
```

20. Root Revalidation

Catalog valid saat snapshot dibuat.

Safety tetap harus melakukan revalidation saat execution.

Catalog bukan pengganti final safety gate.

23. Package Name

Package name harus divalidasi.

Tidak boleh:


24. PackageId

PackageId adalah domain identifier.

Jangan gunakan:

```
String
```

di seluruh pipeline sebagai identity.

Gunakan:

```
PackageId
```

25. UserId

UserId juga typed.

Jangan menggunakan arbitrary integer sebagai user identity tanpa validation.

26. UID

UID adalah platform identity.

UID tidak selalu identik dengan:

```
UserId
PackageId
```

27. Package/User Mapping

Satu package dapat memiliki state berbeda pada beberapa users.

Contoh:

```
Package A
   │
   ├── User 0 = Installed
   ├── User 10 = Installed
   └── User 11 = Removed
```

28. Target Generation

Target identity harus mempertimbangkan user.

Contoh:

```
AppCache(package=A,user=0)
```

berbeda dari:

```
AppCache(package=A,user=10)
```

29. Storage Mapping


Contoh:

```

```

30. Storage Mapping Tidak Boleh Berdasarkan String Saja

Jangan:

```
if path.contains("/user/0/")
    CE
```

31. Credential Protected Mapping

Jika target berada pada credential-protected storage:

```

```

32. Device Protected Mapping

Device-protected target memiliki lifecycle berbeda.

Catalog harus mempertahankan classification tersebut.

33. Shared Storage

Shared storage bukan cache secara default.

Catalog harus:

```
exclude
```

atau
mark unsupported

kecuali explicit supported target definition tersedia.

34. External Storage

External storage harus memiliki semantics terpisah.

Jangan memasukkannya ke generic:

```
AppCache
```

37. Target Protection

39. PlatformProtected

Tidak dapat di-override oleh Policy exception.

40. ConfigProtected

Dapat berasal dari EffectivePolicy.

41. Unknown Protection

Jika protection status diperlukan untuk destructive operation:

```

```

42. Target Availability and Generation


44. Config Reload

Tidak semua config reload membutuhkan Catalog rebuild.

Jika config hanya:

```
minimum_age
```

Catalog tidak berubah.

Jika config mengubah:

```
target enablement
```

maka Effective Target View dapat berubah.

45. Catalog vs Effective Policy

Pisahkan:

```
Physical Target Catalog
Effective Target Policy View
```

Physical Catalog:

```
apa target yang ada?
```

Policy:

```

```

46. Catalog Should Be Broad but Safe

Catalog boleh mengetahui target yang tersedia.

Policy menentukan apakah target eligible.

Namun catalog tetap harus mengecualikan target yang secara invariant tidak boleh menjadi cleanup target.

47. Target Catalog Is Not Allowlist Bypass

Adanya target di catalog tidak berarti:

```
authorized to delete
```

48. Target Catalog Is Not Denylist

Tidak semua target yang tidak ada di catalog dianggap malicious.

Bisa saja:

```
unsupported
unknown
```

Scenario:

```

    │
    ▼

    │
    ▼

    │
    ▼
```

59. Catalog Refresh

Refresh harus atomic.

Flow:

```
OldCatalog
    │
    ▼
Discover
    │
    ▼
Validate
    │
    ▼
NewCatalog
    │
    ▼
AtomicSwap
```

60. Failed Refresh

Jika rebuild gagal:

```
OldCatalog remains active
```

Jangan mengganti dengan:

```
empty catalog
permissive catalog
partially built catalog
```

61. Partial Discovery Failure

Jika package discovery gagal sebagian:

```
target affected = unavailable/unknown
```

Jangan:

```
silently omit safety-critical information and continue as if complete.
```

62. Complete vs Partial Snapshot

CatalogSnapshot dapat memiliki:

```

```

```

```

63. Destructive Planning with Partial Catalog

Default:

```
Partial catalog
    ▼
destructive cleanup blocked for affected scope
```

64. Unaffected Scope

Jika hanya User 10 discovery gagal:

```
User 0 targets
```

dapat tetap tersedia jika independence dapat dibuktikan.

65. Catalog Consistency

Target list harus konsisten.

Tidak boleh:

```

```

66. Duplicate TargetId

```

```

67. Duplicate Root

Dua TargetDescriptor tidak boleh mengklaim identity yang sama jika semantics melarang overlap.

Overlap harus explicit.

68. Target Overlap

Contoh:

```

    /cache

Target B
    /cache/subtree
```

Jika keduanya dapat menghasilkan overlapping deletion:

```

```

69. Parent/Child Targets

```

   │
   ├── AppCache
   ├── AppCodeCache
   └── AppTemporary
```

Parent target tidak otomatis berarti parent deletion allowed.

70. Cleanup Target Must Be Explicit

hanya boleh digunakan sebagai cache/read-only hint.

Jangan langsung gunakan persisted catalog untuk destructive authorization.


145. Crash Recovery

Setelah daemon crash:

```
old catalog
    !=
current truth
```

```
cache != authority
```
