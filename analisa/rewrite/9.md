Lanjut ke **Executor**. Ini adalah boundary paling kritis dalam seluruh desain, karena semua layer sebelumnya masih bersifat “memutuskan”, sedangkan Executor akhirnya melakukan perubahan terhadap filesystem/kernel.

Untuk rewrite ini saya akan pegang aturan keras:

> **Executor tidak pernah menentukan apa yang aman untuk dihapus. Executor hanya mengeksekusi `AuthorizedPlan`, lalu melakukan revalidation terakhir sebelum setiap operasi destruktif.**

---

# 1. Posisi Executor

Arsitekturnya sekarang:

```text
Scanner
   ↓
Candidate
   ↓
Safety
   ↓
Policy
   ↓
Planner
   ↓
CleanupPlan
   ↓
Authorization
   ↓
AuthorizedPlan
   ↓
┌─────────────────────┐
│      EXECUTOR       │
│                     │
│ revalidate          │
│ dispatch            │
│ execute             │
│ observe result      │
│ verify              │
└─────────┬───────────┘
          ↓
ExecutionReport
```

Executor tidak boleh mempunyai logic seperti:

```rust
if file_age > 7_days {
    delete();
}
```

Itu policy.

Atau:

```rust
if path.starts_with("/data/...") {
    delete();
}
```

Itu safety.

Executor hanya:

```text
operation
    ↓
revalidate
    ↓
execute
    ↓
result
```

# 3. `ExecutionContext`

Executor membutuhkan environment, tetapi jangan membuat global state.

```rust
pub struct ExecutionContext {
    pub cancellation: CancellationToken,
    pub runtime: RuntimeSnapshot,
    pub limits: ExecutionLimits,
    pub dry_run: bool,
}
```

Misalnya:

```rust
pub struct ExecutionLimits {
    pub max_bytes: u64,
    pub max_operations: u32,
    pub max_duration: Duration,
}
```

Context ini berbeda dengan `PolicyContext`.

### PolicyContext

Menjawab:

> Apakah operation ini boleh dilakukan?

### ExecutionContext

Menjawab:

> Apakah execution masih boleh dilanjutkan sekarang?

Contohnya:

```text
Policy:
    screen was OFF
    thermal normal

Execution:
    screen sekarang ON
```

Executor/Scheduler harus menghentikan pekerjaan.

```rust
pub trait Executor {
```


Tetapi saya lebih suka **operation-level error tidak langsung menggagalkan seluruh plan**.

Karena partial success normal.

# 5. Dispatcher

Executor utama hanya melakukan dispatch:

```rust
fn execute_operation(
    &self,
    operation: &PlannedOperation,
    context: &ExecutionContext,
) -> OperationResult {
    match &operation.operation {
        Operation::RemoveFile(op) => {
            self.fs.remove_file(op, context)
        }

        Operation::RemoveEmptyDirectory(op) => {
            self.fs.remove_empty_directory(op, context)
        }

        Operation::TrimFilesystem(op) => {
            self.kernel.trim(op, context)
        }

        Operation::F2fsMaintenance(op) => {
            self.kernel.f2fs(op, context)
        }

        Operation::ZramMaintenance(op) => {
            self.kernel.zram(op, context)
        }

        Operation::FrameworkMaintenance(op) => {
            self.framework.execute(op, context)
        }
    }
}
```

Perhatikan bahwa dispatcher **tidak melakukan safety check sendiri**.

Safety check harus berada di abstraction yang tepat dan terutama revalidation filesystem dilakukan oleh filesystem executor.

# 6. Jangan gunakan `PathBuf` sebagai primitive deletion

Ini keputusan desain penting.

Untuk privileged cleanup engine.

Lebih baik:

```rust

pub struct AuthorizedFile {
```

Dengan demikian executor tidak diberi:

```text

```

dan disuruh percaya begitu saja.

Ini object yang sangat penting dari desain filesystem sebelumnya.

```text

reporting
```

Sedangkan operasi filesystem menggunakan:

```text

```

bukan string path.

# 8. Kenapa FD-relative?

Bayangkan:

```text
/data/app/cache/
```

pada saat scan menunjuk ke objek A.

Kemudian sebelum delete terjadi:

```text
cache/
    ↓
diganti
    ↓
symlink / mount / object lain
```

Kalau executor melakukan:

```rust
remove_file("/data/app/cache/foo");
```

ia kembali melakukan name resolution dari root filesystem.

Dengan FD-relative operations:

```text
trusted root FD
       ↓
openat / fstatat / unlinkat
       ↓
relative target
```

scope-nya jauh lebih terkendali.

# 9. RelativePath

Jangan menerima arbitrary `PathBuf` dari layer atas.

Buat type:

```rust
pub struct RelativePath {
    components: Vec<OsString>,

```

Constructor:

```rust
impl RelativePath {
    pub fn parse(path: &Path) -> Result<Self, PathError> {
        ...
    }

```

Reject:

```text
/
absolute path

..
parent traversal

.
ambiguous component
```

Dan hati-hati dengan platform-specific behavior.

Untuk Android/Linux, `OsStr` lebih tepat daripada mengubah semuanya menjadi UTF-8.

# 10. Jangan `canonicalize()` lalu delete

Pattern yang harus dilarang:

```rust
let real = std::fs::canonicalize(path)?;
std::fs::remove_file(real)?;
```

Ini kelihatan aman tetapi memiliki problem TOCTOU:

```text
canonicalize
    ↓
time passes
    ↓
target changes
    ↓
delete different object
```

`canonicalize()` juga menyelesaikan symlink, sedangkan desain kita justru:

> symlink = reject.

Jadi kita tidak membutuhkan canonical path untuk destructive operation.

# 11. Safe file removal

Konsep operasi:

```text
TrustedRoot
    ↓
relative path
    ↓
lookup parent
    ↓
lookup final component with NOFOLLOW
    ↓
fstat
    ↓
verify identity/type/device
    ↓
unlinkat
```

Pseudo-code:

```rust
fn remove_file(
    root: &TrustedRoot,
    target: &AuthorizedFile,
) -> OperationResult {
    let parent = open_parent_directory(root, target.path())?;

    let metadata = fstatat_nofollow(
        parent.fd(),
        target.file_name(),
    )?;

    verify_identity(
        metadata,
        target.identity(),
    )?;

    verify_regular_file(metadata)?;

    verify_same_device(
        metadata,
        root.identity().dev,
    )?;

    unlinkat_file(
        parent.fd(),
        target.file_name(),
    )
}
```

Perhatikan:

**tidak ada `remove_file(path)` dari stdlib.**

# 12. Symlink = hard deny

Kalau:

```text
foo → symlink
```

hasilnya:

```text
Reject(Symlink)
```

Bukan:

```text
follow symlink
```

Bukan:

```text
delete destination
```

Kalau symlink itu sendiri ternyata candidate, keputusan tetap harus eksplisit.

Untuk cache cleaner privileged, pendekatan paling konservatif:

```text
Symlink:
    do not traverse
    do not delete automatically
    report as skipped/rejected
```

Ini menghilangkan kelas masalah besar.

---

# 13. Parent directory juga harus diperiksa

Misalnya:

```text
root/
└── a/
    └── b/
        └── file
```

Tidak cukup hanya:

```text
file → regular
```

Kita juga perlu memastikan traversal:

```text
root → a → b
```

tidak melewati symlink.

Karena:

```text
a → symlink
```

bisa menyebabkan traversal keluar dari trusted boundary.

Jadi walker harus membuka directory satu level demi satu level secara relatif.

---

# 14. `openat` style traversal

Konsepnya:

```text
TrustedRoot FD
      │
      ├── openat("a", directory, NOFOLLOW)
      │         ↓
      │      Directory FD
      │         │
      │         └── openat("b", directory, NOFOLLOW)
      │                    ↓
      │                 Directory FD
      │                    │
      │                    └── fstatat("file", NOFOLLOW)
```

Dengan demikian path resolution tetap berada dalam kontrol kita.

Ini jauh lebih cocok untuk privileged daemon daripada sekadar:

```rust
PathBuf::join(...)
```

# 15. Device boundary

Misalnya root berada di:

```text
st_dev = 123
```

lalu sebuah directory ternyata:

```text
st_dev = 456
```

Itu harus ditolak:

```rust
if entry.dev != root.dev {
    return Err(FsError::CrossDevice);
}
```

Mengapa?

Karena mount boundary dapat membuat:

```text
trusted cache directory
```

secara nama terlihat seperti subtree biasa, padahal sebenarnya mengandung filesystem lain.

Untuk cleaner, prinsipnya:

> **Tidak pernah crossing filesystem boundary secara implicit.**

# 17. Directory removal

Directory hanya boleh dihapus jika:

```text

2. same device
3. bukan symlink
4. masih berada di trusted root
5. identity sesuai
6. sudah kosong
```



Semantics-nya jauh lebih jelas.

# 19. Recursive deletion

Kita bisa membuat internal function:

```rust
fn purge_directory(
    dir: &DirectoryHandle,
    context: &ExecutionContext,
) -> Result<PurgeResult>
```

Flow:

```text
open directory
    ↓
enumerate entries
    ↓
for each entry
    │
    ├── cancellation check
    │
    ├── fstat NOFOLLOW
    │
    ├── same-device check
    │
    ├── regular file?
    │       ↓
    │     unlink
    │
    ├── directory?
    │       ↓
    │     recurse
    │       ↓
    │     remove empty directory
    │
    └── anything else?
            ↓
          skip
```

Tetapi fungsi ini **bukan generic `rm -rf`**.

Ia hanya dipanggil untuk target yang sudah mempunyai authorization yang tepat.

# 20. Cancellation harus masuk recursion

Jangan:

```rust
purge_directory(dir)
```

dan baru setelah selesai mengecek cancellation.

Harus:

```rust
for entry in entries {
    cancellation.check()?;

    process(entry)?;
}
```

Sehingga:

```text
screen ON
    ↓
cancel
    ↓
recursive deletion berhenti
```

dalam waktu yang relatif cepat.

# 21. Handling race condition

Misalnya:

```text
T0:
scanner menemukan foo

T1:
application menghapus foo

T2:
executor mencoba delete foo
```

hasil:

```text
ENOENT
```

→

```text
AlreadyGone
```

Tetapi:

```text
T0:
foo = regular file

T1:
foo diganti symlink

T2:
executor lookup
```

hasil:

```text
Symlink
```

→

```text
Rejected/Skipped
```

Bukan delete.

---

# 22. Race condition bukan selalu bisa "dimenangkan"

Kita tidak boleh mengklaim:

> “Race condition sudah mustahil.”

Yang realistis:

> **Setiap destructive operation melakukan lookup dan validation sedekat mungkin dengan mutation, menggunakan FD-relative operations dan `NOFOLLOW`.**

Ini memperkecil race window secara signifikan dan membuat failure mode menjadi fail-closed.

# 23. Error model Executor

Jangan:

```rust
Box<dyn Error>
```

di seluruh executor.

```rust
    IdentityChanged,
```

Kemudian mapper:

```text

    → AlreadyGone

    → PermissionDenied
```

Dengan begitu Scheduler bisa membuat keputusan berdasarkan **makna**, bukan errno mentah.

# 26. Execution harus berhenti jika global safety berubah

Misalnya saat cleanup berjalan:

```text
screen OFF
    ↓
cleanup
    ↓
user touches device
    ↓
screen ON
```

```rust

```

```text

    ↓

    ↓

```

Jangan:

```text

```

Karena tujuan utama daemon adalah **background optimization**, bukan memaksakan cleanup.

# 29. ZRAM Executor

ZRAM bahkan harus lebih ketat.

Jangan menganggap:

```text
zram enabled
```

berarti:

```text
boleh reset
```

Reset ZRAM mempunyai semantics yang berbeda dari cleanup cache biasa.

Jadi:

```text
ZramMaintenance
```

harus memiliki policy terpisah.

Untuk mode normal, bahkan sangat masuk akal jika:

```text
ZRAM operation = disabled
```

dan hanya diaktifkan pada explicit/deep/emergency policy.

Prinsipnya:

> **Deep cleanup memperluas operation set, bukan melemahkan safety.**

# 35. Invariant paling penting Executor

Saya akan dokumentasikan invariant ini langsung di codebase:

```text
INVARIANT 1
Executor never discovers new cleanup targets.

INVARIANT 2
Executor never expands a target scope.

INVARIANT 3
Executor never follows symlinks.

INVARIANT 4
Executor never crosses filesystem boundaries.

INVARIANT 5
Executor revalidates destructive targets.

INVARIANT 6
Executor honors cancellation.

INVARIANT 7
Executor treats missing targets as idempotent.

INVARIANT 8
Executor does not convert policy rejection into execution.

INVARIANT 9
Executor cannot execute an unauthorised plan.

INVARIANT 10
Unknown filesystem objects are fail-closed.
```

Ini bukan sekadar dokumentasi. Ini harus tercermin dalam type/API design.

# 36. Final Executor architecture

Jadinya:

```text
                 AuthorizedPlan
                       │
                       ▼
              ┌─────────────────┐
              │    Executor     │
              └────────┬────────┘
                       │
              dependency ordering
                       │
                       ▼
                operation dispatch
                       │
        ┌──────────────┼───────────────┐
        ▼              ▼               ▼
   Filesystem        Kernel        Framework
        │              │               │
        ▼              ▼               ▼
   revalidate      revalidate       validate
        │              │               │
        ▼              ▼               ▼
    execute          execute         execute
        │              │               │
        └──────────────┼───────────────┘
                       ▼
                    Verify
                       │
                       ▼
                OperationResult
                       │
                       ▼
                ExecutionReport
```

Dengan model ini, core cleanup engine sudah punya boundary yang cukup kuat:

```text
Scanner     = menemukan
Safety      = melindungi
Policy      = memutuskan
Planner     = merencanakan
Authorization = mengizinkan
Executor    = melakukan
Verifier    = membuktikan hasil
```

Itu pemisahan yang saya rekomendasikan untuk rewrite `cache_cleaner`, sambil tetap mempertahankan karakter penting repo saat ini seperti FD-relative filesystem handling, event-driven daemon, cancellation, F2FS, cgroup/governor, IPC, multi-user/FBE, dan dry-run/explain.

**Tahap berikutnya yang paling tepat adalah Scheduler + Daemon State Machine**, karena sekarang kita sudah punya seluruh mesin cleanup. Di sana kita desain bagaimana daemon menentukan **kapan scan dimulai, kapan harus tidur, bagaimana epoll/timerfd/uevent masuk, bagaimana screen-on langsung membatalkan job, thermal/battery/storage menjadi condition, reload config, signal handling, retry, dan bagaimana state `Idle → Preparing → Scanning → Planning → Cleaning → Paused → Idle` benar-benar diimplementasikan tanpa race.**
