# 92.md — Observability, Diagnostics, Audit, dan Operational Telemetry

## Tujuan

Daemon production-grade harus dapat menjawab bukan hanya "berhasil atau gagal", tetapi mengapa keputusan dibuat, apa yang terjadi, dan bagaimana recovery dapat diverifikasi.

Observability tidak boleh menjadi sumber correctness. Ia adalah evidence tambahan untuk operator dan diagnosis.

## 1. Tiga Pilar

```text
Logs
Metrics
Traces / structured events
```

Untuk daemon kecil, full distributed tracing belum tentu diperlukan, tetapi correlation identity dan structured lifecycle events tetap penting.

## 2. Correlation Identity

Setiap meaningful action dapat dikaitkan dengan:

```text
RequestId
JobId
AttemptId
OperationId
EventId
WorkerId
RecoveryEpoch
```

Ini memungkinkan satu failure ditelusuri dari IPC sampai filesystem mutation.

## 3. Structured Logging

Gunakan structured fields, bukan hanya free-form string.

Contoh conceptual event:

```text
operation=delete
job_id=...
operation_id=...
phase=verification
result=verified
```

## 4. Log Levels

Minimal:

- error
- warn
- info
- debug
- trace

Production default tidak boleh terlalu verbose sampai menghasilkan I/O terus-menerus ketika daemon idle.

## 5. Security Redaction

Log tidak boleh memuat:

- credential
- token
- secret
- sensitive IPC payload

Path/name juga perlu dipertimbangkan jika deployment membutuhkan privacy.

## 6. Lifecycle Events

Useful events:

```text
job accepted
job deduplicated
plan created
operation claimed
mutation started
mutation result
verification result
recovery started
recovery classification
job finalized
```

## 7. Unknown Must Be Visible

`Unknown` harus mempunyai telemetry yang jelas.

Operator harus dapat membedakan:

```text
Failed
Skipped
Cancelled
Unknown
RecoveryRequired
```

## 8. Decision Explainability

Policy/safety decision sebaiknya menyimpan reason code.

Contoh:

```text
Decision = Skip
Reason = TargetNotTrusted
```

Jangan hanya log "skipped".

## 9. Metrics

Minimal metrics:

- jobs accepted/completed/failed
- operations attempted
- operations verified
- operations unknown
- bytes logically removed
- candidates scanned
- candidates skipped
- recovery count
- retry count
- queue depth
- active workers
- resource contention

## 10. Power Metrics

Untuk daemon Android, metrics penting:

- wakeup count
- evaluation count
- CPU active work duration
- idle duration
- suspend/resume count
- wakelock duration if applicable
- cleanup work during screen-off

Jangan menjadikan CPU percentage sebagai satu-satunya power metric.

## 11. Histogram

Useful latency histograms:

- scan duration
- planning duration
- mutation duration
- verification duration
- Job latency
- resource wait
- IPC response
- scheduler wake-to-decision

## 12. Cardinality Control

Jangan menjadikan path lengkap, arbitrary filename, atau request payload sebagai unbounded metric label.

Gunakan bounded categories dan IDs.

## 13. Audit vs Debug Log

Audit adalah durable/security-relevant history.

Debug log adalah operational diagnostic stream.

Keduanya tidak boleh dicampur.

## 14. Durable Audit

Action destructive dapat memiliki audit record:

```text
actor
operation
scope
identity
authorization reference
result
timestamp
```

Audit tidak perlu menyimpan seluruh candidate list.

## 15. Audit Immutability

Audit history tidak boleh diubah hanya untuk merapikan output setelah recovery.

Correction dilakukan dengan event baru.

## 16. Event Schema

Structured event harus versioned jika dikonsumsi tooling eksternal.

Contoh:

```text
schema_version
kind
timestamp
correlation ids
payload
```

## 17. Time Semantics

Telemetry perlu membedakan:

- monotonic duration
- wall-clock timestamp
- boot-relative timestamp bila relevan

Wall clock dapat berubah.

Latency tidak boleh dihitung dari wall clock yang dapat mundur.

## 18. Clock Jumps

Jika wall clock berubah, event ordering berdasarkan timestamp saja dapat salah.

Gunakan sequence/generation/monotonic ordering untuk internal lifecycle.

## 19. Health State

Daemon health sebaiknya structured:

```text
Healthy
Degraded
Recovering
Blocked
Fatal
```

Health tidak boleh hanya berdasarkan process alive.

## 20. Degraded Reasons

Contoh:

- durable store unavailable
- platform capability unavailable
- target catalog stale
- authorization unavailable
- recovery pending
- resource pressure

## 21. Diagnostic Snapshot

Sediakan snapshot yang aman untuk diagnosis:

- daemon state
- active Job
- queue counts
- worker counts
- resource usage
- config generation
- catalog generation
- last recovery
- last error categories

Jangan dump secret atau raw unrestricted filesystem state.

## 22. Status API

IPC status endpoint sebaiknya read-only dan murah.

Ia tidak boleh memaksa daemon melakukan full filesystem scan hanya untuk menjawab health.

## 23. Explain API

Jika CLI/UI membutuhkan alasan kenapa target tidak dibersihkan, gunakan stored decision/result metadata daripada mengulang destructive logic.

## 24. Error Taxonomy

Error harus structured dan machine-readable.

Contoh kategori:

```text
InvalidInput
Unauthorized
Unsafe
Unavailable
Conflict
Timeout
ResourceExhausted
PersistenceFailure
PlatformFailure
UnknownOutcome
```

## 25. Error Context

Error context harus menyimpan correlation identity dan phase.

Contoh:

```text
operation_id
phase=verification
error=TargetReplaced
```

## 26. Metrics Must Not Change Correctness

Jika metrics backend mati:

```text
cleanup correctness tetap berjalan
```

Jika audit yang diwajibkan untuk security-critical action gagal, policy dapat memilih fail-closed. Ini harus explicit contract, bukan accidental dependency.

## 27. Log Backpressure

Logging sendiri dapat menjadi overload source.

Gunakan bounded buffering dan rate limiting untuk repetitive errors.

Critical security/failure events tidak boleh diam-diam hilang tanpa policy.

## 28. Error Storm Suppression

Satu filesystem error berulang pada ribuan candidate tidak perlu menghasilkan ribuan full stack trace.

Aggregate berdasarkan bounded error category/context.

## 29. Crash Diagnostics

Jika process crash, startup diagnostics dapat membaca durable recovery state.

Jangan bergantung pada last log line untuk menentukan operation outcome.

## 30. Startup Report

Startup dapat menghasilkan satu summary:

```text
previous operations recovered = N
unknown operations = M
stale leases = K
config generation = G
catalog generation = C
```

## 31. Shutdown Report

Shutdown dapat mencatat:

- reason
- active operations
- unresolved operations
- resource release status
- duration

## 32. Idle Diagnostics

Power-neutral daemon sebaiknya mempunyai cara membuktikan idle:

```text
last wake reason
last evaluation
next deadline
blocked duration
```

Ini lebih berguna daripada hanya melihat CPU percentage.

## 33. Wake Reason

Every scheduler wakeup sebaiknya mempunyai reason category:

```text
IPC
Timer
PowerEvent
StorageEvent
MountEvent
Recovery
Shutdown
Unknown
```

Jika wake reason unknown sering muncul, dependency/runtime perlu diaudit.

## 34. Wakeup Budget

Gunakan telemetry untuk mengetahui apakah daemon terlalu sering bangun.

Target:

```text
no work
→ minimal wakeups
```

## 35. Resource Diagnostics

Expose bounded information:

- FD usage
- memory estimate
- active permits
- queue depth
- lock contention counters

Jangan expose raw internal pointer/handle values sebagai API contract.

## 36. Performance Attribution

Job duration sebaiknya dapat dipecah:

```text
queue wait
resource wait
scan
plan
execute
verify
persist
publish
```

Ini membantu membedakan CPU problem dari I/O/resource problem.

## 37. Slow Operation Thresholds

Configurable diagnostic threshold dapat memberi warning untuk operation yang terlalu lama.

Threshold tidak boleh menjadi functional timeout kecuali memang dipakai oleh policy.

## 38. Privacy

Diagnostic output harus mempertimbangkan bahwa filename/path dapat mengandung data personal.

CLI dapat menyediakan redacted/full diagnostic modes sesuai authority.

## 39. Export

Jika diagnostics diekspor, format machine-readable seperti JSON dapat berguna.

Export harus bounded dan tidak melakukan full rescan secara default.

## 40. Definition of Done

Observability production-ready jika:

- correlation IDs tersedia
- structured events
- reason codes
- machine-readable errors
- metrics bounded
- audit terpisah dari logs
- Unknown terlihat jelas
- power/wakeup telemetry tersedia
- health state structured
- diagnostic snapshot murah
- logging punya backpressure
- error storm dikontrol
- crash diagnosis berbasis durable state
- privacy/redaction diperhatikan

## Final Invariants

1. Observability bukan source of correctness.
2. Setiap lifecycle operation dapat dikorelasikan.
3. Unknown harus terlihat berbeda dari Failed.
4. Decision harus mempunyai reason code.
5. Metric cardinality harus bounded.
6. Audit berbeda dari debug log.
7. Audit tidak boleh di-rewrite.
8. Duration memakai monotonic semantics.
9. Wall clock bukan satu-satunya ordering source.
10. Health tidak sama dengan process alive.
11. Diagnostic endpoint harus murah.
12. Metrics failure tidak boleh merusak cleanup kecuali contract security mengharuskannya.
13. Logging harus bounded.
14. Error storm harus dikontrol.
15. Crash recovery evidence berasal dari durable state.
16. Idle state harus dapat dibuktikan melalui wake/scheduler telemetry.
17. Wake reason harus observable.
18. Power telemetry tidak bergantung pada CPU percentage saja.
19. Diagnostic output tidak boleh membocorkan secret.
20. Observability harus membantu recovery tanpa menjadi dependency correctness.
