Lanjut. Sekarang kita masuk ke **`fs/`**, fondasi security paling kritis. Kalau layer ini benar, `Scanner` dan `Executor` di atasnya bisa dibuat jauh lebih sederhana.

Saya akan mengunci desainnya dengan prinsip:

> **Filesystem object authority berasal dari FD + identity, bukan dari string path.**

# 208. TOCTOU harus dijelaskan dengan jujur

Ada satu limitation Linux yang penting.

Flow:

```text
fstatat(parent, "x")
        ↓
identity correct
        ↓
unlinkat(parent, "x")
```

masih memiliki race pada final directory entry:

```text
T1 stat x
T2 attacker replaces x
T3 unlink x
```

Tidak ada generic Linux primitive:

```text
unlink this exact already-open inode FD
```

yang bisa kita gunakan untuk membuat final unlink sepenuhnya atomic berdasarkan inode identity.

Jadi jangan pernah mengklaim:

> "TOCTOU impossible."

Yang kita bangun adalah **defense-in-depth**:

```text
trusted root FD
+
component traversal via FD
+
NOFOLLOW
+
same-device
+
identity validation
+
type validation
+
immediate unlink
+
no scope expansion
```

---

# 209. Mengapa masih cukup kuat?

Karena jika final name diganti dengan symlink:

```text
x → /system/important
```

`unlinkat()` hanya menghapus:

```text
x (symlink)
```

bukan:

```text
/system/important
```

Kita tidak mengikuti symlink.

---

# 210. Hard-link race

Lebih menarik lagi:

```text
x → hard link ke inode di luar root
```

Hard link tidak membawa path traversal.

Jika cleaner melakukan:

```text
unlinkat(parent, "x")
```

yang hilang adalah **directory entry `x`**, bukan seluruh inode di luar root.

Ini sangat berbeda dari:

```text
rm -rf
```

yang bisa mengikuti directory hierarchy.

Tetap saja, target root dan permission model harus ketat.

# 211. App cache dan attacker-controlled contents

Ini nuance penting untuk Android.

App dapat menulis ke cache miliknya sendiri.

Jadi cleaner tidak boleh berasumsi:

> semua nama yang ditemukan di app cache adalah immutable.

Sebaliknya security model harus menjamin:

```text
cleaner hanya dapat menghapus directory entry

```

dan tidak pernah:

```text

interpret arbitrary path
```

Dengan begitu app tidak bisa mengubah cache entry menjadi:

```text

```

lalu membuat cleaner mengikuti target tersebut.

# 227. Tahap berikutnya: Scanner

Sekarang kita sudah punya tiga fondasi:

```text
domain
   ↓
fs
   ↓
```

Berikutnya kita bisa implement **Scanner lengkap**:

```text
Target Catalog
      ↓
ScanRequest
      ↓
TrustedRoot
      ↓
Walker
      ↓
DirectoryIterator
      ↓
Metadata
      ↓
Candidate
      ↓
ScanResult
```

Termasuk **algoritma traversal iterative**, `max_depth`, `max_entries`, `max_duration`, cancellation, error policy (`SkipEntry` vs `AbortTarget`), deteksi filesystem boundary, handling symlink, serta cara scanner memastikan **root directory tidak pernah masuk candidate untuk deletion**. Setelah Scanner selesai, baru kita bisa menghubungkan **Safety Validator** secara nyata ke hasil scan.
