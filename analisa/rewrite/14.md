Lanjut. Sekarang kita masuk ke **Kernel + Resource Governor + F2FS + TRIM + ZRAM**.

Bagian ini sebaiknya dianggap sebagai **maintenance subsystem**, bukan bagian dari filesystem cleaner biasa.

Prinsipnya:

> **Cleaner boleh meminta kernel melakukan maintenance, tetapi tidak boleh menganggap kernel maintenance sebagai hak untuk memaksa sistem.**

Linux cgroup memang menyediakan mekanisme pengendalian CPU/IO dan statistik pressure, tetapi availability dan semantics-nya tetap bergantung pada kernel/device. ([Linux Kernel Archives][1])

---

# 1. Pisahkan tiga jenis pekerjaan

Jangan semua disebut `cleanup`.

```text
Filesystem cleanup
    ↓
hapus cache/temp files

Filesystem maintenance
    ↓
TRIM
F2FS GC

Memory/storage maintenance
    ↓
ZRAM-related operations
```

Jadi:

```rust
pub enum MaintenanceOperation {
    Trim(TrimRequest),
    F2fs(F2fsRequest),
    Zram(ZramRequest),
}
```

Sedangkan:

```rust
pub enum Operation {
    RemoveFile(...),
    RemoveEmptyDirectory(...),
    Maintenance(MaintenanceOperation),
}
```

---

# 2. Kenapa harus terpisah?

Karena risk profile berbeda.

Misalnya:

```text
RemoveFile
    impact → local file

TRIM
    impact → block device

F2FS GC
    impact → filesystem behavior

ZRAM
    impact → memory/compression subsystem
```

Kalau semuanya masuk:

```rust
Operation::Cleanup(...)
```

akan terlalu mudah membuat `Deep` berarti:

```text
"lakukan semua hal"
```

Saya justru ingin:

```text
Deep cleanup
    ≠
kernel maintenance
```

# 5. CPU scheduling

Untuk cleaner background, kita ingin priority rendah.

Konsep:

```text
normal app
    ↑
system workload
    ↑
foreground
    ↑
----------------
cleaner
```

`SCHED_IDLE` memang dimaksudkan untuk pekerjaan yang hanya mendapat CPU ketika workload lain tidak membutuhkannya. cgroup v2 juga mempunyai `cpu.idle` yang memberikan semantics serupa pada level cgroup. ([Linux Kernel Archives][1])

Tetapi jangan menganggap:

```text
SCHED_IDLE = selalu aman
```

karena cleaner tetap bisa:

```text
menghasilkan IO
membuka banyak inode
menghasilkan F2FS GC
```

CPU priority hanya satu dimension.

---

# 6. Jangan hard-code satu metode CPU priority

Buat:

```rust
pub enum CpuControl {
    SchedIdle,
    Nice(i32),
    Cgroup(CpuCgroupPolicy),
    None,
}
```

Detector:

```rust
pub struct CpuCapabilities {
    pub sched_idle: bool,
    pub cgroup_cpu: bool,
}
```

Kemudian:

```text
preferred:
    cgroup / SCHED_IDLE

fallback:
    nice

fallback:
    normal
```

Tetapi fallback tidak boleh mengubah correctness.

# 7. I/O priority

Linux menyediakan `IOPRIO_CLASS_IDLE`, yaitu kelas I/O terendah; workload di kelas ini hanya memperoleh waktu I/O ketika workload dengan prioritas lebih tinggi tidak membutuhkan device. ([Kernel][2])

Maka default cleaner:

```text
IOPRIO_CLASS_IDLE
```

jika tersedia dan cocok dengan device/kernel.

Model:

```rust
pub enum IoPriority {
    Idle,
    BestEffort(u8),
    None,
}
```

Saya tidak akan menggunakan:

```text
Realtime
```

untuk cleaner.

Sama sekali tidak perlu.

# 8. Cgroup

Cgroup jangan dianggap selalu tersedia.

Detector:

```rust
pub struct CgroupCapabilities {
    pub mounted: bool,
    pub version: CgroupVersion,
    pub cpu: bool,
```

Kemudian:

```text

    ↓

```

Linux cgroup v2 menyediakan CPU, IO, memory, dan pressure interfaces, tetapi controller yang tersedia bergantung pada konfigurasi hierarchy/kernel. ([Linux Kernel Archives][1])

```text

```

lebih baik.

# 11. Cgroup lifecycle

Ideal:

```text
daemon start
    ↓
discover capabilities

job start
    ↓
create/enter cleaner scope
    ↓
apply CPU/IO policy
    ↓

    ↓

```

Jika daemon crash:

```text

    ↓

```

Scoped resources harus tidak meninggalkan state berbahaya.

# 12. IO throttling

Ini sangat menarik.

cgroup v2 menyediakan:

```text
io.max
    rbps
    wbps
    riops
    wiops
```

untuk membatasi bandwidth atau IOPS. ([Linux Kernel Archives][1])

Jadi kita bisa punya:

```rust
pub struct IoBudget {
    pub max_read_bps: Option<u64>,
    pub max_write_bps: Option<u64>,
    pub max_read_iops: Option<u64>,
    pub max_write_iops: Option<u64>,
}
```

Tetapi saya tidak akan mengaktifkannya default.

# 13. Kenapa tidak default?

Karena device Android sangat bervariasi.

Misalnya:

```text
UFS fast
    → 2 MB/s terlalu rendah

eMMC slow
    → 2 MB/s mungkin masuk akal

weird vendor storage
    → throttling semantics berbeda
```

Lebih baik adaptive governor:

```text
low pressure
    → normal background priority

moderate pressure
    → throttle

high pressure
    → pause/cancel
```

# 14. PSI


# 26. RAII untuk F2FS state

Kalau operation mengubah state sementara:

```text

    ↓

    ↓
perform operation
    ↓
restore state
```

```rust
    ...
}

impl Drop for F2fsGuard {
    fn drop(&mut self) {
        // restore state
    }
}
```

Ini salah satu tempat `Drop` benar-benar berguna.

# 47. Invariant Kernel/Resource

Ini saya jadikan kontrak rewrite:

```text
1. Cleaner never raises its CPU priority above normal workload.

2. Cleaner never uses realtime I/O priority.

3. Resource throttling is best-effort, not correctness-critical.

4. Missing cgroup support does not break filesystem safety.

5. Missing PSI does not break cleanup correctness.

6. Thermal critical cancels/defer cleanup.

7. Unknown thermal state is conservative.

8. F2FS operations require verified F2FS filesystem.

9. TRIM is a separate typed operation.

10. ZRAM maintenance is opt-in and separately authorized.

11. No arbitrary sysfs writes.

12. No arbitrary block-device operations.

13. Temporary kernel state is restored through RAII.

14. Cleaner only restores state it owns.

15. Kernel maintenance failure does not automatically invalidate successful file cleanup.

16. Maintenance never expands filesystem-cleanup scope.
```

## Posisi arsitektur kita sekarang

Kita sudah menyelesaikan hampir semua **core architecture**:

```text
             ┌───────────────┐
             │ CLI / IPC     │
             └───────┬───────┘
                     ↓
              Authorization
                     ↓
                 Scheduler
                     ↓
              ResourceGovernor
                     ↓
               JobController
                     ↓
             Android Platform
                     ↓
              Target Catalog
                     ↓
                  Scanner
                     ↓
                   Safety
                     ↓
                   Policy
                     ↓
                  Planner
                     ↓
              AuthorizedPlan
                     ↓
                 Executor
                  /       \
                 /         \
        Filesystem       Maintenance
                           │
                    ┌──────┼──────┐
                    ↓      ↓      ↓
                   TRIM   F2FS   ZRAM
```

**Tahap berikutnya yang paling penting adalah `Scanner + Walker`**, karena di sanalah kita menerjemahkan seluruh prinsip safety tadi menjadi traversal filesystem Rust yang benar-benar aman: `openat`, `fstatat(AT_SYMLINK_NOFOLLOW)`, `O_DIRECTORY`, `O_NOFOLLOW`, `unlinkat`, FD-relative traversal, cycle/race handling, `st_dev` boundary, cancellation, depth/entry budget, dan bagaimana menangani directory yang berubah ketika sedang discan.

Itu juga akan menjadi salah satu bagian paling krusial dari rewrite karena **Scanner bukan sekadar `read_dir()`**—ia harus menjadi fondasi bagi seluruh guarantee keamanan yang sudah kita desain.
