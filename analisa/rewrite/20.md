Lanjut ke **`scanner/`**. Di sini kita mengubah filesystem yang sudah tervalidasi menjadi kumpulan `Candidate`—tetapi **Scanner tetap tidak boleh memutuskan apakah sesuatu boleh dihapus**.

Prinsipnya:

> **Scanner menemukan fakta. Safety memvalidasi fakta. Policy menentukan kelayakan. Planner menentukan operasi.**

# 229. Kontrak utama Scanner

Saya akan buat sesederhana mungkin:

```rust id="c8m4q2"
pub struct Scanner {
    walker: Walker,
}

impl Scanner {
    pub fn scan(
        &self,
        target: &TargetRoot,
        root: &TrustedRoot,
        request: &ScanRequest,
    ) -> Result<ScanResult, ScanError>;
}
```

Tetapi ada satu nuance: `TargetRoot` berada di domain, sedangkan `TrustedRoot` berasal dari `fs`.

Scanner menerima keduanya karena:

```text id="2qj0h7"

→ semantic identity

TrustedRoot
→ actual opened filesystem object
```

Keduanya harus konsisten.

# 234. Jangan menganggap partial scan = full scan

Ini security/policy nuance.

Misalnya ada:


```text id="j4q9ws"

```

Tidak boleh report:

> "Ada 500 file yang aman dibersihkan."

Lebih tepat:

> "Ditemukan 500 candidate dalam partial scan; hasil tidak merepresentasikan keseluruhan target."

# 237. Walker

Walker adalah mesin traversal.

```rust id="q7b5m2"
pub struct Walker {
    max_depth: usize,
}
```

Tetapi saya tidak mau recursive Rust function seperti:

```rust
fn walk(dir) {
    for child in dir {
        walk(child);
    }
}
```

untuk daemon privileged.

---

# 238. Gunakan explicit stack

```rust id="w3x8p6"
struct WalkFrame {
    directory: DirectoryHandle,
    relative_path: RelativePath,
}
```

Stack:

```text id="n1q5s7"
Vec<WalkFrame>
```

Algorithm:

```text id="v7k2m9"
push(root)

while stack not empty:
    frame = pop()

    enumerate(frame.directory)

    for entry:
        stat entry

        if directory:
            push child

        if regular file:
            emit candidate

        if symlink:
            record/skip

        else:
            skip
```

---

# 239. Mengapa iterative?

Tiga alasan:

1. depth tidak menghabiskan Rust call stack,
2. `max_depth` mudah ditegakkan,
3. cancellation/budget check berada pada loop utama.

# 240. Root tidak pernah candidate

Tidak pernah:


Dengan begitu Executor tidak pernah menerima operation:


# 241. Child directory

Misalnya:

```text id="r3q8y1"
cache/
  old/
    file
```

Scanner:

```text id="1j9m4s"
cache → root
old  → child directory
file → candidate
```

`old` dapat menjadi candidate **hanya jika** policy/planner memang mengizinkan `RemoveEmptyDirectory`.

Scanner sendiri tidak menentukan itu.

# 242. Symlink

Misalnya:

```text id="z6r2v8"
cache/
  link → /data/system
```

Walker:

```text id="p4m7x1"
fstatat(NO_FOLLOW)
```

mendeteksi:

```text id="e2w9k5"
Symlink
```

Kemudian:


# 243. Broken symlink

Sama.

```text id="m5w7r2"

```

`stat()` biasa mungkin memberikan `ENOENT`.

Tetapi:

```text id="b8q1x4"

```

tetap dapat melihat symlink entry.

Scanner harus:

```text id="c1v6s9"
recognize symlink
skip
```

bukan menganggap:

```text id="a2n8k3"
NotFound → safe to remove
```

# 260. Per-entry failure

# 269. Scanner invariant

Saya akan mengunci checklist:

```text id="r1m6q8"
1. Scanner never deletes.
2. Scanner never follows symlinks.
3. Scanner never uses arbitrary deletion paths.
4. Scanner never crosses device boundaries.
5. Scanner never treats partial scan as complete.
6. Scanner respects max depth.
7. Scanner respects entry budget.
8. Scanner respects metadata budget.
9. Scanner respects time budget.
10. Scanner checks cancellation.
11. Scanner does not scan locked CE targets.
12. Root is never emitted as a candidate.
13. Unknown file types are skipped.
14. Entry errors do not silently become candidates.
15. Candidate identity is captured at scan time.
16. Candidate does not imply authorization.
```

# 271. Satu tambahan penting: deterministic ordering

Filesystem enumeration order tidak boleh diasumsikan deterministic.

Kalau:

```text id="k5p2r8"

```

menghasilkan:

```text id="a,b,c"
```

hari ini dan:

```text id="c,a,b"
```

besok, hasil policy seharusnya tetap equivalent.

Untuk testing/reporting kita bisa sort candidate berdasarkan:

```text id="q7m3x1"

```

Tetapi **jangan sort dengan tujuan security**.

Sorting hanya determinism.

## Setelah ini

Layer berikutnya adalah **`safety/`**, dan ini justru bagian yang paling menentukan security architecture.

Di sana kita akan implement konkret:

```text id="p6w2r9"
Candidate
   ↓
Target identity validation
   ↓
TrustedRoot validation
   ↓
User/FBE validation
   ↓
Filesystem/device validation
   ↓
Entry-type validation
   ↓
Protected-target validation
   ↓
Race/staleness validation
   ↓
SafetyProof
   ↓
SafetyValidated
```

Lalu kita bisa mendesain **`SafetyProof` secara kriptografis/struktural—bukan crypto**, yaitu bagaimana Rust type system memastikan bahwa object yang belum melewati safety validation **secara API tidak mungkin masuk ke Policy atau Planner**.
