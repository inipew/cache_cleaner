Job State Machine dan Scheduler Contract

Setelah runtime dan event loop memiliki kontrak implementasi yang jelas, lapisan berikutnya yang harus dibakukan adalah job state machine dan scheduler.

Scheduler bukan executor.

Scheduler tidak menentukan bagaimana file dihapus.

Scheduler tidak melakukan scanning.

Scheduler tidak melakukan policy evaluation.

Scheduler tidak melakukan filesystem mutation.

Scheduler hanya menentukan kapan sebuah job dapat dibuat, kapan job dapat berjalan, kapan job harus ditunda, kapan job harus dibatalkan, dan bagaimana hasil job memengaruhi scheduling berikutnya.

Job state machine menjadi sumber kebenaran untuk lifecycle sebuah pekerjaan.

Setiap job harus selalu berada dalam satu state yang valid.

Tidak boleh ada job yang secara bersamaan dianggap Running dan Cancelled.

Tidak boleh ada job yang sudah Completed kemudian kembali menjadi Executing.

Tidak boleh ada job yang sudah Stale kemudian menggunakan AuthorizedPlan lama.

Tujuan utama

Scheduler harus menyediakan lifecycle yang deterministic.

Event dari runtime masuk.

Scheduler mengevaluasi keadaan sistem.

Jika job belum dapat dijalankan, job menjadi Deferred.

Jika job dapat dijalankan, job masuk Queue.

Worker hanya menerima job yang sudah memenuhi requirement scheduler.

Ketika worker selesai, hasil dikembalikan kepada scheduler/application layer.

Scheduler kemudian menentukan state akhir dan apakah perlu ada job berikutnya.

Job identity

Setiap job memiliki JobId yang unik.

JobId tidak boleh bergantung hanya kepada timestamp.

JobId harus aman digunakan untuk:

IPC status query

cancellation

logging

telemetry

worker correlation

test

Job juga memiliki creation time dan monotonic creation sequence bila diperlukan.

JobId tidak boleh dapat dikendalikan client untuk memaksa collision.

Jika client mengirim request dengan JobId tertentu, application layer harus menentukan apakah nilai tersebut dapat diterima.

Secara default lebih aman jika server menghasilkan JobId.

Job request

StartCleanup menghasilkan CleanupRequest.

CleanupRequest tidak langsung menjadi executable plan.

Request hanya menyatakan intent.

Contoh informasi:

requested profile

target scope

optional package scope

requested user scope

manual atau scheduled trigger

request origin

request metadata

Request harus melewati validation dan authorization sebelum job dianggap runnable.

Request tidak boleh berisi arbitrary destructive filesystem path sebagai shortcut.

JobContext setidaknya menyimpan:

runtime readiness snapshot

creation time

deadline

budget

JobContext harus immutable pada bagian yang memang merupakan snapshot.

Misalnya ConfigSnapshot yang sudah dipasang ke job tidak boleh diam-diam berubah ketika configuration reload terjadi.

Jika configuration berubah, job baru mendapatkan snapshot baru.

Tidak semua state harus dipertahankan sebagai public API.

Beberapa dapat menjadi internal worker state.

Namun state transition harus tetap eksplisit.

Created

Created berarti request sudah diterima dan job object sudah dibuat.

Belum berarti job boleh dijalankan.

Pada state ini:

request harus sudah tervalidasi secara dasar.

JobId sudah tersedia.

Trigger sudah diketahui.

Initial snapshots dapat mulai dikumpulkan.

Job belum boleh melakukan destructive operation.

Queued

Queued berarti job siap menunggu scheduler dispatch.

Queued tidak berarti worker sedang berjalan.

Job dapat tetap berada di queue jika:

worker sedang sibuk

readiness belum tersedia

concurrency limit tercapai

maintenance budget belum tersedia

scheduler sedang throttled

CheckingReadiness

Sebelum worker dimulai, scheduler atau application layer harus memeriksa readiness.

Readiness minimum dapat mencakup:

daemon Running

storage tersedia

user state sesuai policy

screen state sesuai policy

thermal state sesuai policy

configuration valid

platform capability tersedia

target catalog dapat dibangun

tidak ada conflicting job

deadline belum lewat

Job yang gagal readiness tidak otomatis Failed.

Jika masalahnya bersifat sementara, job menjadi Deferred.

Deferred

Deferred berarti job belum aman atau belum tepat untuk dijalankan, tetapi tidak menunjukkan internal failure.

Contoh:

screen masih menyala

device sedang aktif

user storage terkunci

thermal terlalu tinggi

storage sedang berubah

concurrency slot penuh

maintenance cooldown

Deferred harus memiliki reason.

Contoh reason:

ScreenOn

ThermalHigh

UserLocked

StorageUnavailable

StorageChanging

ConcurrencyLimit

Cooldown

SchedulerDisabled

MaintenanceWindowClosed

Deferred reason penting agar scheduler dapat menentukan kapan job dievaluasi kembali.

Deferred bukan error.

Scheduler tidak boleh mencatat Deferred sebagai cleanup failure.

Retry/defer strategy

Tidak semua Deferred harus retry setiap event.

Scheduler dapat menggunakan trigger tertentu.

ScreenOn:

retry saat ScreenOff.

ThermalHigh:

retry saat thermal kembali normal atau setelah cooldown.

UserLocked:

retry saat UserUnlocked.

StorageChanging:

retry setelah storage state stabil.

ConcurrencyLimit:

retry ketika active job selesai.

Cooldown:

retry saat timer berikutnya.

Dengan demikian scheduler tidak melakukan busy loop.

Tidak boleh ada:

Deferred

immediately retry

Deferred

immediately retry

secara tak terbatas.

Preparing

Preparing berarti job sudah lolos readiness dan mulai mempersiapkan execution context.

Tahap ini dapat meliputi:

snapshot acquisition

target catalog acquisition

budget initialization

scanner initialization

worker preparation

resource validation

Namun Preparing tetap tidak boleh melakukan destructive operation.

Jika environment berubah saat Preparing:

job harus dapat menjadi Stale atau Cancelled sesuai event.

Scanning

Scanner melakukan discovery.

Scanner menghasilkan candidate objects.

Scanner tidak boleh menghapus file.

Scanner tidak boleh mengubah filesystem.

Scanner harus menggunakan snapshot dan target catalog yang dimiliki job.

Jika scanner menemukan bahwa root identity sudah berubah:

job tidak boleh melanjutkan seolah-olah filesystem masih sama.

Job harus menjadi Stale atau restart dengan snapshot baru.

Validating

Candidate masuk Safety validation.

Validation harus memastikan:

path masih berada dalam trusted root

identity masih sesuai

file type masih sesuai

filesystem/device masih sesuai

symlink policy terpenuhi

hard-link assumptions terpenuhi

target masih valid

mount state tidak berubah secara unsafe

Jika candidate tidak aman:

candidate ditolak.

Satu candidate yang ditolak tidak otomatis berarti seluruh job Failed.

Job dapat menyelesaikan operation lain yang aman, sesuai policy.

Namun jika terjadi kondisi yang menunjukkan keseluruhan snapshot tidak dapat dipercaya:

job harus dibatalkan atau menjadi Stale.

Planning

Planner mengubah candidate yang sudah lolos menjadi PlannedOperation.

Planner tidak boleh membuat arbitrary operation.

Setiap operation harus berasal dari:

validated candidate

approved policy

trusted target

current job context

Planning tidak berarti operation sudah authorized untuk execution.

Authorizing

Final authorization dilakukan sebelum execution.

Authorization memeriksa kembali:

job state

cancellation

config generation

catalog generation

runtime readiness

target identity

operation budget

operation count

byte budget

policy

safety result

Jika salah satu invariant penting tidak terpenuhi:

AuthorizedPlan tidak boleh dibuat.

Executing

Hanya job dalam Executing yang boleh memiliki destructive operation yang sedang berjalan.

Executor menerima AuthorizedPlan.

Scheduler tidak boleh mengintervensi isi plan.

Namun cancellation state tetap dapat memengaruhi apakah operation berikutnya boleh dimulai.

Executor melaporkan hasil kembali ke application layer.

Executing bukan berarti semua operation berhasil.

Hasil dapat berupa partial success.

Verifying

Setelah execution, job masuk Verifying.

Verification memastikan hasil operation sesuai expectation.

Contoh:

target sudah tidak ada

metadata berubah sesuai expected result

filesystem state tidak menunjukkan anomaly

operation count sesuai

bytes affected sesuai

Verification tidak harus memastikan seluruh filesystem memiliki kondisi tertentu.

Verification hanya memeriksa invariant yang memang dijanjikan oleh operation.

Completed

Completed berarti job selesai dan hasil akhir sudah diketahui.

Completed hanya boleh diberikan setelah verification selesai.

Jika sebagian operation berhasil dan sebagian ditolak, result harus mencerminkan partial completion.

Jangan menggunakan Completed sebagai sinonim “semua file berhasil dihapus”.

Result harus membedakan:

success

partial success

no-op

rejected candidates

failed operations

verification warnings

Cancelled

Cancelled berarti job dihentikan sebelum lifecycle normal selesai.

Cancellation reason harus dicatat.

Contoh:

UserRequested

StorageChanged

ScreenOn

ThermalHigh

Shutdown

Superseded

SafetyInvalidation

Cancellation tidak berarti semua operation gagal.

Jika sebagian operation sudah berhasil sebelum cancellation:

result harus mencatat partial execution.

Failed

Failed berarti lifecycle tidak dapat diselesaikan karena error.

Contoh:

scanner internal failure

planner invariant failure

executor infrastructure failure

verification failure

worker crash

unexpected platform failure

Failed harus memiliki error classification.

Error tidak boleh hanya berupa arbitrary string.

Gunakan typed error category.

Stale

Stale berarti snapshot atau authorization context yang dipakai job sudah tidak dapat dipercaya.

Contoh:

catalog generation berubah

configuration generation berubah pada boundary yang mensyaratkan consistency

mount topology berubah

target root identity berubah

FBE state berubah

platform capability berubah

Stale berbeda dari Failed.

Stale berarti job menjadi tidak valid karena environment berubah.

Normal response terhadap Stale adalah membuat job baru dengan snapshot baru jika policy mengizinkan.

Jangan resume job lama dengan AuthorizedPlan lama.

Stopped

Stopped dapat digunakan untuk kondisi daemon shutdown atau scheduler shutdown.

Namun jika state ini digunakan, semantics harus jelas.

Stopped bukan pengganti Cancelled.

Jika job belum mulai dan daemon shutdown:

Cancelled atau Stopped dapat digunakan sesuai API.

Jika worker sedang berjalan:

job harus memiliki terminal state yang mencerminkan apakah execution benar-benar berhenti.

Stale

Stale dapat menjadi terminal state untuk job tertentu.

Jika scheduler ingin retry, retry harus membuat job attempt baru atau membuat explicit requeue transition yang terdokumentasi.

Jangan menyembunyikan retry dengan mengubah state secara diam-diam.

Invalid transition

Invalid transition harus dianggap programming error atau invariant violation.

Contoh:

Completed → Executing

Cancelled → Scanning

Failed → Executing

Stale → Executing

Queued → Verifying

semuanya harus ditolak.

State machine tidak boleh mempercayai caller.

Method transition_to() harus memeriksa valid transition.

Scheduler queue

Scheduler queue harus bounded.

Tidak boleh menerima jumlah job tanpa batas.

Batas dapat berupa:

maximum pending jobs

maximum jobs per client

maximum scheduled jobs

maximum retry count

maximum deferred lifetime

Jika queue penuh:

request dapat ditolak atau diberi status Deferred/Rejected sesuai API.

Queue overflow tidak boleh menyebabkan memory exhaustion.

Job deduplication

Scheduler harus mencegah cleanup job identik menumpuk.

Contoh:

timer memicu cleanup.

Sebelum job selesai, client mengirim manual cleanup.

Scheduler harus memiliki aturan apakah:

manual request menunggu

manual request digabung

manual request ditolak

manual request mendapat priority

Tidak boleh membuat dua cleanup yang melakukan pekerjaan identik tanpa alasan.

Concurrency

Versi awal sebaiknya konservatif.

Untuk destructive cleanup, satu active cleanup job per daemon dapat menjadi default implementation.

Alasan:

lebih mudah menjaga storage state consistency

lebih mudah mengontrol budget

lebih mudah melakukan cancellation

lebih mudah mencegah dua executor mengakses target yang sama

lebih mudah melakukan audit

Concurrency dapat diperluas kemudian jika model safety memang mendukung.

Worker scan atau read-only tasks dapat memiliki concurrency berbeda jika dibutuhkan.

Namun jangan mengoptimalkan concurrency sebelum correctness stabil.

Minimal:

System-triggered cleanup

Scheduled maintenance

Background maintenance

Priority hanya menentukan scheduling order.

Priority tidak dapat melewati safety gate.

Job priority tinggi tetap harus melalui:

Tidak boleh ada:

HighPriority → SkipSafety

Contoh:

Trigger source berguna untuk:

Trigger source tidak boleh menjadi authorization dengan sendirinya.

Manual tidak berarti allowed.

System event juga tidak berarti allowed.

Configuration generation

Setiap job mengambil ConfigSnapshot.

ConfigSnapshot memiliki generation.

Contoh:

generation 41

job dibuat.

kemudian config reload.

generation 42 menjadi active.

Job generation 41 tidak otomatis berubah menjadi 42.

Job tetap menggunakan snapshot 41 selama snapshot tersebut masih dianggap valid untuk lifecycle job.

Namun sebelum destructive execution, authorization dapat mensyaratkan bahwa generation masih compatible dengan active configuration.

Jika policy mendefinisikan reload sebagai invalidation:

job menjadi Stale.

Jika policy mendefinisikan active job boleh menyelesaikan snapshot lama:

job dapat melanjutkan dengan snapshot 41.

Keputusan tersebut harus explicit.

Jangan bergantung kepada mutable global config.

Catalog generation

Konsep yang sama berlaku untuk Target Catalog.

Job menyimpan catalog generation.

Jika storage berubah:

catalog generation berubah.

Job yang bergantung pada catalog lama harus dicek.

Jika target identity berubah:

job tidak boleh melanjutkan menggunakan target lama.

Catalog generation bukan pengganti identity verification.

Generation membantu mendeteksi perubahan.

Final executor boundary tetap melakukan revalidation.

Platform snapshot

Job juga dapat memiliki PlatformSnapshot.

Snapshot dapat berisi:

API level

kernel capabilities

storage state

user state

thermal state

screen state

mount topology summary

available filesystem features

SELinux/security context capability

PlatformSnapshot tidak boleh dianggap permanent.

Perubahan platform state dapat membuat job Stale atau Deferred.

Readiness snapshot

Readiness harus dipisahkan dari PlatformSnapshot.

PlatformSnapshot menjelaskan keadaan.

Readiness menjelaskan apakah job boleh berjalan.

Contoh:

ScreenOn = true.

PlatformSnapshot menyimpan ScreenOn.

ReadinessPolicy menyimpulkan:

cleanup_not_allowed_due_to_screen_state.

Dengan pemisahan ini platform layer tidak perlu mengetahui business rule cleanup.

Budget

Setiap job memiliki budget.

Minimal:

max_entries

max_metadata_reads

max_operations

max_bytes

max_duration

max_depth

Budget harus bersifat monoton.

Jika operation sudah mengurangi budget:

budget tidak boleh dikembalikan sembarangan.

Contoh:

max_operations = 5000.

Setelah 300 operation dilakukan:

remaining = 4700.

Retry tidak boleh secara tidak sengaja mereset budget menjadi 5000 jika retry tersebut masih merupakan attempt yang sama.

Jika job baru dibuat:

job baru mendapatkan budget baru.

Budget juga harus dibedakan:

scan budget

planning budget

execution budget

verification budget

Scheduler tidak boleh mengubah budget untuk melewati safety limit.

Retry

Retry harus dibatasi.

Retry cocok untuk:

temporary storage unavailable

transient platform failure

temporary worker failure

resource contention

Retry tidak cocok untuk:

safety rejection

invalid target

path traversal attempt

policy rejection

malformed IPC request

authorization failure

Retry terhadap safety rejection hanya akan mengulang unsafe request.

Retry policy harus memiliki:

maximum attempts

backoff

jitter jika diperlukan

terminal condition

reason classification

Backoff harus menggunakan monotonic clock.

Manual request tidak boleh digunakan untuk bypass retry limit kecuali menghasilkan job baru yang tetap melalui semua safety checks.

Deferred versus retry

Deferred dan retry bukan hal yang sama.

Deferred berarti environment belum memenuhi readiness.

Retry berarti job sebelumnya mengalami transient failure dan boleh dicoba kembali.

Contoh:

ScreenOn → Deferred.

Executor mengalami temporary I/O failure → Failed/Retryable.

Scheduler kemudian dapat membuat retry job.

Jangan mencampur dua konsep ini karena akan menyulitkan telemetry dan diagnosis.

Cancellation semantics

CancelJob harus bekerja terhadap semua non-terminal state.

Jika job:

Created

Queued

CheckingReadiness

Deferred

maka cancellation dapat mengubah state secara cepat.

Jika job:

Scanning

Planning

Executing

maka cancellation harus cooperative.

Jika job sudah terminal:

Completed

Cancelled

Failed

Stale

CancelJob tidak boleh mengubah state.

Response dapat berupa AlreadyFinished.

Shutdown cancellation

Shutdown adalah cancellation source khusus.

Semua queued jobs harus berhenti menerima dispatch.

Deferred jobs tidak boleh dijadwalkan ulang selama shutdown.

Active jobs menerima cancellation request.

Scheduler harus memastikan tidak ada job baru dibuat akibat timer event setelah shutdown dimulai.

Scheduler fairness

Scheduler tidak boleh hanya menjalankan job tertua selamanya.

Priority, deadline, retry state, dan trigger source dapat digunakan.

Namun fairness tidak boleh mengizinkan maintenance job menghambat control operations.

Manual cancellation harus selalu dapat diproses.

Status request harus tetap responsif.

Scheduler queue harus mendukung control-plane priority.

Job admission

Sebelum job masuk queue:

request validation

authorization

duplicate detection

queue limit

resource conflict check

configuration snapshot acquisition

trigger classification

harus dilakukan.

Jika request tidak valid:

jangan membuat runnable job.

Jika request valid tetapi belum ready:

buat Deferred jika API membutuhkan persistent scheduling state.

Jika request valid dan ready:

Queued.

Admission tidak boleh melakukan destructive work.

Job persistence

Jika daemon belum membutuhkan persistent job database, versi pertama dapat menggunakan in-memory job state.

Namun architecture harus mempertimbangkan restart semantics.

Setelah daemon crash:

job yang belum selesai tidak boleh dianggap Completed.

AuthorizedPlan lama tidak boleh otomatis dilanjutkan.

Jika persistent job record ada:

state seperti Executing harus dianggap uncertain setelah crash.

Recovery harus conservative.

Job dapat ditandai Interrupted atau RecoveryRequired.

Kemudian scheduler membuat fresh job setelah environment diverifikasi.

Crash recovery

Crash recovery harus mengikuti prinsip:

never assume success.

Jika executor mungkin telah melakukan sebagian operation sebelum crash:

verification harus dilakukan sebelum status final ditetapkan jika memungkinkan.

Namun verification tidak boleh menganggap filesystem state sebagai bukti bahwa seluruh plan berhasil.

Report harus membedakan:

known completed operations

unknown operations

failed operations

unverified operations

Untuk destructive operation, partial execution adalah kondisi normal yang harus dapat direpresentasikan.

Scheduler tidak boleh melakukan rollback massal secara otomatis hanya karena job crash.

Reason:

rollback deletion tidak selalu mungkin.

Filesystem mungkin berubah.

File dapat dibuat ulang.

Identity dapat berubah.

Mount dapat berubah.

User state dapat berubah.

Scheduler tidak dapat melewati safety.

Invariant 3:

Scheduler tidak dapat membuat AuthorizedPlan sendiri.

Invariant 4:

Invariant 6:

Invariant 7:

Invariant 8:

Invariant 9:

Testing state machine

Job state machine harus memiliki model test.

Setiap valid transition diuji.

Setiap invalid transition diuji.

Contoh:

Created → Queued valid.

Queued → Executing invalid.

Scanning → Validating valid.

Scanning → Completed invalid.

Completed → Cancelled invalid.

Cancelled → Executing invalid.

Stale → Executing invalid.

Selain unit test, property-based test dapat digunakan untuk menghasilkan sequence event acak.

State machine harus selalu mempertahankan invariant:

job berada pada satu state.

terminal state tidak berubah.

budget tidak meningkat.

attempt tidak berkurang.

generation tidak berubah secara mutable.

cancellation tidak kembali menjadi false setelah true.

Deterministic scheduler

Scheduler sebaiknya dapat dijalankan dengan fake clock dan fake event source.

Test harus dapat membuat sequence:

t=0 job dibuat.

t=1 screen on.

t=2 timer elapsed.

t=3 screen off.

t=4 worker started.

t=5 storage changed.

t=6 worker cancelled.

Tanpa menunggu waktu nyata.

Deterministic scheduling akan sangat membantu ketika debugging race condition.

Scheduler tidak boleh bergantung kepada sleep dalam test.

Concurrency test

Minimal test:

dua StartCleanup bersamaan.

StartCleanup dan CancelJob bersamaan.

TimerElapsed dan StorageChanged bersamaan.

WorkerCompleted dan ShutdownRequested bersamaan.

ScreenOn dan dispatch bersamaan.

UserLocked dan execution boundary bersamaan.

Expected result harus ditentukan oleh priority dan state transition rules.

Tidak boleh ada hasil yang bergantung kepada timing kebetulan.

Atomic state transition

Contoh:

Job Queued.

dua worker mencoba mengambil job.

Hanya satu yang boleh mendapatkan ownership.

Job kemudian menjadi Preparing atau Running.

Worker kedua harus melihat job sudah diambil.

Ownership worker harus explicit.

Scheduler tidak boleh menggunakan flag boolean terpisah yang dapat menghasilkan state:

running = false

cancelled = true

queued = true

yang semuanya true sekaligus.

Gunakan satu state machine sebagai source of truth.

Worker ownership

Setiap active job memiliki satu owner worker.

Scheduler menyimpan worker assignment.

Worker memiliki JobId.

Worker result harus membawa JobId.

Jika worker mengirim event untuk job yang sudah tidak active:

event harus ditolak atau dicatat sebagai stale worker event.

Jangan menerapkan event tersebut kepada job baru yang kebetulan menggunakan resource lain.

JobId correlation wajib.

Stale worker event

Contoh:

Job A memiliki worker.

Job A cancelled.

Job B dibuat.

Worker A terlambat mengirim Completion.

Scheduler menerima:

WorkerCompleted(JobA)

Scheduler tidak boleh mengubah Job B.

JobId menjadi correlation boundary.

Worker event generation dapat ditambahkan jika diperlukan.

Queue shutdown

Ketika scheduler masuk stopping:

Queued jobs tidak boleh dispatch.

Deferred jobs tidak boleh retry.

Timer trigger tidak boleh membuat job baru.

IPC StartCleanup harus ditolak dengan status daemon stopping.

Status request tetap boleh diproses selama control plane masih hidup.

Setelah runtime benar-benar stopped:

semua request baru ditolak.

Scheduler contract

Interface scheduler minimal:

submit(request)

cancel(job_id)

status(job_id)

list_jobs(filter)

handle_event(event)

tick(now)

shutdown()

dispatch_next()

Scheduler interface tidak boleh memiliki:

delete_path()

remove_file()

execute_plan()

scan_directory()

trim_device()

write_sysfs()

Jika function semacam itu muncul di scheduler, berarti boundary architecture mulai rusak.

ApplicationController integration

ApplicationController menjadi pemilik orchestration.

Scheduler adalah subsystem yang mengelola queue dan timing.

Runtime mengirim event ke ApplicationController.

ApplicationController menentukan subsystem yang menerima event.

Contoh:

SystemEvent::TimerElapsed

→ ApplicationController

→ Scheduler.handle_timer()

SystemEvent::StorageChanged

→ ApplicationController

→ invalidate platform/catalog

→ Scheduler.invalidate_jobs()

SystemEvent::WorkerEvent

→ ApplicationController

→ Scheduler.handle_worker_event()

SystemEvent::ShutdownRequested

→ ApplicationController

→ Scheduler.shutdown()

Dengan pola ini scheduler tidak perlu mengetahui detail epoll, signalfd, timerfd, atau uevent.

Security boundary

Scheduler tidak boleh menerima arbitrary filesystem path dari client lalu memasukkannya ke job.

Job request menggunakan domain-level identifiers.

Contoh:

TargetId

PackageId

UserId

ProfileId

RelativePath hanya muncul setelah discovery atau planning pada layer yang sesuai.

Scheduler tidak boleh membuat TrustedRoot.

TrustedRoot berasal dari platform/safety layer.

Scheduler hanya menyimpan reference terhadap validated job context.

End-to-end flow

Alur lengkap setelah 36.md:

Runtime menerima event.

Runtime menghasilkan SystemEvent.

ApplicationController menerima event.

Jika event merupakan request cleanup, request divalidasi.

Job dibuat.

ConfigSnapshot dipasang.

PlatformSnapshot diambil.

Target Catalog snapshot diambil.

Scheduler melakukan admission.

Readiness diperiksa.

Jika belum ready:

Deferred.

Jika ready:

Queued.

Scheduler dispatch worker.

Job menjadi Preparing.

Scanner berjalan.

Job menjadi Scanning.

Candidate masuk Safety validation.

Job menjadi Validating.

Policy diterapkan.

Planner membuat PlannedOperation.

Job menjadi Planning.

Final authorization dilakukan.

Job menjadi Authorizing.

AuthorizedPlan diterbitkan.

Job menjadi Executing.

Executor menjalankan operation.

Result dikumpulkan.

Job menjadi Verifying.

Verifier memeriksa hasil.

Job menjadi Completed, Failed, Cancelled, atau Stale.

Scheduler menerima result.

Worker slot dilepaskan.

Scheduler mengevaluasi job berikutnya.

Pada seluruh flow tersebut, tidak ada scheduler shortcut menuju filesystem.

Decision

Job state machine harus diperlakukan sebagai kontrak inti, bukan sekadar enum untuk logging.

State menentukan apa yang boleh dilakukan.

State menentukan event apa yang valid.

State menentukan apakah cancellation dapat diterima.

State menentukan apakah worker boleh aktif.

State menentukan apakah result dapat diterapkan.

State menentukan apakah scheduler dapat membuat retry.

Dengan demikian state machine menjadi salah satu security dan correctness boundary.
