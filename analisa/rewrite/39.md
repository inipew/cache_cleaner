39.md

Filesystem Safety Layer, TrustedRoot, FD-relative Resolution, Identity Revalidation, Race Detection, Mount Boundary, dan Final Pre-Execution Safety Gate

1. Tujuan

Safety Layer adalah lapisan keamanan filesystem yang menjadi gate wajib sebelum operasi yang berpotensi mengubah filesystem dijalankan.

Safety Layer bukan helper kecil milik Executor dan bukan bagian dari Scanner. Safety harus menjadi komponen independen yang dapat menolak sebuah operasi walaupun Scanner, Policy, Planner, atau Scheduler sebelumnya menganggap operasi tersebut valid.

Alur keamanan yang wajib dipertahankan:

Candidate
→ SafetyValidatedCandidate
→ PolicyApprovedCandidate
→ PlannedOperation
→ AuthorizedPlan
→ Final Safety Gate
→ Executor
→ Verification

Tidak boleh ada jalur alternatif:

Candidate → Executor

Candidate → unlink/delete

Path string → Executor

AuthorizedPlan → Executor tanpa revalidation

Safety Layer harus menganggap filesystem sebagai lingkungan yang dapat berubah kapan saja setelah scan dilakukan.

2. Tanggung Jawab Safety Layer

Safety Layer bertanggung jawab untuk:

memastikan target berada di TrustedRoot yang benar

memastikan path tidak keluar dari boundary

memastikan traversal tidak mengikuti symlink yang tidak diizinkan

memastikan object type sesuai dengan hasil discovery

memastikan identity object masih sesuai

memastikan filesystem atau mount boundary tidak berubah secara tidak sah

memastikan root masih merupakan root yang sama

memastikan operasi yang akan dilakukan sesuai dengan authorization

melakukan final validation tepat sebelum destructive operation

menolak kondisi yang ambigu

menghasilkan error bertipe yang dapat ditangani Scheduler dan Executor

menjaga agar operasi filesystem berbahaya sulit diekspresikan melalui API

Safety Layer tidak bertanggung jawab untuk:

menentukan apakah cache layak dihapus

menentukan retention policy

menentukan prioritas job

menjalankan recursive deletion

mengubah permission

mengubah ownership

memperbaiki filesystem

menjalankan shell command

menghapus object secara langsung pada tahap discovery

3. Prinsip Fail Closed

Safety Layer harus menggunakan prinsip fail closed.

Jika informasi yang diperlukan untuk membuktikan keamanan tidak tersedia, operasi harus ditolak atau ditunda.

Contoh:

identity tidak dapat dibaca

root identity tidak dapat diverifikasi

mount identity tidak diketahui

object type berubah

path resolution ambigu

filesystem boundary tidak dapat diverifikasi

permission berubah

catalog sudah stale

platform snapshot sudah stale

authorization sudah expired

Dalam kondisi tersebut hasilnya bukan Allowed.

Hasil yang tepat dapat berupa:

Unavailable

ChangedSinceScan

RootChanged

FilesystemChanged

PermissionDenied

Stale

atau error internal yang menyebabkan job gagal secara aman.

Tidak boleh menggunakan asumsi:

“kemungkinan besar masih sama”

“path-nya masih terlihat benar”

“root biasanya tidak berubah”

“symlink mungkin aman”

“kalau gagal stat, tetap hapus saja”

4. TrustedRoot

TrustedRoot adalah representasi terverifikasi dari root filesystem yang boleh digunakan oleh sebuah operasi.

TrustedRoot bukan sekadar string seperti:

/data/user/0/example/cache

TrustedRoot harus memiliki identity dan boundary yang dapat diverifikasi.

Konsep minimal:

TrustedRootId

root path atau relative representation

root directory handle atau mekanisme equivalent

device/filesystem identity

inode/object identity

mount identity jika tersedia

catalog generation

creation context

validation metadata

TrustedRoot harus dibuat oleh komponen yang memiliki pengetahuan tentang target yang sah.

Caller tidak boleh membuat TrustedRoot dari arbitrary path.

Contoh API yang tidak diperbolehkan:

TrustedRoot::new("/some/arbitrary/path")

API seperti ini memungkinkan domain atau client menciptakan root yang belum melalui catalog dan safety validation.

Sebaliknya, root harus berasal dari TargetCatalog atau platform adapter yang telah melakukan validasi.

5. Ownership TrustedRoot

TrustedRoot harus mempunyai ownership yang jelas.

Komponen yang membuat TrustedRoot bertanggung jawab memastikan bahwa identity root telah diverifikasi.

Setelah dibuat, TrustedRoot harus immutable.

TrustedRoot tidak boleh:

diubah path-nya

diganti device identity-nya

diganti inode identity-nya

diganti mount identity-nya

dipakai untuk target lain

digunakan sebagai alias arbitrary path

TrustedRoot yang sudah stale tidak boleh diperbarui secara diam-diam.

Jika filesystem berubah, buat TrustedRoot baru melalui proses discovery/catalog baru.

6. Root Identity

Path bukan identity.

Contoh:

/data/user/0/com.example/cache

dapat menunjuk ke object berbeda setelah:

rename

delete

recreate

mount change

bind mount

filesystem replacement

container atau namespace change

Karena itu Safety Layer harus menyimpan identity root yang dapat diverifikasi.

Minimal identity filesystem object:

device identity

inode identity

object type

Jika platform memungkinkan, tambahkan:

mount identity

filesystem identity

generation atau change indicator

Root validation harus membandingkan identity yang disimpan dengan object yang ditemukan saat operasi akan dijalankan.

Jika berbeda:

RootChanged

Operasi ditolak.

7. FD-relative Filesystem Resolution

Semua operasi destructive harus dilakukan relatif terhadap filesystem handle yang sudah dipercaya.

Model yang diinginkan:

TrustedRoot
→ root directory FD
→ parent directory FD
→ validated final component
→ final safety check
→ unlinkat atau operasi equivalent

Jangan melakukan:

absolute path construction
→ delete(path)

Path string hanya digunakan untuk representasi logical path dan diagnostics.

Executor tidak boleh menjadikan absolute path sebagai authority.

Authority berasal dari:

TrustedRoot

directory handle

validated relative components

object identity

authorization

final safety validation

8. RelativePath

RelativePath harus menjadi tipe domain yang tervalidasi.

RelativePath tidak boleh menerima:

absolute path

empty component

"." sebagai arbitrary traversal component

".." yang dapat keluar dari root

NUL byte

component yang melebihi batas

invalid encoding

path yang tidak dapat direpresentasikan dengan aman

Path parsing harus dilakukan sebelum filesystem operation.

Setelah RelativePath terbentuk, caller tidak boleh mengubah raw representation tanpa melalui validation ulang.

9. Path Component

Traversal harus dilakukan component-by-component.

Contoh logical path:

cache/a/b.tmp

harus diperlakukan sebagai:

cache
→ a
→ b.tmp

bukan sebagai satu string yang kemudian diserahkan kepada arbitrary filesystem API.

Setiap component harus:

valid

relative

tidak mengandung separator tersembunyi

tidak menjadi "." atau ".."

tidak menyebabkan traversal keluar root

Traversal harus menggunakan directory handle dari parent sebelumnya.

10. Symlink Policy

Default Safety Policy adalah tidak mengikuti symlink selama destructive traversal.

Scanner boleh menemukan symlink sebagai object.

Safety Layer tidak boleh mengubah symlink menjadi target object secara otomatis.

Contoh:

cache/link → /data/important

Operasi terhadap:

cache/link

tidak boleh berubah menjadi operasi terhadap:

/data/important

Jika symlink ditemukan pada component traversal yang seharusnya merupakan directory, operasi harus ditolak.

Jika target akhir adalah symlink dan policy tidak secara eksplisit mengizinkan penghapusan symlink itu sendiri, operasi harus ditolak.

Target yang berbeda dari symlink target tidak boleh disentuh.

11. Hard Link

Hard link tidak dapat dianggap sebagai containment boundary hanya berdasarkan path.

Sebuah file dapat mempunyai lebih dari satu directory entry.

Safety Layer harus memahami bahwa:

path identity

object identity

bukan hal yang sama.

Jika policy hanya mengizinkan penghapusan object tertentu yang ditemukan saat scan, identity object harus diverifikasi kembali.

Jika object identity berubah karena race, operasi harus ditolak.

Hard link tidak boleh digunakan untuk mengelabui identity validation.

12. Mount Boundary

Filesystem tree bukan selalu satu filesystem.

Sebuah directory dapat berisi mount point atau boundary lain.

Safety Layer harus mengetahui filesystem identity yang diharapkan dari TrustedRoot dan target.

Jika operasi tiba-tiba menemukan filesystem berbeda dari boundary yang diizinkan, hasilnya:

MountBoundary

atau FilesystemChanged.

Default policy:

jangan melintasi filesystem boundary tanpa authorization eksplisit.

Cross-filesystem traversal tidak boleh menjadi behavior default.

Bind mount juga harus diperlakukan sebagai boundary yang membutuhkan validasi, bukan dianggap sebagai directory biasa hanya karena path berada di bawah root.

13. Object Identity

Candidate harus membawa identity yang diperoleh saat scan.

Identity minimal:

device

inode

object type

Jika platform menyediakan identity tambahan yang berguna, dapat disimpan juga.

Saat final validation, Safety Layer membaca identity object kembali.

Perbandingan:

expected identity
vs
current identity

Jika berbeda:

ChangedSinceScan

Jika object type berbeda:

TypeChanged

Jika object tidak ada:

AlreadyGone

Jika object berada di luar boundary:

OutsideRoot

Identity mismatch tidak boleh diabaikan.

14. Object Type

Safety Layer harus memverifikasi object type.

Contoh object type:

RegularFile

Directory

Symlink

Other

Jika Candidate awalnya adalah RegularFile tetapi saat execution ditemukan sebagai Directory, operasi harus ditolak.

Directory deletion membutuhkan policy dan primitive yang berbeda dari regular file deletion.

Safety Layer tidak boleh membiarkan sebuah operation terhadap RegularFile berubah menjadi recursive directory deletion.

15. Directory Deletion

Recursive deletion harus diperlakukan sebagai operasi yang berbeda dari deletion terhadap regular file.

Planner tidak boleh membuat satu primitive generik:

Delete(path)

yang secara internal dapat memutuskan:

file → unlink

directory → recursive delete

Keputusan tersebut terlalu berbahaya.

Operation type harus eksplisit.

Contoh:

RemoveFile

RemoveEmptyDirectory

RemoveTree

Namun RemoveTree tidak boleh menjadi primitive default dan membutuhkan safety contract khusus.

Untuk versi awal sistem, recursive deletion sebaiknya tidak digunakan sebagai primitive filesystem umum.

Scanner harus menghasilkan candidate individual dan Planner menghasilkan operasi yang dapat diverifikasi satu per satu.

16. Race: Object Hilang

Urutan:

scan

Candidate dibuat

object dihapus oleh pihak lain

executor melakukan validation

object tidak ditemukan

Hasil:

AlreadyGone

Ini bukan security failure.

Job dapat menganggapnya sebagai successful no-op atau partial result sesuai policy.

Yang penting adalah sistem tidak mencoba mencari object pengganti berdasarkan nama.

Jangan:

stat gagal
→ search nearby
→ delete matching filename

17. Race: Object Diganti

Urutan:

scan A

Candidate menunjuk inode A

attacker atau proses lain menghapus A

object B dibuat dengan nama yang sama

executor membuka path

identity menunjukkan inode B

Hasil:

ChangedSinceScan

Executor harus menolak operasi.

Nama yang sama tidak cukup untuk membuktikan object yang sama.

18. Race: Object Type Berubah

Urutan:

scan regular file

file dihapus

directory dengan nama sama dibuat

executor melakukan validation

type berubah

Hasil:

TypeChanged

Operasi harus dihentikan.

Hal yang sama berlaku untuk:

file → symlink

file → device

directory → symlink

directory → file

dan perubahan lain yang melanggar expected object type.

19. Race: Symlink Replacement

Urutan:

scan regular file

file diganti symlink

executor melakukan path traversal

Jika traversal mengikuti symlink, operasi dapat keluar dari target boundary.

Karena itu:

no-follow

FD-relative traversal

identity validation

dan final safety gate

harus bekerja bersama.

Tidak cukup hanya memeriksa symlink saat scan.

20. Race: Root Replacement

Urutan:

TrustedRoot dibuat

root dihapus atau mount berubah

root baru dibuat dengan path yang sama

executor menggunakan path lama

Path masih sama tetapi root identity berbeda.

Hasil:

RootChanged

Operasi harus ditolak.

Active job tidak boleh mencoba melanjutkan menggunakan root baru.

Job harus menjadi stale dan membutuhkan catalog/scan/plan baru.

21. Parent Directory Validation

Final object identity saja tidak selalu cukup.

Safety Layer juga harus memastikan parent directory masih berada pada expected traversal chain.

Parent directory harus diperoleh secara FD-relative dari TrustedRoot.

Setiap traversal component yang relevan harus diverifikasi.

Tujuannya adalah mencegah perubahan namespace menyebabkan operasi berjalan pada directory tree yang berbeda dari yang di-authorize.

22. Final Safety Gate

Safety validation harus dilakukan setidaknya pada dua tahap.

Tahap pertama:

setelah discovery

sebelum policy/planning menggunakan candidate sebagai input terpercaya

Tahap kedua:

tepat sebelum destructive operation

Tahap kedua adalah Final Safety Gate.

Final Safety Gate menerima:

AuthorizedPlan

PlannedOperation

TrustedRoot

current filesystem state

current catalog/platform generation

cancellation state

execution budget

Final Safety Gate harus memvalidasi ulang:

authorization

root identity

path containment

object identity

object type

filesystem boundary

mount identity jika tersedia

operation type

expiry

job state

cancellation

generation consistency

Jika salah satu invariant gagal, Executor tidak boleh melakukan mutation.

23. Safety Validation Tidak Sama dengan Authorization

Safety menentukan:

“Apakah operasi ini aman untuk dilakukan terhadap object yang dimaksud?”

Authorization menentukan:

“Apakah policy dan sistem mengizinkan operasi ini?”

Contoh:

file valid

identity cocok

root cocok

filesystem boundary cocok

tetapi file belum memenuhi minimum age.

Safety: valid.

Policy: reject.

Sebaliknya:

file memenuhi retention policy

tetapi inode berubah.

Policy: approved.

Safety: reject.

Keduanya wajib berhasil.

24. Safety Result

Safety Layer harus menghasilkan result bertipe.

Contoh hasil:

Allowed

AlreadyGone

ChangedSinceScan

TypeChanged

OutsideRoot

RootChanged

FilesystemChanged

MountBoundary

SymlinkRejected

PermissionDenied

Stale

Cancelled

Unavailable

InternalError

Tidak boleh mengandalkan parsing string error untuk menentukan tindakan Scheduler.

Scheduler harus dapat membedakan:

retryable

non-retryable

stale

already-completed

cancelled

security rejection

internal failure

25. Retry Semantics

Tidak semua Safety failure boleh di-retry.

AlreadyGone:

biasanya no-op.

ChangedSinceScan:

stale operation, jangan langsung retry operation yang sama.

RootChanged:

job harus menjadi stale.

FilesystemChanged:

buat snapshot/catalog baru sebelum retry.

PermissionDenied:

retry hanya jika ada event yang menjelaskan perubahan permission.

Cancelled:

tidak boleh retry otomatis.

InternalError:

ikuti error policy, tetapi jangan mengulang destructive operation tanpa safety validation baru.

Retry harus membuat attempt baru dan melakukan validation ulang.

26. Cancellation

Cancellation harus diperiksa:

sebelum traversal

selama traversal

sebelum final validation

setelah final validation jika operasi dapat mengalami delay

tepat sebelum destructive syscall bila architecture memungkinkan

Cancellation tidak boleh menyebabkan Safety Layer melewati validation.

Urutan yang benar:

check cancellation

validate

check cancellation

execute

Jika cancellation terjadi setelah mutation berhasil, result harus mencerminkan actual execution result.

Jangan mengklaim Cancelled jika object sebenarnya sudah dihapus.

27. Generation Validation

Safety Layer harus dapat memeriksa generation:

ConfigGeneration

CatalogGeneration

PlatformGeneration

Jika AuthorizedPlan menggunakan generation yang sudah tidak berlaku, operation harus ditolak sebagai Stale.

Contoh:

config reload

catalog berubah

user lock/unlock

storage berubah

mount berubah

platform state berubah

Active destructive plan tidak boleh otomatis mengikuti state baru.

Buat:

new snapshot

new scan

new validation

new plan

new authorization

28. Safety dan User Storage State

Perubahan storage state dapat membuat TrustedRoot tidak lagi valid.

Contoh:

user menjadi locked

credential-encrypted storage tidak tersedia

mount dilepas

volume berubah

storage namespace berubah

Safety harus menolak operation daripada mencoba mencari path alternatif.

Jika state kembali valid, Scheduler membuat job baru atau attempt baru dengan snapshot baru sesuai policy.

29. API Safety Layer

API harus dibuat sedemikian rupa sehingga misuse sulit dilakukan.

Contoh konseptual:

SafetyValidator

validate_candidate(candidate, context)

validate_operation(operation, authorized_plan, context)

FinalSafetyGate

check(operation, execution_context)

FilesystemResolver

resolve_parent(root, relative_path)

validate_target(root, candidate)

API tidak boleh menyediakan primitive publik seperti:

delete_any_path(path)

remove_recursive(path)

force_delete(path)

delete_without_validation(path)

ignore_identity(path)

follow_symlink(path)

cross_filesystem_delete(path)

30. Separation dari Executor

Executor hanya menerima operation yang sudah melewati Final Safety Gate.

Executor bertanggung jawab atas mutation dan hasil syscall.

Executor tidak boleh mengambil keputusan policy.

Namun Executor tetap harus memanggil atau berada di bawah enforcement Safety Gate.

Architecture yang tidak diperbolehkan:

Planner → Executor → Safety

Karena Executor dapat secara tidak sengaja mempunyai jalur mutation sebelum Safety.

Architecture yang diinginkan:

Planner
→ Authorization
→ Final Safety Gate
→ Executor
→ Filesystem Primitive

Safety enforcement harus berada pada boundary yang tidak mudah dilewati.

31. Filesystem Primitive

Primitive mutation harus seminimal mungkin.

Untuk regular file:

validated parent directory FD

validated final component

expected identity

expected type

unlinkat atau equivalent

Untuk empty directory:

validated parent directory FD

validated final component

expected directory identity

directory-specific removal primitive

Primitive tidak boleh menerima arbitrary absolute path sebagai authority.

32. Syscall Boundary

Raw filesystem syscall harus berada di platform/filesystem abstraction.

Domain tidak boleh mengimpor syscall.

Scanner tidak boleh langsung menggunakan destructive syscall.

Safety menggunakan Filesystem abstraction yang menyediakan operasi:

open directory safely

stat without following symlink

resolve relative component

compare identity

check filesystem boundary

perform final removal primitive

Abstraction harus memudahkan testing dengan fake filesystem.

36. Fuzz Testing

Fuzz target minimal:

37. Mutation Prohibition

Safety validation tahap scan-time harus read-only.

Final Safety Gate juga harus sebisa mungkin melakukan validation sebelum mutation.

Safety Layer tidak boleh mempunyai API yang secara internal melakukan:

delete lalu validate

rename lalu validate

chmod lalu validate

move lalu validate

recursive cleanup

Safety adalah precondition enforcement.

Mutation hanya terjadi setelah semua safety invariant terpenuhi.

38. Observability

Safety rejection harus tercatat dengan informasi yang cukup untuk diagnosis tanpa membocorkan data sensitif.

Contoh metadata:

job id

operation id

target id

relative path jika aman untuk dicatat

expected object type

failure category

attempt

generation

timestamp

duration

Tidak perlu mencatat:

credential

secret

authorization token

raw security-sensitive metadata

full arbitrary filesystem path jika logging policy melarangnya

Logging tidak boleh mengubah safety decision.

39. Security Logging

Security rejection sebaiknya dibedakan dari operational failure.

Contoh:

ChangedSinceScan

RootChanged

OutsideRoot

SymlinkRejected

MountBoundary

harus mudah dibedakan dari:

AlreadyGone

PermissionDenied

Unavailable

Cancelled

InternalError

Tujuannya agar telemetry dapat menunjukkan apakah sistem mengalami kondisi normal karena concurrent mutation atau ada indikasi abnormal.

40. No Safety Bypass

Tidak boleh ada:

environment variable untuk mematikan safety

debug flag yang melewati Final Safety Gate

config option disable_safety

CLI option force_delete

IPC command bypass_safety

test-only public bypass yang ikut tercompile ke production

shell fallback

root fallback

Jika debugging membutuhkan bypass, gunakan fake filesystem atau test-only implementation yang tidak tersedia pada production binary.

41. Privilege Tidak Menggantikan Safety

Process yang memiliki privilege tinggi tetap wajib melewati Safety Layer.

Root privilege bukan bukti bahwa path aman.

SELinux permission bukan bukti bahwa target benar.

Access granted bukan berarti operation authorized.

Safety menjawab correctness dan boundary.

Privilege hanya menentukan apakah operation secara teknis dapat dilakukan.

42. Error Handling

Safety error harus dipropagasikan tanpa diubah menjadi generic success.

Contoh buruk:

SafetyError
→ catch
→ log warning
→ continue delete

Contoh benar:

SafetyError
→ operation rejected
→ Scheduler receives typed result
→ Executor does not mutate
→ job state updated

43. Atomicity Boundary

Tidak mungkin membuat seluruh proses:

scan

policy

authorization

filesystem mutation

sepenuhnya atomic terhadap perubahan external process.

Karena itu architecture harus mengurangi race window dan melakukan validation sedekat mungkin dengan mutation.

Model:

discovery validation

planning

authorization

open/resolve

final identity validation

mutation

verification

Semakin jauh waktu antara final validation dan mutation, semakin besar race window.

Executor tidak boleh melakukan pekerjaan blocking yang tidak perlu setelah Final Safety Gate dan sebelum destructive syscall.

44. Verification Setelah Mutation

Safety bukan pengganti Verification.

Setelah operation berhasil:

Verifier dapat memeriksa hasil sesuai primitive.

Contoh:

unlink berhasil

result = Removed

Jika syscall mengatakan object tidak ada:

result = AlreadyGone

Jika operation gagal karena permission:

result = PermissionDenied

Verification harus membedakan:

operation attempted

operation succeeded

operation was already absent

operation rejected before mutation

45. Complete Execution Contract

Contract lengkap menjadi:

Scanner menemukan Candidate.

Safety memvalidasi Candidate.

Policy menentukan eligibility.

Planner menghasilkan PlannedOperation.

Authorization menghasilkan AuthorizedPlan.

Scheduler menentukan bahwa job boleh execute.

Final Safety Gate memvalidasi state terbaru.

Executor melakukan satu primitive mutation.

Verifier memeriksa hasil.

Scheduler mencatat OperationResult.

Job berpindah ke state berikutnya.

Tidak ada layer yang boleh melewati urutan tersebut.

46. Dependency Rules

Safety Layer boleh bergantung pada:

domain types

filesystem abstraction

platform snapshot

catalog snapshot

authorization types

clock abstraction jika diperlukan

Safety Layer tidak boleh bergantung pada:

CLI

IPC transport

Scheduler implementation

ApplicationController

shell

logging framework sebagai dependency wajib untuk correctness

Executor implementation sebagai shortcut

Safety harus dapat digunakan dan dites tanpa menjalankan daemon penuh.

47. Safety Invariants

Invariant utama:

Tidak ada destructive operation tanpa TrustedRoot.

Tidak ada destructive operation menggunakan arbitrary absolute path.

Tidak ada destructive operation tanpa identity validation.

Tidak ada destructive operation jika object type berubah.

Tidak ada destructive operation jika root berubah.

Tidak ada destructive operation jika filesystem boundary berubah.

Tidak ada destructive operation yang mengikuti symlink secara tidak sengaja.

Tidak ada stale AuthorizedPlan yang dieksekusi.

Tidak ada safety error yang berubah menjadi success.

Tidak ada cancellation yang menyebabkan validation dilewati.

Tidak ada debug/configuration bypass terhadap Final Safety Gate.

Tidak ada Executor API yang dapat menerima arbitrary path sebagai destructive authority.

49. Keputusan Arsitektur

Safety Layer menjadi mandatory security boundary.

TrustedRoot adalah authority filesystem, bukan string path.

RelativePath dan PathComponent adalah typed validated values.

Filesystem traversal dilakukan secara FD-relative.

Symlink tidak diikuti secara default.

Object identity harus diverifikasi ulang sebelum mutation.

Root identity harus diverifikasi ulang sebelum mutation.

Filesystem/mount boundary harus diverifikasi.

Final Safety Gate wajib dilakukan tepat sebelum destructive operation.

Executor tidak boleh menyediakan arbitrary-path deletion API.

Safety failure menghasilkan typed result dan tidak boleh dianggap sebagai success.

Stale state menghasilkan job baru atau revalidation baru, bukan penggunaan ulang plan lama.

Safety Layer sendiri tidak melakukan cleanup.

Dengan keputusan ini, filesystem race bukan lagi kondisi tak terduga yang hanya ditangani setelah error terjadi. Race menjadi bagian resmi dari contract sistem.
