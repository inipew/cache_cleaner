# 84.md — Android Idle Power Contract, Deep Sleep Compatibility, Zero-Work CPU Behavior, Wakeup Minimization, and Fast Resume

## Tujuan

Cache cleaner daemon harus menjadi **power-neutral ketika tidak ada pekerjaan**. Saat tidak ada trigger yang eligible dan tidak ada recovery yang harus dikerjakan, daemon tidak boleh melakukan busy-loop, periodic polling agresif, filesystem scanning, atau mempertahankan wake lock hanya agar dapat "menunggu".

Target desain:

```text
No Work
   ↓
No Runnable Work
   ↓
Blocking Event Wait
   ↓
CPU ~= 0 while daemon idle
   ↓
Android dapat suspend/deep sleep
   ↓
Relevant Wake/Event
   ↓
Fast Re-evaluation
   ↓
Work only if eligible
```

Catatan penting: `CPU 0.00%` adalah **operational target**, bukan jaminan matematis. Scheduler OS, accounting tools, runtime, logging, dan transient wakeups dapat menghasilkan penggunaan kecil sesaat. Invariant yang benar adalah: **daemon tidak mempunyai active polling/runnable loop ketika idle**.

---

## 1. Power Is a First-Class Constraint

Power behavior harus menjadi bagian dari architecture contract, bukan optimization terakhir.

Daemon harus mengoptimalkan:

- CPU residency
- wakeup frequency
- wakeup duration
- filesystem I/O
- memory activity
- logging activity
- binder/socket activity
- unnecessary platform queries
- unnecessary scans

Tujuan bukan hanya CPU rendah saat terukur, tetapi meminimalkan alasan daemon membangunkan CPU.

## 2. Idle Is a Real State

Scheduler harus memiliki explicit state:

```rust
pub enum SchedulerActivity {
    Active,
    WaitingForTrigger,
    WaitingForDeadline,
    WaitingForResource,
    Stopping,
}
```

`WaitingForTrigger` harus berarti tidak ada work CPU aktif.

## 3. No Busy Loop

Dilarang:

```rust
loop {
    check_conditions();
    std::thread::sleep(Duration::from_secs(1));
}
```

untuk main scheduler.

Sleep-based polling tetap membangunkan CPU secara periodik dan dapat mencegah sistem mempertahankan deep idle.

## 4. Blocking Event Wait

Gunakan blocking primitive:

- `epoll`
- `poll`
- `ppoll`
- `eventfd`
- Unix socket readiness
- netlink socket
- platform-specific event source

Scheduler menunggu event daripada terus memeriksa kondisi.

## 5. One Wakeup, One Evaluation

Satu wakeup harus melakukan bounded evaluation:

```text
Wake
 ↓
Drain/coalesce events
 ↓
Read minimum required snapshot
 ↓
Evaluate eligibility
 ↓
Schedule/defer/no-op
 ↓
Return to blocking wait
```

Jangan mengubah satu event menjadi polling window.

## 6. Event-Driven First

Priority wakeup sources:

1. explicit manual request
2. required recovery notification
3. relevant kernel/platform event
4. deadline that is genuinely due
5. bounded reconciliation

Periodic polling adalah fallback consistency mechanism, bukan primary scheduler mechanism.

## 7. Periodic Reconciliation Must Be Sparse

Periodic reconciliation tetap diperlukan karena event dapat hilang.

Namun interval harus dipilih berdasarkan semantic requirement, bukan nilai kecil seperti 1–5 detik.

Contoh:

```text
Event-driven normal operation
+
Sparse reconciliation
+
Immediate re-evaluation on relevant event
```

Jika tidak ada event dan tidak ada deadline, daemon kembali blocking.

## 8. Adaptive Idle Interval

Jika reconciliation deadline memang diperlukan, gunakan adaptive interval:

```text
Active      → short bounded interval
RecentlyIdle → longer interval
DeepIdle    → very long interval
NoDeadline  → no timer; block indefinitely
```

Interval tidak boleh terus reset ke interval pendek hanya karena daemon terbangun untuk event yang tidak relevan.

## 9. No Timer When No Deadline

Jika scheduler tidak mempunyai deadline yang perlu dibangunkan, jangan membuat periodic timer hanya untuk "keep checking".

Conceptual:

```rust
match next_deadline {
    Some(deadline) => wait_until_event_or_deadline(deadline),
    None => wait_for_event(),
}
```

Ini penting untuk CPU idle dan deep sleep.

## 10. Monotonic Deadline

Scheduler menggunakan monotonic/boottime semantics untuk interval internal.

Wall clock tidak boleh membuat daemon wake repeatedly karena clock adjustment.

## 11. Suspend-Aware Clock

Android dapat suspend/resume.

Scheduler harus membedakan:

- monotonic time
- boottime including suspend
- wall clock

Deadline yang harus berlaku melewati suspend harus menggunakan clock semantics yang tepat.

Jangan menganggap `CLOCK_MONOTONIC` dan elapsed real-world time identik selama device suspended.

## 12. Do Not Prevent Suspend

Daemon tidak boleh mempertahankan:

- wakelock
- foreground-service-like permanent activity
- periodic alarm yang tidak diperlukan
- busy native thread
- open activity/UI

hanya untuk menjaga daemon "siap".

Jika platform mechanism membutuhkan wake capability, scope-nya harus sesingkat mungkin dan dilepas segera setelah decision/work selesai.

## 13. Wake Lock Policy

Default:

```text
No wakelock while idle
```

Saat destructive cleanup benar-benar membutuhkan CPU/IO continuity, wake policy harus explicit dan bounded.

```text
Acquire only when required
        ↓
Execute bounded work
        ↓
Verify
        ↓
Release immediately
```

Jangan acquire wakelock di daemon startup dan mempertahankannya sepanjang process lifetime.

## 14. Deep Sleep Compatibility

Deep sleep compatibility berarti daemon **tidak menghalangi suspend**.

Daemon tidak perlu "tidur sendiri" dengan mekanisme khusus jika thread-nya sudah blocking dan tidak ada wake lock.

System suspend tetap merupakan keputusan Android/kernel berdasarkan seluruh wakeup sources.

Daemon harus menjadi passive participant.

## 15. Wakeup Source Is Not CPU Work

Perlu dibedakan:

```text
Wakeup source
    !=
CPU workload
```

Target utama adalah mengurangi keduanya:

- jumlah wakeup
- CPU time setelah wakeup

Satu wakeup yang melakukan 1 ms evaluation jauh lebih baik daripada wakeup setiap detik.

## 16. Avoid Periodic Wakeups During Deep Idle

Jangan membuat:

```text
wake every 1 second
wake every 5 seconds
wake every 10 seconds
```

hanya untuk mengetahui "belum waktunya cleanup".

Jika next cleanup masih berjam-jam lagi, scheduler harus menunggu sampai deadline atau event relevan.

## 17. Scheduled Cleanup and Android Suspend

Jika cleanup dijadwalkan berdasarkan interval panjang:

```text
next_due = 06:00
```

dan device tidur dari 23:00 sampai 07:00, scheduler tidak boleh menghasilkan banyak missed jobs.

Setelah resume:

```text
reconcile schedule
    ↓
coalesce missed occurrence
    ↓
check current readiness/power policy
    ↓
create at most required work
```

Ini mengikuti missed-schedule contract pada scheduler.

## 18. Do Not Wake Solely for Missed History

Riwayat missed tick bukan alasan untuk membangunkan device berkali-kali.

Default cleanup behavior:

```text
many missed ticks → one consideration
```

## 19. Screen-Off Is Not Automatically Deep Sleep

`screen off` hanya platform signal.

Jangan menganggap:

```text
screen off == device idle == deep sleep
```

Policy harus dapat membedakan:

- screen off
- interactive state
- charging
- battery level
- thermal state
- device idle/doze-related state jika tersedia
- storage pressure
- actual suspend/resume observation jika tersedia

## 20. Screen-Off Cleanup

Jika policy mensyaratkan cleanup saat screen off, event screen-off hanya menjadi scheduling hint.

Correct:

```text
ScreenOff
  ↓
Wake scheduler
  ↓
Evaluate policy
  ↓
Check readiness
  ↓
Schedule if eligible
```

Tidak boleh:

```text
ScreenOff
  ↓
Start continuous polling
```

## 21. Fast Wake-Up

Fast wake-up berarti setelah relevant event tersedia, daemon dapat segera kembali ke scheduler path tanpa expensive initialization.

Daemon harus mempertahankan:

- initialized event loop
- lightweight runtime state
- durable state handle
- platform adapter handle jika aman
- socket/event subscriptions

Tetapi tidak boleh mempertahankan active CPU work hanya demi latency.

## 22. Cold Start vs Warm Resume

Pisahkan:

```text
Process restart
Suspend/resume
Scheduler wake
```

Suspend/resume tidak boleh diperlakukan seperti full process restart jika kernel menjaga process.

Wake path harus menghindari:

- full target scan
- full package enumeration
- full mount scan
- full config parse

kecuali generation/event menunjukkan bahwa hal tersebut diperlukan.

## 23. Lazy Refresh

Setelah wake, refresh hanya data yang stale.

```text
Wake
 ↓
Check generation/change hints
 ↓
Refresh affected subsystem
 ↓
Reuse valid snapshot
```

Jangan rebuild seluruh TargetCatalog pada setiap timer wake.

## 24. Snapshot Cache

Immutable snapshots dapat digunakan selama valid.

Contoh:

```rust
struct RuntimeSnapshots {
    platform: Arc<PlatformSnapshot>,
    catalog: Arc<TargetCatalogSnapshot>,
    system: Arc<SystemSnapshot>,
}
```

Snapshot harus memiliki generation/validity semantics.

## 25. Event Coalescing

Android dapat menghasilkan event burst.

Contoh:

```text
mount change
package change
user change
screen change
thermal change
```

Dalam waktu singkat, scheduler sebaiknya:

```text
collect events
     ↓
coalesce
     ↓
one evaluation
```

bukan satu full evaluation per event.

## 26. Event Drain Must Be Bounded

Event burst tidak boleh menyebabkan scheduler starvation.

Gunakan bounded drain:

```text
max events per wake
max evaluation time
```

Jika overflow, lakukan reconciliation pada waktu yang tepat.

## 27. Logging Is a Wakeup Source

Jangan melakukan logging berlebihan saat idle.

Dilarang log setiap timer tick seperti:

```text
"checking cleanup..."
"nothing to do"
"sleeping..."
```

Jika tidak ada perubahan, tidak perlu log.

## 28. Metrics Must Not Create Work

Metrics collection harus low-cost.

Jangan melakukan filesystem write setiap detik untuk mencatat:

```text
idle = true
```

Gunakan counters/state transitions dan flush secara bounded.

## 29. No Heartbeat File

Jangan memperbarui file heartbeat secara periodik hanya untuk membuktikan daemon hidup.

Heartbeat yang dibutuhkan untuk recovery harus menggunakan bounded lease/heartbeat interval dan hanya saat worker/job benar-benar aktif.

## 30. Idle Memory Behavior

CPU 0 bukan satu-satunya objective.

Idle daemon juga harus meminimalkan:

- allocations
- background channels
- queue scans
- lock contention
- timer creation/destruction
- log formatting
- repeated metadata reads

## 31. Thread Count

Idle daemon sebaiknya mempunyai jumlah thread minimum.

Jangan membuat dedicated polling thread untuk setiap subsystem.

Preferred:

```text
one scheduler/event thread
+ bounded worker pool only when needed
```

Worker threads dapat dibuat/dihidupkan sesuai architecture, tetapi tidak boleh spin saat idle.

## 32. Worker Shutdown / Park

Worker yang tidak diperlukan harus:

```text
park/block
```

bukan:

```text
loop { try_work(); }
```

Jika worker pool digunakan, gunakan blocking queue/semaphore/condition mechanism.

## 33. Resource Manager and Idle

ResourceManager tidak boleh polling resource state.

Jika resource tersedia kembali:

```text
resource release
    ↓
explicit wakeup
    ↓
scheduler re-evaluation
```

Jika resource tidak berubah, tidak ada periodic wakeup yang diperlukan.

## 34. IPC Idle Behavior

IPC server harus blocking.

Idle IPC socket tidak boleh menghasilkan CPU activity.

Request processing:

```text
socket readable
 ↓
parse bounded request
 ↓
submit/query
 ↓
reply
 ↓
block again
```

## 35. Eventfd / Control Wakeup

Internal control events dapat menggunakan `eventfd` atau equivalent.

Contoh:

```text
config reload
manual job
shutdown
resource release
new recovery work
```

Event tersebut membangunkan scheduler tanpa periodic polling.

## 36. Config Reload

Config reload harus event-driven.

Jangan membaca ulang config file setiap N detik hanya untuk mendeteksi perubahan.

Gunakan explicit reload request, file event jika reliable, atau sparse reconciliation.

## 37. Filesystem Watchers

Filesystem watcher boleh digunakan jika benar-benar memberikan value.

Namun watcher tidak boleh dianggap authoritative safety evidence.

Event tetap diikuti snapshot/revalidation saat diperlukan.

## 38. Android Event Sources

Adapter dapat memanfaatkan platform/kernel signals yang tersedia untuk:

- screen/interactive changes
- power/battery changes
- thermal changes
- mount/storage changes
- package/user changes
- daemon control events

Event source harus dipilih berdasarkan cost dan reliability.

## 39. Android System Scheduler Boundary

Jika cleanup perlu membangunkan device dari suspend pada waktu tertentu, daemon tidak boleh mengandalkan ordinary process timers sebagai satu-satunya wake-from-suspend mechanism.

Gunakan Android/platform scheduling mechanism yang memang memiliki semantics wake-from-suspend bila requirement tersebut benar-benar diperlukan.

Daemon harus tetap compatible dengan Doze/battery optimization semantics dan tidak boleh memaksa frequent wakeups.

## 40. Wakeup Budget

Scheduler sebaiknya mempunyai explicit conceptual budget:

```rust
struct WakeupBudget {
    max_wakeups_per_window: u32,
    max_cpu_time_per_window: Duration,
}
```

Budget ini bukan permission boundary.

Tujuannya mendeteksi runaway scheduling/polling.

## 41. Wakeup Storm Protection

Jika subsystem menghasilkan event storm:

```text
1000 events
```

jangan menghasilkan:

```text
1000 scheduler evaluations
```

Gunakan debounce/coalescing/backpressure.

## 42. Thermal Interaction

Saat thermal state tinggi, jangan hanya menunda destructive work.

Kurangi juga background evaluation frequency jika policy mengizinkan.

Thermal policy harus mempertimbangkan CPU wakeup cost.

## 43. Battery Interaction

Battery-aware scheduling dapat menunda optional cleanup ketika battery rendah.

Namun battery check sendiri tidak boleh dilakukan melalui aggressive polling.

Gunakan power events + sparse reconciliation.

## 44. Charging Interaction

Jika cleanup hanya eligible saat charging, gunakan charging state event sebagai trigger.

Jangan:

```text
poll battery status every second
```

## 45. Storage Pressure Interaction

Storage pressure dapat menjadi high-value wake trigger karena condition dapat berubah tanpa schedule.

Pressure event membangunkan scheduler untuk bounded evaluation.

## 46. Deep Sleep and Storage Pressure

Jika device sudah suspended, daemon tidak dapat mengendalikan kapan kernel membangunkan CPU kecuali platform wakeup mechanism mengizinkannya.

Untuk cache cleaner, lebih baik membiarkan device tetap tidur dan menangani pressure saat sistem memang bangun, kecuali pressure policy memiliki explicit emergency requirement.

## 47. Emergency Work

Emergency pressure cleanup yang benar-benar membutuhkan wake-from-suspend harus mempunyai explicit platform capability dan power policy.

Default jangan mengaktifkan emergency wake.

## 48. Fast Resume After Suspend

Setelah resume:

```text
resume
 ↓
read lightweight power/platform generation
 ↓
check stale state
 ↓
reconcile only if required
 ↓
return to blocking wait
```

Jangan langsung melakukan full scan hanya karena process mendapat CPU lagi.

## 49. Suspend Gap

Scheduler harus mengetahui bahwa selama suspend:

- monotonic elapsed time semantics dapat berbeda dari wall time
- queued deadlines mungkin sudah lewat
- platform topology dapat berubah
- package/user state dapat berubah
- mount state dapat berubah

Karena itu resume harus menjadi revalidation boundary.

## 50. Resume Reconciliation

Resume event harus menghasilkan:

```text
Resume
 ↓
Invalidate transient assumptions
 ↓
Refresh required platform snapshot
 ↓
Check ConfigGeneration/CatalogGeneration
 ↓
Re-evaluate deferred jobs
```

Tetapi tetap bounded dan lazy.

## 51. Doze / Idle Mode

Jika Android exposes device-idle/Doze state, treat it as policy input.

Do not assume that root privilege means the daemon should bypass Android power policy.

Optional cleanup should normally yield to system power conservation.

## 52. Foreground vs Background

Daemon architecture harus memisahkan:

```text
long-lived process
```

dari:

```text
long-lived active execution
```

Process boleh hidup tetapi harus passive saat idle.

## 53. Process Lifetime Is Not CPU Activity

Menjaga daemon tetap resident tidak otomatis buruk.

Yang harus dihindari adalah:

```text
resident + runnable + polling
```

Target:

```text
resident + blocked + no wake lock
```

## 54. Startup Cost

Startup harus ringan tetapi tidak mengorbankan safety.

Minimum startup work:

- load validated config
- recover durable state
- initialize event sources
- obtain minimum platform snapshot
- establish IPC
- enter blocking scheduler

Full catalog scan hanya jika required by recovery/readiness/generation.

## 55. Shutdown

Shutdown harus segera membangunkan blocked event loop menggunakan control event.

Jangan menunggu polling timeout berakhir hanya agar process berhenti.

## 56. Cancellation

Cancellation harus menggunakan explicit wakeup ketika worker/scheduler sedang blocked.

Cancellation latency tidak boleh bergantung pada long polling interval.

## 57. No Hidden Polling in Dependencies

Audit dependency/runtime behavior.

Aplikasi dapat terlihat idle tetapi dependency dapat menjalankan:

- background timers
- metrics exporters
- log flush loops
- async runtime housekeeping
- network keepalives

Production build harus memverifikasi actual thread/wakeup behavior.

## 58. Async Runtime Caution

Jangan memilih async runtime hanya untuk IPC jika workload sebenarnya event-driven dan kecil.

Jika async runtime digunakan, pastikan:

- no periodic task without requirement
- no busy executor loop
- timers are sparse
- idle worker threads block efficiently
- runtime shutdown is deterministic

## 59. Synchronous Event Loop Is Valid

Untuk daemon kecil dengan bounded event sources, synchronous `poll/epoll` event loop dapat lebih mudah diaudit daripada banyak async tasks.

Pilihan harus berdasarkan measured behavior, bukan style preference.

## 60. CPU Idle Acceptance Test

Production test harus mengukur idle daemon dalam kondisi:

```text
no jobs
no pending events
no recovery
no deadline soon
screen off
battery state stable
```

Expected:

```text
scheduler thread blocked
worker threads blocked/absent
no busy polling
no periodic log writes
no filesystem scan
no wake-lock retention
```

## 61. Wakeup Acceptance Test

Uji:

```text
idle
 ↓
manual request
```

Expected:

```text
one control wakeup
 ↓
job admission
 ↓
normal lifecycle
```

Bukan menunggu polling tick.

## 62. Deep Sleep Acceptance Test

Pada Android device nyata, ukur:

- suspend/resume behavior
- kernel wakeup counts jika tersedia
- daemon CPU time
- daemon thread state
- wakeup sources
- battery drain over idle window
- cleanup latency after resume

Jangan menyimpulkan deep sleep hanya dari process CPU percentage.

## 63. Long Idle Test

Minimal test window harus cukup panjang untuk menangkap periodic wakeups yang jarang.

Contoh:

```text
30 minutes
1 hour
8 hours
overnight
```

Nilai exact disesuaikan test environment.

## 64. Strace/Perfetto/Kernel Evidence

Gunakan instrumentation untuk membuktikan idle behavior.

Cari:

- repeated `poll` timeout
- repeated `nanosleep`
- timerfd expirations
- futex wakeups
- repeated `/proc` reads
- repeated `/sys` reads
- log writes
- socket traffic

Android-specific power analysis dapat menggunakan platform tracing/power tooling yang tersedia.

## 65. CPU Percentage Is Not Enough

Contoh daemon dapat menunjukkan `0.00%` tetapi tetap membangunkan device setiap 5 detik.

Itu belum power-efficient.

Conversely, satu short evaluation setelah event dapat terlihat sebagai CPU spike tetapi tetap power-efficient.

Metric utama:

```text
CPU time
wakeups
wake duration
IO
suspend residency
```

## 66. Power Regression Guard

CI/device test sebaiknya mempunyai regression threshold untuk:

- idle CPU time
- unexpected wake count
- periodic timer count
- background IO
- thread count

Perubahan scheduler tidak boleh diam-diam mengubah daemon menjadi polling service.

## 67. Production Invariant — Idle

Saat tidak ada eligible work:

1. Scheduler tidak busy-loop.
2. Tidak ada periodic filesystem scan yang agresif.
3. Tidak ada periodic config reload.
4. Tidak ada periodic package enumeration.
5. Tidak ada periodic mount enumeration tanpa requirement.
6. Tidak ada heartbeat file write untuk sekadar liveness.
7. Tidak ada continuous logging.
8. Worker tidak spin.
9. ResourceManager tidak polling.
10. IPC menunggu secara blocking.
11. No-work scheduler kembali ke event wait.

## 68. Production Invariant — Power

1. Daemon tidak menahan wakelock saat idle.
2. Daemon tidak mencegah Android suspend.
3. Wakeup sources dibatasi.
4. Event burst dicoalesce.
5. Reconciliation sparse dan adaptive.
6. Deadline menggunakan clock semantics yang benar terhadap suspend.
7. Resume menjadi revalidation boundary.
8. Optional cleanup menghormati power/thermal policy.
9. Emergency wake-from-suspend tidak menjadi default.
10. Platform wake mechanism digunakan hanya jika requirement memang membutuhkan wake.

## 69. Production Invariant — Fast Resume

1. Resume tidak otomatis berarti full scan.
2. Valid snapshot dapat digunakan kembali.
3. Hanya stale subsystem yang di-refresh.
4. Scheduler kembali ke blocking state setelah bounded evaluation.
5. Cancellation/shutdown dapat membangunkan blocked loop immediately.
6. Process initialization tidak diulang jika process tidak restart.

## 70. Definition of Done

Power architecture production-ready jika:

- idle scheduler benar-benar blocking
- no busy polling
- no unnecessary periodic wakeups
- event-driven scheduling menjadi primary mechanism
- periodic reconciliation sparse
- no wake lock retention while idle
- suspend/deep sleep tidak dihalangi daemon
- resume melakukan bounded revalidation
- scheduled cleanup tidak menyebabkan missed-tick storm
- IPC/resource/cancellation paths event-driven
- dependency background activity diaudit
- actual Android device test membuktikan behavior
- CPU time dan wakeup behavior diukur terpisah

## 71. Final Principle

> **When there is nothing to do, the daemon should have nothing runnable to do.**

Target akhir bukan sekadar:

```text
CPU ≈ 0%
```

tetapi:

```text
No Work
  ↓
No Runnable Thread
  ↓
No Unnecessary Wakeup
  ↓
No Wakelock
  ↓
Android Free to Suspend
  ↓
Relevant Event / Deadline
  ↓
Fast Bounded Wake
  ↓
Return to Sleep
```
