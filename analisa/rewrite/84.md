# 84.md — Android Idle Power, Deep Sleep, Wakeup, dan Fast Resume

## Tujuan

Cache cleaner daemon harus **power-neutral ketika tidak mempunyai pekerjaan**.

Daemon yang hidup lama bukan masalah dengan sendirinya. Yang harus dihindari adalah daemon yang hidup lama sekaligus terus runnable, polling, membaca filesystem, mengecek battery, atau membangunkan CPU hanya untuk memastikan bahwa belum waktunya cleanup.

Target sederhananya:

```text
Tidak ada pekerjaan
      ↓
Tidak ada thread yang runnable
      ↓
Blocking wait
      ↓
CPU hampir selalu idle
      ↓
Android bebas masuk suspend/deep sleep
      ↓
Event/deadline yang relevan
      ↓
Wake-up singkat
      ↓
Evaluasi bounded
      ↓
Kerjakan hanya jika memang eligible
      ↓
Kembali blocking
```

`CPU 0.00%` bukan angka yang harus dipaksakan secara literal. Scheduler kernel, runtime, logging, dan monitoring dapat menghasilkan aktivitas kecil sesaat. Invariant yang penting adalah **tidak ada active polling loop ketika daemon idle**.

---

## 1. Prinsip Utama: Idle Berarti Benar-Benar Menunggu

Ketika tidak ada job, recovery, event yang perlu diproses, atau deadline yang sudah dekat, scheduler seharusnya tidak melakukan pekerjaan CPU.

Jangan menggunakan pola seperti:

```rust
loop {
    check_cleanup_conditions();
    std::thread::sleep(Duration::from_secs(5));
}
```

Walaupun CPU percentage terlihat kecil, pola ini tetap menghasilkan wakeup periodik.

Untuk daemon Android yang berjalan berhari-hari, perbedaan antara:

```text
bangun setiap 5 detik
```

dan:

```text
menunggu event selama berjam-jam
```

sangat berarti terhadap power behavior.

Karena itu scheduler harus event-driven terlebih dahulu. Timer hanya digunakan ketika memang ada deadline yang harus diperhatikan.

---

## 2. Scheduler Harus Memiliki Dua Jenis Penantian

Secara konseptual scheduler mempunyai dua kondisi utama:

```text
Ada deadline
    → tunggu event ATAU deadline

Tidak ada deadline
    → tunggu event tanpa timeout
```

Bentuk sederhananya:

```rust
match scheduler.next_deadline() {
    Some(deadline) => wait_for_event_or_deadline(deadline),
    None => wait_for_event(),
}
```

`wait_for_event()` harus benar-benar blocking.

Event dapat berasal dari:

- manual request melalui IPC
- shutdown/cancellation
- scheduler control event
- mount/storage change
- package/user change
- power/battery change
- thermal change
- pressure signal
- resource release
- recovery notification
- platform-specific event source

Setelah wake-up, event dikumpulkan dan dicoalesce sebelum scheduler melakukan evaluasi.

---

## 3. Jangan Membuat Timer Kalau Tidak Ada Deadline

Ini salah satu aturan power yang paling penting.

Jika cleanup berikutnya baru diperlukan 6 jam lagi, scheduler tidak perlu bangun setiap beberapa detik untuk bertanya:

> "Sudah waktunya belum?"

Scheduler cukup menunggu sampai:

```text
relevant event
        atau
actual deadline
```

Timer periodik hanya dibutuhkan untuk reconciliation yang memang mempunyai alasan operasional. Bahkan reconciliation tersebut harus sparse dan adaptive, bukan polling agresif.

Jika tidak ada reconciliation deadline sama sekali, scheduler kembali ke blocking wait tanpa timer.

---

## 4. Periodic Reconciliation Adalah Safety Net, Bukan Mesin Scheduler

Event-driven scheduling tidak boleh bergantung sepenuhnya pada event karena event dapat hilang, terlambat, atau tidak tersedia pada platform tertentu.

Karena itu tetap diperlukan periodic reconciliation.

Namun konsepnya:

```text
Primary:
    event-driven

Secondary:
    sparse reconciliation
```

Bukan:

```text
Primary:
    polling every N seconds

Secondary:
    events
```

Jika tidak ada perubahan dan tidak ada pekerjaan, reconciliation harus menggunakan interval yang cukup panjang. Setelah sistem idle lebih lama, interval dapat diperpanjang lagi.

Jika tidak ada reconciliation deadline sama sekali, scheduler kembali ke blocking wait tanpa timer.

---

## 5. Wake-up Harus Menghasilkan Pekerjaan yang Terukur

Setiap wake-up harus mempunyai alasan.

Alur yang diharapkan:

```text
Wake
  ↓
Drain event yang tersedia
  ↓
Coalesce event
  ↓
Ambil snapshot minimum yang diperlukan
  ↓
Evaluasi scheduler
  ↓
Schedule / defer / no-op
  ↓
Kembali blocking
```

Satu event tidak boleh memicu rangkaian polling baru.

Contohnya, `ScreenOff` dapat membangunkan scheduler satu kali. Setelah policy diperiksa, jika cleanup belum eligible, scheduler kembali tidur. Tidak boleh kemudian muncul loop baru yang mengecek screen state setiap detik.

---

## 6. Event Burst Harus Dicoalesce

Android dapat menghasilkan banyak perubahan dalam waktu singkat.

Misalnya ketika device berubah keadaan dapat muncul kombinasi:

```text
screen change
power change
thermal change
mount change
package change
user change
```

Tidak efisien jika setiap event menyebabkan full evaluation sendiri.

Gunakan pola:

```text
[event, event, event, event]
            ↓
       coalescing window
            ↓
     one bounded evaluation
```

Coalescing harus bounded. Event storm tidak boleh membuat scheduler menghabiskan seluruh waktu CPU untuk mengejar queue.

Jika event queue overflow, scheduler melakukan reconciliation penuh pada waktu yang aman, bukan mencoba memproses event tanpa batas.

---

## 7. Screen Off Bukan Berarti Deep Sleep

Jangan menyamakan:

```text
screen off
    ==
device idle
    ==
deep sleep
```

Ketiganya berbeda.

Screen-off hanya salah satu signal yang dapat digunakan policy.

Scheduler/platform layer tetap perlu mempertimbangkan keadaan seperti:

- interactive state
- charging state
- battery level
- thermal state
- storage pressure
- device-idle/Doze-related state jika tersedia
- mount/storage state
- suspend/resume state jika dapat diamati

Dengan demikian, screen-off dapat menjadi trigger untuk mempertimbangkan cleanup tanpa menjadikan screen-off sebagai alasan untuk menjalankan polling terus-menerus.

---

## 8. Deep Sleep Harus Dipandang Sebagai Kebebasan Sistem untuk Suspend

Daemon tidak perlu membuat mekanisme "sleep sendiri" yang rumit.

Jika thread daemon sedang blocking, tidak ada worker yang spin, dan daemon tidak menahan wakelock, maka daemon sudah berada pada kondisi yang benar untuk membiarkan Android/kernel melakukan suspend.

Targetnya adalah:

```text
resident process
      +
blocked threads
      +
no unnecessary wakelock
      +
no periodic wakeup
```

bukan:

```text
resident process
      +
periodic sleep()
      +
periodic polling
```

Keputusan akhir untuk masuk suspend tetap berada pada Android/kernel dan subsystem wakeup lainnya. Cache cleaner hanya memastikan dirinya sendiri tidak menjadi penghalang.

---

## 9. Wakelock Harus Menjadi Pengecualian

Default daemon:

```text
No wakelock while idle
```

Jika suatu operasi benar-benar memerlukan continuity selama suspend-sensitive work, wake policy harus mempunyai lifecycle yang jelas:

```text
Acquire
   ↓
bounded work
   ↓
verification
   ↓
release immediately
```

Jangan mengambil wakelock ketika daemon startup lalu mempertahankannya selama process hidup.

Untuk cleanup biasa, jangan menganggap wakelock selalu diperlukan. Jika pekerjaan dapat dijalankan ketika device sudah awake dan tidak membutuhkan wake-from-suspend, biarkan Android mengatur power state secara normal.

---

## 10. Scheduled Cleanup Tidak Boleh Menimbulkan Wake Storm

Misalnya jadwal cleanup adalah setiap 6 jam.

Device kemudian tidur selama 24 jam.

Saat resume, daemon tidak boleh membuat:

```text
4 missed ticks
→ 4 cleanup jobs
```

Scheduler cukup melakukan:

```text
resume
  ↓
reconcile schedule
  ↓
coalesce missed occurrences
  ↓
check current policy/readiness
  ↓
create only required job
```

Hal ini konsisten dengan scheduler contract: missed schedule bukan alasan untuk membuat burst pekerjaan.

---

## 11. Clock Harus Suspend-Aware

Android dapat suspend dalam waktu yang cukup lama.

Karena itu scheduler harus membedakan semantics:

- monotonic time
- boottime yang memperhitungkan suspend
- wall clock

Interval internal dan deadline harus memilih clock berdasarkan semantics yang diperlukan.

Jangan membuat keputusan berdasarkan wall clock saja karena perubahan timezone, NTP, user adjustment, atau clock correction dapat menyebabkan schedule drift.

Sebaliknya, jangan menganggap semua monotonic clocks mempunyai perilaku identik selama device suspended.

---

## 12. Resume Harus Ringan, Bukan Full Rebuild

Ketika process tetap hidup dan device kembali dari suspend, resume tidak boleh otomatis berarti:

```text
full config parse
full package enumeration
full mount enumeration
full target scan
full catalog rebuild
```

Urutan yang lebih baik:

```text
Resume
  ↓
periksa perubahan/generation
  ↓
invalidate state yang memang stale
  ↓
refresh subsystem yang affected
  ↓
re-evaluate deferred work
  ↓
return to blocking wait
```

Immutable snapshot yang masih valid boleh dipakai kembali.

Full refresh hanya dilakukan jika event, generation mismatch, recovery, atau safety requirement memang memerlukannya.

---

## 13. Suspend Adalah Revalidation Boundary

Selama device suspended, keadaan dunia dapat berubah tanpa scheduler melihat event satu per satu.

Contohnya:

- mount berubah
- storage dilepas/dipasang
- package berubah
- user/profile berubah
- battery berubah
- thermal state berubah
- system policy berubah
- deadline terlewati

Karena itu resume harus dianggap sebagai batas revalidation.

Tetapi revalidation tidak berarti full scan secara otomatis. Gunakan generation dan change hints untuk menentukan bagian mana yang benar-benar perlu diperbarui.

---

## 14. Fast Wake-up Berarti Jalur Wake yang Pendek

Fast wake-up tidak berarti daemon harus terus aktif untuk mengurangi latency.

Yang lebih tepat adalah mempertahankan struktur runtime yang ringan:

- event loop sudah terinisialisasi
- IPC endpoint sudah tersedia
- scheduler state tersedia
- durable store handle tersedia
- event subscriptions tersedia
- snapshot yang masih valid dapat digunakan kembali

Kemudian ketika event datang, daemon dapat langsung melakukan bounded evaluation.

Dengan demikian:

```text
idle latency rendah
```

dicapai tanpa:

```text
idle CPU activity tinggi
```

---

## 15. Worker Juga Harus Tidur

Masalah idle bukan hanya scheduler.

Worker pool yang tidak mempunyai pekerjaan tidak boleh melakukan:

```rust
loop {
    try_get_work();
}
```

Worker harus menggunakan blocking queue, condition mechanism, semaphore, atau mekanisme park/block lain yang sesuai.

Untuk daemon kecil, jumlah thread sebaiknya minimal. Model yang baik biasanya mendekati:

```text
1 scheduler/event loop
+ worker hanya ketika memang dibutuhkan
```

Jika worker pool bersifat persistent, worker idle harus blocked, bukan runnable.

---

## 16. Resource Manager Tidak Boleh Polling

Resource contention harus dibangunkan oleh perubahan resource, bukan polling.

Contoh:

```text
Worker A releases StorageLock
            ↓
explicit scheduler/resource wakeup
            ↓
Worker B reevaluates eligibility
```

Bukan:

```text
Worker B checks every 1 second
```

Dengan begitu resource waiting tetap efisien tanpa menambah periodic CPU activity.

---

## 17. IPC Harus Blocking

IPC daemon juga merupakan sumber potensial idle activity.

Socket listener harus menunggu secara blocking.

Alurnya:

```text
socket readable
     ↓
parse bounded request
     ↓
submit/query/cancel
     ↓
reply
     ↓
block again
```

Internal scheduler dapat dibangunkan melalui control event seperti `eventfd` atau mekanisme equivalent.

Contoh control event:

```text
manual job
config reload
shutdown
cancellation
resource release
recovery work
```

Tidak diperlukan polling untuk mendeteksi hal tersebut.

---

## 18. Logging dan Metrics Tidak Boleh Menjadi Beban Tersembunyi

Daemon yang idle seharusnya tidak menulis log setiap beberapa detik:

```text
checking...
nothing to do...
sleeping...
```

Log sebaiknya muncul ketika state berubah, terjadi error, job dimulai/selesai, atau event penting lainnya.

Hindari heartbeat file yang ditulis setiap beberapa detik hanya untuk membuktikan process hidup.

Metrics juga harus low-cost. Counter dapat disimpan in-memory dan dipersist/flush secara bounded bila memang diperlukan.

Idle daemon tidak seharusnya menghasilkan filesystem I/O hanya karena ingin mencatat bahwa ia sedang idle.

---

## 19. Hindari Hidden Polling dari Dependency

Audit idle behavior tidak boleh berhenti pada source code daemon.

Dependency atau runtime dapat mempunyai:

- background timer
- metrics exporter
- log flushing loop
- network keepalive
- housekeeping task
- async worker

Karena itu production validation harus melihat behavior process sebenarnya, bukan hanya membaca scheduler implementation.

Jika workload daemon sederhana, synchronous event loop berbasis `poll`/`epoll` dapat menjadi pilihan yang sangat mudah diaudit. Async runtime tetap dapat digunakan jika memang memberikan manfaat, tetapi tidak boleh menambahkan background activity yang tidak dibutuhkan.

---

## 20. Android Platform Event Sources

Platform adapter sebaiknya memanfaatkan event yang memang tersedia untuk perubahan penting seperti:

- power/battery
- screen/interactive state
- thermal state
- mount/storage
- package lifecycle
- user/profile lifecycle
- daemon control

Event hanya merupakan **hint untuk re-evaluation**.

Event tidak menggantikan authoritative snapshot atau final safety check.

Jika event tidak tersedia atau unreliable, sparse reconciliation menjadi safety net.

---

## 21. Doze dan Power Policy Android

Daemon tidak boleh menganggap root privilege sebagai alasan untuk mengabaikan seluruh power policy Android.

Jika cleanup bersifat optional, scheduler sebaiknya dapat menunda pekerjaan ketika power/thermal conditions tidak mendukung.

Jika requirement memang mengharuskan cleanup membangunkan device dari suspend, mekanisme wake-from-suspend harus berasal dari platform scheduling/wakeup mechanism yang mempunyai semantics tersebut. Ordinary process timer bukan jaminan bahwa process dapat membangunkan device dari suspend.

Default untuk cache cleaner sebaiknya konservatif:

```text
jangan membangunkan device hanya karena cleanup belum dilakukan
```

Biarkan cleanup dilakukan ketika device kembali aktif, atau gunakan explicit emergency policy jika kebutuhan produk memang membenarkannya.

---

## 22. Storage Pressure Bukan Alasan untuk Polling

Storage pressure adalah trigger yang bernilai tinggi.

Jika platform dapat memberikan signal pressure, gunakan signal tersebut untuk membangunkan scheduler.

Tidak perlu:

```text
check free space every 5 seconds
```

Jika pressure event hilang, periodic reconciliation yang sparse dapat menjadi fallback.

Emergency cleanup yang benar-benar membutuhkan wake-from-suspend harus menjadi capability dan policy tersendiri, bukan efek samping dari scheduler biasa.

---

## 23. Thermal dan Battery Harus Mengurangi Aktivitas, Bukan Menambah Polling

Ketika thermal state tinggi, scheduler dapat menunda optional cleanup dan memperpanjang reconciliation interval.

Ketika battery rendah, optional cleanup dapat ditunda sesuai policy.

Ketika device mulai charging, charging event dapat menjadi trigger untuk reevaluasi.

Tidak boleh menggunakan kondisi tersebut sebagai alasan untuk melakukan polling battery/thermal setiap detik.

---

## 24. Cancellation dan Shutdown Harus Bisa Membangunkan Scheduler

Blocking event loop tetap harus bisa dihentikan dengan cepat.

Jangan bergantung pada timeout polling panjang untuk shutdown.

Gunakan explicit control event:

```text
shutdown request
      ↓
wake blocked scheduler
      ↓
stop admission
      ↓
drain/cancel according to lifecycle
      ↓
shutdown workers
```

Hal yang sama berlaku untuk cancellation ketika worker sedang menunggu resource atau event.

Power-efficient bukan berarti lambat berhenti.

---

## 25. Wakeup Budget dan Regression Detection

Power behavior perlu dapat diukur.

Secara konseptual scheduler dapat memiliki telemetry seperti:

```rust
struct WakeupStats {
    wakeups: u64,
    evaluations: u64,
    cpu_time: Duration,
    unexpected_wakeups: u64,
}
```

Telemetry ini bukan authorization atau policy boundary. Tujuannya mendeteksi regression seperti scheduler yang tiba-tiba berubah dari event-driven menjadi polling.

Perhatikan bahwa:

```text
CPU percentage rendah
```

belum tentu berarti:

```text
power behavior bagus
```

Daemon yang menggunakan 0.00% CPU tetapi membangunkan CPU setiap 5 detik masih dapat lebih buruk daripada daemon yang menggunakan sedikit CPU sekali setelah event penting.

Metric yang lebih bermakna mencakup:

- CPU time
- wakeup count
- wake duration
- filesystem I/O
- thread activity
- suspend/deep-idle residency jika dapat diukur
- wakelock/wakeup-source behavior

---

## 26. Pengujian Idle di Android Nyata

Idle power tidak cukup diuji di unit test.

Minimal ada scenario:

```text
Daemon start
↓
No job
↓
No event
↓
No recovery
↓
No imminent deadline
↓
Screen off
↓
Long idle
```

Periksa bahwa:

- scheduler thread blocked
- worker blocked/absent
- tidak ada busy loop
- tidak ada periodic filesystem scan
- tidak ada periodic config reload
- tidak ada periodic package enumeration
- tidak ada heartbeat write
- tidak ada unexpected wakelock
- tidak ada wakeup storm

Test harus cukup panjang untuk menangkap timer tersembunyi, misalnya puluhan menit sampai beberapa jam atau overnight untuk device test tertentu.

---

## 27. Cara Membuktikan Bahwa Daemon Benar-Benar Idle

Jangan hanya menggunakan `top`.

`top` atau CPU percentage berguna, tetapi tidak menjawab pertanyaan tentang wakeup.

Gunakan instrumentation yang sesuai dengan platform untuk melihat:

- repeated `poll` timeout
- repeated `nanosleep`
- timerfd expiration
- futex wakeup
- repeated `/proc` access
- repeated `/sys` access
- filesystem I/O
- socket traffic
- thread scheduling
- kernel wakeup source
- suspend/resume behavior

Android-specific tracing/power tooling dapat digunakan pada device test untuk memeriksa apakah daemon benar-benar membiarkan sistem mempertahankan deep idle.

---

## 28. Acceptance Test: Tidak Ada Pekerjaan

Scenario:

```text
no pending job
no recovery
no event
no imminent deadline
```

Expected:

```text
scheduler blocked
workers blocked
IPC blocked
no periodic scan
no periodic config read
no periodic package read
no periodic mount read
no heartbeat write
no wakelock retained
```

CPU activity hanya boleh muncul akibat external event, OS activity, atau observability yang memang dibutuhkan.

---

## 29. Acceptance Test: Event Membuat Daemon Bangun

Scenario:

```text
idle
 ↓
manual cleanup request
```

Expected:

```text
control event
 ↓
one scheduler wake
 ↓
admission
 ↓
normal Job lifecycle
```

Scheduler tidak perlu menunggu polling interval.

Setelah pekerjaan selesai dan tidak ada pekerjaan lain:

```text
return to blocking wait
```

---

## 30. Acceptance Test: Resume dari Suspend

Scenario:

```text
device idle
 ↓
deep sleep/suspend
 ↓
resume
```

Expected:

```text
resume detection
 ↓
lightweight state/generation check
 ↓
revalidate stale assumptions
 ↓
refresh only affected data
 ↓
run cleanup only if currently eligible
 ↓
return to blocking wait
```

Resume tidak boleh otomatis menghasilkan full catalog rebuild tanpa alasan.

---

## 31. Acceptance Test: Long Scheduled Interval

Scenario:

```text
cleanup interval = several hours
screen off
no relevant events
```

Expected:

```text
scheduler waits
```

Bukan:

```text
wake → check → sleep
wake → check → sleep
wake → check → sleep
```

Jika device suspended melewati deadline, scheduler cukup melakukan satu reconciliation setelah resume dan menerapkan misfire/coalescing policy.

---

## 32. Production Invariants

Ketika daemon tidak mempunyai pekerjaan yang eligible:

1. Scheduler tidak busy-loop.
2. Tidak ada aggressive periodic polling.
3. Tidak ada periodic filesystem scan.
4. Tidak ada periodic package enumeration.
5. Tidak ada periodic mount enumeration tanpa requirement.
6. Tidak ada periodic config parsing hanya untuk polling perubahan.
7. Tidak ada heartbeat file write untuk sekadar liveness.
8. Worker tidak spin.
9. Resource manager tidak polling.
10. IPC menunggu secara blocking.
11. Tidak ada wakelock yang dipertahankan hanya karena process hidup.
12. Tidak ada wakeup yang dibuat hanya untuk memastikan "belum waktunya".
13. Event burst dicoalesce.
14. Periodic reconciliation bersifat sparse dan adaptive.
15. Tidak ada deadline berarti tidak ada timer yang diperlukan.

Ketika device suspend/resume:

1. Daemon tidak menghalangi suspend.
2. Resume menjadi revalidation boundary.
3. Resume tidak otomatis berarti full scan.
4. Snapshot yang masih valid dapat digunakan kembali.
5. Hanya state yang stale yang di-refresh jika memungkinkan.
6. Missed schedules dicoalesce.
7. Cleanup tidak otomatis diberi hak untuk membangunkan device.
8. Wake-from-suspend hanya digunakan jika explicit product/policy requirement membutuhkannya.
9. Setelah evaluasi selesai, daemon kembali blocking.

---

## 33. Definition of Done

Power behavior dianggap production-ready jika:

- idle scheduler benar-benar blocking
- tidak ada busy polling
- tidak ada unnecessary periodic wakeup
- event-driven scheduling menjadi mekanisme utama
- reconciliation hanya menjadi fallback consistency mechanism
- tidak ada wakelock retention saat idle
- worker dan resource wait juga blocking
- IPC tidak polling
- logging/metrics tidak menghasilkan idle I/O berlebihan
- dependency/runtime background activity telah diaudit
- suspend/resume diperlakukan dengan benar
- scheduled cleanup tidak menghasilkan missed-tick storm
- resume path ringan dan generation-aware
- actual Android device test mengukur CPU time dan wakeup behavior secara terpisah
- regression test dapat mendeteksi scheduler yang berubah menjadi polling

---

## 34. Prinsip Akhir

Daemon yang baik bukan daemon yang terus-menerus bangun untuk memastikan dirinya siap.

Daemon yang baik adalah daemon yang **benar-benar tidak melakukan apa-apa ketika memang tidak ada yang perlu dilakukan**, tetapi tetap dapat merespons event yang relevan tanpa delay yang tidak perlu.

```text
                 NO WORK
                    │
                    ▼
           No runnable activity
                    │
                    ▼
             Blocking wait
                    │
              No wakelock
                    │
                    ▼
        Android free to suspend
                    │
               Deep idle
                    │
        ┌───────────┴───────────┐
        │                       │
   Relevant event          Real deadline
        │                       │
        └───────────┬───────────┘
                    ▼
             Fast bounded wake
                    │
                    ▼
           Evaluate current state
                    │
             ┌──────┴──────┐
             │             │
          Not ready      Eligible
             │             │
             ▼             ▼
          Wait again    Run Job
                           │
                           ▼
                        Verify
                           │
                           ▼
                    Back to blocking
```

**Target akhirnya bukan sekadar `CPU ≈ 0%`. Targetnya adalah `no unnecessary work, no unnecessary wakeup, no unnecessary wakelock`, sehingga Android bebas mempertahankan deep sleep selama mungkin dan daemon tetap cepat ketika benar-benar dibutuhkan.**
