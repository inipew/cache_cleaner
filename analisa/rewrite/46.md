46.md — Safety Policy Interaction, Decision Precedence, Protected Targets, Deny Rules, Policy Exceptions, and Formal Eligibility Contract

Tujuan

Dokumen ini mendefinisikan kontrak formal antara Safety Layer dan Policy Engine.

Fokus utama:

Safety harus selalu menjadi boundary keamanan yang tidak dapat dilewati Policy.

Policy menentukan apakah object yang sudah lolos safety layak diproses berdasarkan aturan maintenance.

Protected Target, deny rule, exception, dan allow rule harus memiliki precedence yang deterministik.

Tidak boleh ada kombinasi rule yang secara tidak sengaja mengubah object berbahaya menjadi object yang eligible.

Kontrak akhir:

Candidate
│
▼
Safety Validation
│
├── SafetyRejected ───────────────► STOP
│
▼
SafetyValidatedCandidate
│
▼
Policy Evaluation
│
├── Rejected ─────────────────────► STOP
├── Excluded ─────────────────────► STOP
├── Deferred ─────────────────────► WAIT / RETRY
│
▼
PolicyApprovedCandidate
│
▼
Planner
│
▼
Authorization
│
▼
Executor

1. Prinsip Fundamental

Safety dan Policy bukan dua lapisan yang setara.

Safety menjawab:

"Apakah object ini aman untuk dipertimbangkan?"

Policy menjawab:

"Jika aman, apakah object ini memang ingin kita maintenance?"

Dengan demikian:

Safety = security boundary

Policy = maintenance decision

Safety tidak boleh diperlunak oleh Policy.

Policy tidak boleh memperkuat hak akses Safety.

Policy tidak boleh mengubah object yang SafetyRejected menjadi PolicyApproved.

Contoh:

Object berada di luar TrustedRoot.

Safety:
Rejected

Policy:
Allow

Hasil akhir:
Rejected

2. Formal Model

Untuk setiap Candidate terdapat dua keputusan utama:

SafetyDecision
PolicyDecision

SafetyDecision:

```
Valid
Rejected
Stale
Changed
AlreadyGone
TypeChanged
MountChanged
IdentityChanged
RootInvalid
BoundaryViolation
Unknown
```

PolicyDecision:

```
Eligible
Excluded
Deferred
Rejected
```

Keduanya kemudian dikombinasikan oleh Decision Combiner.

3. Decision Combiner

Decision Combiner adalah fungsi deterministik:

combine(SafetyDecision, PolicyDecision)
-> EligibilityDecision

Safety selalu memiliki precedence lebih tinggi.

Model konseptual:

SafetyRejected
│
└──► FinalRejected

SafetyStale
│
└──► FinalStale

SafetyChanged
│
└──► FinalStale

SafetyValid
│
▼
PolicyDecision
│
├── Rejected ──► FinalRejected
├── Excluded ──► FinalExcluded
├── Deferred ──► FinalDeferred
└── Eligible ──► FinalEligible

4. Formal Eligibility Contract

Sebuah Candidate hanya boleh menjadi eligible apabila seluruh mandatory predicate terpenuhi.

Secara konseptual:

Eligible(Candidate) =
SafetyValid
AND
PolicyAllows
AND
ScopeAllowed
AND
TargetAllowed
AND
UserAllowed
AND
PackageAllowed
AND
AgeAllowed
AND
NotProtected
AND
NoExplicitDeny
AND
RuntimeConditionsSatisfied

5. Safety Predicate

Safety predicate harus dievaluasi sebelum Policy.

SafetyValid berarti:

```
TrustedRoot valid
AND path tetap berada dalam boundary
AND object identity valid
AND object type sesuai
AND filesystem boundary valid
AND symlink policy terpenuhi
AND mount boundary terpenuhi
AND parent traversal valid
AND object belum berubah secara unsafe
```

Jika salah satu mandatory safety predicate gagal:

```
Candidate != Eligible
```

6. Policy Predicate

Policy hanya berjalan terhadap object yang sudah memiliki SafetyValidatedCandidate.

Policy tidak boleh menerima:

```
raw path
arbitrary filesystem path
unchecked inode reference
unchecked symlink
unchecked mount
raw dirent
```

Policy menerima domain object yang sudah tervalidasi.

7. Safety Tidak Boleh Dipanggil "Optional"

Arsitektur berikut dilarang:

Candidate
│
├──► Policy
│
└──► Safety
│
▼
Executor

Karena Policy dapat menghasilkan allow sebelum safety selesai.

Arsitektur wajib:

Candidate
│
▼
Safety
│
▼
SafetyValidatedCandidate
│
▼
Policy

8. Policy Tidak Boleh Menjadi Safety Layer

Arsitektur berikut juga dilarang:

Policy:
if path starts_with("/data/user/0")
allow

Karena Policy tidak memiliki otoritas untuk menentukan filesystem boundary.

Path classification bukan pengganti TrustedRoot.

Policy boleh mengetahui:

```
TargetId
PackageId
UserId
TargetClass
metadata snapshot
```

Policy tidak boleh melakukan:

```
open()
stat()
lstat()
unlink()
mount inspection
raw path traversal
```

9. Protected Target

Protected Target adalah target yang secara eksplisit tidak boleh diproses oleh cleanup engine.

Contoh konseptual:

```
system-critical
package metadata
runtime state
security-sensitive storage
platform-managed data
unknown critical target
```

Protected status harus berasal dari trusted configuration/catalog/platform knowledge.

Client tidak boleh menentukan sendiri:

```
protected = false
```

10. Protected Target Memiliki Precedence Tinggi

Jika:

```
Safety = Valid
Policy = Allow
Target = Protected
```

Maka:

```
Final = Excluded
```

11. Protected Target Tidak Boleh Di-Override

Konfigurasi berikut dilarang:

```
protected_target = false
```

jika protected status berasal dari immutable platform invariant.

Perbedaan penting:

Configurable protection:
dapat berubah melalui validated policy configuration

Platform invariant:
tidak dapat dihapus oleh configuration

Contoh:

PlatformInvariantProtected
> ConfiguredAllow

12. Protected Package

Package tertentu dapat memiliki protection.

Protection dapat berdasarkan:

```
PackageId
UID mapping
target class
platform role
system classification
```

Policy tidak boleh menerima arbitrary package name sebagai trusted identity.

Package identity harus berasal dari CatalogSnapshot.

13. Unknown Package

Unknown package identity tidak boleh dianggap safe.

Jika package ownership diperlukan untuk eligibility:

```
Unknown package
    │
    ▼
Deferred atau Excluded
```

Bukan:

```
Unknown package
    │
    ▼
Allow
```

14. Unknown Target

Target yang tidak dikenal tidak boleh diperlakukan sebagai generic cache.

Default:

```
UnknownTarget
    │
    ▼
Excluded
```

15. Deny Rule

Deny rule adalah aturan yang secara eksplisit melarang eligibility.

Contoh konseptual:

```
Deny(TargetClass::Protected)
Deny(PackageId::ProtectedPackage)
Deny(UserId::LockedUser)
Deny(SharedStorage)
Deny(UnknownOwnership)
```

Deny rule tidak melakukan mutation.

Deny rule hanya menghasilkan decision.

16. Deny Rule vs Safety Rejection

Keduanya berbeda.

Safety:

```
"Object tidak aman untuk disentuh."
```

Policy deny:

```
"Object aman secara teknis, tetapi tidak boleh dibersihkan."
```

Contoh:

Symlink escape:
SafetyRejected

Cache milik protected package:
SafetyValid
PolicyExcluded

17. Explicit Deny Harus Menang Atas Allow

Jika:

```
Allow(target)
Deny(package)
```

Maka:

```
Deny
```

18. Exception

Policy exception adalah mekanisme untuk mengubah default eligibility secara terbatas.

Contoh:

Default:
SharedCache = Excluded

Exception:
package X dapat dibersihkan

Namun exception tidak boleh mengubah Safety.

Exception hanya dapat mempengaruhi Policy.

Model:

SafetyValid
│
▼
DefaultPolicy
│
▼
ExceptionEvaluation
│
▼
PolicyDecision

19. Exception Tidak Boleh Memperluas Security Boundary

Contoh dilarang:

```
exception:
    root = "/"
```

Exception tidak boleh:

```
mengubah TrustedRoot
mengaktifkan symlink traversal
mengizinkan mount crossing
mengabaikan identity
mengabaikan object type
bypass final safety gate
```

20. Exception Harus Scope-Bounded

Exception harus memiliki scope eksplisit.

Contoh:

```
target_id
package_id
user_id
target_class
```

Semakin luas scope exception, semakin tinggi risiko konfigurasi.

Default harus:

```
narrow scope
```

21. Exception Tidak Boleh Menggunakan Arbitrary Path

Dilarang:

```
exception.path = "/some/arbitrary/path"
```

Gunakan:

```
exception.target_id = TargetId(...)
```

TargetId kemudian di-resolve melalui CatalogSnapshot.

22. Exception Tidak Boleh Membuat Target Baru

Policy exception tidak boleh membuat:

```
TargetId baru
TrustedRoot baru
filesystem boundary baru
```

Exception hanya memilih dari domain object yang sudah diketahui.

23. Exception Precedence

Baseline precedence:

```
Safety failure
    >
Platform invariant protection
    >
Explicit deny
    >
Explicit protection
    >
Exception constraints
    >
Default policy
    >
Allow
```

24. Formal Decision Precedence

Urutan final yang direkomendasikan:

1. Safety failure

2. Invalid generation/snapshot

3. Platform invariant protection

4. Explicit deny

5. Protected target

6. Scope restriction

7. Runtime defer condition

8. Explicit exception

9. Normal allow rule

10. Default decision

11. Default Decision

Default policy harus konservatif.

Jika tidak ada rule yang cocok:

```
Default = Excluded
```

Bukan:

```
Default = Eligible
```

26. Unknown Condition

Jika policy membutuhkan data yang tidak tersedia:

```
Unknown != Allow
```

Contoh:

minimum age membutuhkan timestamp.

Timestamp tidak tersedia.

Hasil:

```
Deferred
```

atau
Excluded

tergantung apakah informasi kemungkinan tersedia kemudian.

27. Deferred

Deferred digunakan jika kondisi dapat berubah secara legitimate.

Contoh:

```
user locked
device busy
runtime not ready
timestamp unavailable temporarily
storage state unstable
```

Deferred berarti:

```
"Belum saatnya membuat keputusan final."
```

28. Excluded

Excluded berarti:

```
"Object ini tidak termasuk target cleanup menurut policy."
```

Contoh:

```
shared storage
protected package
target class excluded
object terlalu baru
```

29. Rejected

Rejected berarti:

```
"Permintaan atau object melanggar invariant yang tidak boleh diteruskan."
```

Contoh:

```
invalid policy
invalid target scope
impossible policy state
safety contract violation
```

30. Perbedaan Excluded dan Rejected

Excluded:

```
valid object
valid scope
policy memilih tidak memproses
```

Rejected:

```
sesuatu melanggar contract
tidak boleh diteruskan
```

Deferred:

```
valid tetapi kondisi belum memungkinkan
```

31. Decision Lattice

Model sederhana:

```
                Safety Failure
                     │
                     ▼
                 REJECTED
                     │
          ┌──────────┴──────────┐
          │                     │
      Safety Valid         Safety Stale
          │                     │
          ▼                     ▼
    Policy Evaluation        STALE
          │
   ┌──────┼───────┐
   │      │       │
Reject Exclude Deferred
   │      │       │
   └──────┴───────┘
          │
          ▼
        Allow
          │
          ▼
       ELIGIBLE
```

32. Policy Approval Tidak Sama Dengan Authorization

Policy:

```
"Object layak dibersihkan."
```

Authorization:

```
"Job/actor ini memiliki authority untuk menjalankan operation tersebut."
```

Maka:

PolicyApprovedCandidate
!=
AuthorizedOperation

33. Policy Approval Tidak Sama Dengan Execution Permission

Walaupun:

```
Policy = Eligible
```

Executor tetap tidak boleh langsung menerima Candidate.

Flow:

PolicyApprovedCandidate
│
▼
Planner
│
▼
PlannedOperation
│
▼
Authorization
│
▼
AuthorizedPlan
│
▼
Executor

34. Policy Cannot Override Planner Safety

Planner tidak boleh mengatakan:

```
"Policy allowed, therefore delete."
```

Planner hanya menyusun operation graph.

Final safety tetap dilakukan oleh Executor.

35. Policy Decision Must Be Immutable

PolicyDecision harus immutable setelah dibuat.

Tidak boleh:

```
decision.allow()
decision.deny()
```

setelah object digunakan oleh Planner.

Gunakan value object:

```
PolicyDecision
```

36. Policy Decision Metadata

PolicyDecision minimal memiliki:

```
decision
rule_id
reason_code
policy_generation
target_id
package_id
user_id
evaluation_context_hash
```

Jika diperlukan:

```
exception_id
matched_rule
defer_until
explanation
```

37. Rule ID

Setiap rule harus memiliki stable identifier.

Contoh:

```
policy.target.protected
policy.package.excluded
policy.age.minimum
policy.user.locked
policy.shared_storage.default_deny
```

38. Reason Code

Reason code harus machine-readable.

Contoh:

```
PROTECTED_TARGET
EXPLICIT_DENY
MINIMUM_AGE_NOT_REACHED
USER_LOCKED
UNKNOWN_OWNERSHIP
SHARED_STORAGE
POLICY_EXCEPTION
RUNTIME_NOT_READY
```

39. Human Explanation

Reason code dapat diterjemahkan menjadi penjelasan untuk user.

Contoh:

```
PROTECTED_TARGET
```

menjadi:

```
"Target ditandai sebagai protected dan tidak dapat dibersihkan oleh policy ini."
```

40. Explanation Tidak Boleh Mengubah Decision

Explain API hanya membaca decision.

Tidak boleh:

```
ExplainRequest
    └──► change policy
    └──► retry with override
    └──► bypass protection
```

41. Deterministic Evaluation

Untuk snapshot dan input yang sama:

```
evaluate(C, P)
    ==
evaluate(C, P)
```

Tidak boleh bergantung pada:

```
random
wall-clock current time secara implisit
filesystem query
global mutable state
thread scheduling
```

42. Time Semantics

Jika policy menggunakan waktu:

```
now
```

harus berasal dari evaluation context.

Contoh:

```
EvaluationContext {
    monotonic_now
    wall_clock_now
}
```

Dengan demikian test dapat menggunakan FakeClock.

43. Minimum Age

Jika:

```
object_time = T
now = N
minimum_age = A
```

Maka:

```
eligible_age = (N - T) >= A
```

44. Clock Anomaly

Jika:

```
object_time > now
```

jangan langsung menganggap object eligible.

Default:

```
Deferred
```

atau
Excluded

tergantung policy contract.

Konservatif lebih diutamakan.

45. Timestamp Tidak Diketahui

Jika timestamp diperlukan tetapi:

```
timestamp = Unknown
```

maka:

```
Unknown != Eligible
```

46. Negative Age

Jika:

```
now < object_time
```

maka age negatif.

Object tidak boleh dibersihkan hanya karena perhitungan unsigned atau overflow.

Arithmetic harus checked.

47. Integer Overflow

Policy evaluation tidak boleh memiliki:

```
unchecked addition
unchecked duration conversion
unchecked size multiplication
```

Semua arithmetic budget/time harus bounded.

48. Rule Composition

Rule dapat dikomposisikan:

```
ALL
ANY
NOT
```

Contoh:

```
ALL(
    TargetIsAppCache,
    AgeAtLeast(7d),
    PackageNotProtected
)
```

49. Default Composition

Operator harus memiliki semantics deterministik.

ALL:

```
satu false
    -> false
```

ANY:

```
satu true
    -> true
```

NOT:

```
true -> false
false -> true
```

Unknown harus memiliki semantics eksplisit.

50. Unknown Propagation

Untuk security-sensitive predicates:

```
Unknown
    !=
True
```

Contoh:

```
PackageProtected = Unknown
```

maka:

```
NOT PackageProtected
```

tidak boleh otomatis menjadi True.

51. Three-Valued Logic

Policy internal dapat menggunakan:

```
True
False
Unknown
```

Namun mapping ke final decision harus eksplisit.

Contoh:

```
True  -> Allow candidate
False -> Exclude
Unknown -> Deferred
```

Untuk invariant protection:

```
Unknown -> Exclude
```

52. Exception Evaluation

Exception harus dievaluasi setelah mandatory deny/protection predicates.

Contoh:

```
ProtectedTarget
    │
    ▼
Exception
    │
    X
```

Exception tidak dapat override ProtectedTarget jika protection adalah platform invariant.

53. Configurable Protection

Jika protection berasal dari konfigurasi user, maka konfigurasi dapat menentukan:

```
protected package
excluded target
custom deny
```

Namun configuration validator harus memastikan tidak ada rule yang mengubah immutable platform invariant.

54. Immutable Platform Rules

Platform invariant dapat berupa:

```
CE locked storage protection
SELinux boundary
TrustedRoot boundary
kernel-enforced restrictions
protected system target
```

Policy tidak memiliki authority untuk mengubahnya.

55. Rule Priority

Priority integer boleh digunakan untuk ordering internal.

Tetapi security semantics tidak boleh bergantung hanya pada:

```
priority = 100
priority = 99
```

Lebih aman menggunakan rule class precedence.

Contoh:

```
SafetyInvariant
ProtectedInvariant
ExplicitDeny
Exclusion
Exception
Allow
```

56. No Priority Abuse

Config berikut harus ditolak:

```
allow_rule.priority = 999999
deny_rule.priority = 1
```

jika priority tersebut dapat membuat allow mengalahkan mandatory protection.

57. Rule Conflict

Jika dua rule menghasilkan:

```
Allow
Exclude
```

maka conflict resolver harus deterministic.

Baseline:

```
Exclude wins.
```

58. Allow vs Defer

Jika:

```
Allow
DeferredCondition
```

maka:

```
Deferred
```

karena kondisi mandatory belum terpenuhi.

59. Deny vs Defer

Jika:

```
Deny
Deferred
```

maka:

```
Deny
```

Karena defer tidak boleh menghidupkan kembali object yang memang dilarang.

60. Protection vs Exception

Jika:

```
Protected
ExceptionAllow
```

maka:

```
Excluded
```

jika protection bersifat invariant.

61. Safety vs Exception

Jika:

```
SafetyRejected
ExceptionAllow
```

maka:

```
Rejected
```

Selamanya.

Tidak ada policy exception yang dapat mengubah safety result.

62. Formal Combiner

Secara konseptual:

```
final =
    if safety != Valid:
        mapSafety(safety)

    else if platformInvariantViolation:
        Rejected

    else if explicitDeny:
        Excluded

    else if protected:
        Excluded

    else if deferredCondition:
        Deferred

    else if exceptionAllows:
        Eligible

    else if normalPolicyAllows:
        Eligible

    else:
        Excluded
```

63. Candidate Identity

Policy decision harus tetap terikat dengan Candidate identity.

Minimal:

```
TargetId
PackageId
UserId
RelativePath
object identity snapshot
```

Policy tidak boleh menghasilkan keputusan yang kemudian dipakai untuk object berbeda.

64. Snapshot Binding

Policy decision harus membawa:

```
ConfigGeneration
CatalogGeneration
PlatformGeneration
```

Contoh:

```
PolicyDecision {
    config_generation = 17
    catalog_generation = 22
    platform_generation = 9
}
```

65. Generation Mismatch

Jika Planner menerima:

```
PolicyDecision(config=17)
```

tetapi job sekarang menggunakan:

```
config=18
```

maka decision dianggap stale.

Jangan silently reuse.

66. Config Reload

Saat configuration reload:

```
OldConfig
    │
    ▼
Validate
    │
    ▼
NewConfig
    │
    ▼
NewGeneration
```

Active job:

```
tetap menggunakan snapshot lama
```

New job:

```
menggunakan snapshot baru
```

67. Failed Config Reload

Jika configuration baru invalid:

```
OldConfig remains active
```

Jangan:

```
partially apply config
clear active policy
switch to permissive defaults
```

68. Safe Failure

Jika Policy Engine gagal:

```
no PolicyApprovedCandidate
```

Result:

```
Failed
```

atau
Deferred

berdasarkan failure class.

Tidak boleh:

```
PolicyError -> Allow
```

69. Policy Engine Side Effect

Policy evaluation harus zero-side-effect.

Tidak boleh:

```
delete
rename
chmod
chown
mount
write sysfs
change zram
invoke shell
mutate global state
```

70. Filesystem Access

Policy Engine tidak boleh melakukan filesystem access.

Jika membutuhkan metadata:

```
Scanner
    │
    ▼
Candidate.metadata
```

Jika metadata tidak tersedia:

```
Unknown / Deferred / Excluded
```

71. Network Access

Policy Engine tidak boleh membutuhkan network.

Decision tidak boleh bergantung pada:

```
DNS
remote API
HTTP service
external policy server
```

untuk baseline cleanup authorization.

72. Environment Variables

Policy tidak boleh menggunakan environment variable sebagai hidden override.

Dilarang:

```
CACHE_CLEANER_FORCE=1
```

yang mengubah safety/policy semantics.

73. Debug Override

Debug mode tidak boleh memiliki kemampuan:

```
bypass safety
bypass protected target
bypass authorization
```

Debug hanya boleh meningkatkan:

```
logging
tracing
explainability
test instrumentation
```

74. Test Override

Test fixture boleh membuat synthetic Candidate.

Tetapi production constructor harus tetap private atau validated.

Jangan membuat public API:

```
Candidate::unsafe_from_path()
```

75. Formal Type Boundary

Idealnya domain menggunakan type-state:

```
Candidate
    │
    ▼
SafetyValidatedCandidate
    │
    ▼
PolicyApprovedCandidate
    │
    ▼
PlannedOperation
    │
    ▼
AuthorizedOperation
```

76. Unsafe Conversion

Conversion berikut harus tidak tersedia:

```
Candidate -> PolicyApprovedCandidate
```

Tanpa Safety validation.

Dan:

```
SafetyValidatedCandidate -> AuthorizedOperation
```

Tanpa Planner + Authorization.

77. Policy Output

Policy Engine hanya boleh menghasilkan:

```
PolicyDecision
PolicyApprovedCandidate
PolicyExplanation
```

78. Planner Input

Planner menerima:

```
PolicyApprovedCandidate
```

Bukan:

```
Candidate + PolicyDecision
```

secara terpisah jika kombinasi tersebut memungkinkan mismatch.

Lebih aman:

```
PolicyApprovedCandidate {
    candidate
    decision_proof
}
```

79. Decision Proof

Decision proof bukan cryptographic proof.

Ia adalah immutable binding bahwa:

```
Candidate
+ PolicySnapshot
+ EvaluationContext
```

telah menghasilkan:

```
Eligible
```

80. PolicyApprovedCandidate Contract

PolicyApprovedCandidate harus memastikan:

```
safety validated
policy eligible
generation matched
identity preserved
target scope preserved
decision immutable
```

81. No Planner Override

Planner tidak boleh mengubah:

```
eligibility
protected status
policy decision
```

Jika planner menemukan candidate tidak valid:

```
reject plan construction
```

82. Partial Policy Failure

Jika 1 candidate mengalami policy evaluation error:

```
jangan otomatis menggagalkan seluruh scan
```

kecuali error tersebut menunjukkan:

```
policy snapshot corrupt
rule engine invariant broken
generation mismatch global
```

Candidate-local uncertainty dapat:

```
Excluded
```

atau
Deferred

83. Global Policy Failure

Jika EffectivePolicy invalid:

```
seluruh job tidak boleh melakukan destructive planning.
```

Flow:

```
EffectivePolicy invalid
    │
    ▼
Job Failed
```

84. Rule Engine Panic

Policy engine panic dianggap fatal untuk evaluation context.

Jangan recover dengan:

```
allow all
```

Lebih aman:

```
fail closed
```

85. Bounded Evaluation

Policy engine harus memiliki budget:

```
max_rules
max_expression_depth
max_operations
max_string_length
max_exception_count
```

Tujuan:

```
malformed policy tidak dapat menyebabkan CPU/memory exhaustion.
```

86. Rule Recursion

Rule tidak boleh memiliki recursive expansion tanpa bound.

Dilarang:

```
A -> B
B -> C
C -> A
```

Validator harus mendeteksi cycle.

87. Rule Graph

Jika rule references rule lain:

```
Rule A
   │
   ▼
Rule B
   │
   ▼
Rule C
```

harus berbentuk DAG.

Cycle:

```
reject configuration
```

88. Rule Compilation

```
textual rules
```

harus diproses menjadi:

```

    │
    ▼
ValidatedPolicy
    │
    ▼

    │
    ▼
EffectivePolicy
```

89. Policy Validation

```

90. Duplicate Rule ID

Contoh:

```

policy.age.minimum
```

Tidak boleh menghasilkan ambiguity.

91. Duplicate Exception ID

Sama untuk:

```

```

92. Exception Expiration

Exception dapat memiliki:

```
expires_at
```

Setelah expiration:

```
exception tidak berlaku
```

Expired exception tidak boleh diam-diam menjadi allow.

93. Exception Scope

Exception harus menyatakan scope:

```
target
package
user
operation class
```

Scope yang terlalu luas harus ditolak atau membutuhkan explicit administrative configuration.

94. Exception Audit

```

rule_id
generation
decision
timestamp
```

95. No Hidden Exceptions

Exception tidak boleh disisipkan dari:

```
environment
debug flag
IPC field
CLI undocumented option
```

Semua exception harus berasal dari validated policy.

96. CLI

CLI hanya boleh meminta:

```
explain

```

CLI tidak boleh mengirim:

```
force_policy_allow

```

97. IPC

```
"override = true"
```

yang memiliki semantics:

```

```

IPC hanya dapat meminta operation yang tersedia berdasarkan server-side authorization.

98. Scheduler

109. Property: Safety Dominance

Property test:

```
SafetyRejected + any PolicyDecision
    ==
not eligible
```

```

    ==
Excluded
```

Jika invariant protected:

```

    ==
Excluded
```

112. Property: Unknown Conservative

```

```

```

```

```

```

```

115. Property: Generation Binding

PolicyDecision generation N tidak boleh diterima pada PolicySnapshot generation M.

Jika:

```

```

hasil:

```

```

116. Property: Monotonic Safety

Jika Candidate menjadi kurang safe:

```
Eligible -> non-Eligible
```

Tidak boleh:

```

```

karena perubahan safety.

117. Property: Adding Deny Rule

Jika sebuah deny rule ditambahkan:

```

```

Tidak boleh:

```

```

118. Property: Removing Allow Rule

Menghapus allow rule tidak boleh membuat candidate yang sebelumnya protected menjadi eligible.

119. Property: Exception Locality

Menambahkan exception untuk Candidate A tidak boleh mengubah decision Candidate B yang berada di luar scope.

120. Property: No Filesystem Side Effect
