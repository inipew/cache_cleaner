# 93.md — Durable Schema Evolution, Migration, dan Compatibility

## Tujuan

Durable state membuat daemon restart-safe, tetapi durable state juga hidup lebih lama daripada satu binary. Upgrade aplikasi, rollback, perubahan schema, dan perubahan semantics harus dapat dilakukan tanpa kehilangan recovery evidence atau membuat daemon menjalankan mutation berdasarkan state yang salah.

Prinsipnya:

```text
old durable state
      ↓
validate version
      ↓
migrate/interpret
      ↓
new durable model
      ↓
verify invariants
      ↓
start normal execution
```

## 1. Schema Version Adalah Explicit

Setiap durable schema harus memiliki version.

Jangan mengandalkan binary version sebagai implicit schema version.

## 2. Binary Version vs Schema Version

Bedakan:

```text
BinaryVersion
SchemaVersion
PlanVersion
ProtocolVersion
```

Keempatnya dapat berubah secara independen.

## 3. Migration Sebelum Mutation

Jika durable state belum compatible, daemon tidak boleh langsung menjalankan destructive work.

Urutan:

```text
open store
→ validate
→ migrate
→ integrity check
→ normal startup
```

## 4. Transactional Migration

Migration yang dapat mengubah banyak records harus transactional jika database mendukungnya.

Jika migration gagal di tengah jalan, state harus kembali ke valid old/new schema, bukan hybrid schema.

## 5. Backup

Sebelum migration berisiko, pertimbangkan backup/snapshot sesuai storage capabilities.

Backup tidak boleh dianggap sebagai satu-satunya recovery mechanism.

## 6. Forward Compatibility

Jika binary baru membaca schema lama, migration path harus explicit.

Jika binary lama membaca schema baru, jangan menganggap compatible kecuali memang didefinisikan.

## 7. Unknown Fields

Untuk format seperti JSON/TOML, unknown fields harus mempunyai policy:

- ignore safely
- preserve
- reject

Untuk security-sensitive state, reject dapat lebih aman.

## 8. Enum Evolution

Menambah enum variant dapat merusak binary assumptions.

Reader harus menangani unknown variant secara explicit.

Contoh:

```text
UnknownJobState
UnknownOperationKind
```

Jangan default unknown ke `Completed`/`Failed`.

## 9. State Machine Compatibility

Migration tidak boleh menghasilkan state yang melanggar invariant lifecycle.

Setelah migration, setiap Job/Attempt/Operation harus lolos state validation.

## 10. Journal Compatibility

Journal records harus mempunyai schema/version sendiri bila format berubah.

Recovery harus dapat membaca historical evidence yang valid.

## 11. Audit Compatibility

Audit history sebaiknya immutable.

Schema baru dapat menambahkan event type/field tanpa mengedit historical records.

Reader harus tetap mampu menampilkan historical event secara aman.

## 12. Outbox Compatibility

Pending outbox events adalah durable work.

Upgrade tidak boleh menghapus event hanya karena event schema lama.

Publisher dapat melakukan version translation jika diperlukan.

## 13. Idempotency Record Migration

Idempotency keys/tombstones tidak boleh hilang saat migration.

Jika hilang, duplicate request dapat membuat duplicate Job.

## 14. Lease/Ownership Records

Active claims/leases harus dipertahankan atau secara aman ditandai stale/recovery-required.

Migration tidak boleh mengubah owner menjadi arbitrary new worker.

## 15. Generation Values

Config/Catalog generation harus tetap monotonic atau mempunyai migration mapping yang jelas.

Jangan reset generation ke zero hanya karena schema berubah jika generation digunakan untuk stale-context detection.

## 16. Time Fields

Migration time fields harus mempertahankan semantics:

- wall timestamp
- monotonic duration/relative data
- boot-relative timestamp

Jangan mengubah duration menjadi timestamp tanpa definisi.

## 17. Atomic Schema Upgrade

Idealnya:

```text
schema vN
 ↓ transaction
schema vN+1
```

dan migration marker disimpan durable.

## 18. Migration Marker

Marker membantu startup mengetahui apakah migration:

- belum dimulai
- sedang berjalan
- selesai
- gagal/recovery-required

Jangan menggunakan log sebagai migration marker.

## 19. Interrupted Migration

Jika process mati selama migration, startup harus dapat menentukan state migration dari durable marker/transaction semantics.

Tidak boleh menjalankan normal cleanup dari partially migrated state.

## 20. Migration Lock

Hanya satu migration actor boleh mengubah schema pada satu waktu.

Normal scheduler/worker harus ditahan sampai migration selesai dan validated.

## 21. Protocol Compatibility

IPC protocol version harus dipisahkan dari durable schema.

Client lama dapat berkomunikasi dengan daemon baru hanya jika compatibility matrix mengizinkan.

## 22. Protocol Negotiation

Jika diperlukan, handshake dapat menyatakan:

```text
protocol version
capabilities
feature flags
```

Client tidak boleh menganggap feature tersedia hanya karena binary merespons.

## 23. Feature Flags

New behavior dapat dilindungi feature flag tetapi security/safety invariants tidak boleh dimatikan secara remote melalui arbitrary client flag.

## 24. Plan Compatibility

Persisted Plan harus memiliki plan schema/version.

Jika plan tidak lagi executable pada binary baru:

```text
do not blindly execute
→ revalidate/replan/recovery
```

## 25. Operation Compatibility

Historical OperationId tetap valid sebagai identity setelah upgrade.

New attempt dapat menggunakan executor version baru dengan semantics yang compatible atau melalui explicit migration.

## 26. Executor Version

Audit dapat mencatat executor/binary version yang menjalankan attempt.

Ini penting untuk debugging behavior changes.

## 27. Rollback

Rollback binary tidak selalu aman jika schema sudah migrated forward.

Release policy harus menentukan apakah rollback:

- supported
- supported only before migration
- requires downgrade migration
- unsupported

## 28. No Silent Downgrade

Jangan otomatis mengubah schema baru kembali ke schema lama hanya agar binary lama bisa start.

Downgrade migration harus explicit dan membuktikan tidak ada information loss.

## 29. Mixed-Version State

Jika update terjadi sementara operation aktif, system harus mempunyai deployment contract.

Untuk single daemon/device, paling sederhana:

```text
stop admission
→ safe shutdown/recovery
→ migrate
→ start new binary
```

## 30. Active Operation During Upgrade

Operation yang unresolved tidak boleh dianggap completed hanya karena upgrade terjadi.

Recovery harus membaca durable operation state setelah new binary start.

## 31. Compatibility Matrix

Dokumentasikan:

```text
binary N ↔ schema N
binary N+1 ↔ schema N
binary N+1 ↔ schema N+1
rollback N ↔ schema N+1
```

## 32. Data Retention

Migration tidak boleh membuat historical data grow tanpa batas.

Retention policy harus membedakan:

- active recovery data
- audit history
- idempotency tombstones
- operational metrics

## 33. Destructive Migration

Migration yang membuang field harus mempunyai explicit justification.

Jika field masih diperlukan untuk recovery/audit, jangan drop hanya karena domain model baru tidak menggunakannya.

## 34. Validation After Migration

Minimal validate:

- foreign-key/reference integrity
- state machine validity
- unique identities
- generation consistency
- lease ownership
- operation dependencies
- outbox integrity

## 35. Read-Only Startup

Jika migration/validation belum selesai, daemon dapat start dalam recovery/read-only mode agar operator dapat mendiagnosis tanpa destructive mutation.

## 36. Corrupt Schema

Jika schema version invalid/unknown:

```text
stop destructive execution
→ preserve store
→ report degraded/fatal state
```

## 37. Migration Observability

Migration perlu telemetry:

- from version
- to version
- duration
- records affected
- success/failure
- recovery marker

Jangan log sensitive record contents.

## 38. Testing

Migration test harus mencakup:

- empty database
- large database
- old valid schema
- malformed record
- interrupted migration
- duplicate migration invocation
- rollback attempt
- active operation records
- pending outbox
- idempotency records

## 39. Golden Fixtures

Simpan representative old-schema fixtures untuk memastikan binary baru tetap dapat migrate historical data.

Fixture dapat mencakup edge state yang sulit dibuat oleh current binary.

## 40. Definition of Done

Schema evolution production-ready jika:

- schema version explicit
- migration transactional
- interrupted migration recoverable
- state invariants validated
- journal/audit compatible
- outbox preserved
- idempotency preserved
- lease ownership preserved
- generation semantics preserved
- protocol/schema versions separated
- plan compatibility defined
- rollback policy explicit
- no silent downgrade
- migration observable
- historical fixtures tested

## Final Invariants

1. Binary version bukan schema version.
2. Schema migration terjadi sebelum destructive execution.
3. Migration tidak boleh menghasilkan hybrid invalid state.
4. Interrupted migration harus recoverable.
5. Historical journal/audit evidence tidak boleh hilang.
6. Outbox tidak boleh hilang saat upgrade.
7. Idempotency records tidak boleh hilang sembarangan.
8. Lease ownership tidak boleh berubah tanpa recovery semantics.
9. Generation tidak boleh reset secara sembarang.
10. Unknown enum/state tidak boleh default ke success.
11. Persisted plan harus mempunyai compatibility contract.
12. Historical OperationId tetap stabil.
13. Rollback tidak boleh diasumsikan aman.
14. Downgrade harus explicit.
15. Corrupt/unknown schema fail-closed.
16. Migration state harus durable.
17. Normal worker menunggu migration selesai.
18. Post-migration invariants harus diverifikasi.
19. Migration harus diuji dengan interrupted/crash scenarios.
20. Schema evolution tidak boleh merusak recovery correctness.
