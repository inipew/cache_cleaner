Lanjut. Sekarang kita desain **Config + Target Policy + Profiles**. Ini bagian yang sangat penting karena konfigurasi cleaner tidak boleh berubah menjadi “remote control untuk mematikan safety”.

Prinsip utamanya:

> **Config boleh mengubah kebijakan cleanup, tetapi tidak boleh mengubah security invariant.**

---

# 1. Pisahkan Security Invariant dari Policy

Ini boundary paling penting.

### Tidak boleh dikonfigurasi

```text
follow symlink
cross filesystem boundary
delete arbitrary path
touch locked CE storage
ignore identity change
disable NOFOLLOW
disable authorization
bypass executor validation
delete protected targets
```

### Boleh dikonfigurasi

```text
minimum age
profile
max bytes
max operations
scan budget
target enable/disable
trim enable
F2FS maintenance
ZRAM maintenance
thermal threshold
idle requirement
cleanup interval
user scope
```

Jadi:

```text
                 Config
                   │
                   ▼
              PolicyEngine
                   │
                   ▼
            PolicyDecision
```

tetapi:

```text
Config ─────X────→ SafetyValidator
```

Config tidak punya jalan langsung untuk mematikan Safety.

---

# 2. Jangan membuat config sebagai giant struct

Contoh yang kurang bagus:

```rust
pub struct Config {
    pub age: u64,
    pub deep: bool,
    pub trim: bool,
    pub zram: bool,
    pub thermal: u32,
    pub ...
}
```

Lama-lama menjadi:

```text
Config
 ├── scheduler
 ├── filesystem
 ├── security
 ├── targets
 ├── logging
 ├── kernel
 ├── IPC
 └── 100 boolean
```

Lebih baik dikelompokkan.

```rust
pub struct Config {
    pub version: ConfigVersion,
    pub profile: ProfileConfig,
    pub targets: TargetConfig,
    pub scheduler: SchedulerConfig,
    pub budgets: BudgetConfig,
    pub maintenance: MaintenanceConfig,
    pub logging: LoggingConfig,
}
```

---

# 3. Profile

Saya sarankan tiga profile utama:

```rust
pub enum CleanupProfile {
    Conservative,
    Normal,
    Deep,
}
```

Bukan:

```text
safe = false
```

atau:

```text
dangerous = true
```

Karena `Deep` harus tetap melewati semua Safety validation.

---

# 4. Arti setiap profile

### Conservative

```text
minimum age lebih tinggi
target lebih sedikit
maintenance minimal
budget kecil
```

Cocok untuk automatic cleanup.

### Normal

```text
default
```

Balance antara reclaim dan impact.

### Deep

```text
lebih banyak target
minimum age lebih rendah
budget lebih besar
maintenance tambahan jika diizinkan
```

Tetapi:

```text
Deep ≠ unsafe
```

Contoh:

```text
Symlink
```

tetap reject.

```text
Cross-device
```

tetap reject.

```text
CE locked
```

tetap reject/defer.

---

# 5. Profile sebaiknya bukan kumpulan boolean

Hindari:

```toml
deep = true
aggressive = true
unsafe = true
```

Lebih baik:

```toml
[profile]
name = "normal"
```

Kemudian policy engine memiliki predefined semantics.

Misalnya:

```rust
pub struct ProfilePolicy {
    pub min_age: Duration,
    pub max_bytes: u64,
    pub max_operations: usize,
    pub allow_framework_cache: bool,
    pub allow_package_cache: bool,
}
```

---

# 6. Tetapi user tetap perlu override

Kita bisa:

```toml
[profiles.normal]
min_age = "7d"
max_bytes = "512MiB"

[profiles.deep]
min_age = "1d"
max_bytes = "2GiB"
```

Jadi profile tetap declarative.

---

# 7. Config hierarchy

Saya sarankan:

```text
Built-in defaults
       ↓
config.toml
       ↓
runtime request
       ↓
effective policy
```

Tetapi setiap layer hanya boleh mempersempit atau memilih policy dalam batas aman.

Contoh:

```text
Built-in:
max_bytes = 2 GiB

Config:
max_bytes = 1 GiB

Request:
profile = deep
```

Effective:

```text
profile = deep
max_bytes = 1 GiB
```

Request tidak boleh:

```text
max_bytes = 999999 TiB
```

melewati hard limit.

---

# 8. Hard limits

Ini sangat bagus untuk privileged daemon.

Misalnya:

```rust
pub struct SafetyLimits {
    pub max_plan_operations: usize,
    pub max_plan_bytes: u64,
    pub max_scan_entries: usize,
    pub max_request_size: usize,
}
```

Dan:

```text
effective_limit =
    min(config_limit, hard_limit)
```

Jadi meskipun config rusak:

```text
max_bytes = 1000000000000000000
```

daemon tetap memiliki upper bound.

---

# 9. Budget jangan hanya bytes

Ada empat budget berbeda:

```text
scan budget
operation budget
byte budget
time budget
```

Contoh:

```rust
pub struct BudgetConfig {
    pub max_scan_entries: usize,
    pub max_operations: usize,
    pub max_bytes: u64,
    pub max_duration: Duration,
}
```

Kenapa?

Directory dengan:

```text
1,000,000 files × 1 KB
```

hanya ~1 GB, tetapi scanning-nya sangat mahal.

Sebaliknya:

```text
1 file × 20 GB
```

scan murah, delete impact besar.

---

# 10. Pisahkan scan budget dan delete budget

Ini harus eksplisit.

```text
Scan:
    max_scan_entries
    max_scan_depth
    max_scan_duration

Cleanup:
    max_operations
    max_bytes
    max_duration
```

Karena:

```text
scan terlalu besar
```

dan:

```text
delete terlalu besar
```

adalah dua failure mode berbeda.

# 11. Target configuration

Misalnya:

```toml
[targets]
app_cache = true
app_code_cache = true
package_cache = true
framework_cache = false
temporary = true
```

Tetapi jangan membiarkan:

```toml
[targets]
custom_path = "/"
```

Ini harus **tidak didukung**.

Target harus berasal dari Target Catalog yang trusted.

---

# 12. Config hanya memilih target ID

Lebih aman:

```toml
[targets]
app_cache = true
package_cache = false
framework_cache = false
```

daripada:

```toml
[targets]
paths = [
    "/data/user/0/foo/cache",
    "/data/..."
]
```

Jadi:

```text
config
  ↓
TargetKind / TargetId
  ↓
TargetCatalog
  ↓
trusted root
```

bukan:

```text
config
  ↓
PathBuf
  ↓
delete
```

---

# 13. Exclusion

Exclusion sangat berguna.

Contoh:

```toml
[exclude]
packages = [
    "com.example.important"
]
```

Tetapi exclusion adalah **policy**, bukan safety.

Artinya:

```text
exclude package
    → reject candidate
```

Bukan:

```text
exclude package
    → somehow bypass validation
```

---

# 14. Package exclusion harus exact match

Jangan:

```text
"foo"
```

berarti:

```text
com.foo
com.foo.bar
com.foobar
```

Lebih baik:

```rust
pub struct PackageName(String);
```

dengan validasi package identifier.

Lalu:

```rust
HashSet<PackageName>
```

dan exact lookup.

---

# 15. User exclusion

Karena multi-user:

```toml
[users]
mode = "active"
exclude = [10]
```

atau secara API:

```rust
pub enum UserSelection {
    Active,
    AllEligible,
    Explicit(Vec<UserId>),
}
```

Namun lagi-lagi:

```text
Explicit(10)
```

tidak berarti daemon boleh menyentuh CE yang locked.

Selection ≠ authorization.

---

# 16. Age policy

Config:

```toml
[profiles.normal]
min_age = "7d"
```

Tetapi parser harus menghasilkan:

```rust
Duration
```

bukan string di seluruh code.

Jadi:

```text
"7d"
    ↓
Config parser
    ↓
Duration::from_secs(...)
```

Setelah config validated:

```rust
pub struct ValidatedConfig {
    ...
}
```

tidak ada lagi parsing string.

---

# 17. Jangan gunakan timestamp mentah sebagai trust

Candidate:

```rust
modified_at: SystemTime
```

Policy:

```text
now - modified_at >= min_age
```

Tetapi kalau:

```text
mtime > now
```

jangan menganggap:

```text
age = 0
```

secara diam-diam.

Lebih aman:

```rust
pub enum AgeDecision {
    OldEnough,
    TooYoung,
    InvalidTimestamp,
}
```

`InvalidTimestamp` → reject/defer.

---

# 18. Clock anomaly

Android device bisa mengalami perubahan waktu.

Maka age calculation perlu hati-hati.

Untuk eligibility:

```text
future timestamp
    → not eligible
```

bukan:

```text
abs(now - timestamp)
```

karena itu bisa membuat file timestamp masa depan terlihat “tua”.

---

# 19. Scheduler configuration

Contoh:

```toml
[scheduler]
enabled = true
interval = "6h"
require_screen_off = true
require_idle = true
```

Tapi `require_screen_off = false` tidak boleh otomatis berarti cleaner bebas berjalan kapan saja.

Hard runtime safety tetap berlaku.

---

# 20. Jadi ada dua layer condition

```text
Configurable condition
        +
Hard safety condition
```

Misalnya:

```text
Config:
require_screen_off = false
```

tetapi hard rule:

```text
user interaction active
    → cancel/defer
```

tetap bisa berlaku.

---

# 21. Thermal config

Saya tidak menyarankan user mengkonfigurasi:

```toml
thermal.max = 100
```

secara bebas.

Karena itu bisa menjadi safety bypass.

Lebih baik:

```toml
[scheduler]
thermal_policy = "conservative"
```

dengan predefined behavior:

```text
Normal  → allowed
Warm    → allowed with reduced budget
Hot     → defer/cancel
Critical → immediate cancellation
Unknown → conservative
```

---

# 22. Unknown harus conservative

Rule global:

```text
unknown != safe
```

Contoh:

```text
thermal = Unknown
storage = Unknown
filesystem = Unknown
user state = Unknown
package identity = Unknown
```

Jangan:

```text
Unknown → assume okay
```

Untuk high-impact operation:

```text
Unknown → reject/defer
```

---

# 23. Maintenance configuration

Pisahkan:

```toml
[maintenance]
trim = false
f2fs = false
zram = false
```

dari filesystem cleanup.

Karena:

```text
delete cache
```

dan:

```text
TRIM
F2FS GC
ZRAM maintenance
```

memiliki risk/performance characteristics berbeda.

---

# 24. Deep tidak otomatis mengaktifkan maintenance

Saya lebih menyukai:

```toml
[profiles.deep]
...
```

tetapi:

```toml
[maintenance]
trim = false
f2fs = false
zram = false
```

Kemudian manual request:

```text
clean --deep --trim
```

secara eksplisit meminta maintenance.

Dengan demikian:

```text
Deep
```

tidak memiliki efek tersembunyi besar.

---

# 25. ZRAM harus paling konservatif

ZRAM bukan filesystem cache biasa.

Maka:

```text
cleanup cache
```

boleh otomatis.

Tetapi:

```text
zram maintenance
```

sebaiknya:

```text
manual / explicit
```

dan capability authorization terpisah.

# 26. Config schema version

Wajib:

```toml
version = 1
```

Kemudian:

```rust
pub struct ConfigVersion(pub u16);
```

Saat format berubah:

```text
v1
 ↓
migration
 ↓
v2
```

atau reject jika migration tidak aman.

# 27. Jangan silently accept typo

Ini penting untuk daemon privileged.

Misalnya user menulis:

```toml
[profile]
min_ag = "7d"
```

Jangan:

```text
unknown field → ignored
```

Lebih baik:

```text
configuration invalid:
unknown field `min_ag`
```

dan daemon tetap menggunakan config lama.

# 28. Config reload

Flow:

```text
SIGHUP / IPC reload
        ↓
read file
        ↓
parse
        ↓
schema validation
        ↓
semantic validation
        ↓
build ValidatedConfig
        ↓
atomic swap
```

Jika gagal:

```text
old config remains active
```

Ini jauh lebih aman daripada:

```text
config = broken config
```

---

# 29. Config generation

Setiap config memiliki:

```rust
pub struct ConfigSnapshot {
    pub generation: u64,
    pub config: Arc<ValidatedConfig>,
}
```

Job mengambil snapshot:

```text
Job #123
config generation = 17
```

Jika reload:

```text
generation = 18
```

job #123 tidak tiba-tiba berubah di tengah planning.

Job berikutnya menggunakan:

```text
generation = 18
```

---

# 30. Ini penting untuk reproducibility

Bayangkan:

```text
10:00
scan menggunakan age = 7d

10:01
config reload
age = 30d

10:02
executor menjalankan plan lama
```

Kalau policy config mutable reference dipakai sembarangan, hasil bisa membingungkan.

Dengan snapshot:

```text
Job #123
    ConfigGeneration 17
    ↓
scan
    ↓
policy
    ↓
plan
    ↓
execute
```

seluruh job konsisten.

# 31. `EffectivePolicy`

Jangan passing seluruh `Config` ke semua module.

Buat:

```rust
pub struct EffectivePolicy {
    pub profile: CleanupProfile,
    pub targets: TargetSelection,
    pub age: AgePolicy,
    pub budget: Budget,
    pub runtime: RuntimePolicy,
    pub maintenance: MaintenancePolicy,
}
```

Kemudian PolicyEngine menerima:

```rust
evaluate_candidate(
    &candidate,
    &effective_policy,
    &context,
)
```

---

# 32. Config → EffectivePolicy

Pipeline:

```text
Raw TOML
   ↓
ParsedConfig
   ↓
ValidatedConfig
   ↓
Profile selection
   ↓
Target selection
   ↓
EffectivePolicy
```

Jangan:

```text
Candidate
   ↓
parse TOML
```

Itu akan membuat policy logic kacau.

# 33. Semantic validation

Schema validation belum cukup.

Misalnya:

```toml
max_bytes = "10MiB"
min_age = "30d"
```

secara sintaks valid.

Tetapi mungkin:

```text
max_operations = 0
```

atau:

```text
max_scan_entries = 0
```

yang secara semantic tidak berguna.

Validator harus memastikan:

```text
> 0
≤ hard limit
compatible combination
```

Contoh:


dan:


# 37. Config permissions

Karena config mengontrol privileged daemon:

```text
config.toml
```

harus dianggap security-sensitive.

Minimal:

```text
owner = trusted uid
mode = restrictive
```

Sebelum load:

```text
open
↓
validate ownership/mode
↓
read
↓
parse
```

Jangan menjalankan:

```text
chmod config
```

secara otomatis untuk "memperbaiki".

# 38. Config symlink juga harus ditolak

Jangan:

Gunakan prinsip filesystem safety yang sama:

```text

```

# 42. Final boundary

Arsitektur sekarang menjadi:

```text
                 config.toml
                      │
                      ▼
                 ConfigLoader
                      │
                      ▼
                ConfigValidator
                      │
                      ▼
              ValidatedConfig
                      │
             ┌────────┴────────┐
             ▼                 ▼
        Scheduler         PolicyEngine
                               │
                               ▼
                       EffectivePolicy
                               │
                         Candidate
                               │
                               ▼
                         PolicyDecision
```

Dan yang paling penting:

```text
Config
   │
   ├── boleh mengubah policy
   │
   └── TIDAK boleh mematikan:
          ├── NOFOLLOW
          ├── device boundary
          ├── identity validation
          ├── CE lock protection
          ├── authorization
          ├── plan validation
          └── executor revalidation
```
