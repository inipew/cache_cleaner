# 689. `O_NOFOLLOW` tidak cukup untuk seluruh path

Ini sangat penting.

`O_NOFOLLOW` melindungi **final component**, bukan seluruh traversal path. Linux path resolution secara umum dapat mengikuti symlink pada parent components. `openat2()` menyediakan `RESOLVE_NO_SYMLINKS` untuk melarang resolusi symlink pada seluruh path, dan `RESOLVE_NO_XDEV` untuk melarang crossing mount points. ([man7.org][1])

Karena itu ada dua mode.

### Mode A — fallback

```text id="q7m2x4"
openat()
+
O_NOFOLLOW
+
FD-by-FD traversal
+
fstatat(NO_FOLLOW)
+
device validation
```

### Mode B — hardening

```text id="m8p3r1"
openat2()
+
RESOLVE_BENEATH
+
RESOLVE_NO_SYMLINKS
+
RESOLVE_NO_MAGICLINKS
+
RESOLVE_NO_XDEV
```

---

# 690. `openat2()` bukan sekadar convenience

`RESOLVE_BENEATH` memastikan resolution tetap descendant dari `dirfd`; `RESOLVE_NO_SYMLINKS` melarang resolusi symlink; `RESOLVE_NO_XDEV` melarang crossing mount point. `openat2()` tersedia sejak Linux 5.6. ([man7.org][1])

Tetapi Android deployment kita mencakup versi kernel yang berbeda.

Jadi:

```text id="p3x8m2"
capability detect
      │
 ┌────┴────┐
 │         │
yes       no
 │         │
openat2   secure fallback
```

---

# 691. Fallback bukan “less secure mode”

Ini penting.

Jangan desain:

```text id="x7m2q4"

```

Fallback harus tetap mempertahankan invariant:

```text id="m5r8p1"

no symlink traversal

trusted root

```

`openat2()` adalah hardening tambahan, bukan permission untuk menjadi ceroboh jika tidak tersedia.

# 701. `unlinkat`

Untuk file:

```rust id="m8r2x4"
unlinkat(parent_fd, name, 0)
```

Untuk empty directory:

```rust id="q3p7n1"
unlinkat(parent_fd, name, AT_REMOVEDIR)
```

`unlinkat()` melakukan operasi relatif terhadap directory FD; `AT_REMOVEDIR` membedakan removal directory dari normal unlink. ([man7.org][3])

---

# 702. Symlink pada final component

Ada nuance penting:

`unlink()`/`unlinkat()` menghapus **directory entry** yang bernama itu; jika entry tersebut adalah symlink, ia tidak mengikuti target symlink. ([man7.org][3])

Namun cleaner tetap **harus reject symlink sebelum unlink**.

Kenapa?

Karena policy kita mengatakan:

```text id="m5x8q2"
symlink = unsupported object
```

bukan:

```text id="p7r3n1"
symlink = allowed because unlink won't follow it
```

Security invariant dan semantic policy harus konsisten.

---

# 703. TOCTOU utama

Urutan:

```text id="x4m8q2"
T0:
fstatat(name)
→ inode 100

T1:
attacker/process replaces name

T2:
unlinkat(name)
```

`unlinkat()` bekerja berdasarkan **nama directory entry saat syscall dilakukan**, bukan handle ke inode yang sebelumnya di-stat.

Jadi identity check sebelumnya tidak membuat sequence tersebut atomik.

# 704. Apakah desain kita race-proof?

**Tidak.**

Dan jangan pernah mendokumentasikannya sebagai race-proof.

Kita bisa membuatnya:

```text id="m7p2r5"
+
fail-closed
+
namespace-confined
```

tetapi bukan:

```text id="q8x3n1"

```

Linux tidak menyediakan generic “unlink exactly this inode referenced by this open FD” primitive yang menyelesaikan semua kasus tersebut.

# 705. Kenapa masih cukup kuat?

Karena attacker/process tidak bisa begitu saja mengubah:

```text id="p4m8x2"

```

menjadi:

```text id="n7q3r1"

```

Kita sudah membatasi:

```text id="m3x8p2"

+
no ..
+

+
expected type
+

```

Jika object berubah, sebagian besar perubahan akan menghasilkan reject atau setidaknya operasi terbatas pada directory entry yang memang sedang diproses.

# 706. `openat2()` memperkuat traversal

Untuk path resolution multi-component, bila tersedia:

```text id="q8m2r4"
openat2(
    root_fd,
    relative_path,
    RESOLVE_BENEATH |
    RESOLVE_NO_SYMLINKS |
    RESOLVE_NO_MAGICLINKS |
    RESOLVE_NO_XDEV
)
```

`RESOLVE_BENEATH` membatasi resolution terhadap root; `RESOLVE_NO_MAGICLINKS` mencegah magic-link resolution; `RESOLVE_NO_XDEV` melarang mount crossing. ([man7.org][1])

---

# 707. `RESOLVE_NO_XDEV` vs `st_dev`

Keduanya berguna tetapi berbeda.

`RESOLVE_NO_XDEV`:

```text id="m7x3p2"
mencegah mount crossing saat path resolution
```

`st_dev`:

```text id="q4r8n1"
memvalidasi identity filesystem object
```

Jangan membuang salah satunya hanya karena yang lain tersedia.

---

# 708. Bind mount nuance

`RESOLVE_NO_XDEV` juga memblokir crossing mount point termasuk bind mount. Dokumentasi Linux bahkan mencatat bahwa ini dapat menyebabkan failure pada path yang memang secara normal menggunakan bind mount. ([man7.org][1])

Untuk cleaner kita justru cenderung **menerima false negative** tersebut.

Lebih baik:

```text id="x8m2q4"
skip target
```

daripada:

```text id="p3r7n1"
cross boundary unexpectedly
```

## Posisi architecture sekarang

Kita sudah punya hampir semua security-critical boundary:

```text id="n5m8q2"
                    Runtime
                       │
                    Scheduler
                       │
              ┌────────┴────────┐
              │                 │
          Platform           Kernel
              │                 │
              └───────┬─────────┘
                      ▼
                  TargetCatalog
                      │
                      ▼
                   Scanner
                      │
                      ▼
                    Safety
                      │
                      ▼
                    Policy
                      │
                      ▼
                   Planner
                      │
                      ▼
                Authorization
                      │
                      ▼
                 AuthorizedPlan
                      │
                      ▼
                  Executor
                      │
                      ▼
                     fs
                      │
                 Linux syscalls
```

**Tahap berikutnya yang paling tepat adalah `ipc/`**, karena setelah security boundary filesystem selesai, kita perlu memastikan tidak ada jalan dari luar yang bisa menyuntikkan `PathBuf`, target arbitrary, profile palsu, atau capability palsu ke pipeline.

Di sana kita akan desain **binary protocol, framing anti-DoS, request/response IDs, `SO_PEERCRED`, Root/System/Shell RBAC, capability matrix, request cancellation, bounded payload, versioning, dan lifecycle `UDS → Authorization → Scheduler`**.
